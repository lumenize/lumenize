# Broadcast

`this.lmz.broadcast(targets, remote, options?)` sends one continuation to many `(bindingName, instanceName)` targets: one `this.lmz.call(...)` per target, made by the node that decided to push. Every mesh node's `this.lmz` carries it — a [LumenizeDO](./lumenize-do), a [LumenizeWorker](./lumenize-worker) and a [LumenizeClient](./lumenize-client).

It is the loop in [Making Calls § Breaking Call Chains](./calls#breaking-call-chains), with drop-on-failed-fanout cleanup built in. That helper passes `newChain: true`; `broadcast` inherits the caller's chain unless you pass the same option.

## Basic Usage

```typescript @skip-check
import { LumenizeDO } from '@lumenize/mesh';

class RoomDO extends LumenizeDO<Env> {
  @mesh()
  postMessage(text: string) {
    this.ctx.storage.kv.put(`msg:${Date.now()}`, text);
    const subscribers: Set<string> = this.ctx.storage.kv.get('subscribers') ?? new Set();

    // Build the list of targets and the continuation. Each subscriber's
    // Gateway gets the same `handleMessage` call.
    const targets = [...subscribers].map(clientId => ({
      bindingName: 'LUMENIZE_CLIENT_GATEWAY',
      instanceName: clientId,
    }));
    this.lmz.broadcast(targets, this.ctn<RoomClient>().handleMessage(text));
  }
}
```

That's it for the success path. Every delivery comes from `RoomDO` at any number of targets, so a receiver that checks who called it sees the node that pushed.

## Options

```typescript @check-example('packages/mesh/src/broadcast.ts')
export interface BroadcastOptions extends Pick<CallOptions, 'newChain' | 'state'> {
  onResult?: AnyContinuation;
}
```

- **`onResult`** — a handler that hears failed deliveries. See [Result Handling](#result-handling-drop-on-failed-fanout) below.
- **`newChain`** — `true` starts a fresh chain at this node for each target, carrying no `originAuth`. By default each target inherits the caller's chain with this node appended, exactly as a [`call()`](./mesh-api#calloptions) does.
- **`state`** — seeds or merges `callContext.state` for each target, as on `call()`.

## Result Handling (Drop-on-Failed-Fanout)

For drop-on-failed-fanout cleanup, pass a partial continuation as `onResult`. The framework completes it by appending the per-target result via the standard last-argument convention (same mechanism the 4-arg `lmz.call` form uses):

```typescript @skip-check
class RoomDO extends LumenizeDO<Env> {
  @mesh()
  postMessage(text: string) {
    const subscribers: Set<string> = this.ctx.storage.kv.get('subscribers') ?? new Set();
    const targets = [...subscribers].map(clientId => ({
      bindingName: 'LUMENIZE_CLIENT_GATEWAY',
      instanceName: clientId,
    }));

    this.lmz.broadcast(targets, this.ctn<RoomClient>().handleMessage(text), {
      onResult: this.ctn<this>().onMessageDelivered(),
    });
  }

  // No `@mesh()` — a Gateway answers inside its ack, so this runs on this node's own dispatch,
  // where the member-level check is off. Adding one would make this reaper callable as an ordinary
  // request, with caller-chosen arguments; only the framework-supplied callee makes that harmless.
  onMessageDelivered(result?: unknown): void {
    if (result instanceof Error && result.name === 'ClientDisconnectedError') {
      const clientId = this.lmz.callContext.callee?.instanceName;
      if (clientId) {
        const subscribers: Set<string> = this.ctx.storage.kv.get('subscribers') ?? new Set();
        subscribers.delete(clientId);
        this.ctx.storage.kv.put('subscribers', subscribers);
      }
    }
  }
}
```

The handler's `result` argument is appended automatically. For failed Gateway deliveries the result is a `ClientDisconnectedError`, and WHICH subscriber dropped comes from `this.lmz.callContext.callee` — the address the framework sent that push to. It is deliberately not on the error: a reply is authored by the far side, so a field there could name anyone.

:::warning[`callee` names the failing target only when the handler runs on the broadcaster's dispatch]

A Gateway answers a push inside its acknowledgement, and so does any target that refuses the call at admission. For those, the handler runs on the broadcaster's own dispatch and `callee` is the target — which is the case drop-on-failed-fanout cleanup reads. A DO or Worker that accepts the call and throws afterwards fires its Error back to the broadcaster instead, and there `callee` names the broadcaster itself.

:::

:::warning[Errors-only handler dispatch]

`onResult` is invoked **only on Error**. Successful per-target deliveries silently drop the result; the handler is never dispatched in that case. `broadcast` adds [`lmz.call`'s `onErrorOnly` option](/docs/mesh/mesh-api#calloptions) to every call whenever you pass an `onResult`.

For the dominant use case — drop-on-failed-fanout cleanup — this is exactly the desired behavior. It also avoids a structural latency cost on Cloudflare workerd: success-path handler chains attached to outbound subrequests appear to keep the originating invocation alive until they settle, which adds up to hundreds of milliseconds of wall-clock RT to the originator at high N. Skipping them is both correct and faster.

If you have a real need for success callbacks, file an issue; the design accommodates a future `fireOn: 'always' | 'error'` option on `BroadcastOptions`.

:::

## Limits

- **Every target gets the same continuation.** If each subscriber needs a different payload, you're sending N calls, not broadcasting — write the loop directly with `this.lmz.call(...)`.
- **No success callbacks**: see the warning above — `onResult` is errors-only.
- **Tail latency grows with the number of targets.** Each target is its own call from one node, so the last subscriber of a large broadcast waits longest. An earlier release handed long lists to a recursive Worker tier that cut that tail; it was removed because its deliveries came from the tier rather than from the node that pushed.
- **No per-target catch.** On a DO or Worker, a target whose binding does not route throws synchronously and stops the loop there, so a misconfigured address fails loudly at the first one. Store each target's binding from a source the client cannot write.
- **From a client, targets past 100 can be lost.** A client's calls wait in a queue while its socket is down or it is refreshing a token about to expire, and the queue holds 100. A broadcast to more targets than that, in one of those windows, drops the rest, and `onResult` never hears about them.

## Implementation

```typescript @check-example('packages/mesh/src/broadcast.ts')
const { onResult, ...passedThrough } = options;
const callOptions: CallOptions = { ...passedThrough };
if (onResult) callOptions.onErrorOnly = true;
for (const t of targets) {
  lmz.call(t.bindingName, t.instanceName, remote, onResult, callOptions);
}
```

The same function backs every node's `broadcast`: it reads nothing from the node but its `lmz.call`.
