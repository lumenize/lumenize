**Notes:**

- **→ Arrows:** the left side is what the current release does, and the right side is where it is heading. Workers RPC plans to drop cycles and aliases, and Cap'n Web's `RegExp` support is merged but not yet released. The Cap'n Web column reflects capnweb 0.12.0, and a [test](https://github.com/lumenize/lumenize/blob/main/doc-test/rpc/capn-web-comparison-basics-and-types/test/type-support-table.test.ts) re-checks every cell in it against the installed version.
- **⚠️ Errors before compatibility date 2026-04-21:** the Workers RPC and DO Storage cells assume that date or later, when the `enhanced_error_serialization` flag turns on by default. Before it, both drop a custom error's `name` and custom properties, and a thrown one arrives as a plain `Error` with its class name inside the message (`"CustomError: boom"`) and no `cause`.
- **⚠️ Map/Set with Object Keys/Values:** While `Map` and `Set` are fully supported, object identity behavior depends on serialization boundaries:
  - **Identity preserved**: Within a single RPC call (Workers RPC, `@lumenize/rpc`) or single `stringify()`/`parse()` cycle
  - **Identity lost**: Across separate storage operations (DO Storage `put()`/`get()`)
  
  See [Map and Set Behavior](/docs/structured-clone/maps-and-sets) for detailed explanation and patterns.
- **❌ Types read with `await`:** `stringify()` and `parse()` are synchronous, like `structuredClone()` itself, and they also run in browsers, where a page can reach a `Blob`'s bytes, a `Request` or `Response` body, a stream's contents, or a `CryptoKey`'s key material only through a Promise. So Lumenize doesn't carry them. Where another column shows ✅, it's the runtime handling the type natively, or Cap'n Web, whose calls are asynchronous anyway. For requests and responses, [`RequestSync` and `ResponseSync`](/docs/structured-clone#web-api-objects-example) hold a body that has already been read, so they serialize like any other value.
- **❌ CryptoKey:** Browsers and Node can structured-clone a `CryptoKey`, but workerd can't, so Workers RPC and DO Storage throw `DataCloneError`. Lumenize throws the same error, for the reason in the note above, and `exportKey()` refuses a key created with `extractable: false` altogether. To move or persist a key, create it with `extractable: true`, send or store `await crypto.subtle.exportKey('jwk', key)`, and `crypto.subtle.importKey()` it on the other side.
