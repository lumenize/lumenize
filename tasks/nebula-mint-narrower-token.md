**Objective — an endpoint whose name says what it does, and which only lets an admin impersonate someone whose access they already hold in full.**

Two changes drive it: the **vocabulary** (`delegated` / `actFor` / "act as" are re-derived on sight) and the **invariant** (the endpoint today mints a token that is not narrower at all — it wears the subject's `sub` while acting with **admin-derived** authority the subject may not have). Two consequences fall out of making the invariant true, and are why this reaches beyond `nebula-auth`: the claims must describe **two people** (Phase 3), and an impersonated destructive action must record **who drove it** (Phase 4).

## Context and current state

`POST /auth/{callerScope}/delegated-token`, body `{ actFor, activeScope }`, handled by `handleDelegatedToken` ([worker-token.ts](../packages/nebula-auth/src/worker-token.ts)). Registered in the router's `AUTHENTICATED_SUFFIXES`.

**The use case — an admin impersonating a user.** An admin narrows to a specific person's fine-grained orgTree permissions so they can interact with a Star **the way that user does** — the direct path to "why can't this user do X?". The minted token is `sub` = the user, `act` = the admin. That is the whole feature; everything below exists to make it safe and to make the token a faithful view of the user's access rather than the admin's.

**Gates today, in order** — referred to by these numbers throughout: **(1)** caller's token carries no `act` chain (no re-delegation) · **(2)** `matchAccess(caller.authScopePattern, activeScope)` · **(3)** `caller.access.admin === true` · **(4)** `getIdentityScope(actFor)` resolves. ⚠️ **Nothing constrains *which* subject** — `getIdentityScope` resolves by `sub` across the entire registry.

**What it mints:** `sub` ← `actFor` (the subject) · `profileId` ← **the subject's** · `act.sub` ← the caller · `admin` ← the **caller's** bit · `authScopePattern` ← derived from the **requested** `activeScope`.

**Callers:** none in production (`apps/nebula/src`, Studio UI); the admin-debug flow that will use it is a Non-goal here. One test helper, `mintDelegatedToken` (`apps/nebula/test/test-helpers.ts:488`), renamed in Phase 1. ⚠️ **It survives** — Phase 2 retires its only *current* caller, and Phase 3 becomes its caller: it is the only path in `apps/nebula` to an endpoint-minted narrower token, which `packages/nebula-auth` cannot supply.

**This endpoint is the only producer of a JWT `act` claim.** The builder is [access-claims.ts:114](../packages/nebula-auth/src/access-claims.ts); its two callers are this handler — the only **production** actor-passing path — and `create-nebula-test-token.ts`, whose `actorSub?` option exists solely to build gate-1's fixture. ⚠️ The claim is **read** outside `nebula-auth` — [resources.ts:164](../apps/nebula/src/resources.ts) `#buildChangedBy` persists it — so the claim's *shape* is not contained to one package even though its *construction* is (Phase 3).

**There is one branch.** A second — the subject pre-authorizing an actor via an `AuthorizedActors` table — was cut in the surrogate-`sub` wipe; only two comments record it. Nothing to carry forward.

## Design intent, constraints, and future state

**Two rules, and a consequence that falls out of them.**

> **1. Eligibility — you may only impersonate someone you already administer *entirely*.** The caller must hold `admin` **and** a pattern covering **the subject's scope**: `hasAdminOverScope(caller.access, subjectIdentity.universeGalaxyStarId)`. A caller narrower than the subject in *either* scope or the `admin` bit is refused outright. And the subject must be somebody else.
>
> **2. Faithfulness — the minted token mirrors that person's access, not the caller's.** The subject's `admin` bit, the subject's reach, bounded to the requested `activeScope`.
>
> **⇒ Therefore no minted token can exceed the caller.** Eligibility (1) has already placed the subject's entire scope inside the caller's authority, so the mirror that faithfulness (2) produces can only ever be **narrower** than the caller's own token. **Escalation-safety is a consequence of the two rules, not a third property to maintain separately.**

**Why faithfulness is the change that matters.** Today the token carries `sub` = subject *and* the **caller's** `admin` bit. In [dag-tree.ts:186](../apps/nebula/src/dag-tree.ts) the scope-admin bypass fires off `access`, so `resolvePermission(view, sub, …)` is **never consulted** — the token wears the subject's name while acting with admin-derived authority the subject may not have. That defeats the use case at its root: you cannot see *why* a user is denied something through a token that bypasses the denial. Mirroring the subject's `admin` bit is what puts `resolvePermission` back in the decision. It also stops every `sub`-keyed side effect from recording the subject while the authority driving it was the caller's.

✅ **Why eligibility is sufficient — and the one condition that would reopen it.** Eligibility bounds the caller against the **subject's scope**, so it guarantees the caller administers every host at or below that scope. What a token can actually *reach* is its `aud` **and that aud's ancestors** — [nebula-do.ts:128-135](../apps/nebula/src/nebula-do.ts) `enforceScopeReach`'s tenant branch admits a caller whose `aud` sits below a node. An **ancestor** host is therefore one eligibility does not cover: there the scope-admin bypass does not fire, and authority would fall to `resolvePermission` on the **subject's** grants.

**Today that gap is empty, and the change that opens it also closes it.** The only DAG-deciding hosts are star-tier and reachable solely as their own `aud`, so no impersonating token reaches one as an ancestor. The Galaxy collapse is what creates the first ancestor host — and it carries the closure in the same phase: the Galaxy's Session/Message plane is composed `scopeAdminOnly`, so `setPermission` throws, no grant can exist, and the scope-admin bypass is the sole path ([nebula-galaxy-collapse-and-chat.md](nebula-galaxy-collapse-and-chat.md) Phase 1 — moved there 2026-07-28 because the hazard does not exist before it). That matches the decision that file already records: a collaborator **enrolls as a Galaxy admin**, and the less-privileged non-admin tier is deferred. ⚠️ **Nothing in THIS task depends on it** — it is stated here because this is where the reasoning lives, not because it is work to do here.

⚠️ **The deferred non-admin collaborator tier is the condition under which this must be re-derived — it does not automatically reopen the path.** Whether it does depends on where those identities are **scoped relative to the host they are granted on.** Scope them *at* the host — enrolled at `{u}.{g}`, granted on `{u}.{g}` — and it stays closed: eligibility over them requires a pattern covering `{u}.{g}`, so every eligible caller administers the host and already holds *more* with their own token than the mirror gives them. Scope them *below* it — enrolled at `{u}.{g}.dev`, granted on `{u}.{g}` — and it opens: a `{u}.{g}.dev` star admin satisfies eligibility, does not administer the Galaxy, and with their own token would resolve only their own grants there. **Design constraint for whoever builds that tier: grant a person only on hosts at or below their own scope.** Do **not** pre-emptively tighten `enforceScopeReach` in either case — that is admission, not authority (ADR-015 §3), and narrowing it breaks legitimate tenant-facing upward reads.

**The profile is not on this lattice at all.** A `profileId` is a **global** object ([ADR-012](../docs/adr/012-global-profile-visibility.md)), outside the scope tree, so administering someone's scope says nothing about their profile — eligibility neither grants nor denies anything there. Its rule is separate and absolute: **a delegated token is never an *owner*** (below). ⚠️ Admin-derived profile authority does survive via `profile.ts` branches (3)/(4), bounded by the mirrored `admin` bit and the minted pattern; branch (4) dies with ADR-012's amendment — see Phase 3's ⚠️.

### The claims describe two people, so say so

The token's claims answer two different questions — *whose access is this?* and *who is driving?* — and one `profileId` field cannot answer both. RFC 8693 already has the shape: top-level claims pertain to the **subject**, and `act` is a JSON object whose members are claims identifying the **actor**.

```jsonc
{ "sub": "sub-xyz…", "profileId": "profile-xyz…",          // the subject — whose access this is
  "act": { "sub": "sub-abc…", "profileId": "profile-abc…" } // the caller — who is driving
}
```

The invariant this keeps: **top-level `sub` and top-level `profileId` always describe the same person.** [query-subscriptions.ts:143](../apps/nebula/src/query-subscriptions.ts) persists that pair into the `QuerySubscribers` roster and [resource-data-plane.ts](../apps/nebula/src/resource-data-plane.ts) `#rosterFor` broadcasts it, so keeping the pair coherent means those consumers need **no change**. It is also the position [nebula-galaxy-collapse-and-chat.md](nebula-galaxy-collapse-and-chat.md) took for attribution: *authorization keys off the authority `sub`, never `act`; the display shows both.*

⚠️ **The presence roster captures no actor.** `QuerySubscribers` → `#rosterFor` holds `{ sub, profileId }` and no `act` column, so a narrower token makes the *subject* appear actively subscribed with no sign it was delegated. Note the reach: this is **every query subscription on every data-plane host** (`star.ts` and `dev-studio.ts` both broadcast it), not just chat. (The per-resource `Subscribers` table carries no `profileId` and feeds no roster, so it is unaffected.) Accepted; see Decisions.

**A delegated token is never an owner.** The Profile DO's instance name *is* the `profileId`, so `#requireOwnerOrAdmin`'s owner branch is a zero-read equality: `claims.profileId === <this profile>`. Under impersonation the token carries the **subject's** `profileId` — so branch (1) **matches**, and without a further check the admin driving it owns that person's profile: writing their public fields and reading their `privateNotes`. One clause closes it:

```typescript
// (1) Owner — the JWT's own profileId equals this instance, AND the token is not delegated.
if (claims?.profileId && claims.profileId === profileId && !claims.act) return;
```

It tests only that the token *is* delegated, never who the actor is. ⚠️ **Record this as ADR-012 does — a deliberate EXCEPTION to `security.md`'s read-side rule, not an application of it.** It is the one place where the presence of `act` changes an authz outcome, licensed by *global*: a manufactured scope contains nothing of the victim's except a global object. Do not write "the rule holds" into standing guidance — ADR-012 and the always-loaded `workflow.md:72` one-liner both say the opposite, and softening it dissolves a bright line into a general "presence is fine" licence. ⚠️ **The invariant is *an admin-driven session is never an owner*** — **not** "the two subs are different people": `#mintIdentity` keys on (email, scope), so one human legitimately holds several `sub`s, and `foundStarAndLogin` provisions a universe owner and a star founder under the **same email by construction**. Stating it the other way invites comparing `act.profileId`, which would read the chain's identity for an authz decision.

**Delegation depth stays ≤ 1 here, deliberately.** `ActClaim` is recursive (`act?: ActClaim`) per RFC 8693 §4.1, and the repo's model adopts the nesting direction (outermost = current). This mint never nests: gate 1 rejects a caller whose token already carries `act`, and the builder writes a flat actor. Both mechanisms are load-bearing — keep them. ⚠️ **Depth ≤ 1 is a property of THIS mint, not of the system.** A separate operation — the platform **prepending itself as an additional actor** when it writes on a person's behalf (Studio's agent turn records `changedBy = { sub: human, act: { sub: Nebula } }`, via the `prependActor` helper the Galaxy collapse plans) — **does** nest, outermost-is-current. That is why Phase 3's `#buildChangedBy` projection must be **recursive**: a one-level projection passes every fixture this endpoint can produce and still leaks `profileId` at depth ≥ 2.

**Naming principle:** the request parameters are the **token fields the caller is asking for**, named so no reader has to hold a mapping. `subOfNarrowerToken` is the minted token's `sub`; `activeScope` is its `activeScope`/`aud` and the source of its derived pattern. The actor is always the caller, taken from the Bearer token, so it is never a parameter. ⚠️ Do **not** reintroduce `actFor`, "delegated", or "act as" in prose, symbols, or comments.

## Decisions

| Decision | Rejected alternative — why |
|---|---|
| Endpoint `/mint-narrower-token`, handler **`mintNarrowerToken`** | Keeping `/delegated-token` / `handleDelegatedToken`. The rename costs a one-time sweep; the confusing name costs reviewer re-derivation every session it comes up. Sibling handlers are `handleX`, but this one sits beside `mintAccessToken` in the same file and "handle" adds nothing. |
| Body `{ subOfNarrowerToken, activeScope }` | `{ actFor, activeScope }`. Also rejected: bare `{ sub }` — correct but ambiguous at the call site, where the caller's own `sub` is also in scope. |
| **Reject self-narrowing** — `subOfNarrowerToken === caller sub` → 400 | Permitting it. There is no second party, so `act: { sub: X }` on a token whose `sub` is `X` records nothing; it pollutes attribution, muddies `!claims.act`, and leaves a token re-narrowable past gate 1. |
| **Eligibility is the rule** — `hasAdminOverScope(caller.access, subjectIdentity.universeGalaxyStarId)`, run **before the scope mirror** | Leaving the subject unbounded: any admin could mint for any identity in any universe. Its uniquely load-bearing case is **upward** — caller pattern `{u}.{g}.*`, the subject's scope `{u}`, `activeScope = {u}.{g}` satisfies every other check, and only this one stops a lower admin wearing a superior's identity (ADR-015 §2, "upward is nil"). **Ordering matters:** a faithfulness bound can pass while eligibility fails, so running one first would tell a caller who is about to be refused **where the subject sits in the tree** — across a Star boundary ADR-008 bounds visibility to. (Subject *existence* is disclosed either way by gate 4's 404, which is pre-existing and unchanged.) Neither 403 body may name the subject's scope; echo the caller's own pattern or nothing. |
| **`admin` ← `caller.admin && subject.isAdmin`** (faithfulness) | The caller's bit alone — it makes the token act with admin-derived authority the subject may not have, so `dag-tree.ts:186`'s bypass fires and the denial you came to observe never happens. Also rejected: the **subject's** bit alone — `security.md` rule (2) forbids copying it, because a copy can exceed the caller. Under eligibility the conjunction *equals* the subject's bit, so the `&&` is belt-and-braces against a future caller reaching this line without eligibility having run. |
| **`activeScope` bounded by the subject's reach** (faithfulness) | Bounding it by the caller alone. A subject whose scope is `{u}.{g}.{s1}` would otherwise get a token admin over all of `{u}.{g}` — inside the caller's authority, so not an escalation, but **not a mirror of that person** either, which is the property the use case needs. |
| **Actor pair — `act: { sub, profileId? }`, subject's pair stays top-level** | The caller's `profileId` top-level: it makes top-level `sub` and `profileId` name different people, silently corrupting the `QuerySubscribers` roster and every future `{sub → profileId}` consumer. Also rejected: `{ subProfileId, act: { subProfileId } }` — invents vocabulary and abandons the `profileId` claim name consumers already read; and `profileIds: [a, b]` — an array loses which-is-which and cannot express a chain. |
| **`#buildChangedBy` projects `act` down RECURSIVELY to `{ sub, act? }`** | Letting the widened claim reach the persisted `Snapshots.changedBy` — it would land `act.profileId` in storage with no wiring, under a type that cannot declare it (ADR-001), and change the same-actor coalesce key at `resources.ts:212`. Also rejected: a **one-level** projection — `{ sub: a.sub, ...(a.act && { act: a.act }) }` re-admits `profileId` at depth ≥ 2, nothing catches it (spread of a variable ⇒ no excess-property check), and no criterion can red it while every producer here is flat. That is a guard resting on today's producers (`calibration.md` §4); the recursive form costs the same. |
| **`!claims.act` on the Profile owner branch** — a delegated token is never an owner | Letting the subject's `profileId` claim confer profile write to whoever holds the token, which hands an admin unilaterally and without consent what ADR-012's amendment removed. Also rejected, both because they read the chain's *identity* to decide authz (rule (1)): `!claims.act \|\| claims.act.sub === claims.sub`, and `\|\| claims.act.profileId === claims.profileId`. |
| **Impersonation carries the subject's authority everywhere, including destructive registry ops** | Gating `delete-scope`/`delete-scope-plan` against act-bearing tokens. Authz keys off `sub`; `act` is traceability (`security.md` rule (1)) — if the subject may do it, so may an admin impersonating them. ⚠️ `nebula-auth-registry.ts:911`'s comment reads like a revocation gate (*"a just-removed admin … must not be able to wipe a shared scope"*), but the check it guards is **warning integrity**: `#affectedUsers`'s own JSDoc says the fail-closed exists because *"a null there would silently under-count and make the warning lie."* A 15-minute post-revocation window is the accepted posture repo-wide (`security.md`). Phase 4 fixes the comment. |
| **The `Scope deleted` record carries the ACTOR** | Recording `callerSub` alone — under impersonation that is the subject, so the record names the person acted upon as the person who acted. [ADR-016](../docs/adr/016-record-the-acting-principal.md) generalizes this; only this one site is in scope here. |
| **Presence shows the subject, not the actor** | Adding `actSub`/`actProfileId` to `QuerySubscribers` now, or storing the whole claims object per subscription. Two reasons to wait, neither of them payload size. **(1) The table deliberately stores a VERDICT, not a claim** — `subscriptions.ts:71-73` explains why `accessAdmin` is a stored verdict (*"the push path never re-reads the JWT"*, sound under ADR-013 because it is monotonically narrowing); a full claim beside it would contradict its neighbour. **(2) Presence is a LIVE fact, not history** — a subscriber row asserts "here **now**" and outlives the token that made it (refresh remints every 15 min), so a stored `exp`/`iat`/`jti` is stale within the hour — ADR-013's unsafely-staling copy. ⚠️ **And ADR-016's retrofit argument does NOT carry over:** a subscriber row **dies with the subscription**, so nothing is lost by waiting — unlike an audit record, where an actor uncaptured at write time is gone. Revisit with the admin-debug UI, and take the **actor pair** (`actSub`/`actProfileId`) then, not the claim. |
| **A local recursive `ActClaim` in `nebula-auth`** carrying an optional `profileId` | Widening `@lumenize/auth`'s — separate package, own consumers, out of scope. `profileId` is **optional**, matching every source of it. ⚠️ `apps/nebula/src/resources.ts` keeps importing `@lumenize/auth`'s **narrow** type: its `changedBy` is a persistence boundary, and declaring an optional `profileId` there is the ADR-001 divergence the projection exists to prevent. |
| Delegation depth **≤ 1** from this mint | Allowing re-delegation. Gate 1 already refuses a caller carrying `act`, and a flat builder cannot nest; keeping both means neither is load-bearing alone. |
| Keep the capability; do not delete the endpoint | Deleting it. The admin-debug use case above is the reason it exists — real, if not yet built. |

## Existing tests — two principals, and a disposition for every one

**Two canonical principals cover every test that touches this endpoint.** Both are ADR-009 rung 1 — real founding, real invite, real login. Each costs one extra magic-link round trip (~1.4s standalone, ~0.9s marginal in a running suite); **that cost is never a reason to substitute a `createNebulaTestToken` mint**, and ADR-009 says so explicitly.

- **P1 — non-admin subject (the default, and the use case).** `foundUniverse(u, admin@)` gives the caller a universe admin (`{u}.*`, scope `{u}`); `inviteAndLogin(scope, …, user@)` gives the subject a member with `isAdmin=0`. Impersonate at an `activeScope` inside the subject's own reach. Eligibility passes (`matchAccess('{u}.*','{u}')`), the scope mirror passes, and the `admin` mirror yields a token with **no `access.admin`** — exactly the "see what this user sees" shape. ✅ This is already the house fixture: four existing tests build it.
- **P2 — admin subject.** Same caller; the subject is a **`claimStar` founder**, which is the only real path to a sub-universe `isAdmin=1` identity (`nebula-auth-registry.ts:423`, stamped at the full 3-segment id). `activeScope` = that star, so the minted pattern is the exact star id and the `admin` mirror is `true`. Required wherever the token must actually carry admin — the gate-1 re-delegation criterion, where a non-admin subject would let gate 3 mask the mutation.

⚠️ **P2 and two other principals need a RECIPE, not just provenance — no phase currently owns building them.** Add a Phase-2 bullet:
- **P2** — `packages/nebula-auth/test/test-helpers.ts` exports stop at `adminRequest`; there is no star-founder end-to-end helper. Build one (working exemplar: `nebula-auth-routes.test.ts:95-112`). ⚠️ Non-obvious prerequisite: **`createGalaxy` must run first** or `claim-star` 400s `parent_not_found` (`nebula-auth-routes.test.ts:114-123`).
- **The eligibility-upward case** (Phase 2's only uniquely-eligibility criterion) additionally needs a **star-tier admin caller** *and* a **galaxy-tier subject** — the latter only via `issueInvites` at a `{u}.{g}` instance path.
- **The widest path** needs a **bootstrap `*` admin**, whose only rung-1 recipe is a non-exported local `platformLogin` in `nebula-auth-bootstrap-array.test.ts:19-26`, keyed to the email bound in `vitest.config.js:41`. Promote it into the shared helpers.

Without these, a builder reaches for a rung-3 `createNebulaTestToken` caller — which the paragraph above forbids.
