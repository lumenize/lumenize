# Every Registry route runs the same pipeline

**Status:** 📐 **`/write-task` Pass 1 — design intent only; phases are deliberately unwritten and this file MUST NOT be built from.** Replaces the stub of the same name (2026-08-13). Mechanism for [nebula-registry-route-guards.md](nebula-registry-route-guards.md), which pins the route table's *shape* and leaves the machinery unbuilt — that file can land without this one, so this blocks nothing.

**Objective — one runner that takes a route's ordered list of steps and executes it.**

What a route and its list look like, from [`docs/vision/auth.md`](../docs/vision/auth.md) § *Coarse-grained access control*, which is the authority if the two ever disagree:

```
/auth/:scope/invite     [parseScopeGuard, verifyJwtGuard, …, handleInvite]
/auth/claim-universe    [rateLimitGuard, turnstileGuard, handleClaimUniverse]
```

These are the goals, in the order they matter:

1. **Legibility.** Today's routes are a mish-mash of conditionals and handlers. It's hard to even identify the full list of routes, nevermind answering *"what protects `/invite`?"* doing that means reading three branches and two `Set`s and knowing which order they execute in. Once we finish building out the routes in [nebula-registry-route-guards.md](nebula-registry-route-guards.md) the list of routes will be in one place along with what each route requires and in what order. `coding-style.md` § *Guard naming* assures that the name of each guard clearly says what it does.
2. **A contract for each step and the runner.** A step refuses by returning a `Response` which short circuits the remaining steps. It adds context by modifying `routeState` or returning an altered `Request`. If the step returns `undefined` then it just moves on to the next step using the existing `Request`. `router.ts` catches thrown Errors and answers `500`. 
3. **Build with Registry routes as the 1st consumer without foreclosing future consumers.** The Registry may remain the only consumer. Regardless, do not encode Registry-specifics in the contract and evaluate the design on flexibility or extensibility for future consumers.

**Scope is the worked example of goal 3, and it takes two steps.** Matching `/auth/:scope/invite` into `params` is generic: any consumer with a URL pattern gets that from the runner. Turning `params.scope` into a validated scope is Registry-specific — the `{u}.{g}.{s}` grammar is `nebula-auth`'s alone — so it is a **step**, and the per-step Needs/Adds types carry its result to the guards that want it. That is the seam: the runner never learns what a scope is, and a route that needs one says so in its own list.

## Context and current state

**Built already**, and each part has a different fate. `packages/nebula-auth/src/router.ts` routes every Registry endpoint by hand:

- **Three auth mechanisms, each reached by its own branch:** `checkTurnstile` gated by the `TURNSTILE_ENDPOINTS` set; `checkJwtForRegistry` for routes whose scope arrives in the request body, which injects `verifiedAccess` and forwards to the Registry DO; and `verifyInstanceJwt` for routes whose scope is a URL segment, gated by the `AUTHENTICATED_SUFFIXES` set. ⇒ **The checks survive as steps; the dispatch around them does not.** `checkTurnstile`'s logic carries over. The two JWT paths **collapse into one**: the route-guards sibling decomposes `verifyInstanceJwt` (it does four things, only one of which is a verify), and once the body-scoped routes take their scope from the URL there is nothing left for `checkJwtForRegistry` to do differently — its inject-and-forward half is a handler concern, not a guard's.
- **Two `Set`s plus a chain of equality branches** decide which of those a route gets. ✅ **Checkable: 15 distinct route suffixes** — 11 reached by `endpoint ===` / `suffix ===` comparisons, plus `mint-narrower-token` and the three in `TURNSTILE_ENDPOINTS` that no equality branch names. ⇒ **Left behind entirely.** Both `Set`s and every equality branch are replaced by table lookup; the 15 is here to size the table, not to be preserved.
- **Refusal is already `Response`-shaped**, not thrown: each check returns a `Response` or `null`/a result object, and the caller tests which. ⇒ **Carried over unchanged**, and it is why this is a migration rather than a rewrite — the step contract formalises a convention the code already follows, so no existing check has to change how it refuses.

## Design intent, constraints, and future state

**This file is not about listing the Registry routes or steps**. That's left to [nebula-registry-route-guards.md](nebula-registry-route-guards.md). Where this file names a route that is an example which may be stale.

**Two levels of routing, and this file operates in the inner one.** The outer level is in `entrypoint.ts`. Its contents is a list of routers. When a router returns `undefined` that means *"not my path, try the next router"*. Each router can take a different approach. For the inner `/auth` router, each route specifies a step list. For the inner WS upgrade routers (`/gateway`),  they use `routeDORequest` which detects WS upgrade, resolves binding and instance name, gets the stub, and forwards the `Request`. Other inner routers could use a different approach (direct-http-to-DO for example).

**The deliverable for this task file is a runner and a step contract.** [`docs/vision/auth.md`](../docs/vision/auth.md) § *Coarse-grained access control* (`status: accepted`) states what a Registry route must do, as R1–R7 plus the two families that present no access token. It is written mechanism-neutrally on purpose. 

**The route table's keys *are* the set of routes**. This is what makes goal 1 structural.

**`routeState` carries per-request knowledge a later step or the handler needs.** The runner produces `params` from the URL match; everything else a step puts there. A field belongs if it is per-request — never by which step produced it.

**No single type describes it, and that is the point.** Each step declares the slice it requires and the slice it adds, so `handleInvite` reads `claims` non-optionally *because it declared it needs them*, and `handleClaimUniverse` declares it needs none — a route with no verify step is ordinary rather than an exception.

```ts
type Step<Needs extends object = {}, Adds extends object = {}> =
  (request: Request, state: Needs & Partial<Adds>) => Response | Request | void

const verifyJwtGuard: Step<{}, { claims: NebulaJwtPayload }>       // adds claims
const passageGuard:   Step<Params & { claims: NebulaJwtPayload }>  // needs claims
const handleClaimUniverse: Step                                    // needs neither
```

⚠️ **Nothing enforces the ORDER, and nothing should.** The array is read left to right, and that reading *is* the audit — which is why goal 1 wants an array at all. § *Decisions* carries the type-level alternative and why it is not taken.

**`env` is not in `routeState`.** It is ambient and identical on every request, so it fails the per-request test. How a step reaches it instead is § *Open questions* 3.

**R1 is the runner's — the table *is* the registration. R2 is `parseScopeGuard`**, first in every scoped route's list. A malformed scope gets a `Response`; a well-formed one lands on `routeState` parsed and validated. That is the Needs/Adds contract's first real use — it needs `params` and adds `scope`, so every guard comparing against a scope declares it needs `scope` rather than the raw capture.

⚠️ **The example above elides the middle of that list** — `…` stands for the guards [nebula-registry-route-guards.md](nebula-registry-route-guards.md) owns; the shape is the pattern, an ordered list, and a handler last. **`auth.md`'s worked example carries neither the parse step nor the elision yet.** Its layers are mechanism-neutral so nothing there is wrong, but it is the authority when the two disagree, so it and the sibling's table both take `parseScopeGuard` next.

**Refusal has one shape: return a `Response`.** The runner stops at the first step that returns one. `coding-style.md` § *Guard naming* already binds this and explains the cost of the alternative; the runner's contract makes it the only thing a step *can* do, rather than a rule each step follows.

**Scope-free routes are first-class, not an omission.** `auth.md`'s two no-access-token families and `my-scopes` all legitimately take no scope, so a step list that omits the scope-dependent steps must be expressible as a complete, valid registration — never as a table entry with holes in it.

### Constraints

- **[`docs/vision/auth.md`](../docs/vision/auth.md) § *Coarse-grained access control* — `status: accepted`.** R1–R7 are the behaviour this must produce. Per `docs/vision/_review-lens.md` § *Status convention*, contradicting it is a blocker.
- **[nebula-registry-route-guards.md](nebula-registry-route-guards.md)** owns the route table's contents, the guards and their operands, and which fields `routeState` carries (this file decides only that URL captures land on `params`). It lands first and does not depend on this file.
- **`.claude/rules/coding-style.md` § *Guard naming*** — the `*Guard` suffix and the return-a-`Response` contract.
- **`.claude/rules/raw-comm.md`** permits a hono dependency only *"unless you have more than a dozen routes and/or significant middleware needs"* — a threshold the 15 routes above and this file's own subject both satisfy, so the rule no longer argues against it either way.
- **A dependency needs explicit approval** (`CLAUDE.md`), and **startup cost is the criterion, measured rather than inferred** (`workflow.md` § *Startup cost is the criterion*). `nebula-auth` fronts the Registry singleton and a DO pays for its whole Worker's import graph, so the measurement is per-Worker-bundle and the `packages/auth` precedent does not transfer.

### Open questions

1. **Does the table key on path, or on path + method?** `router.ts` answers **405** today for a known path with the wrong method (`:253`, `:264`), and the sibling's table is keyed by suffix string alone — so a straight transcription loses that distinction and turns a wrong-method request into a 404. ⚠️ **Gates the table's key shape**, and therefore what "the table is the registration" means: one entry per path, or one per path+method. Both hono and itty key on method+path natively, which is a point in favour of buying the routing if the answer is the latter.
2. **Where does the rate limiter's key put it in the order?** Connection-keyed must precede the verify step, because it is what bounds how much signature verification an anonymous caller can force; `sub`-keyed must follow it, because `sub` does not exist yet. Possibly both, as two entries. ⚠️ Gates nothing structural, but it is a worked example the runner's contract must be able to express.
3. **Does a step reach `env` by importing it, or by being handed it?** `cloudflare:workers` exports `env`, which would keep the step signature to `(request, routeState)`. ⚠️ **Gates the step signature**, so it settles before the contract does. One thing to check first: whether that import reflects vitest-pool-workers' `miniflare.bindings`, which is where test-mode flags live by rule — a step reading a flag the import cannot see would be untestable in-lane. ⚠️ `checkRateLimit`'s widened `Env & { NEBULA_AUTH_RATE_LIMITER?: RateLimit }` is **not** a second obstacle: once every program that compiles this source declares that binding — which the sibling's Phase 1 starts — the widening's reason goes with it.


### Design considerations

- ⚠️ **Design consideration: the `*Guard` suffix is spelled inconsistently across the two files this conforms to.** `auth.md`'s worked example writes `rateLimitGuard` / `verifyJwtGuard`; the sibling's table writes bare `verifyJwt` / `rateLimit`. `coding-style.md`'s rule settles which is correct; the fix belongs wherever it is found and gates nothing here.
- ⚠️ **Design consideration: whether this becomes a package — and `packages/routing` is the tempting home, which is exactly why it is worth saying it is not the one.** `@lumenize/routing` is **MIT with no `private` flag**, and `routeDORequest` is documented at `lumenize.com/docs/routing/route-do-request`, so a runner landing there is public API under a semver commitment — for a mechanism with one real consumer. `@lumenize/nebula-auth` is `private: true` / `UNLICENSED`, so building it there is free to move later and free to get wrong once. The mesh side is not a candidate at all: it has its own convention (`require*` throws).
- ⚠️ **Design consideration: `verifyInstanceJwt` does four things**, and the sibling decomposes it. Whatever this runner's verify step looks like, it inherits that decomposition rather than the current function.

## Decisions

⏳ **Started during the Pass-1 gate; open questions above are deliberately absent — only settled things go here.**

| Decision | Rejected alternative — why |
|---|---|
| **This file decides how a list of steps executes, and nothing else** | Deciding policy here too — `auth.md` § *Coarse-grained access control* owns the behaviour and the route-guards sibling owns which steps and their operands. ⚠️ Nor is it purpose-built for the Registry: that is the first consumer, and the step contract should not encode anything only the Registry needs. A mechanism file that also decides policy is the shape that makes both unreviewable, which is why the passage/dominion work was split four ways in the first place. |
| **The threaded value is named `routeState`** | `ctx` / `context` — both already taken (`this.ctx` is `DurableObjectState`, 103 uses; `callContext` is mesh's, 138), so a third repeats the ambiguity ADR-015 spent a rename ending. Also rejected: `verified`, which names the bag for its *provenance*, so anything later steps add that nobody verified becomes a lie. `state` follows `callContext.state`, the repo's existing name for a value threading a long call chain. |
| **`env` stays out of `routeState`** | Threading it — `routeState` holds *per-request* knowledge and `env` is ambient, identical on every request. ⚠️ The criterion is **per-request, not established-by-a-step**: `params` is matched out by the runner rather than established, and belongs in the bag. ⚠️ Rejecting `env` from the bag is not the same as choosing the `cloudflare:workers` import; see § *Design intent* for the two things that must be checked first. |
| **The step's state type is a parameter, not fixed to `routeState`** | Fixing it — a type parameter costs the same as a concrete one, and `workflow.md` § *Evaluating alternatives* makes the narrow form strictly worse when the general one costs the same or less. ⚠️ **Not justified by a second consumer**, and an earlier draft claimed one: `routeDORequest`'s hooks share the step *shape* but consume nothing here, and the sibling already records that mirroring in § *The shape — a linear step pipeline*. The cost test settles it without one. |
| **`URLPattern` matches the path** | Hand-rolled segment splitting, or copying itty's matcher. `URLPattern` is a web standard **native to workerd** (`@cloudflare/workers-types` declares it), so it costs no dependency, no attribution and no startup budget, and `exec()` returns named captures directly. ⚠️ **It brings `:scope` syntax, not `{scope}`, and every route pattern in `auth.md` and above was changed to match (2026-08-13).** RFC 6570 — what MCP uses — is a template for *constructing* a URL; a route table only ever *matches*, so brace syntax there taught a translation for nothing. Braces stay everywhere they stand in for a value in prose (`{u}.{g}.{s}`, the refresh cookie's `Path`), which is the split `auth.md` § *Scopes* now states. |
| **Only the pathname is patterned** — hostname and query come from `new URL()` | Patterning `hostname` or `search` as well. Both are single values read directly (`url.hostname`, `url.searchParams`), and patterning `search` would make presence and order part of the match for no gain. ✅ **This is also what keeps `params` a flat, safe namespace**: multi-component matching yields one `groups` record per component, so the same capture name in two of them (`:scope.lumenize.dev` + `/auth/:scope/…`) would collide on flattening, with spread order deciding silently. One patterned component, one record, no collision. |
| **Path captures land on `routeState.params`** | `pathname.groups` (mirroring `URLPattern`) — `groups` is ES2018 named-capture heritage, so it names *how the value was captured* rather than what it holds, which `coding-style.md`'s tiers forbid; it also couples the state shape to the matcher, so swapping matchers would rename a field every step reads. Also rejected: `urlParams`, which is invented and redundant since everything in a route comes from the URL. `params` is what both routers already call this (itty's `request.params`, hono's `param(key)`), it is one level, and the query side keeps its own standard name in `searchParams`. |
| **The runner owns registration: a route's step list IS its entry** | A registration set alongside the table — that is today's shape (`AUTHENTICATED_SUFFIXES` + `TURNSTILE_ENDPOINTS` + equality branches), and two enumerations means a route can be in one and not the other. One table makes goal 2 structural instead of a rule to remember. |
| **Write the runner; do not adopt hono** — and the decider is `routeState` | Adopting hono. ⚠️ **Two commonly-cited reasons are WRONG and must not be re-derived.** (a) *"hono is onion-style and we are linear"* — false: `compose` passes `next` as `() => dispatch(i + 1)`, so a step that returns a `Response` **without** calling it short-circuits the chain, and hono's route API already takes an array of handlers. Linear-with-short-circuit is first-class there. (b) *"routing is the bulk we do not need"* — true (`compose` is 1.2 KB against ~87 KB of router and base) but not decisive on its own, since `hono/tiny` is a real minimal preset and neither `compose` nor `context` does module-scope work. **The actual decider: `compose` passes `(context, next)` and nothing else, so a typed `routeState` has nowhere to ride except `c` — i.e. `c.set`/`c.get`, the string-keyed bag § *Decisions* rejects above.** A closure or module-scope value is worse: that is the cross-request-leak hazard in a reused isolate. ⚠️ **Re-open this if the design drifts toward a general-purpose context object or genuine onion middleware** — at that point we would be building hono badly. ⚠️ Using a library *only* for URL matching and parameter extraction is a **separate** question this does not foreclose, as is fork-vs-dependency. ⚠️ **For that question the candidate to evaluate is `itty-router`, not hono** — it forwards arbitrary extra arguments to every handler, so a typed `routeState` rides as a real parameter and the decider above does not apply; its chain is already return-`undefined`-to-continue, which is this file's refusal convention; and its core is sub-kilobyte. ⚠️ **Unverified — not installed, assessed from knowledge on 2026-08-13.** It would not change what we build either way: routing and parameter extraction are the parts that are cheap for ~15 mostly-literal suffixes. ⚠️ **And the likely answer there is not a dependency at all.** `workflow.md` favours copy-paste-with-attribution over a dependency under 1000 SLOC, which itty's core is well inside; `ATTRIBUTIONS.md` already carries the lighter *"(Inspiration)"* form for `@ungap/structured-clone` and Cap'n Web — read for shape, implemented from scratch, divergence noted. That form fits here for a second reason: itty is written for minimum characters, and this repo spends real effort on legible naming, so even a straight copy would be rewritten — at which point it was pseudo-code and *Inspiration* is the honest filing. |
| **The step's state parameter is generic; the entrypoint is a consumer we do not migrate** | Fixing the state type to `routeState` — a type parameter costs the same as a concrete one, and `workflow.md` § *Evaluating alternatives* rejects the narrow form where the general one costs the same or less. **That cost test is the whole argument.** ⚠️ **Not a second consumer:** `routeDORequest`'s hooks carry this file's step signature over a *different* state (`{ doNamespace, doInstanceNameOrId }`), which is a precedent for the **shape** and not a consumer of this runner — the sibling records that mirroring in § *The shape — a linear step pipeline*. ⚠️ Two things rejected separately, and neither follows from the other: **migrating the entrypoint in this file** — it works, its list is four entries, and this file's whole discipline is to build the mechanism and change no policy — and **landing the runner in `packages/routing`**, per § *Design considerations*. |
| **Steps declare what they need and what they add; the array is not folded** | One `routeState` type every step shares — wrong for the open routes, which have no verify step and never carry `claims`, and wrong *before* the verify step on the routes that do. Also rejected: a recursive fold over the tuple that checks order. ⚠️ **It works** — built and compiled 2026-08-13, ~15 lines plus a `const` type parameter and a phantom property that stops a step being a plain function — **and it is declined on value, not difficulty.** Nothing here compiles (`wrangler` bundles at deploy, dev imports `.ts` directly, `type-check` runs in no CI workflow), so it would fire only in an editor; and a mis-ordered guard throws on `access.authScope` and answers 500 on every call to that route, which the first test catches. `calibration.md` §9 puts prevention on failures with no signal. ⚠️ Verified with `tsc --strict` that a plain array literal does **not** catch order: each element is checked against a common step type, never the sequence. |
| **`parseScopeGuard`** | `validScopeGuard` — *valid* means something different at every layer here (well-formed? existing? reachable?) and this guard means only the first. `wellFormedScopeGuard` — the most precise, and the longest, which costs real legibility in a table goal 1 needs readable: a sixth step took that route to 125 characters before the elision. `parse` coins nothing, being already the repo's word (`parseId`, `parse-id.ts`). |
| **An array literal, not a builder chain** | A builder chain — it threads types naturally and stops reading like a table. Two levels of list exist (§ *Design intent*), and the array is the form that reads as a table at **both**; the entrypoint's outer list is a sequence of calls today, and a builder there would read worse. With the fold declined above, the builder's one real advantage is gone. |
