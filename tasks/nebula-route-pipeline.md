**Objective — one runner that takes a route's ordered list of steps and executes it.**

What a route and its list look like — the real shape, with `…` standing in for the guards the sibling owns. Which steps each route carries is [`docs/vision/auth.md`](../docs/vision/auth.md) § *Coarse-grained access control*'s, and stays the authority if the two disagree.

```js
[
  { path: '/auth/:scope/invite',  method: 'POST', steps: [parseScopeGuard, verifyJwtGuard, …, handleInvite] },
  { path: '/auth/claim-universe', method: 'POST', steps: [rateLimitGuard, turnstileGuard, handleClaimUniverse] },
]
```

These are the goals, in the order they matter:

1. **Legibility.** Today's routes are a mish-mash of conditionals and handlers. It's hard to even identify the full list of routes, nevermind answering *"what protects `/invite`?"* doing that means reading three branches and four `Set`s and knowing which order they execute in. Once we finish building out the routes in [nebula-registry-route-guards.md](nebula-registry-route-guards.md) the list of routes will be in one place along with what each route requires and in what order. `coding-style.md` § *Guard naming* assures that the name of each guard clearly says what it does.
2. **A contract for each step and the runner.** A step refuses by returning a `Response` which short circuits the remaining steps. It adds context by modifying `routeState` or returning an altered `Request`. If the step returns `undefined` then it just moves on to the next step using the existing `Request`. A step that **throws** is not caught by the runner: the error propagates to whatever embeds it, and that embedder answers. `router.ts`'s blanket `500` is one embedder's answer, not the contract — which is also why `coding-style.md` § *Guard naming* wants refusals returned rather than thrown. 
3. **Build with Registry routes as the 1st consumer without foreclosing future consumers.** The Registry may remain the only consumer. Regardless, do not encode Registry-specifics in the contract and evaluate the design on flexibility or extensibility for future consumers.

**Scope is the worked example of goal 3, and it takes two steps.** Matching `/auth/:scope/invite` into `params` is generic: any consumer with a URL pattern gets that from the runner. Turning `params.scope` into a validated scope is Registry-specific — the `{u}.{g}.{s}` grammar is `nebula-auth`'s alone — so it is a **step**, and the per-step Needs/Adds types carry its result to the guards that want it. That is the seam: the runner never learns what a scope is, and a route that needs one says so in its own list.

## Context and current state

**Nothing here changes an existing file.** This task adds the runner, the step contract and their tests; migrating `packages/nebula-auth/src/router.ts` onto them belongs to [nebula-registry-route-guards.md](nebula-registry-route-guards.md), which owns the route table. ⚠️ **`router.ts` appears below as evidence about what the contract must support** — a step has to fit these checks as they already are, not as a rewrite would like them. Each part also has a different fate under that later migration, noted so the contract is not shaped around something being left behind:

- **Three auth mechanisms, each reached by its own branch:** `checkTurnstile` gated by the `TURNSTILE_ENDPOINTS` set; `checkJwtForRegistry` for routes whose scope arrives in the request body, which injects `verifiedAccess` and forwards to the Registry DO; and `verifyInstanceJwt` for routes whose scope is a URL segment, gated by the `AUTHENTICATED_SUFFIXES` set. ⇒ **The checks survive as steps; the dispatch around them does not.** `checkTurnstile`'s logic carries over. The two JWT paths **collapse into one**: the route-guards sibling decomposes `verifyInstanceJwt` (it does four things, only one of which is a verify), and once the body-scoped routes take their scope from the URL there is nothing left for `checkJwtForRegistry` to do differently — its inject-and-forward half is a handler concern, not a guard's.
- **Four `Set`s plus a chain of equality branches** decide which of those a route gets (`REGISTRY_ENDPOINTS`, `AUTH_FLOW_SUFFIXES`, `AUTHENTICATED_SUFFIXES`, `TURNSTILE_ENDPOINTS`). ✅ **Checkable: 15 distinct route suffixes** — 11 reached by `endpoint ===` / `suffix ===` comparisons, plus `mint-narrower-token` and the three in `TURNSTILE_ENDPOINTS` that no equality branch names. ⇒ **Left behind entirely** when the sibling migrates. All four `Set`s and every equality branch give way to table lookup; the 15 is here to size the runner's table, not to be preserved.
- **Refusal is already `Response`-shaped**, not thrown: each check returns a `Response` or `null`/a result object, and the caller tests which. ⇒ **Carried over unchanged**, and it is why that later change is a migration rather than a rewrite — the step contract formalises a convention the code already follows, so no existing check has to change how it refuses.

## Design intent, constraints, and future state

**This file is not about listing the Registry routes or steps**. That's left to [nebula-registry-route-guards.md](nebula-registry-route-guards.md). Where this file names a route that is an example which may be stale.

**Two levels of routing, and this file operates in the inner one.** The outer level is in `entrypoint.ts`. Its contents is a list of routers. When a router returns `undefined` that means *"not my path, try the next router"*. Each router can take a different approach. For the inner `/auth` router, each route specifies a step list. For the inner WS upgrade routers (`/gateway`),  they use `routeDORequest` which detects WS upgrade, resolves binding and instance name, gets the stub, and forwards the `Request`. Other inner routers could use a different approach (direct-http-to-DO for example).

**The deliverable for this task file is a runner and a step contract.** [`docs/vision/auth.md`](../docs/vision/auth.md) § *Coarse-grained access control* (`status: accepted`) states what a Registry route must do, as R1–R7 plus the two families that present no access token. It is written mechanism-neutrally on purpose. 

**The table *is* the set of routes** — an array of entries, each `{ path, method?, steps }`. `steps` is required; `method` is optional, and an entry without one takes any verb. This is what makes goal 1 structural, and it is why a route needing few steps registers a short list rather than a padded one — there are no holes to fill. ⚠️ **An array, not an object keyed by path** — measured on Node 24.19: a duplicate key collapses **silently**, the earlier entry gone with no error, which would foreclose two entries sharing a path; and an array shows the ordering below rather than leaving it to a property of JS key ordering.

**`routeState` carries per-request knowledge a later step or the handler needs.** The runner produces `params` from the URL match; everything else a step puts there. A field belongs if it is per-request — never by which step produced it.

**No single type describes it, and that is the point.** Each step declares the slice it requires and the slice it adds, so `handleInvite` reads `claims` non-optionally *because it declared it needs them*, and `handleClaimUniverse` declares it needs none — a route with no verify step is ordinary rather than an exception.

```ts
type Step<Needs extends object = {}, Adds extends object = {}> =
  (request: Request, state: Needs & Partial<Adds>) =>
    Promise<Response | Request | void> | Response | Request | void
type Params = { params: Record<string, string> }

const verifyJwtGuard: Step<{}, { claims: NebulaJwtPayload }>       // adds claims
const passageGuard:   Step<Params & { claims: NebulaJwtPayload }>  // needs claims
const handleClaimUniverse: Step                                    // needs neither
```

⚠️ **Every real guard is async, so the union carries the `Promise` arm** — `verifyNebulaAccessToken`, `checkTurnstile`'s siteverify `fetch` and `rateLimiter.limit` all are, and `routeDORequest`'s hooks (the convention this mirrors) already spell it that way. **The runner `await`s each step's result before narrowing it**, and a rejection propagates uncaught exactly as a sync throw does. 🚨 **Dropping the `await` fails OPEN and silently:** a pending Promise is neither `instanceof Response` nor `instanceof Request`, so it reads as *continue* — the refusal is discarded and the handler runs.

⚠️ **Nothing enforces the ORDER, and nothing should.** The array is read left to right, and that reading *is* the audit — which is why goal 1 wants an array at all. § *Decisions* carries the type-level alternative and why it is not taken.

**`env` is not in `routeState`.** It is ambient and identical on every request, so it fails the per-request test. A step that needs it imports it from `cloudflare:workers`.

**R1 is the runner's — the table *is* the registration, matched by a linear scan whose first `exec()` hit wins. R2 is `parseScopeGuard`**, first in every scoped route's list. A malformed scope gets a `Response`; a well-formed one lands on `routeState` parsed and validated. That is the Needs/Adds contract's first real use — it needs `params` and adds `scope`, so every guard comparing against a scope declares it needs `scope` rather than the raw capture.

⚠️ **The example above elides the middle of that list** — `…` stands for the guards [nebula-registry-route-guards.md](nebula-registry-route-guards.md) owns; the shape is the pattern, an ordered list, and a handler last. ⚠️ **`auth.md` is the authority and the sibling reconciles against it** — this file keeps no list of what the two owe each other, because route contents are not its to track. (Live examples rather than an inventory: neither carries `parseScopeGuard`; the sibling spells guards bare where `coding-style.md` § *Guard naming* settles otherwise; and the two give `claim-universe` different lists.)

⚠️ **First match wins among the entries that match, so the table's ORDER is part of its meaning.** The scan takes the first entry whose `exec()` returns non-null **and** whose `method` matches or is absent; a path match with a different method is **skipped, not refused**, so two entries may share a path. `405` is answered only when some entry matched the path and none took the method — which separates *wrong method* from *no such route* without a second lookup. There is no best-match or specificity ranking, so two entries that could both take one request are resolved by whichever is listed first, and the more specific goes earlier. ✅ **Measured on Node 24.19, 2026-08-13: matching is segment-exact, which makes the collision narrower than it looks.** `/a` does not match `/a/b`, a capture never spans `/`, and `delete-scope` does not match `delete-scope-plan` — two distinct literal suffixes cannot shadow one another. Overlaps come from a **literal against a capture in the same position** (`/auth/:scope/invite` vs `/auth/:scope/:action`), and from two entries deliberately sharing a path, which is ordinary for a REST resource. No Registry route registers either today, so for the Registry the rule is preventive. ⚠️ **Trailing slashes are exact as well** — `/auth/x/invite/` matches neither, so it falls through to the embedder as an unmatched path; today's suffix comparison is the behaviour to diff that against.

**What the RUNNER returns when no step answered.** Three cases, decided differently. **No path match → `undefined`** — the composition contract above, *not my path, try the next router*; `entrypoint.ts` chains on exactly that, and a runner minting its own 404 would answer for `/gateway/…` and make the Gateway unreachable. **A path matched but no entry took the method → `405`**, from the runner, because only the table can separate wrong-verb from no-such-route. **A matched entry whose list runs out → a `500`**, distinguishable from both: an empty `steps` and a handler that falls through are the same bug, and a route that is registered but broken must not read as one that does not exist.

**Refusal has one shape: return a `Response`.** The runner stops at the first step that returns one. `coding-style.md` § *Guard naming* already binds this and explains the cost of the alternative; the runner's contract makes it the only thing a step *can* do, rather than a rule each step follows.

### Constraints

- **[`docs/vision/auth.md`](../docs/vision/auth.md) § *Coarse-grained access control* — `status: accepted`.** R1–R7 are the behaviour this must produce. Per `docs/vision/_review-lens.md` § *Status convention*, contradicting it is a blocker.
- **[nebula-registry-route-guards.md](nebula-registry-route-guards.md)** owns the route table's contents, the guards and their operands, and which fields `routeState` carries (this file decides only that URL captures land on `params`). It lands first and does not depend on this file.
- **`.claude/rules/coding-style.md` § *Guard naming*** — the `*Guard` suffix and the return-a-`Response` contract.

### Design considerations

- ⚠️ **Design consideration: the method field is the narrow case of a predicate, and the widening is obvious.** `routeDORequest` selects on the **WebSocket upgrade header**, not on a method — so a consumer that ever replaced it with this runner would want a callback where `method` sits today. YAGNI now: nothing needs it, and `method` is what every Registry route uses today. Recorded because the extension path being this cheap is evidence the shape is right — the runner selects on *something about the request*, and an HTTP method is one instance of that.
- ⚠️ **Design consideration: the rate limiter may want two entries in one list, not one.** Connection-keyed must precede the verify step, because it bounds how much signature verification an anonymous caller can force; `sub`-keyed must follow it, because `sub` does not exist yet. Which the Registry uses is the sibling's call; what this file owes is a contract that can express the same guard twice in one list.
- ⚠️ **Design consideration: `verifyInstanceJwt` does four things**, and the sibling decomposes it. Whatever this runner's verify step looks like, it inherits that decomposition rather than the current function.

## Decisions

| Decision | Rejected alternative — why |
|---|---|
| **This file decides how a list of steps executes, and nothing else** | Deciding policy here too — `auth.md` § *Coarse-grained access control* owns the behaviour and the route-guards sibling owns which steps and their operands. ⚠️ Nor is it purpose-built for the Registry: that is the first consumer, and the step contract should not encode anything only the Registry needs. A mechanism file that also decides policy is the shape that makes both unreviewable, which is why the passage/dominion work was split four ways in the first place. |
| **The threaded value is named `routeState`** | `ctx` / `context` — both already taken (`this.ctx` is `DurableObjectState`; `callContext` is mesh's), each heavily used, so a third repeats the ambiguity ADR-015 spent a rename ending. Also rejected: `verified`, which names the bag for its *provenance*, so anything later steps add that nobody verified becomes a lie. `state` follows `callContext.state`, the repo's existing name for a value threading a long call chain. |
| **`env` stays out of `routeState`** | Threading it — `routeState` holds *per-request* knowledge and `env` is ambient, identical on every request. ⚠️ The criterion is **per-request, not established-by-a-step**: `params` is matched out by the runner rather than established, and belongs in the bag. ⚠️ Rejecting `env` from the bag is a separate decision from how a step *reaches* it, which the `cloudflare:workers` import row carries. |
| **`URLPattern` matches the path** | Hand-rolled segment splitting, or copying itty's matcher. `URLPattern` is a web standard **native to workerd** (`@cloudflare/workers-types` declares it), so it costs no dependency, no attribution and no startup budget. ⚠️ **`exec()` is the ROUTER as well as the extractor:** it returns `URLPatternResult | null` (workerd's own types, `worker-configuration.d.ts:3092`), so one call answers *did this route match* and *what did it capture* together. Matching is then a linear scan of the table, first non-null wins — no test-then-parse, and no match index to keep in sync with the entries. ⚠️ **It brings `:scope` syntax, not `{scope}`, and every route pattern in `auth.md` and above was changed to match (2026-08-13).** RFC 6570 — what MCP uses — is a template for *constructing* a URL; a route table only ever *matches*, so brace syntax there taught a translation for nothing. Braces stay everywhere they stand in for a value in prose (`{u}.{g}.{s}`, the refresh cookie's `Path`), which is the split `auth.md` § *Scopes* now states. |
| **Only the pathname is patterned** — hostname and query come from `new URL()` | Patterning `hostname` or `search` as well. Both are single values read directly (`url.hostname`, `url.searchParams`), and patterning `search` would make presence and order part of the match for no gain. ✅ **This is also what keeps `params` a flat, safe namespace**: multi-component matching yields one `groups` record per component, so the same capture name in two of them (`:scope.lumenize.dev` + `/auth/:scope/…`) would collide on flattening, with spread order deciding silently. One patterned component, one record, no collision. |
| **Path captures land on `routeState.params`** | `pathname.groups` (mirroring `URLPattern`) — `groups` is ES2018 named-capture heritage, so it names *how the value was captured* rather than what it holds, which `coding-style.md`'s tiers forbid; it also couples the state shape to the matcher, so swapping matchers would rename a field every step reads. Also rejected: `urlParams`, which is invented and redundant since everything in a route comes from the URL. `params` is what both routers already call this (itty's `request.params`, hono's `param(key)`), it is one level, and the query side keeps its own standard name in `searchParams`. |
| **The runner owns registration: a route's step list IS its entry** | A registration set alongside the table — that is today's shape (`AUTHENTICATED_SUFFIXES` + `TURNSTILE_ENDPOINTS` + equality branches), and two enumerations means a route can be in one and not the other. One table makes goal 2 structural instead of a rule to remember. |
| **Write the runner; do not adopt hono** | Adopting hono. ⚠️ **Two commonly-cited reasons are WRONG and must not be re-derived.** (a) *"hono is onion-style and we are linear"* — false: `compose` passes `next` as `() => dispatch(i + 1)`, so a step that returns a `Response` **without** calling it short-circuits the chain, and hono's route API already takes an array of handlers. Linear-with-short-circuit is first-class there. (b) *"routing is the bulk we do not need"* — true (`compose` is 1.2 KB against ~87 KB of router and base) but not decisive on its own, since `hono/tiny` is a real minimal preset and neither `compose` nor `context` does module-scope work. **The actual decider: `compose` passes `(context, next)` and nothing else, so a step has nowhere to declare its own slice except `c` — i.e. `c.set`/`c.get`, a string-keyed lookup that can only return `T | undefined`, under which no step could require `claims` and read them non-optionally.** A closure or module-scope value is worse: that is the cross-request-leak hazard in a reused isolate. ⚠️ **Re-open this if the design drifts toward a general-purpose context object or genuine onion middleware** — at that point we would be building hono badly. ⚠️ Using a library *only* for URL matching and parameter extraction is a **separate** question this does not foreclose, as is fork-vs-dependency. ⚠️ **For that question the candidate to evaluate is `itty-router`, not hono** — it forwards arbitrary extra arguments to every handler, so a typed `routeState` rides as a real parameter and the decider above does not apply; its chain is already return-`undefined`-to-continue, which is this file's refusal convention; and its core is sub-kilobyte. ⚠️ **Unverified — not installed, assessed from knowledge on 2026-08-13.** It would not change what we build either way: routing and parameter extraction are the parts that are cheap for ~15 mostly-literal suffixes. ⚠️ **And the likely answer there is not a dependency at all.** `workflow.md` favours copy-paste-with-attribution over a dependency under 1000 SLOC, which itty's core is well inside; `ATTRIBUTIONS.md` already carries the lighter *"(Inspiration)"* form for `@ungap/structured-clone` and Cap'n Web — read for shape, implemented from scratch, divergence noted. That form fits here for a second reason: itty is written for minimum characters, and this repo spends real effort on legible naming, so even a straight copy would be rewritten — at which point it was pseudo-code and *Inspiration* is the honest filing. ⚠️ **Nothing FORBADE it, which the re-open clause above depends on:** `raw-comm.md`'s threshold — *"more than a dozen routes and/or significant middleware needs"* — is met by the 15 routes and by this file's own subject, so the rule permits the dependency and we declined on the `routeState` argument alone. A reader who believes a rule blocks it will never revisit. ⚠️ **`packages/auth` already depending on hono is not a precedent** — a DO pays for its whole Worker's import graph, so startup cost is per-Worker-bundle; re-opening owes a **measurement** (`workflow.md` § *Startup cost is the criterion*), never an inference from the other package. |

Also rejected: a `methodGuard` step, which spends an entry in every route's list to express an HTTP universal, against goal 1. ⚠️ **Optional means permissive:** an absent `method` takes any verb — right for a consumer that does not care about verbs, wrong for every Registry route, which are all single-verb. ### Phase 1 — The runner matches a request to an entry and runs its steps

The `Step<Needs, Adds>` type, the table type `{ path, method?, steps }`, `URLPattern` matching, and the executor. A todo mini-app with single-method routes is the consumer; there is no other, by design.

**Criteria (capable of failing).** Each names the single change that reds it.

- 🔒 **A request matching no entry's path returns `undefined`, and no step runs.** The mini-app's own fallback answers 404; the runner does not. Assert the no-step limb through a step that records it, not through the status — a 404 and a refusal look identical to a caller. *Mutation: mint a 404 inside the runner → the mini-app's fallback never runs and its recorder stays empty.*
- 🔒 **A matched entry whose steps run out returns a 500, distinguishable from the no-match case.** Test both an empty `steps: []` and a last step returning `undefined`. *Mutation: return the no-match answer for an exhausted list → a registered-but-broken route becomes indistinguishable from an unregistered path and the assertion separating them reds.*
- 🔒 **Path captures land on `routeState.params`, flat.** `/todos/:id` against `/todos/7` gives `params.id === '7'`. *Mutation: assign `exec()`'s whole `URLPatternResult` to `params` → the step reads `params.pathname.groups.id` and the flat read reds.* ⚠️ Assigning `pathname.groups` **is** the correct flat behaviour — `URLPatternComponentResult` is `{ input, groups }` — so that change is a no-op and would validate nothing.
- 🔒 **A step returning a `Response` short-circuits.** The next step in the list does not run and its recorder stays empty. *Mutation: continue the loop after a `Response` → the recorder fires.*
- 🔒 **A step returning a `Request` replaces the one later steps receive.** A later step reads a header the replacement added. *Mutation: ignore the returned `Request` → the later step sees the original.*
- 🔒 **A step returning `undefined` continues with the existing `Request`.** *Mutation: treat `undefined` as terminal → the handler never runs.*
- 🔒 **An `async` step returning a `Response` short-circuits.** At least one mini-app step is genuinely `async`; without one the suite is structurally blind to this. *Mutation: drop the `await` → the Promise is neither `instanceof Response` nor `Request`, reads as continue, the later recorder fires and the handler answers 200.* 🚨 **This is the fail-open case**, and the only criterion that can see it.
- 🔒 **An `async` step that rejects propagates uncaught**, distinct from the sync throw below. *Mutation: swallow the rejection → the assertion that it escapes reds.*
- 🔒 **A throw propagates out of the runner, uncaught.** `expect(() => run(...)).rejects` — the runner answers no status of its own. *Mutation: wrap the loop in `try/catch` returning 500 → the assertion that the throw escapes reds.* ⚠️ This is the contract goal 2 states; `router.ts`'s blanket 500 is one embedder's answer and is not this runner's.
- 🔒 **`routeState` threads.** A value one step adds is visible to a later step and to the handler. *Mutation: pass a fresh object per step → the later read is `undefined`.*

### Phase 2 — The mini-app is a real app, and that is the goal-3 check

The todo app grows REST-shaped routes. This phase exists because a runner shaped around the Registry passes Phase 1 intact — every criterion above holds for a table where each path takes exactly one verb.

- 🔒 **Two entries share a path with different methods, and each request reaches its own handler.** `GET /todos` lists, `POST /todos` adds. *Mutation: refuse on the first method mismatch instead of continuing the scan → the `POST` reds with 405.* ⚠️ **This is the criterion the Stage-1 panel's blocker asks for**, and the case a Registry-only table cannot produce.
- 🔒 **405 distinguishes a wrong method from an absent route.** `DELETE /todos` returns **405 from the runner** — the path exists and no entry takes the verb; `DELETE /nope` returns **`undefined`**, and 404 only from the mini-app's fallback. *Mutation: return `undefined` for both → the 405 limb reds, and the wrong-verb case becomes indistinguishable from an unregistered path.*
- 🔒 **An entry with no `method` takes any verb.** *Mutation: treat an absent `method` as `'GET'` → the `POST` reds.*
- 🔒 **A step cannot read a field it did not declare.** A mini-app step carries `@ts-expect-error` over a read outside its `Needs`, checked by the existing `npm run type-check`. *Mutation: widen the state parameter to `Partial<…>` or `Record<string, unknown>` → the directive goes unused and type-check reds.* ⚠️ **This is the property the hono decision rests on** (§ *Decisions*); without a criterion it can degrade to a `T | undefined` bag and that argument evaporates silently.
- 🔒 **No state survives between runs.** Two **sequential** `run()` calls; the second must not see what the first's steps added. *Mutation: hoist the state object or a cached `params` to module scope → the second read is populated.* ⚠️ Needs no concurrency; the same row's *cross-request-leak in a reused isolate* clause is otherwise unchecked until the sibling lands.
- 🔒 **Order decides between two entries that can both take one request**, and the earlier wins. *Mutation: iterate the table in reverse → the wrong handler answers.*
- 🔒 **The runner module imports nothing of `nebula-auth`'s own.** `grep -nE 'parseId|AccessEntry|matchAccess|hasDominionOver' ` over the runner's files returns nothing, and its only imports are its own types. *Mutation: have the runner import `parseId` to validate a capture → reds.* ⚠️ **This is where goal 3 is checkable, not in the mini-app** — the app lives under `test/` and would import the runner relatively either way, so grepping it for the string `nebula-auth` tests an import spelling rather than a dependency. The app's own limb is narrower and still worth asserting: **its only pipeline import is the runner module.**

**Verifier panel: both phases CONFORM.** Four of its minor findings were fixed rather than filed:

- 🚨 **The table's `method` was compared raw.** The platform normalises only the standard verbs — measured: `{method:'get'}` arrives as `GET`, `{method:'patch'}` stays `patch` — so an entry spelled `'get'` could never match and the request 405'd **silently**. The table's method is now uppercased at compile time. The request's is deliberately NOT: HTTP methods are case-sensitive (RFC 9110 §9.1), and the mutation removing that half reddened nothing, which is what exposed it as dead code rather than untested code. This one mattered because the sibling hand-writes every entry against that field.
- **The settled name `routeState` was absent from source** — the type was `RouteParams` and the step's parameter `state`, while the sibling is already written against `routeState`. Renamed to `RouteState` / `routeState`.
- **The 405 carried no `Allow`**, which RFC 9110 §15.5.6 requires and only the table can build.
- **No test said why `/live` was declined**, which `live.md` and `testing.md` both state as a MUST. The reason now heads the test file, naming the sibling as the tier's owner.

Also strengthened: criterion 10's *later step* and *handler* limbs had collapsed onto one mechanism (only handlers read what a step added), so `auditActorStep` now reads `token` between `authGuard` and the handler.

## Non-goals

- **Migrating `router.ts`.** [nebula-registry-route-guards.md](nebula-registry-route-guards.md)'s, which owns the route table and consumes this runner.
- **The guards themselves** — `parseScopeGuard`, `passageGuard`, `dominionOverScopeGuard`, `turnstileGuard`, `sameOriginGuard`. Named here only as examples of the contract; the sibling builds them.
- **The entrypoint's outer router.** § *Decisions* says why it is not migrated.
- **Landing in `packages/routing`.** § *Decisions* carries the argument; revisit only when a second consumer exists.
- **A predicate callback in place of `method`.** § *Design considerations* records why the extension is obvious and why it is not built.

- **Policing that a consumer declares a `method` on every entry.** The runner treats an absent one as any verb by design; the sibling carries 🔒 *Every entry in the table declares a `method`* so the Registry's own policy is checkable there.
