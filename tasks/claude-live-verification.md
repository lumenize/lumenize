## Why

Today I verify with unit/integration suites, then report "done." That misses whole-system truth — the chat-history gap and the preview-cold-boot gap were both **shipped-green but broken in the live UI**, found only by Larry using prod. The fix is a harness that lets **me** drive and inspect a *running* Nebula (local `wrangler dev` first; prod later) as an authenticated identity, so self-verification is part of my build cycle.

**Non-force-fit ethos (how the harness is used):** for any goal, go as far as possible on existing capability; where I hit a real wall, **name the missing framework capability and propose it** rather than contorting Nebula around it (CLAUDE.md: Nebula fighting a package API is product feedback).

## What already EXISTS — reuse, don't rebuild (verified 2026-07-05)

- **Local drive stack** — `apps/nebula/test/ui-smoke/global-setup.ts` boots `wrangler dev` (+ Docker + vite) via `spawnWranglerDev` (`@lumenize/testing/wrangler`), drives the rendered Studio with raw Playwright, wipes `.wrangler/state` each run (so every scope starts **fresh**), and logs in via **real magic-link** — on-Cloudflare, WS-delivered instantly (~<1s warm; cold-start-only 50–100s), via the deployed email-test Worker. **Trapped in a vitest project + fixed test** — that's what we lift out.
- **⚠️ Token shape — the base mint is NOT enough for Nebula.** `createTestRefreshFunction` (`packages/mesh`) signs a JWT via `@lumenize/auth` `signJwt` with a **flat `isAdmin`** and **no `access` field** — the *base* mesh/auth shape. But **Nebula authorization keys on `access.authScopePattern` + `access.admin`** (`nebula-auth/router.ts:462`, `dag-tree.ts:159`), minted **only** by `nebula-auth` `#generateAccessToken` (`:1387`) for a **DB-promoted subject**. So a base-minted token is the wrong shape for a Nebula scope. **Correct token, two ways:** **(local)** a `createNebulaTestToken` test-util that **reuses (factor out to share, don't copy)** nebula-auth's `access`-claim construction → correct shape, signed with the `.dev.vars` key, **no email**; **(login/prod)** real login → nebula-auth promotion → `#generateAccessToken`. (Active key for any signing: `activeKey = env.PRIMARY_JWT_KEY || 'BLUE'` → `JWT_PRIVATE_KEY_${activeKey}` — `lumenize-auth.ts:1268`; never hardcode BLUE.)
- **⚠️ Identity domain constraint:** the harness identity is `claude@lumenize.io` — the `@lumenize.io` domain is **required for any login path** so the magic-link is machine-readable (routed to the deployed email-test Worker, same mechanism as `test@lumenize.io`); a non-`@lumenize.io` identity can't complete a real login here. (The *local mint* path needs no email, but keep the identity `@lumenize.io` so login/prod work uniformly.)
- **Promotion has two triggers** (`#loginSubject`, `nebula-auth.ts:1321`): **founder** (`subjectCount===0` — first email into a *fresh* instance → admin **of that scope**, no list) and **bootstrap** (email in the seed list → admin; at `nebula-platform` → global **`*`** super-admin). Founder is per-scope and needs no config; `*` needs the seed list.
- **Client** — `LumenizeClient` (mesh) connects to a gateway URL with a `refresh` fn; bench harness-clients already drive it. `callAsync`/`subscribe`/`resources.*` surfaces.
- **Admin identity model** — `delegated-token` act-as, `NebulaAuthRegistry.discover`, `resetDevData` wipe, `wrangler tail` (prod logs), `/_version` liveness.
- **Interactive browser MCP** (this session) — `mcp__Claude_Preview__*` + claude-in-chrome. Good WITH a human watching; not the unattended path.

No bootstrap-array, no production `nebula-auth` change. (Cross-scope `*` reach — scopes `claude@lumenize.io` didn't found — is the Phase-3 bootstrap-array; **prod** tokens come via audited login/refresh, never a local mint.)

3. **API/inspection client** — a Node `LumenizeClient` + the login-minted token to query/subscribe/transact/inspect any resource in a scope. **This IS "Turn-log inspection v0"** — for *own-scope* it's Phase 1; the *cross-user fanout* form needs `*` (Phase 3). ⚠️ **m2 — it is a mesh CLIENT:** driven via `NebulaClient` `resources.*`/`subscribe`/`callAsync` only — **never raw stub RPC or DO-internal access**, and `callAsync` is its *only* awaitable (`mesh.md` bright line; net-new client code). If inspecting a surface `NebulaClient` lacks, that's mesh/nebula product feedback to surface, not a reason to drop to raw RPC.

## Capability wishlist (deliberately not minimal)

This is what makes explore-first ("pull it up before acting", per the `/live` rule) a comfortable default rather than a tax. Best for read-only inspect (a *mutating* scenario against a live instance would pollute it; keep those on the fresh-boot path).

## Security invariants (powerful, dual-use tooling)

- The signing key (`JWT_PRIVATE_KEY_${PRIMARY_JWT_KEY}`, the **prod** key) lives in `.dev.vars` — loaded by `wrangler dev` too, **never committed**. **Local:** `createNebulaTestToken` reads it to mint a fresh per-run token (like `createTestRefreshFunction`). **Prod:** the harness gets tokens via audited login / stored-refresh — it does **NOT** locally-mint a prod `*` token (that would be the M1-flagged highest-risk artifact).
- **Bootstrap knobs go in local `--var` / vitest `miniflare.bindings`, NEVER a production worker's committed `vars`** (`packaging.md` §Environment variables). *(Note: there is currently NO `audit-test-mode.sh` guard for `*_BOOTSTRAP_EMAIL` — the script scans `*_TEST_MODE` only. If a committed-config guard is wanted, **extending the audit is an explicit Phase-3 deliverable**, not an assumed safety net.)*
- `claude@lumenize.io` as a standing `*`-admin is a **Phase-3** capability: writes attributable (audit), default to the `claude` sandbox; prod writes deliberate and rare. Phase 1's local token is scoped to `claude@lumenize.io`'s own sandbox — no `*` power.
- Minting a prod-valid admin token (Phase-3 (d), if built) uses the prod signing key — legitimate but privileged.
