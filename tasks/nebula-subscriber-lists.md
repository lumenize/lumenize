# Subscriber-lists — subscribe to a subscription's subscriber-list, + reactive-store (`lmz.*`) wiring for lists & profiles

**Status**: Framing review DONE (2026-07-15) → decision: **build both now**. Multi-user chat — the gated-next milestone this whole line of work exists for — is the roster's near-term consumer, so the mechanism is **needed next, not YAGNI**. Standalone stays pinned. Pending Stage-2 conformance, then `/build-task`. Supersedes the presence build (see § Relationship for what's reused vs replaced).

## Objective (target, present tense)
A client **subscribes to the live subscriber-list of any reachable query** — the distinct-by-`sub` set of `{ sub, profileId }` for everyone *currently subscribed* to that query's data (the live `QuerySubscribers` set, maintained by the subscribe/unsubscribe lifecycle — NOT message-author history) — **standalone** (no need to subscribe to the data itself), delivered reactively into **`store.lmz.querySubscribers.*`**. A consumer resolves each `profileId → display` by reading **`store.lmz.profiles[profileId].value`** (windowed automatically). Generic across hosts (Star + DevStudio compose the same capability).

**Why now (persona / strategy):** this is not collaboration-first speculation. **Multi-user chat is the committed next milestone** (gated behind this work + a few others), and a live participant roster is a direct requirement of it — coach-loop-adjacent shared-session display, the ~10% multi-user substrate, not a general collaboration surface. The single-player half (a user seeing their *own* name/avatar via `store.lmz.profiles[myId]`) is usable the moment it ships. So both halves clear strategy check #3 on their own merits: profiles are single-player-useful today; the roster is the next milestone's requirement, built with its consumer in view.

## Pinned decisions (settled with the user, 2026-07-15 — do NOT re-litigate)
1. **Standalone, not coupled.** Subscribing to a query's subscriber-list is its own subscription — a **watcher-registry** tracks who's watching the list, a separate audience from the query's data-subscribers. The deciding reason: we expose rosters as **first-class store paths** (`store.lmz.querySubscribers.*`) for DX, and *given that*, coupling the roster to the data-sub would make a roster-path read **silently open a subscription to the message data** (load every message just to render "who's here") — a footgun against the no-footguns wedge. Standalone keeps roster-path reads roster-only. (The near-term consumer — multi-user chat's participant list — *does* data-subscribe, so it wouldn't strictly need the decoupling; the footgun-avoidance is what makes standalone correct regardless.)
2. **`lmz.*` namespace for both** the subscriber-list and Profiles — NOT `resources.*`. `store.resources.<type>.<id>`'s `<type>` segment is the **dev-user's own ontology type name** and the factory **routes off it**, so `store.resources.Profile` would collide (name *and* routing ambiguity) with any app that has a `Profile` type → it would force reserving `Profile` as a forbidden type name (a footgun). `lmz.*` is the framework namespace (`connection`, `orgTree` already live there); `profiles` and `querySubscribers` join them. Neither adds a new top-level reserved name.
3. **Profile is a resource shape, hosted globally, surfaced at `store.lmz.profiles[id].value`.** eTag **already exists** (forward-only ULID in the built Profile DO — `profile.ts`); **no history** (last-writer-wins) and none needed. **One small Profile-DO change** (conformance-required — see § BLOCKER fix in Phase 1): the DO fires a **dedicated `@mesh handleProfileUpdate(profileId, snapshot)`** client receiver instead of `handleResourceUpdate('Profile', …)`, so the platform profile never shares the resource-type keyspace/routing with a dev-user ontology type named `Profile` (Decision 2). Everything else is client/factory wiring.
4. **The roster is a DISTINCT-by-`sub` array** `[{ sub, profileId }]` — so `v-for` is trivial (`v-for="{ sub, profileId } in …"`), re-rendering live on join/leave. (Vue `v-for` handles objects too, but an array is the right shape for an ordered roster.)
5. **Profile-resolution is a dev-user PATTERN, not built-in.** The consumer subscribes to the list, then subscribes to the individual profiles it renders (windowed — 25 of 1000 via `.slice()`/virtual-scroll). The store's read-triggered auto-subscribe makes "only visible profiles subscribe" automatic; we do NOT auto-resolve all profiles.
6. **Two roster store surfaces — build BOTH** (§ Client + factory):
   - **(a) query-in-path** `store.lmz.querySubscribers.<typeName>.<field>[value]` — the path segments *are* the `parentChild` query, so a read auto-subscribes (pure declarative, no hash, no explicit subscribe). Accepts the `parentChild`-shape coupling for v1 (future `queryType`s extend the grammar or use (b)).
   - **(b) named** `client.subscribeQuerySubscribers(query, name)` → `store.lmz.querySubscribers.byName.<name>` — explicit subscribe + read-by-name; future-proof across any query shape. **`byName` is a reserved segment** (a dev-user ontology type named `byName` is forbidden — the single reserved word) so it can never collide with the (a) `<typeName>` first segment (kills the `name === typeName` ambiguity — a footgun the bare `.<name>` form had).
7. **Rename `presence` → `subscribers`/`querySubscribers`** everywhere ("presence" survives only as a documented *use case*). Aligns with the existing `Subscribers`/`QuerySubscribers` tables.

## API surface (imperative + declarative)
| Thing | Namespace | Imperative | Declarative (Vue template) |
|---|---|---|---|
| dev-user resource | `resources.*` | `client.resources.subscribe(type, id)` | `store.resources.Document[docId].value.title` |
| **Profile** | `lmz.*` | `client.subscribeProfile(id)` | `store.lmz.profiles[profileId].value.name` |
| **subscriber-list (a)** | `lmz.*` | *(read-triggered — none)* | `store.lmz.querySubscribers.Message.session[sessionId]` |
| **subscriber-list (b)** | `lmz.*` | `client.subscribeQuerySubscribers(query, name)` | `store.lmz.querySubscribers.byName[name]` |

Canonical consumer (chat roster), windowed:
```vue
<script setup>
const q = { queryType:'parentChild', typeName:'Message', field:'session', value: sessionId }
client.subscribeQuerySubscribers(q, 'chatRoster')      // (b); or omit for the (a) query-in-path form
</script>
<template>
  <li v-for="{ sub, profileId } in store.lmz.querySubscribers.byName.chatRoster.slice(0, 25)" :key="sub">
    <img :src="store.lmz.profiles[profileId].value.picture" />
    <span>{{ store.lmz.profiles[profileId].value.name }}</span>
  </li>
</template>
```

## Server design — the standalone subscriber-list
The roster **content** is the data-subscribers of query Q (`QuerySubscribers.forQueryHash`, projected distinct-by-`sub` to `{ sub, profileId }`) — **reused verbatim from the presence build** (the `profileId` capture, `#rosterFor` dedup, the `isNewSub`/`rowsWritten` change guards). What changes is the **audience**: the roster is delivered to a **separate set of watchers**, not the data-subscribers.
- **New watcher registry** (`QuerySubscriberListSubs` — final name at build) — a separate table, keyed `(queryHash, clientId)`, `WITHOUT ROWID`, holding `{ queryHash, clientId, subscriberBinding, subscribedAt }`. **Separate from `QuerySubscribers`** so a watcher registration never enters the data commit/rerun scan (echo-free by table-separation — the original design intent). A near-clone of `TreeSubscriptions` (clientId-keyed, no `sub`/permission), but keyed by `queryHash` too.
- **`@mesh subscribeQuerySubscribers(query)` / `unsubscribeQuerySubscribers(queryHash)`** on Star + DevStudio (via `ResourceDataPlane`): register the watcher (identity from `callChain`, reachability-gated like every subscribe entry) + deliver the **current roster** to the joining watcher (single-target — this is the ONLY "initial roster to a joiner" path). A watcher joining does NOT change the roster content → no re-push to other watchers. **Fail-closed validation**: run the same `#validateQuery` `doSubscribeQuery` uses (known `queryType`, to-one field, supported `orderBy`); on failure reject the watcher handle (Error keyed by `queryHash`) — else a typo'd/malformed watcher query registers a watcher whose `queryHash` matches no validated data-sub → a permanently-empty, silent roster (a footgun).
- **Re-push on content change**: ONLY when Q's data-subscriber set *actually* changes — a **new-`sub` join** (`doSubscribeQuery` `isNewSub === true`) or an **actual removal** (`removeQuerySubscriber` `rowsWritten > 0`) — fire `#broadcastRoster(queryHash)` → project the roster → deliver to the **watchers** (`QuerySubscriberListSubs.forQueryHash`), via `svc.broadcast`. **No else-branch delivery**: a non-`isNewSub` join (2nd tab / reconnect) fires ZERO roster pushes — **remove** the presence build's else-branch that single-target-delivered the roster to the joining *data-subscriber* (post-rework that target has no binding for it: a wasted cross-Gateway push that violates Decision 1's roster⇒watchers-only). (Contrast the presence build, which delivered to the data-subscribers.)
- **Cleanup**: a dead watcher's row dropped on a failed roster push by a **dedicated** `@mesh onQuerySubscriberListBroadcastResult(queryHash, result?)` (Star + DevStudio) → a new `removeQuerySubscriberListWatcher(queryHash, clientId)` that drops **only** from `QuerySubscriberListSubs` and does **NOT** re-fire `#broadcastRoster`. ⚠️ **Do NOT reuse `onQueryBroadcastResult`** — it reaps the `QuerySubscribers` *data* table and re-broadcasts, so reusing it would (a) never reap the watcher table (dead watchers leak) and (b) for a **dual-role** client (data-subscriber AND watcher of Q — the chat participant) a failed roster push would delete its *data* row and silently unsubscribe it from message data.
- **Ontology-install cleanup**: `Star.#installState` must also drain the watcher registry — add `clearWatchers()` and **union** its dropped `(subscriberBinding, clientId)` into the single `OntologyStaleError` signal set (alongside `clearSubscribers()`/`clearQuerySubscribers()`), so a watcher whose watched type/field an install removed is cleared + signalled, not left silently stale (the near-term chat consumer data-subscribes so it's covered incidentally; the standalone watcher is not).
- **Mesh-legal + intra-Star** (unchanged from the presence analysis): no raw registry/PROFILE from platform DOs; the roster fans to same-Star watchers sharing the Star's `aud`, so no Gateway `onBeforeCallToClient` fence needed.
- **ADR-008**: reachability-gated (a Star member may watch any reachable query's subscriber-list), no per-resource read-gate; the roster carries `{ sub, profileId }` only.

## Client design
- **`client.subscribeQuerySubscribers(query, name?)`** — registers the watcher (routes `lmz.call(host, activeScope, …subscribeQuerySubscribers(query))`), returns a **disposable handle** (see Handle contracts); the delivered roster lands in the reactive store (§ factory). `name` keys the store path for surface (b); omitted for the read-triggered (a) path.
- **`@mesh handleQuerySubscribersUpdate(queryHash, roster)`** — receives the roster push and writes it into the store (via the factory adapter), keyed so both the (a) query-path and (b) named path resolve.
- **`client.subscribeProfile(id)`** — already built (routes `lmz.call('PROFILE', id, …)`); gains the disposable/refcount contract in Phase 1 (see Handle contracts). The factory makes `store.lmz.profiles[id]` route through it.
- Reconnect: the client re-establishes watcher (and profile) subscriptions on reconnect (mirrors the query-sub reconnect walk).
- **Handle contracts (pin now — the factory holds all three shapes uniformly):** the factory's 0→1 auto-subscribe holds the returned handle and calls `handle.snapshot.catch(...)` to surface failures (`componentHandles: Map<string, ResourceSubscription>`, `create-nebula-client.ts:159/216`), then disposes at 1→0. So every held handle needs a **common shape**: `[Symbol.dispose]` + an error-surfacing promise. ⚠️ `subscribeProfile` currently returns a **bare** `Promise<Snapshot|null>` and 3 shipped test sites `await` it then read `?.value` — a Disposable is not thenable, so **change it to return `{ snapshot: Promise<Snapshot|null> } & Disposable`** (the existing Promise becomes `.snapshot`) and **migrate those 3 sites** (`profile-subscribe.test.ts:147/160/174`) to `.snapshot`. `subscribeQuerySubscribers` returns `{ ready: Promise<void> } & Disposable` (the roster's error-surface analog is `.ready`, not `.snapshot`). Widen `componentHandles`' value type + the `.snapshot.catch` hold-path to the common `Disposable & { snapshot?; ready? }` (branch per prefix), and widen the `StoreClient` seam (`frontend/types.ts`) so the MockClient recorders match structurally.

## Frontend factory (`create-nebula-client.ts`) design (grounded 2026-07-15)
**Two matchers, both `resources`-scoped by different mechanisms** — I change only the read one: **READ→subscribe** is an array-segment check (`path.length===2 && path[0]==='resources'`, ~L400/L412 — NOT the `^resources\.` regex); **WRITE→transaction** IS the `^resources\.` regex (~L497). Profiles + rosters are **read-only**, so the write regex stays `resources`-only; my edits touch the **read matcher + routing + fanout-landing** only. **`lmz.*` is push-only today** (`connection`/`orgTree` written via `internalDeepWrite`, never read-triggered — confirmed); (A)/(B) **add read-triggers** to `lmz.profiles`/`lmz.querySubscribers` (net-new). Reactive arrays of plain objects (`{sub, profileId}[]`) are fully `v-for`-reactive (`isWrappable` covers arrays/Maps/Sets/plain objects).

**Common edit surface** (all localized to `create-nebula-client.ts` + `frontend/types.ts` + the MockClient): widen the `StoreClient` seam (`frontend/types.ts` — the real `NebulaClient` already satisfies it) to expose `subscribeProfile`/`unsubscribeProfile`/`subscribeQuerySubscribers`; add a **prefix→method dispatcher** where `incrementRefcount` hardwires `client.resources.subscribe(rt, rid)` (~L216); extend the read matcher (~L412) + seed the new subtrees (~L114); branch the adapter's `applyFanout` (~L545) to land non-`resources` snapshots at their `lmz.*` path.

- **(A) `store.lmz.profiles[id].value.*` → `subscribeProfile(id)`.** Read matcher `path.length===2 && path[0]==='lmz' && path[1]==='profiles'` → `profileId=key` → 0→1 calls `client.subscribeProfile(profileId)`. ⚠️ **Dedicated profile channel (BLOCKER fix — the platform profile must NOT reuse the resource-type keyspace/routing, or it collides with a legal dev-user `Profile` type, Decision 2):** the Profile DO fires a **dedicated `@mesh handleProfileUpdate(profileId, snapshot)`** → a **dedicated store adapter** lands it at `lmz.profiles[id].value/meta`. The shared `applyFanout` gets **NO `rt==='Profile'` branch**; the client keeps profiles in a **dedicated `#profileSubs` map** (bare `profileId` key), and `#resubscribeAll` walks it in a **dedicated branch** (always → `PROFILE`), so it no longer branches on `resourceType==='Profile'`. **This also fixes a SHIPPED bug** (`nebula-client.ts:771`, committed `2a2978b`): today a dev-user `Profile`-typed resource is silently re-subscribed to the global PROFILE DO on every reconnect. The client-side disposable/refcount lifecycle is pinned in § Client design (Handle contracts) + Phase 1.
- **(B) `store.lmz.querySubscribers.<typeName>.<field>[value]` (query-in-path).** Read matcher `path.length===4 && path[0]==='lmz' && path[1]==='querySubscribers'` → build `{ queryType:'parentChild', typeName:path[2], field:path[3], value:key }` → 0→1 calls **`client.subscribeQuerySubscribers(query)` — the STANDALONE method (roster only), NOT the coupled `subscribeQuery`+`presenceRoster`** (which would subscribe you to the message DATA — Decision 1). It must return a **disposable handle** (so the hold-and-dispose machinery works); the roster lands via `handleQuerySubscribersUpdate` → a new adapter method writes the array to `lmz.querySubscribers.<type>.<field>[value]` (the client maps `queryHash → store path`). Seed `lmz.querySubscribers` + extend the 4-level vivification.
- **(C) `store.lmz.querySubscribers.byName[name]` (named).** Imperative `client.subscribeQuerySubscribers(query, name)` (or a factory `store` method) holds the standalone handle + mirrors the roster into `lmz.querySubscribers.byName[name]` on each update. **No read-trigger** → thinnest wiring; `(B) = (C) + the read-trigger`. The `byName` segment keeps (b) out of the (a) `<typeName>` keyspace.

**Tests** (jsdom `frontend` project): synthetic-scope (`factory-basics.test.ts` pattern) + real-component mount/unmount (`q4-auto-subscribe.test.ts` pattern, asserting subscribe on mount / unsubscribe after the 2s grace). Extend `MockClient` (`test/frontend/mock-client.ts`) with `subscribeProfile`/`unsubscribeProfile`/`subscribeQuerySubscribers` recorders + `simulateProfileFanout`/`simulateRoster` helpers (mirroring `subscribe`/`simulateFanout`).

## Phases (Goal + capable-of-failing criteria)
**Build order:** the profile half ships first as a self-contained, single-player-testable increment; the roster half then builds on the same factory machinery. Both halves share ONE hot file (`create-nebula-client.ts`), so they stay in this single pass — do NOT split across worktrees/PRs.

### Phase 1 — Profile subscription lifecycle + dedicated (collision-free) profile channel
**Goal:** the client can subscribe AND unsubscribe a single profile, refcount-managed, via a channel that does NOT share the resource-type keyspace — so a dev-user `Profile` type can't collide (BLOCKER fix). One small Profile-DO change; the DO `unsubscribe()` already ships (`profile.ts:123`).
- [ ] **Dedicated channel (BLOCKER fix)**: the Profile DO fires `@mesh handleProfileUpdate(profileId, snapshot)` (a dedicated receiver, NOT `handleResourceUpdate('Profile', …)`); the client keeps profiles in a dedicated `#profileSubs` map (bare `profileId` key). Capable-of-failing: subscribe a dev-user resource of a type named `Profile` **and** a global profile → assert distinct registry entries + distinct routing (they never share a `Profile:${id}` refcount entry).
- [ ] **Shipped-bug fix**: `#resubscribeAll` walks `#profileSubs` in a dedicated branch (always → `PROFILE`) and no longer branches on `resourceType==='Profile'`. Force a reconnect with a dev-user `Profile` resource subscribed → it re-subscribes to its **Star** (not the global PROFILE DO); reds against today's `nebula-client.ts:771` behavior.
- [ ] `NebulaClient.subscribeProfile(id)` returns `{ snapshot: Promise<Snapshot|null> } & Disposable` (the current bare `Promise` becomes `.snapshot`); **migrate the 3 shipped await-sites** (`profile-subscribe.test.ts:147/160/174`) to `.snapshot`. A 2nd `subscribeProfile(id)` coalesces (`#subscribeRefcount`++), not a duplicate sub.
- [ ] Disposing the last handle (or `unsubscribeProfile(id)`) fires the Profile DO `@mesh unsubscribe()` **routed to `PROFILE`, NOT the Star** (do NOT literally mirror `#disposeSubscription`, which hardwires the Star binding — mirror only its refcount/dispose *pattern*) exactly once, at refcount 0 (reds if it fires early, twice, never, or hits the Star).
- [ ] Reconnect re-establishes live profile subs.

### Phase 2 — Frontend factory: profiles surface
**Goal:** `store.lmz.profiles[id].value.*` is reactive + auto-windowed; single-player-usable on landing (own name/avatar).
- [ ] Reading `store.lmz.profiles[id].value` auto-subscribes via `subscribeProfile` (routes to `PROFILE`, NOT the Star) on 0→1; a **dedicated adapter** (fed by `handleProfileUpdate`, NOT the shared `applyFanout rt==='Profile'` branch) lands the snapshot at `lmz.profiles[id].value/meta`.
- [ ] **No collision with a dev-user `Profile` type**: a dev-user `Profile` resource's fanout lands at `store.resources.Profile[id]` (the normal resource path), NOT `lmz.profiles` — reds if the platform-profile landing hijacks it.
- [ ] Unmount → after the 2s grace, `unsubscribeProfile` fires (1→0) — asserted with a real component mount/unmount (`q4-auto-subscribe.test.ts` pattern).
- [ ] **Windowing**: a 25-of-N `v-for` over profile ids opens 25 profile subs, not N.

### Phase 3 — Server: standalone subscriber-list
**Goal:** a watcher subscribes a query's live roster WITHOUT being a data-subscriber; the roster re-pushes to watchers on any data-subscriber join/leave.
- [ ] New watcher registry `QuerySubscriberListSubs` (`(queryHash, clientId)` PK, `WITHOUT ROWID`), **separate table** from `QuerySubscribers`.
- [ ] `@mesh subscribeQuerySubscribers(query)` / `unsubscribeQuerySubscribers(queryHash)` on Star + DevStudio (identity from `callChain`, reachability-gated); a joining watcher gets the current roster (single-target), and joining does NOT re-push to other watchers.
- [ ] **Fail-closed validation**: an invalid/typo'd watcher query is rejected (Error keyed by `queryHash`), parity with `doSubscribeQuery`'s `#validateQuery` — reds if a malformed query registers a silent, permanently-empty watcher.
- [ ] **Standalone**: a watcher that is NOT a data-subscriber still receives the roster (reds if delivery is tied to the data-subscriber set).
- [ ] **Watchers, not data-subscribers, receive the re-push**: on a data-subscriber join/leave, `#broadcastRoster` delivers to `QuerySubscriberListSubs.forQueryHash` — a data-subscriber who is NOT a watcher gets NO roster push; a watcher who is NOT a data-subscriber DOES.
- [ ] **No dead else-push**: a non-`isNewSub` data-sub join (2nd tab / reconnect) fires ZERO roster pushes (reds if the removed else-branch still single-target-delivers to the joining data-subscriber; the reused `presence.test.ts` shape must be updated, not carried).
- [ ] **Roster content = distinct-by-`sub` `{ sub, profileId }`** — reuse the presence projection + its mutation-checks (dedup-by-`sub` / defined-profileId-wins / non-null profileId end-to-end / never `accessAdmin`). Keep `QuerySubscribers.profileId` + `isNewSub` + `rowsWritten`.
- [ ] **Dedicated dead-watcher reap**: a failed roster push drops ONLY the watcher's `QuerySubscriberListSubs` row (`removeQuerySubscriberListWatcher`), NOT its `QuerySubscribers` data row, and does NOT re-fire `#broadcastRoster`. Capable-of-failing for a **dual-role** client (data-subscriber AND watcher of Q): after a failed roster push it keeps its data row, loses only its watcher row — **assert BOTH tables** (they share the `(queryHash, clientId)` key, so a watcher-count-only check false-passes).
- [ ] **Echo-free (behavioral, capable-of-failing)**: after `subscribeQuerySubscribers`, the watcher receives a `handleQuerySubscribersUpdate` (roster) but **NO** `handleQueryUpdate` (data) push, and `QuerySubscribers.forQueryHash(queryHash)` count is **unchanged**. Reuse the presence build's positive-signal pattern (`queryUpdateCount`) — reds if the registration leaks into the data commit/rerun scan. (A bare "no debug marker" assertion is vacuously green — the separate table emits none.)
- [ ] **Ontology-install**: an install drops the watcher's row and signals it one `OntologyStaleError` (unioned via `clearWatchers()`), like the two data registries — reds if a watcher survives an install of its watched type silently.
- [ ] Reachability-gated, no per-resource read-gate; mesh-legal (no raw RPC); Star + DevStudio genericity (same capability both hosts).

### Phase 4 — Client channel
**Goal:** the client subscribes the roster and lands it in the store.
- [ ] `subscribeQuerySubscribers(query, name?)` returns a **disposable handle**; `handleQuerySubscribersUpdate(queryHash, roster)` maps `queryHash → store path` and writes the array.
- [ ] Reconnect re-establishes watcher subs. The old `presenceRoster` accessor / `QueryEntry.roster` are gone.

### Phase 5 — Frontend factory: roster surfaces (a) + (b)
**Goal:** both roster store paths work; the array is `v-for`-reactive.
- [ ] **(a) query-in-path**: reading `store.lmz.querySubscribers.<type>.<field>[value]` builds the `parentChild` query, auto-subscribes via the **standalone** `subscribeQuerySubscribers` (NOT the coupled `subscribeQuery`), and the roster array renders in a `v-for`.
- [ ] **(b) named**: `client.subscribeQuerySubscribers(query, name)` lands at `store.lmz.querySubscribers.byName[name]` — a `name` equal to a `typeName` no longer collides (distinct `byName` segment).
- [ ] Unmount → after grace, the roster watcher unsubscribes.
