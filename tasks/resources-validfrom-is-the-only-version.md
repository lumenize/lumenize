# `validFrom` is a resource's only version

**Status:** Pass 2 written after the second Stage 1; Stage 2 next. Nothing gates it, and the pre-alpha roadmap waits behind it (Larry, 2026-11-06). It changes the `Snapshots` schema, so in [nebula-pre-alpha.md](nebula-pre-alpha.md)'s vocabulary it is `data`-gated and lands before the wipe.

## Conventions

A list that other sections cite gives each item a prefixed ID: `B` for a blocker in today's code, `DI` for an item of design intent, `C` for a checkable claim, and `D` for a decision. IDs follow the order items were raised, not the order shown, and are never reused, so D7 is the seventh decision made wherever its row sits, and a gap such as C4 is an item removed. A decision that answers an open question records it, as D5's "(was Q1)" does. `R2` and its siblings are requirements of the MCP Resource Events proposal, numbered there, and "the proposal's D6" is its sixth decision, not this file's.

Three words keep three roles. A transaction gets a *moment*, each snapshot it writes takes that moment as its `validFrom`, and a *version* is what a writer names to show which snapshot it read, which after this task is always a `validFrom`.

## Objective

**Each committed transaction gets one moment, which the server assigns as it commits, and that moment, the `validFrom` of every snapshot it writes, is the only version a resource has.** It orders every change in the Durable Object that holds the resources, a Star or a Galaxy today. When an outside protocol wants a version-like field, such as HTTP's `ETag` or the `revision` in the MCP Filesystems draft, `validFrom` fills it.

A moment is an ISO 8601 millisecond string, the form [ADR-011](../docs/adr/011-iso-timestamps.md) gives every timestamp: `2026-11-06T15:09:41.007Z`.

Right now, two values serve as a resource's version: (1) `validFrom`, and (2) `eTag`. The goal of this task file is to reduce that to just `validFrom`. After this change, a writer shows that it holds the most recent `validFrom` before any change is permitted.

Here is one put, today and after:

```ts
// Today: the client mints the new version and sends it
transaction(ontologyVersion, 'b3c1e7d0-…', {        // newETag, the new version
  'todo-1': { op: 'put', eTag: '9f2e41aa-…', value }, // the version it read
})
// → { ok: true, eTags: { 'todo-1': 'b3c1e7d0-…' } }
// stored: eTag 'b3c1e7d0-…', validFrom '2026-11-06T15:09:41.007Z'

// After: the server mints it
transaction(ontologyVersion, {
  'todo-1': { op: 'put', ifValidFromMatches: '2026-11-06T15:04:05.123Z', value },
})
// → { ok: true, validFrom: '2026-11-06T15:09:41.007Z' }
// stored: validFrom '2026-11-06T15:09:41.007Z', and no eTag
```

The field names in the second half are D7's.

## Context

**Why now.** The MCP Resource Events proposal ([experimental-ext-triggers-events#19](https://github.com/modelcontextprotocol/experimental-ext-triggers-events/pull/19)) asks this of a server's changes:

1. A new moment for every change to a resource, its creation and deletion included (R2). In Lumenize Resources a change is a snapshot, and its moment is the snapshot's `validFrom`.
2. Moments that strictly increase in byte order (R3), which ISO timestamps meet "only at a precision finer than the time between any two changes". Millisecond strings meet it because D10 pushes each moment past the latest one, so a moment is an ISO-shaped value minted later than the latest moment, not a clock reading.
3. One moment for a transaction that changes several resources (R4).
4. Changes that commit in the order of their moments (R5), so once a reader has seen a moment, no change at or before it can still appear. R3 orders moments as they are minted, and R5 orders them as they become visible. A server that mints a moment, awaits, and then commits keeps R2 and R3 and still breaks R5, which is B3 below.
5. A catch-up that returns every resource changed after a moment the client names (R13).

The proposal asks this of each timeline, its word for the ordered record of changes to a set of resources. In Resources a timeline is one Durable Object, so every resource a Star holds shares the Star's moments.

Resources is close. The server already stamps `validFrom`, it is already a string that sorts, and [ADR-004](../docs/adr/004-snodgrass-temporal-resources.md) already makes history the substrate.

Larry put the pre-alpha roadmap on hold to do this first, because it serves both strategies he is weighing: Nebula, and an open-source framework with Resources included.

### Blockers

Several things in `snapshots.ts`'s `Snapshots` class stand in the way.

- **B1. Coalescing gives a later transaction an earlier one's moment** (against R2 and R4). `#writeSnapshot` overwrites the current snapshot in place when the same actor writes within an hour of its `validFrom` (`if (withinWindow && sameActor)`). Say transaction T1 writes `todo-1` at `…:05.123Z`, and ten minutes later the same actor's T2 writes it again. T2 overwrites T1's snapshot in place and the row keeps `.123`, so T1 and T2 share a moment and only the `eTag` tells them apart. If T2 also writes a resource that doesn't coalesce, that resource gets T2's own moment, so T2 ends up with two.
- **B2. A moment is unique per resource, not per Durable Object** (against R3). `#calculateValidFrom` moves `Date.now()` past the batch's own current snapshots only, so two transactions on different resources in one millisecond share a `validFrom`. The backlog's *`validFrom` global monotonicity* row has tracked this since 2026-06-30.
- **B3. A moment is picked before the validator's `await`, so commit order and moment order can disagree** (against R5). Step 2 of `transaction` picks it, Step 5 awaits `facet.parseBatch`, and Step 10 writes it. Say transaction T1 picks `…:05.100Z` and awaits. T2 arrives, picks `…:05.101Z`, needs no validation because it is a delete, and commits. T1 then commits at `.100`. A reader that has seen `.101` and asks for changes after it never sees T1.

**Why the eTag goes too.** The client mints it: `newETag` is a UUID from `crypto.randomUUID()`, and the server stores it as the version. So a client chooses what the server records, and one that chooses wrong is told something false. Step 4.5a answers a transaction `committed` when any resource it names is already at its `newETag`, so a caller that passes the eTag it read as the new one, which `api-reference.md`'s per-call `newETag` override allows, is told its write committed while nothing is written. A UUID also orders nothing: compared only for equality, it cannot say which of two revisions is newer, which is why the proposal's D6 makes moments the version. [ADR-005](../docs/adr/005-optimistic-concurrency.md) gives the eTag two jobs, and `validFrom` can do both:

1. **It proves a writer holds the current snapshot.** Once coalescing goes, `validFrom` does this alone, since no two writes share one.
2. **It lets a repeated transaction be answered `committed`.** A repeat carries the same `newETag`, and Steps 4.5a and 6.5 find it already stored. With coalescing gone, history keeps every write, so the server can recognize a repeat from the snapshots it wrote instead.

Larry's second MCP prototype, `resource-webhooks-on-events`, tried at first to keep eTag semantics alive beside moments, which added complexity, and its code got clearer once moment strings were the version (Larry, 2026-11-06). So the server mints the only version, and the code says `validFrom` throughout. An eTag-like field appears only where an outside protocol expects one, and `validFrom` fills it.

The sections below set what the build must make true, what exists now and what becomes of each part, the constraints, and the decisions taken so far.

## Goals

1. **Each transaction that writes gets one moment, and no other transaction in the Durable Object has it.** Every resource the transaction writes gets that moment as its `validFrom`. Today coalescing can give two transactions one moment, or one transaction two, and uniqueness stops at the resource (B1 and B2).
2. **Moments sort in commit order.** A reader that has seen a moment and asks for later changes misses nothing. Today a moment is picked before the validator's `await` (B3).
3. **Only the server mints a version.** Nothing a client chose is stored as a version. Today the client mints `newETag` and the server stores it (Context, *Why the eTag goes too*).
4. **Every committed op is a snapshot.** History holds every version, so undo, audit and a merge base can find any of them, and each records its writer. Today coalescing overwrites some (B1). Also, a move to the node a resource is already on writes nothing, which is a bug we found while planning this task file. It should always have created a new snapshot.

## Design intent

- **DI1. A transaction's moment is assigned as it commits.** Inside the `transactionSync` that writes its snapshots, after the validator's `await`, the transaction reads the Durable Object's latest moment and takes the later of the current time and that moment plus one millisecond, compared as ISO strings, which sort as they compare because ADR-011 fixes their width (D5, D10):

   ```ts
   // One KV key, read and written inside this transactionSync; undefined at first
   const latestMoment = kv.get<string>('resources:latestMoment');
   const now = new Date().toISOString();
   const next = latestMoment
     ? new Date(Date.parse(latestMoment) + 1).toISOString()
     : now;
   const moment = next > now ? next : now;
   // … every snapshot this transaction writes gets `moment` …
   kv.put('resources:latestMoment', moment);
   ```

   A Durable Object runs one `transactionSync` at a time and the key only moves forward, so moments are unique in the Durable Object and sort in commit order: the check that a new moment is later than the latest one and the commit are one atomic step, as R5 asks. The key is written only with the snapshots, after op validation, the permission check and the conflict check, so a transaction that is refused or conflicts leaves it as it was. The result returns `moment` once the block commits. With the latest moment at `15:09:41.007Z`, a transaction in that same millisecond gets `15:09:41.008Z`, and one at `.010` gets `.010`.
- **DI2. The latest moment is the Durable Object's most recent moment**, the proposal's term for a timeline's. The next moment starts from it. It lives in one KV key, `resources:latestMoment`, which each transaction reads into a local variable and writes back (D5). A `.dev` wipe drops the plane's tables, the keys in `PLANE_KEYS` and every `ontology:` key, and keeps this one. Under D10 the latest moment can run ahead of the clock, so only the stored key makes a moment minted after a wipe later than every moment minted before it (C6).
- **DI3. A writer proves it holds the current snapshot by naming that snapshot's `validFrom`.** A put, move or delete names it as `ifValidFromMatches` (D7), and a mismatch is a conflict, decided at Step 9 as today. A create still asserts that the resource does not exist. ADR-005's monotonic pre-check rule, for checks outside the transaction, carries over: a resource whose `validFrom` has moved past the op's never moves back, so Step 4.5b may still skip a doomed validation.
- **DI4. Every committed op is a snapshot, and the client's debounce affects how many there will be.** That includes a put of the value already there and a move to the node already held, whose snapshots differ from the one before only in `validFrom`, `actingToken` and `ontologyVersion` (D11). The engine's default quiet window (1 s) and maximum wait (3 s) keep keystrokes from becoming versions (D13), and the server keeps whatever arrives. The cost lands on writes that coalesce today:
   
   - **Rows written.** An in-place update writes 1 row; a new snapshot writes 4: it closes the old row, inserts the new one, and moves the partial index's entry out and in. Writing the latest moment's key (D5) makes a one-resource transaction 5. At $1.00 per million rows written (`durable-objects.md` § *SQLite write-cost optimization*), an hour of steady typing that submits every 3 s costs about $0.006, where today's coalescing, submitting every 2 s, costs about $0.0018.
   - **Storage.** Each snapshot stores the whole value and the writer's acting token, so that hour on a 10 KB note keeps about 1,200 copies, about 12 MB, where today it keeps one. At $0.20 per GB-month that costs little, but a Star is one Durable Object, which Cloudflare caps at 10 GB, so about 830 such hours fill it. D9 accepts that growth through pre-alpha and names what reopens it.
   - **Later, compaction.** Coalescing can come back as a batch job that folds one actor's run of snapshots into its last, over history older than the oldest moment a catch-up answers from (the proposal's R21), so no client still catching up misses a moment it removes. It may run in the same pass that moves older snapshots to R2, ADR-004's offload. The backlog's *Compaction* row holds it, and `auth.md` § *Attribution* is clarified before it is built.
- **DI5. Only the server mints a version, and every name in the code for it is `validFrom`.** `newETag` is removed from the door's signature, from the client engine and from storage. Each Resources identifier that names an eTag is renamed for `validFrom` or removed with it, among them `baselineETag`, `genETag`, `meshNewETag`, `applyCommit`'s `eTag`, the store's `meta.eTag` and the `eTag` column, so a reader meets one name for the version. Nothing in Lumenize fills an outside protocol's version field yet, and the first thing that does fills it from `validFrom` (D3). Profile's `eTag` lives in Mesh and stays (D8).
- **DI6. A transaction retry is idempotent: existing checks keep it from committing twice, and a retry of one that committed is told so.**
   - **What recognition adds.** C3 already keeps a retry from committing twice, and recognition decides what the retry is told: a retry of a committed transaction is answered `committed`, with the moment it committed at, found from the snapshots it wrote, which D1 keeps. D6 says why the answer matters.
   - **Where it looks.** For each op, the snapshot that followed the version the op names: the old row's `validTo` is that snapshot's `validFrom`, so it takes one key read. For a create, the resource's first snapshot.
   - **When it is the same write.** All of those snapshots share one moment, were written under the caller's identity (`identityKey`), and hold what the op would write, compared in stored form after the validator fills `@default`s. Otherwise the precondition decides, as for any write.
   - **A case.** Say `todo-1` was at `…:05.123Z`, a put moved it to `…:41.007Z`, and the answer was lost. The client sends the same put again, naming `…:05.123Z`. That row now has `validTo` `…:41.007Z`, and the snapshot there holds the same value under the same identity, so the answer is `committed` at `…:41.007Z`.
   - **Where it runs.** Inside `transactionSync`, where Step 6.5 runs today, ahead of op validation, the permission check and the conflict check, so a write that landed is never refused after the fact, which is Step 6.5's reason today. It returns only a moment. It judges the writer by `identityKey` alone, never by the stored `access` or `aud`, so a resend under a re-minted token, or after a grant was revoked, is still recognized.
   - **How a repeat reaches the validator.** A repeat names a version that has moved on, so Step 4.5b would take it for a conflict and skip validating it. Step 4.5b now skips a suspect only when the snapshot that followed the version it names was written by another writer. That snapshot never changes once written, so the pre-check stays monotonic, as ADR-005 requires.
   - **The client keeps the later version.** When a recognized moment arrives after a later one the client already holds from fanout, the engine keeps the later `validFrom` and the value that came with it, compared as ISO strings, and drops no held fanout newer than the result.

These claims carry the design, and each can be checked.

- **C1. A client learns its own transaction's moment only from the result.** Resource fanout skips the client that wrote (`#broadcast`'s `if (row.clientAddress === originatorAddress) continue;`), so no fanout of a client's own transaction races its result.
- **C2. Having the server mint the moment costs the client no extra wait.** A client must know a resource's new moment before it can name it in that resource's next write. The client engine already holds that next write until the previous result returns, since it keeps at most one transaction in flight per resource (`debounce.ts`'s "serial per resource" rule), so the moment arrives in a result it was waiting for anyway. The claim is about one client and one resource. On the server, transactions on other resources and from other clients still interleave at the validator's `await`, as today.
- **C3. Nothing commits twice, whether or not a repeat is recognized.** Once a put, move or delete commits, its resource's `validFrom` has moved past the one the op names and never moves back, so the op's precondition fails on every later attempt. A create fails on every later attempt because the resource exists, and a deleted resource still exists as its tombstone, so an id is created at most once (Step 7's "already exists — use put instead"). Recognition only changes what a repeat is told (DI6).
- **C5. Repeats are coming, though no shipped client path sends one today.** Mesh never re-sends a message once sent (`#sendOrQueue`'s comment, "a message already SENT is never replayed"), and across a reconnect the engine keeps the original `callAsync` waiting rather than firing a new one (`setConnectionState`, and the debounce test that asserts "(A): NO re-fire"). The backlog's *A Client resends a call its socket lost* row, decided 2026-10-07, resends every call whose receipt died with its socket, and counts on `resources.transaction` and `postUserMessage` being safe to repeat, and [mesh-1-alpha.md](mesh-1-alpha.md) § *Item 11: Durable calls* builds on that row. [nebula-pre-alpha-fast-follow.md](nebula-pre-alpha-fast-follow.md) § *Item 4* plans to resend a page's unsaved writes after a reload, a sent one under its same `newETag`. After this task it stores the write's `ifValidFromMatches` and value, which is what recognition compares, and Pass 2 updates that item to say so. A timed-out transaction the app resubmits is a repeat too.
- **C6. A moment minted after a wipe is later than every moment minted before it.** The wipe keeps `resources:latestMoment` (DI2), and DI1 mints past it.
- **C7. Nothing edits a Message or a `ServedBuild` once it exists, so each one's latest moment is its creation moment.** Each is created in a transaction of its own, so no two share a moment, and sorting them by `validFrom` puts them in the order they were created. `postUserMessage` sends a create, and `ensureResource` creates only if absent (`if (this.#snapshots.read(resourceId)) return;`). The door would accept a put on either from a caller with write at the chat node; no shipped path sends one.

## Constraints

- **[ADR-005](../docs/adr/005-optimistic-concurrency.md) (Accepted) is rewritten in place** (D14), as `docs/adr/README.md` § *Forward-facing discipline* has an ADR do when reality drifts. Its commitment stands: writes are optimistic, a version only moves forward, and there are no locks, leases or dedupe ledger. Its mechanism changes: `validFrom` proves currency, only the server mints it, and a repeat is recognized from what it wrote. The client-minted `newETag` moves to its *Alternatives considered*, its title and slug drop "eTags", its one-liner in `workflow.md`'s ADR index changes with it, and its status returns to `Proposed`, since server minting and recognition are new. During pre-alpha no ADR is ratified, and Larry reads it himself (`docs/adr/README.md` § *The ratification gate*).
- **[ADR-004](../docs/adr/004-snodgrass-temporal-resources.md) (Accepted) is amended.** What rests on coalescing goes: the *Granularity is the meaningful version, not the keystroke* bullet, and one of the two reasons Context and Consequences give for a client-held merge base, that coalescing overwrites the value a client diverged from, so history may not hold it. The base stays client-held for the other reason, which still holds: it decouples the merge from history retention and the R2 offload. *Replay/idempotency checks consult committed snapshots rather than a side ledger* stays, since recognition (D6) reads committed snapshots. The Negative *Hot storage grows without bound until the R2 offload ships* grows faster (D9). Its core, history as the substrate and `[validFrom, validTo)` intervals that tile time, stays, and so does its `Accepted` status: the bullet that goes was the one exception to its rule that "every write closes the current snapshot and opens a new one".
- **[ADR-016](../docs/adr/016-record-the-acting-principal.md)**'s Corollary names "`snapshots.ts`'s coalescing compare" as the live instance of keying a record on identity, and one Alternatives row argues from the coalesce key. Recognition's same-writer check (DI6) becomes the live instance, and both are reworded.
- **[ADR-006](../docs/adr/006-resources-reference-by-id.md)**'s transaction bullet names `newETag`, and that clause changes.
- **[ADR-003](../docs/adr/003-continuation-messaging.md)** has write retry lean on "ADR-005's replay idempotency". Recognition keeps that true, so only the pointer changes.
- **[ADR-010](../docs/adr/010-random-opaque-keys.md) governs keys, and a version is not a key**, but each reason it gives against a counter can be asked of a version. A round trip to learn it: C2. Blocking idempotent creation: a repeated create is recognized (DI6). Blocking offline creation: the engine holds an offline write, naming the version it read, and the server mints the new one when it arrives. Guessable and enumerable: knowing a version lets a writer assert only that it read it. Colliding across Durable Objects: two may mint the same moment, which is harmless, since a version is compared only with another from its own Durable Object.
- **[ADR-011](../docs/adr/011-iso-timestamps.md):** moments stay fixed-width ISO strings from `toISOString()`, so a moment moved forward by a millisecond still sorts as a string.
- **`durable-objects.md` § *SQLite write-cost optimization*** prices every row this task adds.
- **Pass 1 decides no index** (Larry, at the Stage 1 gate). Indexes are thought through at Stage 2, once phases exist. The catch-up's read, every resource changed after a moment, is the one known to want an index with `validFrom` in it, likely compound.
- **The `data` gate.** The schema changes without a migration ([nebula-pre-alpha.md](nebula-pre-alpha.md) § *⑥ The wipe*).

## Beyond this task

- **The catch-up read** finds every resource changed after the client's moment, keeps current snapshots and tombstones, and hands back the latest moment as the next cursor, the proposal's `nextFrom`.
  - **The latest moment can serve as the version of a query's results,** because a resource leaving them moves the latest moment while the newest `validFrom` among those left stays put. Say `todo-1` is at `…:05.005Z` and `todo-2` at `…:05.007Z`, and `todo-2` is deleted at `…:05.009Z`. The newest `validFrom` left is `.005`, and the latest moment is `.009`.
  - **One resource's version field carries its `validFrom`** (D3): an HTTP `ETag`, or the `revision` of the Filesystems strawman ([experimental-ext-filesystems#2](https://github.com/modelcontextprotocol/experimental-ext-filesystems/pull/2)), which the proposal's R7 fills with the moment of each change.
  - ⚠️ Design consideration: a `.dev` wipe drops `Snapshots` and leaves no tombstones, so a catch-up cannot tell a client what the wipe removed. The catch-up therefore needs the oldest moment it answers from (the proposal's R21). A wipe mints one moment past the latest and makes it both the latest moment and the oldest, as the second prototype's `Timelines.wipe()` (`version-store.ts`) does, and a client whose cursor is older starts over. Keeping the key through the wipe (DI2) is what lets the wipe mint past the latest.
- **A merge base from history.** With every write kept, history holds the version a writer diverged from, so the conflict resolver could look it up instead of holding it. This task leaves the base where it is, held by the client.

| D10 | A transaction's moment is the later of the current time and the latest moment plus 1 ms, compared as ISO strings, and the latest moment's key holds an ISO string, the form `validFrom` has (DI1). This settles the backlog's *`validFrom` global monotonicity* row's open tradeoff. (Larry, at the Stage 1 gate) | **A `(validFrom, seq)` pair:** it keeps moments true to wall time, but a version stops being one string that sorts, which the proposal's R3 asks for. **A counter or a ULID:** ADR-011 keeps timestamps ISO. **The latest moment converted to epoch milliseconds:** it saves a parse per commit, but holds a moment in a second form. |
| D11 | Every committed op writes a snapshot, with no comparison of old and new. A put of the value already there, or a move to the node a resource is already on, writes one that differs from the one before only in `validFrom`, `actingToken` (when someone else writes) and `ontologyVersion` (when the transaction names a newer one). Such ops are rare: a put whose typing was undone within the debounce window, or one that writes back what it read. (Larry, at the Stage 1 gate) | **Skipping a same-node move, as today:** that resource keeps its old version, so the result needs a moment per resource, and the writer goes unrecorded. **A snapshot only when the value or meta differs:** a comparison on every op, for a rare case. **The engine skipping a put whose value equals `baseValue`, the value it read:** a check whose only gain is a little storage in a rare case. |

| D13 | The client engine's default windows move from a 500 ms quiet window and a 2 s maximum wait to 1 s and 3 s, so steady typing writes a third fewer snapshots. An app still sets its own: per type through `client.resources.transactionDebounce`, per write through `quietMs`, and per field through `@debounce` once the ontology emits it. `@longform` keeps 1 s and 5 s, so "slower" now means its longer maximum wait. (Larry, 2026-11-08, hand review, who put the defaults at the upper end of what still feels real-time, 1 to 3 s) | **Keeping 500 ms and 2 s:** with nothing coalescing, every burst of keystrokes becomes a snapshot, for a collaborator's view that is a second fresher. **Longer still, such as 5 s:** collaborators would watch each other's edits arrive late, and an app that needs sub-second updates shortens its own windows either way. |

Either would also need a new name for `orderBy`. |

(Larry, 2026-11-08, Stage 2 gate; corrected the same day, when a run with the value bound showed the index already serves those queries) | **Dropping the index:** a put would write 2 rows instead of 4, but every query over current rows would scan all of history, which D1 makes grow; at 100,000 history rows one scan costs about $0.0001 in reads, against about $0.000002 for the index's rows on a put. **Running `ANALYZE` so the planner picks the index:** a write, and statistics to keep fresh as history grows, where reading by primary key needs neither. **Leaving the current-row read as it is:** it walks every past row of the resource, and D1 makes that grow. |

## Phases

The `/live` scenario `each-transaction-gets-one-moment` is the witness for Phases 1 and 2. It signs in for real, works on `Chat`s it creates at the chat node, and gains limbs as the phases land. Each limb that answers a transaction asserts `outcome.resources[id].kind` and that resource's `validFrom`, because the default verdict for a conflict is `use-server`, which writes nothing and still rolls up to a top-level `committed`. The vitest-plugin lane carries only what a client cannot reach, and each such test says what that is.

Every phase that changes code ends on the same gate: `npm run type-check` passes, `npm test` passes in `packages/resources` and `apps/nebula` with the Test Files counts compared against the phase's start, and the task-file handle grep in `workflow.md` § *Referring to things across files* prints nothing over the files the phase changed.

1. **One moment per transaction, minted at commit, and every op a snapshot.** `snapshots.ts` mints the moment inside the `transactionSync` that writes it, from `resources:latestMoment`, and writes the key only with the snapshots (DI1, D5, D10, D12). `#calculateValidFrom` goes, and Step 9's comment stops calling its `return` a rollback. Coalescing goes with the same-node move skip (D1, D11), and `coalesceWindowMs` leaves `#bootstrapConfig`. The wipe keeps the key, and the `PLANE_KEYS` JSDoc says why (DI2). `enumerateCurrentByField`'s JSDoc says what its order is (D15). `newETag`, the op's `eTag` and the result's `eTags` still run as today, so no caller changes in this phase.
   - **A read that history no longer slows.** `#getCurrentSnapshot` and `currentTypeName` read a resource's current row by primary key, `ORDER BY validFrom DESC LIMIT 1`, which D10 makes the current one. The cross-resource queries keep their bound sentinel, which `idx_Snapshots_current` already serves. No phase adds or drops an index, and recognition in Phase 2 reads by primary key alone.
   - **Tests whose behaviour goes.** `star-resources.test.ts`'s "same sub within debounce window overwrites in place" and "move to same node is idempotent no-op" are inverted to assert a new snapshot. `mint-narrower-token-payoff.test.ts`'s two coalescing tests keep their persisted-record and wire-projection assertions and lose their row counts; their identity witnesses move to Phase 2's recognition tests.
   - **Success criteria (capable of failing):**
     - The scenario is written first and registered in `drive.ts`, and its three limbs red on today's tree:
       - *Every write is a snapshot.* The driver puts a `Chat`'s title, then puts it again a few seconds later, and the second read-back's `meta.validFrom` is later than the first's.
       - *One moment per transaction.* One transaction puts that `Chat`, which coalesces today, and creates a second one, and both read back with the same `meta.validFrom`.
       - *A move to the node it is on is a write.* Moving the first `Chat` to the chat node, where it already is, leaves a later `meta.validFrom`.
     - In the vitest-plugin lane, with `Date` alone faked (`vi.useFakeTimers({ toFake: ['Date'] })`, then `vi.setSystemTime` past the setup's latest moment), since only a pinned clock puts several commits in one millisecond. Each test is also run once with the freeze deleted, and goes red.
       - Three transactions on three resources get `.000`, `.001` and `.002`. A conflicting transaction and a permission-refused one, sent between the second and third, leave `resources:latestMoment` unchanged.
       - A put held in its validator by `applyOntologyForTest(config, holdParseMs)`, as `plane-wipe.test.ts` holds one, and a delete sent while it waits: the delete gets the earlier moment and the put the later. Only a test can stretch a validation on demand.
       - In `plane-wipe.test.ts`, commits push the latest moment ahead of the clock, the clock goes back, `resetDevData` runs, and the next commit's moment is later than every moment before the wipe. `resources:latestMoment` is still in storage afterwards.
     - In the vitest-plugin lane, since `rowsRead` is visible only inside the Durable Object: with 100 snapshots of one resource and a few others current, a read of that resource reports `rowsRead` of at most 2, and `enumerateCurrentByField` reports no more than the current rows. The second holds today and guards the index's use in workerd.

     - `git grep -nw coalesceWindowMs -- apps packages` prints nothing.

Restoring `#calculateValidFrom` gives all three pinned transactions `.000`, and writing the key at the top of `transactionSync` moves it on the refused ones. Picking the moment before the `await` reds the commit-order test, and adding the key to `PLANE_KEYS` reds the wipe test. Restoring `validTo = ?` in `#getCurrentSnapshot` reads all 100 rows, and dropping `idx_Snapshots_current` makes `enumerateCurrentByField` read the whole table.

2. **`validFrom` is the only version: ops name it, the server mints it, and a repeat is recognized.** The `eTag` column, `SnapshotMeta.eTag`, `newETag` and the result's `eTags` go. An op names `ifValidFromMatches`, and a result carries one `validFrom` (D7).    - **The docs.** The pages that teach these types change with them, since their `@check-example` blocks compile against them. So do `api-reference.md`'s query order (D15) and `coding-your-ui.md` § *Lists*, where two tabs of one person creating the same list are now both told `committed`. The platform embed is regenerated.
   - **Local state.** The `eTag` column goes with no migration, so a hand-driven `npm run dev` stack starts from a fresh `apps/nebula/.wrangler/state` after this phase.
   - **Success criteria (capable of failing):**
     - The scenario gains seven limbs:
       - *A repeated put is recognized.* The driver puts the first `Chat` naming its current `validFrom`, v0, and commits at v1, then sends the identical put naming v0 again: `committed` at v1.
       - *A repeated create is recognized.* Creating a third `Chat` twice, with one id and one value, answers the second `committed` at the first's moment.
       - *A different write is not a repeat.* A collaborator holding write at the chat node through a real invite, as `four-party-chat`'s does, sends the same put naming v0, and the driver sends a put naming v0 with a different title. Each answers `use-server`.
       - *The client advances its version.* The driver, subscribed to the first `Chat`, fires a second put before the first resolves. Both answer `committed`, the second at a later moment, and the read-back holds the second title.
       - *The client keeps the later version.* The driver puts at v1, and the collaborator puts at v2, which the subscribed driver hears. The driver resends its v0 put and is told `committed` at v1, its store still shows v2, and its next put, naming no version, answers `committed`.
       - *A resend after a revoked grant.* The collaborator commits, the owner revokes the grant with `orgTree.revokePermission`, and the collaborator resends: `committed` at the landed moment.
       - *Moves, deletes, and a mixed pair.* A repeated move and a repeated delete are each recognized. A two-op repeat whose second resource was last written by another transaction answers `use-server` for both.
     - In the vitest-plugin lane:
       - Recognition compares stored form: a type with an `@default` field, installed with `applyOntologyForTest` as `star-ontology.test.ts` installs `"medium"`, and a put leaving the field out, repeated naming the same version, answers `committed`. In-lane because the shared app's ontology has no `@default` field.
       - Recognition keys on identity: the same `sub` with a different `profileId` or `access` is recognized, and a write made under impersonation and resent from the member's own session is not. These are the witnesses the payoff tests held, moved where their tokens are already minted.
