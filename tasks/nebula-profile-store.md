## Identity schema — this task's additions
Surrogate-sub's landed shapes — the registry `Identities` / `Scopes` / `RefreshTokenIndex` / login-channel rows, the Workers-KV `RefreshTokenKV` refresh record, and the Worker JWT mint — live in `packages/nebula-auth/src/{types,schemas}.ts`; read them there, don't re-copy. This task adds exactly four things (TypeScript is the schema of record — ADR-001; timestamps ISO 8601 Zulu — ADR-011):

```typescript
// 1 · `profileId` column on the registry `Identities` row (+ its index).
interface Identity {     // + surrogate-sub's fields (sub PK, scope, email, isAdmin, emailVerified, …)
  profileId: string;     // ADDED · minted UUID · the PUBLIC address (distinct from `sub`)
}
// Index `idx_Identities_profileId` serves the reverse `profileId → scopes` lookup (scoped-admin).

// 2 · `profileId` on the KV refresh record — so `profile` survives the pure-KV refresh mint.
interface RefreshTokenKV {   // + surrogate-sub's { sub, universeGalaxyStarId, isAdmin, expiresAt }
  profileId: string;         // ADDED
}

// 3 · A bare custom `profileId` JWT claim (the UUID itself, sibling of `sub`), at JWT assembly.

// 4 · The Profile DO value (one per profileId, global; holds NO email/sub/scope).
interface Profile {
  // PUBLIC — the only fields a pushed/subscribed Snapshot carries; anyone with the profileId reads.
  name?: string;             // OIDC full name
  nickname?: string;         // OIDC display/casual name
  picture?: string;          // OIDC avatar image URL (R2)
  // (no `profile` page-URL field — YAGNI, no external profile page yet. The JWT
  //  claim is a bare `profileId`, so nothing forces this field either way.)
  // PRIVATE — owner/admin only, via a SEPARATE gated read; NEVER rides a pushed snapshot.
  privateNotes?: string;     // MD-formatted "what the LLM knows about you"
}

// INVARIANTS
//  • `profileId` minted WITH `sub` (one INSERT); the PUBLIC address; resolved LIVE off the
//    `Identities` row, NEVER copied onto grants/snapshots (those key on `sub`).
//  • sub → EXACTLY ONE profileId; profileId ← 1..N subs — the P2 unification substrate
//    (re-point a sub via a one-row UPDATE; additive). NEVER two profileIds per sub.
//  • REPLICATION (ADR-010): `sub`+`profileId` are immutable surrogates, copy freely (JWT/KV).
//    `profileId` immutable in P1; a P2 re-point mutates it → joins `isAdmin`'s convergence re-put.
```
(Prior drafts — a per-scope `NebulaAuth` DO, a `profileId` join table, `email` in the JWT — were dissolved/superseded by surrogate-sub; that history lives in [its archive](archive/nebula-auth-surrogate-sub.md), not here.)

## Why (grounded facts, verified 2026-07-08)
- **`sub` is per-scope, not global.** Surrogate-sub keys identity on the registry `Identities` table with `UNIQUE (email, universeGalaxyStarId)` — the same email in two scopes mints two `sub`s. A person has a **different `sub` per scope**; the cross-scope link is `email` (a registry-indexed lookup, never a key). (Pre-dissolution this lived in per-instance `Subjects` tables + a registry `Emails` table; the per-scope *conclusion* is unchanged.)
- **There is no global person-id today** — and because a person can use different emails per scope (corp in one, personal in another), even email doesn't reliably link them. So "one identity across Universes" is a concept that **does not exist yet** and must be *introduced* (deferred to P2).
- **Three consumers already need `sub → display identity`**: the presence roster (chat), the org-tree UI (today it can only show `abc123: admin`), and chat authorship. Resolving it once, well, is the point.
- The earlier-deferred "Nebula-knows-you" memory returns here as a cheap **private field**, not a separate store.

## Scope decision & framing (2026-07-08, Larry)
- **Build the FULL store now — deliberate; do not re-litigate the split.** The Stage-1 framing panel recommended deferring the content-store half (reactive `subscribe`, `picture`/`profile`, the private blob + owner-gate) and shipping only the resolution model. **Overridden by design:** the `profileId` rail and the private "Nebula-knows-you" blob are laid now to avoid a re-key / re-open later, and `picture`/`profile` are cheap additive fields on the same schema.
- **Within the ~90%-solo persona ([strategy.md](docs/vision/strategy.md)), this is attribution + personalization, NOT a social graph.** `profileId` + resolution is the identity substrate for `changedBy`-attribution and roster display — a near-free byproduct of already-justified features (identity-from-`changedBy`, subscribe), the same framing [chat](nebula-chat-history-multiuser.md) uses. The private blob is **single-player** (Nebula personalizing to *this* user-developer), not social. `picture`/`profile` are the **display layer of attribution** (who wrote this), not a directory / feed / follow / discovery surface — there is no profile *browsing*.

## The model (P1 — per-scope, forward-compatible with P2)
- A **new `profileId`** (UUID), a **distinct namespace from `sub`** (it becomes the *public* address — keep it decoupled from the auth `sub`). Because `sub → profileId` is **single-valued** (many subs → one profile; each sub → exactly one profile), it's a **plain column on the `Identities` row**, NOT a separate join table: a join earns its keep only for true **n:m** (a sub pointing at several profiles — which we forbid) or **per-connection metadata** (YAGNI, and the plausible P2 case — a canonical sub — is answered by the Profile DO, not link metadata). An index `idx_Identities_profileId` serves the reverse **`profileId → scopes`** lookup (the scoped-admin scope-check); the scope comes off the same row, so nothing is duplicated. (This is *cheaper* than a join table — one fewer row + index write per mint, no duplicated `sub`/scope — which matters for the 10 GB ceiling.)
- **`sub → profileId` is the single source of truth on the `Identities` row, resolved LIVE (cached)** — and **never copied onto grants/snapshots.** So P2 linking (point a second `sub` at an existing `profileId`) is **additive: no re-key, no stale copies, no "person-layer above" needed** — the `Identities.profileId` column *is* the authority (re-point = a one-row `UPDATE`).
- **P1**: one `profileId` per `sub`. **P2 (deferred)**: point `sub`s at one shared `profileId` (a one-row `UPDATE` per sub; the column absorbs it).
- **Safe-denormalization principle** (the rule that keeps it clean): denormalize the **stable KEY** (`profileId`) *only where it self-heals* — the JWT (ephemeral) and subscriber rows (ephemeral, refresh on reconnect); resolve the **churning FIELDS** (email/name/…) **and the authZ scope-set live** (a stored scope-set would go stale on P2-link / teardown — stale authZ is a security bug); **never** put `profileId` on **resource** records — grants/snapshots stay `sub`-only and resolve profileId live from `Identities.profileId` (the authoritative `sub → profileId` on the Identity row is the source of truth, not a stale copy). **Key every churny resolution off `sub`** (1:1, stable), never off `profileId` — nothing reverse-maps `profileId` → a single email/sub, which is *precisely* why P2 unification is additive: it only makes `profileId ← more subs`, leaving every existing `sub → …` lookup unchanged.

## Identity fields (OIDC-standard terminology)
Use OIDC Standard Claim names, not invented ones:
- **`name`** (full name), **`nickname`** (display/casual name), **`picture`** (avatar *image* URL — R2). *(No `profile`-page-URL field for now — it would collide with the JWT `profile` **claim**; dropped, re-addable later with a namespaced claim — § JWT decisions.)*
- **`email`** — **NOT** in the Profile store, and (post-surrogate-sub) **not in the JWT** either. It's a registry-only, per-scope **mutable** attribute; consumers resolve `sub → email` via the registry for the contextually-correct scope.
- **private markdown blob** — "what the LLM knows about this entity" (human or agent). Owner + admins only (the LLM writes/reads it *acting as the owner* — see AuthZ). Which fields are public vs private is **platform-controlled for now** (can change later).

## JWT decisions
- **`email` is NOT in the JWT** (surrogate-sub removed it — `NebulaJwtPayload` in [types.ts](packages/nebula-auth/src/types.ts) has no `email`), making it a registry-only **mutable** attribute (the cleanest ADR-010 — one copy, nothing to converge). This **reverses** this file's earlier "email stays in the JWT" call; [surrogate-sub § Blast radius](archive/nebula-auth-surrogate-sub.md) supersedes it. Display/audit consumers resolve `sub → email` via the registry; authz never keyed off it (`sub`+`access`).
- **The one claim this task adds is a bare `profileId`** — a top-level custom JWT claim (the UUID itself, a sibling of `sub`), **NOT** the OIDC `profile` claim. Private/custom claim names are explicitly allowed ([RFC 7519 §4.3](https://www.rfc-editor.org/rfc/rfc7519#section-4.3)), and this token is **first-party** (`buildNebulaJwtPayload` mints it, only Nebula verifies it — no third-party relying party to benefit from a "standard" name). It **pre-computes the `sub → profileId` hop for the bearer's own** profile (others resolve via `Identities.profileId`, cached) and **rides the `RefreshTokenKV` record** (Store 2 above) so it survives the pure-KV refresh mint. **Owner authz is then a direct equality** — `claims.profileId === this.lmz.instanceName` — with **no URL to parse and no overload footgun**. (The earlier plan overloaded OIDC's URL-valued `profile` claim to carry `/profiles/PROFILE/{profileId}/`, which forced a "never *correct* this to a real URL or you lock every owner out" hazard; a bare claim deletes that entirely.) It also **frees the real `profile` claim** for an actual OIDC profile-*page* URL if ever wanted (§ Store shape — the store's `profile` page-URL field stays dropped on **YAGNI**, no longer on collision-avoidance).
- **No `name`/`nickname`/`picture` in the JWT** — they churn; resolve them live.

## The Profile DO
- **Code home: `@lumenize/nebula-auth`** (identity/registry-infra layer — it's a raw DO that reads the registry for the scoped-admin scope-check). `apps/nebula`'s platform DOs are scope-bound business logic, so identity infra belongs with auth — **not** because a Worker can't host a global thing (the registry itself runs in the one `nebula` Worker; see the routing pre-req's wiring note). **Raw DO base (extends `DurableObject`) that COMPOSES the mesh comms core** (`lmz-api`) for its client-facing subscribe — the ADR-007 composition pattern (precedent: `NebulaContainer`/`LumenizeContainer`, the 4th type to compose it; this is the 5th). **Not `extends LumenizeDO`** — that base classifies a node **Mesh-layer** ([workers-projects.md](.claude/rules/workers-projects.md)), whose never-raw-RPC rule ([mesh.md](.claude/rules/mesh.md)) would forbid exactly the raw registry read the scoped-admin authz needs; a raw-DO-layer node that *composes* `lmz-api` legitimately does **both** (raw RPC to the registry + mesh subscribe), and needs none of `LumenizeDO`'s other machinery (`onStart`/`alarms`/`svc.broadcast`) — ADR-007 "take only the comms core." **This choice is independent of the hand-rolled fanout below** (that's fence-driven, not base-driven). This adds a new **`@lumenize/nebula-auth → @lumenize/mesh`** dependency edge (not a cycle — mesh never imports nebula-auth). Talks to the registry via plain Workers RPC (the registry is a raw DO, not a mesh node).
- **Considered + rejected — `apps/nebula` / `NebulaDO` / Resources (2026-07-14).** Two structural blocks: (1) the Profile is **global/cross-scope**, but `NebulaDO`'s guard (`onBeforeCall`→`enforceScopeReach`) derives scope via `buildAuthScopePattern(instanceName)`, which **throws on a non-tier name** — a `profileId` fail-closes *every* call (soundness "rests on name == a `parseId`-valid id" — [nebula-do.ts](apps/nebula/src/nebula-do.ts)); (2) `apps/nebula` is **mesh-only**, but the scoped-admin authz needs **raw-RPC reads of the raw registry**, native only in `nebula-auth`. (The `NebulaClientGateway` precedent shows `apps/nebula` *can* host a non-`NebulaDO`, so this is **not** a layer-purity call — it's these two blocks.) Variants weighed: **(a) override `onBeforeCall`** — legal (an ADR-007 hook, not `#private`; `NebulaDO` itself overrides it), but the *async* reach-check can't live in a *sync* hook (→ a hollow guard) **and** you'd inherit `NebulaDO`'s `@mesh` methods (`teardown`, …) whose security assumes the guard you disabled; **(b) a `NebulaHelper` base = Resources−authz** — not a clean carve (the DAG check is woven *into* resource ops — security.md) and the Profile wants none of Resources' history/OCC/ontology; **(c) carve a reusable subscribe+broadcast** — right instinct, but its home is **mesh** (à la `LumenizeClientGateway`), not a new `apps/nebula` base, and it's premature for one consumer → hand-roll now, extract on the 2nd ([backlog.md](backlog.md) § Lumenize Mesh). Net: raw DO in `nebula-auth` composing `lmz-api`.
- **Keyed by `profileId`** — instance name = `profileId`, binding = `PROFILE` (reached via mesh `lmz.call('PROFILE', profileId, …)`, not HTTP). Lazy (created on first access, like a Star). Its own durable state is the **public fields + private `privateNotes` + subscriber rows** — *not* its ownership/scopes: **ownership is a JWT check** (the caller's `profileId` claim vs this instance name), and the profile's **scope-set** resolves live from the registry (`Identities WHERE profileId = ?`) only for the **one** gated case that needs it (a scoped admin, below).
- **Public fields are OPEN; one gate (`requireOwnerOrAdmin`) covers writes + the private blob.** The `profileId` is the **public address** — an unguessable UUID you only obtain by legitimately resolving a `sub` you already hold (the public-GitHub-profile model, but the handle isn't even guessable). So:
  - **Read / subscribe the public fields** (`name`/`nickname`/`picture`/`profile`) — **no authZ beyond the Gateway's authN.** Any authenticated caller holding the `profileId` reads. **No `requireProfileReach`**, no scope-intersection, **no registry read** on this path — the hot path is gate-free. (Cross-scope visibility is intentional; the `profileId` handle is the capability.)
  - **Write public fields, and read/write `privateNotes`** — gated by **`requireOwnerOrAdmin()`**, an async method-body helper at the top of each write/blob `@mesh` method (NOT `onBeforeCall`, which is sync and can't do the registry read). Resolve **top-down, reading only if forced**:
    1. **Owner** (`claims.profileId === this.lmz.instanceName`, a **direct equality — no URL parse**) → pass, **no read**. Sound because `sub → exactly one profileId`, so owner ⟺ the JWT's `profileId` equals this instance; the `profileId` claim is **server-minted + signature-verified** (unforgeable). *(Common: LLM-as-owner blob writes; a user editing their own profile.)*
    2. **Not admin** (`!claims.access.admin`) → reject, **no read**.
    3. **Super-admin** (`authScopePattern === '*'`) → pass, **no read** — `matchAccess('*', S)` is trivially true for **any** profile scope `S`, so the scopes needn't be fetched.
    4. **Scoped admin** (`access.admin && authScopePattern !== '*'`) → the **one** path that reads: the Profile DO calls a **NEW registry method `getScopesForProfile(profileId): string[]`** (`SELECT universeGalaxyStarId FROM Identities WHERE profileId = ?` via `idx_Identities_profileId`, run *inside the registry DO* — `Identities` lives there, not in the Profile DO; the registry exposes nothing keyed on `profileId` today, so this is a build deliverable). Pass iff `matchAccess(pattern, S)` for some returned scope `S` (a different-scope admin covering none is rejected). *(matchAccess direction for a bare-ancestor scope: mechanical, settle at build.)*
  - The **LLM needs no authz identity** — it writes/reads the blob *acting as the owner* (its JWT carries the owner's `profileId` claim), passing owner short-circuit **(1)**. No reserved agent `sub` as an authZ principal (which would also break security.md — authz keys off the authority identity, never `act`).
  - **The registry read runs on the scoped-admin path ONLY** — never owner, super-admin, non-admin, or any public read. It fetches only the profile's scopes (`profileId → scopes`); the owner check is pure-JWT (no owner-subs read). Kept **fresh** (a stored scope-set goes stale on P2-link/teardown). The JWT short-circuits are **bounded-stale** (≤ the 15-min access-TTL, converge on refresh — same trust window as `isAdmin`): acceptable because P1 `profileId` is immutable and the only P2 drift is a re-pointed sub touching its *own* old profile for ≤15 min. Raw-RPC gotchas on the `getScopesForProfile` read: **await** it; it's a **public** method (a `#` method returns `undefined` over RPC → fail-**open**); narrow `using` stub; **fail closed** on error/empty. ⚠️ **It must RETURN plain data (a `string[]`; `[]` on absent), never THROW a status-carrying error** — [raw-comm.md § Errors](.claude/rules/raw-comm.md) (custom-error own-props like `status`/`errorCode` are **dropped** across raw Workers RPC → a thrown `RegistryError` arrives with `status === undefined`; return-shaped reads, or gate expected errors caller-side).
- **Resources-compatible subscribe — PUBLIC fields ONLY in the value.** The client sees it via the **same reactive store**, so the Profile DO emits `Snapshot { value, meta: { eTag } }` with a **forward-only ULID `eTag`** (the client's `handleResourceUpdate` → engine dereferences `meta.eTag`, so an eTag is *required*). ⚠️ **The subscribed / fanned-out `value` carries ONLY the public OIDC fields** (`name`/`nickname`/`picture` — there's no stored `profile` page-URL field; § Store shape); **`privateNotes` NEVER rides a pushed or subscribed snapshot** — it is served solely by a separate `requireOwnerOrAdmin`-gated one-shot read. The delivery bridge pushes the whole `value` with **no field-projection** (`star.ts` / `resource-data-plane.ts`), so the DO must build the snapshot `value` from the public subset — **not** hand it the stored record (which contains `privateNotes`). It does **NOT** do ADR-005 optimistic-concurrency conflict-checking (**last-writer-wins**) and has **no ADR-004 history** — "Resources-compatible" = reuses the store **delivery shape** only. Needs `NebulaClient` upgrades (client-side, binding-agnostic).
- **Fanout is a hand-rolled `lmz.call` loop — fence-mandated, NOT a cost of the raw base.** `svc.broadcast` is `LumenizeDO`-only ([lumenize-do.ts:485](packages/mesh/src/lumenize-do.ts)), but the load-bearing reason to hand-roll is the cross-scope `PROFILE`-fence: `svc.broadcast`'s tier-worker path (past its direct-path threshold) **rewrites `metadata.caller`**, so **even a `LumenizeDO` couldn't safely use it here** at scale — the loop would be required in either base. The Profile DO loops its own subscriber rows firing a 4-arg `onErrorOnly` `this.lmz.call('NEBULA_CLIENT_GATEWAY', clientId, remote)` where `remote` targets the client's `handleResourceUpdate`. ⚠️ **Do NOT import `NebulaClient`/`Snapshot`** (apps/nebula-owned) to type that continuation — nebula-auth sits *below* apps/nebula, so it's an **upward/circular edge** a type-only import silently passes tests on (mesh.md § dependency-direction). Use an **untyped `ctn()`** (the type param is runtime-erased) + a **local LWW payload type**, or a minimal structural `ResourceUpdateReceiver` interface defined in nebula-auth. The dead-subscriber cleanup handler `onProfileBroadcastResult` (drops the row on a `ClientDisconnectedError` fire-back) is **`public` but NOT `@mesh()`**: the fire-back lands via `__handleResponse` at `requireMeshDecorator:false`, so no decorator is needed — unlike `Star.onBroadcastResult`, which carries `@mesh` *only* for `svc.broadcast`'s tier-worker remote dispatch, a path this hand-rolled loop lacks. ⚠️ **`@mesh` here would be a client-callable DoS surface** — with the now-open `onBeforeCall`, any authenticated client holding the profileId could forge a `ClientDisconnectedError` and drop another subscriber's row. ADR-003-clean; fine at profile-scale N; keeps `metadata.caller` = `PROFILE` (no tier hop → the fence signal is reliable at any N).
- **No per-subscribe scale concern** — open read does **zero** registry reads on the subscribe/read hot path (the only read is the rare scoped-admin write). The one hot resolution (`sub → profileId` for roster display) is Phase 4's loss-tolerant cache, not a per-subscribe reach read.

## Routing model (verified — completed pre-req, not a build phase)
A profile subscribe is an **ordinary `lmz.call('PROFILE', profileId, …)`** — the existing binding+instance mechanism, no new routing. The **Gateway does authN + routing only**; authZ lives in the **PROFILE DO** (public read is open; `requireOwnerOrAdmin` gates writes + the private blob — above). The client already parameterizes the binding ([nebula-client.ts:283](apps/nebula/src/nebula-client.ts)). The **one** framework change is a PROFILE-fenced skip of the deliver-to-client aud-check (below); the acceptance for it lives in Phase 3.

### Verified mechanism (2026-07-08, code-grounded)
**Verdict: the "ordinary `lmz.call('PROFILE', profileId, …)`, authZ in the PROFILE DO" approach is viable. One small, PROFILE-fenced tweak on the deliver-to-client leg; the inbound leg needs nothing.** There is exactly **one** active-scope check — `NebulaClientGateway.onBeforeCallToClient` (the *only* override; no `onBeforeCallToMesh`/`onBeforeAccept` override — verified by grep). It is a **deliver-to-client-leg** guard, not an inbound one.

- **Inbound leg (client → mesh) — ALREADY ADMITS, no tweak.** `#handleClientCall` → `onBeforeCallToMesh` is a base passthrough (not overridden by Nebula); it forwards `(binding, instance)` verbatim to `env[binding]`. Nothing ties the *callee* instance to `activeScope` — `onBeforeAccept` only validates the *client's own* connection name (`{sub}.{tabId}`). So `lmz.call('PROFILE', profileId, …)` is forwarded untouched; the PROFILE DO's authZ (open public read; `requireOwnerOrAdmin` on writes/blob) applies. ✅
- **Deliver-to-client leg (mesh → client) — NEEDS THE FENCED TWEAK.** `onBeforeCallToClient` asserts `envelope.callContext.originAuth?.claims.aud === connectionInfo.claims.aud`. This passes for Resources only because **all same-Star subscribers share the Star's `aud`** (locked by `enforceScopeReach`) and the fanout **inherits** the mutator's `originAuth` ([broadcast.ts:138-141](packages/mesh/src/broadcast.ts) — no `newChain`). A **global profile** has subscribers across *different* scopes (ADR-008-extended visibility), so the push's origin `aud` ≠ a cross-scope subscriber's connection `aud` → **rejected.** `newChain:true` doesn't help (origin `aud` → `undefined` ≠ subscriber `aud`); per-subscriber re-mint defeats a fanout. So the fence is genuinely required.
  - **Which leg actually needs the fence — the UPDATE fanout, not the initial snapshot.** The **initial snapshot** is fired *inside the subscriber's own subscribe call* (a 3-arg `lmz.call('NEBULA_CLIENT_GATEWAY', clientId, …)`, analogous to Star's `deliverResourceUpdate`, [star.ts:65-67](apps/nebula/src/star.ts)); it **inherits the subscriber's `originAuth`**, so its `aud` == the subscriber's connection `aud` and `onBeforeCallToClient` **passes with or without the fence**. Only the **update fanout** (fired when a *different* sub — the owner/admin — mutates; origin `aud` ≠ a cross-scope subscriber's connection `aud`) makes the fence load-bearing. So the fence's capable-of-failing lever is the **update leg only** (Phase 3).
  - **Fence signal:** the push's `envelope.metadata?.caller?.bindingName === 'PROFILE'` (the pushing DO's identity, stamped by the framework on the outbound call — [lmz-api.ts:308](packages/mesh/src/lmz-api.ts)). Skip/replace the aud-equality check for PROFILE-origin pushes; leave `STAR`/`DEV_STUDIO` pushes **behavior-identical** (Phase 3 criterion). Sound because **public fields are intentionally world-readable given the `profileId` handle** (there is no reach gate to bypass) **and the pushed `value` carries public fields ONLY** — the private blob never rides it (§ subscribe, above). Trust boundary: `metadata.caller` is set by the trusted mesh, not the client — acceptable within the mesh trust model.
  - ✅ **Fence signal is reliable at any N** — because the fanout is the hand-rolled `lmz.call` loop (svc.broadcast is unavailable to the raw composer), it never traverses the broadcast tier worker, so `metadata.caller` is always `PROFILE`. (The tier-path caveat that would apply to `svc.broadcast` is moot — there is no tier hop.)
  - The client's own `onBeforeCall` is intentionally permissive and *delegates* the boundary to this Gateway check ([nebula-client.ts:1445-1461](apps/nebula/src/nebula-client.ts)), so fencing the Gateway check is the **complete** boundary change — the client won't independently reject.

**Two wiring dependencies this surfaced (required for the approach to route end-to-end; realized in Phases 1–3):**
1. **`env.PROFILE` must be bound in the single `nebula` Worker** that hosts `NebulaClientGateway` (`#handleClientCall` does `getDOStub(this.env['PROFILE'], profileId)`). The PROFILE DO class is **coded in `@lumenize/nebula-auth`** but **runs in the one `nebula` Worker** — re-exported from [worker.ts](apps/nebula/src/worker.ts) alongside `NebulaAuthRegistry`/`NebulaEmailSender` (the established pattern: `export { …, Profile } from '@lumenize/nebula-auth'`; note the per-scope `NebulaAuth` DO is dissolved by surrogate-sub), bound as an **ordinary local** DO binding `{ name: 'PROFILE', class_name: 'Profile' }` + a `new_sqlite_classes` migration entry in [wrangler.jsonc](apps/nebula/wrangler.jsonc). **No cross-script binding / `script_name`** — `env.PROFILE` resolves in-Worker, identical to `env.NEBULA_AUTH_REGISTRY` today. (Package-layer ≠ Worker: nebula-auth is the *code* home; deployment is one Worker.)
2. **The client needs a profile-subscribe entry that passes `profileId` as the instance.** Today *every* client call pairs `#resourceHostBinding` with `this.#activeScope` (nebula-client.ts call sites 477–1210); the binding is parameterized but the instance is hardcoded to `activeScope`. A profile subscribe must supply `('PROFILE', profileId)` — a new/parameterized path (Phase 3).

## Build phases
Real-login-grounded per [ADR-009](docs/adr/009-real-auth-path.md): any criterion touching the JWT `profileId` claim or an authed identity is asserted on a **real email-login round-trip** (or rung-2 test-mode server issuance) — never a client-side mint. Note the `profileId` claim can't ride rung-2/3 today (`buildNebulaJwtPayload` has no `profileId` field yet), so **claim-presence assertions use rung-1 real login only**; any lower-rung mint that needs it must seed it explicitly.

### Phase 1 — Registry: mint `profileId` (an `Identities` column); add the `profile` JWT claim
**Goal**: every `sub` gets a `profileId` (1:1 in P1) set on its `Identities` row, and the minted JWT carries the bearer's own `profileId` (a bare custom claim). **Anchored to surrogate-sub's landed seams** (the old `nebula-auth.ts` DO is dissolved): `sub` is minted in the **registry** at authority points; the JWT is assembled in the **Worker** (`mintAccessToken` → `buildNebulaJwtPayload`), driven on refresh by the `RefreshTokenKV` record. ✅ **Reverified against the completed surrogate-sub code (2026-07-13):** `#mintIdentity` **is** the single mint funnel (3 call sites — `claimUniverse`, `issueInvites`, the `nebula-platform` bootstrap; **there is no `claimStar`** — Star self-signup is a deferred future flow); `#recordRefreshToken` (called by `consumeMagicLink`/`consumeInvite`) is the registry's single KV-write funnel, and `setIdentityAdmin` is the convergence re-put; `RefreshTokenKV = { sub, universeGalaxyStarId, isAdmin, expiresAt }`. **Line numbers are omitted throughout this task's code refs — the landed file is still being touched and symbols are the stable anchor.**
**Success criteria** (capable-of-failing):
- [ ] **Mint `profileId` in the one authority-point helper.** `#mintIdentity` (in [nebula-auth-registry.ts](packages/nebula-auth/src/nebula-auth-registry.ts) — the single helper **every** mint funnels through: `claimUniverse`, `issueInvites`, and the `nebula-platform` bootstrap; there is **no `claimStar`**) sets a fresh `profileId` (UUID) **in the same `Identities` INSERT** (one write, not a second row). **Schema — no migration/backfill:** the surrogate-sub `Identities` schema isn't deployed yet (its wipe is still pending — see banner), so add `profileId` + `idx_Identities_profileId` straight to the **baseline `IDENTITIES_SCHEMA`**; the one pending wipe brings it up greenfield. (An `ALTER`+backfill would only be needed if `profileId` landed *after* the wipe had already deployed `Identities` with data — not the plan, so the column's one apparent cost is moot.) ⚠️ **Editing `IDENTITIES_SCHEMA` (applied migration id 2) is normally forbidden by its own APPEND-ONLY banner** ([schemas.ts](packages/nebula-auth/src/schemas.ts)) — permitted **only** because surrogate-sub's wipe resets the id sequence and hasn't deployed; **update that banner** to note `profileId` is part of the pre-wipe baseline. Persisted-local trap: a `wrangler dev` DO that already applied id 2 won't re-run it (→ `profileId` INSERTs fail) — `rm -rf .wrangler` to recover (fresh vitest masks this). Its existing `(email, scope)` idempotency **extends to `profileId`** (an already-minted identity keeps its existing `sub` **and** `profileId` — the INSERT is not re-run). Login **verify** (`getAndVerifyIdentity`) NEVER mints, so no `profileId` there. `sub → profileId` is single-valued by construction (a column on the `sub`-PK row — a second value is structurally impossible, not just rejected).
- [ ] **No async-seam split.** Setting `profileId` is part of the same synchronous `Identities` INSERT in the single-writer registry — there is no cross-DO async-RPC seam to design around (the old per-instance mint DO is dissolved), and `sub → universeGalaxyStarId` is on the same row, so no separate scope lookup.
- [ ] **`profileId` rides the KV refresh record so the claim survives refresh.** `RefreshTokenKV` gains a `profileId` field ([types.ts](packages/nebula-auth/src/types.ts)), and **every writer of that record includes it — there are THREE** (all in [nebula-auth-registry.ts](packages/nebula-auth/src/nebula-auth-registry.ts)): **(a)** `#recordRefreshToken` (the KV-write funnel for `consumeMagicLink`/`consumeInvite`; `profileId` is on the `Identities` row `getAndVerifyIdentity` already reads); **(b)** the `setIdentityAdmin` **convergence re-put** (it **rebuilds** the record, so it must carry `profileId` forward, exactly as it re-applies the original expiry — else the claim vanishes after any admin change); **(c)** ⚠️ **`getRefreshRecord` — the KV-miss self-heal on the refresh hot path.** `handleRefreshToken` falls back to it cross-colo (login → first-refresh), and it RE-PUTs a record rebuilt from `getIdentityScope`, which returns **no `profileId` today** → a self-healed record is `profileId`-less for the token's ~30-day life → its tokens lack the `profileId` claim → the owner can't edit their own profile. **Fix: extend `getIdentityScope` to return `profileId`** and thread it through `getRefreshRecord` (this also closes the delegated-token gap — same method). In **P1** `profileId` is immutable (carry-forward, not convergence); a **P2 re-point** *mutates* it → it then joins `isAdmin`'s convergence machinery (additive) — so **don't annotate it as eternally immutable.** Refresh (`handleRefreshToken` in [worker-token.ts](packages/nebula-auth/src/worker-token.ts)) is the **only** normal JWT-mint path; ADR-010-safe to denormalize (unlike `email`).
- [ ] **The `profileId` claim is added at JWT assembly.** A top-level `profileId: <uuid>` is emitted by [`buildNebulaJwtPayload`](packages/nebula-auth/src/access-claims.ts) (add it to `NebulaAccessClaimInput` + `NebulaJwtPayload`, sibling of `sub`) — `mintAccessToken` ([worker-token.ts](packages/nebula-auth/src/worker-token.ts)) passes `profileId` from the KV record. Asserted on a **real login round-trip** (ADR-009). **Capable-of-failing — FORCE the KV miss:** miniflare KV is strongly consistent, so a normal login→refresh always HITS KV (path (a)) and never exercises the (c) self-heal — so after login **delete `refresh:{tokenHash}` from `REFRESH_TOKEN_KV`** (keep the `RefreshTokenIndex` row), *then* refresh, and assert the minted JWT carries the `profileId` claim; mutation-check by reverting the `getIdentityScope` extension (must red). The **delegated-token** mint (`handleDelegatedToken` → `getIdentityScope`) carries the claim for free once (c) extends `getIdentityScope`. (A KV record genuinely without `profileId` mints gracefully without the claim — shouldn't occur post-fix.)
- [ ] **The `setIdentityAdmin` convergence re-put carries `profileId` forward** (writer (b)). Toggle an identity's admin bit via `setIdentityAdmin`, *then* refresh, and assert the minted JWT **still** carries the `profileId` claim — capable-of-failing (reds if the re-put rebuilds `RefreshTokenKV` without `profileId`, exactly as it must re-apply the original expiry). A **distinct** failure mode from the (c) self-heal above: **(b) fires on every admin change**, (c) only on a cross-colo KV miss — a fix to one does not cover the other, so both need their own red.
- [ ] `sub → profileId` is authoritative on `Identities.profileId` and **never copied onto resource records** — grep-verify no `profileId` column on **grants/snapshots** (it belongs ONLY on `Identities`, resolved live where needed).
- [ ] The new **`@lumenize/nebula-auth → @lumenize/mesh`** dependency is added (`package.json` + `npm install`/type-gen) and is not a cycle.

### Phase 2 — the Profile DO (public fields + private notes; open read + the `requireOwnerOrAdmin` gate)
**Goal**: a `PROFILE` DO (nebula-auth, composes `lmz-api`, keyed by `profileId`) holds the public OIDC fields + private `privateNotes`. **Public read/subscribe is OPEN** — any authenticated caller holding the `profileId`, no gate, no registry read; **`requireOwnerOrAdmin` gates public-field writes + `privateNotes` read/write**, short-circuiting owner + super-admin from the JWT and reading `Identities` (`WHERE profileId = ?`) only for the scoped-admin case.
**Composition**: `extends ComposedMeshDO(DurableObject, 'Profile')` from `@lumenize/mesh` — the mixin is **LANDED** (2026-07-14, [backlog.md](backlog.md) § Lumenize Mesh; `LumenizeDO`/`LumenizeContainer` already compose it). It supplies `lmz`/`onBeforeCall`/`__executeOperation`/`__handleResponse`; **add a per-class `ctn()`** (5-line stanza — it stays off the mixin, see backlog). The Profile needs **only** that receive core (no self-served `fetch`/WS: clients terminate at the Gateway, so it receives mesh RPC only), then adds its `requireOwnerOrAdmin` gate + storage + hand-rolled fanout on top.
**Success criteria** (capable-of-failing):
- [ ] **Registered + reachable**: `Profile` re-exported from [worker.ts](apps/nebula/src/worker.ts); local `PROFILE` binding + `new_sqlite_classes`; `getDOStub(env.PROFILE, profileId)` resolves in-Worker. Tables (fields + subscriber rows) created **synchronously in the constructor** (raw-DO init, **not** `onStart` — a raw composer has none), `WITHOUT ROWID` on the `profileId`/PK columns (write-cost).
- [ ] **`ComposedMeshDO` resolves cross-package as a VALUE.** `import { ComposedMeshDO } from '@lumenize/mesh'` in `packages/nebula-auth/src` binds a **value** (the Profile DO does `extends ComposedMeshDO(DurableObject, 'Profile')`), not a type-only export — capable-of-failing (reds if it regresses to the type-only export it briefly shipped as; the value export is [index.ts:37](packages/mesh/src/index.ts)). A `type-check` run over the nebula-auth program is the cheapest red — a type-only import fails `extends` there but not in a same-package unit test.
- [ ] **Public read/subscribe is OPEN — no gate, no read.** Any authenticated caller reads/subscribes the public fields; a caller in a **different scope** from the profile's `sub` (with no admin bit) **succeeds** — capable-of-failing (reds if a reach gate is reintroduced). Assert via debug-sink that a public read fires **zero** registry reads.
- [ ] **The subscribed / fanned-out `Snapshot.value` carries the PUBLIC fields ONLY (#① — no `privateNotes` leak).** **Seed `privateNotes` with a distinctive non-empty sentinel first** — an absent/empty blob makes the assertion vacuous. A cross-scope / non-owner subscriber's received snapshot contains `name`/`nickname`/`picture` and **never** `privateNotes` (grep the whole received payload for the sentinel string — it must be **absent**) — capable-of-failing (reds if the DO hands the stored record, blob included, to the fanout). Cover both the initial snapshot and an update push.
- [ ] **`requireOwnerOrAdmin`** (top-down, read only if forced): **owner** (JWT profileId === instance) and **super-admin** (`authScopePattern === '*'`) pass with **NO read**; a **non-admin non-owner** is rejected with **NO read**; only a **scoped admin** (`access.admin && pattern !== '*'`) reads — pass iff `matchAccess(pattern, S)` for a profile scope `S`. Capable-of-failing: a **different-scope admin** whose pattern covers **none** of the profile's scopes is rejected (cross-Galaxy-admin case); assert the owner/super-admin paths fire **zero** reads — **with a positive control**: the *scoped-admin* path in the same suite fires **exactly one** read, proving the debug-sink read-counter is genuinely wired (a dead counter makes every "zero reads" assertion pass vacuously).
- [ ] **`privateNotes` gate = `requireOwnerOrAdmin`, via a SEPARATE gated read (never a snapshot).** Owner/super-admin/scoped-admin read+write `privateNotes` through a dedicated method; **any other caller — including one who can freely read the public fields — reading `privateNotes` must RED.** The LLM path passes **via the owner short-circuit** (its JWT carries the owner's `profileId` claim) — no separate agent principal (authz off the authority identity, never `act`). Blob **seeded directly** for the test (its LLM-write flow is deferred).
- [ ] `requireOwnerOrAdmin` is an **async method-body call** (awaited registry read on the scoped-admin path; public registry method; narrow `using` stub) at the top of each write/blob `@mesh` method — **not** `onBeforeCall`.
- [ ] **Fail-closed on a registry-read error.** If the scoped-admin registry read **throws** (registry unreachable / malformed response / RPC rejection), `requireOwnerOrAdmin` **rejects the call** (deny), never falls through to allow. Capable-of-failing: force the read to reject (e.g. a throwing `using` stub) on a scoped-admin write and assert the write is **denied** — reds if a `try/catch` swallows the error into an allow, or an unhandled rejection escapes the gate. (Owner/super-admin still pass here — they never reach the read.)
- [ ] **No ADR-004/005**: a second write **replaces** the current fields (last-writer-wins), not a new snapshot row; the emitted `Snapshot` carries a forward-only ULID `eTag` (for the client engine) but no OCC conflict-check.

### Phase 3 — client subscribe (binding-agnostic) + the Gateway PROFILE-fence + fanout
**Goal**: a client subscribes to a `profileId` and receives live updates cross-scope; the scoped path is untouched.
**Success criteria** (capable-of-failing; from the verified routing model):
- [ ] A profile subscribe routes end-to-end `lmz.call('PROFILE', profileId, …)` → Gateway (authN + route) → PROFILE DO, **without** the profile instance equaling the client's `activeScope`.
- [ ] **The headline — the UPDATE leg is the fence's capable-of-failing lever.** A subscriber in scope **X** receives a profile **update** for a person whose `sub` lives in scope **Y** (`X ≠ Y`) — **reds without** the `onBeforeCallToClient` PROFILE-fence, green with it. X's **subscribe is admitted** (public read is open — no reach gate to red first), isolating the **fence**. The **initial-snapshot** leg is asserted the *opposite* way — X receives it **even without** the fence (it inherits X's own `aud`; § Routing) — the open-read demonstration, not a fence test. **Vehicle**: two logins into **distinct** scopes (Y owns + mutates, X subscribes, neither an admin) so the `aud`s genuinely differ — **rung-2 test-mode issuance in the vitest lane suffices** (the lever is the distinct `aud`, not real email; reconciles with the rung-2 allowance in § Build phases). A same-scope fixture makes "reds without the fence" **vacuous**. The rung-1 real-email round-trip is an *optional harness* grounding, not the vitest vehicle.
- [ ] **Fanout** is the hand-rolled `lmz.call` loop from the Profile DO to `NEBULA_CLIENT_GATEWAY` over its subscriber rows (not `svc.broadcast`). A **disconnected subscriber's row is dropped** after a failed push — assert the transient removal via the `onProfileBroadcastResult` (`onErrorOnly`) handler, mirroring `Star.onBroadcastResult` (per testing.md §self-healing-transient, not just "no error").
- [ ] **No upward import** — grep-verify `packages/nebula-auth/src` imports **nothing** from `apps/nebula` (the fanout continuation is typed by an untyped `ctn()` + a local structural payload type, never `NebulaClient`/`Snapshot`; § Routing). A type-only upward import compiles *and* passes same-package tests, yet inverts the dependency graph (mesh.md § dependency-direction) — the bare grep is the only reliable red.
- [ ] The client gains a `('PROFILE', profileId)` subscribe path (instance ≠ `activeScope`) landing in the **same reactive store** (forward-eTag `Snapshot` via `handleResourceUpdate`).
- [ ] The scoped `STAR`/`DEV_STUDIO` path stays **behavior-identical** (the fence keys on PROFILE-origin pushes only — a scoped-push regression must red).
- [ ] **No revocation concern (by construction).** Pushes carry **public fields only** (#①) and public read is **open**, so there is nothing to revoke on the push leg — a subscriber who loses membership was never *gated* from the public fields. The private blob is never pushed (it's a separate gated read that re-checks on every call). The only subscriber-lifecycle action is the **dead-row drop** on a failed push (above). *(This is the payoff of open-read + the public/private split: the earlier "accepted revocation window" softening is gone.)*

### Phase 4 — `sub → profileId → display` resolution for consumers
**Goal**: presence / chat / org-tree resolve a bare `sub` to a display identity. **Transport is mesh-legal end-to-end** — the consumers are `apps/nebula` platform DOs (**mesh-only, never raw** — mesh.md), so the `profileId → display` read is `lmz.call('PROFILE', profileId, …)` (the Profile DO is a mesh node), and a Star DO **must never** raw-RPC the raw registry for the `sub → profileId` half. **Preferred mechanism — stamp, don't resolve:** `profileId` rides every authed caller's JWT (the `profileId` claim), so the Star **captures `profileId` alongside `sub` at write time** (subscribe/presence row, message attribution) from `callContext.originAuth` — the consumer then already *holds* `profileId` and needs **no live `sub → profileId` registry hop** on the hot path. **The remaining hop is OPEN** — the held-`profileId` → public-field read is ungated (the public-profile model, § The Profile DO). The handle-chain is the boundary: you only hold `sub`s/`profileId`s you legitimately encountered (attribution, roster) — both are unguessable registry UUIDs, so open-resolution ≠ enumeration.
**Success criteria** (capable-of-failing):
- [ ] **`profileId` is captured alongside `sub` at write time** (from the writer's JWT `profileId` claim via `callContext.originAuth`), so the consumer holds it directly — **no live `sub → profileId` registry hop** on the display path. Capable-of-failing: assert a presence/attribution row carries the writer's `profileId`; reds if only `sub` is stored (which would force a later registry resolution the mesh-only Star can't legally do).
- [ ] **Mesh-legal transport (Nebula-never-raw).** The `profileId → display` read is `lmz.call('PROFILE', profileId, …)` (Profile is a mesh node). grep-verify **no raw `env.NEBULA_AUTH_REGISTRY` or `env.PROFILE` stub access in `apps/nebula/src`** Star/Galaxy/Universe/Resources DOs — those are mesh-only (mesh.md); the raw registry is reachable only from the Worker/Gateway layer. **Open design point (resolve at the presence/chat build, NOT here):** any *residual* live `sub → profileId` for a `sub` never seen authed by this consumer routes through the **Worker/Gateway** (which may legally raw-RPC the registry, as the Gateway does today), never a raw call from a Star DO; until then such a `sub` degrades gracefully (below).
- [ ] A consumer resolves a roster `sub → display` (email now; `name`/`nickname` when set) via its held `profileId` → the Profile DO; the resolved-value cache is **loss-tolerant** (no durable instance state — [durable-objects.md](.claude/rules/durable-objects.md)).
- [ ] A profile field change **invalidates/refreshes** the resolved value for holders (assert the transient refresh, not just the converged value — testing.md §25).
- [ ] An unknown / departed `sub` **degrades gracefully** (render the `sub` or a generic label), never throws.

## Non-goals / deferred
- **P2 — global "person" / cross-Universe profile sharing** (link many `sub`s' profiles into one canonical the person edits once). The `Identities.profileId` column + live-resolution make it **additive later** (re-point a second `sub` at an existing `profileId` — a one-row `UPDATE`, no re-key). **Re-point convergence (decided 2026-07-13 — option a):** re-pointing *mutates* that `sub`'s `profileId`, so the registry **converges** the denormalized copy into the `sub`'s KV refresh record(s) via the existing `isAdmin`-style push ([`setIdentityAdmin`](packages/nebula-auth/src/nebula-auth-registry.ts) — enumerate `RefreshTokenIndex WHERE sub`, re-put with the new `profileId` + the record's original expiry), so the `profileId` claim refreshes on next refresh. (Rejected — option b, dropping `profileId` from the JWT/KV to sidestep convergence: it fights the pure-KV refresh path and loses the claim convenience.) Trigger = a real cross-Universe sharing need. **Do not** build the person-layer now. **Planned unification trigger (design seed, 2026-07-13):** a **root-path, non-httpOnly breadcrumb cookie** (`Path=/` set **explicitly** — omitting Path scopes to the setting dir, not the origin; `SameSite=Lax`, host-only) records the last `profileId` seen in this browser, set at **login** (`consumeAndLogin`, riding the existing refresh `Set-Cookie` — refresh no longer re-sets cookies). Its point is the one case the server **cannot** see — *different email, same person, same browser* (same-email-across-scopes the registry already links via `discover(email)`, so the cookie isn't redundant with it). ⚠️ **The cookie is UNTRUSTED / advisory only** — it may trigger a "link to your existing profile?" prompt but is **never** an input to the link decision: the link must independently **prove control of both** identities (safe form: auto-offer only when a **live** session for the other profile exists; a stale breadcrumb only prompts a "sign in to link" flow). Shared/kiosk-browser identity contamination is the failure mode this rail closes. JS may **write** it only to clear it ("not me"); read-only otherwise. A manual **"merge profiles"** feature is the fallback for the rest.
- **Per-scope display name** (the way `email` is per-scope) — v1 is one `name`/`nickname` per profile; the per-scope door is the same one `email` opened, if ever needed.
- **Profile-DO teardown on scope deletion** — `executeScopeDeletion` drops the `Identities` rows + KV + tokens but does **not** tear down the now-orphaned Profile DOs (fields + blob + subscriber rows); in P1 (1 sub : 1 profile) each deleted member orphans one. **Acceptable pre-alpha** — unreachable after the ≤15-min token window, and the pending wipe clears it. P2 teardown = "delete the Profile DO when `Identities WHERE profileId` is empty," folded into the scope-deletion cascade.
- **The LLM-writes-the-blob flow** — the field + its owner/admin read-gate ship now (Phase 2), but Nebula *extracting/updating* personal understanding is a later write path (the gate is tested by seeding the blob directly).

## ADR candidacy
The identity model (`profileId` as an `Identities` column + safe-denormalization principle + JWT-short-circuit-authZ-then-resolve-scope-set-live) is **ADR-ready** now that the routing + authZ are settled. Write it **alongside the build** — once the concrete mechanism (the PROFILE-fence + the JWT-short-circuit + live-lookup owner/admin helper + `sub → profileId → display` resolution) lands — so the ADR records real code, not a plan.

**Accepted decision — owed an ADR ratification (does NOT block the build): global, cross-scope profile visibility via an unguessable handle.** Public profile fields (`name`/`nickname`/`picture`) are readable/subscribable by **any authenticated caller that holds the `profileId`**, across scope/Star/Universe boundaries — no reach gate, no registry read (§ The Profile DO, Phases 2–4). **Reasoning:** (1) the `profileId` is a random opaque registry UUID ([ADR-010](docs/adr/010-random-opaque-keys.md)) — unguessable and non-enumerable, so *holding* one is itself the capability (the GitHub-public-profile model, minus the guessable slug); (2) a caller only obtains a `profileId` by legitimately encountering the `sub`/handle (attribution, roster, org-tree) — open-resolution ≠ enumeration; (3) it **generalizes** [ADR-008](docs/adr/008-full-org-tree-visibility.md)'s "identity is not confidential" from within-a-Star to a **global public-address handle** — but ADR-008 is explicitly intra-Star and disclaims cross-tenant visibility, so this **exceeds** ADR-008 and needs its own ratification. **Boundary:** only the **public** fields are open; `privateNotes` (and any future protected-class field) stays behind `requireOwnerOrAdmin`. **Ratify or amend** as part of the alongside-the-build ADR; if ratification is *rejected*, the fallback is a scope-intersection reach gate on the `sub → profileId` and public-read paths (the capable-of-failing tests in Phases 2–4 already pin exactly which paths would flip).
