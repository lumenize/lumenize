## Unified identity schema (reconciled to the landed surrogate-sub model, 2026-07-13)
The **intended *after* picture**: the two homes surrogate-sub actually landed — the **registry** (singleton DO, the single writer) and **Workers KV** (+ the Worker JWT mint) — shown **with this task's additions** (`profileId`, the `sub↔profileId` join, the `profile` claim), plus the **Profile DO** (Store 3) in full. TypeScript is the schema of record (ADR-001); timestamps are ISO 8601 Zulu strings (ADR-011), never epoch `number`. This **supersedes** the earlier "verbatim snapshot," which modeled a per-scope `NebulaAuth` DO holding `Subject`/`RefreshToken`/`AuthorizedActor` and a `profileId` FK column on `Identity` — all **dissolved or superseded** by surrogate-sub (`NebulaAuth` DO gone; `Subject`→registry `Identity`; `RefreshToken`→KV; `AuthorizedActor` cut; `Identity.profileId` column → a separate live-resolved join, § The model).

```typescript
// ── STORE 1 · Registry (singleton DO) — identity authority + THE SINGLE WRITER ──
// Mints `sub` + `profileId`; owns `email` as a mutable attribute (the ONLY copy).
// Surrogate-sub dissolved the per-scope NebulaAuth DO INTO this registry — it now writes
// ALL durable auth state + the KV refresh record. Rows below are surrogate-sub's landed
// shapes (packages/nebula-auth/src/{types,schemas}.ts); this task ADDS only `ProfileJoin`.
interface Scope {                  // SQL `Scopes` (renamed from `Instances`) — existence + consent
  universeGalaxyStarId: string;    // PK · "this scope exists" (independent of membership)
  improveProductConsent?: boolean; // Universe-level opt-IN; absent on non-Universe scopes
}
interface Identity {               // SQL `Identities` (was `Emails` + `Subjects`)
  sub: string;                     // PK · registry-minted UUID surrogate — the identity key
  universeGalaxyStarId: string;    // FK → Scope · gives `sub → scope` NATIVELY (B2 neutralized)
  email: string;                   // MUTABLE · login address (lowercased) · the ONLY copy
  isAdmin: boolean;                // scope-admin (drives access.admin) · set at grant/creation
  emailVerified: boolean;          // per-scope proof-click · the "authorized member" signal
  createdAt: string;               // ISO 8601 Zulu
}
interface ProfileJoin {            // SQL `ProfileJoins` — ADDED BY THIS TASK
  profileId: string;               // registry-minted UUID · the PUBLIC address (distinct from `sub`)
  sub: string;                     // FK → Identity.sub · resolved LIVE, NEVER on a durable row
  universeGalaxyStarId: string;    // the sub's scope, for the reach set (also on Identity now — B2)
}
// Also registry-owned, unchanged here (surrogate-sub shapes; hashed tokens; ISO timestamps):
//   RefreshTokenIndex (tokenHash → sub · KV invalidation) · MagicLink · InviteToken (login channel).
// INVARIANTS
//  • REPLICATION (ADR-010): `sub`+`profileId` copy freely (JWT, KV). `email`/`isAdmin`
//    are MUTABLE → ONE copy here + convergence (`isAdmin` → KV, registry-pushed).
//    `profileId`: immutable in P1; a P2 re-point mutates it → converge then.
//  • UNIQUE (email, universeGalaxyStarId) — one identity per email per scope.
//  • sub → EXACTLY ONE profileId; profileId ← 1..N subs (the P2 profile-unification
//    substrate: re-point subs at a shared profileId — additive). NEVER two per sub.
//  • `sub → profileId` resolves LIVE via `ProfileJoins`, NEVER a column on a durable row.

// ── STORE 2 · Workers KV + the Worker JWT mint — refresh state; NO per-scope DO ──
// Surrogate-sub moved the hot refresh record to KV (edge, TTL) and JWT-minting to the default
// Worker (`worker-token.mintAccessToken` → `access-claims.buildNebulaJwtPayload`). `Subject`
// folded into registry `Identity`; `RefreshToken` → this KV record; `AuthorizedActor` CUT.
interface RefreshTokenKV {          // KV `refresh:{tokenHash}` · read at the edge on refresh
  sub: string;
  universeGalaxyStarId: string;
  isAdmin: boolean;                 // denormalized · registry-pushed convergence
  profileId: string;                // ADDED HERE · so `profile` survives the pure-KV refresh
  expiresAt: string;                // absolute ISO · re-applied on a re-put (KV drops TTL on put)
}
// The minted JWT carries `sub` + `access` (+ optional `act`) + this task's OIDC `profile` claim
// = `/profiles/PROFILE/{profileId}/`. `email` is NOT a claim (surrogate-sub removed it).

// ── STORE 3 · Profile DO (one per profileId, global) — BUILT in this task (Phases 2–4) ──
// Keyed by profileId. Holds NO email, NO sub, NO scope (all registry-owned). Editable display
// identity + private memory. Fields/authz/subscribe/co-membership are this task's build.
interface Profile {
  name?: string;          // OIDC full name
  nickname?: string;      // OIDC display/casual name
  picture?: string;       // OIDC avatar image URL (R2)
  profile?: string;       // OIDC profile-page URL
  privateNotes?: string;  // "what the LLM knows about you" — owner + admin only
}
```

## Why (grounded facts, verified 2026-07-08)
- **`sub` is per-scope, not global.** Surrogate-sub keys identity on the registry `Identities` table with `UNIQUE (email, universeGalaxyStarId)` — the same email in two scopes mints two `sub`s. A person has a **different `sub` per scope**; the cross-scope link is `email` (a registry-indexed lookup, never a key). (Pre-dissolution this lived in per-instance `Subjects` tables + a registry `Emails` table; the per-scope *conclusion* is unchanged.)
- **There is no global person-id today** — and because a person can use different emails per scope (corp in one, personal in another), even email doesn't reliably link them. So "one identity across Universes" is a concept that **does not exist yet** and must be *introduced* (deferred to P2).
- **Three consumers already need `sub → display identity`**: the presence roster (chat), the org-tree UI (today it can only show `abc123: admin`), and chat authorship. Resolving it once, well, is the point.
- The earlier-deferred "Nebula-knows-you" memory returns here as a cheap **private field**, not a separate store.

## Scope decision & framing (2026-07-08, Larry)
- **Build the FULL store now — deliberate; do not re-litigate the split.** The Stage-1 framing panel recommended deferring the content-store half (reactive `subscribe`, `picture`/`profile`, the private blob + owner-gate) and shipping only the resolution model. **Overridden by design:** the `profileId` rail and the private "Nebula-knows-you" blob are laid now to avoid a re-key / re-open later, and `picture`/`profile` are cheap additive fields on the same schema.
- **Within the ~90%-solo persona ([strategy.md](docs/vision/strategy.md)), this is attribution + personalization, NOT a social graph.** `profileId` + join + resolution is the identity substrate for `changedBy`-attribution and roster display — a near-free byproduct of already-justified features (identity-from-`changedBy`, subscribe), the same framing [chat](nebula-chat-history-multiuser.md) uses. The private blob is **single-player** (Nebula personalizing to *this* user-developer), not social. `picture`/`profile` are the **display layer of attribution** (who wrote this), not a directory / feed / follow / discovery surface — there is no profile *browsing*.

## The model (P1 — per-scope, forward-compatible with P2)
- A **new `profileId`** (UUID), a **distinct namespace from `sub`** (it becomes the *public* address — keep it decoupled from the auth `sub`). A **`profileId ↔ sub` join** lives in the **global registry**, modeled **n:m from the start** (schema-flexible) and **carrying each sub's scope** (`universeGalaxyStarId` — now also natively on `Identities`, B2 neutralized); the *useful* cardinality is **one profile ⇢ many `sub`s** so `sub → profileId` stays single-valued ("which profile for this sub" must have one answer).
- **`sub → profileId` is the single source of truth, resolved LIVE (cached)** — **never denormalized onto durable records.** So P2 linking (point a second `sub` at an existing `profileId`) is **additive: no re-key, no stale copies, no "person-layer above" needed** — the join *is* the authority.
- **P1**: one `profileId` per `sub`. **P2 (deferred)**: link `sub`s under one profile (the join absorbs it).
- **Safe-denormalization principle** (the rule that keeps it clean): denormalize the **stable KEY** (`profileId`) *only where it self-heals* — the JWT (ephemeral) and subscriber rows (ephemeral, refresh on reconnect); resolve the **churning FIELDS** (email/name/…) **and the authZ scope-set live** (a stored scope-set would go stale on P2-link / teardown — stale authZ is a security bug); **never** put `profileId` (or identity) on **durable** records (grants stay `sub`-only, resolve via the join). **Key every churny resolution off `sub`** (1:1, stable), never off `profileId` — nothing reverse-maps `profileId` → a single email/sub, which is *precisely* why P2 unification is additive: it only makes `profileId ← more subs`, leaving every existing `sub → …` lookup unchanged.

## Identity fields (OIDC-standard terminology)
Use OIDC Standard Claim names, not invented ones:
- **`name`** (full name), **`nickname`** (display/casual name), **`picture`** (avatar *image* URL — R2), **`profile`** (profile-*page* URL).
- **`email`** — **NOT** in the Profile store, and (post-surrogate-sub) **not in the JWT** either. It's a registry-only, per-scope **mutable** attribute; consumers resolve `sub → email` via the registry for the contextually-correct scope.
- **private markdown blob** — "what the LLM knows about this entity" (human or agent). Owner + admins only (the LLM writes/reads it *acting as the owner* — see AuthZ). Which fields are public vs private is **platform-controlled for now** (can change later).

## JWT decisions
- **`email` is NOT in the JWT** (surrogate-sub removed it — [types.ts:52](packages/nebula-auth/src/types.ts)), making it a registry-only **mutable** attribute (the cleanest ADR-010 — one copy, nothing to converge). This **reverses** this file's earlier "email stays in the JWT" call; [surrogate-sub § Blast radius](archive/nebula-auth-surrogate-sub.md) supersedes it. Display/audit consumers resolve `sub → email` via the registry; authz never keyed off it (`sub`+`access`).
- **The one claim this task adds is `profileId`**, encoded as the OIDC **`profile`** claim = the URL **`/profiles/PROFILE/{profileId}/`** — `routeDORequest`-compatible (binding `PROFILE`, instance `profileId`). This pre-computes the `sub → profileId` hop for **the bearer's own** profile (others resolve via the join, cached). It **rides the `RefreshTokenKV` record** (Store 2 above) so it survives the pure-KV refresh mint.
- **No `name`/`nickname`/`picture` in the JWT** — they churn; resolve them live.

## The Profile DO
- **Code home: `@lumenize/nebula-auth`** (identity/registry-infra layer — it's a raw DO that reads the registry for the join + scope-reach). `apps/nebula`'s platform DOs are scope-bound business logic, so identity infra belongs with auth — **not** because a Worker can't host a global thing (the registry itself runs in the one `nebula` Worker; see the routing pre-req's wiring note). **Raw DO base (extends `DurableObject`) that COMPOSES the mesh comms core** (`lmz-api`) for its client-facing subscribe — the ADR-007 composition pattern (precedent: `NebulaContainer`/`LumenizeContainer`, the 4th type to compose it; this is the 5th). This adds a new **`@lumenize/nebula-auth → @lumenize/mesh`** dependency edge (not a cycle — mesh never imports nebula-auth). Talks to the registry via plain Workers RPC (the registry is a raw DO, not a mesh node).
- **Keyed by `profileId`** — instance name = `profileId`, binding = `PROFILE`; addressed at `/profiles/PROFILE/{profileId}/` (`routeDORequest`). Lazy (created on first access, like a Star). Its own durable state is the **fields + private blob + subscriber rows** — *not* its ownership/scopes (those resolve live from the join).
- **AuthZ = two async method-body helpers (the DAG-check pattern), NOT `onBeforeCall`.** `onBeforeCall` is **sync**; scope-reach here needs an **async** registry read, so it can't live there. Each `@mesh` entry method calls, at its top, one of:
  - **`requireProfileReach()`** — read public fields + subscribe. **Reach** = *(caller's reachable scopes)* ∩ *(the profile's scopes, resolved live from the join)* ≠ ∅. Caller's set = `{aud}` for a non-admin, the `authScopePattern`-covered set for an admin. The set-generalization of `enforceScopeReach` ([nebula-do.ts:66](apps/nebula/src/nebula-do.ts)) — one instance-name check becomes "any of the profile's scopes."
  - **`requireOwnerOrAdmin()`** — write public fields + read/write the private blob. **Owner** (`caller.sub` ∈ the profile's owner-subs, live from the join) **OR admin** (`claims.access.admin` **and** `matchAccess(claims.access.authScopePattern, S)` for some profile scope `S`; super-admin `*` covers all; a different-scope admin whose pattern covers none of the profile's scopes is rejected).
  - The **LLM needs no authz identity** — it writes/reads the blob *acting as the owner* (runs under the owner's context → `originAuth.sub == owner`), so the plain owner check passes. No reserved agent `sub` as an authZ principal (which would also break security.md — authz keys off the authority `sub`, never `act`).
  - Both helpers do a **live** registry read (fresh — a stored scope-set goes stale on P2-link/teardown). Raw Workers RPC gotchas apply: **await** it, the registry method is **public** (not `#` — a `#` method returns `undefined` over RPC → fail-**open**), hold the stub in a narrow `using` scope. **Fail closed** on a lookup error.
- **Resources-compatible subscribe** — the client sees it via the **same reactive store**, so the Profile DO emits `Snapshot { value, meta: { eTag } }` with a **forward-only ULID `eTag`** (the client's `handleResourceUpdate` → engine dereferences `meta.eTag`, so an eTag is *required*). It does **NOT** do ADR-005 optimistic-concurrency conflict-checking (**last-writer-wins**) and has **no ADR-004 history** — "Resources-compatible" = reuses the store **delivery shape** only. Needs `NebulaClient` upgrades (client-side, binding-agnostic).
- **Fanout is a hand-rolled `lmz.call` loop** — `svc.broadcast` is **LumenizeDO-only** ([lumenize-do.ts:485](packages/mesh/src/lumenize-do.ts)) and unavailable to a raw `lmz-api` composer. The Profile DO loops its own subscriber rows firing `this.lmz.call('NEBULA_CLIENT_GATEWAY', clientId, this.ctn<NebulaClient>().handleResourceUpdate(...))` (4-arg `onErrorOnly` + a **public `@mesh()` `onProfileBroadcastResult`** that drops a dead subscriber row — mirrors `Star.onBroadcastResult`; it can't *inherit* it). ADR-003-clean; fine at profile-scale N; keeps `metadata.caller` = `PROFILE` (no tier hop → the fence signal is reliable at any N).
- **Scale plan (deferred):** denormalize the profile's scope-set onto each Profile DO, **pushed by the registry on change** — a denormalize-**with-invalidation** (the invalidation is what makes the cache safe, unlike a naive stored copy). Deferred until the per-subscribe registry read is a *measured* bottleneck; it also closes the revocation window (Phase 3).

## Routing model (verified — completed pre-req, not a build phase)
A profile subscribe is an **ordinary `lmz.call('PROFILE', profileId, …)`** — the existing binding+instance mechanism, no new routing. The **Gateway does authN + routing only**; authZ lives in the **PROFILE DO's `requireProfileReach`/`requireOwnerOrAdmin` helpers** (above). The client already parameterizes the binding ([nebula-client.ts:283](apps/nebula/src/nebula-client.ts)). The **one** framework change is a PROFILE-fenced skip of the deliver-to-client aud-check (below); the acceptance for it lives in Phase 3.

### Verified mechanism (2026-07-08, code-grounded)
**Verdict: the "ordinary `lmz.call('PROFILE', profileId, …)`, authZ in the PROFILE DO" approach is viable. One small, PROFILE-fenced tweak on the deliver-to-client leg; the inbound leg needs nothing.** There is exactly **one** active-scope check — `NebulaClientGateway.onBeforeCallToClient` (the *only* override; no `onBeforeCallToMesh`/`onBeforeAccept` override — verified by grep). It is a **deliver-to-client-leg** guard, not an inbound one.

- **Inbound leg (client → mesh) — ALREADY ADMITS, no tweak.** `#handleClientCall` → `onBeforeCallToMesh` is a base passthrough (not overridden by Nebula); it forwards `(binding, instance)` verbatim to `env[binding]`. Nothing ties the *callee* instance to `activeScope` — `onBeforeAccept` only validates the *client's own* connection name (`{sub}.{tabId}`). So `lmz.call('PROFILE', profileId, …)` is forwarded untouched; the PROFILE DO's `requireProfileReach`/`requireOwnerOrAdmin` helpers are the authZ. ✅
- **Deliver-to-client leg (mesh → client) — NEEDS THE FENCED TWEAK.** `onBeforeCallToClient` asserts `envelope.callContext.originAuth?.claims.aud === connectionInfo.claims.aud`. This passes for Resources only because **all same-Star subscribers share the Star's `aud`** (locked by `enforceScopeReach`) and the fanout **inherits** the mutator's `originAuth` ([broadcast.ts:138-141](packages/mesh/src/broadcast.ts) — no `newChain`). A **global profile** has subscribers across *different* scopes (ADR-008-extended visibility), so the push's origin `aud` ≠ a cross-scope subscriber's connection `aud` → **rejected.** `newChain:true` doesn't help (origin `aud` → `undefined` ≠ subscriber `aud`); per-subscriber re-mint defeats a fanout. So the fence is genuinely required.
  - **Both delivery pushes traverse this leg** (not the check-skipping `__handleResponse`): the **initial snapshot** (a 3-arg `lmz.call('NEBULA_CLIENT_GATEWAY', clientId, …)` at subscribe, analogous to Star's `deliverResourceUpdate`, [star.ts:65-67](apps/nebula/src/star.ts)) **and** the **update fanout** (the hand-rolled loop → `__executeOperation`). Both need to pass.
  - **Fence signal:** the push's `envelope.metadata?.caller?.bindingName === 'PROFILE'` (the pushing DO's identity, stamped by the framework on the outbound call — [lmz-api.ts:308](packages/mesh/src/lmz-api.ts)). Skip/replace the aud-equality check for PROFILE-origin pushes; leave `STAR`/`DEV_STUDIO` pushes **behavior-identical** (Phase 3 criterion). Sound because reach was already enforced by `requireProfileReach` at subscribe time, and a profile is intentionally cross-scope-visible. Trust boundary: `metadata.caller` is set by the trusted mesh, not the client — acceptable within the mesh trust model.
  - ✅ **Fence signal is reliable at any N** — because the fanout is the hand-rolled `lmz.call` loop (svc.broadcast is unavailable to the raw composer), it never traverses the broadcast tier worker, so `metadata.caller` is always `PROFILE`. (The tier-path caveat that would apply to `svc.broadcast` is moot — there is no tier hop.)
  - The client's own `onBeforeCall` is intentionally permissive and *delegates* the boundary to this Gateway check ([nebula-client.ts:1445-1461](apps/nebula/src/nebula-client.ts)), so fencing the Gateway check is the **complete** boundary change — the client won't independently reject.

**Two wiring dependencies this surfaced (required for the approach to route end-to-end; realized in Phases 1–3):**
1. **`env.PROFILE` must be bound in the single `nebula` Worker** that hosts `NebulaClientGateway` (`#handleClientCall` does `getDOStub(this.env['PROFILE'], profileId)`). The PROFILE DO class is **coded in `@lumenize/nebula-auth`** but **runs in the one `nebula` Worker** — re-exported from [worker.ts](apps/nebula/src/worker.ts) alongside `NebulaAuthRegistry`/`NebulaEmailSender` (the established pattern: `export { …, Profile } from '@lumenize/nebula-auth'`; note the per-scope `NebulaAuth` DO is dissolved by surrogate-sub), bound as an **ordinary local** DO binding `{ name: 'PROFILE', class_name: 'Profile' }` + a `new_sqlite_classes` migration entry in [wrangler.jsonc](apps/nebula/wrangler.jsonc). **No cross-script binding / `script_name`** — `env.PROFILE` resolves in-Worker, identical to `env.NEBULA_AUTH_REGISTRY` today. (Package-layer ≠ Worker: nebula-auth is the *code* home; deployment is one Worker.)
2. **The client needs a profile-subscribe entry that passes `profileId` as the instance.** Today *every* client call pairs `#resourceHostBinding` with `this.#activeScope` (nebula-client.ts call sites 477–1210); the binding is parameterized but the instance is hardcoded to `activeScope`. A profile subscribe must supply `('PROFILE', profileId)` — a new/parameterized path (Phase 3).

## Build phases
Real-login-grounded per [ADR-009](docs/adr/009-real-auth-path.md): any criterion touching the JWT `profile` claim or an authed identity is asserted on a **real email-login round-trip** (or rung-2 test-mode server issuance) — never a client-side mint. Note the `profile` claim can't ride rung-2/3 today (`buildNebulaJwtPayload` has no `profile` field), so **claim-presence assertions use rung-1 real login only**; any lower-rung mint that needs it must seed it explicitly.

### Phase 1 — Registry: mint `profileId` + the `sub↔profileId` join; add the `profile` JWT claim
**Goal**: every `sub` gets a `profileId` (1:1 in P1) + a join row, and the minted JWT carries the bearer's own profile URL. **Anchored to surrogate-sub's landed seams** (the old `nebula-auth.ts` DO is dissolved): `sub` is minted in the **registry** at authority points; the JWT is assembled in the **Worker** (`mintAccessToken` → `buildNebulaJwtPayload`), driven on refresh by the `RefreshTokenKV` record. ⚠️ **Anchors set mid-surrogate-sub-build (2026-07-13) — reconfirm at build start** that `#mintIdentity` is still the single mint funnel, `RefreshTokenKV` is still the shape, and the registry (not the Worker) writes the KV record in `consume*`; adjust if surrogate-sub settled differently.
**Success criteria** (capable-of-failing):
- [ ] **Mint `profileId` in the one authority-point helper.** `#mintIdentity` ([nebula-auth-registry.ts:119](packages/nebula-auth/src/nebula-auth-registry.ts) — the single helper `claimUniverse`/`claimStar`/`issueInvites` all funnel through) also mints a `profileId` (UUID) + writes a `ProfileJoins (profileId, sub, universeGalaxyStarId)` row on its **INSERT branch**, synchronously in the same method. Its existing `(email, scope)` idempotency **extends to `profileId`** (an already-minted identity returns its existing `sub` **and** existing `profileId` — never a second join row). Login **verify** (`getAndVerifyIdentity:145`) NEVER mints, so no `profileId` there. `sub → profileId` returns exactly one row (a second for the same `sub` must be rejected — reds if the single-valued invariant is dropped).
- [ ] **No async-seam split (B5 neutralized).** The join is a plain synchronous `sql.exec` in the single-writer registry — there is **no** `#loginSubject`-can't-do-async-RPC seam to design around (that per-instance DO is dissolved). `sub → universeGalaxyStarId` is a native `Identities` column (**B2 neutralized**), so the join needs no separate scope lookup.
- [ ] **`profileId` rides the KV refresh record so the claim survives refresh.** `RefreshTokenKV` gains a `profileId` field ([types.ts:111](packages/nebula-auth/src/types.ts)), and **every writer of that record includes it** — there are two: **(a)** `#recordRefreshToken` ([nebula-auth-registry.ts:564](packages/nebula-auth/src/nebula-auth-registry.ts) — the single KV-write funnel for `consumeMagicLink`/`consumeInvite`; resolve `profileId` from the join beside the existing `sub`); **(b)** the `setIdentityAdmin` **convergence re-put** ([:600](packages/nebula-auth/src/nebula-auth-registry.ts) — it **rebuilds** the record, so it must **carry `profileId` forward**, exactly as it re-applies the original expiry, or the claim vanishes after any admin change; M4-analogous). In **P1** `profileId` is immutable, so this is **carry-forward, not convergence**; ⚠️ a **P2 re-point** (moving a `sub` onto a shared `profileId`) *mutates* it, at which point it joins `isAdmin` in the convergence re-put — additive (same machinery), but **don't annotate `profileId` as eternally immutable.** **Required** because refresh ([worker-token.ts `handleRefreshToken`:184](packages/nebula-auth/src/worker-token.ts)) is the **only** normal JWT-mint path and is **pure-KV** (never touches the registry). ADR-010-safe to denormalize (unlike `email`).
- [ ] **The `profile` claim is added at JWT assembly.** `profile: /profiles/PROFILE/{profileId}/` is emitted by [`buildNebulaJwtPayload`](packages/nebula-auth/src/access-claims.ts) — `mintAccessToken` ([worker-token.ts](packages/nebula-auth/src/worker-token.ts)) passes `profileId` from the KV record. Asserted on a **real login round-trip** (ADR-009). **Graceful**: a KV record without `profileId` mints the token **without** the `profile` claim (shouldn't occur post-wipe). The **delegated-token** mint (`handleDelegatedToken` → `getIdentityScope`, which returns no `profileId` today) likewise mints without the claim — **acceptable** (an act-for token resolves the acted-for profile via the join); extend `getIdentityScope` to return `profileId` only if delegated tokens should carry it.
- [ ] `sub → profileId` resolves **via the join, never off a durable record** — grep-verify no `profileId` column on `Identities`/grants/snapshots.
- [ ] The new **`@lumenize/nebula-auth → @lumenize/mesh`** dependency is added (`package.json` + `npm install`/type-gen) and is not a cycle.

### Phase 2 — the Profile DO (fields + private blob + the two async authz helpers)
**Goal**: a `PROFILE` DO (nebula-auth, composes `lmz-api`, keyed by `profileId`) holds the OIDC fields + private blob, gated by `requireProfileReach` (read) + `requireOwnerOrAdmin` (write/blob), resolved **live** from the join.
**Success criteria** (capable-of-failing):
- [ ] **Registered + reachable**: `Profile` re-exported from [worker.ts](apps/nebula/src/worker.ts); local `PROFILE` binding + `new_sqlite_classes`; `getDOStub(env.PROFILE, profileId)` resolves in-Worker. Tables (fields + subscriber rows) created **synchronously in the constructor** (raw-DO init, **not** `onStart` — a raw composer has none), `WITHOUT ROWID` on the `profileId`/PK columns (write-cost).
- [ ] **`requireProfileReach` REJECT**: a caller whose reachable-scope-set (`{aud}` non-admin / `authScopePattern`-coverage admin) does **not** intersect the profile's scopes (live from the join) is refused. **Fail closed** on a registry-lookup error (an error rejects, never admits).
- [ ] **`requireOwnerOrAdmin`**: owner (`caller.sub` ∈ the profile's owner-subs, live) **or** admin (`access.admin` && `matchAccess(pattern, S)` for a profile scope `S`; super-admin `*` covers all). A **different-scope admin** whose pattern covers **none** of the profile's scopes is rejected (capable-of-failing — the cross-Galaxy-admin case).
- [ ] **Blob gate = `requireOwnerOrAdmin`**: owner/admin read+write the blob; a **reach-only co-member** reading the blob must **RED**. The LLM path passes **as the owner** (`originAuth.sub == owner`) — no separate agent principal (authz off the authority `sub`, never `act`). Blob **seeded directly** for the test (its LLM-write flow is deferred).
- [ ] The helpers are **async method-body calls** (awaited live registry read; public registry method; narrow `using` stub) at the top of each `@mesh` method — **not** `onBeforeCall`.
- [ ] **No ADR-004/005**: a second write **replaces** the current fields (last-writer-wins), not a new snapshot row; the emitted `Snapshot` carries a forward-only ULID `eTag` (for the client engine) but no OCC conflict-check.

### Phase 3 — client subscribe (binding-agnostic) + the Gateway PROFILE-fence + fanout
**Goal**: a client subscribes to a `profileId` and receives live updates cross-scope; the scoped path is untouched.
**Success criteria** (capable-of-failing; from the verified routing model):
- [ ] A profile subscribe routes end-to-end `lmz.call('PROFILE', profileId, …)` → Gateway (authN + route) → PROFILE DO, **without** the profile instance equaling the client's `activeScope`.
- [ ] **The headline**: a subscriber in scope **X** receives a profile update for a person whose `sub` lives in scope **Y** (`X ≠ Y`) — **reds without** the `onBeforeCallToClient` PROFILE-fence, green with it. **Vehicle**: two **real magic-link logins** into **distinct** scopes (Y owns + mutates the profile, X subscribes) — ADR-009 rung-1; a same-scope fixture makes "reds without the fence" **vacuous**. Cover **both** the initial-snapshot and update-fanout legs.
- [ ] **Fanout** is the hand-rolled `lmz.call` loop from the Profile DO to `NEBULA_CLIENT_GATEWAY` over its subscriber rows (not `svc.broadcast`). A **disconnected subscriber's row is dropped** after a failed push — assert the transient removal via the `onProfileBroadcastResult` (`onErrorOnly`) handler, mirroring `Star.onBroadcastResult` (per testing.md §self-healing-transient, not just "no error").
- [ ] The client gains a `('PROFILE', profileId)` subscribe path (instance ≠ `activeScope`) landing in the **same reactive store** (forward-eTag `Snapshot` via `handleResourceUpdate`).
- [ ] The scoped `STAR`/`DEV_STUDIO` path stays **behavior-identical** (the fence keys on PROFILE-origin pushes only — a scoped-push regression must red).
- [ ] **Revocation window (accepted + stated)**: a subscriber who loses co-membership **after** subscribing keeps receiving **public-OIDC-field** pushes until reconnect/unsubscribe (the push leg isn't re-gated — the fence skips `onBeforeCallToClient`, and the DO lacks the subscriber's *live* claims at push time). Blast radius = fields that are Star-visible anyway; the **private blob never rides a co-member push**. The drop-on-revoke fix rides with the deferred denormalization-push. Justified against ADR-008 for pre-alpha (rare; public fields only) — documented, not silent.

### Phase 4 — `sub → profileId → display` resolution for consumers
**Goal**: presence / chat / org-tree resolve a bare `sub` to a display identity via the live-cached join.
**Success criteria** (capable-of-failing):
- [ ] A consumer resolves a roster `sub → display` (email now; `name`/`nickname` when set) through the join; the cache is **loss-tolerant** (no durable instance state — [durable-objects.md](.claude/rules/durable-objects.md)).
- [ ] A profile field change **invalidates/refreshes** the resolved value for holders (assert the transient refresh, not just the converged value — testing.md §25).
- [ ] An unknown / departed `sub` **degrades gracefully** (render the `sub` or a generic label), never throws.

## Non-goals / deferred
- **P2 — global "person" / cross-Universe profile sharing** (link many `sub`s' profiles into one canonical the person edits once). The join + live-resolution make it **additive later** (re-point a second `sub` at an existing `profileId` — no re-key); trigger = a real cross-Universe sharing need. **Do not** build the person-layer now. **Planned unification trigger (design seed, 2026-07-13):** a **root-path, non-httpOnly breadcrumb cookie** (`Path=/` set **explicitly** — omitting Path scopes to the setting dir, not the origin; `SameSite=Lax`, host-only) records the last `profileId` seen in this browser, set at **login** (`consumeAndLogin`, riding the existing refresh `Set-Cookie` — refresh no longer re-sets cookies). Its point is the one case the server **cannot** see — *different email, same person, same browser* (same-email-across-scopes the registry already links via `discover(email)`, so the cookie isn't redundant with it). ⚠️ **The cookie is UNTRUSTED / advisory only** — it may trigger a "link to your existing profile?" prompt but is **never** an input to the link decision: the link must independently **prove control of both** identities (safe form: auto-offer only when a **live** session for the other profile exists; a stale breadcrumb only prompts a "sign in to link" flow). Shared/kiosk-browser identity contamination is the failure mode this rail closes. JS may **write** it only to clear it ("not me"); read-only otherwise. A manual **"merge profiles"** feature is the fallback for the rest.
- **Per-scope display name** (the way `email` is per-scope) — v1 is one `name`/`nickname` per profile; the per-scope door is the same one `email` opened, if ever needed.
- **The denormalize-scope-set-to-Profile-DO scale fix** — deferred until the per-subscribe registry read is a *measured* bottleneck. It must be denormalize-**with-invalidation** (registry pushes on change); that same push **closes the Phase-3 revocation window**.
- **The LLM-writes-the-blob flow** — the field + its owner/admin read-gate ship now (Phase 2), but Nebula *extracting/updating* personal understanding is a later write path (the gate is tested by seeding the blob directly).
