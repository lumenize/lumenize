## Objective (target, present tense)
The Studio chat is a **durable, multi-user, reactive** thread. Human messages AND the AI (Nebula) reply already persist as `Message` Resources, so the bulk of the work is **render + host-binding + attribution** (not adding storage) — plus a **schema tightening** (drop the spoofable `role`/`author` fields, Phase 1). Concretely: **render the thread from a live subscription** so reload / reconnect / multi-tab / a second participant all restore + stay live, and **attribute each message to a stable identity**. A message's author is its snapshot's server-stamped **`changedBy.sub`** (an opaque per-person UUID) — never a client-supplied field; the display **name** is resolved by a **reactive lookup into a live roster subscription** (`sub → name`; email now, friendly-name later — the roster is built in the [presence prerequisite](archive/nebula-presence-subscription.md), chat consumes it). This completes the `Message` substrate **THE GATE (capture-live) rides on** — durable, identity-attributed messages are what make "what did each user ask?" capturable.

## Participant model (settled with Larry 2026-07-06)
`/review-task` pins mechanics, not the model.

- **Author attribution = the snapshot's `changedBy.sub`; the DISPLAYED author = `{actor} for {principal}` when an `act` is present (e.g. *Nebula for {human}*), else just the `sub`** — the `Message` type carries **no `author` field** (the data form of DRY; the existing `author?` is actively dropped — see Phase 1). `changedBy` is an **`ActClaim`** (`@lumenize/auth`'s recursive `{ sub, act? }` type — the authority `sub` plus the nested actor chain; RFC-8693 provenance) server-stamped from `callContext` on every snapshot ([resources.ts:36](apps/nebula/src/resources.ts)), unforgeable, **already delivered** on `Snapshot.meta` (just not consumed yet). `sub` is a durable per-person UUID (`Subjects` PK), not an email. This **eliminates the author-spoof** (B2) at the **render** layer — the displayed author derives from `changedBy.sub`, so a stray/injected `author` key in the value is simply never read. The guarantee is render-side derivation, **not** validation-stripping (typia `validate` is non-strict → excess keys are NOT stripped; see Phase 1).
  - **Authorization always keys off the authority `sub`, never `act`** (RFC-8693: `sub` = the principal whose permissions apply, `act.sub` = the actor, traceability only). The display (above) deliberately shows **both** — a Nebula message → *Nebula for {human}*; an admin who minted an **`actFor`** delegation → *{admin} for {user}* — else just the principal, which dissolves the impersonation-display question rather than deferring it.
- **The `Message` type has no `role` field** (dropped — see Phase 1); our model uses **`agent`** (kind + method names) + the display name **`Nebula`**, never "assistant". ⚠️ **Separate thing, leave it:** `ChatMessage.role:'user'|'assistant'` ([dev-studio.ts:736](apps/nebula/src/dev-studio.ts)) is the **codegen model provider's** request format (the `{role, content}` array `callModel` sends to `env.AI`) — not our `Message` Resource. The human-vs-agent distinction lives in `kind` (next bullet), not a `role`.
- **`Participant { sub, kind, name }` is RESOLVED by a reactive lookup (not a per-render re-fetch), never stored on a Message.** Three sources: `sub` (from `changedBy`), `name` ← `email` via a reactive lookup into the **live roster subscription** the client holds (departed authors degrade, Q3), and **`kind` derived** — `sub === NEBULA_SUB` → `agent`, else `human` (pre-alpha assumes everyone but Nebula is a human). Nothing (`name`/`kind`) is stored on the Message; `Nebula` is a static roster entry. *(Richer per-person memory — what Nebula learns/asks about someone — is explicitly deferred; see Non-goals.)*
- **Human vs agent is a participant property, not a capability role.** Capabilities are uniform at the API, gated in the UI — streaming-thinking is an agent affordance any author *could* emit; humans just don't get the option.
- **Author stamping — the asymmetry is correct:**
  - **Human message** → `changedBy` is stamped from `callContext.originAuth` automatically (the human is a real remote origin). Nothing to build — it already happens.
  - **Nebula message** → the codegen round runs under the **triggering human's** `callContext` (fired by that human's `chat()` call), so the authority `sub` stamps automatically; DevStudio adds Nebula as the **actor** — a **trusted, server-supplied write-option** (the actor id ONLY — never a full `changedBy` override, and NOT `callContext.state`, which a client can seed → forge), composed in `#buildChangedBy` to *prepend* the outermost `act`. Result `{ sub: <triggering human>, act: { sub: NEBULA_SUB } }` — so each Nebula reply is attributed to the human who prompted it (a capture win). The authority `sub` can never be caller-set → the authz-off-`sub` invariant holds by construction. *(Mechanism shape — signature/threading — lives in **Files**. Cross-node agents supply the same actor via a trusted callContext field → [on-hold/delegation-hardening.md](on-hold/delegation-hardening.md).)*
- **"Immutable" is a UI convention, not a backend property** (ADR-004): a write within the debounce window updates the current snapshot *in place* (new value, new eTag) — this is what powers streaming below. Chat enforces immutability in the UI: text box local until submit, one write on submit, read-only after.
- **Writes go through the standard `transaction`** — the user message via `client.resources.transaction`, Nebula's via DevStudio's internal `transaction`. The reactive `Message where session==…` query-sub view IS "the list"; no separate list resource.

## Name resolution — consume the presence subscription
Name resolution rides the **presence subscription** built in the prerequisite [nebula-presence-subscription.md](archive/nebula-presence-subscription.md) (a read-gated `ResourceDataPlane` capability: a client subscribes to a query's *subscriber set*). Chat **subscribes** to the session's participant roster (`sub → name`) and resolves each message's author by a **reactive lookup** on `changedBy.sub`; departed authors degrade (Q3); `kind` is derived (`sub === NEBULA_SUB` → agent). Everything server-side — the claims storage, the fail-closed read-gate, the join/leave re-push, the separate `PresenceSubs` registry — lives in the presence task; chat only consumes the client subscription. Nebula's codegen also reads the roster in-DO on DevStudio ("who's in the chat") for free. *(The earlier "no security cost, generic across hosts" framing was corrected: the flat multi-node set would leak `sub`+`email`, and there is no existing "read of a query" gate to compose with — so the presence task ships the **single-node** version, sound because a chat session pins one shared node; generic multi-node is deferred there.)*

## Deferred generalization (fenced — do NOT read the shortcut as the model)
The general target is that *every* agent (Nebula + a future **Claude Code bridge**) participates via the same mesh-authenticated path. Three layers, different costs:
1. **Data + participant model** *(general NOW — ~zero cost)*: identity-from-`changedBy`, `Participant{kind}`, no `role`. A future external agent slots in with no schema change.
2. **Write mechanism** *(contained)*: in-DO now (Nebula's `actAs` write-option) vs cross-node later (the actor arrives via a trusted callContext field) — **same `#buildChangedBy` composition, only the transport differs**; cross-node deferred → [on-hold/delegation-hardening.md](on-hold/delegation-hardening.md).
3. **Agent capability surface** *(DEFERRED — high cost + speculative)*: exposing `writeSource`/commit/preview-push as participant-facing mesh operations + authorization. Triggered by the first EXTERNAL agent. Nebula's internal write is a fenced shortcut, not the end state.

## Open questions (pin at `/review-task`)
1. **Nebula's reserved `sub`** — a reserved UUID (uniform with human subs; the static roster entry says it's Nebula) vs a self-describing `agent:nebula` id. Lean reserved UUID.
2. **Host-binding fix shape** — the user Message currently lands on **STAR**, not DevStudio, because `App.vue` builds the client with no `resourceHostBinding` (defaults `'STAR'`, [nebula-client.ts:499](apps/nebula/src/nebula-client.ts)) while the session + query-sub live on DevStudio. But a `DEV_STUDIO`-bound client "must NOT enable `onReload`/an org-tree" ([nebula-client.ts:201-204](apps/nebula/src/nebula-client.ts)) and the studio *does* those — so pin: one `DEV_STUDIO`-bound client for chat + a separate path for org-tree, vs. route `postUserMessage` explicitly at `DEV_STUDIO` (like `chat()` already does at [nebula-client.ts:1373](apps/nebula/src/nebula-client.ts)). Lean the latter (smaller).
3. **Historical author not currently subscribed** — for pre-alpha (single fixed session, few mostly-present participants) **degrade gracefully** (render the `sub` or a generic label); don't build a cross-DO resolver. Revisit if sessions get many rotating participants.
## Phases

### Phase 1 — Identity-from-`changedBy` + host-binding (backend)
**Goal**: messages are attributed to a stable `sub` with no spoofable field; the user message lands on DevStudio. *(Name-resolution / roster moved to the [presence prerequisite](archive/nebula-presence-subscription.md).)*
**Success Criteria**:
- [ ] `Message` ontology ([devstudio-resource-ontology.ts:60](apps/nebula/src/devstudio-resource-ontology.ts)) **drops `role` AND the existing `author?` field** — and (critical) **stops writing them at the two write sites** (`postUserMessage`, `commitAgentMessage`). typia `validate` is **non-strict** (it neither rejects nor strips excess keys — `transaction` writes `result.data` verbatim), so a type-only drop would leave `role`/`author` silently persisting at rest **with a green build**. **Run the mandatory breaking-ontology ritual** (header L17-22): bump `SESSION_MESSAGE_ONTOLOGY_VERSION` + the `/vN` of `SESSION_MESSAGE_BUNDLE_ID` (so a warm Worker-Loader doesn't serve a stale validator) + wipe DevStudio snapshots (cheap — greenfield pre-alpha). Update the stale `author` doc-comment. *(Coordinate with THE GATE's container-git-hash field, master L86 — land both in one bump, not two back-to-back.)*
- [ ] `postUserMessage` stops writing the client `author` (and `role`); attribution comes from `changedBy` (server-stamped) with zero client input — **B2 closed at the render layer**. Capable-of-failing (render-side, since typia won't strip): a client that **writes a conflicting `author`/identity key into the Message value** cannot alter the **rendered/subscribed** author — it derives from `changedBy.sub`. Assert the render, **not** absence-from-storage (the stray key persists, so that assertion is vacuous).
- [ ] The user Message lands on **DevStudio** (the session/query-sub host), not STAR (Q2). Verified by the query-sub emitting the user message.
- [ ] **Nebula's** message write produces `changedBy = { sub: <triggering human>, act: { sub: NEBULA_SUB } }` (via the `actAs` write-option — mechanism shape in **Files**); define/import `NEBULA_SUB` (the **actor id**, not a standalone subject). Capable-of-failing: a client seeding `CallOptions.state` cannot alter the stamped actor, and `changedBy.sub` is the triggering human, never `NEBULA_SUB`. Rename `commitAssistantMessage → commitAgentMessage` (leave the model-provider `ChatMessage role` alone; grep-verify the bare identifier).
- [ ] **Migrate, don't ossify** (testing.md): update the existing tests that assert `.role`/`.author` on a `Message` value to the new shape — at least `child3-post.test.ts:57` + `child3-session.test.ts:84`; grep `\.role`/`\.author` across the baseline suite for the full set.

### Phase 2 — Reactive multi-user thread: subscribe + render (SPA)
**Goal**: the thread renders from the subscription; reload/reconnect/multi-tab + **three participants** work; each message shows its resolved name.
**Success Criteria**:
- [ ] `App.vue` replaces the local `messages` array with a live `client.resources.subscribe` to the session's Messages (load all — windowing is YAGNI, few messages).
- [ ] `App.vue` subscribes to the session's **presence roster** (from the [presence prerequisite](archive/nebula-presence-subscription.md)) and each Message renders by its author's **`kind`** (human vs agent — agent gets Nebula's affordances), labeled with the **resolved name** — a reactive lookup of `changedBy.sub` into that roster (`email` now, "Nebula" for the agent), so a late-joiner's name back-fills all their earlier messages automatically. The user's own message renders immediately.
- [ ] **Reconnect and reload are asserted as distinct paths** (ADR-003 — reconnect replays the in-heap subscription registry [nebula-client.ts:756](apps/nebula/src/nebula-client.ts); reload rebuilds from a fresh heap; the idempotent end-state hides a broken reconnect re-walk, testing.md §25): (a) **reconnect** — force a WS close, assert the subscription **re-delivers without a full reload** (assert the transient re-push, not just the healed list); (b) **reload** — fresh client, assert **restore-from-subscription**.
- [ ] **Multi-user (the headline)**: `/live` drives **three participants live in one chat** — Nebula + two simulated humans via **real email login** (ADR-009: two `@lumenize.io` addresses through the catch-all, **not** minted tokens) — and every participant sees all messages, correctly attributed, live. *(Blocked on the harness real-email multi-user conversion — see Prerequisites.)*

Must red against pre-fix `App.vue` (local-array, no subscribe).

### Phase 3 — Update-in-place streaming (single mechanism)
**Goal**: Nebula's thinking streams through the *normal* subscription; the old ephemeral paths are gone (no dual-path interim — Larry: "interim becomes ossification").
**Success Criteria**:
- [ ] Nebula's `Message` streams via **create-once-then-`put`**: the first chunk creates it, each later chunk **`put`-updates in place** through the debounce branch (`op !== 'create'`, same-actor + within-window — ADR-004). **NOT `ensureResource`** — it's create-if-absent (short-circuits on an existing snapshot, only emits `op:'create'`), so a 2nd streaming write is a silent no-op; `ensureResource` stays only the session-seed / idempotent-first-create path. **`actAs: NEBULA_SUB` must be byte-identical on the create AND every `put`** — the in-place collapse is a `JSON.stringify(changedBy)` compare ([resources.ts:217](apps/nebula/src/resources.ts)), so any per-chunk drift opens a new snapshot row (the duplicate this phase forbids).
- [ ] The `svc.broadcast` transient stream + the ephemeral `onChatResult` local-array path are **removed** (master's Child-3 deferral).
- [ ] Capable-of-failing test: a streamed message stays **one snapshot row** across all chunks — assert the snapshot count / stable `validFrom`, **not** just the healed "renders once" end-state (the self-healing trap, testing.md §25). A variant where an intermediate chunk's `changedBy` differs (actAs dropped) **must red** — proving the byte-identical-`actAs` invariant.

## Multi-user / security / act-as notes
- **Authorization unchanged** — post/subscribe is DAG-gated per-push (Child-2 `accessAdmin` recheck under `SESSION_NODE_ID = ROOT_NODE_ID`). Multi-user works because all participants with access to the scope's DevStudio share the one session.
- **Act-as delegation**: a delegated (`actFor`) token keys off the authority `sub` not `act`, so `changedBy.sub` = the acted-for user — attributed to that synthetic `@example.com` subject. Correct for exercising multi-user.
- **Why multi-user is justified pre-alpha** (preempts the solo-persona strategy check): it's a **near-free byproduct** of identity-from-`changedBy` + subscribe (no extra mechanism), and it's the generic participant substrate the platform needs regardless — exercised now via act-as/simulated users. Not a collaboration-first pivot; the substrate is generic (a helper joining a chat is just another participant).
- **Feeds THE GATE**: capture reads these Messages; identity-attributed user messages are the highest-value signal.

## Non-goals
- Friendly display names / profiles / avatars — deferred; names resolve to email (from claims) until a friendly-name JWT claim / profile store lands (then it resolves for free).
- **Per-person memory / preferences** — Nebula learning + storing what it knows about each participant (extracting it from the conversation, letting them edit it via chat, a structured store — probably markdown — for it) is a real future direction, but **not now**. Pre-alpha gets away with `sub` + `email` from the subscriber roster.
- The **general agent capability surface** — deferred to the first external agent (→ Deferred generalization, layer 3).
- Presence *UI* (online/typing/read-receipts), anti-flap/debounce, and the presence mechanics generally → owned by the [presence prerequisite](archive/nebula-presence-subscription.md)'s Non-goals; chat just consumes the roster for name resolution.
- Multi-**session** management UI (`DEFAULT_SESSION_ID` stays the single fixed session).
- The offline replay harness (Wave 2).
- **Email-reuse hardening** — the login email→sub mapping means a reassigned mailbox + stale `Subjects` row lets a new human inherit the old `sub` (rare; auth-model, orthogonal to chat). Negligible pre-alpha; tracked in backlog for alpha/beta.
