- [ ] **`subscriptionRequired` is broken — it reports "subscriptions intact" when the Star has already dropped them.** The Gateway computes the flag from its **own** grace alarm ([`#isSubscriptionRequired`](../packages/mesh/src/lumenize-client-gateway.ts), ~:823): sockets present, or alarm pending within grace → `false`, meaning *"your server-side rows are still registered, don't re-subscribe."* But rows are dropped by the **Star**, reactively, on a `ClientDisconnectedError` from a broadcast ([`star.ts` `onBroadcastResult`](../apps/nebula/src/star.ts)) — a decision the Gateway's alarm knows nothing about. The two are uncoordinated, and the token-expiry branch drives them apart on the **most common** refresh path:
  - `__executeOperation` finds a live socket whose `exp` has passed → `ws.close(4401)` **and** returns `ClientDisconnectedError('Client token expired')` ([`lumenize-client-gateway.ts`](../packages/mesh/src/lumenize-client-gateway.ts), ~:502) — before any grace window exists.
  - `Star.onBroadcastResult` → `removeSubscriber`. **Row gone.**
  - `webSocketClose(4401)` → grace alarm set. Client refreshes (~100 ms) and reconnects *within* grace.
  - `#isSubscriptionRequired()` → **`false`**. A client that trusted the flag has silently lost that subscription until a page reload — it just sees a resource that stops updating.
  - **Nothing is broken today** because `NebulaClient` **ignores the flag entirely** and re-subscribes unconditionally on the `reconnecting → connected` transition ([`nebula-client.ts` `#resubscribeAll`](../apps/nebula/src/nebula-client.ts)). The flag has **zero** Nebula consumers; its only users are a mesh unit test and the for-docs mini-apps. Per the Nebula-is-Mesh's-first-consumer rule this is **mesh product feedback**: the flag can't express what a real consumer needs, because it lives in the Gateway and the cleanup decision lives in the Star.
  - **Consequence of not being able to use it — write cost.** Ignoring the flag means *every* reconnect re-issues N subscribes → N `INSERT OR REPLACE` **billed DO writes** (DO SQLite writes are ~1000× reads) + N initial-snapshot pushes back, for a client that may have lost nothing at all. The snapshot pushes deep-equal-dedup client-side, so this costs writes and bytes, not UI churn — but a flappy connection on a client with many subs pays it on every blip. **This is the symptom; the flag being wrong is the defect.**
  - **Fix direction (unverified):** stop conflating "I couldn't deliver" with "the client is gone" — a live-socket-expired-token client is *self-healing*, so the Gateway should report it distinctly (or not at all) and the Star should not drop on it. That alone would make the flag honest for the common path.
  - ⚠️ **A fix is necessary but NOT sufficient for gating the client resubscribe.** Two more things the flag cannot express even when correct: (1) **pending-snapshot recovery** — rows-intact ≠ snapshot-delivered; a subscribe whose initial push was lost in flight leaves the row registered and the client's `snapshot` Promise hanging forever, since already-sent fire-and-forget messages aren't replayed; (2) **`accessAdmin` re-derivation** — the confined admin verdict is pinned onto the row at subscribe time from `originAuth` ([`query-subscriptions.ts`](../apps/nebula/src/query-subscriptions.ts), ~:140, same for `Subscribers`), and a fresh `subscribe` is the only thing that re-derives it, so a gated reconnect would skip re-derivation in exactly the case where the token's claims just changed (the demote self-heal). Any gating proposal must answer all three, not just this one.

- [ ] Add retry + skip logic for alarm handler failures
  - **Problem**: Currently, handler errors are caught and the alarm is deleted (one-time) or rescheduled (cron) — silent fire-and-forget with no retry
  - **Design**:
    1. Add `retryCount INTEGER DEFAULT 0` and `status TEXT DEFAULT 'pending' CHECK(status IN ('pending', 'skipped'))` columns to `__lmz_alarms` (migration needed)
    2. On handler failure, increment `retryCount` and set `time` to `now + 2^retryCount` seconds (exponential backoff)
    3. After 5 failures, set `status = 'skipped'` and log via `@lumenize/debug` (`lmz.alarms.Alarms` namespace)

- [ ] **`keepAlive` primitive for long-running DO operations (LLM calls, agent turns) — defeat idle-eviction during a single long await**
  - **The platform reality (analysis, 2026-06-22)**: per Cloudflare's [2026-06-19 changelog](https://developers.cloudflare.com/changelog/post/2026-06-19-outbound-connections-keep-dos-alive/) + [DO lifecycle docs](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/), an outbound **TCP / WebSocket** connection now keeps a DO alive for up to **15 min** — but **plain `fetch()`, Workers RPC, and bindings get nothing**. They're *subrequests*: while a handler awaits one, the DO counts as **idle** and is evicted after 70–140s of no *incoming* traffic, killing the in-flight call (streaming response bytes don't reset the clock). The shield is transport-specific (`connect()` TCP / outbound WS only, incl. a `fetch()` upgraded via `Upgrade: websocket`), NOT operation-duration. CF's own Agents docs confirm this shape is evictable and build `keepAlive`/`chatRecovery` for it.
  - **Motivating consumer**: `DevStudio.chat` ([dev-studio.ts](../apps/nebula/src/dev-studio.ts)) calls the model via the **Workers AI binding** (`env.AI.run`) — a subrequest, so **zero** connection shield. Today's single-SFC turn finishes inside the window, but the real agentic loop (multi-step, longer thinking) stacked on a cold container boot (`ensureUp`) can cross 70–140s with no incoming traffic → DevStudio evicted mid-generation. Wire the scoped heartbeat into `chat` when the agentic loop next gets a substantive pass (sequenced in [tasks/nebula-pre-alpha.md](nebula-pre-alpha.md); loop spec frozen at [tasks/archive/nebula-codegen-loop.md](archive/nebula-codegen-loop.md) — deliberately not wired here).
  - **Design**: a scoped `keepAlive` that **arms a self-rescheduling alarm** (≤~60s, under the 70s floor — go ~45–50s for jitter margin) at the start of a long op and **clears it at the end**. An alarm *is* an incoming event → resets the eviction clock; a self-`setTimeout` loop is internal JS (not clearly an "incoming event") and a single long one falls into the same idle-evict trap. Client-driven app-level pings are NOT the answer — a backgrounded / frozen / discarded tab is unreliable exactly when a long turn is running. Build it on **`svc.alarms`** (it already owns the single physical alarm slot) so it **multiplexes** with real app alarms instead of clobbering them — the slot collision is the actual integration cost. Scope it to the op (don't pin idle DOs alive forever — burns duration billing and defeats hibernation).
  - **Not a substitute for durability**: a heartbeat defeats *idle eviction* only; it does nothing for DO restarts/deploys (~1–2×/day) — anything you can't lose still needs checkpoint/resume. (The `cf-long-stream-limits` memory holds the platform-fact version of this, currently the older model.)
  - **Related**: the alarm retry/skip item above (same `packages/mesh/src/alarms.ts`); [tasks/icebox/lmz-call-eviction-safe-by-default.md](icebox/lmz-call-eviction-safe-by-default.md) (different mechanism — an RPC stub held across an await); [tasks/on-hold/mesh-cost-guidance-rebalance.md](on-hold/mesh-cost-guidance-rebalance.md) (the lifecycle-diagram billing data point — "waiting on a `fetch()`" bills; RPC rides the subrequest path).

- [ ] Audit tests for unawaited expected-rejection cases and remove `dangerouslyIgnoreUnhandledErrors` flag

    ```ts
    someOp();  // kicks off an op that will reject
    expect(somethingElse).toBe(x);  // test completes
    // someOp's rejection arrives AFTER the test → unhandled
    ```

- [ ] Audit RPC call sites for proper `await` and turn off SonarQube `no-return-await` rule
  - **Why**: Cloudflare DO best practice says always `await` Workers RPC calls — unawaited calls become fire-and-forget, which (a) may rejection-leak (surfaces as vitest 4 "Unhandled Errors"), and (b) can end the request context before the RPC completes. SonarQube's `no-return-await` rule pushes you to remove `await` from `return await rpc()`, which changes try/catch semantics in a DO-hostile way: `return await foo()` catches errors *locally* in the current try/catch; `return foo()` passes them to the caller. The `no-return-await` rule was retracted by ESLint/typescript-eslint in 2023–2024 for this exact reason — SonarQube hasn't caught up.
  - **Audit approach**:
    1. Grep for RPC call patterns: `grep -rn '^\s*\(env\|this\.\w\+\|stub\)\.\w\+(' src/ packages/*/src/`
    2. For each hit, classify: awaited / returned / fire-and-forget
    3. Fire-and-forget cases must be intentional (`ctx.waitUntil` / `lmz.call` with explicit callback per the fire-and-forget-error-delivery pattern in CLAUDE.md) — anything else gets an `await` or `return`
    4. Inside try/catch that wants local error handling, prefer `return await` over `return` (SonarQube will complain — that's the point)

- [ ] **One verified-claims HEADER on the edge→DO hop, replacing the body injections (surfaced 2026-07-29, Larry).** Two conventions exist today for "the edge verified a JWT, downstream needs the claims", and they disagree. The **registry** path parses the body, mutates it, and re-`JSON.stringify`s it to carry `verifiedAccess` / `callerSub` / `callerClaims` ([router.ts](../packages/nebula-auth/src/router.ts) `forwardToRegistry`). The **mesh** path forwards the raw token and re-decodes it downstream, hand-rolled, in [lumenize-client-gateway.ts](../packages/mesh/src/lumenize-client-gateway.ts). **Replace both with a single decoded-claims header** set on the way in.
  - **Why the header wins on mechanism, not taste:** body injection **cannot work for GET** or any bodyless request, and it forces a body rebuild whose costs `raw-comm.md` already documents (stream consumed, so a body-reading pre-check must `clone()`; a `JSON.stringify` round-trip that re-encodes the payload). A header-only rewrite touches **neither** — `new Request(request, { headers })` passes the body through as a stream and preserves every existing header. ⚠️ *This is not a return to raw `stub.fetch(request)` forwarding*; it is a header-only rewrite, which is a third thing.
  - **The machinery already exists and is already used twice.** [route-do-request.ts](../packages/routing/src/route-do-request.ts) does exactly this move for the routing metadata (`X-Lumenize-DO-Instance-Name-Or-Id`, `X-Lumenize-DO-Binding-Name`), and `routeDORequest`'s `onBeforeConnect` / `onBeforeRequest` hooks already accept a returned `Request` as a first-class way to enhance one — which is how `apps/nebula/src/entrypoint.ts` normalizes the WS subprotocol token into `Authorization: Bearer`. Name the new header into the same `X-Lumenize-…` family.
  - 🔒 **Security discipline — `set`, never merge.** A client-supplied copy of the header must be **unconditionally overwritten** at the edge (`security.md` § trust-boundary crossings; the same rule the body injection already lives under). What makes it sound is platform-enforced rather than assumed: a DO is reachable only through a binding held by a Worker in the account, so there is no public route that bypasses the edge.
  - 🔒 **Keep forwarding the raw token alongside it — do NOT let the header replace it.** The header is **derived and unverifiable**; the token is self-authenticating. Frame the header as a **per-hop cache of the token's payload**, never a parallel channel: the token stays authoritative, the header must never be persisted or outlive the hop, and a consumer that needs to *establish* trust verifies the token rather than trusting the header. ⚠️ **This is the clause that protects the reason for doing it at all** — mesh nodes answering HTTP (Resources reads, MCP) are reachable by routes that are not today's WS entrypoint, and only the signature lets such a node establish trust for itself.
  - **Contract ownership:** `@lumenize/auth` should own the header name + shape — it is what verifies, and `packages/mesh` already depends on it (declared, non-circular, and already imported by `lumenize-client.ts`). Mesh and `nebula-auth` then read one defined contract instead of two ad-hoc conventions. Update `raw-comm.md` § *Edge Worker fronting a DO*, whose "rebuild only to inject trusted claims" guidance this supersedes.
  - **Simplifications it buys:** the three registry body injections collapse to one header — including the `callerClaims` field added 2026-07-29 for [ADR-016](../docs/adr/016-record-the-acting-principal.md), which stops being a special case; and the Gateway's hand-rolled base64url decode goes away entirely rather than needing a fix.

- [ ] **The scope/admin gates throw bare `Error`, so a refusal is indistinguishable from a bug.** `requireDominionHere` ([nebula-do.ts:54](../apps/nebula/src/nebula-do.ts:54)) and `requirePassage` ([:100](../apps/nebula/src/nebula-do.ts:100)) refuse with prose — `'Admin access required'`, `` `Admin access required for ${name} — your admin scope is …` ``, `'Active-scope mismatch'` — so nothing downstream can tell an authorization refusal from an internal failure, and the only way to branch is to match the message text.

  ⚠️ **Do NOT reuse `PermissionDeniedError` for these** — the reflex, and wrong three ways. Its constructor is `(tier: PermissionTier, nodeId: string)` and the gates have neither (they hold an instance/scope name, an `authScope` and the `scopeAdmin` bit). It is a **different check**: the per-node DAG tier check ([ADR-008](../docs/adr/008-full-org-tree-visibility.md) point-of-action) vs the scope boundary ([ADR-015](../docs/adr/015-passage-and-dominion.md)). And [resources.ts:557](../apps/nebula/src/resources.ts:557) catches that class as meaning *exactly* the node-tier case, so widening it pulls scope-boundary failures into that branch — the too-broad-catch failure [mesh.md](../.claude/rules/mesh.md) § *Errors across mesh calls* and [security.md](../.claude/rules/security.md) § *Permission checks before resource mutation* both warn about by name.

  **The shape:** one class per refusal plus an `isX` guard, following [errors.ts](../apps/nebula/src/errors.ts) — roughly `AdminRequiredError { nodeName, authScope, scopeAdmin }` — ⚠️ **the discriminator changed with [nebula-passage-dominion-from-scope.md](archive/nebula-passage-dominion-from-scope.md)**: this shape originally keyed on *presence* of `authScopePattern` to separate "not an admin anywhere" from "admin, but not of this node", and that no longer works, because every member has an `authScope` and it is always present. The bit is now the discriminator — `scopeAdmin` false means the former, `scopeAdmin` true with a non-covering scope means the latter and `ScopeMismatchError { nodeName, aud }`. ⚠️ **Leave the fail-closed throws bare** ([:58](../apps/nebula/src/nebula-do.ts:58) and [:106](../apps/nebula/src/nebula-do.ts:106), both "missing callee instance name"): those are invariant violations, not refusals, and typing them as refusals is how a bug starts rendering to the user as "you lack permission."

  **Why it is worth doing at all:** the comment at [nebula-do.ts:64-67](../apps/nebula/src/nebula-do.ts:64) already records that the two admin refusals imply **different user actions** (switch scope vs. ask the admin above you) — a UX branch reachable today only by matching prose. ⓘ **No consumer needs it yet** — no `.name ===` branch in [nebula-client.ts](../apps/nebula/src/nebula-client.ts), and every in-repo match on these strings is a test assertion — so the status quo sits inside `mesh.md`'s own escape hatch (*"One typed Error per case, or string-match the message and mark the site with a TODO"*). ⚠️ **The ~31 string-matching assertions under `apps/nebula/test/test-apps/` are NOT an argument against** ([calibration.md](../.claude/rules/calibration.md) §3(c) — test callers weigh ≈ zero); noted only so the churn isn't mistaken for a blocker.

### Ontology depth (post-demo)

Strengthen the case that Nebula's data layer is an *ontology* (not just a typed schema + DAG). Triggered by the 2026-05-03 Kumar article and successors — see [tasks/reference/ontology-research.md](reference/ontology-research.md). Items below in priority order; each is independently shippable.

- [ ] **Action types** — typed semantic verbs on top of `resources.transaction` (e.g. `approveOrder`, `releaseHold`), each binding {typia input schema + precondition predicate + patch shape + emitted provenance event}. This is the single primitive most cited as the schema-vs-ontology dividing line (Palantir's moat; Fabric IQ's "permitted actions" is a shallower version). Highest narrative payoff per LOC. Provenance / audit-trail story falls out for free once verbs emit events.

- [ ] **Ontology introspection endpoint** — runtime API returning types, properties, relationships, action types, and constraints. typia already has this metadata at compile time; the work is exposing it. Required for Studio's LLM to ground itself without re-shipping types, and the cheapest item that flips Nebula from "typed CRUD" to "agent-readable ontology." JSON-LD / OWL serialization is a v2 if we ever want the vendor-neutral story.

- [ ] **Typed relationships** — promote DAG edges (or add a parallel relationship graph) to carry `relationshipType` with its own schema, navigable bidirectionally with `@inverse` already sketched in [website/docs/nebula/ontology.md](../website/docs/nebula/ontology.md). Without this the relationship story reads as "we have a DAG" rather than "we have an ontology graph." Cheap on top of the 5.3-shipped DAG normalization (`{nodes, edges, permissions}`).

- [ ] **Derived / denormalized-field invariants** — a declarative way to specify a stored field as a function of others (e.g. an annotation `@derived count(items where status === 'open')`) that the **server computes, stores, enforces, and lands in snapshot history** for time-series analytics — provably consistent, no client drift. The real fix for *stored* aggregates: round-4 (#9, 2026-06-14) made `openCount` a **client-computed view-only** value precisely because this doesn't exist yet (see [tasks/archive/nebula-frontend.md](archive/nebula-frontend.md) Out-of-scope + the round-4 decision). Extends the typia/JSDoc annotation vocabulary (ADR-001); feeds the temporal/analytics substrate (ADR-004). Likely pairs with **Action types** (the verb that maintains the invariant) and the **introspection endpoint** (exposing the derivation).

### Other Nebula backlog

- [ ] **`build-box`: a clean REBUILD after a broken bundle does not publish — *"the built dist did not arrive back from the container (sync pull incomplete)"* (INTERMITTENT — four consecutive reds on 2026-09-03, then green, with no build-path change in between).** Bundle ok, typeCheck clean, then `#distArrived()` finds no `dist/index.html` in the VFS. **Mechanism, grounded 2026-09-03:** the job runs plain `vite build`, so vite's DEFAULT `emptyOutDir` applies, and vite empties at WRITE time — a failed bundle leaves the old dist serving (build-box's `stillServes` passes), while a successful rebuild deletes first and writes second. In local materialize-mode the deletions sync back at once and the new writes can lag (the Discord-reported 1-in-3 `pending` pull), so for that window the VFS has NO dist — and if the pull never completes the app serves 404 until the next build. That is the real hazard; the red scenario is its messenger. `#buildOnce` already verifies arrival by reading the file (the `sync.status` field is deliberately not trusted — `pending` means the pull threw and is over) and re-pulls with a no-op exec, budget 5 — but the five fired back-to-back and could exhaust themselves inside the same in-flight pull; they are now spaced 250 ms doubling (~8 s). **Measured 2026-09-03 with the spacing in place:** the five re-pulls fired at 0.3/0.5/1/2/4 s, each exec returned at once, and after all five the dist still had `arrived: false` with the job reporting `pulled: 4` — and the next runs' builds reported `pulled: 0` outright. So in this state the pull is MISSING the writes, not lagging them, and no amount of re-pulling finds them; the no-op-exec heal did not reproduce. It had been green two hours earlier, which points at local computerd/sidecar state degrading over a day of container churn (stale `-proxy` sidecars from failed runs were still up). The spacing stays — it costs nothing on the happy path and is the right shape for the flake as originally described — but it is not the fix. **Real fix:** build into a temp dir and swap into `dist` atomically (or snapshot the last-good dist host-side and restore on non-arrival), so a lost pull never leaves nothing to serve. The assertion now carries `publish.why` so the next run says this on its face.
- [ ] **`callModel` has no timeout — a hung model call runs to the 300 s generation deadline.** `Galaxy.#callModelRest` is a bare `fetch` with no `signal`, and the deadline that eventually releases the single-flight latch never aborts the call. Today the client's idle window is the only thing that notices, and the turn heartbeat (`turn-heartbeat.ts`, 2026-09-03) is BOUNDED by that deadline precisely so it cannot mask this. A per-call `AbortSignal.timeout` would fail a dead model call in seconds rather than minutes — but it changes model-lane failure semantics (a slow-but-alive generation would be cut off), so it is a decision about the codegen loop, not a patch. - [ ] **Sweep: where does composing the data plane force convenience methods into the host? (surfaced 2026-07-28, Larry).** Now that `ResourceDataPlane` is composed onto more than one DO — `Star` + `DevStudio` today, and the collapsed `Galaxy` by the time anyone reads this — audit **every compose site** for methods that exist *only* because the data plane needed something from its host, and consider moving them inside it. **The known example is `#broadcastRosterUpdate`:** [star.ts:777](../apps/nebula/src/star.ts) and [dev-studio.ts:731](../apps/nebula/src/dev-studio.ts) are **byte-identical apart from a `ctn<T>()` type parameter that is erased at runtime**, with their JSDoc duplicated too; `onQueryBroadcastResult` and `onQuerySubscriberListBroadcastResult` are likewise identical pairs. **Root cause:** the data plane is constructed with `(ctx, () => lmz.callContext, ontologyProvider, { …six bridge callbacks… })` — it never receives `lmz`/`svc`, so it cannot originate a mesh call and every fanout has to bounce back out to the host. **Candidate fix:** pass a narrow mesh port (`{ broadcast, ctn }`, or just `lmz`) into the constructor; the six bridge callbacks and the three private fanout methods then collapse into the capability. ⚠️ **What must stay on the host:** the `@mesh()` result handlers — they are continuation targets the Gateway calls back **by name on the node**, and a method on a nested plain object is not in the mesh surface. - [ ] **`validFrom` global monotonicity (high-water mark) — future-proof transaction ordering for higher per-DO rates.** `#calculateValidFrom` ([resources.ts:140-161](../apps/nebula/src/resources.ts)) advances `validFrom` past the **batch's own** current snapshots only → per-resource monotonic, but two same-millisecond transactions on **disjoint** resources can share a `validFrom`. **Safe now** (Resources transactions peak ~400/sec, well under the 1000/sec ms-granularity floor — collision risk negligible). **Exposure:** if Cloudflare raises the per-DO throughput ceiling (e.g. ~4000/sec), same-ms collisions become real and break any use of `validFrom` as a **global** order. **Fix — server (Resources logic):** keep a **global high-water mark** and advance `validFrom` past *it* (not just the batch's max) → a strict total order of transactions on the DO. Two impls: **(A)** an in-memory mark seeded from `MAX(validFrom)` on cold start, advanced in memory (loss-acceptable, re-derivable — **no per-txn write**, at the cost of a cold-start derivation / a small `validFrom` index); or **(B)** a persisted KV high-water mark, read+write per txn (**+1 write/txn**, no cold-start scan — Larry's lean, "probably correct regardless"). Tradeoff to settle: advancing the ms under sustained >1000/sec makes `validFrom` a **logical clock** drifting from wall time; a composite `(validFrom, seq)` tiebreaker preserves wall-clock fidelity instead. **Fix — client:** the deferred query-sub delta-catch-up baseline ([nebula-query-subscriptions.md](archive/nebula-query-subscriptions.md)) must track a client-side **high-water mark of every observed `validFrom`** (NOT the max of its current set — removed members aren't in it). Server global monotonicity + that client HWM together enable **temporal-diff-since-`validFrom`** membership deltas with **no change-feed** (the snapshot history is the substrate). **Trigger:** whichever comes first — the per-DO rate ceiling rises materially, or we build the deferred query-sub delta optimization (this is its prerequisite). Surfaced 2026-06-30 (Larry).

- [ ] **Soft-delete (tombstone) + grace-period reaper + undelete — NOT a hard `deleteAll()`.** De-risks scope deletion and is the **ADR-004 model one level up** (non-destructive/temporal is already how Resources work). - [ ] **Self-service support sessions via user-consented delegation (distinct from admin god-mode reach).** Any user can start a support session with a support agent (likely an AI agent). Out of scope for pre-alpha. **Related but different:** the narrower-token consent UX sketched in [nebula-pre-alpha.md](nebula-pre-alpha.md) (UX-exploratory) and [nebula-request-access.md](on-hold/nebula-request-access.md) — the latter *requests a new grant* by climbing the org tree, vs. this *borrowing the user's existing access*.
- [ ] **Audit log of denied authorization attempts (request-access fishing detection).** [ADR-008](../docs/adr/008-full-org-tree-visibility.md) makes the full org tree — including **admin identity** — universally visible within a Star, and names this audit log as the load-bearing surface for detecting fishing-style probing of that visibility. - [ ] **Current-state aggregations have no design, and the R2 history plan does not cover them.** Historical aggregations over temporal data are answered by the R2 route ([resource-history-r2](on-hold/nebula-resource-history-r2.md)): once snapshots land in R2 Iceberg, "open issues per project over the last 90 days" is an R2 SQL query. **Live counts are a different problem** — "how many open items in this project right now" should not scan history.
