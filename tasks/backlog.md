## Lumenize Mesh

- [ ] **A Client resends a call its socket lost: a receipt for every call, and every mutating call safe to repeat (decided by Larry 2026-10-07; build after the package merge).** A Client never resends a call it already sent: `#sendOrQueue` in `packages/mesh/src/lumenize-client.ts` queues only while the socket is closed or its token is due, and its comment says a message already sent is never replayed. In the 2026-10-07 deployed sweep, `studio-guidance-loop`'s driver posted at about 08:41:27 on a socket that had come in through LHR. The route then moved to FRA, the next packet on the old connection was reset, and the Client reconnected through FRA at 08:41:29.8 and resubscribed. The post never reached the Galaxy, and `callAsync` rejected 30 s later; a one-way `call` would never have heard. The packet that discovers a broken connection is the one that dies, so the first send after any network change (a colo reroute, Wi-Fi to cellular, a VPN toggle) is the likeliest loss. Nobody decided against resending. ADR-005 commits to the opposite: client loops lean on replay idempotency because one-way messaging cannot deliver exactly once. The other direction is built: a host node keeps every call it sends a Client and resends each unanswered one down the new socket (`ClientGateway`'s `#resendPendingCalls`), and the Client resends its unanswered subscribes. Only the Client's own calls were never covered.
  - **A receipt for every call.** The host sends the call's `callId` back as soon as it accepts the frame. It is the early ack every node-to-node call already gets (ADR-003), on the one leg that has none. An error cannot stand in for it: a frame lost in transit reaches nobody, so nothing comes back, and the Client sees the same silence as for a call that arrived and is still running.
  - **The Client keeps each call's frame until it is done with it:** until its answer for a `callAsync` or a call with a handler, and until its receipt for an `onErrorOnly` call, which never hears success.
  - **On reconnect, the Client resends every call with no receipt, in its original order,** before the queue flushes. A receipted call waits: the host already sends its answer to whatever socket the Client is on.
  - **Every mutating call a Client can make is made safe to repeat,** because a call that arrived and whose receipt died with the socket runs twice. Measured 2026-10-07 against `NebulaClient`'s calls:
    - *Safe already:* reads, subscribes, `resources.transaction` and `postUserMessage` (the `newETag` replay check), the org tree's `addEdge`, `deleteNode` and `revokePermission` (each a no-op on repeat, per its code), and membership creation (find-or-create).
    - *Done right but answered wrong on repeat:* `orgTree.createNode` throws "Slug … already exists" though the first call succeeded; creating and deleting a scope probably answer the same way, unverified. Make the repeat recognize itself, which ADR-010 already promises for a create keyed by a client-minted id.
    - *Done twice:* `invite` (a second email; it can recognize a pending invite to the same address), `impersonate` (a second token, harmless) and `resetDevData` (a second reset). Decide each.
  - **After the package merge** (`tasks/mesh-is-built-on-the-scope-tree.md`), because it changes `LumenizeClient` and `ClientGateway`, which the merge moves. The receipt is a change to the socket protocol, which mesh owns (`mesh.md` § *Package dependency direction*).

- [ ] Add retry + skip logic for alarm handler failures
  - **Problem**: Currently, handler errors are caught and the alarm is deleted (one-time) or rescheduled (cron) — silent fire-and-forget with no retry
  - **Design**:
    1. Add `retryCount INTEGER DEFAULT 0` and `status TEXT DEFAULT 'pending' CHECK(status IN ('pending', 'skipped'))` columns to `__lmz_alarms` (migration needed)
    2. On handler failure, increment `retryCount` and set `time` to `now + 2^retryCount` seconds (exponential backoff)

- [ ] Audit tests for unawaited expected-rejection cases and remove `dangerouslyIgnoreUnhandledErrors` flag
  - **Why**: During the vitest 3→4 migration we added `dangerouslyIgnoreUnhandledErrors: true` to every `vitest.config.*` because vitest 4 now fails the run (exit 1) on unhandled rejections that vitest 3 silently swallowed. The flag restores vitest 3's behavior but masks real issues (see follow-up notes in that task).
  - **Pattern to find**: Tests that fire-and-forget a promise which is expected to reject. Example:
    ```ts
    someOp();  // kicks off an op that will reject
    expect(somethingElse).toBe(x);  // test completes
    // someOp's rejection arrives AFTER the test → unhandled
    ```
  - **Fix pattern**: Either `await` the promise and use `rejects.toThrow()`, OR attach `.catch()` to silence the expected rejection:
    ```ts
    someOp().catch(() => {});  // expected to reject
    ```
  - **Also common**: teardown code that disconnects a client (e.g., `client[Symbol.dispose]()`) which rejects pending in-flight promises. These need `.catch` on the in-flight promises, or the disconnect should settle them gracefully.
  - **Success criteria**: Remove `dangerouslyIgnoreUnhandledErrors: true` from every vitest config, full suite runs green with exit 0.
  - **Overlap**: Very related to the RPC-await audit above — both surface through "Unhandled Errors" counts. Probably worth doing together.

- [ ] Audit RPC call sites for proper `await`
  - **Why**: Cloudflare DO best practice says always `await` Workers RPC calls — unawaited calls become fire-and-forget, which (a) may rejection-leak (surfaces as vitest 4 "Unhandled Errors"), and (b) can end the request context before the RPC completes. Inside a try/catch, keep the `await` in `return await rpc()`: `return await foo()` catches errors *locally* in the current try/catch; `return foo()` passes them to the caller. ESLint/typescript-eslint retracted their `no-return-await` rule in 2023–2024 for this exact reason, so a linter suggesting the removal is wrong here.
  - **Audit approach**:
    1. Grep for RPC call patterns: `grep -rn '^\s*\(env\|this\.\w\+\|stub\)\.\w\+(' src/ packages/*/src/`
    2. For each hit, classify: awaited / returned / fire-and-forget
    3. Fire-and-forget cases must be intentional (`ctx.waitUntil` / `lmz.call` with explicit callback per the fire-and-forget-error-delivery pattern in CLAUDE.md) — anything else gets an `await` or `return`
    4. Inside try/catch that wants local error handling, prefer `return await` over `return`

- [ ] **One verified-claims HEADER on the edge→DO hop, replacing the body injections (surfaced 2026-07-29, Larry).** Two conventions exist today for "the edge verified a JWT, downstream needs the claims", and they disagree.   - **Abuse.** No mesh call is rate limited today (`archive/nebula-scope-moves-to-subdomain.md` § *Decisions*), on the premise that every caller holds a token naming them. An anonymous caller breaks that premise.
  - **Where they would connect (2026-10-06, `nebula-clients-connect-to-their-scope`):** such a visitor's socket would sit on the Star its page's host names, beside every member's, and so adds to that Star's load.
  - Related: the Registry-as-mesh-node row below, whose trigger this design is.

- [ ] **A periodic sweep removes scope Durable Objects that no `Scopes` row names (Larry, 2026-10-02).** A creation tears down only the scopes it writes, so every other scope under a re-created name, a deleted account's other apps and their tenant Stars included, can keep what a teammate's live token wrote after the deletion, or what a failed teardown left, and whoever re-claims the name reaches them by dominion ([nebula-scope-moves-to-subdomain.md](archive/nebula-scope-moves-to-subdomain.md) § *Which host answers what*). The sweep:
  - **Lists each scope namespace's objects** (`UNIVERSE`, `GALAXY`, `STAR`) through Cloudflare's API, which returns each one's `id` and `hasStoredData` but no name, with a Workers Scripts Read token.
  - **Computes the id of every `Scopes` row** with `idFromName`, in one Registry read per sweep, which is periodic and bounded (ADR-018).
  - **Re-reads each candidate's row just before wiping it**, since a slug re-claimed during a run would otherwise be wiped from a list read minutes earlier. The window left is the gap between that re-read and the wipe landing, and it loses data only when a creation of that exact name commits inside it and its creator writes before the wipe lands; a wipe landing before the creator's first write repeats the creation's own teardown.
  - **Wipes each orphan through a second `@rawRpc` entry reached by id**, which stamps no identity, makes no pair check and accepts only `teardown`. The first entry cannot serve: it is reached by name, the identity stamp refuses an id, a leftover already stamped would throw a name mismatch, and the sweep knows only the id.
  - **Records each wipe** through ADR-016's one projection, with the server-composed actor `agent:nebula` that the convergence record uses, naming the namespace and id. The sweep destroys state a live path could still read, so ADR-016's exclusion for a sweep does not cover it.
  - **Doubles as the production check that `deleteAll()` took**, which is why the deletion itself does not confirm: any confirming call would stamp the node's identity and write storage again.
  - **Trigger:** public signup, when strangers can re-claim a slug at scale, alongside the Turnstile row above.

  - **Two shapes of the same residual this sweep would not see** ([archive/nebula-scope-moves-to-subdomain.md](archive/nebula-scope-moves-to-subdomain.md) § *Which host answers what*): a creation whose own teardown fails is logged and goes ahead, and its scope's row exists; and the acceptance teardown's guarantee is per request, so a double submit or the link page and Home in two tabs can answer "already accepted" while the first is still tearing down.

## `@lumenize/ts-runtime-parser-validator`

- [ ] **The tool-args facet needs a mode that REFUSES excess keys (package feedback from the guidance file tree, 2026-09-05).** The facet is typia's `createValidate`, which ignores keys the type does not declare — so when `BuildArgs.publish` was renamed `preview`, a stale `{ "publish": true }` from the model would have validated clean and run a build WITHOUT the override it asked for, silently. `apps/nebula`'s `Galaxy.#validateToolArgs` now refuses unknown keys by name against the tool's declared `parameters.properties` (`unknownToolArgKeys`, `codegen-loop.ts`) — a second copy of the key list the type already holds. typia has the machinery (`validateEquals`); expose it as a per-type or per-parse option so a caller can ask for the strict shape and the app-side list can go. Related: the plane-wide excess-key row under § *Nebula* (stored Resources), which is the same gap at the other boundary.

- [ ] **`@default` input/output type asymmetry — dual-type exposure.** Promoted from [`tasks/archive/nebula-5.2.4.1-validator-engine-upgrade.md`](archive/nebula-5.2.4.1-validator-engine-upgrade.md) Phase -1 (closed 2026-04-24). `@default` on a field creates an input/output type mismatch: input-side the field is absent-allowed, output-side it's always present.
