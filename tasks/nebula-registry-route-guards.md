**Objective — every Registry HTTP route states what it requires, completely, in a list you can read without opening a handler; and `/mint-narrower-token` asks one question.** Today the requirement for the two authenticated routes is a conjunction split across a **file boundary**, `/mint-narrower-token` assembles four invariants inline, and **four separate enumerations** decide which checks a route gets.

## Context and current state

### There is no authorization hole here

⚠️ **The Registry gate is not a hole.** `verifyInstanceJwt` ([router.ts](../packages/nebula-auth/src/router.ts)) proves containment only — `isAtOrAbove(payload.access.authScope, instanceName)` — and fronts exactly two routes, and **both handlers re-read `scopeAdmin` themselves**. `handleInvite`'s own comment states the invariant outright: the router proves containment, *so the bare bit legitimately completes the conjunction, and this line must never be copied to a site that lacks the router's check.* ⚠️ A conjunction split across a file boundary is invisible to anyone reading only the enclosing function — **read the consumers**, or you will file this as a hole again.

🚨 **Therefore `hasPassageInto` at that gate would be an ESCALATION**, and it was the original shape of this work. `passage` admits upward for free; the handler's bare bit then completes the conjunction, so a Star `scopeAdmin` could POST `/auth/{u}/invite` and mint identities at the Universe. The containment check refuses exactly that today. It would violate ADR-015 *"upward is nil"* and falsify an `accepted` [`docs/vision/auth.md`](../docs/vision/auth.md) table row.

### What is actually defective

**The guard asks HALF a question, and its correctness is borrowed from every consumer re-checking the bit.** That is falsified the day someone adds a third entry to `AUTHENTICATED_SUFFIXES` — a one-line addition to a `Set` that reads like ordinary route registration, with no test and no grep that would catch it. 🚨 **And today's dispatch does not fail closed on that**: it ends in a catch-all (`if (suffix === 'invite') return handleInvite(...); return mintNarrowerToken(...)`), so a third entry reaches **`/mint-narrower-token`**.

⚠️ **The location of the Worker-side half is NOT drift — the rules require it.** `raw-comm.md`: an RPC-called DO method must not throw a status-carrying error the caller inspects, because Workers RPC drops custom Error props, so expected client errors are gated *before* the RPC. `handleInvite`'s comment says exactly that. **Fix the completeness, not the location.**

⚠️ **The reason to convert is inspectability, not a stack of latent CVEs.** The narrower-token mint's caller bound and `router.ts`'s `verifyInstanceJwt` are textually identical bare containment checks; one is completed by `hasDominionOver` a few lines below, the other by `handleInvite` across a file boundary — so telling them apart costs a full function read per site. ✅ **Half of this already landed**: `parse-id.ts`'s module header carries the **containment allow-list**, so a bare containment check absent from it is non-conformant **by definition** and the next one surfaces in a grep. **Do not let a phase justify itself on urgency the audit did not find.**

### `verifyInstanceJwt` does four things, and only one of them is ever discussed

Token extraction, signature verify, the containment gate, **and `checkRateLimit(env, payload.sub)`**. ⚠️ A decomposition that names one of the four is how the other three go missing — and `checkRateLimit`'s own signature (it takes a verified `sub`) is what makes it the only abuse bound that reaches these two routes at all.

🔒 **`verifyJwtGuard` reads the `Authorization: Bearer` header ONLY — `verifyInstanceJwt`'s WebSocket limb is DROPPED, and that is a deliberate, declared narrowing.** Today the carrier is chosen by header, either/or rather than as a fallback: `Upgrade: websocket` present means `extractWebSocketToken(request)` and **`Authorization` is ignored entirely**. ⚠️ **That limb serves no WebSocket here.** Its function has one caller, gated on `AUTHENTICATED_SUFFIXES … && method === 'POST'`, and neither `handleInvite` nor `mintNarrowerToken` ever constructs a `WebSocketPair`; the Gateway does not pass through it at all — `apps/nebula/src/entrypoint.ts` calls `extractWebSocketToken` directly on `/gateway`, and **that path is untouched by any of this**. So the limb's only reachable form is a POST to these two routes carrying `Upgrade` with its token in `Sec-WebSocket-Protocol`.

⚠️ **It is not a hole — it is a silent WIDENING, which is why it is decided here rather than transcribed.** The token still verifies, containment still runs, the limiter still applies, and `Upgrade` is a forbidden header name in the Fetch spec so browser JS cannot set it. But `checkJwtForRegistry` is **Bearer-only**, so one shared `verifyJwtGuard` that kept the limb would hand `my-scopes`, `create-galaxy`, `create-star` and `delete-scope(-plan)` a credential carrier all four refuse today — four routes newly *accepting* something, inside a claim that no route changes what it refuses. ⚠️ **Dropping it NARROWS two routes**, so it is stated rather than slipped in: a non-browser client using that carrier gets 401 afterwards. Nothing in the repo does, but *no caller in the repo* is not *no caller*. ⚠️ **`extractWebSocketToken`'s import leaves `router.ts` with it** — a dangling import is how the branch gets rebuilt later.

## Design intent, constraints, and future state

### The shape — a linear step pipeline

**The runner and the step contract are ✅ BUILT** — [nebula-route-pipeline.md](archive/nebula-route-pipeline.md), archived 2026-08-13; the code is `packages/nebula-auth/src/route-pipeline.ts` and is the authority now. This file supplies the table it runs: which routes exist, which steps each carries, and in what order. The contract in one line — a step returns a `Response` to terminate, a `Request` to replace the one it received, or `undefined`/`void` to pass through — is stated there, not restated here; that convention mirrors `routeDORequest`'s `onBeforeRequest` / `onBeforeConnect` (`routeDORequest`'s `onBeforeRequest` / `onBeforeConnect`).

⚠️ **An entry is `{ path, method, steps }`.** The tables below give path and steps and **elide `method`, which is uniform**: `POST` everywhere except `magic-link` and `accept-invite`, which are `GET`. 🔒 **Every Registry entry states its method** — the runner treats an absent one as *any verb*, which is right for a consumer indifferent to verbs and wrong for all of these.

⚠️ **`onBeforeCall` is NOT that convention, and citing it teaches the opposite.** It is a **mesh** hook (`lmz-api.ts`), it returns `void`, and its JSDoc says *"reject by throwing"*. A builder who resolves the citation there writes throwing guards, which land in `routeNebulaAuthRequest`'s catch and return **500 `internal_error`** instead of a 403 — defeating the refusals rule below, and caught by no criterion, since they only require the request be *refused*. `nebula-auth`'s router imports only CORS helpers from `routing` and never calls `routeDORequest`, so this pipeline **mirrors** that hook shape rather than reusing it.

🔒 **The `*Guard` suffix is a CONTRACT, and its home is `.claude/rules/coding-style.md` § *Guard naming*** (moved there 2026-08-11 so it outlives these task files). In one line: **`require*` throws** (mesh — `requireDominionHere`, `requirePassage`, `requirePermission`); **`*Guard` returns a `Response`** (these route steps). ⚠️ **A route step named `require…` would be a 500-shaped bug, not a style preference** — `router.ts`'s blanket catch has no typed-error branch, so a step written by analogy with its throwing neighbour returns `500 internal_error` where a 403 belongs. The first draft of this file had exactly that, naming these steps one letter from `requireDominion`. ⚠️ **Do not "unify" the mesh `requirePassage` with this pipeline's `passageGuard`** — same verdict, two boundaries, two error contracts.

🔒 **THE TABLE — all fifteen routes, and it is the deliverable.** The sections below carry the *reasoning* for the contested rows and MUST NOT restate the rows themselves; this block is the single home. Order within a family does not matter (`createRouter` matches on path + method, not position); order **within a row** is the audit.

**Scope-less registry paths** — `/auth/{suffix}`

```
'discover':           POST  [connectionRateLimitGuard, turnstileGuard, forwardRaw]   // 🔓 TERMINAL — retired by the sibling
'claim-universe':     POST  [connectionRateLimitGuard, turnstileGuard, forwardRaw]
'claim-star':         POST  [connectionRateLimitGuard, turnstileGuard, forwardRaw]
'my-scopes':          POST  [verifyJwtGuard, subRateLimitGuard, forwardWithAccess]
'create-galaxy':      POST  [verifyJwtGuard, subRateLimitGuard, forwardWithAccess]    // dominion stays in the DO — see § Non-goals
'create-star':        POST  [verifyJwtGuard, subRateLimitGuard, forwardWithAccess]    //   ″
'delete-scope':       POST  [verifyJwtGuard, subRateLimitGuard, forwardWithClaims]    //   ″
'delete-scope-plan':  POST  [verifyJwtGuard, subRateLimitGuard, forwardWithClaims]    //   ″
```

**Instance paths** — `/auth/:scope/{suffix}`

```
'magic-link':          GET  [parseScopeGuard, connectionRateLimitGuard, handleMagicLinkClick]
'accept-invite':       GET  [parseScopeGuard, connectionRateLimitGuard, handleAcceptInvite]
'email-magic-link':   POST  [parseScopeGuard, connectionRateLimitGuard, turnstileGuard, handleEmailMagicLink]
'refresh-token':      POST  [parseScopeGuard, connectionRateLimitGuard, handleRefreshToken]
'logout':             POST  [parseScopeGuard, connectionRateLimitGuard, handleLogout]
'invite':             POST  [parseScopeGuard, verifyJwtGuard, subRateLimitGuard, passageGuard, dominionOverScopeGuard, handleInvite]
'mint-narrower-token':POST  [parseScopeGuard, verifyJwtGuard, subRateLimitGuard, passageGuard, dominionOverScopeGuard, mintNarrowerToken]   // 🔓 goes SCOPE-LESS in Phase 3
```

**The shape is DERIVED, not per-route** — *parse the segment → one limiter → prove identity → prove passage → ask the endpoint's own question → handle* — so a new route inherits its list rather than negotiating one.

🔒 **The three forward terminals are NOT one symbol, and which one a row takes is decided by `raw-comm.md`, not by preference.** *"The ORIGINAL request MUST be forwarded — `stub.fetch(request)` — whenever the edge has nothing to add. It MAY be rebuilt only to inject trusted claims the DO cannot derive."* ⇒ the taxonomy is **what the edge injects**: `forwardRaw` where it injects **nothing** (`stub.fetch(request)` — the shape already in source); `forwardWithAccess` where it adds `verifiedAccess`; `forwardWithClaims` where it adds `verifiedAccess` + `callerSub` + `callerClaims` ([ADR-016](../docs/adr/016-record-the-acting-principal.md)'s fail-closed input, under `router.ts`'s ⚠️ *ASSIGN, never merge*). They also declare different `Needs`, which one shared name could not.

🚨 **Naming them alike is not cosmetic — it prescribes a MUST violation on the three open rows.** `forwardToRegistry` **rebuilds**: it re-serializes the body and sets `headers: { 'Content-Type': 'application/json' }`, dropping every other header. The open routes are forwarded raw today *because that rebuild was already found harmful and removed*, with the reason recorded at the site — *"Rebuilding also silently dropped every header but Content-Type, and made a malformed body indistinguishable from an empty one — the registry's own JSON guard now owns that, returning 400 `invalid_request` instead of a 500."* A single name puts that defect back on three routes inside a phase claiming no verdict changes. ⚠️ **The helper's own "avoids stream races" comment is NOT the reason it rebuilds** and MUST NOT be repeated here: both of its call sites rebuild because they **inject**, and `routeDORequest` forwards with `new Request(request, { headers })` — new Request, body untouched — in production, with no race. Whether the claims should ride in a **header** instead of the body is an open question owned by [nebula-registry-scope-in-url.md](nebula-registry-scope-in-url.md).

🔒 **`parseScopeGuard` is first on every instance path, and it is a STEP rather than something the table does implicitly.** Accepted `auth.md` states it that way — *"It is itself a step — `parseScopeGuard`, first in the list — not something the table does, so a route carrying no scope simply omits it"* — and today the parse lives above the suffix dispatch in `handleInstancePath`, covering all seven instance routes at once, which is exactly the code the table dissolves. 🚨 **Omitting it regresses two things no other criterion catches**: `POST /auth/bad..name/email-magic-link` stops answering 400 and reaches the singleton, and the newly-URL'd creates accept `/auth/{u}.{g}.{s}.{x}/invite` — a scope no grammar can produce — because `isAtOrAbove` is string math and will happily accept it. It sits ahead of the limiter because parsing is local and a `limit()` is not, which is also `auth.md`'s R2-before-R3 order.

⚠️ **`magic-link` and `accept-invite` take the limiter too.** They are GET navigations carrying a token, and consuming one is a singleton lookup — so a garbage token in a URL is the same faucet as a forged cookie. Brute-forcing the token is not the threat (they are hashed random values); the unbounded singleton reach is.

⚠️ **`claim-universe` and `claim-star` keep their scope in the BODY — deliberately, and this is not an oversight to tidy.** [nebula-registry-scope-in-url.md](nebula-registry-scope-in-url.md) moves a scope onto the URL so a guard can read it; these are open routes where no guard reads one, so a segment would be decoration bought with a change to a published flow. ⚠️ **`my-scopes` stays `POST` with no body** — semantically a GET, but changing the verb buys nothing and costs a caller.

⚠️ **`my-scopes` carries no scope guard because it has no TARGET, not because it is unauthenticated.** `myScopeTree(callerAccess)` takes no target — it *enumerates* what the caller can reach, so the answer is the set itself and there is nothing for `passageGuard` to compare against; inventing a segment would mean a scope meaning "the caller's own", which the JWT already says. ⚠️ **It IS authenticated today**, via `checkJwtForRegistry` — a **fourth** auth path distinct from `AUTHENTICATED_SUFFIXES`/`verifyInstanceJwt`, reached from the `handleRegistryPath` branch that also covers `create-galaxy`/`create-star`. 🔓 **The unauthenticated route in this neighbourhood is `discover`, not `my-scopes`.**

🔒 **ONE limiter per route, keyed by whatever identity exists at that point, placed immediately before the first EXPENSIVE thing.** Derived from cost, and what the derivation needs is the **ORDERING**, not the magnitudes: **local CPU ≪ colo-local counter ≪ DO round trip ≪ outbound `siteverify` ≪ email send.** ⚠️ **Only the last is measured here** (~1.4 s — `tasks/archive/decision-email-latency-cf-vs-resend.md`); a JWT verify is order-of-magnitude *sub-millisecond* local CPU (`verify.ts` imports BLUE and GREEN on every call with no cache, then up to two Ed25519 verifies) and a DO round trip order-of-magnitude *milliseconds* — **neither has an artifact in this repo, and neither is load-bearing**: the argument turns on the ordering, which no plausible measurement inverts. ⇒ **A limiter earns its place ahead of a DO hop, a siteverify or a send — never ahead of a signature check**, where it would pay roughly what it saves. What falls out, per family:

- **A JWT route** (every row carrying `verifyJwtGuard`) takes ONE **`sub`-keyed** limiter **after** `verifyJwtGuard`. Everything costly sits after the verify — a registry read for the narrower-token mint, a DO write plus an email for `/invite` — and `sub` is the identity the verify establishes. `checkRateLimit(env, payload.sub)` already is this. ⚠️ **Do not add a pre-verify limiter here.**
- **A cookie route** (`refresh-token`, `logout`) takes ONE **connection-keyed** limiter **before** the cookie is resolved, and there is no `sub` yet to key on. 🚨 **This is the live gap.** A forged cookie was never written to KV, so it always misses and always falls through to `getRefreshRecord` on the **singleton** — one DO round trip and storage read per request, anonymous and unbounded. The comment at that site reads *"in practice … this rarely fires"*, which is true of legitimate traffic and false of precisely the traffic that matters. [ADR-018](../docs/adr/018-singleton-is-the-scarce-resource.md) is why this is 🚨 rather than a nicety: the ceiling arrives as an outage.
- **An open route** (`claim-universe`, `claim-star`, `email-magic-link`, `discover`) takes ONE **connection-keyed** limiter **before** `turnstileGuard`, which `auth.md` already orders this way *"because it costs a `siteverify` round trip"*. `discover` has a second reason — it is keyed on the email address and is filed as an enumeration oracle, so the limiter bounds **enumeration**, not only spend.

⚠️ **No route takes two**, and a signature-forgery threat model MUST NOT be offered as a reason for one: forging Ed25519 is ~2^128 work, so the key length is that control and a limiter is irrelevant to it. 🔒 **`connectionRateLimitGuard` needs a BINDING and a KEY, and without both it ships inert.** Cloudflare's rate limiter is per-binding, so a connection-keyed limit is a **second** declaration — `NEBULA_AUTH_CONNECTION_RATE_LIMITER` — in `apps/nebula/wrangler.jsonc` **and** `packages/nebula-auth/test/wrangler.jsonc`; `NEBULA_AUTH_RATE_LIMITER` is the only limiter name in the repo today and `apps/nebula/wrangler.jsonc` declares no `ratelimits` block at all. The key is **`CF-Connecting-IP`**, and its absent-header fallback is **allow**, matching `checkRateLimit`'s existing no-op-when-unbound contract — miniflare supplies no such header, so a test lane would otherwise collapse every caller onto one key and 429 the suite into what look like auth failures. ⚠️ **Both are needed or the 🚨 below is not closed**: with allow-on-absent, a guard with no binding is a no-op, so the forged-cookie faucet stays exactly as open as today while every in-lane criterion greens — `calibration.md` §9, inside the phase written to close it. **Phase 1 declares both bindings; Phase 2 lands the guard on the routes.** ⚠️ Whether the two spellings are one factory or two symbols is a build detail; the tables name them `subRateLimitGuard` and `connectionRateLimitGuard` so the **key** is always visible in the row. Only the terminal steps carry no `Guard` suffix — the Worker-handled handlers and the three forward terminals; every step that can refuse does.

🔓 **This AMENDS `accepted` `auth.md` § *The layers a call passes*, and the amendment is a Phase-1 deliverable — see that phase's done-checks.** ⚠️ **The change is larger than "the rationale only", and saying otherwise was wrong:** `auth.md` specifies R3 as **connection-keyed** and running **before** R4, with a `sub`-keyed **second** limiter as optional — while the table above gives a JWT route ONE `sub`-keyed limiter **after** `verifyJwtGuard` and § *Decisions* pins that no route takes two. **Key, position and count all change.** ⇒ Restate R3 as a derivation rather than a fixed position: **the limiter's key and place follow from whether verified identity exists at that point** — connection-keyed ahead of the work on the families that have no `sub`, `sub`-keyed after the verify on token-bearing ones, never both. The measured cost tiers above are the argument and stand; only the claim about *what* changes was wrong (`calibration.md` §7 — a supporting clause written for a conclusion already agreed). ⚠️ **Two neighbouring statements are falsified and must move with it**: the elision note (*"`rateLimitGuard` sits where R3 does"* — wrong symbol **and** wrong position), and the `claim-universe` worked example's own `rateLimitGuard` token, which splits into two names.

⚠️ **The two lists being IDENTICAL is the honest state of today's code, not a smell.** Both routes genuinely require dominion over the route's instance right now — the difference is only that each says so across a file boundary. 🔓 **[nebula-invite.md](nebula-invite.md) is what makes them diverge**, by opening `/invite` to a member at their own scope; that file owns the openness question entirely — see § *Non-goals*.

- **`passageGuard` replaces the router's containment check**, and is the same verdict the mesh boundary computes — which is what makes `docs/vision/auth.md` § *The Registry* true rather than aspirational; it currently claims the scoped routes are gated by the same two rules, and they are not.
  - ⚠️ **It is strictly SUBSUMED on both of today's routes, and must SAY so at the site.** `dominionOverScopeGuard` implies dominion, and dominion implies passage, so every refusal the criteria assert is produced identically with `passageGuard` removed — it can never *decide* a verdict here, so **no behavioural limb can cover it and the shape limb is what does.** It is a **uniform boundary step**, present so a route whose endpoint guard is weaker inherits the boundary rule (which is what `/invite` becomes next file), and because accepted `auth.md` § *The Registry* requires it. Left unstated at the site it is § *Decisions*' dead-operand defect rebuilt one level up; `mintNarrowerToken`'s *"eligibility strictly subsumes this gate's verdict"* comment is the in-repo model for saying it.
- **Each handler's bare `scopeAdmin` read becomes a named guard** asking one complete question. Both take `dominionOverScopeGuard`, which is exactly today's verdict for both.
  - ⚠️ **`dominionOverScopeGuard`, never `…OverTarget`.** "Target" is the one word that reads as *either* operand: it is the containment predicates' second argument (`targetScope`), and in archived vocabulary it was the impersonation **subject**. This guard takes the **URL's instance**, and it sits one file from the call `canMintFor` exists to foreclose — `hasDominionOver(access, instanceName)` versus `hasDominionOver(access, subject.authScope)`, *"the same call, the wrong second argument"* — so a guard named for the ambiguous operand is the confusion pre-built. A Stage-2 reviewer did read `…OverTarget` as the subject and filed a blocker on that reading.
- **Claims travel by COMPOSITION, never in a merged state type.** 🔒 **`RouteState` stays `{ params }` — the built contract, unmodified**: `verifyJwtGuard` declares `Adds: { claims: NebulaJwtPayload }`, and every guard and handler that reads claims declares `Needs: { claims }`, so a claims-less state is not constructible for a step that needs one. ⚠️ **Editing `route-pipeline.ts` to put `claims` on `RouteState` is the wrong move and it is SILENT** — the runner's JSDoc says it deliberately knows nothing about Nebula, the archived sibling's Decisions table rejects one shared state type by name (the open routes never carry claims), and doing it hands every open route an optional `claims`, destroying the non-optionality below. No grep or type criterion here would red it. See § *Non-goals*. 🔒 **The addressed scope is read by ROLE, per the frozen runner's contract: `parseScopeGuard` reads `params` because it IS the parser and declares `Adds: { scope }`; every guard comparing against a scope declares `Needs: { scope }` and reads THAT, never the raw capture; a scope-less route carries neither.** [nebula-route-pipeline.md](archive/nebula-route-pipeline.md) § *Design intent* states it in those terms, and reading `params` in a consumer is the alternative it names and rejects. ⚠️ **The reason is fail-LOUD, not prevention — do not overstate it.** That frozen file measured the limit: *"a plain array literal does not catch order: each element is checked against a common step type, never the sequence"*, so **neither form makes a mis-ordered guard impossible.** What differs is the failure: a guard needing `scope` before the parse ran reads `undefined` and the route 500s or refuses on every call, which the first test catches; a guard reading `params.scope` gets a **present but unvalidated** capture and compares against it happily — running the whole refusal to completion on a scope no grammar can produce. That second mode is exactly what 🚨 *A malformed scope segment is refused at the edge* exists to catch, so the two must not fight each other. ⚠️ **`env` is NOT in it** — it is ambient rather than per-request; [nebula-route-pipeline.md](archive/nebula-route-pipeline.md) carries that decision and the two things to verify before relying on the `cloudflare:workers` import. ⚠️ **`routeState`, never `ctx` or `context`** — both are already taken in this repo; [nebula-route-pipeline.md](archive/nebula-route-pipeline.md) § *Decisions* carries the reasoning and the rejected alternatives.
  - 🚨 **`access` alone is NOT enough — narrowing to it makes the ADR-016 record unbuildable.** `handleInvite`'s JSDoc says so outright: it takes the whole payload because issuing an invite mints a membership, so *"narrowing to `access` here would make that record unbuildable downstream without re-verifying, and a `sub`-only record names the person acted upon as the person who acted."* `issueInvites` calls `projectActingToken(callerClaims)` — the ONE shared projection ADR-016 mandates. `mintNarrowerToken` needs `act` (root-identity gate), `sub` (self-narrow refusal, actor pair) and `profileId`. **Guards read `routeState.claims.access`; handlers take `routeState.claims` whole.** ⚠️ The crude narrowing fails type-check; the **quiet** failure is a *reconstructed partial* claims object, which `ActingTokenRecord`'s optional `act`/`profileId` project as a wrong-but-believed record — unrecoverable, since a record not captured at write time is gone.
  - **`claims` is non-optional on the steps that need it**, declared per-step, so a guard cannot be *written* to accept a claims-less state. ⚠️ **Order is not enforced by types, and is not meant to be** — the array is read left to right, and [nebula-route-pipeline.md](archive/nebula-route-pipeline.md) § *Decisions* carries the type-level alternative and why it is declined. Mis-ordering fails loudly anyway (a 500 on every call to that route). ⚠️ An optional `access?` makes it a runtime concern instead, and the runtime behaviour is worse than it looks: `isAtOrBelow(access.authScope, node)` on an absent `access` would throw on a property read — which is why both verdicts carry an explicit fail-closed guard, and why `hasPassageInto`'s is documented at the site as *not* inheritable from `hasDominionOver`'s (the upward arm has no `scopeAdmin` operand to be accidentally protected by).
- ⚠️ **Not on `this` — and the reason is the WORKER isolate, not the DO rule.** `router.ts` defines no class at all (the DOs are in `nebula-auth-registry.ts` and `profile.ts`), so per `workers-projects.md` this file is Worker code and none of the three DO files apply. The hazard is **module-scope state persisting across requests in a reused isolate**: a `let currentCtx` would be shared by two in-flight requests. ⚠️ `durable-objects.md` § *No mutable instance state* is NOT the authority here — it argues from hibernation/eviction loss, never mentions cross-request reads, and invites the "move the guards into the DO" move `raw-comm.md` forbids.
- **The pipeline table SUBSUMES all FOUR enumerations** — `AUTHENTICATED_SUFFIXES`, `TURNSTILE_ENDPOINTS`, `REGISTRY_ENDPOINTS`, `AUTH_FLOW_SUFFIXES` — so the map's keys **are** the registration and a route cannot exist without a guard list. 🚨 **This is what actually deletes the borrowed-safety failure mode, and deleting only ONE of the four does not.** Leave any of them standing and the same one-line addition still lands on a handler.
  - 🔒 **Deleting `TURNSTILE_ENDPOINTS` requires a SUCCESSOR ORACLE, and the successor is behavioural. Deleting the test-mode short-circuit in `checkTurnstile` is a SEPARATE, smaller decision — do not justify it by the oracle.** ⚠️ **The oracle does not require it:** `checkTurnstile` reads both values off the `env` **parameter**, and `nebula-auth-cors.test.ts` already calls `routeNebulaAuthRequest(request, env)` directly, so a doctored `{ ...env, NEBULA_AUTH_TEST_MODE: undefined, TURNSTILE_SECRET_KEY: '2x…AA' }` reaches the real gated path with **no source change** — which is exactly what the cited precedent does (`packages/auth/test/auth.test.ts` builds a `prodEnv` and calls `createAuthRoutes(prodEnv)`; the dummy key is the precedent, the deletion is not). ⇒ **The deletion stands on BLAST RADIUS instead**: `security.md` § *test-mode flags* turns on `NEBULA_AUTH_TEST_MODE` having no second factor, and one flag that both hands out magic links **and** disables the only bound on the unauthenticated endpoints is a strictly worse thing to leak than one that does the first alone. That function skips on `NEBULA_AUTH_TEST_MODE` **before** consulting the gate, so under the test binding a gated endpoint and an ungated one are byte-identical; the criterion *Every open route still refuses a bad Turnstile token exactly as before* is therefore structurally blind to a route silently losing `turnstileGuard`. ⚠️ **The fix is one deletion, not a new flag.** `checkTurnstile`'s very next branch already skips when `TURNSTILE_SECRET_KEY` is absent, and **neither vitest config sets that key** — so the test-mode line is redundant today and every existing test is unaffected by its removal. What it buys: a test that wants gating just binds Cloudflare's **always-fail** dummy secret `2x0000000000000000000000000000000AA` and the real path runs, making gating **observable** rather than described. ⚠️ **Decouple by DELETION, never by adding a second flag** — `security.md` turns on this binding having no second factor and `scripts/audit-test-mode.sh` holding it out of every deployable config; a sibling flag would double that audit surface to buy the same thing. This also stops `NEBULA_AUTH_TEST_MODE` meaning two unrelated things (return links instead of emailing · skip Turnstile), which is what let every test that wanted the first silently disable the second. ✅ Precedent, already resolved and built: `tasks/archive/auth-bootstrap-and-roles.md` records the dummy-key strategy, `packages/auth/test/auth.test.ts` uses it at five sites, and `apps/nebula/harness/scenarios/turnstile-canary.ts` drives a really-booted worker with Turnstile genuinely on. 🚨 **Bind `TURNSTILE_SECRET_KEY: ''` explicitly in the vitest configs, in the SAME commit as the deletion — otherwise this breaks on developer machines and stays green in CI.** *"Neither vitest config sets that key"* is true of the configs and **false of the resolved env**: `.dev.vars` is a `postinstall` symlink into `packages/nebula-auth/test/` and `apps/nebula/`, pool-workers loads it, and `.dev.vars.example` ships `TURNSTILE_SECRET_KEY=…` **uncommented** with the setup script telling developers to copy it. On such a checkout, deleting the short-circuit sends every `email-magic-link` / `claim-*` / `discover` test at a real `siteverify` with a bogus key. CI writes no Turnstile key, so **CI passes while the developer's machine goes red** — and the likeliest repair for a mass red is to restore the short-circuit, reversing this decision. An explicit `''` binding wins over `.dev.vars` and `checkTurnstile`'s `if (!secretKey) return null` then holds on any checkout. ⚠️ **The verify-before-landing clause is therefore "no lane that binds `NEBULA_AUTH_TEST_MODE` also RESOLVES a `TURNSTILE_SECRET_KEY`"** — resolved, not written in the config, which is the distinction that made this invisible. Comment the key out of `.dev.vars.example`, or note there that it must stay unset for the suite.

🚨 **`TURNSTILE_ENDPOINTS` is the DANGEROUS one, and its own source comment says so** — it is the sole bound on the unauthenticated endpoints (`checkRateLimit` keys on the verified `sub`, so it never runs where there is no JWT), and the comment warns that a method copied from a listed sibling *arrives ungated with nothing red*, which for `claim-star` means an open mutation endpoint that mints `scopeAdmin` identities and sends mail. Converting `AUTHENTICATED_SUFFIXES` while leaving that one migrates the **safer** half of the defect.
- 🚨 **The limiter is UNBOUND in production, and nothing reds.** `NEBULA_AUTH_RATE_LIMITER` is declared only in test wrangler configs (`packages/nebula-auth/test/`, two `apps/nebula` test workers); `apps/nebula/wrangler.jsonc` has no `ratelimits` block, and `checkRateLimit` **returns `null` — allow — when the binding is absent** (`checkRateLimit` returns `null` when the binding is absent). Every criterion below therefore passes in-lane while production carries no bound at all: `calibration.md` §9's shape exactly, green where anyone looks and silent where it matters. ⚠️ **`wrangler types` cannot fix it** — `packages/nebula-auth` has no `wrangler.jsonc` of its own, so the `Env & { NEBULA_AUTH_RATE_LIMITER?: RateLimit }` widening is `packaging.md` § *Use the global `Env` type*'s licensed form. **Resolved three ways in Phase 1** (decided 2026-08-13): the guard stays in every list regardless, it no-ops when unbound, and the Registry DO's constructor logs `debug.error` when the binding is absent. The binding is declared with a deliberately loose limit now; picking real numbers is a backlog row.
- **`checkRateLimit` survives, named.** It matters *more* after this sequence, not less: accepted `auth.md` § *Grants* says the residual risk of the own-scope invite path is precisely mail abuse — *"That is rate-limiting and attribution."*
- Refusals name **which** rule failed. The existing `insufficient_scope` message describes a *satisfied* scope relationship and would be actively misleading on the new path (ADR-008 discloses the denial).

✅ **Every guard here is a pure claim-read — `access` plus the URL's instance, no storage — so this costs the singleton nothing** (auth.md: *"this decision is completely local. No network hop is needed."*). The one Registry read on these routes is the narrower-token mint's subject lookup, keyed on the request body, which therefore belongs inside the handler. **On the two Worker-handled routes (`/invite`, `/mint-narrower-token`), keep the existing RPC to the DO rather than switching to `stub.fetch`** — ⚠️ every other row is a **forward** and MUST stay one, since the DO converts its own typed errors to a `Response` in-process and converting those to RPC would make its 409/400 existence refusals lossy (`raw-comm.md`): one round trip either way, and RPC's real cost — lossy errors, hence pre-gating — is already paid by these very guards.

Its replacement is the intermediate email-proof token plus the `profileId`-keyed union (§ *Non-goals*), and only once that exists can this row go. ⚠️ **Do not read the row as permanent, and do not "tidy" the marker away.** ✅ **Meanwhile this file measurably improves a recorded residual for free**: [backlog.md](backlog.md) § *Nebula Auth* diagnoses the oracle as *"unauthenticated + unthrottled ... the CF rate-limiter keys on JWT `sub` ... so it never covers the pre-auth `discover`"* — which is exactly what `connectionRateLimitGuard` closes. The **volume** is bounded here; the **leak** is the sibling's. ⚠️ That backlog row must be updated when this ships, or it goes on asserting "unthrottled" in a file people triage from.

⚠️ **`logout` is the SECOND site of the unauthenticated-singleton faucet, and it is the reason the connection-keyed limiter is not optional here.** `handleLogout` hashes *any* cookie value and calls `registry(env).revokeRefreshToken(tokenHash)` without validating it first — so, exactly like `refresh-token`, a forged cookie buys one singleton round trip per request.

⚠️ **CSRF on these two routes is already closed by `SameSite=Strict`, so no origin-guard slot is reserved for them above** — the derivation is [nebula-same-origin-guard.md](nebula-same-origin-guard.md) § *`SameSite=Strict` already closes CSRF on the cookie routes*, which also marks it as needing re-derivation rather than settled. ⚠️ What IS this file's: the derived-session rule (`security.md` — a derived session must not revoke on the originator's credential path) **cannot** be enforced at this route, which reads a cookie and cannot tell the two apart, so it stays client-side in `NebulaClient.logout()`'s `#mintedFrom` branch by necessity, not by oversight.

### `/mint-narrower-token` asks one question

`/mint-narrower-token`'s authorization becomes **one predicate call**, behind a thin `canMintFor(callerClaims, subject)` whose job is naming which scope goes in. ⚠️ **This DELETES checks rather than reorganising them.** The old `activeScope` bounds were asserting by hand what two already-pinned decisions guarantee:

- **A derived token carries the SUBJECT's `authScope`**, not something derived from `activeScope`.
- **`verify.ts` already forces `aud` ⊆ `authScope`** on every read — verified: the check is unconditional, runs on every verification, and returns `null` (fails closed).

Chain them and the old invariants fall out as *consequences*: eligibility places the subject's whole scope inside the caller's dominion; the minted `authScope` **is** the subject's scope; `aud` must sit inside it or the token is dead. So `aud ⊆ subject ⊆ caller` is a theorem.

```
authorize:  ¬caller.act  ∧  hasDominionOver(caller.access, subject.authScope)  ∧  caller.sub ≠ subject.sub
mint:       { sub, authScope, scopeAdmin } ← all the SUBJECT's;  aud ← requested;  act ← caller
```

🔒 **Keep a thin named `canMintFor(callerClaims, subject)`, for one reason only: naming which scope goes in.** With a single predicate call the only substitution left is `hasDominionOver(access, instanceName)` where `hasDominionOver(access, subject.authScope)` belongs — and the route's `instanceName` is right there in scope. ⚠️ It takes **no `activeScope` parameter**. It lives in `worker-token.ts` alongside `mintNarrowerToken`, not exported to `apps/nebula`, which has no business minting.

🚨 **The deletion inventory is PER-SITE, and getting it wrong is how this ships a hole.**

| Site | Today | After |
|---|---|---|
| caller bound | `isAtOrAbove(payload.access.authScope, body.activeScope)` — what the caller's own scope covers | **DELETED** — subsumed, since dominion over the subject plus the row below gives `aud ⊆ subject ⊆ caller` |
| subject bound | `isAtOrAbove(subjectIdentity.universeGalaxyStarId, body.activeScope)` — the subject bound | 🔒 **RETAINED**, reworded in place as the **`aud` validation**. Never deleted, not even briefly |
| the bit intersection | `caller.scopeAdmin && subject.scopeAdmin` | **DELETED** — the left operand can never be false once dominion holds (§ *Decisions*) |
| **the standalone bare-bit gate** | `if (!payload.access.scopeAdmin) return 403 'forbidden'` | **DELETED in Phase 1's wake** — see the two rows of reasoning below |
| **`handleInvite`'s bare-bit gate** | `if (verifiedAccess.scopeAdmin !== true) return 403 'forbidden'` | **DELETED**, same reason — this is the *other* half of the conjunction § *There is no authorization hole here* describes, so the guard now asks once for both routes |
| **the root-identity gate** | `if (payload.act) return 403 'forbidden'` | 🔒 **RETAINED** — a licensed mint-side presence gate under `security.md` rule (1), and it is now on the `authorize:` line above, which is the complete predicate. ⚠️ **Its 403 message is load-bearing and MUST NOT be reworded**: `apps/nebula/src/impersonation.ts` classifies terminal failures by matching `/root identity/i` against `error_description`, and no test asserts that string — so a reword greens everywhere and breaks the client's classification |
| the `mintAccessToken` call | `authScopeOverride: body.activeScope` | the **subject's** `authScope`, verbatim |

🚨 **Why the bare-bit gates go, and what has to travel with them.** Their own comment claims three reasons *"none of them subsumable"* — **(a)** ordering, since the gate fires before the registry read so a non-admin cannot probe which `sub`s exist; **(b)** a `denied` log line; **(c)** a distinct `forbidden` code. ⚠️ **(a) is falsified by Phase 1** and this is the whole argument: `hasDominionOver` is `access.scopeAdmin && isAtOrAbove(…)`, so the bare bit **is its left operand** — `dominionOverScopeGuard` refuses every non-admin at the edge, before dispatch and therefore before `getIdentityScope`, and it refuses a strict *superset* (a caller holding the bit but lacking dominion over the URL scope is stopped too). What remains is an operand that can never be false: § *Decisions*' dead-code-inside-a-security-predicate, invisible to mutation testing. **(b) and (c) are observability, not authorization, and MUST travel to the guard:**

- 🔒 **The two-code distinction survives, via a POST-VERDICT branch.** Today `forbidden` means *you lack the authority* and `insufficient_scope` means *you have authority but asked beyond your scope*, and `auth.md` requires a refusal to name which rule failed. So the guard picks its `error` string **inside the already-refused branch** — `const code = access.scopeAdmin ? 'insufficient_scope' : 'forbidden'` — after a single `hasDominionOver` call has made the decision. ⚠️ That bit read cannot change an authorization outcome, so it is **not** the bare-bit pattern this file deletes; the distinction is a message, the verdict is the predicate. Both messages name the caller's own `authScope` and the URL scope — values the caller already holds — so ADR-008 is satisfied. ⚠️ **This licensed message shape belongs to `dominionOverScopeGuard` on `/invite` — the only row with a URL scope after Phase 3 — and MUST NOT be carried into `canMintFor`.** The source is explicit that **NEITHER** mint refusal may name the subject's scope, and the one that structurally can is the **eligibility** refusal, whose second operand *is* `subjectIdentity.universeGalaxyStarId`; the `aud` validation names only the caller-supplied `activeScope`. ⇒ `canMintFor`'s refusal body may name the **caller's own `authScope`** and nothing else.
- ⚠️ **The `denied` log becomes SHARED, so it MUST carry the route.** `debug('nebula-auth.worker.narrower.denied')` is a per-endpoint namespace for a check on one route; the guard serves **every route whose list carries it** — two here, one after Phase 3, and more as siblings add them — so it needs a shared namespace plus the route in the payload, or one line standing for several routes cannot say which denied. This is not tidiness: several criteria assert through the debug sink.

🚨 **The SUBJECT bound is what makes every intermediate ordering safe.** Retained, it bounds `activeScope` inside the subject's scope, so even while the `mintAccessToken` call still takes `body.activeScope` the minted token cannot exceed the subject. ⚠️ **The hazard is a window in which it is ABSENT** — deleted "to be replaced by the validation later" — because the `mintAccessToken` call then takes an unbounded `authScope` from a caller-chosen `activeScope`, and an admin at `{u}` impersonating a `scopeAdmin` subject at `{u}.{g}` receives a token covering **all** of `{u}` carrying the subject's bit. It verifies cleanly, because `aud` sits inside the widened scope. ⇒ **Reword the subject bound in place; never delete-then-reintroduce it.** ⚠️ **Anchor on its MESSAGE — `outside the subject's own scope` — never on a line number.** The sibling phase already deleted lines above it, and the caller bound it must not be confused with is textually near-identical and sits a few lines away.

🚨 **`canMintFor` runs BEFORE the `aud` validation, and the validation's 403 MUST NOT name the subject's scope.** An explicit ADR-008 disclosure decision lives **only** in the ORDER-MATTERS comment above `mintNarrowerToken`'s eligibility check, which this work deletes along with the check it orders, while the validation survives: *"A faithfulness bound can pass while eligibility fails, so running the mirror first would tell a caller who is about to be refused WHERE the subject sits in the tree… Neither 403 body may name the subject's scope."* ⚠️ The *"fail-fast on an unverifiable token"* framing pushes the validation **earlier** — the order that comment forbids. No criterion, ADR or rule restates it, so **carry the rationale into the new comment**.

✅ **The `aud` validation is a FOURTH containment site, and it needs NO special arm.** The reserved platform scope is the **ROOT** of the scope tree, so `isAtOrAbove('nebula-platform', '{u}')` is **true**, and the branch delivering that lives inside `isAtOrAbove` itself. `#bootstrapEmails` being an array is therefore not a problem: a platform caller holding dominion over a second platform subject validates any `aud` under the ordinary rule. ⇒ **Call `isAtOrAbove` and add nothing** — a platform disjunct here would be an operand that can never be false, which § *Decisions* calls dead code inside a security predicate.

**Delete the `authScopeOverride` option too, or it outlives its own safety argument.** `access-claims.ts`'s `authScopeOverride?` opt exists solely for this endpoint, and its JSDoc argues its safety from exactly the two bounds this work deletes — it states that the overridden scope is separately bounded by BOTH the caller's dominion and the subject's, so it can exceed neither. Afterwards it has **no caller at all**, yet stays exported via `testing.ts`, keeping constructible the shape this work deletes: a token whose `authScope` is decoupled from its issuing scope. Remove it from `NebulaAccessClaimInput` / `buildNebulaAccessEntry` / `mintAccessToken`'s opts; the handler then passes `universeGalaxyStarId: subjectIdentity.universeGalaxyStarId` with `activeScope: body.activeScope`, so **one parameter carries the claim and one carries `aud`**.

- **`security.md` rule (2)** — already narrowed 2026-08-11 to the one predicate plus the identity check, and it says restoring the deleted invariants is a **regression, not hardening**. ⚠️ **The rule file must NOT be "translated to scope terms"** — translating four invariants that no longer exist would preserve the shape this deletes.

- **[ADR-008](../docs/adr/008-full-org-tree-visibility.md)** — the denied-node set is disclosed, but the narrower-token mint's refusal must not disclose the subject's scope.
- **[`docs/vision/auth.md`](../docs/vision/auth.md) — `status: accepted`**, so contradicting it is a blocker. § *The Registry* is the statement to conform to.
- ⚠️ **Vocabulary: MUST NOT use "reach" as a noun for either verdict.** `dominion` and `passage` are ADR-015's reserved terms.

| Decision | Rejected alternative — why |
|---|---|
| **Each route states its complete requirement, in a readable list** | `hasPassageInto` at the shared gate — an **escalation**: passage admits upward, the handler's bare bit completes the conjunction, and a Star admin mints at the Universe. |

It works, and it tests the *table* rather than the *path*; the real-path form was already resolved and built next door, so preferring the cheap tier here is `calibration.md` §6 rather than judgement. *A second test flag* to separate links-vs-Turnstile — doubles the never-deploy audit surface `security.md` turns on, to buy what one deletion buys. *Leaving it behavioural-only* — under the test binding a gated and an ungated route are identical, so the criterion cannot fail. |

## Acceptance criteria
