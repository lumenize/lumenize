# Multi-user sessions

**Status:** Pass 1, 2026-09-09 — design intent only, no phases. Drafted as the prerequisite [nebula-testing-with-personas.md](nebula-testing-with-personas.md) discovered it needed; that file is the first consumer, not the reason. **Gated on a hand review of the amendment to [ADR-012](../docs/adr/012-global-profile-visibility.md), which is ACCEPTED — read it there, in § *Decision*'s sub-bullets on mailbox proof and on platform-created profiles, under the acceptance argument, since that is the committed text. It blocks everything below it.**

## Context

One browser, one session per scope. That is the assumption `refresh-token` was built on, and it is written into the cookie: one fixed name at `Path=/auth/{scope}`, so a second login at the same scope overwrites the first. The overwrite is not even loud — `handleAcceptMembership` resolves whatever cookie it finds through the registry to *its own* membership rather than to the scope named in the URL, so two sessions at one scope read as a silent identity swap rather than a refusal.

That assumption holds for a person. It stops holding the moment someone wants to look at their app as several of its users at once. That is the whole of [nebula-testing-with-personas.md](nebula-testing-with-personas.md), and [ADR-009](../docs/adr/009-real-auth-path.md) § *Decision* already committed us to it: the real multi-user login is *"dual-use"* — our own harness infrastructure, and a user-developer feature, logging several users into their own preview tabs to test an access-control model. It says to build it *"in a reusable place, not per-test."* This file is that place.

The second problem arrives with the first. A real session begins with a link sent to a mailbox, and that is deliberate — [ADR-012](../docs/adr/012-global-profile-visibility.md) makes mailbox proof the thing that stops an inviter manufacturing an accepted membership for someone else's address. But a cast of eight synthetic users has eight mailboxes nobody reads, and routing real mail to them to fish the link back out is a delivery pipeline built to move a value the sender already holds.

This file changes both, and the two are one change: **several real sessions in one browser needs cookies that do not collide, and a way to obtain each session's link that does not need a mailbox.**

## Objective and goals

**Objective — one browser holds several concurrent real sessions, and the platform can hand a session's link to whoever owns the identity's namespace, without weakening what mailbox proof protects.**

**Goals:**

1. **A refresh cookie per IDENTITY, not per scope.** Two *different* identities logged in at one scope coexist and neither overwrites the other; the same identity logging in again still replaces its own cookie, exactly as today, which is what keeps the jar bounded.
2. **A restricted way to OBTAIN a platform-issued identity's invite link — never to create one**, licensed by one predicate over the caller and the address together rather than by a guard around either — with every way that property can lapse written down in § *Constraints Pass 2 inherits* rather than assumed, since none of them is enforced by code.

## Design intent

### The cookie: derive the name, do not add a second one

Today the cookie IS the identifier — the server hashes whatever arrives and looks the session up, so it never has to know *which* user. With several sessions at one path that stops working: the browser sends them all, and the server has to pick.

**The name carries the discriminator, and the caller says which one it wants.** Both halves of that sentence cost something, and both are pinned below: what the name derives from, and what shape a caller-supplied name may take.

**A supplied name must match the derived form exactly** — `refresh-token.` plus a `Memberships.sub` UUID — and is refused **before** the jar is read. Without that, the name is an arbitrary string into `extractCookie`, which is a bare equality over every cookie the browser presented; the signup ticket sits at `Path=/auth`, a prefix of `/auth/{scope}`, so it is presented on all five read sites. Every one of them fails closed on today's code, which is exactly the condition under which nobody notices the constraint was never written. On the write side the name is interpolated into `Set-Cookie`, where an arbitrary string is attribute injection rather than a failed lookup.

**The discriminator is the membership's `sub`** — literally `refresh-token.f3a1…`, one name per (address, scope) row. `Memberships` carries `UNIQUE (emailId, universeGalaxyStarId)` and `#mintIdentity` early-returns the existing row, so one identity at one scope keeps one `sub` across every login and across a `.dev` wipe. **That is what keeps goal 1 true**: a person logging in again at a scope they already hold overwrites their own cookie exactly as today, so the SINGLE-SESSION jar does not grow. ⚠️ `MINT_ALL_COOKIE_CAP`'s value survives; its **reason** does not. Its JSDoc sizes 24 to sit far below a browser's per-domain ceiling, and that budget now divides across concurrent identities at one scope — so a change to the cap, or to how many tabs open at once, must re-derive it. A random per-session id would have made every login an addition with nothing reaping it. ⚠️ **`handleLogoutAll` needs the sibling `sub`s to clear their cookies**, and `revokeAllForAddress` returns `{ scopes }` alone — so it owes a widened return, which is a cross-component RPC contract change rather than a helper edit.

### How a tab learns which identity it is — UNSETTLED, with the bar an answer must clear

The name solves the server's problem — which of several cookies to read. It creates the client's: a tab has to supply a name, and it cannot read an `HttpOnly` cookie to learn its own.

⚠️ **A mechanism was drafted here on 2026-09-10 and is WITHDRAWN, because its premise was false.** It argued that the `nebula.authScope:{activeScope}` localStorage hint would collide across persona tabs. It cannot: `previewStar(s) = ${s}.dev` means Studio's own active scope is the GALAXY and `.dev` appears only as an iframe src, so Studio reads `nebula.authScope:{u}.{g}` while a persona tab would write `nebula.authScope:{u}.{g}.dev`. Different keys, no overwrite. The direction — a stored SCOPE cannot name which of two identities to spend — survives; the failure story does not, and neither does the walk built on it. This is `calibration.md` §7 exactly: the conclusion was agreed first, so nobody checked the premise.

**What an answer must clear.** These are selection criteria, not phase acceptance — they decide BETWEEN designs and each one is a real defect somebody already walked into:

1. **A shared link works on BOTH surfaces.** Studio's and a user-developer's app. [ADR-017](../docs/adr/017-the-url-is-the-view-state.md) need not be fully reached in this file, but the affordance may not regress — and an identity the follower CANNOT HONOUR — one they hold no cookie for — must leave them on the same page as themselves, rather than at an error or a detour that loses the destination. ⚠️ The test is capability, never difference: a persona tab's own reload names an identity that differs from any default and MUST be honoured.
2. **Persona-specific mechanisms should be limited only to aspects that cannot be solved with the general-purpose design.** Personas are one consumer of multi-user sessions. A cast-only solution fails this but a cast-only extension might be OK.
3. **Two identities in one browser hold sessions that do not displace each other** — on login, on refresh, and on reload. That is the outcome to test. ⚠️ The defect's general form, which is narrower than "unique keys": **wherever a STORED VALUE varies by identity, its key must vary by identity too.** **Both of today's stores fail it.** The refresh cookie holds a per-identity token under a fixed name at a per-scope path; the localStorage hint holds a per-identity `authScope` in one slot per active scope. What fixes the cookie is the discriminator moving into the NAME — `Path=/auth/{scope}` stays keyed by scope and becomes correct, because the key as a whole then varies by identity.
4. **A tab never comes up as a MORE privileged identity than the one it names.** A persona tab resuming as the user-developer, still labelled `mary`, is a false negative on the exact check a cast exists to run — and it is why impersonation was rejected.
5. **The client refreshes where its OWN cookie is presented.** `#serveBuiltApp` injects `authScope` as the parent galaxy, so a preview client asking there is handed the user-developer's cookie and never the persona's; `Path=/auth/{u}.{g}.dev` is not sent to `/auth/{u}.{g}/…`.
6. **No new permanent Gateway DO name per page load.** `instanceName` is `${sub}.${tabId}` and a name reservation cannot be deleted, by us or from the dashboard. A second client in one tab MUST derive — `childInstanceName` is the shipped pattern — and MUST NOT call `getOrCreateTabId`, which `tab-id.ts` warns would rewrite the stored id out from under the first client. ⚠️ Same-origin iframes share the top-level tab's sessionStorage, so this is reached by the natural implementation, not by an exotic one.
7. **An unnamed read carrying more than one cookie is refused, never guessed** — and every read site needs a policy, not only refresh. There are five, plus `HomeScreen.bootstrap()`.
8. **The recovery path stays reachable.** Home cannot be the escape hatch if reaching it is itself an unnamed read that criterion 7 refuses.
9. **Identity survives a refresh without the parent.** No callback, no re-mint, nothing the top-level page must be alive to supply.

10. **A cast's sessions can be ENDED, or the residue is accepted in writing.** `handleLogoutAll` is address-scoped, so a user-developer's logout reaps none of the personas — eight real sessions outlive it for a fixed 30-day `REFRESH_TOKEN_TTL`, with no slide and no rotation. Candidates differ on whether teardown is even reachable: a URL-carried identity leaves nothing client-side to revoke, while a stored one can be cleared. Say what a teardown reaches.

⚠️ **Two things are NOT criteria, and were mistaken for them today.** Staying out of the URL is not required — a `sub` in a `.dev` preview URL is accepted (Larry, 2026-09-10). And the existing mechanism is not an anchor: server-injected meta, the localStorage hint upgraded to a per-identity key, sessionStorage, and the URL are all live candidates.

⏳ **Three measurements decide most of it**, and are owed before another design is drafted: what the preview SPA can read from its own `location`; what a per-persona Gateway DO name actually costs, given reservations are permanent; and the behaviour of the shared sessionStorage under our own harness rather than from a spec reading.
### The link: what licenses issuing one instead of delivering it

An invite URL is a **bearer credential for the identity it names**, and it is larger than "a link to one membership". Four facts, each load-bearing for the rule below:

- **Multi-use for seven days.** `INVITE_TTL` is 604800 and the consume does not delete the row — its own JSDoc describes *"re-clicking a link that is multi-use within its TTL."*
- **Address-wide, not per-membership.** The consume mints a cookie for every membership the ADDRESS holds, capped at `MINT_ALL_COOKIE_CAP` (24), each at its own `Path`.
- **It proves the mailbox globally.** `resolveConsume`'s mailbox-proof UPDATE keys on the address, never on the scope, and is guarded to fire only once.
- **An already-accepted membership needs no accept step.** `handleRefreshToken` refuses only `!record.accepted`, so the cookie the consume places mints tokens straight away.

Acceptance is then load-bearing far beyond the scope the link was issued in: one address is one Profile globally ([ADR-013](../docs/adr/013-identity-profileid-resolution.md)), and ADR-012's owner branch keys on the `profileId` the token carries. So anyone handed the link for an address they invited could accept it and own that person's Profile everywhere. That is why the URL is fenced today — stripped from every caller-facing summary except the test-mode one (§ *Verified on disk*).

**What licenses an issue is one predicate over the caller and the address together: the address names a scope, and the caller must govern that scope's parent.** Neither half carries it alone. The address half is what ADR-012 turns on — a namespace no human can hold — and the caller's authority is not a substitute for it, because dominion is the wrong axis and ADR-012 says so directly — a `profileId` is global and scope-free while dominion is scope-local, so an admin's dominion cannot bound what a taken-over identity reaches. What bounds it is that there is no one to take over: an address on a domain we operate, whose local part encodes the issuing scope, which the platform alone ever issues.

**The address names the scope its identity lives in**, so the local part is a complete scope id and a slug: `acme.crm.dev~mary@personas.lumenize.io`, never `acme.crm~mary`. That is what lets every rule below be an **equality** rather than a containment, and it is what keeps two personas called `mary` in two Stars of one galaxy from composing one address — one address is one Profile ([ADR-013](../docs/adr/013-identity-profileid-resolution.md)), so they would silently share an identity.

**The rule is ONE predicate over the caller and the address together**, because what licenses an issue is a relation between them: this caller governs the scope this address names. Every input is read from the address or from verified claims, and the caller names no scope at all:

```typescript
// personaScope(address) — the ONE definition of "is this ours, and whose?", called by
// mayIssueLink AND by #mintIdentity. It returns the encoded scope rather than a boolean,
// because both callers need it: one to find the parent, one to compare against the mint's.
function personaScope(address: string): ParsedId | undefined {
  const addr = normalizeEmail(address);            // toLowerCase().trim(), once, then never again
  const at = addr.indexOf('@');
  if (at < 1 || at !== addr.lastIndexOf('@')) return;             // ① exactly one '@', ever
  if (addr.slice(at + 1) !== PERSONA_DOMAIN) return;              //    and it is our domain
  const local = addr.slice(0, at);
  const tilde = local.indexOf('~');
  if (tilde < 1) return;                           // no prefix at all is not a persona address
  let scope: ParsedId;
  try { scope = parseId(local.slice(0, tilde)); }  // "acme.crm.dev~mary" → parseId("acme.crm.dev")
  catch { return; }                                // ⚠️ parseId THROWS; this predicate must not
  if (scope.tier !== 'star') return;                              // ② a Star…
  if (!PERSONA_STARS.has(scope.star!)) return;                    //    and one with no real users
  return scope;
}

// mayIssueLink(access, address) — `access` is the caller's verified AccessEntry.
const scope = personaScope(address);
if (!scope) return false;
const galaxy = getParentId(scope)!;                // "acme.crm.dev" → "acme.crm"
return access.authScope === galaxy                              // ③ `invite`'s own eligibility,
    || hasDominionOver(access, galaxy);            //    aimed at the PARENT of the named scope
```

**`PERSONA_STARS` is `{ 'dev' }` and carries its own reason**, never `RESERVED_STAR_SLUGS`. That set exists to stop slug squatting and its JSDoc already plans to grow — *"extend this with any environment name the Galaxy collapse pins for its `{u}.{g}.{env}` cast (`staging`/`prod`)"* — so borrowing it would make personas mintable in production the day `prod` is reserved, for a reason nobody weighed. The invariant here is different and must travel with the value: **a Star with no real users in it.** Adding a member to this set is asserting that of the Star, which is a question the squatting list never asks.

| Condition | What it stops | The mutation that reds it |
|---|---|---|
| ① Exactly one `@`, and the domain after it is one we operate for this purpose | Targeting a **human** — dominion cannot do this, since the attacker's own scope is a legitimate place to invite anyone, so no authority test bounds it. The one-`@` half stops an **address two parsers read differently**: `isValidEmail` — the only address check on the invite path, duplicated at `nebula-auth-registry.ts:2181` and `worker-token.ts:54` — splits on the FIRST `@` and merely asserts one exists off the edges, so `acme.crm.dev~ma@evil.com@personas.lumenize.io` satisfies it while this predicate reads our domain. | Drop the domain half and `victim@gmail.com` is issuable to whoever invited them. Drop the one-`@` half and the address above is licensed here and then handed to a mail transport that parses it a third way. |
| ② The prefix parses to a Star, and that Star is in `PERSONA_STARS` | Two different things. **Tier** stops the caller check drifting upward: `parseId` takes one to three segments, so `acme.crm~mary@personas.lumenize.io` parses happily, its parent is the *universe*, and ③ would then clear any universe admin with nothing to do with `acme.crm`. **The Star's VALUE** stops a persona being minted inside a live tenancy: every safety argument in this file is a `.dev` argument, and `acme.crm.tenant1~mary@…` passes tier just as well. ⚠️ **A universe admin reaches the cast legitimately, by dominion, and ② is not what bounds him** — `isAtOrAbove('acme', 'acme.crm')` holds, which is ADR-015 working as designed. | Drop the tier half and a **non-admin** member of universe `acme` requests `acme.crm~evil@personas.lumenize.io`: the parent is `acme`, so ③ arm 1 clears him, the mint rule places that identity at `acme.crm`, and once logged in it passes ③ for **every persona in every Star of that galaxy**. Drop the value half and a galaxy collaborator mints a member inside `acme.crm.tenant1` and takes its session link — **a Star `invite` refuses him for outright**, which is the asymmetry to assert. |
| ③ The caller passes `invite`'s eligibility at the named scope's **PARENT** | Targeting **another tenant's** cast, and a **persona reaching another persona**. The scope is read out of the address rather than supplied, so a caller holding `evil.corp` has nothing to name; and a persona's own membership is at the Star, whose parent is the galaxy, where it holds no membership and — dominion being downward only — can hold none. ⚠️ It does REACH the galaxy, by upward passage, which is how it reads the SPA bundle hosted there; passage is the arm that confers nothing, so it satisfies neither of ③'s. | Drop it and any authenticated caller reaches any tenant's personas, Mary included, whose tab's client is reachable from generated app code. |

⚠️ **③ is a CONJUNCT of the licence, not a tunable guard beside it.** The namespace makes the address safe *for its own galaxy's people*; ③ is what says this caller is one of them, and the two are one sentence — relaxing ③ re-opens [ADR-012](../docs/adr/012-global-profile-visibility.md) rather than tuning a local control. ⚠️ **None of the three is defence in depth** — each is the only thing standing between an attacker and a different outcome. A change that drops one is a change to the invariant, not a simplification.

**③ needs the address to decide where its identity may LIVE, or it rests on a convention.** A persona holds no membership at the galaxy only because the provisioning procedure never mints one there — `#mintIdentity` takes whatever `(email, scope)` pair it is handed, and `isValidEmail` is the whole address check on that path (`atIdx > 0 && atIdx < email.length - 1`). So a galaxy member can invite `acme.crm.dev~mary@personas.lumenize.io` into `acme.crm`; mint-all deposits a cookie at that `Path` on Mary's next consume; `accept-membership` carries only `parseScopeGuard` and the rate limiter, no CSRF token and no proof of a human; and Mary's tab, being same-origin, posts her own acceptance. She then passes ③ for every other persona. **So: an address in the persona namespace may hold a membership at EXACTLY the scope its local part encodes, and nowhere else** — refused at `#mintIdentity`, which is the one choke point every **mint** path reaches, with a message naming why. ⚠️ **Mints are not the only way an address arrives in the namespace** — see § *Constraints Pass 2 inherits* on `changeEmail`, which re-points one without passing here at all. ⚠️ **The invite that trips this is likelier a user-developer adding "Mary" to their galaxy than an attacker**, and today it succeeds silently — which is why this is a refusal at the mint rather than a note in a task file.

⚠️ **"Is this address in the persona namespace?" gets ONE definition, called by both the predicate and the mint** — never two spellings of one question. The natural spelling is the wrong one, and the divergence needs the right example to show it. `addr.endsWith('@personas.lumenize.io')` is what a second site reaches for, and it **accepts** `acme.crm.dev~ma@evil.com@personas.lumenize.io` — which the shared predicate refuses on ①'s two `@`s. So the mint rule would treat as ours an address the issuance rule does not, and place it wherever the caller named. (`indexOf('@')`, this package's other habit, happens to agree with ① on that address: both read a domain that is not ours. It is `endsWith` that splits them.) Nothing can then have a link issued for it, so this is a divergence rather than a live hole; it is worth closing because a rule whose two halves ask the same question differently is one edit away from disagreeing about something that matters, and because the mint rule is the only guard if a second issuance path ever exists. One exported predicate carrying ①'s exactly-one-`@` form, one home for the domain constant beside it. ⚠️ **`tasks/backlog.md` § *Nebula Auth* proposes one shared address validator** strict enough to make any address unambiguous, deleting both `isValidEmail` copies. This predicate is deliberately narrower — it answers *is this ours*, not *is this a well-formed address* — so it does not become that validator, and that row's characterisation of it as issuance-only wants updating once the mint rule lands.

**The ENTRY refuses an address that holds no membership at its encoded scope, and that conjunct is the entry's rather than the predicate's.** `#mintIdentity` is find-or-create and `issueInvites` carries no existence check, so predicate-plus-`issueInvites` composes to **create-or-get** — which is not what goal 2 says and not the floor the sibling justified: its two-floor row reads *"opening a tab requests an already-provisioned persona's link."* Without the conjunct, a galaxy collaborator holding only that floor mints a brand-new identity wherever the address points and takes a seven-day bearer credential for it. It belongs on the entry rather than in `personaScope` because the two ask different kinds of question. `personaScope` asks *is this address ours, and whose* — a fact about a string, true before anything exists. *Does this identity exist* is a fact about the world. Fusing them would make the predicate un-callable from the mint, whose whole job is to run before the membership does.

⚠️ **Every comparison happens after ONE normalization, and `normalizeEmail` is private to the registry today.** `acme.crm.Dev~mary@personas.lumenize.io` is refused if the prefix is parsed raw and accepted if it is parsed after lowercasing, so the order is load-bearing and the helper has to become reachable from wherever this predicate lives.

**Why the scope comes from the address and never from the caller.** `invite` takes its scope as a parameter — `access.authScope === targetScope || hasDominionOver(access, targetScope)` — so a rule phrased around *the caller's own parent galaxy* is satisfied by any galaxy the caller cares to name, including one with nothing to do with the address. Deriving it makes the substitution unrepresentable. It also makes the check statable for the caller who most needs it: `createGalaxy` writes `Scopes` rows and calls `#mintIdentity` zero times, so a Galaxy owner has no `{u}.{g}` membership of their own to match and reaches ③ by the dominion arm; its JSDoc states that founder rule as prose.

### The ADR-012 amendment — the gate on this whole file

ADR-012 is **Accepted**, and it states the property this design bends: acceptance needs the mailbox and an explicit act, its writer authenticated by the cookie a click on mail to that address placed. **One half of that survives here and one does not, and the gate should see which.** The endpoint still demands *that membership's own cookie*, which is the half carrying the manufacture argument. What lapses, for persona-namespace addresses only, is the human-at-a-form claim: `acceptMembership`'s JSDoc rests on *"Acceptance behind a form submit cannot be forged by any fetch, redirect-follow, or JS render"*, and `router.ts`'s absent-Turnstile comment on *"it reached this browser only via a proved mailbox"* — and a tab following a handed-over link and POSTing with `credentials:'include'` is precisely a redirect-follow and a fetch. Both comments are corrected by this change (§ *Criteria*), because a dead justification left standing at a security site is what the next reader trusts. What the amendment licenses is a **second restricted way for a link to reach a legitimate holder**. It is committed — the Status line above says where — and deliberately not copied here, because a copy would rot the moment either text is reworded (`.claude/rules/workflow.md` § *Referring to things across files*).

**Keeping the two in step is this file's obligation, and it has already been missed once.** The predicate above is the whole licence, so the ADR carries the same relation. The local part encodes the **Star** the identity lives in. The caller is checked at that Star's parent galaxy. The caller condition is a conjunct, not a tunable guard beside it. When the address gained its Star on 2026-09-09, this file was updated and the ADR was not — so the gate briefly pointed at a text stating a different rule. ⚠️ **Drafted for Larry's hand review, never for ratification** — no ADR is ratified before pre-alpha launches, and this one is his to read.

## Verified on disk — so it need not be re-derived

- **The cookie name is spelled at eight sites in `worker-token.ts`, and each read is a policy decision.** `extractCookie(cookieHeader, name)` takes the name as a **parameter**, so it is not a definition point: the literal appears at five reads — `handleLogoutAll`, `handleAcceptMembership`, `handlePendingMembership`, `handleRefreshToken`, `handleLogout` — and three writes, the `refreshCookie` builder, the `expiredRefreshCookie` builder, and `handleLogout`'s hand-rolled clear beside it. Each read decides *which session that endpoint acts on*, so none is a mechanical substitution. **This is not a rename**, and any estimate weighing it against the per-origin split has to price it as eight decisions.
- **The literal has a second home outside the package, on the `/live` rung-1 login path.** `apps/nebula/test/lib/email-login.ts` both reads it (`if (!c.startsWith('refresh-token='))`, disambiguating by the `Path` tail) and hand-builds `Cookie:` headers from it; that module is what `provisionAndLogin` and `loginViaEmail` run on, so the registry sweep goes mechanically red before it can say anything about behaviour. ⚠️ Its `Path`-tail match is **silently wrong the moment two sessions share a scope**, since `Path` derives from the scope alone — so the harness needs the same single-definition treatment, never a helper that bridges the old name and the new (`.claude/rules/live.md` § *A `/live` scenario MUST NOT compensate for its environment*). `packages/auth` keeps its own `refresh-token` at `Path=/` and is deliberately out of scope, per the fork `tasks/backlog.md` § *@lumenize/auth* records.
- **The accept endpoint resolves the cookie, never the URL — and it DOES change.** `handleAcceptMembership` reads the refresh cookie and resolves it through the registry to that session's own membership, which is why a colliding cookie is an identity swap today. But its JSDoc rests the safety on *"the browser only sends it to this scope's auth routes, so no cross-membership authorization rule exists to get wrong"* — and a caller-supplied name is exactly that rule. ⚠️ **It and `handlePendingMembership` run BEFORE any session exists**: the tab has just followed a link, holds no token, and cannot read an `HttpOnly` cookie, so the name has to reach the browser some other way. Pass 2 owes where it is born; the 302's landing URL is the natural home, which makes it a change to the landing contract.
- **The localStorage hint has TWO writers and one key.** `nebula-client.ts` writes `nebula.authScope:{activeScope}` on every successful token acquisition, `HomeScreen.vue` writes it again when it sends someone into a scope, and `App.vue` reads it as `authHint(urlScope) ?? urlScope`. Its own comment says the client must know the authScope *"to hit the path-scoped refresh endpoint"* — which is exactly the job the walk takes over.
- **Home cannot rescue a cold tab, so the walk is not optional.** `HomeScreen`'s `bootstrap()` calls `/auth/${props.scope}/refresh-token` — it needs a scope before it can get a token, `scope-summary` is `POST` behind `verifyJwtGuard`, and the scope list is what you would use to choose. `handleLogoutAll`'s JSDoc states why no scope-less route escapes it: cookies are `Path={prefix}/{scope}`, so a scope-less route receives none.
- **The preview's injected scope is ROUTE-derived, and it carries THREE fields.** `#serveBuiltApp` writes `nebula-scope` as `{ activeScope: star, authScope: '{u}.{g}', ontologyVersion }` — the star from `url.pathname.split('/')[2]`, the authScope as that star minus a segment, and the version from `#appliedHead()`. ⚠️ **`authScope` is the parent GALAXY**, which is why a preview client asking there is handed the user-developer's cookie and never a persona's. ⓘ Only `ontologyVersion` actually needs the server; the two scope fields are URL-derivable, and a refresh re-derives all three because the Worker re-injects from the path. Its JSDoc's *"never request-supplied — the wrong-Star footgun guard"* is about the scope, not about an identity selector.
- **`NebulaAuthFacade` exposes exactly one `@mesh()` method today** (`invite`), and its header states the discipline any second one inherits: verdicts compute from `originAuth`, identity is never hand-threaded, and the call's shape is validated at that boundary (ADR-001).
- **Scope slugs are already `isValidSlug`-gated at creation**, which is what lets the predicate trust `parseId` on the left of the tilde: `claimStar` and the universe claim both refuse an invalid slug, and `SLUG_RE` is `/^[a-z0-9][a-z0-9-]*$/`, so no universe or galaxy slug can contain `~`, `.` or `@`. ⚠️ **A PERSONA slug cannot move which SCOPE this rule reads, so do not relax ② or ③ on the belief that a slug validator is backing them.** The prefix ends at the FIRST tilde, so `acme.crm.dev~ma~ry@…` and `acme.crm.dev~ma.ry@…` both read `acme.crm.dev`. ⚠️ **That is narrower than "the slug carries no security weight", which is false** — a slug carrying `@` composes an address our own `isValidEmail` and this predicate read differently, which is why ① requires exactly one `@` rather than trusting the composer. The slug validator is still wanted, for reasons [nebula-testing-with-personas.md](nebula-testing-with-personas.md) owns: the address derives from the slug, and a machine-composed address must parse identically everywhere it is read.
- **The invite URL exists server-side at mint time, and one carrier past the entry already exists.** `issueInvites` returns it to the entry, which uses it to build the letter; `summarizeInvites` strips it from the caller-facing summary **except under `NEBULA_AUTH_TEST_MODE`**, where it returns every link in `summary.links` and the facade sends no mail at all. So goal 2 is a fence decision, not a plumbing one — but it is a *second* fence beside a wider test-only one, and the honest question is whether the test-mode carrier can be deleted once a rule-gated production path exists, which is a smaller total surface than today's.

## Criteria — what a phase must satisfy

- **Two real logins at one scope coexist in one browser, and each reaches its own identity.** Mutation: revert the cookie name to the shared literal, and the second login silently becomes the first — which is the defect this file exists to remove, and it must be asserted as an identity check rather than a "still logged in" check.
- **Every existing single-session flow is unchanged.** The full `/live` registry sweep is the evidence, because login, accept, refresh and logout are what most scenarios open with.
- **`mayIssueLink` refuses each attack separately**, with a mutation per **half** — five, not three, since ① and ② each carry two — and a positive control proving the entry is reachable under the un-mutated predicate. What each mutation lets through is the table's own third column; transcribe them from there rather than restating them.
- **The entry refuses an address that holds no membership at its encoded scope**, so the licence can only hand back a link for something provisioning already created. Mutation: drop the conjunct, and a galaxy collaborator holding no dominion mints a new identity in a Star of his choosing and takes its link. ⚠️ Assert it as the **asymmetry**: the same caller, the same Star, refused by `invite` and admitted here, is what makes this checkable rather than a matter of opinion. ⚠️ Match the refusal MESSAGE — three refusals that are the same boolean are indistinguishable, and telling them apart is the point. ⚠️ A multi-limb scenario reds on its FIRST failing limb and hides every later limb's vacuity (`.claude/rules/live.md`), so each condition owes its own run.
- **The prefix parse is unambiguous by construction**, asserted in three directions: an address whose slug contains `~` or `.` still reads the same `{u}.{g}.{s}`; an address with no `~` at all is refused rather than parsed; and one whose slug contains `@` is refused by ① rather than parsed at all. Mutation: split on the LAST tilde instead of the first, or match the whole local part with a regex, and a slug carrying a tilde moves which scope the rule authorizes against.
- ⏳ **The carriage criteria are WITHDRAWN with the mechanism they tested** (§ *How a tab learns which identity it is*). One of them could not fail — its mutation was "restore the localStorage hint", which mutates nothing, since Studio and a persona tab key that hint differently. Whatever answer replaces the withdrawn design brings its own, and the bar it must clear is in that section.
- **A persona address is refused a membership anywhere but the scope it names**, at `#mintIdentity` rather than at any one caller, and the refusal says which scope the address permits. Mutation: drop the rule, invite `acme.crm.dev~mary@personas.lumenize.io` into `acme.crm`, and that persona's own tab can accept it and then request every other persona's link — so the mutation's assertion is the ISSUANCE that follows, never just the mint.
- **The persona domain resolves NO mail destination**, asserted rather than assumed — it is the whole of "no human can hold it" and today nothing in the repo witnesses it. Both records must be empty, because RFC 5321 falls back to the address record when there is no MX:

  ```sh
  dig +short MX personas.lumenize.io     # → (empty)
  dig +short A personas.lumenize.io      # → (empty)
  dig +short AAAA personas.lumenize.io   # → (empty)
  ```

  ✅ Verified 2026-09-10: all three empty, while `lumenize.io` returns Cloudflare's three MX. ⚠️ **The check must query real DNS**, so it belongs in a lane that runs against the world rather than a local stack; Pass 2 picks between the persona `/live` scenario and `deploy.sh`. Mutation: point an MX at that label and the check reds — where today every tier stays green while every persona address becomes human-holdable.
- **The SESSION record names who caused the session to exist when that is not its subject** ([ADR-016](../docs/adr/016-record-the-acting-principal.md), which enumerates *establishing a session* by name). That is `recordSessions`, reached from `consumeAndLogin` — not `invite.issued`, which already carries `projectActingToken(callerClaims)` and would satisfy a criterion here with zero work while recording nothing about a handover. `login.established` logs `sessions`, `requested` and `expiresAt` and no acting principal at all, which is right while the actor is always the subject and wrong the moment a user-developer's handover establishes a persona's session. ⚠️ **The actor must be SERVER-COMPOSED**, carried from the issuing principal on the `InviteTokens` row — there is no Bearer token on a consume, and ADR-016's *token-attested or server-composed* clause licenses exactly this. Do not spec threading `callerClaims`. Mutation: strip it and the log cannot tell a handover from a person clicking their own mail.
- **`acceptMembership`'s and the accept route's JSDoc are corrected in this change**, not left to be believed — the form-submit and proved-mailbox claims above. Check by reading them, since no test can red a stale comment.
- **[ADR-012](../docs/adr/012-global-profile-visibility.md)'s `Today's code differs` note is deleted in the same change that makes it false**, never as a follow-up — the same rule `tasks/backlog.md` § *Lumenize Mesh* states for ADR-007's divergence note. Check with the README's own enumeration, `grep -rn '^> \*\*Today' docs/adr/`: **ADR-012's row is gone and ADR-015's survives** — the grep prints one line, never none, so a criterion reading "prints nothing" would be unsatisfiable.

## Constraints Pass 2 inherits

- **[ADR-013](../docs/adr/013-identity-profileid-resolution.md) is what makes the namespace argument true**, and it is a dependency rather than a citation: one address is one Profile globally, so the safety of issuing a link rests entirely on the address being one no human holds. A change that let two scopes share a synthetic address would break this file's invariant without touching its code.
- **[ADR-016](../docs/adr/016-record-the-acting-principal.md) binds the SESSION, and that work is owed rather than present.** Issuance already records its actor; establishing a session does not, and the accept path records none either — `handleAcceptMembership` calls `acceptMembership(record.sub)` with no claims, and that method's own comment says `callerClaims` is absent on the cookie-credentialed path. § *Criteria* carries the shape, including why the actor has to be server-composed.
- **The namespace holds only while `personas.lumenize.io` has NO inbound route.** That is what makes "no human can hold it" true today — `dig +short MX personas.lumenize.io` returns nothing, while the `lumenize.io` apex returns Cloudflare's three. Nothing in code enforces it and no test reds if it changes, so **adding delivery there is an ADR-012 change rather than a mail-config chore.** ADR-009 anticipated the shape — *"reserve the apex for named identities, subdomain-isolate later only if a real inbox appears"* — and this subdomain is isolated for the opposite reason: to stay undeliverable.
- **`tasks/backlog.md` § *Nebula Auth*'s persona-reaping row is tripped twice here, and both halves are dispositioned rather than left to be re-derived.** Its address assumption was settled on the two-segment grammar, which this file replaced — the row now reads `{u}.{g}.{s}~{slug}`, edited in this same change. And its *"a stranded membership authorizes nothing"* premise was written before tabs were real logins: a stranded persona now holds a session, so reaping matters more than the row assumed. Its trigger is unchanged; what moves is the weight behind it.
- **An address may not be RE-POINTED into the namespace, and the mint rule cannot see that happen.** `changeEmail` is a bare `UPDATE Emails SET email = ?` with no address check, and it never touches `#mintIdentity`. Because memberships ride `emailId` and `profileId` hangs off the `Emails` row, re-pointing a human's address to `acme.crm.dev~mary@personas.lumenize.io` carries their memberships **and their global `profileId`** into the namespace — at which point ADR-012's *"the only profiles reachable that way are ones the platform itself created"* is false. It has no production caller today and its JSDoc names the flow that will build one, so this is a pinned future path rather than a live hole: the constraint belongs beside that JSDoc's existing *"Do not expose this method as an endpoint without building that."*
- **The namespace claim is time-varying, so it holds for the CURRENT holder of the prefix.** `executeScopeDeletion` removes `Memberships`, `MagicLinks`, `InviteTokens` and `Scopes` — never `Emails` — while `checkSlugAvailable` frees the slug with no tombstone and universe claim is open self-signup. So a stranger who claims `acme` and creates galaxy `crm` inherits every `acme.crm.dev~*@personas.lumenize.io` row, and `#mintIdentity` hands their persona the previous cast's `profileId`. **Accepted, not closed:** the blast radius is ADR-012's field set — display fields plus the private set, never scope contents — and `emailVerified` carries over beside the `profileId`. ⚠️ **Nothing currently owes the reap**: the Profile-GC row sweeps Profile DOs with no memberships and never touches `Emails`, so it would leave exactly the row described. What would close it is a Registry-side sweep of persona-namespace `Emails` rows whose scope no longer exists — the tombstone row in the same backlog section.
- **The URL is never logged, at any level, anywhere on this path.** `critical.md` names magic-link URLs and `request.url` itself as MUST-NOT-log, and pre-alpha runs broad `DEBUG`, so the rule is not theoretical — every existing site in the package already logs identifiers only, and says so. The new path carries the same value to a new consumer, over mesh rather than mail. Criterion: a `/live` run with broad `DEBUG` shows no invite URL in the sink.
- **The tab uses the ORDINARY invite link, unchanged — no narrower token, no second issuance path** (Larry, 2026-09-10). It is wider than a tab strictly needs: multi-use for the seven days of `INVITE_TTL`, and every consume flips `emailVerified` for the address. Neither is worth a bespoke mechanism. **Re-derived rather than inherited or deleted** (`calibration.md` §4): multi-use exists because *"corporate email scanners fetch these links and follow the redirect"*, which does not reach a link handed to the tab that asked for it — but tightening it to single-use would make correctness depend on `personas.lumenize.io` having no inbound route, which is the premise two bullets up that has no witness. Multi-use is what makes that failure impossible, so it stays, and the reason is recorded here rather than left to expire again.
  - **Token accumulation is the shared mechanism's property, not this file's, and is accepted.** `issueInvites` writes a fresh `InviteTokens` row per call and rows die only at the expiry sweep, so repeated calls leave concurrent live credentials — identically for a human admin who resends an invite. It barely arises here: a tab resumes from its own cookie and never re-issues, and provisioning invites only a persona the Registry calls unaccepted or absent. A persona token is also worth strictly less than a human's, which reaches that person's global Profile. Nor is a live token revoked by anything — `resolveConsume` leaves the row and `types.ts` says rows die only at the expiry sweep, which is equally true of every human's invite today. ⇒ If either ever matters it is one backlog row against `issueInvites` for every caller, never a persona special case. The one place it could bite here is reaping a removed persona while its link is still live, which is the reaping row's business above.
