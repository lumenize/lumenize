## Objective (target, present tense)
Every client subscribed to a query also receives that query's **live roster** — the set of `{ sub, profileId }` for the **distinct people** currently subscribed to it — re-pushed whenever a subscriber joins or leaves. The roster lands in a reactive store keyed by the query; a consumer resolves each `profileId → display` via the built `subscribeProfile(profileId)`. First consumer: chat's participant roster (a chat participant subscribes to the session's `Message` query, so the roster *is* the participant list).

## Why no read-gate (ADR-008 covers presence)
The roster is a **flat set gated only by Star reachability** — no per-resource read-gate, no per-viewer filtering — because [ADR-008](../docs/adr/008-full-org-tree-visibility.md) (amended 2026-07-08 to cover presence) makes *who is actively subscribed* visible to every Star member:
- **Visibility ≠ capability.** Seeing who else is subscribed confers no ability to read or mutate the query's data. The org tree (nodes, grants, grantee identity) is already Star-public via [dag-tree.ts](apps/nebula/src/dag-tree.ts) `getState()`, so the roster adds only the *behavioral* increment "who is watching now" — never any grant/permission data (the roster projects `{ sub, profileId }` only, never `accessAdmin`).
- **Reachability is the boundary.** A client only receives a query's roster because it is already subscribed to that query, which already required reaching the host Star (the `onBeforeCall` aud-lock). Cross-Star stays closed by that same boundary.
- **Intra-Star, so the profile resolution it feeds is intra-Star too.** The roster's participants are same-Star members, so resolving their `profileId`s is same-Star — this task does **not** exercise the profile store's *global cross-scope* open-read generalization (that's the profile store's own ADR-candidacy call).
- **Advisory / display-only** — the roster MUST NOT gate any capability.

## Why multi-user is justified pre-alpha (coach-loop, not collaboration-first)
Presence is the platform's **participant substrate**, not a collaboration-first pivot (the persona is ~90% solo — [strategy.md](docs/vision/strategy.md) check #3). It's a **near-free byproduct** of the identity-from-`changedBy` + subscribe machinery the platform needs regardless: a coach (or a second participant) is just another entry in a query's roster, exercised now via act-as / synthetic users. This mirrors [chat](nebula-chat-history-multiuser.md)'s and the profile store's own framing — the multi-participant substrate exists for the **coach loop first** (support + the highest-bandwidth feedback surface), and team collaboration inherits it later for free. The presence-UI non-goals below (typing / read-receipts / anti-flap) are held out for exactly this reason: they are the collaboration-first surface, not the substrate.

## The set is `{ sub, profileId }` pairs — resolve display via the built Profile store
The roster carries **`{ sub, profileId }` pairs**, the profile store's Phase-4 **"stamp, don't resolve"** pattern: `profileId` rides every authed caller's JWT (a bare, optional top-level claim on `NebulaJwtPayload`), so we **capture it alongside `sub` at subscribe time** — right where the roster row's `sub` is already derived from `callContext.originAuth` ([query-subscriptions.ts:113-116](apps/nebula/src/query-subscriptions.ts)) — and deliver it in the roster. So there is **no live `sub → profileId` hop** on the display path, and the mesh-only Star never raw-RPCs the registry ([mesh.md](.claude/rules/mesh.md) Nebula-never-raw).
- **`profileId` → display.** A consumer resolves `name`/`nickname`/`picture` via **`subscribeProfile(profileId)`** ([nebula-client.ts:1150](apps/nebula/src/nebula-client.ts) — built, binding-agnostic, reactive: a field change re-pushes for free; public read is OPEN so no gate). Display resolution — resolving the name, refreshing on change, degrading when a `sub`/`profileId` is unknown — is the **consumer's job** ([chat](nebula-chat-history-multiuser.md)), which picks *which* `profileId`s to resolve. This task delivers the raw `{ sub, profileId }` set into a reactive store; it does not render names.
- **`sub` → the join key.** The roster IS the `sub → profileId` lookup table: chat attributes each message by its server-stamped `changedBy.sub`, then maps `sub → profileId` **via this roster** to resolve a name. This lookup is 1:1, which is why the roster must be **distinct-by-`sub`** (below).
- **`profileId` may be absent** — the claim is optional (a pre-rollout token omits it). The row and roster carry it as optional; a consumer degrades to rendering the `sub`.

## How it works (mechanism — the roster rides the query subscription)
A `profileId` column on the roster rows, a distinct-by-`sub` roster projection, two bridge methods, one client handler. **No new registry, no new subscribe surface** — the roster's audience *is* its content: the clients subscribed to the query (`QuerySubscribers.forQueryHash(queryHash)`), which already tracks `sub` and now also `profileId`.
- **`QuerySubscribers` gains `profileId`** — captured in `registerQuerySubscriber` from `callContext.originAuth?.claims.profileId`, one line after the existing `sub`/`accessAdmin` derivation. ⚠️ **Add `profileId` to the three column lists too** — the `CREATE TABLE` (nullable `TEXT`, not in the PK), the `INSERT`, **and** every `SELECT`/returned-row site (`registerQuerySubscriber`'s returned row, `forQueryHash`, `all()`) — else a correct write is silently dropped by a `SELECT` that never names the column (it survives type-check behind the `as unknown as` cast). No `email` migration.
- **The roster is DISTINCT-by-`sub`, dedup by `sub` ALONE — never the `(sub, profileId)` tuple.** `QuerySubscribers` is keyed per-`clientId` (per tab), so `forQueryHash` returns one row **per connection**. The roster is a set of **people**, so `#broadcastPresence` **dedups by `sub`** into `{ sub, profileId }[]` — a `Map<sub, …>` in code (or `GROUP BY sub`), **coalescing `profileId` so a present value never loses to a NULL** (`MAX(profileId)` / prefer-defined). ⚠️ **NOT `SELECT DISTINCT sub, profileId`** — that dedups the *pair*, so the same person holding one pre-rollout (`profileId` NULL) and one post-rollout (`profileId` set) token — which coexist for up to the 30-day refresh TTL — would appear as **two** roster entries, breaking chat's 1:1 `sub → profileId` lookup. **Delivery targeting is separate from content dedup** — the push must reach **every** tab, so the target list is built from **all** rows (per-connection) while the payload is the deduped set.
- **Build presence targets from `forQueryHash` directly — NOT `targetsForQuery`.** ⚠️ `ResourceDataPlane.targetsForQuery(query, nodeId)` ([resource-data-plane.ts:142](apps/nebula/src/resource-data-plane.ts)) is the obvious-but-wrong method: it **read-gates** targets by `evaluatePermissions(…, 'read')` (an **ADR-008 violation** — presence is reachability-gated, uniform) and needs a `nodeId` presence has no basis to supply. Build targets straight from `forQueryHash` rows (`{ bindingName: subscriberBinding, instanceName: clientId }`), with **no permission filter**.
- **A roster push fires only when the DISTINCT-by-`sub` roster actually changes.** `#broadcastPresence` reads `forQueryHash`, dedups, and delivers the roster. The two seams, asymmetric because `subscribeQuery` is idempotent (`INSERT OR REPLACE` → `rowsWritten` can't tell insert from replace) while a leave is a real `DELETE`:
  - **Join** (`doSubscribeQuery`, after the initial query-data push): a cheap `forQueryHash` **pre-check** reports new-sub-vs-already-present. **New sub** → the roster *grew* → **broadcast** to the full (per-connection) target set (the joiner is included, so it gets its roster too). **Already-present** (a reconnect or a 2nd tab of a sub already in the roster) → the set is unchanged → **do NOT broadcast**; instead **deliver the current roster to the joining connection only** (single-target `deliverPresenceUpdate`), so the new tab renders the roster while existing subscribers are not re-notified. This kills the reconnect storm: `#resubscribeAll` re-fires every live query on every WS reconnect, so an unconditional join-broadcast would re-push an unchanged roster to everyone — O(M²) on a correlated mass reconnect of a hot shared query (exactly chat's single-session `queryHash`).
  - **Leave** (`removeQuerySubscriber` — the single funnel for explicit `unsubscribeQuery` **and** the dead-client cleanup path): guard on the `DELETE`'s **`rowsWritten > 0`** (a no-op remove emits nothing), then **broadcast** the re-projected (shrunk) roster to the remaining target set. This is an intentional **data → presence coupling** (a data-push that detects a dead client also refreshes the roster). *(A multi-tab sub closing one of several tabs still broadcasts a set-unchanged roster — a minor accepted redundancy; a set-level "sub's last connection?" post-check is a deferred micro-optimization.)*
- **No echo.** A roster push is a **read-only projection** of `QuerySubscribers`, never a row *in* it — so it can never become a fanout target the next commit re-pushes to. (Loop-*freedom* against the commit/rerun path; distinct from the **bounded** cleanup re-entrancy, which the `rowsWritten` guard terminates.)
- **Roster ≠ query-data.** A **distinct client channel** (`handlePresenceUpdate(queryHash, roster)` + `PresenceUpdatePayload` = the distinct `{ sub, profileId }[]`), not folded into the query-data push (`handleQueryUpdate` carries `{ resourceIds, deniedNodes }`) — different trigger, different payload. Roster-only: it does **not** re-evaluate the query or touch the commit/rerun path.
- **No Gateway fence needed (intra-Star).** A roster fans to the **same same-Star subscriber set** as the query-data push — all sharing the Star's `aud` — so it survives the Gateway's `onBeforeCallToClient` aud-equality check *identically* to `broadcastQueryUpdate`, with no change. Contrast the profile store's global push (spans scopes → needed the `PROFILE`-fence): **presence is intra-Star, so no fence.**
- **Cleanup reuses the query-sub handler.** Both presence pushes use `svc.broadcast`/`lmz.call` with `onResult: onQueryBroadcastResult(queryHash)` — a dead subscriber's failed push drops its `QuerySubscribers` row (the right table), and because `removeQuerySubscriber` re-fires `#broadcastPresence` on the actual removal, the roster self-heals for survivors (bounded, not a cascade). **No new `@mesh` cleanup handler.** ⚠️ Do **not** pass `onErrorOnly` to `svc.broadcast` — it applies it internally for any `onResult` ([broadcast.ts:143-155](packages/mesh/src/broadcast.ts)) and it is not a `BroadcastOptions` field (silently ignored).
- **Reconnect is free.** The client's existing query-sub reconnect walk re-fires `subscribeQuery` ([nebula-client.ts:780](apps/nebula/src/nebula-client.ts)); the server's `doSubscribeQuery` re-delivers the roster to the reconnecting connection (single-target, per the join rule). No separate presence reconnect entry.
- **The client folds the roster onto the existing `QueryEntry`, not a parallel map.** `@mesh() handlePresenceUpdate(queryHash, roster)` looks up the query entry (`if (!entry) return` — the same unknown-`queryHash` guard as `handleQueryUpdate`, so a late/racing push can't resurrect a disposed entry), sets `entry.roster`, and fires the entry's listeners. Folding onto `QueryEntry` gets cleanup for free at `#disposeQuerySubscription` (no stale-roster leak of real co-members) and matches "rides the query subscription." **No `subscribePresence` surface.**

## Decisions (pinned)
- **`profileId` on `QuerySubscribers`: baseline `CREATE TABLE`, no `ALTER`.** `QuerySubscribers` uses a plain `CREATE TABLE IF NOT EXISTS` in the constructor (not the `SQLSchemaMigrations` runner `Subscribers` uses). Pre-alpha is greenfield + the profile store's shared prod wipe is still pending, so add `profileId` (nullable `TEXT`, not in the PK) straight to the baseline `CREATE` — mirroring the profile store's "no migration/backfill" call. (Persisted-local trap: a `wrangler dev` DO that already created the table won't add the column → `rm -rf .wrangler`; fresh vitest masks it.)
- **Dedup by `sub` alone** (above) — a set of people, not connections, and NULL `profileId` never overwrites a present one.
- **The client-side `profileId → name` resolution glue lives in the consumer (chat), not here.** This task ships the roster push + the client's `QueryEntry.roster` + an `@internal` read accessor; the per-`profileId` `subscribeProfile` join and name-rendering are chat's.
- **The read accessor is public-but-undocumented (an `@internal` JSDoc tag), not `#`-private.** The `NebulaClientTest` subclass and the frontend consumer must read it, and a true `#`-private can't be read by a subclass — so use a public getter (the shape of the existing `streamingProgress(id)` getter) carrying an `@internal` JSDoc tag, per [coding-style.md](.claude/rules/coding-style.md). It becomes a documented public `client.resources.*` capability additively if/when an app needs "who's viewing."
- **Presence rides every query subscription (platform-wide).** `subscribeQuery` is the public `client.resources.*` API, so pushing the roster to every subscriber is a **platform-wide** behavior, not chat-only — owned deliberately, not opt-in (an opt-in flag is a config footgun). It is **inert** for non-consumers: a client that never reads `QueryEntry.roster` never re-renders (Vue reads-drive-effects). Honest cost — the scale axis is **fan-out count, not per-push bytes**: every query subscriber (incl. data-only ones) is woken **O(N) per co-subscriber join/leave**; acceptable at pre-alpha (join/leave is infrequent, rosters are small), with push coalescing as the deferred scale fix (§ Non-goals, anti-flap). ADR-008 makes presence *visible*/legitimate; it does not by itself *mandate* the push — the push is a cost-justified platform choice.
- **No special ontology-install handling.** On a version install, `#installState` already drains `QuerySubscribers` and pushes one `OntologyStaleError` per client; the roster (derived from `QuerySubscribers`) follows it and rebuilds when clients re-subscribe. Nothing presence-specific to drain.

## Success criteria (capable-of-failing — sketch)
- [ ] **A `QuerySubscribers` row carries the subscriber's `profileId` end-to-end** — mint a token **with** a `profileId`, subscribe, and assert a **non-null `profileId`** arrives in the delivered roster (not merely that the payload has the key — that false-greens the `SELECT`-omission bug M4). Reds if only `sub` is stored/selected. Cover a **`profileId`-absent** token → the row/roster carry it absent, no throw. Mutation-check the capture line.
- [ ] **The roster dedups by `sub` alone.** Two connections of the **same `sub`** carrying **different `profileId` presence** (one token with, one without) → the roster has **exactly one** entry for that sub, carrying the **defined** `profileId` (NULL never wins). Reds under `DISTINCT (sub, profileId)` (two entries) or NULL-overwrite. A second tab of an already-present `sub` also does **not** grow the roster, though delivery still reaches the new tab.
- [ ] **The pushed roster is `{ sub, profileId }` pairs** — never `accessAdmin`; reds if the projection leaks `accessAdmin`.
- [ ] **A new sub joining re-pushes the grown roster to existing subscribers**: a second client with a **distinct `sub`** subscribing causes the first client's `handlePresenceUpdate` to fire with the **2-participant** roster (from `doSubscribeQuery`, not a client-local recompute → must red).
- [ ] **A reconnect / already-present re-subscribe does NOT broadcast to others** — re-firing `subscribeQuery` for a `sub` already in the roster delivers the roster to the **re-subscribing connection only** (single-target), and existing subscribers' `handlePresenceUpdate` does **NOT** fire (assert the existing subscriber's `presenceUpdateCount` is unchanged). Reds if the join path broadcasts unconditionally (the reconnect storm).
- [ ] **A leave/disconnect re-pushes the shrunk roster to the remaining subscribers** — an explicit `unsubscribeQuery` and a forced disconnect both drop the row (via `removeQuerySubscriber`) and re-push (assert the transient roster shrink, per testing.md §self-healing-transient, not just a converged empty set).
- [ ] **A no-op `removeQuerySubscriber` emits NO roster push** — an `unsubscribeQuery` for a `(queryHash, clientId)` with no matching row, or a duplicate disconnect fire-back, does **not** broadcast (guarded on `rowsWritten`). Reds if `#broadcastPresence` fires unconditionally on remove. Mutation-check **both** operands (row-present → fires; no-op → silent).
- [ ] **Reachability is the only gate — reachability, not read.** An in-scope subscriber with **zero read grants** on the query's matched nodes (reuse the `child2-query-subs.test.ts` all-denied scaffold) still receives the **identical full** `{ sub, profileId }` roster, and the payload carries **neither `deniedNodes` nor `resourceIds`**. Reds if presence is routed through `targetsForQuery` (read-gated → ADR-008 violation). A cross-Star caller is refused at the query-subscribe boundary.
- [ ] **A roster push does NOT trigger a query-data rerun** — firing `#broadcastPresence` re-broadcasts the roster without re-evaluating the query or incrementing the data rerun/commit count (debug-sink transient marker — the roster-only invariant).
- [ ] **Mesh-legal transport** — grep-verify no raw `env.NEBULA_AUTH_REGISTRY`/`env.PROFILE` stub access added to `apps/nebula/src` Star/DevStudio/ResourceDataPlane (the `profileId` rides `callContext`; no registry hop).
- [ ] Core reds run in the **Star** resource test-app too (not only DevStudio); `it.skip` with the blocker named if deferred.

## Non-goals
- **An independent "watch a query's roster without subscribing to its data" channel** — deferred until a consumer (e.g. an admin dashboard of "who's active in each chat") actually needs it. Chat, the near-term consumer, subscribes to the query it wants the roster of, so audience == content; a separate `PresenceSubs` registry would just duplicate `QuerySubscribers`. When such a consumer materializes, the roster projection here is the reusable piece.
- **Display resolution (`profileId → name/nickname/picture`)** — the consumer's job ([chat](nebula-chat-history-multiuser.md)) via the built `subscribeProfile`; presence delivers only the raw `{ sub, profileId }` set.
- **Single-resource presence** ("who's viewing resource X", vs a query roster) — a later add; it would live on the single-resource `Subscribers` table (add `profileId` there the same way), not this query-roster path.
- **Org-tree presence** ("who's viewing the org tree now") — the org tree is delivered on the **separate `TreeSubscriptions` registry** (`subscribeTree`, [star.ts](apps/nebula/src/star.ts)), whose viewers are never rows in `QuerySubscribers`, so it **cannot** ride this query-sub roster. A deferred non-goal that would **reuse the roster projection on `TreeSubscriptions`** (exactly as single-resource presence reuses `Subscribers`), not a consumer of this channel.
- **Presence UI** (online/typing/read-receipts) + **anti-flap / debounce / push coalescing** — later; the collaboration-first surface, held out per § Why multi-user (build coalescing only when a roster is displayed and the O(N)-per-join/leave fan-out or WS-toggle flapping actually bites — likely client-side, only-when-displayed).
