# A cross-origin browser request is refused, without anyone maintaining a list

**Status:** ⏸️ **ON HOLD 2026-08-13, the same day it was drafted — the near-term protection is being delivered a cheaper way, and this file is the LATER, BIGGER version of it.** Never reviewed; `/write-task` Pass 1 only, phases deliberately unwritten, MUST NOT be built from.

**What replaced it, and what did not.** [`../nebula-registry-route-guards.md`](../nebula-registry-route-guards.md) § *The open routes state their origin requirement* now carries a `sameOriginGuard` **step** in `nebula-auth`'s own route table, covering the unauthenticated self-signup routes — which is where the protection actually bites. That needs no change to a published MIT package, so it costs no docs, no semver and no release. **What this file still uniquely holds** is the *package* version: a named `'same-origin'` variant on `@lumenize/routing`'s `CorsOptions`, which is the only shape that also reaches the **`/gateway/` WebSocket upgrade** and gives the whole Worker one posture from one value.

⚠️ **Resume when the guard wants to become the posture** — the trigger is wanting origin refusal on the WS upgrade, or a second consumer outside `nebula-auth`. At that point the `nebula-auth` guard is what gets **deleted**, not extended; that deletion is this file's real cost, and it is small on purpose. ⚠️ **Its § *Context and current state* fates are written against a world with no `sameOriginGuard` and are stale on resume** — re-derive them rather than trusting them.

**Objective — `routeDORequest` gains a CORS posture that refuses a cross-origin browser request without being told which origins are legitimate, and Nebula runs it in production.** The posture compares the caller's `Origin` against the origin the caller addressed, so it needs no configuration and holds for a hostname nobody enumerated.

Three goals, in the order they matter. Each carries how it goes wrong today:

1. **A cross-origin browser request is refused before the handler runs — on every surface, including the WebSocket upgrade.** Today production ships `cors: false`, which disables the check rather than restricting it: a disallowed origin's simple request reaches the handler, and for Registry routes potentially the singleton, with only the *browser* discarding the response afterward. On the `/gateway/` WebSocket upgrade browsers enforce nothing at all, so today there is no origin check anywhere in the system.
2. **The posture holds for a domain nobody enumerated.** Today the only non-trivial form is `{ origin: string[] }`, and `buildCorsOptions` is structurally incapable of emitting anything else — it splits a comma-separated string. Every custom domain a tenant attaches would need a config entry and a deploy, which is the shape that cannot survive self-service.
3. **The test lanes stop being wired around the absence of a check.** Today the `ui-smoke` lane's setup depends on CORS being off and explicitly forbids both obvious alternatives — adding the vite port to an allowlist, or bypassing the proxy — because the only configuration an allowlist could live in is `apps/nebula/wrangler.jsonc`, the production one. A posture needing no configuration removes that dilemma rather than resolving it.

## Context and current state

**Built already**, and each part has a different fate.

- **The CORS helpers in `@lumenize/routing`** — `CorsOptions`, `isOriginAllowed`, `applyCorsPolicy`, `addCorsHeaders`. ⇒ **Extended, not replaced.** The union gains one variant and `isOriginAllowed` gains one branch; `applyCorsPolicy` and `addCorsHeaders` are untouched.
- **The server-side-rejection design itself** — refuse before the handler, `204` on a preflight from a disallowed origin, refuse a WebSocket upgrade before upgrading. ⇒ **Carried over unchanged**, and it is what makes this additive: the work supplies a new way to *decide*, never a new way to refuse.
- **`applyCorsPolicy`'s `!requestOrigin` short-circuit** — a request with no `Origin` header passes in every mode. ⇒ **Carried over unchanged and deliberately**; § *Design intent* states why it is load-bearing rather than an oversight.
- **A second, structurally identical `CorsOptions`** at `packages/auth/src/types.ts`, declared locally while the same package's `create-auth-routes.ts` imports the one from `@lumenize/routing`. ⇒ **Fate is an open question below** — a variant added to routing's union does not reach it, so `@lumenize/auth`'s documented option surface silently diverges from its own router's.
- **`buildCorsOptions` in `apps/nebula/src/entrypoint.ts`**, whose output feeds all three router calls (nebula-auth, `/gateway/`, direct-DO). ⇒ **Changes shape** — from "allowlist or nothing" to "same-origin, plus any configured extras". The single-value-for-three-callers property is carried over and is what gives the whole Worker one posture.
- **The production setting** — `LUMENIZE_APPROVED_ORIGINS: ""` in `apps/nebula/wrangler.jsonc`. ⇒ **The empty-means-off behaviour is left behind.** The variable survives with a narrower meaning: origins allowed *in addition to* same-origin.
- **Two browser test lanes, wired differently** ⇒ **both adapted, and not by the same change.**
  - **`test/chromium`**, via `dynamicEnvProxyPlugin` in `apps/nebula/vitest.config.js`: proxies with `changeOrigin: true` *and* already overwrites the forwarded `Origin` with a literal localhost value, for the stated purpose of satisfying a server-side origin check. ⇒ **The rewrite survives, retargeted** — only the value it presents changes, and it can be derived from the proxy target the plugin already reads per request.
  - **`test/ui-smoke`**, via the Studio's own proxy in `apps/nebula-studio-ui/vite.config.ts`: three entries with `changeOrigin: true` and **no** `Origin` rewrite of any kind. ⇒ **Needs a mechanism it does not currently have in any form**; which one is an open question below.
- **`packages/mesh`'s browser lane** passes neither `approvedOrigin` nor a `cors` option. ⇒ **Left alone** — checked 2026-08-13, and it is the evidence behind the default-stays decision.
- **`packages/nebula-auth/test/nebula-auth-cors.test.ts`**, covering the `false`, allowlist and permissive modes against the router. ⇒ **Adapted, and gains the new mode.**
- **`website/docs/routing/cors-support.mdx`**, which teaches every `CorsOptions` form and states the non-standard server-side-rejection behaviour. ⇒ **Adapted.** ⚠️ The blog post that argues this design is a **dated artifact and MUST NOT be edited** (`blog-posts-frozen`); the docs page is the only place the new mode is taught.

## Design intent, constraints, and future state

**The comparison target is the origin the request addressed — `new URL(request.url).origin`.** In Workers that value is built from the request's `Host` / `:authority`, and Cloudflare's routing layer is what constrains it: a request only reaches this Worker if its hostname matched a route or custom domain bound to it. That is the invariant — *the hostname was resolved against this Worker's own bindings* — not the incidental fact that today's hostname list is short. It is also why the posture extends to custom domains at no cost: attaching a domain is what makes `url.origin` able to hold it.

**This repo already trusts that value on a higher-stakes path, which is the strongest available evidence that it is sound.** `worker-token.ts` and `nebula-auth-registry.ts` build the **emailed magic-link URL** from `url.origin`. If it were attacker-controllable, Nebula could be made to mail a login link pointing at someone else's host — a strictly worse outcome than a CORS bypass. ⚠️ **Checkable claim:** every existing `url.origin` read reaches a magic-link or claim URL, and none reaches an authorization decision.

**Soundness rests on the browser setting both sides and script forging neither.** `Origin` and `Host` are forbidden header names in the Fetch spec, so page JavaScript can set neither. A page on one origin fetching another sends its own `Origin` and the target's `Host`, and has no way to make them agree — the only client that can make them agree deliberately is a non-browser client. ⚠️ **Checkable claim:** the refusal therefore discriminates browser-originated cross-origin traffic and nothing else.

**This is a fence, not an authorization boundary, and the `!requestOrigin` short-circuit is the reason to say so out loud.** A request omitting `Origin` passes in this mode exactly as in every other, so the posture refuses only callers that *declare* a different origin. Forging an omission is free, so refusing Origin-less requests would cost every non-browser caller — curl, server-to-server, the `/live` harness — while stopping nobody. ⇒ **What this buys is that casual and accidental cross-origin use fails, that the singleton stops doing discardable work, and that the WebSocket upgrade has an origin check at all.** It buys no authorization; every route's real gate is unchanged.

**The posture composes with configured extras; it is not pure equality.** An origin-changing proxy in the request path legitimately breaks `Origin === url.origin` — that is exactly both test lanes' situation, and would be any future reverse-proxy deploy's. So the mode is *same-origin ∪ configured extras*, with the extras empty in production. A mode with no escape valve would force every proxied deployment back onto a hand-maintained allowlist, which is goal 2 lost.

**An equality match decorates nothing, which makes this mode a pure inbound guard rather than a guard plus a decorator.** Every other flavour is both: it decides inbound, then stamps `Access-Control-Allow-Origin` on the way out, because a *cross-origin* caller it permitted needs that header or the browser blocks the read. Same-origin has no such caller — a same-origin request is not subject to CORS, so the browser never looks for the header. Emitting it is inert, and the `Vary: Origin` that `addCorsHeaders` sets alongside it is **not** inert: it fragments cache keys on every response the deployment serves. ⇒ **An equality match yields no allowed-origin and nothing is wrapped.** ⚠️ **The extras are the asymmetric arm and MUST NOT inherit that** — an origin permitted by configuration genuinely *is* cross-origin, so it needs the headers exactly as the allowlist form does today. One mode, two outcomes, discriminated by which arm matched.

**One value, three callers, one posture.** `buildCorsOptions` produces a single `CorsOptions` that `entrypoint.ts` threads to the nebula-auth router, the `/gateway/` route and the direct-DO route. That property is why the posture is adopted in the package rather than at any one call site: `/gateway/` is the WebSocket surface, where browsers enforce nothing, so a fix that reaches only `/auth/*` would protect what browsers already protect and skip what they do not.

### Constraints

- **`.claude/rules/security.md`** — CORS is never an authorization boundary. This work changes no authz decision, adds no claim, and touches no guard. Anything here that reads as a security *control* is misread.
- **`.claude/rules/documentation.md`** — `cors-support.mdx` is already `.mdx` and stays; the sidebar entry exists.
- **`workflow.md` § *Evaluating alternatives*** — the interim to avoid is a same-origin check hardcoded in one router, which leaves the other two callers on the old posture and must later be unlearned from whichever surface got it first.
- **`blog-posts-frozen`** — the CORS blog post is a dated artifact; it is not updated when this lands.
- **Additive to a published surface.** `@lumenize/routing` is MIT with no `private` flag, so `CorsOptions` is public API. A new union member is additive and breaks no existing caller; the *default* is what would break one, which § *Decisions* settles.

### Open questions

1. **Which mechanism adapts the `ui-smoke` lane — flip `changeOrigin` to `false`, or add an `Origin` rewrite?** They are not equivalent, and the difference is not in the CORS outcome. Flipping `changeOrigin` makes the worker see the *browser's* `Host`, so `url.origin` becomes the vite origin — and `url.origin` is what builds the emailed magic-link URL, so dev links would start pointing at the SPA rather than at the worker. Adding an `Origin` rewrite (the shape the chromium lane already has) leaves `url.origin` untouched. ⚠️ **Gates dev magic-link behaviour**, and one of the two options may be an improvement rather than a cost — decide it deliberately rather than by which edit is smaller.
2. **What happens to `@lumenize/auth`'s duplicate `CorsOptions`?** Delete it and re-export routing's, or leave it and accept that the two drift from this task onward. ⚠️ **Gates whether this task touches a second package**, and the answer changes the blast radius rather than the design.

### Design considerations

- ⚠️ **Design consideration: the variable name outlives its meaning.** `LUMENIZE_APPROVED_ORIGINS` currently names *the* allowlist; afterwards it names *additional* origins beyond same-origin. A rename is a `calibration.md` §5 candidate the first time someone has to explain it, and it gates nothing here.
- ⚠️ **Design consideration: an async validator is NOT needed and must not be added speculatively.** A policy that consults storage — "has some tenant verified this domain?" — would require `isOriginAllowed` to return a `Promise`. Same-origin needs no lookup at all, so this work supplies no evidence that the async form is wanted.
- ⚠️ **Design consideration: `Origin: null`** (sandboxed iframes, some cross-origin redirects) is refused under this mode, since `null` equals no real origin. That is a behaviour change from `false` and belongs in the docs page rather than being discovered.

## Decisions

⏳ **Started during the Pass-1 gate; the open questions above are deliberately absent — only settled things go here.**

| Decision | Rejected alternative — why |
|---|---|
| **A named `'same-origin'` variant on `CorsOptions`** | A hand-rolled predicate closure in `entrypoint.ts`. It would live in one caller, so the `/gateway/` and direct-DO routes need it copied or threaded; and the package is where the documentation, the tests and the existing three forms already are. A fourth union member costs less than the closure and is the thing that can be taught. |
| **Not hardcoded into `nebula-auth`'s router** | Hardcoding the check where the Registry routes are dispatched — it leaves `/gateway/` on the old posture, which is backwards: that is the **WebSocket** surface, where browsers enforce nothing, so it is the one place server-side origin checking is the only control rather than a second one. |
| **`routeDORequest`'s default stays `false`** | Making `'same-origin'` the default. `packages/mesh`'s browser lane passes no `cors` option and proxies with `changeOrigin: true`, so it would start refusing on upgrade (checked 2026-08-13) — and a published package that changes *refusal* behaviour for callers who configured nothing is a semver-major this task needs nothing from. Nebula opts in explicitly; that is the whole adoption. |
| **The posture is same-origin ∪ configured extras** | Pure origin equality with no escape valve — an origin-changing proxy in the path breaks equality legitimately, which is both test lanes today and any reverse-proxy deploy later. Without extras those deployments fall back to a hand-maintained allowlist, losing goal 2. |
| **The `!requestOrigin` short-circuit is carried over unchanged** | Refusing requests that omit `Origin` — it would break every non-browser caller (curl, server-to-server, the `/live` harness) while stopping nobody, since a client that can forge `Origin` can omit it instead. Carrying it is also what keeps this a fence rather than something that reads as an authorization control. |
| **The production posture changes in this task, not a later one** | Landing the variant and adopting it separately — an unadopted variant is a published API with no consumer, and the test-lane changes only make sense against a posture that is actually on. |
