## B — cross-node `actAs` mechanism (trigger: first external/remote agent)
The general append-an-actor-on-an-outgoing-mesh-call mechanism. **No near-term consumer** (chat's `actAs` is in-DO; multi-agent is post-pre-alpha) — verified `NEBULA_SUB`/`actAs` exist nowhere in source. Build when a *remote* agent (e.g. a Node `LumenizeClient` bridge) must nest itself across a hop.

- **Placement (grounded, ADR-007-safe)**: an `actAs?` field on `CallOptions` (`packages/mesh/src/types.ts`), handled once in the shared `buildOutgoingCallContext` (`packages/mesh/src/lmz-api.ts`) — `createLmzApiForDO`/`ForWorker` both route through `callShared` → `buildOutgoingCallContext`, so DO/Container/Worker get it by composition (no LumenizeDO-only site). `LumenizeClient` *mirrors* `buildOutgoingCallContext` (sanctioned ADR-007 deviation) — it needs the option for the client-side agent case.
- **Reaches provenance only via a representation decision**: `#buildChangedBy` (`apps/nebula/src/resources.ts`) reads **only** `originAuth.claims.act`. So either (a) `actAs` mutates `originAuth.claims.act` — collides with the "originAuth is JWT-verified/immutable every hop" invariant (mesh.md / ADR-003) — **or** (b, *lean*) `actAs` appends to a **separate growable callContext field** and `#buildChangedBy` is taught to compose `originAuth.sub` + that field (keeps verified claims clean; serves the in-DO chat path too). Settle before building.
- **Secure by construction**: append-only; authz keys off the authority `sub`, which `actAs` never touches → cannot escalate. Authority inherited from the verified `originAuth`. **Constraint — the `actAs` value must be a trusted server-side value** (a platform constant like `NEBULA_SUB`, or the node's own identity), never client-supplied: a forged actor id can't escalate but would falsify provenance.
