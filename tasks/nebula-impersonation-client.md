# Impersonation sessions — a client that acts as another person

Reviewed via `/review-task` first (Stage 1 twice — 21 then 26 findings; Stage 2 once — 32 findings), then built and put through the `/build-task` verifier panel, which failed two phases and found two blockers; both are fixed and covered. **No criterion is deferred.** The terminal-re-mint-failure test that was briefly `it.skip`'d is delivered — `connect()` is public and reversible, so a test can drive the re-mint the cascade otherwise prevents. ⚠️ **The `/live` deferral in Phase 4 was reasoned on the wrong axis** and is corrected: it weighed only the RUNG ("rung 1 adds only the email transport"), which is true and beside the point — `/live`'s value here is a real runtime and a **real clock**. `harness/scenarios/impersonation-expiry.ts` now drives a genuine token lapse and PASSES, with both mutations red (no re-mint → a real 401; renew off the cookie → the child silently becomes the admin). ⚠️ **A second false claim in that same header — "pool-workers cannot let time pass" — was measured and is FALSE**: `vi.setSystemTime` moves the clock **both** the Worker and the DO see, so `impersonate-lifetime.test.ts` now also drives a genuine expiry in-lane (jump verified load-bearing: removing it reds the test). `/live` keeps its place on **fidelity** — an unpatched clock — not capability. `harness/scenarios/impersonation-lifecycle.ts` covers the deterministic behaviours, including the dangerous **same-scope** child logout — reached by inviting a second identity into the universe through the real email loop, which an earlier note wrongly called impossible here (mutation: drop the `#mintedFrom` branch → the admin's real refresh cookie 401s). Drafted 2026-07-29 via `/write-task`.

**Objective — `impersonate()`: an admin's client can produce a working `NebulaClient` that acts as another person.** What lands is that capability, plus the retirement of the two hand-rolled test helpers that stood in for it; the admin-debug UI that will consume it is a Non-goal. The question it exists to answer — *why can't this user do X?* — becomes answerable by driving the app as them.

## Context and current state

**Built already.**

- **The endpoint.** `/auth/{callerScope}/mint-narrower-token` (`mintNarrowerToken`, `worker-token.ts`) mints a token whose `sub` is the subject and whose `act` is the caller, under an ordered gate chain — root identity, self-narrow rejection, caller reach, admin bit, subject exists, eligibility, subject-reach mirror, in that order (the ordering is itself a disclosure decision, ADR-008). It is the only **production** producer of a JWT `act` claim (`create-nebula-test-token.ts`'s `actor` option is the rung-3 exception, used by `mint-narrower-token.test.ts` to synthesise an act-bearing caller) — **the production qualifier is load-bearing**: the planned `prependActor` ([nebula-galaxy-collapse-and-chat.md](nebula-galaxy-collapse-and-chat.md)) composes an `act` chain onto a `changedBy` **record**, never onto a signed token, so `claims.act` remains an exact signal for *this is an impersonation session*. Fully tested; see `tasks/archive/nebula-mint-narrower-token.md`.
- **The record.** `executeScopeDeletion` stamps `actingToken` — the full verified claims including the `act` chain — on scope deletion ([ADR-016](../docs/adr/016-record-the-acting-principal.md)), so a destructive action taken under impersonation already names both parties.
- **The transport.** `LumenizeClient.authedFetch` is `protected`, injects the in-memory token as `Authorization: Bearer`, refreshes when it is missing or near expiry, and retries once on a 401 — `NebulaClient`'s `scopes` namespace is built on it, keeping the JWT inside the client. ⚠️ **It has no test coverage, direct or indirect.** ✅ *Checkable:* no test file references `authedFetch`, and nothing outside `apps/nebula-studio-ui/src/App.vue` drives `client.scopes.*` — so its refresh-on-expiry, its retry branch, and its de-duplication with the WS-connect refresh are today exercised only by a human clicking through Studio. This task makes `impersonate()` its second caller and its first tested one, and the paths it leans on are exactly the untested ones.
- **Three teardown doors, none of which chain.** `LumenizeClient[Symbol.dispose]()` is **sync** and calls only `disconnect()` — this is what `using` hits in tests. `NebulaClient.dispose()` is **async**, does engine teardown, and is what production calls (`create-nebula-client.ts`). `NebulaClient.logout()` — the actual *end my admin session* action — revokes the cookie and calls `disconnect()`, reaching **neither** dispose door.

**Missing.**

1. **A way for a client to RENEW a token that did not come from its cookie.** A `NebulaClient` can already be *handed* one: `accessToken` is public on `LumenizeClientConfig`, survives the `Omit` (which lists only `refresh` and `gatewayBindingName`), and seeds `#accessToken`, `#claims`, and the derived `instanceName`. What it cannot be told is where the **next** token comes from — `refresh` is hard-coded to the cookie POST, and the constructor spreads the caller's config and *then* overwrites `refresh`, so it cannot be supplied even by casting. ⇒ a handed token works for at most `ACCESS_TOKEN_TTL`, after which the client refreshes **off the cookie**. For a **same-identity** token that is harmless — the cookie returns the same person, which is why several suites hand one over legitimately. For a **narrower** token it is a silent identity swap: the child becomes the **admin** while `instanceName` still names the subject. That is the gap this task closes; the `accessToken` seam itself stays open and out of scope (see Decisions, which owns that rationale).
2. **A lifetime model for a token that cannot be refreshed from a cookie.** The minted token dies with `ACCESS_TOKEN_TTL`; nothing renews it, and the built-in refresh failure path raises `LoginRequiredError`, which `NebulaClient`'s connect path turns into `onLoginRequired`.
3. **A production path the tests can share.** Two suites hand-roll `refresh: async () => ({ access_token, sub })` over a raw `LumenizeClient` — `mint-narrower-token-payoff.test.ts` and `profile-do.test.ts`. They are the only two such **helpers** in `apps/nebula` (four call sites between them — Phase 4 works per call site), and they exist solely because item 1 has no answer.

## Design intent, constraints, and future state

The beneficiary is a solo user-developer diagnosing their own app for a tenant who reported a problem. The design is authority-**reducing**: faithfulness gives the admin the subject's permissions, which are narrower than their own.

`await client.impersonate(sub, activeScope, opts?)` resolves to a **full `NebulaClient`** whose identity is that person. Both positional parameters are required; `opts` carries only `ttlSeconds`, which the child reuses on every re-mint. Full is the load-bearing word: every existing surface (`resources`, `orgTree`, `subscribe`) works on it unchanged, which is what lets a test and the Studio exercise one path.

### The parent is the credential

The returned client holds a private `#mintedFrom` handle to the client that produced it, and re-mints by calling **the same private mint helper on that handle that `impersonate()` itself calls**. One mint path, so the first mint and every re-mint cannot drift on body shape, URL, or error handling — and the child depends on the parent's *capability to mint*, never on how the parent talks to the endpoint. Five properties follow from that one fact, and they are the reason this shape was chosen over holding a fixed token:

- **No new durable credential exists anywhere.** The child's ability to act is derived entirely from the parent's in-memory session; nothing is written, cookied, or independently stealable.
- **Revocation propagates — on the SUBJECT side at every re-mint, on the CALLER side at the parent's own.** Every re-mint re-runs the endpoint's full gate chain, and that chain reads the **registry** for the subject but the **caller's token** for the caller. So a moved or deleted subject ends the session at the next re-mint; a **demoted admin** is caught when the *parent* next refreshes off its cookie (≤ `ACCESS_TOKEN_TTL` plus KV propagation), which is the parent-session bound the last bullet claims. Both are bounded, but not by the same clock — and stating one bound for both is what makes `ttlSeconds` look like a revocation control it is not (Phase 1).
- **Readiness follows the parent's *credential*, not its *connection*.** `authedFetch` obtains a token from the refresh cookie on its own path, so a parent that is **disconnected or holding an expired token** still mints. ✅ *Checkable:* `LumenizeClient` shares one in-flight refresh between the WS-connect path and `authedFetch`, and neither requires the other to have run. ⚠️ **One precondition, and it is about the NAME rather than the credential:** the parent must already have an `instanceName` — it has connected at least once, or was constructed with one — because the child's name derives from the parent's tabId, which exists nowhere but inside that name. A never-connected parent is therefore out of scope; no consumer needs it (a subject picker cannot render before the admin's session is up).
- **Lifetime follows the parent *object*, through ONE named teardown seam.** All three of the parent's teardown doors route through it; a parent losing its socket does not. These are different events and the distinction is user-visible — a network blip must not end an impersonation session. ⚠️ Naming one seam is what makes the cascade real: hooking only `[Symbol.dispose]()` satisfies every `using`-based test while the *production* path (`dispose()`) and the actual end-of-session (`logout()`) both leak a child holding an open socket.
- **Duration is bounded by the admin's browser session**, re-authorized every `ACCESS_TOKEN_TTL`. Pinned as intended semantics by Larry, 2026-07-29.

When a re-mint terminally fails, the child terminates. The invariant: **the admin's own session is untouched by the end of an impersonation session** — and what secures it is that the child does not hold the admin's `onLoginRequired`, so mesh's terminal path has nothing to call. The protection is the absent handler, not the shape of the error.

### Two sessions are two clients

A second identity requires a second client object, because the subscriber tables key on the per-client id. ✅ *Checkable:* `clientId` **is** the client's `instanceName` (`callChain[0].instanceName`); `QuerySubscribers` keys on `(queryHash, clientId)` and carries `sub` + `profileId`, and the per-resource `Subscribers` keys on `(resourceId, clientId)` and carries `sub` — so in both, `clientId` is the only identity discriminator, and one connection carrying two identities owns one row per query/resource with two answers to "who is here". This is why the child's **deterministic, scope-distinguished name** (Decisions) is what makes two sessions two subscribers: distinctness comes from that name, not from auto-generation, which the child deliberately bypasses.

### The claims are the API

The child exposes nothing new. `client.claims` already answers both questions the caller has, structurally: top-level `sub` and `profileId` are the person being acted as, and the presence of `act` is what makes this an impersonation session. ✅ *Checkable:* `NebulaClient` re-declares `claims` as non-null on the strength of the factory's `ready` resolving after the first refresh — a client from `impersonate()` must preserve that guarantee, since every blessed example writes `client.claims.sub` unguarded.

### Authorization stays on the server

This task changes no authorization. The endpoint's gate chain remains the enforcement, and the client adds no check that could disagree with them. The single client-side refusal — that impersonation does not chain — is decidable from the client's own claims, is enforced independently by the endpoint's root-identity gate, and exists to convert a structurally impossible call into an accurate message instead of a 403 that reads as a problem with the subject.

⚠️ **`security.md` delegation rule (1) binds here**: the client reads `act` for presence only, never to decide an authorization outcome, and the licensed exception list stays at one member (the Profile owner branch).

### Retiring the workaround is the point

The two hand-rolled helpers are not incidental cleanup — they are the reason this task is being built now rather than backlogged. They are currently the only worked example in the repo of "drive a DO as an impersonated user", so the next person needing that copies them, and the shape ossifies. Moving both onto `impersonate()` while there are exactly two of them is the whole argument for the timing.

The gain is fidelity, not tidiness: those helpers construct a raw `LumenizeClient`, so they exercise a path the Studio can never take, and any defect specific to a `NebulaClient` carrying a narrower token is invisible to them.

### Constraints

- [ADR-009](../docs/adr/009-real-auth-path.md) — the adopted tests stay **rung 2**, as the whole `baseline` lane is: real server issuance through the real endpoint, no email transport, no client mint. The load-bearing half is that the token under test comes from the **real endpoint via a real admin's real session** — rung 1 would add only the email hop. ⚠️ **Do not write "rung 1" anywhere here.** `browserLogin` reads the magic link out of the response and is gated by the `NEBULA_AUTH_TEST_MODE` binding alone, which is ADR-009's rung 2 verbatim; the label is currently wrong in two test headers and in `testing.md`, and Phases 4 and 5 fix those.
- [ADR-016](../docs/adr/016-record-the-acting-principal.md) — already satisfied by the endpoint and the registry record; this task adds no new destructive action.
- `.claude/rules/security.md` delegation rules (1) and (2) — both hold unchanged (above).
- `.claude/rules/mesh.md` — the child is an ordinary client; `impersonate()` reaches the `/mint-narrower-token` **endpoint** over `authedFetch`, matching how `scopes` reaches nebula-auth's registry routes. The two names sit at different levels on purpose: the endpoint mints a **token** and asserts a checkable property of it; the client method returns a **client** and names the use case.
- CLAUDE.md § package feedback — the `Omit` that closed a footgun also closed the capability; the resolution keeps the `Omit` and adds a factory, so callers never supply a token and scope that can disagree.

### Future state

This is the client capability the admin-debug UI needs; the UI itself is out of scope. It also makes an impersonated session available to any future test that needs to observe the app as a specific person.

⚠️ **Design consideration:** [ADR-017](../docs/adr/017-the-url-is-the-view-state.md) is the other half of the support flow — an admin needs the subject's `activeScope`, and Studio's URL does not yet carry it (`backlog.md` § Nebula Studio UI). Neither task gates the other.

⚠️ **Design consideration:** `#mintedFrom` / `#minted` are private with no public accessor, which keeps the option of changing the parent-child representation later without a public break.

### Open questions

None. Every decision this file depends on was settled in conversation on 2026-07-29 — the API shape and its name, both parameters explicit and required, expiry via re-mint, the dispose-vs-disconnect distinction, exposing nothing beyond `claims`, refusing to chain, and allowing codegen from an impersonated session.

## Decisions

| Decision | Rejected alternative — why |
|---|---|
| **`await client.impersonate(sub, activeScope)` returns a full `NebulaClient`** | `client.impersonation.{methods}` as a namespace property — a property cannot take the subject, and an admin may want two subjects live at once. Worse, every existing namespace (`resources`, `orgTree`, `scopes`) is a stateless facade over the *same* identity, so `client.impersonation.resources` would look symmetric with `client.resources` while differing in the one thing that must never be subtle. Also rejected: `getNarrowerPermissionedClient()` — names the *token's* property rather than what the caller wants, and coins "permissioned". Also rejected: returning a **restricted subset** exposing only what impersonation "needs" — tests would still reach for a raw `LumenizeClient` for anything outside the subset, so the workaround this task exists to retire would survive it. *Full* is therefore load-bearing: every existing surface (`resources`, `orgTree`, `subscribe`) works unchanged, which is what lets a test and the Studio exercise one path. |
| **A second identity is a second client object** | A mode flag on one client (`switchToImpersonation()`). It cannot produce a second `clientId`, so it either tears down and rebuilds the connection on every toggle — losing every subscription, twice — or writes one subscriber row with two answers to "who is here". Independently: any reference held across a switch silently changes identity. |
| **The parent is the credential — the child re-mints through it** | A fixed, non-refreshable token expiring with `ACCESS_TOKEN_TTL`. It needs a new lifecycle concept for ordinary expiry, and it grants up to a full token lifetime of *stale* authority with no re-check. Also rejected: having the endpoint set a Path-scoped refresh cookie for the impersonated scope — that manufactures a 30-day, independently stealable durable credential for someone else's identity, which is the wrong lifetime for this capability. |
| **`impersonate()` is a factory; `refresh` stays unsuppliable by callers** | Exposing `refresh` publicly on `NebulaClientConfig`. A public `refresh` lets any caller build a client whose token and `authScope` disagree; a factory supplies both from one mint response, so they cannot diverge. ⚠️ The factory rests on **`refresh`** being closed — **not** on `accessToken`, which is NOT in the `Omit` and stays open, with a number of legitimate same-identity consumers (Phase 4's criterion covers them by property rather than by count). Closing `accessToken` is deliberately out of scope and would buy **no** security: `Omit` is compile-time only, the browser is the user's machine, and an exploit needs a validly signed token either way — it is a developer footgun in our own code, not an attack surface. Simplifying it away is filed under Testing & Quality in the backlog, which owns this rationale. |
| **The child re-mints via the parent's private mint helper** | The child calling `#mintedFrom.authedFetch(...)` directly. Two mint paths free to drift on body shape, URL, and error handling — the seam `access-claims.ts` exists to hold closed. It also makes the child depend on the parent's *transport* rather than its *capability*. |
| **Both positional parameters required and explicit; `ttlSeconds` an optional third-argument option** | A third positional parameter — an options object keeps the two required arguments unambiguous and leaves room to extend. Also rejected: deriving `activeScope` from the subject's identity row — mechanically possible (`Identities.universeGalaxyStarId` is single-valued), and wrong: `activeScope` is the token's `aud`, bounded by the subject's reach rather than equal to it, so deriving picks the **widest** valid value — the wrong end of the range for a debug session, which wants the specific star where the trouble is. It fails by *succeeding at the wrong scope*. Also rejected: optional-with-derive-as-default, which reproduces that for anyone who omits it. |
| **No client-side validation of `activeScope`** | Pre-checking reach in the client. The client cannot know the answer — it depends on registry state — so the check would be both a guess and a duplicate of a security decision. |
| **The chain refusal IS thrown client-side** | Relying on the endpoint's 403 alone. That reads as "you are not authorized to impersonate this person", pointing a developer at the subject and their permissions when the real answer is that impersonation does not chain. ⚠️ Distinct from the row above: this is decidable with certainty from the client's own claims, is not a guess, and the endpoint still enforces it. |
| **The child exposes nothing beyond `claims`** | An `impersonating` getter. `claims` already answers both questions structurally — top-level `sub`/`profileId` is who you are acting as, and the presence of `act` is what makes it an impersonation session. Naming a convenience before there is a caller is how `actFor` happened, and the obvious names (`actingAs`, `viewingAs`) are the role-noun disease. |
| **Cascade on the parent's TEARDOWN SEAM — reached by `dispose()`, `[Symbol.dispose]()` and `logout()`; never on a transient `disconnect`** | Hooking `[Symbol.dispose]()` alone. It is the door `using` hits, so every test would pass while production — which calls `dispose()` — and `logout()`, which reaches neither, both leak a child that keeps re-minting until the parent's access token lapses. Also rejected: hooking a **connection-state transition**. Disposal is intentional end-of-session; a blip is transient, and firing on the transition out of `'connected'` would silently end the admin's impersonation session, which reads as a defect in the endpoint. ⚠️ **The state to reason about is `'reconnecting'`, not `'disconnected'`** — a transient close never reaches `'disconnected'` (`#handleClose` → `#scheduleReconnect()` → `'reconnecting'`), which is set only by the deliberate `disconnect()` and by terminal auth failure. Stating the rejected alternative as `'disconnected'` made it un-testable, since hooking that state is *indistinguishable from correct* on a blip. ✅ *Checkable:* all three teardown doors route through `disconnect()` and no transient path does, so the cascade is one hook at that seam. |
| **`logout()` on a CHILD is child-only teardown — dispose + deregister, never a cookie revoke** | Letting the child inherit the parent's `logout()`. `authScope` **is** the refresh-cookie path (`security.md` § two-scope model) and is the child's only reader of it, so an inherited `logout()` revokes the **admin's** 30-day refresh token — inverting *the admin's own session is untouched*. This is the **one carve-out to the FULL-client row above**, and it is not a subset: a child holds no refresh cookie, so `logout()`'s revoke half is vacuous and the rest *is* dispose. Also rejected: pinning `authScope = activeScope` — safe only while the two differ, and an admin who logged in *at* the scope they impersonate into gets an exact cookie-path match, which is the ordinary support shape. Also rejected: throwing — it fights the FULL-client decision and makes a generic sign-out button throw instead of doing the sensible thing. |
| **Deregistration is explicit, on BOTH dispose and terminal disconnect** | `WeakSet`/`WeakMap` for the children — not iterable (`[Symbol.iterator]` is `undefined`, `for..of` throws), so the cascade cannot be written at all. Also rejected: `Set<WeakRef>` — it trades determinism for GC timing in a mechanism (`using`) chosen *for* determinism, and it is inert where it matters: an undisposed child holds an open WebSocket, so it stays reachable and the weak reference never goes stale. The leak it appears to fix is a connection, which GC does not close. |
| **A terminal re-mint failure REUSES `LoginRequiredError`; the admin is protected by the child not inheriting `onLoginRequired`** | Giving the failure its own error class. Two mesh paths defeat it. `#connectInternal`'s catch is `instanceof LoginRequiredError` with a **deliberate transient default** (its comment: *"the more precise (un-spoofable) test with the safer transient default"*), so a new class falls to `#scheduleReconnect()` and the child **loops instead of terminating**. And `#handleTokenExpired` **discards** what was thrown and manufactures its own `LoginRequiredError`, so even where it terminates the class never reaches anyone. ⇒ a distinct class loops on one path and is erased on the other. Reusing `LoginRequiredError` is correct on **both**, because both report only via `onLoginRequired`, which a child does not have. ⚠️ **This reverses an earlier decision, and the reason is worth keeping:** that row's premise was *"the connect path turns it into `onLoginRequired`, bouncing the admin"* — false once the child stops inheriting the handler, which is a **structural** protection rather than a classification one and therefore cannot be defeated by a mis-classification. Also rejected: a generic terminal seam in mesh — it extends a considered mesh decision for a capability with no consumer. Also rejected: the child tearing itself down inside its own refresh — the throw still reaches `#scheduleReconnect()` *after* that teardown and arms a fresh timer, turning termination into a slow endpoint-hitting loop. |
| **Codegen from an impersonated session is allowed** | Blocking it. Doing so requires reading `act` to make an authorization decision — a second exception to `security.md` rule (1), with none of ADR-012's justification (a profile is *global* and its scope authority can be manufactured; codegen is scope-local, where the ordinary model already works). There is also no escalation to prevent: authz keys off `sub`, and eligibility means the caller could do the same thing with their own token carrying *more* authority. |
| **`impersonate()` lives on `NebulaClient`** | `LumenizeClient`. Impersonation is a nebula-auth concept and mesh must not know about it (`mesh.md` § dependency direction). |
| **`ttlSeconds` on the token mints, CLAMPED to `ACCESS_TOKEN_TTL`** | Leaving the re-mint criterion unreachable, or reaching for a test-mode binding. ⚠️ **A clamped TTL is categorically not a test-mode flag** (`security.md`): it can only ever *shorten* a token, so it grants strictly less authority-over-time, bypasses nothing, needs no binding, and is safe — indeed useful — in production, where the admin-debug UI may want a deliberately brief session. Also rejected: an unclamped `ttlSeconds`, which would let a caller mint a long-lived token and is the only shape that could do harm. |
| **The child's `instanceName` is DETERMINISTIC: `${subjectSub}.${parentTabId}.${activeScope with dots as dashes}`** | A random suffix per call. ⚠️ **The segment ORDER is load-bearing, not stylistic** — `LumenizeClientGateway.onBeforeAccept` rejects a name with no `.`, then requires `instanceName.substring(0, indexOf('.'))` to equal the `sub` of the verified JWT, and `NebulaClientGateway` does not override it. So the subject's `sub` must come **first**, and this name works only because a surrogate `sub` is a dotless UUID. Put the tabId or the scope first and the Gateway returns a 403 identity mismatch that reads as a token problem. Everything after the first `.` is free. ⚠️ **A DO name reservation is PERMANENT** — it cannot be deleted, by us or from the dashboard — so a random suffix reserves a fresh Gateway DO name on every `impersonate()` call, forever. Unused reservations cost nothing only because the Gateway is deliberately zero-storage, which makes keeping it storage-less load-bearing. Determinism also means a reload with the same tab, subject and scope reuses one name. Also rejected: letting the child call `getOrCreateTabId` — it reads the *parent's* sessionStorage, the cloned-tab probe fires, and the child **rewrites the tab's stored id**, so the admin's own session silently loses tab identity after a reload. Also rejected: `${subjectSub}.${parentTabId}` without the scope — two live children for the same subject at different `activeScope`s collide, and scope is not otherwise in the name. Also rejected: deduping by (subject, scope) in a keyed `#minted` — it needs a composite key, a scope-distinguishing name anyway, *and* refcounted disposal, for a continuity benefit no consumer has asked for. |
| **Duration is bounded by the admin's session, with no hard cap** | A maximum impersonation lifetime. Deliberately absent — the session is re-authorized against the full gate chain every `ACCESS_TOKEN_TTL` and dies with the tab. Were one ever wanted, the re-mint is the single place it would live. |

## Phases

1. **A `ttlSeconds` request parameter on the token mints, clamped so it can only shorten, and advisory-warned when implausibly short.** `buildNebulaJwtPayload` already accepts `ttlSeconds`; expose it through `mintAccessToken` and accept it on `/mint-narrower-token` and `/refresh-token`, clamped to `ACCESS_TOKEN_TTL` and **validated by an accept-list on TYPE and LOWER bound — an integer ≥ 1, rejected in the handler before the mint** (not a rejection of one sub-case). ⚠️ **The ceiling is CLAMPED, never rejected** — asking for more than `ACCESS_TOKEN_TTL` is a preference the server silently shortens and reports honestly via `expires_in`, which is why the clamp criterion below expects a token rather than a 400. Only shapes that could yield an unbounded or absent `exp` are refusals. This is what makes Phase 3's re-mint criterion reachable, and it is a capability worth having independently.
   - 🛑 **A non-NUMERIC `ttlSeconds` mints a token that NEVER EXPIRES, and a non-positive check does not catch it.** Verified end to end: `access-claims.ts` computes `exp: now + (input.ttlSeconds ?? ACCESS_TOKEN_TTL)`, so a non-numeric value yields `exp: NaN` — and **both** obvious guards pass it, since `NaN <= 0` is `false` and `Math.min(NaN, 900)` is `NaN`. `signJwt` serializes via `JSON.stringify`, which writes `NaN` as `null`; `verifyJwt`'s check is `if (payload.exp && payload.exp < now)`, and a `null` `exp` is **falsy**, so expiry is skipped and the token verifies forever. The client never refreshes it either (`if (typeof exp !== 'number') return false`). ⚠️ **Reachability is worst on the arm this phase adds:** `/refresh-token` is in `AUTH_FLOW_SUFFIXES`, so it is gated by the **refresh cookie alone** — no JWT, no scope check — and its existing body validation is truthiness-only (`if (!body.activeScope)`), which is the precedent a builder copies. ⇒ this is not cosmetic: `security.md` § revocation-is-KV-eventually-consistent names the short access-TTL as **the** mitigation, so an `exp`-less token deletes that bound entirely.
   - **Success (capable of failing) — a malformed `ttlSeconds` is refused, and no path can mint a token without a finite `exp`.** On **both** endpoints, each of `'abc'`, `null`, `{}`, `1.5`, `0`, `-1` returns `400 invalid_request`. Then assert the property that protects the revocation bound directly: every token either endpoint mints has a decoded `exp` that is a **finite number**. **Mutation:** validate with `ttlSeconds <= 0` only → `'abc'` passes the guard, `exp` decodes as `null`, and the finite-`exp` assertion reds. ⚠️ This replaces the weaker "a non-positive TTL is refused", which was the one criterion in this phase with no mutation — and non-positive was never the dangerous case.
   - **Both arms have a distinct consumer — neither is here for symmetry.** `/mint-narrower-token` is the only seam that can age the **child's** token (the child is constructed by `impersonate()`, so no test can hand it one), and `/refresh-token` is the only rung-1/2 way to age the **parent's**, which is what Phase 3's half (b) needs to reach `authedFetch`'s untested refresh-on-expiry branch. Recorded because the `/refresh-token` arm was originally kept on *consistency* grounds, which reads as weak and invites re-litigation; the mechanical reason is the real one.
   - **Sub-goal — warn below `RECOMMENDED_MIN_TTL_SECONDS` (120) at the MINT, advisory and never enforced.** One `debug.warn`, **server-side only**, at the clamp seam above so the two endpoints cannot diverge. Declare the constant in `types.ts` beside `ACCESS_TOKEN_TTL` and import it internally in `worker-token.ts`: **no export change, no new public surface.** The message must name **both** hazards — continuous re-minting, and that a shorter TTL does **not** shorten the caller-side revocation window. Log the requested and effective values plus identifiers only, never the token.
     - ⚠️ **A CLIENT-side warn was considered and deliberately dropped — it buys no coverage and costs public API surface.** It would fire before the request, and the request then trips this one, so **no call path trips one without the other**; the only difference is which console the line lands in. ⚠️ **A secondary clause here said the client "cannot import the constant". That was overstated and is corrected** — the conclusion survives on the no-coverage-gain reason above, which is why the wrong buttress went unchallenged. What is true is that no *currently exported* subpath carries it: `@lumenize/nebula-auth`'s barrel re-exports `NebulaAuthRegistry` → `cloudflare:workers`, and `nebula-client.ts` is deliberately Node/browser-safe (its header: *"import only from /client to keep this module Node-importable in full"*), so a value import breaks the Node harnesses and the Studio bundle at import time — the [[mesh-do-in-light-index-breaks-transform]] failure. The alternatives were a **new** public light subpath, misusing `./testing` (whose header says the split is *"by intent, not by runtime"* — it is an audience label, so production client code has no business there), or duplicating the number and re-creating the drift this sub-goal exists to prevent. ⚠️ **The first of those is cheap, not impossible** — `src/types.ts` imports exactly one type-only symbol from `@lumenize/auth` (erased) and one value from `@lumenize/mesh/client` (already the Node-safe subpath), so it *is* Node-safe today and a `"./types"` entry in `exports` is a one-line change. That is public API surface we chose not to spend for a warn that duplicates a server-side one — a **cost** judgement, which is defensible, rather than a constraint, which was not. **The author-facing guidance moves to `impersonate()`'s JSDoc instead** (Phase 2), which reaches them at LSP-hover time — earlier and harder to miss than a console line seen only after a run — and prose can name the number without importing it.
     - ⚠️ **`RECOMMENDED_MIN_TTL_SECONDS` is a name that makes a claim, and the claim is "advisory":** unlike `ACCESS_TOKEN_TTL`, which is *enforced* as the ceiling, this is never enforced. A floor was considered and **rejected** — it would make Phase 3's forced re-mint untestable without a test-mode bypass or a private reach-in, and it does nothing about the second hazard, which is semantic rather than a range problem. *(Name is a proposal — `naming-judgment`.)*
     - ⚠️ **`@lumenize/debug` gates on `DEBUG`, so with it unset in production the warn does not print.** That is acceptable and deliberate: the reader this guards against is a developer building the admin-debug UI, who has `DEBUG` on. It is a **dev-time** guard, not a production alarm — do not mistake it for one, and do not "fix" it by logging unconditionally.
   - **Success (capable of failing) — an implausibly short TTL warns at the MINT.** Via the debug sink (`testing.md` § *Asserting on `@lumenize/debug` log output*), in `packages/nebula-auth/test`: a request below `RECOMMENDED_MIN_TTL_SECONDS` on either endpoint emits the server warn; a value at or above it emits none. **Mutation:** drop the warn → the marker is absent → reds. ⚠️ This criterion is why the warn is not decorative: Phase 3's forced re-mint deliberately uses a sub-30s TTL and so trips it on every run — asserted, that is coverage rather than noise.
   - **Success (capable of failing) — the clamp holds, ON BOTH ENDPOINTS.** Asserted separately for `/mint-narrower-token` and `/refresh-token`: a request for a TTL **longer** than `ACCESS_TOKEN_TTL` mints a token whose `exp - iat` is `ACCESS_TOKEN_TTL`, not the requested value. Naming the endpoint is load-bearing — an endpoint-agnostic criterion is satisfiable on `/mint-narrower-token` alone, shipping the parameter untested on the cookie-authenticated path. **Mutation:** pass the requested value straight through → `exp - iat` exceeds the ceiling → reds. ⚠️ **Unclamped is NOT the worst shape** — un-*typed* is, because it is unbounded rather than merely long (see the 🛑 above). Both assertions are security-relevant; this one bounds a long token, that one prevents an immortal one.
   - **Success (capable of failing) — a short TTL is honoured, on both endpoints.** A request below the ceiling mints a token with exactly that lifetime, and the response's `expires_in` reports the **effective** (post-clamp) lifetime rather than the constant `ACCESS_TOKEN_TTL`. Without the `expires_in` half, a build that honours `ttlSeconds` in the JWT while leaving the response constant passes while misreporting lifetime by up to 15 minutes on the OAuth-conventional field. **Mutation:** ignore the parameter → `exp - iat` is the default → reds.
   - **Sub-goal — pin the clamp seam, because `mintAccessToken` cannot report a lifetime.** It returns `Promise<string>`, and both handlers hard-code `expires_in: ACCESS_TOKEN_TTL` — so "the clamp lives in the shared path" and "`expires_in` reports the **effective** lifetime" cannot both hold unless the effective value is *reachable* from the handlers. **Constraint:** one clamp, whose result both handlers can read; the shape is implementation (return `{ accessToken, effectiveTtlSeconds }`, or export a `clampTtlSeconds()` both the mint and the handlers call). ⚠️ Following "put it where the clamp is" without this forces a builder to re-derive the clamp per handler — exactly the divergence that instruction exists to prevent. The **validation** (the 400) stays in each handler's existing body-validation block, which already returns `invalid_request`; a throw from inside `mintAccessToken` would surface as a 500 through the router's catch.
   - ⚠️ **Two hazards, both of which the JSDoc must state, because only one is about the value's range.**
     1. **A TTL at or below 30 seconds produces CONTINUOUS re-minting**, because `LumenizeClient` refreshes when `exp - 30 <= now` — so such a token is already inside the refresh-ahead window the moment it is minted. That is precisely what makes it a deterministic, instant trigger for Phase 3, and a footgun for any real session. ⚠️ `RECOMMENDED_MIN_TTL_SECONDS` is **4× that 30s window**, and the coupling has to be **prose** for a reason worth stating correctly: not a dependency-direction problem (`nebula-auth` already depends on `@lumenize/mesh` and imports it in `profile.ts`; only the reverse is forbidden) but because **mesh does not export the window** — it is an inline `exp - 30` literal. So the JSDoc must name the relation or the two drift silently. ⚠️ **Package feedback rather than work for this phase** (CLAUDE.md § when Nebula fights a package API): naming and exporting it from mesh — `TOKEN_REFRESH_AHEAD_SECONDS = 30` — would make the "4×" relation checkable in code instead of in a comment. One generic line, no new concept; raise it, do not silently absorb it.
     2. **A shorter TTL does NOT shorten the caller-side revocation window** — the tempting misreading, and the reason a floor would not have helped. Every caller-side gate on `/mint-narrower-token` reads the **caller's token** (`payload.act`, `payload.access.authScopePattern`, `payload.access.admin`, `hasAdminOverScope(payload.access, …)`); the registry is read only for the **subject**. So a re-mint catches a deleted or moved *subject* but **not** a demoted *admin*, who stays bounded by the parent's own token lifetime plus KV propagation (`security.md` § revocation is KV-eventually-consistent). ⇒ `ttlSeconds` tightens the subject-side leash only. Whoever builds the admin-debug UI will otherwise assume the opposite.

2. **`impersonate()` mints a narrower token and returns a live client — MINT FIRST, then seed the child with that token.** `impersonate(sub, activeScope, opts?)` awaits the mint, then constructs a `NebulaClient` seeded with the minted token via the `accessToken` config field, whose `refresh` calls the **same** mint helper for every *subsequent* token, and registers the child against the parent. `impersonate()` throws locally when `this.claims?.act` is present — ⚠️ **`?.` is required, not defensive style**: `claims` is genuinely nullable on the base and `NebulaClient` only *re-types* it non-null, as its own JSDoc says (*"Code that runs before `ready` … must still guard with `?.`"*), so `this.claims.act` would raise a TypeError instead of refusing the chain.
   - ⚠️ **Mint-then-seed is load-bearing, and the ordering is what three criteria below rest on.** The alternative — construct the child with no token and let its constructor's own refresh *be* the single mint — mints exactly once too, but it moves the **first mint's failure** inside `super()`, where it lands in `#connectInternal`'s catch and becomes a `#scheduleReconnect()`. `impersonate()` would then resolve a client that silently retries a call which can never succeed, and the caller would get **no error at all** — instead of the clean rejection the failed-first-mint criterion requires. Seeding also populates `#accessToken`/`#claims`/the derived name at construction, which is what *`ready` still holds* wants. ⚠️ It also makes `impersonate()` itself an `accessToken`-config construction — fine, and covered **by construction** by Phase 4's property criterion (its token carries `act` and came from `impersonate()`), which is the third site in this task that phrasing saves.
   - **Sub-goal — ENCAPSULATE impersonation; `NebulaClient` gets exactly TWO touchpoints.** The only reason a `NebulaClient` would know `/mint-narrower-token` exists is this feature, so the feature owns its own knowledge. **Constraint — the commitment is the touchpoint count, not the file layout:**
     1. **One hook in `disconnect()`** — the cascade and the un-mintable marking. Irreducible: the *parent* is an ordinary client built by `createNebulaClient` long before anyone knows impersonation will be used, so it cannot be a subclass; and there is no external state to poll instead, since `disconnect()` deliberately keeps the token and `authedFetch` needs no connection. ✅ *Checkable:* all three teardown doors route through `disconnect()` and no transient path does, so this is **one** call site.
     2. **One internal construction seam** — the conditional that lets an internally-constructed client supply its own `refresh` instead of the cookie one. Needed even with a subclass, since `super()` runs `NebulaClient`'s constructor, which is what overwrites `refresh`. **Reachable from `impersonate()`, unreachable from public config** — a publicly suppliable `refresh` reopens the token/`authScope` mismatch for every caller, which is what the factory decision rests on.
   - **Everything else lives with the feature, not in `NebulaClient`:** the mint helper (pass a bound `(url, init) => this.authedFetch(url, init)` — `protected` blocks a free function from calling it, not from receiving it, and one helper keeps first-mint and re-mint on one path); the chain refusal; the child's naming; the child's `#mintedFrom` and its `logout()` override; and the first-mint error mapping, which only *has* a home here because of mint-then-seed. The child-registry may key **by parent** (a `WeakMap<parent, Set<child>>`) — ⚠️ **not** the `WeakSet`/`WeakRef` the Decisions table rejects, which was about holding the *children* weakly (not iterable, GC-timed); a strong iterable Set keyed by parent has neither problem.
     - *Shape left open:* whether the child is a `NebulaClient` subclass or the same class with a branch is genuinely marginal — one override and one field is thin justification for a new type. A subclass does **not** violate the FULL-client decision (that rejected a restricted *subset*; a subclass only adds, and `instanceof NebulaClient` still holds).
     - ⚠️ **`refresh` is not the only thing the seam has to carry** — and this is what makes it buildable-or-not rather than tidy. `LumenizeClient`'s `#config` is `#`-private, only `authedFetch` and `pendingAsyncCallCount` are `protected`, and `NebulaClient` retains nine fields that do **not** include the transport (`nebula-client.ts`'s own comment: *"a method can't reach the constructor's `config`"*). Every **baseline-lane** client supplies `WebSocket: browser.WebSocket` (`connectClient`), so a child built without it reaches for `globalThis.WebSocket` and the first criterion below cannot pass. ⚠️ **Scoped to that lane deliberately — the `/live` harness passes NO `WebSocket`** and relies on the Node global, so the seam must pass the parent's value **through, `undefined` included**, never require one. Making `WebSocket` a required input of the seam would break the harness path, which is the one path the readiness clause depends on.
     - **Pin the inheritance contract.** The child receives `baseUrl`, `appVersion`, `fetch`, `WebSocket`, `sessionStorage`, `BroadcastChannel`, `resourceHostBinding`; its `activeScope` is the impersonated scope. It deliberately does **not** receive `onLoginRequired` — Phase 3's *does not log the admin out* criterion rests on the child not holding the admin's handler. `authScope` is **inert** on a child (see Phase 3's child-`logout()` sub-goal): it names a refresh-cookie path, and a child has no refresh cookie.
     - 🛑 **The child's `refresh` closure CAN RUN DURING `super()`, before the child's private fields exist — so it must NOT read `this.#mintedFrom`.** `LumenizeClient`'s constructor eagerly connects; with an explicit `instanceName` set, `#connectInternal` takes the `else if (this.#needsTokenRefresh())` branch, and `#refreshToken` invokes `refresh()` in its **synchronous prologue**. Mint-then-seed makes this benign for a normal TTL (the seeded token is fresh, so the branch is not taken) — **but not for the short-`ttlSeconds` fixture Phase 3 prescribes**, where the seeded token is *born* inside the refresh-ahead window and the branch fires immediately. A closure reading `this.#mintedFrom` would then throw a TypeError inside `#connectInternal`'s try, land in `#scheduleReconnect()`, and cost a silent 1s backoff. ⇒ **the re-mint path reaches the parent through a reference LEXICALLY CAPTURED in `impersonate()`**, never through the child's own field. `#mintedFrom` stays, for the post-construction users — deregistration and the child's `logout()`.
     - ⚠️ **Two criteria therefore need DIFFERENT `ttlSeconds`, and it is not a detail.** *Mints exactly once* must use a TTL comfortably **above** the 30s refresh-ahead window, or the seeded child re-mints during its own construction and a correct build shows two markers. Phase 3's forced re-mint wants the opposite — and under mint-then-seed its second marker appears **during construction**, not on "the very next operation".
   - **Sub-goal — thread `opts` through to the mint request, and store it on the child.** `opts?: { ttlSeconds?: number }` reaches the private mint helper and into the request body, and the child **retains it** so every re-mint replays the same value. Without this, Phase 3's re-mint criterion has no way to produce a short-lived child.
   - **Sub-goal — state the short-TTL guidance in `impersonate()`'s JSDoc, on `opts.ttlSeconds`.** ⚠️ **This is the author-facing half of Phase 1's warn, and it is deliberately PROSE rather than a client-side `debug.warn`** — it reaches the caller at LSP-hover time, while they type the argument, which is earlier and harder to miss than a console line after a run; and prose can name the number without importing it, which is what keeps this file Node/browser-safe (see Phase 1's dropped-client-warn note). Both hazards, in the caller's terms: below ~120s (4× the client's 30s refresh-ahead window) the token is born inside that window and re-mints continuously; and a shorter TTL bounds only the **subject** side, never the caller's own revocation window.
   - **Sub-goal — name the child deterministically, and never touch the parent's tab storage.** Pass an explicit `instanceName` of `${subjectSub}.${parentTabId}.${activeScope with dots as dashes}`, which short-circuits `getOrCreateTabId` entirely (so the child neither reads nor writes `lmz_tab`, and registers no BroadcastChannel listener that could answer a future parent's probe). Tab-duplication safety is inherited: the parent's tabId is already disambiguated by the probe before the child exists, so the child is exactly as unique as its tab.
   - **Success (capable of failing) — the returned client IS the subject.** A real universe admin impersonates a real invited member; the returned client reaches `connected`, and its `claims.sub` / `claims.profileId` are the subject's while `claims.act.sub` is the admin's. ADR-009 **rung 2** throughout — real founding, real invite, real server-issued login, real endpoint; no email hop, no client mint. **Mutation:** construct the child from the parent's own token instead of the mint response → `claims.act` is absent → reds.
   - **Success (capable of failing) — `impersonate()` mints exactly once.** One server-side `nebula-auth.worker.narrower.issued` marker for the expected subject, via the debug sink, **with a `ttlSeconds` above the refresh-ahead window** (or defaulted) so construction itself does not re-mint. **Mutation:** construct the child WITHOUT seeding the minted token → its eager connect finds no token, `#needsTokenRefresh()` is true, and its `refresh` mints a second time → two markers → reds. ⚠️ That mutation is the plain reading of an unpinned goal sentence, which is why mint-then-seed is stated above rather than left to the builder. The *shared-helper* property cannot be observed here — nothing in this phase triggers a re-mint — so it is asserted in Phase 3.
   - **Success (capable of failing) — impersonation does not chain.** Calling `impersonate()` on an impersonated client throws with a message naming chaining rather than authorization, and **makes no network call** — instrumented by **counting requests on the injected `fetch`** (the config field every fixture already supplies) and asserting zero to `/mint-narrower-token`. ⚠️ The instrument has to be named, because the debug sink cannot serve here: the endpoint's root-identity gate returns a bare `errorResponse` with **no** marker (unlike the non-admin branch, which emits `narrower.denied`), so the sink cannot tell "never called" from "called and refused" — and without an instrument a build that hits the endpoint, takes the 403, then throws a chaining message would pass. **Mutation:** delete the guard → the request count is 1 → reds.
   - **Success (capable of failing) — a failed FIRST mint rejects cleanly and leaves no half-registered child.** `impersonate()` with an `activeScope` outside the subject's reach rejects (rather than resolving a client that never connects), surfaces the endpoint's status and message, and leaves the parent's `#minted` unchanged. ⚠️ Not an edge case: the Decisions table deliberately does **no** client-side `activeScope` validation, so a wrong scope is an *expected* caller error — and a half-registered child would hold an open socket, the exact leak the `Set<WeakRef>` rejection argues GC cannot close. **Mutation:** register the child before the mint resolves → a failed mint leaves it in `#minted` → reds.
   - **Success (capable of failing) — two children coexist.** From one parent, `impersonate()` two different subjects, and separately one subject at two different `activeScope`s: all reach `connected`, their `lmz.instanceName`s differ, and a call on each succeeds. ⚠️ **This is the only criterion protecting two load-bearing Decisions** — "an admin may want two subjects live at once" (which rejects the mode flag) and the scope segment in the child's name — and the failure it catches is **silent**: the Gateway names one DO per `instanceName`, so a colliding pair *supersedes* each other's socket rather than erroring. **Mutation:** drop the scope segment from the child's name → the same-subject pair knocks each other offline → reds.
   - **Success — `ready` still holds.** The client from `impersonate()` resolves its readiness only after claims are populated, so `claims.sub` is non-null-safe for the blessed examples. ⚠️ `NebulaClient` re-declares `claims` as non-null on that guarantee; a child that resolves early makes every unguarded `client.claims.sub` a latent null deref.
   - **Success (capable of failing) — `ttlSeconds` round-trips.** A child minted with an explicit `ttlSeconds` gets a token whose `exp - iat` is that value, not the default. **Mutation:** accept `opts` and drop it before the request → the default lifetime comes back → reds.
   - **Success (capable of failing) — `impersonate()` leaves the parent's tab identity alone.** The parent's stored `lmz_tab` is byte-identical before and after. **Mutation:** let the child derive its own tabId via `getOrCreateTabId` → the probe fires, the value is rewritten → reds. ⚠️ Silent otherwise: the admin's client keeps working this session and only loses continuity on a later reload, which no runtime assertion would notice.
   - ⚠️ **Comment the DO-name-permanence constraint AT THE SITE**, not only here — this table will not be read again. `packages/mesh/src/tab-id.ts`'s header now carries the general rule (persist, never randomize, because a DO name reservation is permanent); the child's naming site needs the specific consequence, **and the first-segment-must-equal-`sub` constraint from the Decisions row** — a builder reordering the segments for readability gets a 403 that reads as a token problem. `.claude/rules/` routing: a local invariant belongs in JSDoc at the site.
   - ⚠️ **Where `parentTabId` comes from, because there is no accessor for it.** The tabId exists only as a local inside `#connectInternal`, embedded into `#instanceName`; `#instanceName` is private to `LumenizeClient`, so the reachable route is the `lmz` facade getter, which returns the **whole** `${sub}.${tabId}` and **throws** while it is unset (*"instanceName is only available after connected state"*). So: parse the tabId off `parent.lmz.instanceName`, and treat the parent-has-a-name precondition (design intent, § *The parent is the credential*) as real. Safe because a `sub` is a dotless UUID — the same fact the Gateway's first-segment check depends on.
   - ⚠️ **`a?.#b` is a compile error** (`TS18030: An optional chain cannot contain private identifiers`). `#mintedFrom` is optional on a non-impersonated client, so use `if (this.#mintedFrom) this.#mintedFrom.#minted…`, never `this.#mintedFrom?.#minted…`. Cross-instance `#private` access is otherwise legal and is the mechanism here — verified against Node 22 + tsc 5.9.3 `--strict` on 2026-07-29.

3. **Lifetime: the session outlives its token and dies with its parent.** The child re-mints on expiry through `#mintedFrom`; a terminal re-mint failure terminates the child without reaching the admin's `onLoginRequired`; disposing the parent disposes its children; a child deregisters from `#minted` on dispose **and** on terminal disconnect; a child's own `logout()` tears down only the child.
   - **Sub-goal — `logout()` on an impersonated child is CHILD-ONLY teardown.** It disposes the child and deregisters it from the parent's `#minted`, and does **not** POST the auth logout endpoint. ⚠️ **Not a weakening of the method — the faithful implementation of it for a child.** `logout()` is revoke + clear + disconnect; a child holds **no refresh cookie** (*"No new durable credential exists anywhere"*), so the revoke half is vacuous and the remainder *is* dispose. Left inheriting the parent's behaviour it is actively harmful: `authScope` **is** the cookie path (`security.md` § two-scope model), `logout()` is its only reader on a child, and it POSTs `/auth/{authScope}/logout` with `credentials: 'include'` — so the natural implementation revokes the **admin's** 30-day refresh token, inverting this file's own invariant. Branch on `#mintedFrom`, which the design already tracks.
     - ⚠️ **Pinning `authScope = activeScope` is NOT a sufficient fix**, and is the tempting one. It works only while the two differ (cookie-path `/auth/u` fails to path-match request-path `/auth/u.g.s/logout` — the first uncovered character is `.`, not `/`). When an admin logged in **at** the scope they impersonate into, the paths match exactly, the cookie is sent, and the admin is logged out. That is the ordinary support shape, not an edge case.
   - **Success (capable of failing) — `child.logout()` leaves the admin's session intact.** After it, the parent still connects and still mints. **Mutation:** give the child the parent's `authScope` and let the POST through → the admin's refresh token is revoked → reds. ⚠️ Silent without this criterion: nothing else calls `child.logout()`, so it ships green and surfaces as an admin's session dying for no visible reason.
   - **Success (capable of failing) — dispose cascades.** Disposing the parent tears the child down: the child reaches `disconnected` and does **not** come back. ⚠️ **Assert `connectionState` plus "does it come back?", NOT a call.** After `disconnect()` the socket is null and no reconnect is armed, so a fresh `callAsync` is *queued* rather than rejected and settles only at the 30s default — four cascade assertions at 30s each is ~2 minutes that reads as a hang. If a call is used anywhere, pass an explicit short `timeoutMs`. **Mutation:** drop the cascade → the child reconnects and keeps working → reds.
   - Teardown makes a **best-effort** unsubscribe; nothing asserts it landed. ⚠️ **Do NOT assert server-side `Subscribers` / `QuerySubscribers` rows.** The mesh is designed for any node to vanish without notice — a force-quit browser is indistinguishable there from a clean dispose — so those rows are a deliberately **self-healing** surface (reactive reap on the next failed fanout, `mesh.md` § *`LumenizeClientGateway` is NOT a mesh participant*) and cannot discriminate. `testing.md` § *Self-healing end-state* points at the transient surface only for a **churn-avoidance optimization**; this cascade changes whether the child works at all, which is an ordinary end-state difference. *"Does it come back?"* is the discriminator.
   - **Success (capable of failing) — the cascade fires through EVERY teardown door, not just `using`.** Asserted separately for `dispose()` (the production path) and `logout()` (end-of-session) as well as `[Symbol.dispose]()`. **Mutation:** hook the cascade on `[Symbol.dispose]()` only → the `using` case stays green while both others red. ⚠️ This is the criterion that distinguishes a real cascade from one that merely satisfies the suite. ✅ *Checkable, and it makes the work small:* all three doors route through **`disconnect()`** — `dispose()` calls it, `logout()` calls it, `[Symbol.dispose]()` **is** it — and no transient path does. So the cascade is **one** hook at that single seam, not three overrides; the criterion asserts three doors because a builder can still hook the wrong one.
   - **Sub-goal — the teardown seam marks the parent UN-MINTABLE, and the mint helper refuses afterwards.** ⚠️ **This is new state, not a consequence of disposal** — and without it the criterion below reads as already-true and a builder ships nothing. Neither dispose door revokes minting capability: `dispose()` is `engine.dispose()` + `disconnect()`, `[Symbol.dispose]()` is just `disconnect()`, and `disconnect()` deliberately **keeps** the token so a reconnect succeeds — while `authedFetch` needs only a `fetch` and a token, no connection. So a disposed parent otherwise keeps minting for its full remaining token life. Since all three doors route through `disconnect()`, the marking is **one assignment at one site**.
     - ⚠️ **`logout()` is NOT exempt, and `clearAccessToken()` does not close minting** — it makes the next mint **refresh first**, because a missing token sets `#needsTokenRefresh()` true and `authedFetch` calls `#ensureFreshToken()` before every request. Worse, `logout()`'s revoke is explicitly **best-effort with a swallowed catch**: on an offline or 5xx logout the cookie-clearing response never arrives and the KV record is never revoked, so the parent's refresh cookie stays live and `authedFetch` mints again — for the **30-day cookie life**, not one token lifetime. Exempting `logout()` would leave the exact hole this sub-goal exists to close, on the door the file itself calls *the actual end-my-admin-session action*.
   - **Success (capable of failing) — a torn-down parent cannot re-mint, through ANY door.** After `dispose()`, and separately after `logout()`, the child's re-mint path fails rather than silently succeeding for another token lifetime. **Mutation:** leave the child's captured closure live after teardown → the re-mint succeeds → reds. **Second mutation:** mark un-mintable on `dispose()` but not `logout()` → the `dispose()` arm stays green while the `logout()` arm reds.
   - **Success (capable of failing) — a blip does NOT cascade.** A parent that loses its socket and reconnects leaves its children **working across the blip**. **Mutation:** fire the cascade on any transition **out of `'connected'` (i.e. on `'reconnecting'`)** → the child is torn down by a blip → reds. ⚠️ **The mutation has to be `'reconnecting'`, not `'disconnected'`** — a transient close never reaches `'disconnected'` at all (`#handleClose` → `#scheduleReconnect()` → `'reconnecting'`; the 4401 path likewise). `'disconnected'` is set only by the deliberate `disconnect()` and by terminal auth failure, so hooking *that* state would leave children working across a blip and this criterion could not red. Keep the criterion — hooking a state transition is the obvious wrong implementation, and this is the only thing that catches it.
   - **Sub-goal — classify a failed re-mint STRUCTURALLY: 4xx is terminal, 5xx and a network throw are transient.** Stated as a property, not a status list, so a status the endpoint gains later inherits the right behaviour instead of falling into whichever default the code happened to pick — the same reasoning that made Phase 4 a property rather than an enumeration. A 4xx means the endpoint's gate chain now refuses this pairing (deleted subject, demoted caller, scope no longer reachable), which is exactly the revocation the design intent promises; retrying cannot help. A 5xx or a thrown fetch is the case retrying exists for, and treating it as terminal would end an impersonation session on a blip. ⚠️ `authedFetch` already retries once on **401** before the closure sees it, so 401 is not a case to re-handle here.
     - ⚠️ **Two of the 4xx are STRUCTURALLY IMPOSSIBLE on a re-mint, and reaching one is a bug — so warn.** The chaining refusal (403 root-identity) and self-narrow (400) both depend on the parent, which has not changed since the first mint succeeded; if they could fire, they would have fired then. They stay **terminal** — behaviour identical to the rest of the 4xx group, no special case in the predicate — but emit a distinct `debug.warn`, because the child otherwise just quietly dies and the two causes are indistinguishable afterwards. This separates *"the session ended because authority changed"* (expected; the design working) from *"the session ended because the mint path is broken"* (a real defect, otherwise invisible).
   - **Success (capable of failing) — a terminal re-mint failure terminates the child and does NOT log the admin out.** Delete the subject and force a re-mint: the child reaches `disconnected` and stops re-minting, and the parent's `onLoginRequired` never fires. **Mutation:** hand the child the parent's `onLoginRequired` → the admin is bounced to login because someone else's session ended → reds. ⚠️ The mutation targets the **inheritance contract**, which is what actually protects the admin — not an error class, which mesh either treats as transient or overwrites.
   - **Success (capable of failing) — a NON-terminal re-mint failure does NOT end the session.** Force a 5xx (or a thrown fetch) on the re-mint: the child stays `reconnecting` and recovers when the next attempt succeeds. **Mutation:** classify every mint failure as terminal → the child dies on a blip → reds. ⚠️ **Without this, the criterion above is satisfied by a build that terminates on everything**, which inverts the blip invariant this file states three times — and `testing.md` § *Tests must be capable of failing* requires each operand of a terminal-vs-transient condition to be mutated independently rather than toggling the branch as a whole.
   - **Success — deregistration.** Disposing a child individually, and a child terminating on a failed re-mint, both remove it from the parent's `#minted`.
   - **Success (capable of failing) — readiness follows the parent's CREDENTIAL, not its CONNECTION.** The design intent asserts this and nothing tested it. Both halves: (a) a parent that is **disconnected** still mints a working child; (b) a parent whose **own token has expired** still mints — `authedFetch` refreshes it off the cookie first, then mints. **Half (b)'s mechanism, stated because no client-side channel for it exists:** `NebulaClient`'s own refresh closure hard-codes its body and cannot request a `ttlSeconds`, so the fixture calls `POST /auth/{authScope}/refresh-token` **directly** with a short `ttlSeconds` (Phase 1's other arm) and seeds the parent through the `accessToken` config field. **Two preconditions, both load-bearing, both easy to get wrong:**
     - 🛑 **The parent must be built on the SAME `Browser`/`fetch` that performed the login** (the shape `connectClient` uses), or there is no Path-scoped refresh cookie for `authedFetch` to spend — the refresh 401s, `NebulaClient`'s closure throws `LoginRequiredError`, and the criterion reds for a reason unrelated to what it asserts (or a builder reaches for a rung-3 mint to get past it, breaking the stated rung). ⚠️ Do **not** copy `nebula-client-reconnect.test.ts` wholesale: its second client is on a **fresh, cookie-less `Browser`** and never refreshes at all, which is precisely why the absence is invisible there. Borrow only its `accessToken`-construction *shape*. Consider a fixture guard that the parent's first `authedFetch` actually refreshed, so a cookie-less parent fails loudly instead of looking like a mint failure.
     - 🛑 **Build the parent with NO `instanceName`, and drop the phrase "without connecting" — the constructor ALWAYS connects.** With `instanceName` set, `#connectInternal` takes the `#needsTokenRefresh()` branch and refreshes off the cookie *during construction*, so by the time the test sees `connected` the parent already holds a fresh 15-minute token and this criterion is **vacuous** — its mutation would not red. With no `instanceName` the constructor takes the derive-from-`claims.sub` branch instead, which runs **no** refresh check, so the near-expired token survives construction and the parent-has-a-name precondition is still met. Then make the discriminator explicit: assert the parent's `claims.exp` (or a counted `/refresh-token` request on the injected `fetch`) advanced **during** `impersonate()`, not before it.
     - ⚠️ **This adds an `accessToken`-config construction, so Phase 4's criterion is phrased over a PROPERTY rather than a file list** — that restatement is not optional bookkeeping, it is what keeps Phases 3 and 4 from contradicting. **Mutation:** gate `impersonate()` on the parent being connected, or on it holding an unexpired token → reds.
   - **Success (capable of failing) — a re-mint never changes who the child is.** Across a forced re-mint the child's `claims.sub` stays the subject's. **Mutation:** route the child's refresh through the parent's cookie path instead of the mint helper → the re-minted token is the **admin's**, `sub` changes → reds. ⚠️ This is the identity-swap hazard from *Missing* #1 caught as a test — a handed token renewing off the wrong source is the one way an impersonation session silently becomes the admin.
   - **Success (capable of failing) — the child re-mints through its parent.** Mint the child with a `ttlSeconds` inside the client's 30-second refresh-ahead window, so the seeded token is already due and the re-mint fires with no waiting. A **second** server-side `nebula-auth.worker.narrower.issued` marker appears for the same subject, and the child keeps working. ⚠️ Under mint-then-seed the trigger is the child's **own construction**, not a later call — the eager connect finds a token already inside the window and refreshes through the mint helper. Assert on the marker count reaching two, never on "after the next operation", which would pass vacuously. **Mutation:** give the child a `refresh` that returns its original token unchanged → no second marker, and the child fails once the token actually expires → reds.

## Non-goals

- **A hard cap on impersonation duration** — see Decisions.
- **Any convenience getter for "am I impersonating"** — `claims` answers it; adding one waits for a caller.
- **Server-side authorization changes.** The endpoint's gate chain is unchanged and no new authz decision is added anywhere. ⚠️ The `ttlSeconds` parameter is a server-side *capability* change, not an authorization one — clamped, it can only reduce a token's lifetime.
- **The verified-claims header on the edge→DO hop** — filed in [backlog.md](backlog.md) § `@lumenize/auth`. Independent: `impersonate()` rides `authedFetch`, which that work does not touch.
- **Studio reflecting `activeScope` in the URL** ([ADR-017](../docs/adr/017-the-url-is-the-view-state.md), `backlog.md` § Nebula Studio UI) — the other half of the support flow. Neither task gates the other.
- **Testing that codegen admits an impersonated caller.** The Decisions row stands — codegen from an impersonated session is allowed — but the *test* is cut. `DevStudio.chat` is `@mesh(requireAdmin)` and needs a live container, so the canonical non-admin subject reds on correct code for a reason unrelated to `act`; and the collapse is re-pinning that gate from admin-only to "any chat participant may trigger", so a test now asserts a model being replaced. The requirement is handed to [nebula-galaxy-collapse-and-chat.md](nebula-galaxy-collapse-and-chat.md)'s chat-authz work — *the trigger gate keys off `sub`, never `act`* — and any `act`-reading authz addition anywhere in `apps/nebula/src` is already caught by Phase 5's reader-list instrument, which is broader than a test pinned to `chat`.
