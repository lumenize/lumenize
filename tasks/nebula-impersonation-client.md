# Impersonation sessions — a client that acts as another person

**Status:** Drafted 2026-07-29 via `/write-task`; design intent hand-reviewed and approved, Pass 2 (Decisions + phases) written against it. Ready for `/review-task`. Unblocks nothing in pre-alpha; it exists because `/mint-narrower-token` shipped with **no consumer able to consume it**, and because the two test helpers written around that gap are already the anchoring workaround (pinned by Larry 2026-07-29: fix it now rather than backlog it).

**Objective — an admin can obtain a working `NebulaClient` that acts as another person, so that "why can't this user do X?" is answered by driving the app as them.**

## Context and current state

**Built already.**

- **The endpoint.** `/auth/{callerScope}/mint-narrower-token` (`mintNarrowerToken`, `worker-token.ts`) mints a token whose `sub` is the subject and whose `act` is the caller, under an ordered gate chain — root identity, self-narrow rejection, caller reach, admin bit, subject exists, eligibility, subject-reach mirror, in that order (the ordering is itself a disclosure decision, ADR-008). It is the only producer of a JWT `act` claim — **the qualifier is load-bearing**: the planned `prependActor` ([nebula-galaxy-collapse-and-chat.md](nebula-galaxy-collapse-and-chat.md)) composes an `act` chain onto a `changedBy` **record**, never onto a signed token, so `claims.act` remains an exact signal for *this is an impersonation session*. Fully tested; see `tasks/archive/nebula-mint-narrower-token.md`.
- **The record.** `executeScopeDeletion` stamps `actingToken` — the full verified claims including the `act` chain — on scope deletion ([ADR-016](../docs/adr/016-record-the-acting-principal.md)), so a destructive action taken under impersonation already names both parties.
- **The transport.** `LumenizeClient.authedFetch` is `protected`, injects the in-memory token as `Authorization: Bearer`, refreshes when it is missing or near expiry, and retries once on a 401 — `NebulaClient`'s `scopes` namespace is built on it, keeping the JWT inside the client. ⚠️ **It has no test coverage, direct or indirect.** ✅ *Checkable:* no test file references `authedFetch`, and nothing outside `apps/nebula-studio-ui/src/App.vue` drives `client.scopes.*` — so its refresh-on-expiry, its retry branch, and its de-duplication with the WS-connect refresh are today exercised only by a human clicking through Studio. This task makes `impersonate()` its second caller and its first tested one, and the paths it leans on are exactly the untested ones.
- **The disposal seam.** `LumenizeClient[Symbol.dispose]` exists, so `using` works on a client today.

**Missing.**

1. **A way for a client to RENEW a token that did not come from its cookie.** A `NebulaClient` can already be *handed* one: `accessToken` is public on `LumenizeClientConfig`, survives the `Omit` (which lists only `refresh` and `gatewayBindingName`), and seeds `#accessToken`, `#claims`, and the derived `instanceName`. What it cannot be told is where the **next** token comes from — `refresh` is hard-coded to the cookie POST, and the constructor spreads the caller's config and *then* overwrites `refresh`, so it cannot be supplied even by casting. ⇒ a handed token works for at most `ACCESS_TOKEN_TTL`, after which the client refreshes **off the cookie**. For a same-identity token (the `/live` harness ×2, `multi-client.ts`, `fanout.benchmark.ts`) that is harmless — the cookie returns the same person. For a **narrower** token it is a silent identity swap: the child becomes the **admin** while `instanceName` still names the subject. ⚠️ A correctness hole, not an attack surface — `Omit` is compile-time only, the browser is the user's own machine, and any exploit needs a validly signed token regardless.
2. **A lifetime model for a token that cannot be refreshed from a cookie.** The minted token dies with `ACCESS_TOKEN_TTL`; nothing renews it, and the built-in refresh failure path raises `LoginRequiredError`, which `NebulaClient`'s connect path turns into `onLoginRequired`.
3. **A production path the tests can share.** Two suites hand-roll `refresh: async () => ({ access_token, sub })` over a raw `LumenizeClient` — `mint-narrower-token-payoff.test.ts` and `profile-do.test.ts`. They are the only two sites in `apps/nebula` doing this, and they exist solely because item 1 has no answer.

## Design intent, constraints, and future state

`await client.impersonate(sub, activeScope, opts?)` resolves to a **full `NebulaClient`** whose identity is that person. Both positional parameters are required; `opts` carries only `ttlSeconds`, which the child reuses on every re-mint. Full is the load-bearing word: every existing surface (`resources`, `orgTree`, `subscribe`) works on it unchanged, which is what lets a test and the Studio exercise one path.

### The parent is the credential

The returned client holds a private `#mintedFrom` handle to the client that produced it, and re-mints by calling **the same private mint helper on that handle that `impersonate()` itself calls**. One mint path, so the first mint and every re-mint cannot drift on body shape, URL, or error handling — and the child depends on the parent's *capability to mint*, never on how the parent talks to the endpoint. Five properties follow from that one fact, and they are the reason this shape was chosen over holding a fixed token:

- **No new durable credential exists anywhere.** The child's ability to act is derived entirely from the parent's in-memory session; nothing is written, cookied, or independently stealable.
- **Revocation propagates.** Every re-mint re-runs the endpoint's full gate chain, so a demoted admin, a moved subject, or a deleted subject ends the session at the next token boundary rather than at term.
- **Readiness follows the parent's *credential*, not its *connection*.** `authedFetch` obtains a token from the refresh cookie on its own path, so a parent that is disconnected, reconnecting, or not yet ready still mints. ✅ *Checkable:* `LumenizeClient` shares one in-flight refresh between the WS-connect path and `authedFetch`, and neither requires the other to have run.
- **Lifetime follows the parent *object*.** Disposing the parent disposes its children; a parent losing its socket does not. These are different events and the distinction is user-visible — a network blip must not end an impersonation session.
- **Duration is bounded by the admin's browser session**, re-authorized every `ACCESS_TOKEN_TTL`. Pinned as intended semantics by Larry, 2026-07-29.

When a re-mint terminally fails, the child surfaces a terminal disconnect of its own kind. The invariant: **the admin's own session is untouched by the end of an impersonation session**, so the failure must not travel the `LoginRequiredError` path that bounces a user to login.

### Two sessions are two clients

A second identity requires a second client object, because the subscriber tables key on the per-client id. ✅ *Checkable:* `clientId` is auto-generated per client instance at first connect; `QuerySubscribers` keys on `(queryHash, clientId)` while carrying `sub` and `profileId`, and the per-resource `Subscribers` table keys on `clientId` alone — so one connection carrying two identities writes one row with two answers to "who is here".

### The claims are the API

The child exposes nothing new. `client.claims` already answers both questions the caller has, structurally: top-level `sub` and `profileId` are the person being acted as, and the presence of `act` is what makes this an impersonation session. ✅ *Checkable:* `NebulaClient` re-declares `claims` as non-null on the strength of the factory's `ready` resolving after the first refresh — a client from `impersonate()` must preserve that guarantee, since every blessed example writes `client.claims.sub` unguarded.

### Authorization stays on the server

This task changes no authorization. The endpoint's gate chain remains the enforcement, and the client adds no check that could disagree with them. The single client-side refusal — that impersonation does not chain — is decidable from the client's own claims, is enforced independently by the endpoint's root-identity gate, and exists to convert a structurally impossible call into an accurate message instead of a 403 that reads as a problem with the subject.

⚠️ **`security.md` delegation rule (1) binds here**: the client reads `act` for presence only, never to decide an authorization outcome, and the licensed exception list stays at one member (the Profile owner branch).

### Retiring the workaround is the point

The two hand-rolled helpers are not incidental cleanup — they are the reason this task is being built now rather than backlogged. They are currently the only worked example in the repo of "drive a DO as an impersonated user", so the next person needing that copies them, and the shape ossifies. Moving both onto `impersonate()` while there are exactly two of them is the whole argument for the timing.

The gain is fidelity, not tidiness: those helpers construct a raw `LumenizeClient`, so they exercise a path the Studio can never take, and any defect specific to a `NebulaClient` carrying a narrower token is invisible to them.

### Constraints

- [ADR-009](../docs/adr/009-real-auth-path.md) — the adopted tests stay rung 1; the token under test comes from the real endpoint via a real admin's real session.
- [ADR-016](../docs/adr/016-record-the-acting-principal.md) — already satisfied by the endpoint and the registry record; this task adds no new destructive action.
- `.claude/rules/security.md` delegation rules (1) and (2) — both hold unchanged (above).
- `.claude/rules/mesh.md` — the child is an ordinary client; `impersonate()` reaches the `/mint-narrower-token` **endpoint** over `authedFetch`, matching how `scopes` reaches nebula-auth's registry routes. The two names sit at different levels on purpose: the endpoint mints a **token** and asserts a checkable property of it; the client method returns a **client** and names the use case.
- CLAUDE.md § package feedback — the `Omit` that closed a footgun also closed the capability; the resolution keeps the `Omit` and adds a factory, so callers never supply a token and scope that can disagree.

### Future state

This is the client capability the admin-debug UI needs; the UI itself is out of scope. It also makes an impersonated session available to any future test that needs to observe the app as a specific person.

⚠️ **Design consideration:** [ADR-017](../docs/adr/017-the-url-is-the-view-state.md) is the other half of the support flow — an admin needs the subject's `activeScope`, and Studio's URL does not yet carry it (`backlog.md` § Nebula Studio UI). Neither task gates the other.

⚠️ **Design consideration:** a hard cap on impersonation duration is deliberately absent. Should one ever be wanted, the re-mint is the single place it would live.

⚠️ **Design consideration:** `#mintedFrom` / `#minted` are private with no public accessor, which keeps the option of changing the parent-child representation later without a public break.

⚠️ **Design consideration:** two things here rest on `claims.act` being an exact signal for an impersonation session — the refusal to chain, and the self-awareness story that adds no new API. Keeping `prependActor` on the record side preserves that. Were an `act` chain ever composed onto a **token**, this file's chain refusal would reject a legitimate call from a person whose own session carried a prepended platform actor, and the Profile owner branch would deny them their own profile (already noted at `profile.ts`). That is a reason to keep the prepend on records, not a constraint this task enforces.

### Open questions

None. Every decision this file depends on was settled in conversation on 2026-07-29 — the API shape and its name, both parameters explicit and required, expiry via re-mint, the dispose-vs-disconnect distinction, exposing nothing beyond `claims`, refusing to chain, and allowing codegen from an impersonated session.

## Decisions

| Decision | Rejected alternative — why |
|---|---|
| **`await client.impersonate(sub, activeScope)` returns a full `NebulaClient`** | `client.impersonation.{methods}` as a namespace property — a property cannot take the subject, and an admin may want two subjects live at once. Worse, every existing namespace (`resources`, `orgTree`, `scopes`) is a stateless facade over the *same* identity, so `client.impersonation.resources` would look symmetric with `client.resources` while differing in the one thing that must never be subtle. Also rejected: `getNarrowerPermissionedClient()` — names the *token's* property rather than what the caller wants, and coins "permissioned". |
| **A second identity is a second client object** | A mode flag on one client (`switchToImpersonation()`). It cannot produce a second `clientId`, so it either tears down and rebuilds the connection on every toggle — losing every subscription, twice — or writes one subscriber row with two answers to "who is here". Independently: any reference held across a switch silently changes identity. |
| **The returned object is a FULL `NebulaClient`** | A restricted subset exposing only what impersonation "needs". Tests would still reach for a raw `LumenizeClient` for anything outside the subset, so the workaround this task exists to retire would survive it. |
| **The parent is the credential — the child re-mints through it** | A fixed, non-refreshable token expiring with `ACCESS_TOKEN_TTL`. It needs a new lifecycle concept for ordinary expiry, and it grants up to a full token lifetime of *stale* authority with no re-check. Also rejected: having the endpoint set a Path-scoped refresh cookie for the impersonated scope — that manufactures a 30-day, independently stealable durable credential for someone else's identity, which is the wrong lifetime for this capability. |
| **`impersonate()` is a factory; `refresh` stays unsuppliable by callers** | Exposing `refresh` publicly on `NebulaClientConfig`. A public `refresh` lets any caller build a client whose token and `authScope` disagree; a factory supplies both from one mint response, so they cannot diverge. ⚠️ The factory rests on **`refresh`** being closed — **not** on `accessToken`, which is NOT in the `Omit` and stays open (three consumers, including the `/live` harness twice). Closing `accessToken` is deliberately out of scope and would buy **no** security: `Omit` is compile-time only, the browser is the user's machine, and an exploit needs a validly signed token either way. Simplifying it away is filed under Testing and Quality in the backlog. |
| **The child re-mints via the parent's private mint helper** | The child calling `#mintedFrom.authedFetch(...)` directly. Two mint paths free to drift on body shape, URL, and error handling — the seam `access-claims.ts` exists to hold closed. It also makes the child depend on the parent's *transport* rather than its *capability*. |
| **Both positional parameters required and explicit; `ttlSeconds` an optional third-argument option** | A third positional parameter — an options object keeps the two required arguments unambiguous and leaves room to extend. Also rejected: deriving `activeScope` from the subject's identity row — mechanically possible (`Identities.universeGalaxyStarId` is single-valued), and wrong: `activeScope` is the token's `aud`, bounded by the subject's reach rather than equal to it, so deriving picks the **widest** valid value — the wrong end of the range for a debug session, which wants the specific star where the trouble is. It fails by *succeeding at the wrong scope*. Also rejected: optional-with-derive-as-default, which reproduces that for anyone who omits it. |
| **No client-side validation of `activeScope`** | Pre-checking reach in the client. The client cannot know the answer — it depends on registry state — so the check would be both a guess and a duplicate of a security decision. |
| **The chain refusal IS thrown client-side** | Relying on the endpoint's 403 alone. That reads as "you are not authorized to impersonate this person", pointing a developer at the subject and their permissions when the real answer is that impersonation does not chain. ⚠️ Distinct from the row above: this is decidable with certainty from the client's own claims, is not a guess, and the endpoint still enforces it. |
| **The child exposes nothing beyond `claims`** | An `impersonating` getter. `claims` already answers both questions structurally — top-level `sub`/`profileId` is who you are acting as, and the presence of `act` is what makes it an impersonation session. Naming a convenience before there is a caller is how `actFor` happened, and the obvious names (`actingAs`, `viewingAs`) are the role-noun disease. |
| **Cascade on dispose; never on disconnect** | Hooking `connectionState === 'disconnected'`. A parent's network blip would silently end the admin's impersonation session, which reads as a defect in the endpoint. Disposal is intentional end-of-session; disconnect is transient. |
| **Deregistration is explicit, on BOTH dispose and terminal disconnect** | `WeakSet`/`WeakMap` for the children — not iterable (`[Symbol.iterator]` is `undefined`, `for..of` throws), so the cascade cannot be written at all. Also rejected: `Set<WeakRef>` — it trades determinism for GC timing in a mechanism (`using`) chosen *for* determinism, and it is inert where it matters: an undisposed child holds an open WebSocket, so it stays reachable and the weak reference never goes stale. The leak it appears to fix is a connection, which GC does not close. |
| **A terminal impersonation failure gets its own error class** | Reusing `LoginRequiredError`. `NebulaClient`'s connect path turns that into `onLoginRequired`, which would bounce the **admin** to the login page because someone else's session ended. |
| **Codegen from an impersonated session is allowed** | Blocking it. Doing so requires reading `act` to make an authorization decision — a second exception to `security.md` rule (1), with none of ADR-012's justification (a profile is *global* and its scope authority can be manufactured; codegen is scope-local, where the ordinary model already works). There is also no escalation to prevent: authz keys off `sub`, and eligibility means the caller could do the same thing with their own token carrying *more* authority. |
| **`impersonate()` lives on `NebulaClient`** | `LumenizeClient`. Impersonation is a nebula-auth concept and mesh must not know about it (`mesh.md` § dependency direction). |
| **`ttlSeconds` on the token mints, CLAMPED to `ACCESS_TOKEN_TTL`** | Leaving the re-mint criterion unreachable, or reaching for a test-mode binding. ⚠️ **A clamped TTL is categorically not a test-mode flag** (`security.md`): it can only ever *shorten* a token, so it grants strictly less authority-over-time, bypasses nothing, needs no binding, and is safe — indeed useful — in production, where the admin-debug UI may want a deliberately brief session. Also rejected: an unclamped `ttlSeconds`, which would let a caller mint a long-lived token and is the only shape that could do harm. |
| **Duration is bounded by the admin's session, with no hard cap** | A maximum impersonation lifetime. Deliberately absent — the session is re-authorized against the full gate chain every `ACCESS_TOKEN_TTL` and dies with the tab. Were one ever wanted, the re-mint is the single place it would live. |

## Phases

1. **`impersonate()` mints a narrower token and returns a live client.** One private mint helper on `NebulaClient` wraps the `/mint-narrower-token` call over `authedFetch`; `impersonate(sub, activeScope)` calls it, constructs a `NebulaClient` whose `refresh` calls that same helper, and registers the child in the parent's `#minted`. The child records `#mintedFrom`. `impersonate()` throws locally when `this.claims.act` is present.
   - **Success (capable of failing) — the returned client IS the subject.** A real universe admin impersonates a real invited member; the returned client reaches `connected`, and its `claims.sub` / `claims.profileId` are the subject's while `claims.act.sub` is the admin's. ADR-009 rung 1 throughout — real founding, real invite, real login, real endpoint. **Mutation:** construct the child from the parent's own token instead of the mint response → `claims.act` is absent → reds.
   - **Success (capable of failing) — `impersonate()` mints exactly once.** One server-side `nebula-auth.worker.narrower.issued` marker for the expected subject, via the debug sink. **Mutation:** mint again inside the child's construction → two markers → reds. ⚠️ The *shared-helper* property cannot be observed here — nothing in this phase triggers a re-mint — so it is asserted in Phase 3, where one is forced.
   - **Success (capable of failing) — impersonation does not chain.** Calling `impersonate()` on an impersonated client throws **before any network call**, with a message naming chaining rather than authorization. **Mutation:** delete the guard → the call reaches the endpoint and returns 403 → the "no network call" assertion reds.
   - **Success — `ready` still holds.** The client from `impersonate()` resolves its readiness only after claims are populated, so `claims.sub` is non-null-safe for the blessed examples. ⚠️ `NebulaClient` re-declares `claims` as non-null on that guarantee; a child that resolves early makes every unguarded `client.claims.sub` a latent null deref.
   - **Sub-goal — the internal refresh seam, without which nothing here is buildable.** `impersonate()` cannot construct the child through the public config: `refresh` is omitted from `NebulaClientConfig` **and** overwritten by the constructor after the spread, so it cannot be supplied even by casting. `NebulaClient` needs an internal way to hand a child its own refresh. **Constraint:** reachable from `impersonate()`, unreachable from public config — a publicly suppliable `refresh` reopens the token/`authScope` mismatch for every caller, which is what the factory decision rests on. The shape is implementation (a protected construction path, a private factory, an internal-only option); the constraint is the commitment.
   - ⚠️ **`a?.#b` is a compile error** (`TS18030: An optional chain cannot contain private identifiers`). `#mintedFrom` is optional on a non-impersonated client, so use `if (this.#mintedFrom) this.#mintedFrom.#minted…`, never `this.#mintedFrom?.#minted…`. Cross-instance `#private` access is otherwise legal and is the mechanism here — verified against Node 22 + tsc 5.9.3 `--strict` on 2026-07-29.

2. **A `ttlSeconds` request parameter on the token mints, clamped so it can only shorten.** `buildNebulaJwtPayload` already accepts `ttlSeconds`; expose it through `mintAccessToken` and accept it on `/mint-narrower-token` and `/refresh-token`, clamped to `ACCESS_TOKEN_TTL` and rejecting a non-positive value. This is what makes the next phase's re-mint criterion reachable, and it is a capability worth having independently.
   - **Success (capable of failing) — the clamp holds, ON BOTH ENDPOINTS.** Asserted separately for `/mint-narrower-token` and `/refresh-token`: a request for a TTL **longer** than `ACCESS_TOKEN_TTL` mints a token whose `exp - iat` is `ACCESS_TOKEN_TTL`, not the requested value. ⚠️ Naming the endpoint is load-bearing — an endpoint-agnostic criterion is satisfiable on `/mint-narrower-token` alone, shipping the parameter untested on the cookie-authenticated path. **Mutation:** pass the requested value straight through → `exp - iat` exceeds the ceiling → reds. ⚠️ This is the one security-relevant assertion in the phase: unclamped is the only shape of this parameter that could do harm.
   - **Success (capable of failing) — a short TTL is honoured, on both endpoints.** A request below the ceiling mints a token with exactly that lifetime, and the response's `expires_in` reports the **effective** (post-clamp) lifetime rather than the constant `ACCESS_TOKEN_TTL`. ⚠️ Without the `expires_in` half, a build that honours `ttlSeconds` in the JWT while leaving the response constant passes while misreporting lifetime by up to 15 minutes on the OAuth-conventional field. **Mutation:** ignore the parameter → `exp - iat` is the default → reds.
   - **Success — a non-positive TTL is refused** with `400 invalid_request` on both endpoints, rather than minting an already-dead token.
   - ⚠️ **A TTL at or below 30 seconds produces CONTINUOUS re-minting**, because `LumenizeClient` refreshes when `exp - 30 <= now` — so such a token is already inside the refresh-ahead window at the moment it is minted. That is precisely what makes it a deterministic, instant trigger for the next phase, and a footgun for any real session. Say so at the parameter's JSDoc.

3. **Lifetime: the session outlives its token and dies with its parent.** The child re-mints on expiry through `#mintedFrom`; a terminal re-mint failure surfaces as its own error class rather than `LoginRequiredError`; disposing the parent disposes its children; a child deregisters from `#minted` on dispose **and** on terminal disconnect.
   - **Success (capable of failing) — dispose cascades.** Disposing the parent leaves the child's server-side `Subscribers` / `QuerySubscribers` rows gone. ⚠️ Assert the **server-side** rows, not `child.connectionState`: a child that merely lost its socket looks identical to one properly torn down (`testing.md` § self-healing end-state). **Mutation:** drop the cascade → the rows survive → reds.
   - **Success (capable of failing) — a disposed parent cannot re-mint.** After disposing the parent, the child's re-mint path fails rather than silently succeeding for another token lifetime. This is what makes "ending my session ends impersonation" true by construction rather than by timing. **Mutation:** leave the child's captured closure live after parent disposal → the re-mint succeeds → reds.
   - **Success (capable of failing) — disconnect does NOT cascade.** A parent that loses its socket and reconnects leaves its children live and their subscriber rows intact. **Mutation:** hook the cascade on `connectionState === 'disconnected'` → the child is torn down by a blip → reds. ⚠️ This criterion is the one that catches the naive implementation, so it earns its keep even though it asserts a non-event.
   - **Success (capable of failing) — a terminal re-mint failure does not log the admin out.** Revoke the caller's eligibility (demote, or delete the subject) and force a re-mint: the child terminates without the parent's `onLoginRequired` firing. **Mutation:** throw `LoginRequiredError` from the child's refresh → the parent's handler fires → reds.
   - **Success — deregistration.** Disposing a child individually, and a child terminating on a failed re-mint, both remove it from the parent's `#minted`.
   - **Success (capable of failing) — readiness follows the parent's CREDENTIAL, not its CONNECTION.** The design intent asserts this and nothing tested it. Both halves: (a) a parent that is **disconnected** still mints a working child; (b) a parent whose **own token has expired** still mints — `authedFetch` refreshes it off the cookie first, then mints. Half (b) is what the `/refresh-token` arm of Phase 2 exists for: age the parent's token with a short `ttlSeconds`, then impersonate. **Mutation:** gate `impersonate()` on the parent being connected, or on it holding an unexpired token → reds.
   - **Success (capable of failing) — a re-mint never changes who the child is.** Across a forced re-mint the child's `claims.sub` stays the subject's. **Mutation:** route the child's refresh through the parent's cookie path instead of the mint helper → the re-minted token is the **admin's**, `sub` changes → reds. ⚠️ This is the identity-swap hazard from *Missing* #1 caught as a test — a handed token renewing off the wrong source is the one way an impersonation session silently becomes the admin.
   - **Success (capable of failing) — the child re-mints through its parent.** Mint the child with a `ttlSeconds` inside the client's 30-second refresh-ahead window, so the very next operation triggers a refresh with no waiting. A **second** server-side `nebula-auth.worker.narrower.issued` marker appears for the same subject, and the child keeps working. **Mutation:** give the child a `refresh` that returns its original token unchanged → no second marker, and the child fails once the token actually expires → reds.

4. **Adopt it — per call site, not per helper.** Three of the four hand-rolled sites are impersonation and move to `impersonate()`: `mint-narrower-token-payoff.test.ts` (×2) and `profile-do.test.ts`'s narrower-token client. The fourth is **not**: `profile-do.test.ts`'s owner **control** carries the member's OWN login token and asserts the write RESOLVES, which is what proves the denial above it comes from `!claims.act`. `impersonate()` structurally cannot produce it — every token it mints carries `act` — so it moves to a real cookie-login `NebulaClient` via `createInvitedClient` (`test-helpers.ts`). Delete `clientCarrying` and `clientWithToken` once all four are re-homed, and state the fate of `mintNarrowerToken` (`test-helpers.ts`), which has zero callers afterwards.
   - ⚠️ **Do not convert the control to `impersonate()`.** Its red would be a *denial*, and the site's own comment names dropping `!claims.act` as the mutation — putting a builder chasing that red one edit from removing the guard the test exists to protect.
   - ⚠️ These stay ADR-009 **rung 2**, as the whole `baseline` lane is. Rung 1 for impersonation belongs to a `/live` scenario once the admin-debug UI exists; promoting one test here would make it an outlier for no coverage gain, since rung 1 adds only the email transport, which nothing asserted here depends on.
   - **Success — no client in `apps/nebula` presents a NARROWER token it did not obtain from `impersonate()`.** Scoped over the construct rather than one shape, because there are **two**: a `refresh` closure returning a fixed `access_token`, and the `accessToken` config field. Anchoring on only the first would let a builder retire the hand-rolled helpers while the more dangerous shape survived. Named carve-outs, all carrying same-identity tokens and none of them impersonation: `harness/lib/harness.ts` (×2), `test/browser/multi-client.ts`, `test/browser/fanout.benchmark.ts`. (`packages/mesh`'s `lumenize-client.test.ts` tests `LumenizeClient` itself — out of scope.)
   - **Success — the criteria those suites already carry survive the move**, unchanged in strength: the DAG verdict (a narrower token for a non-admin member is denied a write the caller is allowed), the persisted `changedBy` shape and its coalescing, and the Profile owner denial with its owner-succeeds control.
   - ⚠️ **This is the phase the task exists for.** The fidelity gain is that both suites stop exercising a raw `LumenizeClient` path the Studio can never take.

5. **Codegen from an impersonated session is not blocked.** No production change — a test that reds if someone later adds a block.
   - **Success (capable of failing) — the codegen entry admits an impersonated caller.** Drive it from a client returned by `impersonate()` and assert the guard admitted the call, via the DO-side debug-sink marker rather than a completed turn. **Mutation:** add `if (claims.act) throw` to the codegen path → the marker never fires → reds.
   - ⚠️ **Deliberately not a full codegen turn.** That needs `env.AI` + a container, so it belongs to the `wrangler dev` lane (`testing.md`), and it would defend against "codegen broke" — which every existing codegen test already covers. The regression this guards is narrower: a future well-meaning block.

6. **Bring the standing guidance back into line.** `testing.md`'s vehicle note and `security.md`'s `act`-reader enumeration.
   - ⚠️ **This is LAST on purpose, against the usual "the work lives in the phase that causes it".** Both edits are enumerations whose correctness is a property of the task's *end state*: Phase 1 adds a `.act` reader in `apps/nebula/src/nebula-client.ts`, and Phase 4 retires the two files `testing.md` currently names as canonical. Writing either edit in the phase that causes it would ship guidance a later phase falsifies — the trap recorded in `/write-task` and in `build-task`'s verify step.
   - **`testing.md`** — the note reading *"the vehicle is a plain `LumenizeClient`, never a `NebulaClient`"* becomes false for the impersonation case: the vehicle is `impersonate()`. Rewrite it to say a handed token still needs a plain `LumenizeClient`, **except** an endpoint-minted narrower token, which has a first-class path — and repoint the canonical examples, which by then no longer hand-roll.
   - **`security.md` rule (1)** — the reader list gains a **presence-only** reader: `nebula-client.ts`'s chain refusal. Prefer restating structurally over re-counting, so a later addition does not silently falsify it again.
   - **Success — the enumeration matches its own instrument.** Running `grep -rn '\.act\b' packages/nebula-auth/src apps/nebula/src` returns nothing the list does not account for.

## Non-goals

- **The admin-debug UI.** This is the client capability it needs; the UI, its banner, and how an admin picks a subject are out of scope.
- **A hard cap on impersonation duration** — see Decisions; the re-mint is where one would live if ever wanted.
- **Any convenience getter for "am I impersonating"** — `claims` answers it; adding one waits for a caller.
- **Server-side authorization changes.** The endpoint's gate chain is unchanged and no new authz decision is added anywhere. ⚠️ The `ttlSeconds` parameter is a server-side *capability* change, not an authorization one — clamped, it can only reduce a token's lifetime.
- **The verified-claims header on the edge→DO hop** — filed in [backlog.md](backlog.md) § `@lumenize/auth`. Independent: `impersonate()` rides `authedFetch`, which that work does not touch.
- **Studio reflecting `activeScope` in the URL** ([ADR-017](../docs/adr/017-the-url-is-the-view-state.md), `backlog.md` § Nebula Studio UI) — the other half of the support flow. Neither task gates the other.
- **A full-fidelity codegen turn under impersonation** — a `wrangler dev` + Docker follow-on if wanted, not this task.
