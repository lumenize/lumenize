## Context

One of Lumenize Nebula's main selling points is that every app built automatically gets a robust fine-grained access control model using our DAG orgTree model for Resources.

Right now, the preview in Nebula Studio is a single iframe. The user-dev is be expected to log in as founder, invite other users with their own dummy email addresses, accept those invites, and then log out as founder and in as each of those other users one at a time to test their fine-grained access control and see how the UI changes based upon those permissions. That does not align with Lumenize's de✨light✨ful DX core value.

Further, we want to guide each user to good software development practices and one of those practices includes utilizing a cast of named personas to think about the experience of their users. We already have some support in the platform standing guidance for encouraging this but we have more planned including testing. That guidance is `apps/nebula/platform/`: `AGENTS.md` names the cast file, and `apps/nebula/platform/skills/define-the-cast/SKILL.md` is the skill that elicits it. The files the model writes into the user-developer's Workspace repo are `docs/personas.md` and `docs/permissions.md`; the skill itself is ours and ships in the bundle. There is no third file — see § *Pinned*.

This task is the next increment on that fine-grained permissioning journey and we've chosen to tie the permissioning model to a cast of personas, not a list "roles", partially to highlight the difference between our ReBAC, not RBAC, model. That case is made in [auth.md](../docs/vision/auth.md) § *The layers a call passes* — the M7 data-plane DAG bullet, and the *Why relationships rather than roles?* paragraph beneath it, which cites AuthZed on role explosion.

## Objective and goals

**Objective -- create a de✨light✨ful experience for testing a Studio authored app as each persona.**

**Goals:**

1. **Provision each persona as a user.** Everytime the personas file changes, either provision from scratch, if the .dev Star was wiped, or adjust the existing provisioning to match the latest version of that file.
2. **Populate with (on a wipe), or adjust existing (no wipe), test data to minimally show off the difference in each persona's permissions.** *(In scope, and § *Pinned* carries how — a fifth verb in the procedure, written as the owning persona.)*
3. **Accept each persona's invite.** Create dynamic email addresses for each persona. Send those emails and auto-accept those invites. *(The address, who composes it, and where production reads the resulting mail are all in § *Pinned*.)*
4. **Log each persona in to a separate tab in the preview area.** The preview area gets a list of tabs with the persona slug as the tab label.

## Design intent — a cast of real users, and where each half runs

**Provisioning a cast is server work; being one is browser work.** The Galaxy mints each persona's membership, builds the tree and attaches the grants. Studio opens a tab per persona, and **every tab is a real login** — its own session, its own refresh cookie, obtained the way any member's is. The seam between the halves is a link, and finding the right one took two wrong turns worth recording, because both are the obvious first answer and the second ran for a day.

**First attempt — one server-side executor does all of it**: mint, accept each persona off inbound mail, then write that persona's data by impersonating it. It fails at the code. A Durable Object holds `callContext.originAuth`, which is **verified claims rather than a replayable credential**, so it has no session to mint from and the mint is an authed HTTP call. And seeding runs *after* the mail round trip, by which time the confirm has returned and nothing holds the authority to do it at all.

**Second attempt — tabs run under impersonation**, minted by Studio off the user-developer's own session and handed into each iframe. Subtler, and wrong in three ways at once. It needs the parent to hand a renewal closure across a realm boundary, which reopens a widening [backlog.md](backlog.md) § *Lumenize Mesh* forbids by name — and whose failure mode is a tab's session quietly renewing **as the user-developer** while its label still reads `mary`. The teardown seam does not cross realms, so a tab outlives the user-developer's logout until its own token lapses. And the gate meant to select a persona tab cannot distinguish the user-developer's own, which the mint refuses to impersonate anyway.

**What we do: every tab is a real login**, and the auth mechanics are their own file. Two things had to become true, and both live in [nebula-persona-sessions.md](nebula-persona-sessions.md): a refresh cookie per membership, so eight tabs at one scope stop overwriting each other; and a restricted rule under which a platform-issued identity's invite link may be handed to a caller instead of delivered to a mailbox. That file carries the rule, its three clauses, and the [ADR-012](../docs/adr/012-global-profile-visibility.md) amendment that licenses it.

- **The Galaxy owns provisioning.** Ask the Registry which personas have accepted, mint and invite the ones it does not know, build nodes and edges, attach grants, write the run record. All synchronous, all under the confirming user's claims.
- **Studio owns being them.** Per open tab: request that persona's invite link, follow it in the tab, accept — and the tab now holds a real session. Seeding that persona's data runs through the same session, so what it writes is genuinely its own.

⚠️ **Impersonation is gone from this feature entirely.** It remains what it was built for — the admin-debug flow in [backlog.md](backlog.md) § *Nebula Studio UI* — and a tab is not it. That also retires a claim this file made for a day: *"impersonation is a browser capability"* is false, and the three `/live` scenarios that impersonate from plain Node with `needsContainer = false` are the disproof. What is true is narrower: a DO has no session to mint from.

### Why the mail round trip is not needed, and why the mail still goes

The invite link exists server-side the moment the membership is minted — `issueInvites` hands it to the entry that builds the letter, and only the caller-facing summary strips it. Routing real mail to a mailbox nobody reads, to fish that value back out, is a delivery pipeline for something already in the room.

⚠️ **What made that fence right is not transport, and it nearly cost us a security hole.** An invite URL is a bearer credential for the identity it names: follow it and you may accept that membership, and by [ADR-013](../docs/adr/013-identity-profileid-resolution.md) one address is one Profile globally, so accepting for someone else's address reaches their Profile everywhere. The prerequisite's rule is what makes issuing one safe, and it turns on the address belonging to a namespace no human can hold — never on the caller's authority, because dominion is scope-local and a `profileId` is not.

**Real invite mail still sends**, because nothing depends on reading it and [ADR-009](../docs/adr/009-real-auth-path.md) prefers the real path where it costs nothing. **No inbound receiver is built**: this task ships no `email()` handler, no ingress, and no path by which outside content reaches the platform.

## The order it runs in — a sketch, expected to change

⚠️ **Roughed out 2026-09-09 and deliberately not pinned** (Larry: *we'll have to evolve this with trial and error*). It follows § *Design intent*'s split: the Galaxy does one synchronous pass, and everything after it happens per tab, in the browser.

**① In the Galaxy, inside the confirm.** Nodes and edges need no ontology — the DAG has its own tables — and the facade's `invite` returns each `sub` synchronously, so the tree and every grant land in one pass:

1. **read acceptance** per persona from the Registry; **mint and invite** the ones it does not know
2. **node** → **edge**, building the tree
3. **grant** — `setPermission` per persona, needing the `sub` from 1 and the node from 2
4. write `.nebula/`: the slug-to-`sub` map, plus which personas are still pending
5. return the realized tree, the map, and each persona's acceptance state

**② In Studio, per tab, once.** A persona that already accepted skips this entirely:

6. request that persona's invite link → navigate the tab to it → the consume places **that tab's own refresh cookie** → POST accept, carrying the display name in the same body

**③ In Studio, per persona.** Seeding writes through the tab's own session, so what it writes is genuinely that persona's:

7. for each accepted persona with unseeded data steps: run them through that tab's session, then mark them done

⚠️ **Seeding keys on the persona being USABLE, never on a step ② having just run.** An accepted persona survives a `.dev` wipe on the same `sub`, so after a wipe ③ runs for the whole cast and ② never fires — which is the case goal 2 names. Chaining ③ to ② would strand it.

**This does not fight the one-procedure pin.** One authored procedure, one validation, one confirm — what changes is that its steps are applied in two places, and ① returns before ② and ③ finish. The pending work waits in the `.nebula/` record, which already survives `resetDevData`. ⚠️ ③'s first write against a freshly wiped Star may answer `installing` while the Star's lazy ontology pull completes, and the client retries — so the seeding step handles a retry rather than assuming first-time success.

## Verified on disk — so it need not be re-derived

- **`invite()` returns the minted `sub`** on `InviteeSummary`, which is the slug-to-`sub` map's source. ⚠️ **And nothing else** — the type is `{ email, sub, outcome }`, and `summarizeInvites` is what strips `accepted` and `inviteUrl` before any caller sees them. ⚠️ **The `inviteUrl` half of that fence is a SECURITY fence, not plumbing**: the URL is a bearer credential for the identity it names, so crossing it is what [nebula-persona-sessions.md](nebula-persona-sessions.md)'s rule licenses, and only inside a namespace no human can hold. The `accepted` half is unrelated — acceptance comes from the Registry read (§ *Pinned*).
- **`impersonate()` is built and driven, and this task no longer uses it.** Three `/live` scenarios exercise it — `impersonation-lifecycle.ts`, `impersonation-expiry.ts`, `profile-takeover-refused.ts` — all with `needsContainer = false`, from plain Node. ⚠️ That is the disproof of a claim this file carried for a day: impersonation is not a browser capability. What is true is narrower — a Durable Object has no session to mint from, because `callContext.originAuth` is verified claims rather than a replayable credential. Tabs are real logins instead (§ *Design intent*); impersonation stays the admin-debug flow's.
- **`dagTree().setPermission` attaches the grants.** ⚠️ After ④ ([nebula-data-plane-owns-its-guards.md](nebula-data-plane-owns-its-guards.md)) the entrance is gone, not merely re-homed: that task's § *Design intent, constraints, and future state* states `@mesh() dagTree()` does not survive beside the one `resources()` door, and the call becomes `resources().dagTree.setPermission(...)` — **no parens on `dagTree`, it is a getter**. Type-check catches every stale site, so this needs no letter; a site written before ④ carries a `TEMP → target=resources() gate` comment, as `star.ts`'s host forwards already do.
- **A re-provision reuses the persona's `sub`, and an accepted persona stays accepted through a `.dev` wipe.** `Memberships` carries `UNIQUE (emailId, universeGalaxyStarId)`; `#mintIdentity` early-returns the existing row and its JSDoc says the mint never touches the `scopeAdmin` or `accepted` state it reports; and `Star.resetDevData` is a `.dev`-guarded `deleteAll()` on that Star's own storage, so the Registry is untouched. An unchanged persona therefore needs no second round trip — it is immediately impersonable after a wipe, on the same `sub`, and the `.nebula/` map stays valid. ⚠️ **One-time only**: ⑥'s worker-delete destroys the Registry, after which every persona re-mints pending.
- **Re-inviting an accepted persona still sends mail, just a link-less letter.** `invite-entry.ts`'s `buildInviteMessage` discriminates on acceptance: an accepted member gets `invite-existing`, a landing `redirectUrl` with no magic link. ⚠️ **Provisioning never reaches that branch** — it invites only a persona the Registry read calls unaccepted or absent (§ *Pinned*), so every letter it sends is `invite-new`. The discrimination matters here as the reason a re-provision costs nothing, not as a path this task exercises.
- **The preview already runs as the user-developer, and reaches `.dev` two different ways.** The scaffold builds its client from an injected scope — `authScope` the parent Galaxy, `activeScope` the `.dev` Star. A Galaxy creator holds no `.dev` membership (`createGalaxy` withholds it) and arrives by dominion; a collaborator holds one, because `issueInvites` mints `{scope}.dev` on every galaxy-tier invite. Neither is a persona.
- **A Star lazy-pulls an ontology version it does not hold.** `appendWorkspaceOntology`'s JSDoc states it — the Star pulls `getOntologyVersion(version)` from its Galaxy *"inside that op's own call context"*, and upward passage is free for every member so it works under any claims — and `star.ts` implements both arms: `#pullOntology(version)` for a client-pinned version and `#pullOntologyCurrent()` for first touch, with a result handler that survives the DO's eviction. ## The address facts, and why they stopped blocking

**Two facts about the address had never been checked, and until 2026-09-09 they gated Pass 2** — the design routed persona mail into a platform handler, so a `~` the provider refused, or a subdomain that was not a valid destination, would have broken provisioning outright. **Neither blocks any more.** Nothing reads persona mail, so a send that fails is log noise rather than a stalled cast.

- **Does a `~` local part survive an outbound send, and is `personas.lumenize.io` a valid verified destination for Routing?** Worth answering before the mail row is called done, and cheap — one send. Not a gate.
- ⚠️ **What the `~` still IS load-bearing for is internal and already verified**: `isValidEmail` accepts it, `normalizeEmail` lowercases around it, and the rule licensing an issued link parses the address's `{u}.{g}.{s}` prefix on it (§ *Pinned*). That parse is the security boundary, and it never leaves our own code.

## The coverage this task owes

`.claude/rules/live.md` makes `/live` the first tier for behavioural work, and **nothing here is pure** — a real mail round trip, a real accept through the two endpoints a human uses, real impersonation, a tab strip. Two scenarios, split on `needsContainer` because the boundary is measured rather than tasteful: the provisioning half runs container-free in about thirteen seconds and belongs in the inner loop; the tab half needs the built app in the iframe and pays the full `build-box` path at about a hundred and ten.

- **`personas-provisioned` (no container).** Claim a Galaxy, seed a two-persona cast, provision. Each persona's link is requested, the tab follows it, both personas accept, and the tree and grants match the prose — all of it against a local stack, since nothing waits on inbound mail. Then wipe the `.dev` Star and re-provision: **each persona keeps the same `sub`, no mail is sent at all, and seeding still runs** — which is the case the run order's ③ exists to protect.
- **`persona-tabs` (container).** Two tabs open in the strip, each renders the built app as its persona under its own session, with the user-developer performing no login, and the denied persona sees its **disclosed denied-node set** rather than an empty screen — which is what makes the [ADR-008](../docs/adr/008-full-org-tree-visibility.md) criterion below checkable at all. Closing a tab tears down its client; disposing the parent tears down every tab.

⚠️ **A mutation per LIMB, never per scenario.** A multi-limb scenario reddens on its first failing limb and hides every later limb's vacuity, so each limb needs a mutation that isolates it and a positive control proving the thing it calls is reachable. Where a limb asserts a refusal, **match the message** — a boundary refusal and a dominion refusal are the same boolean, and telling them apart is usually the point.

⚠️ **`drive.ts all` is a phase criterion, not a closing chore.** Sixteen of the twenty-eight scenarios in the registry touch the scaffold, login or invite paths this task changes, and a scenario nobody owns breaks silently. The guidance edits additionally ride `.claude/rules/studio-guidance.md` § *Changing what the model is told* — `studio-guidance-loop`, `four-party-chat` and `first-app-built` — and a limb whose outcome moves owes a dated findings line in [nebula-pre-alpha.md](nebula-pre-alpha.md) § *Data-bound generation*.
