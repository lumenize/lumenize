## Context

One of Lumenize Nebula's main selling points is that every app built automatically gets a robust fine-grained access control model using our DAG orgTree model for Resources.

Right now, the preview in Nebula Studio is a single iframe. The user-dev is be expected to log in as founder, invite other users with their own dummy email addresses, accept those invites, and then log out as founder and in as each of those other users one at a time to test their fine-grained access control and see how the UI changes based upon those permissions. That does not align with Lumenize's de✨light✨ful DX core value.

Further, we want to guide each user to good software development practices and one of those practices includes utilizing a cast of named personas to think about the experience of their users. We already have some support in the platform standing guidance for encouraging this but we have more planned including testing. That guidance is `apps/nebula/platform/`: `AGENTS.md` names the cast file, and `apps/nebula/platform/skills/define-the-cast/SKILL.md` is the skill that elicits it. The files the model writes into the user-developer's Workspace repo are `docs/personas.md` and `docs/permissions.md`; the skill itself is ours and ships in the bundle. There is no third file — see § *Pinned*.

This task is the next increment on that fine-grained permissioning journey and we've chosen to tie the permissioning model to a cast of personas, not a list "roles", partially to highlight the difference between our ReBAC, not RBAC, model. That case is made in [auth.md](../docs/vision/auth.md) § *The layers a call passes* — the M7 data-plane DAG bullet, and the *Why relationships rather than roles?* paragraph beneath it, which cites AuthZed on role explosion.

## Objective and goals

**Objective -- create a de✨light✨ful experience for testing a Studio authored app as each persona.**

**Goals:**

1. **Provision each persona as a user.** Everytime the personas file changes, either provision from scratch, if the .dev Star was wiped, or adjust the existing provisioning to match the latest version of that file. *(Since ADR-022 nothing is provisioned in the Registry: provisioning is each persona's nodes, edges and grants, keyed on the id its host spells, plus the Galaxy's record of whom it provisioned.)*
2. **Populate with (on a wipe), or adjust existing (no wipe), test data to minimally show off the difference in each persona's permissions.** *(In scope, and § *Pinned* carries how — a verb in the procedure, written as the owning persona.)*
3. ~~**Accept each persona's invite.** Create dynamic email addresses for each persona. Send those emails and auto-accept those invites.~~ *(Obsolete since ADR-022: a persona has no address, invite or accept. Larry's to cut or rewrite.)*
4. **Log each persona in to a separate tab in the preview area.** The preview area gets a list of tabs with the persona slug as the tab label.

## Design intent — a cast on hosts of its own

**Provisioning a cast is Galaxy work; being one is a page on the persona's own host.** The Galaxy builds the tree, attaches each persona's grants, and records whom it provisioned. Studio frames one host per open persona, such as `mary--dev.crm.acme.lumenize.dev`, and the page there gets a token as Mary from the cookie of the user-developer who opened it. Nothing is created in the Registry: Mary has no address, no membership, no invite to accept and no cookie of her own.

- **A persona's identity is computed, never stored.** Its `sub` and `profileId` are one version-5 UUID of `acme.crm.dev/mary`, from `personaId` in `packages/mesh/src/auth/hosts.ts`. So a grant attached before Mary's tab ever opens names the `sub` her token will carry, and a `.dev` wipe changes nothing about who she is.
- **The Galaxy owns provisioning.** It runs the procedure's nodes, edges and grants under the confirming user's claims, then writes the record. ADR-022 asks for the record because `personas.md` drops a removed persona, and the record is what lets a deletion or a rename reap that persona's Profile.
- **Studio owns being them.** For each open tab it frames the persona's host. The page refreshes off the opener's cookie, which ADR-022 allows only in a Star with no real users, today only `dev`, and only where that cookie's membership has dominion over the Star. Seeding writes through a persona's token, so what Mary writes is genuinely Mary's.
- **The token is plain:** Mary's `sub` and `profileId`, `acme.crm.dev` as `authScope` and `aud`, and no `act` or `scopeAdmin`. ADR-022 trades attribution for testing fidelity here, which costs nothing on a Star with no real users.

**It took three wrong turns to get here, and each is the obvious first answer.**

1. **One server-side executor does all of it**: mint, accept each persona off inbound mail, then write that persona's data by impersonating it. A Durable Object holds `callContext.originAuth`, which is verified claims rather than a replayable credential, so it has no session to mint from. And seeding runs after the mail round trip, by which time nothing holds the authority to do it.
2. **Tabs run under impersonation**, minted by Studio off the user-developer's own session and handed into each iframe. The parent has to hand a renewal closure across a realm boundary, which [backlog.md](backlog.md) § *Lumenize Mesh* forbids by name, and whose failure is a tab quietly renewing as the user-developer while its label still reads `mary`. A tab also outlives the user-developer's logout, and the gate meant to select a persona tab cannot tell the user-developer's own.
3. **Every tab is a real login** (2026-09-09 to 2026-09-18): a real account per persona at `acme.crm.dev~mary@personas.lumenize.io`, a refresh cookie per membership so eight tabs at one scope stop overwriting each other, and the invite link handed to Studio instead of a mailbox. It was safe only because no human could hold a persona's address, which is a negative to prove. A persona with no address at all makes that true by construction.

Impersonation stays what it was built for, the admin-debug flow in [backlog.md](backlog.md) § *Nebula Studio UI*. A persona tab is not it.

## Questions the rewrite owes

1. **Can a collaborator whose memberships carry no admin bit open a persona tab?** ADR-022 lets a page refresh as a persona only where the opener's membership has dominion over the Star. A peer's invite co-mints the `.dev` membership without the admin bit when the inviter lacks dominion (`issueInvites`), so that collaborator can open no tab. The struck two-floors row had given them one.
2. **How does seeding reach a persona whose tab is closed?** Only a page on the persona's host can get its token, and not every tab opens by default (the strip row).
3. **Where is a persona's display name written?** The accept used to carry it. A persona nobody has written has an empty Profile, and only a token as that persona owns it.
4. **What is the Galaxy's record of whom it provisioned?** ADR-022 requires one. Whether it is the `.nebula/` run record in the Workspace repo, or Galaxy storage, decides what a galaxy's deletion can read when it reaps.
5. **Are iframes still the only kind of tab?** Each persona is now its own origin, and a separate browser tab on its host refreshes off the same cookie, so the iframe row's reason now holds for both.
6. **Does the `me` check still earn its place?** `parseHost` refuses a persona slug shorter than three characters (`MIN_PERSONA_SLUG_LENGTH` in `hosts.ts`, which keeps a label out of punycode's `xn--` shape), so the host grammar already refuses `me`.

## The order it runs in — a sketch, expected to change

⚠️ **Roughed out 2026-09-09, re-cut 2026-10-08 for ADR-022, and deliberately not pinned** (Larry: *we'll have to evolve this with trial and error*). The Galaxy does one synchronous pass, and everything after it happens per tab, in the browser.

**① In the Galaxy, inside the confirm.** Nodes and edges need no ontology, and every persona's `sub` is computable, so the tree and every grant land in one pass:

1. **node** → **edge**, building the tree
2. **grant** — `setPermission` per persona, naming `personaId(star, slug)` and a node from step 1
3. write the record of whom it provisioned
4. return the realized tree

**② In Studio, per open tab.** Frame the persona's host; the page refreshes off the opener's cookie and holds a token as that persona. Nothing is accepted and nothing waits on mail.

**③ Seeding, per persona.** For each persona with unseeded data steps, run them through that persona's token, then mark them done. Question 2 asks how this reaches a persona whose tab is closed.

⚠️ **Seeding keys on the target node being empty, never on a tab having just opened.** After a `.dev` wipe every node is empty and every persona keeps its `sub`, so ③ runs for the whole cast — the case goal 2 names. Its first write against a freshly wiped Star may answer `installing` while the Star's lazy ontology pull completes, and the client retries, so the seeding step handles a retry rather than assuming first-time success.

## Verified on disk — so it need not be re-derived

- **A persona's `sub` and `profileId` are computed from its host, so they survive anything.** `personaId(star, slug)` in `packages/mesh/src/auth/hosts.ts` hashes `acme.crm.dev/mary` into a version-5 UUID under a fixed namespace, and a person's ids from `crypto.randomUUID()` are always version 4. A re-provision, a `.dev` wipe and ⑥'s worker-delete all leave it unchanged.
- **The host grammar validates a persona's slug.** `parseHost` in `hosts.ts` refuses a persona label that fails `isValidSlug` or is shorter than three characters, and `parse-id.ts` caps a slug so `{persona}--{star}` fits one 63-character label.
- **`impersonate()` is built and driven, and this task does not use it.** Three `/live` scenarios exercise it — `impersonation-lifecycle.ts`, `impersonation-expiry.ts`, `profile-takeover-refused.ts` — all with `needsContainer = false`, from plain Node.
- **`resources.orgTree.setPermission` attaches the grants.** ④ ([nebula-data-plane-owns-its-guards.md](archive/nebula-data-plane-owns-its-guards.md), built 2026-09-28) deleted `@mesh() orgTree()`; the tree is reached through each host's one `@mesh() get resources` door as `resources.orgTree.setPermission(...)` — **no parens on either, both are getters**. Type-check catches a stale site.
- **The preview already runs as the user-developer, and reaches `.dev` two different ways.** The scaffold builds its client from an injected scope — `authScope` the parent Galaxy, `activeScope` the `.dev` Star. A Galaxy creator holds no `.dev` membership (`createGalaxy` withholds it) and arrives by dominion; a collaborator holds one, because `issueInvites` mints `{scope}.dev` on every galaxy-tier invite. Neither is a persona.
- **A Star lazy-pulls an ontology version it does not hold.** Since ④ the rule is the plane's: an op on a Star with nothing installed, or pinned to a version other than the installed one, asks the Galaxy for its CURRENT row with `getCurrentOntology()` under the op's own claims — upward passage is free for every member, so it works under any claims — and is answered `installing` while the client retries. The answer lands at `resourcesResults.onOntologyPulled`, which survives the DO's eviction; a Galaxy with nothing applied answers `null` and the Star installs nothing. ⚠️ So a `.dev` wipe does not strand seeding, and the only real precondition is that an ontology was applied at least once.
- **A tab can write as its persona, and can ask whether a node is empty.** Both fall out of the tab holding an ordinary token: `resources.transaction` writes and `resources.subscribeQuery` reads, exactly as the app itself does. ⚠️ **`subscribeQuery` is permission-filtered per subscriber**, so an emptiness check run as persona A reads a node A cannot see as empty — the check must run as the persona whose data it gates, or as a caller that can see the whole node.
- **The model holds no scope slug, so it cannot compose a host.** `TOOL_CONTRACT` in `codegen-loop.ts`, `apps/nebula/platform/AGENTS.md` and the Workspace `AGENTS.md` seed carry no universe or galaxy identifier; the one `.universe/` mention is a reserved path prefix. Checked 2026-09-08.
- **The two shipped cast-guidance homes are `apps/nebula/container/app/docs/personas.md` and `platform/skills/define-the-cast/SKILL.md`.** Both ship — through `scaffold-seed.ts` and `platform-embed.ts`, each held by a drift test — so the model reads them every turn, and an edit that skips the regenerate reaches nobody (`.claude/rules/studio-guidance.md` § *How the homes ship*). Both were corrected on 2026-09-11: neither names an address, and both key on the slug. Two of § *Criteria*'s sub-edits are still open: step 6's hand-off, and the worked step 1's bundled `scopeAdmin`.

## The coverage this task owes

`.claude/rules/live.md` makes `/live` the first tier for behavioural work, and **nothing here is pure** — a real persona refresh off a real login's cookie, a real provisioning confirm, a tab strip. Two scenarios, split on `needsContainer` because the boundary is measured rather than tasteful: the provisioning half runs container-free in about thirteen seconds and belongs in the inner loop; the tab half needs the built app in the iframe and pays the full `build-box` path at about a hundred and ten.

- **`personas-provisioned` (no container).** Claim a Galaxy, seed a two-persona cast, provision. Each persona's page refreshes off the claimant's cookie, and the tree and grants match the prose, all against a local stack. Then wipe the `.dev` Star and re-provision: **each persona keeps the same `sub`, and seeding runs again** — which is the case the run order's ③ exists to protect.
- **`persona-tabs` (container).** Two tabs open in the strip, each renders the built app as its persona under its own token, with the user-developer performing no login, and the denied persona sees its **disclosed denied-node set** rather than an empty screen — which is what makes the [ADR-008](../docs/adr/008-full-org-tree-visibility.md) criterion below checkable at all. Closing a tab tears down its client; disposing the parent tears down every tab.

⚠️ **A mutation per LIMB, never per scenario.** A multi-limb scenario reddens on its first failing limb and hides every later limb's vacuity, so each limb needs a mutation that isolates it and a positive control proving the thing it calls is reachable. Where a limb asserts a refusal, **match the message** — a boundary refusal and a dominion refusal are the same boolean, and telling them apart is usually the point.

⚠️ **`drive.ts all` is a phase criterion, not a closing chore.** Many scenarios in the registry touch the scaffold, login or Studio paths this task changes, and a scenario nobody owns breaks silently. The guidance edits additionally ride `.claude/rules/studio-guidance.md` § *Changing what the model is told* — `studio-guidance-loop`, `four-party-chat` and `first-app-built` — and a limb whose outcome moves owes a dated findings line in [nebula-pre-alpha.md](nebula-pre-alpha.md) § *Data-bound generation*.

- **The scaffold no longer self-redirects to `/login` in a dev preview**, so a failed persona session leaves the iframe where Studio can paint it. Mutation: restore the redirect, and a tab whose session fails shows a login page inside the preview strip.

- **A slug the validator refuses stops the run before anything is composed.** Uppercase, `.`, `~`, `@`, a leading or trailing hyphen and `--` are all refused, because the slug is the persona's KEY and its host and `sub` are derived from it. - **No verb does two things, and none names `scopeAdmin`.** `grant` carries a DAG tier and nothing else. Mutation: give the procedure a way to request `scopeAdmin`, and the persona that gets it bypasses `requirePermission` on the whole `.dev` Star — so every grant in the cast becomes decorative and the demo silently stops demonstrating anything.
