## Context

One of Lumenize Nebula's main selling points is that every app built automatically gets a robust fine-grained access control model using our DAG orgTree model for Resources.

Right now, the preview in Nebula Studio is a single iframe. The user-dev is be expected to log in as founder, invite other users with their own dummy email addresses, accept those invites, and then log out as founder and in as each of those other users one at a time to test their fine-grained access control and see how the UI changes based upon those permissions. That does not align with Lumenize's de✨light✨ful DX core value.

Further, we want to guide each user to good software development practices and one of those practices includes utilizing a cast of named personas to think about the experience of their users. We already have some support in the platform standing guidance for encouraging this but we have more planned including testing. That guidance is `apps/nebula/platform/`: `AGENTS.md` names the cast file, and `apps/nebula/platform/skills/define-the-cast/SKILL.md` is the skill that elicits it. The files the model writes into the user-developer's Workspace repo are `docs/personas.md` and `docs/permissions.md`; the skill itself is ours and ships in the bundle. There is no third file — see § *Pinned*.

This task is the next increment on that fine-grained permissioning journey and we've chosen to tie the permissioning model to a cast of personas, not a list "roles", partially to highlight the difference between our ReBAC, not RBAC, model. That case is made in [auth.md](../docs/vision/auth.md) § *The layers a call passes* — the M7 data-plane DAG bullet, and the *Why relationships rather than roles?* paragraph beneath it, which cites AuthZed on role explosion.

## Objective and goals

**Objective -- create a de✨light✨ful experience for testing a Studio authored app as each persona.**

**Goals:**

1. **Provision each persona as a user.** Everytime the personas file changes, either provision from scratch, if the .dev Star was wiped, or adjust the existing provisioning to match the latest version of that file.
2. **Populate with (on a wipe), or adjust existing (no wipe), test data to minimally show off the difference in each persona's permissions.** *(In scope, and § *Pinned* carries how — a fifth verb in the procedure, written as the owning persona.)*
3. **Accept each persona's invite.** Create dynamic email addresses for each persona. Send those emails and auto-accept those invites. *(The address, who composes it, and where production reads the resulting mail are all in § *Pinned*.)*
4. **Log each persona in to a separate tab in the preview area.** The preview area gets a list of tabs with the persona slug as the tab label.

## Design intent — where each half runs, and why

**The four goals do not all run in the same place, and that is the whole design.** Provisioning a cast is server work: mint memberships, build the tree, attach grants, answer a mail round trip. Running a cast is browser work: several seats, each holding an identity, each rendering an app. The seam between them is a credential, and finding it took two wrong turns worth writing down, because both are the obvious first answer.

**First attempt — one server-side executor does all of it.** `provision(procedure)` runs in the Galaxy under the confirming user's claims: mint each persona, accept it off the inbound mail, then seed that persona's data by impersonating it. It fails twice at the code. `impersonate()` is a `NebulaClient` instance method — it wants `window.location.origin`, a client that has connected at least once, and an `authedFetch` that refreshes through the refresh cookie; a Durable Object has none of the three. And seeding runs *after* the mail round trip, by which time the confirm has returned and the accept session has been discarded, so nothing holds the authority to do it at all.

**Second attempt — give each persona its own cookie, and let each iframe log in normally.** Then no handoff is needed and every seat authenticates the way a real user does. This fails on a fact about the cookie rather than about the design. `worker-token.ts` writes one fixed name at one path per scope — `refresh-token=…; Path=/auth/{scope}; HttpOnly; Secure; SameSite=Strict` — and every persona is a member of the same scope, `{u}.{g}.dev`. Same-origin iframes share one jar, so the second persona's cookie overwrites the first's, and `handleAcceptMembership` resolves whatever cookie it finds to *its own* membership rather than to the scope named in the URL — which makes the collision a silent identity swap instead of a refusal.

**What we do: split at the credential.**

- **The Galaxy owns provisioning.** Ask the Registry which personas have accepted, mint and invite the ones it does not know, build nodes and edges, attach grants, write the run record; then, when a persona's mail arrives, follow the link and POST the accept carrying the display name. That tail needs no user claims at all — it authenticates as the persona it has just become, off the `Set-Cookie` the link handed back.
- **Studio's page owns running.** Per open seat it calls `client.impersonate(sub, devStar)` and hands the result to that seat's iframe. Seeding a persona's test data is the same call — a `resources.transaction` through the impersonated child, in the page where the user-developer's live session already is.

### The seat handoff

`impersonate()` already builds a cookie-less client and seeds it with a token plus a renewal closure:

```ts
const child = new NebulaClient({
  ...this.#childConfigBase,
  authScope: activeScope,                 // INERT on a child — it has no cookie
  activeScope,
  accessToken: minted.access_token,       // seeded, never fetched
  [INTERNAL_REFRESH]: async () => mint(), // renews through the parent
});
```

A persona seat needs that same shape one realm over. Same-origin makes `iframe.contentWindow` reachable, so the parent hands across `{ accessToken, refresh }` — a string and a closure, never a client instance, so the parent's bundle and the iframe's never have to share a class. Two changes carry it: `createNebulaClient` accepts those two as supported inputs rather than internal symbols, and the scaffold's `nebula.ts` waits for the handoff on a persona seat instead of self-authenticating. The generated app above it changes not at all — it already awaits `ready`, which simply resolves a beat later.

The gate is `isDevPreview`, which already exists in `nebula.ts` and is already load-bearing for `onReload`. It reads the scope the Galaxy stamps into the page, so a tenant Star computes `false` and the persona path is inert there.

### Why the cookie route stays closed — and the one trigger to reopen it

The jar collision bites first and is the only one a cookie redesign would fix. Two more survive it, and both are about a durable credential existing at all:

- **A per-persona refresh cookie manufactures a 30-day credential for someone else's identity.** Already rejected on exactly those grounds for the admin-debug UI ([backlog.md](backlog.md) § *Nebula Studio UI*, the impersonation row), where the shipped answer was a session whose lifetime is the admin's.
- **Impersonation revokes; a cookie does not.** `impersonate()`'s JSDoc states the property: the parent is the credential, no durable credential is created anywhere, and the session dies with the parent client rather than at term. Disposing Studio's client tears every seat down through one seam, `onClientTornDown`. A cookie outlives the user-developer's logout.

⚠️ **The trigger to reopen is a requirement we do not have: a persona session that must OUTLIVE Studio's page** — survive a close, or be driven by something that is not Studio. Cookies win that outright. Nothing in the four goals asks for it; if something later does, reopen this rather than work around it.

**The fidelity cost is two sites wide and enumerable.** A seat's token carries `act` where a real end user's does not, so anything reading `act` differs. There are two such sites: `forwardWithSubject`, which withholds the tenancy summary and expand-scope views under impersonation, and the mint's root-identity gate refusing to re-narrow. Neither is a surface a generated app reaches. [ADR-009](../docs/adr/009-real-auth-path.md)'s ladder is satisfied where it matters — a persona's *acceptance* is a real login against a real mailbox, rung 1; only its runtime session is impersonated.

### What this settles, and what it leaves out

**Seeding waits on impersonability, never on mail.** An accepted persona survives a `.dev` wipe on the same `sub`, so it is impersonable at once and its data steps run with no letter sent. Acceptance and seeding stop being a chain, which is what makes goal 2's *"populate on a wipe"* reachable.

**Out of scope, deliberately: the model driving the preview.** Studio's page can reach `iframe.contentDocument`, so a Studio-resident driver would let the model exercise the app it just wrote. That capability is real and wanted, and it is scoped separately in [nebula-pre-alpha-fast-follow.md](nebula-pre-alpha-fast-follow.md) § *Item 10*. It shares one dependency with this design, worth stating here because nothing else states it: **both the seat handoff and any future driver rest on the preview being same-origin with Studio.**

## The order it runs in — a sketch, expected to change

⚠️ **Roughed out 2026-09-09 and deliberately not pinned** (Larry: *we'll have to evolve this with trial and error*). It is here so Pass 2 starts from a shape rather than inventing one. It follows § *Design intent*'s split: three phases, and the executor changes hands twice.

**① In the Galaxy, inside the confirm.** Nodes and edges need no ontology — the DAG has its own tables — and the facade's `invite` returns each `sub` synchronously, so the tree and every grant land in one pass:

1. **read acceptance** per persona from the Registry; **mint** the ones it does not know
2. **node** → **edge**, building the tree
3. **grant** — `setPermission` per persona, needing the `sub` from 1 and the node from 2
4. write `.nebula/`: the slug-to-`sub` map, plus which personas are still pending
5. return the realized tree, the map, and each persona's acceptance state

**② In the Galaxy, per persona, off the mail.** Acceptance is a round trip, so it waits on that persona and no other. It carries no user claims — it authenticates as the persona it has just become:

6. receiver parses the address → follow the link → POST accept, carrying the display name in the same body → mark that persona accepted in `.nebula/`

**③ In Studio's page, per persona.** Seeding runs AS the persona, so it runs where impersonation lives:

7. for each accepted persona with unseeded data steps: `impersonate(sub, devStar)` → run its steps through that child → mark them done

⚠️ **Seeding keys on IMPERSONABILITY, never on mail arriving.** An accepted persona survives a `.dev` wipe on the same `sub`, so after a wipe ③ runs immediately for the whole cast and ② never fires — which is the case goal 2 names. Chaining ③ to ② would strand it.

**This does not fight the one-procedure pin.** One authored procedure, one validation, one confirm — what changes is that its steps are applied by two executors rather than one, and ① returns before ② and ③ finish. The pending work waits in the `.nebula/` record, which already survives `resetDevData`. ⚠️ ③'s first write against a freshly wiped Star may answer `installing` while the lazy pull completes, and the client retries — so the seeding step handles a retry rather than assuming first-time success.

## Verified on disk — so it need not be re-derived

- **`invite()` returns the minted `sub`** on `InviteeSummary`, which is the slug-to-`sub` map's source. ⚠️ **And nothing else**: that type is `{ email, sub, outcome }`, its JSDoc says it *carries no token or URL*, and `InviteSummary.links` — the raw invite URLs — appears in test mode only, where the same JSDoc calls it the sole carrier of the URL past the entry. So the invite call cannot hand Studio a link to click — which is why a receiver exists at all (§ *Pinned*) — and cannot report acceptance either: `summarizeInvites` strips `accepted` and `inviteUrl`, and two tests pin the exact key set against unfiltered pass-through. Acceptance comes from the Registry read instead (§ *Pinned*).
- **`impersonate(sub, activeScope)` is built and driven** by three `/live` scenarios — `impersonation-lifecycle.ts`, `impersonation-expiry.ts`, and `profile-takeover-refused.ts`, whose mint limb landed 2026-09-08. Disposing the parent tears every child down through one seam, `onClientTornDown`; a bare disconnect does not mark the parent torn down, so a blip or a reconnect leaves the personas intact.
- **`dagTree().setPermission` attaches the grants.** ⚠️ After ④ ([nebula-data-plane-owns-its-guards.md](nebula-data-plane-owns-its-guards.md)) the entrance is gone, not merely re-homed: that task's § *Design intent, constraints, and future state* states `@mesh() dagTree()` does not survive beside the one `resources()` door, and the call becomes `resources().dagTree.setPermission(...)` — **no parens on `dagTree`, it is a getter**. Type-check catches every stale site, so this needs no letter; a site written before ④ carries a `TEMP → target=resources() gate` comment, as `star.ts`'s host forwards already do.
- **A re-provision reuses the persona's `sub`, and an accepted persona stays accepted through a `.dev` wipe.** `Memberships` carries `UNIQUE (emailId, universeGalaxyStarId)`; `#mintIdentity` early-returns the existing row and its JSDoc says the mint never touches the `scopeAdmin` or `accepted` state it reports; and `Star.resetDevData` is a `.dev`-guarded `deleteAll()` on that Star's own storage, so the Registry is untouched. An unchanged persona therefore needs no second round trip — it is immediately impersonable after a wipe, on the same `sub`, and the `.nebula/` map stays valid. ⚠️ **One-time only**: ⑥'s worker-delete destroys the Registry, after which every persona re-mints pending.
- **Re-inviting an accepted persona still sends mail, just a link-less letter.** `invite-entry.ts`'s `buildInviteMessage` discriminates on acceptance: an accepted member gets `invite-existing`, a landing `redirectUrl` with no magic link. ⚠️ **Provisioning never reaches that branch** — it invites only a persona the Registry read calls unaccepted or absent (§ *Pinned*), so every letter it sends is `invite-new`. The discrimination matters here as the reason a re-provision costs nothing, not as a path this task exercises.
- **The preview already runs as the user-developer, and reaches `.dev` two different ways.** The scaffold builds its client from an injected scope — `authScope` the parent Galaxy, `activeScope` the `.dev` Star. A Galaxy creator holds no `.dev` membership (`createGalaxy` withholds it) and arrives by dominion; a collaborator holds one, because `issueInvites` mints `{scope}.dev` on every galaxy-tier invite. Neither is a persona.
- **A Star lazy-pulls an ontology version it does not hold.** `appendWorkspaceOntology`'s JSDoc states it — the Star pulls `getOntologyVersion(version)` from its Galaxy *"inside that op's own call context"*, and upward passage is free for every member so it works under any claims — and `star.ts` implements both arms: `#pullOntology(version)` for a client-pinned version and `#pullOntologyCurrent()` for first touch, with a result handler that survives the DO's eviction. - **The executor can already write as a persona, and can already ask whether a node is empty.** `impersonate()` returns a full child `NebulaClient`, and `resources.subscribeQuery` answers the node-emptiness check seeding keys on — so neither half of the data verb needs a new mechanism.

## The one spike that blocks Pass 2

**Two facts about the address have never been checked, and either can invalidate a pinned row — so this runs before phases are written against them, not as a criterion inside one.**

1. **Does a `~` local part survive the whole path?** `~` is legal per RFC 5322's atext, and § *Verified on disk* confirms the Registry accepts it — but the provider's validator and Email Routing's rule matching are a different question. If either refuses it, § *Pinned*'s delimiter changes, and that row already carries the analysis of the two runners-up: `.` reads as a Star in the `{u}.{g}.{s}` grammar, and `+` is the one delimiter third-party tooling strips.
2. **Is `personas.lumenize.io` a valid verified destination for Routing's send?** `lumenize.io` is verified and carries the catch-all today. § *Pinned* established that Routing supports subdomains of the same zone for **inbound**; whether a *subdomain* is a verified destination for the bundled outbound send is a separate fact nobody has established.

**The shape:** send to `a.b~c@personas.lumenize.io` through the deployed sender on the Cloudflare path, and assert it arrives at the receiver — one message, both facts. Until it passes, the address grammar and the receiver's split-on-`~` parse are provisional.

## The coverage this task owes

`.claude/rules/live.md` makes `/live` the first tier for behavioural work, and **nothing here is pure** — a real mail round trip, a real accept through the two endpoints a human uses, real impersonation, a tab strip. Two scenarios, split on `needsContainer` because the boundary is measured rather than tasteful: the provisioning half runs container-free in about thirteen seconds and belongs in the inner loop; the seat half needs the built app in the iframe and pays the full `build-box` path at about a hundred and ten.
