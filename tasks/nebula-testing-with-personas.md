## Context

One of Lumenize Nebula's main selling points is that every app built automatically gets a robust fine-grained access control model using our DAG orgTree model for Resources.

Right now, the preview in Nebula Studio is a single iframe. The user-dev is be expected to log in as founder, invite other users with their own dummy email addresses, accept those invites, and then log out as founder and in as each of those other users one at a time to test their fine-grained access control and see how the UI changes based upon those permissions. That does not align with Lumenize's de✨light✨ful DX core value.

Further, we want to guide each user to good software development practices and one of those practices includes utilizing a cast of named personas to think about the experience of their users. We already have some support in the platform standing guidance for encouraging this but we have more planned including testing. That guidance is `apps/nebula/platform/`: `AGENTS.md` names the cast file, and `apps/nebula/platform/skills/define-the-cast/SKILL.md` is the skill that elicits it. The files the model writes into the user-developer's Workspace repo are `docs/personas.md` and `docs/permissions.md`; the skill itself is ours and ships in the bundle. There is no third file — see § *Pinned*.

This task is the next increment on that fine-grained permissioning journey and we've chosen to tie the permissioning model to a cast of personas, not a list "roles", partially to highlight the difference between our ReBAC, not RBAC, model. That case is made in [auth.md](../docs/vision/auth.md) § *The layers a call passes* — the M7 data-plane DAG bullet, and the *Why relationships rather than roles?* paragraph beneath it, which cites AuthZed on role explosion.

## Objective and goals

**Objective -- create a de✨light✨ful experience for testing a Studio authored app as each persona.**

**Goals:**

1. **Provision each persona as a user.** Everytime the personas file changes, either provision from scratch, if the .dev Star was wiped, or adjust the existing provisioning to match the latest version of that file.
2. **Populate with (on a wipe), or adjust existing (no wipe), test data to minimally show off the difference in each persona's permissions.** *(In scope, and § *Pinned* carries how — a fifth plan verb, written as the owning persona.)*
3. **Accept each persona's invite.** Create dynamic email addresses for each persona. Send those emails and auto-accept those invites. *(The address, who composes it, and where production reads the resulting mail are all in § *Pinned*.)*
4. **Log each persona in to a separate tab in the preview area.** The preview area gets a list of tabs with the persona slug as the tab label.

## Verified on disk — so it need not be re-derived

- **`invite()` returns the minted `sub`** on `InviteeSummary`, which is the name-to-`sub` map's source. ⚠️ **And nothing else**: that type is `{ email, sub, outcome }`, its JSDoc says it *carries no token or URL*, and `InviteSummary.links` — the raw invite URLs — appears in test mode only, where the same JSDoc calls it the sole carrier of the URL past the entry. So the invite call cannot hand Studio a link to click — which is why a receiver exists at all (§ *Pinned*) — and cannot report acceptance either — `summarizeInvites` strips `accepted` and `inviteUrl`, and two tests pin the exact key set against unfiltered pass-through, so the executor derives acceptance from its own context instead (§ *Pinned*).
- **`impersonate(sub, activeScope)` is built and driven** by three `/live` scenarios — `impersonation-lifecycle.ts`, `impersonation-expiry.ts`, and `profile-takeover-refused.ts`, whose mint limb landed 2026-09-08. Disposing the parent tears every child down through one seam, `onClientTornDown`; a bare disconnect does not mark the parent torn down, so a blip or a reconnect leaves the personas intact.
- **`dagTree().setPermission` attaches the grants.** ⚠️ After ④ ([nebula-data-plane-owns-its-guards.md](nebula-data-plane-owns-its-guards.md)) the entrance is gone, not merely re-homed: that task's § *Design intent, constraints, and future state* states `@mesh() dagTree()` does not survive beside the one `resources()` door, and the call becomes `resources().dagTree.setPermission(...)` — **no parens on `dagTree`, it is a getter**. Type-check catches every stale site, so this needs no letter; a site written before ④ carries a `TEMP → target=resources() gate` comment, as `star.ts`'s host forwards already do.
- **A re-provision reuses the persona's `sub`, and an accepted persona stays accepted through a `.dev` wipe.** `Memberships` carries `UNIQUE (emailId, universeGalaxyStarId)`; `#mintIdentity` early-returns the existing row and its JSDoc says the mint never touches the `scopeAdmin` or `accepted` state it reports; and `Star.resetDevData` is a `.dev`-guarded `deleteAll()` on that Star's own storage, so the Registry is untouched. An unchanged persona therefore needs no second round trip — it is immediately impersonable after a wipe, on the same `sub`, and the `.nebula/` map stays valid. ⚠️ **One-time only**: ⑥'s worker-delete destroys the Registry, after which every persona re-mints pending.
- **Re-inviting an accepted persona still sends mail, just a link-less letter.** `invite-entry.ts`'s `buildInviteMessage` discriminates on acceptance: an accepted member gets `invite-existing`, a landing `redirectUrl` with no magic link. So a re-provision bounces one link-less letter off the sender — accepted as a residual cost, since the executor invites on every run and the receiver drops it on the same parse (§ *Pinned*).
- **The preview already runs as the user-developer, and reaches `.dev` two different ways.** The scaffold builds its client from an injected scope — `authScope` the parent Galaxy, `activeScope` the `.dev` Star. A Galaxy creator holds no `.dev` membership (`createGalaxy` withholds it) and arrives by dominion; a collaborator holds one, because `issueInvites` mints `{scope}.dev` on every galaxy-tier invite. Neither is a persona.
- **The executor can already write as a persona, and can already ask whether a node is empty.** `impersonate()` returns a full child `NebulaClient`, and `resources.subscribeQuery` answers the node-emptiness check seeding keys on — so neither half of the data verb needs a new mechanism.
- **`ResourceDataPlane.invite` fails closed without an ontology, and a `.dev` wipe removes one.** Its JSDoc states the precondition — the `pending` `_InviteStatus` rows ride the ordinary Resources pipeline — and `dev-star-data-lifecycle.test.ts` states the other half: *"resetDevData wipes the ontology too (full deleteAll)"*. **Nothing consumes `_InviteStatus` in either UI** — checked 2026-09-08 across `apps/nebula-studio-ui/src` and the generated-app scaffold — so its rows serve a members panel that does not exist yet.
- **The model holds no scope slug, so it cannot compose an address.** `TOOL_CONTRACT` in `codegen-loop.ts`, `apps/nebula/platform/AGENTS.md` and the Workspace `AGENTS.md` seed carry no universe or galaxy identifier; the one `.universe/` mention is a reserved path prefix. Checked 2026-09-08.
- **The Registry accepts the address grammar already.** `isValidEmail` is `atIdx > 0 && atIdx < email.length - 1` — the only email check on every Registry path a persona address crosses — so `~` and `.` pass unconditionally. ⚠️ `normalizeEmail` lowercases and trims every stored and compared address, and `SLUG_RE` (`/^[a-z0-9][a-z0-9-]*$/`, no leading or trailing hyphen, no `--`) forces every slug lowercase and free of `.`, `~` and `+` — which is what makes the tilde parse unambiguously, and what a name-derived slug must round-trip through. ⚠️ What is NOT verified is the catch-all itself against a tilde local part — a check the receiver phase owes before it relies on one. The Resend half is moot: persona mail rides Cloudflare Email Sending (§ *Pinned*).
- **The refresh cookie is one fixed name at `Path=/auth/{scope}`, and `HttpOnly`**, so two real logins at one scope overwrite each other and page JS can never hold one. `handleAcceptMembership` resolves it *"to ITS OWN membership through the registry, never to the scope named in the URL"*, so the collision reads as a silent identity swap rather than a refusal. That is why impersonation won, and why the accept runs server-side (§ *Pinned*).
- **An unaccepted persona is refused by the mint, and the refusal names the wrong cause.** As built, `getIdentityScope` filters on acceptance, so an unaccepted subject reads as absent and lands in the mint's deliberately collapsed 403 — *does not administer this subject*, the same answer given for a `sub` that does not exist and for one the caller may not act for. **Studio cannot diagnose a persona from that reply**, which is why the executor speaks from its own context rather than relaying the refusal (§ *Pinned*).
- **The shipped cast guidance mandates the opposite of goal 3, in two live files.** `apps/nebula/container/app/docs/personas.md` reads *"Every persona is synthetic, on a reserved dead domain (`@example.com`, `*.test`, `*.invalid`), never a real address"* and mints `sally@example.com`; `platform/skills/define-the-cast/SKILL.md` repeats it. Both ship — through `scaffold-seed.ts` and `platform-embed.ts`, each held by a drift test — so the model reads it every turn. The failure is silent end to end: `isValidEmail` accepts `sally@example.com`, the mail goes to a reserved domain, nothing accepts, and the impersonation returns the collapsed 403 above. The guidance edit that fixes it is in § *Criteria*, and `.claude/rules/studio-guidance.md` § *How the homes ship* carries the regenerate-and-commit step.
- **The `email()` handler exposes no DKIM, SPF or DMARC result.** `ForwardableEmailMessage` carries `from`, `to`, `headers`, `raw`, `rawSize`, `canBeForwarded`, plus `setReject`, `forward` and `reply`; Cloudflare verifies internally (its `reply` requires a valid DMARC result) but surfaces nothing. So a provenance check is not available without hand-rolling DKIM over `raw` — checked 2026-09-08, and it is why the origin check carries the trust boundary instead.
- **`NebulaEmailSender.headers()` is a uniform hook** — one stamp applied to every message type, deliberately outside the template switch *"so a new type cannot silently ship untagged"*.
- **The only mailbox-reading path on disk is test-only.** `tooling/email-test` is `"private": true` and a **devDependency** of `apps/nebula`, so nothing in the production bundle can import it; its client pins one deployed host and one shared `testToken`, and its DO pushes to already-connected sockets rather than replaying stored mail, so a waiter must be armed before the send. `apps/nebula/src` has no inbound-mail handler at all. ⚠️ **There is no shared extractor to port, either** — `apps/nebula/test/lib/email-login.ts`'s `acceptInviteAndLogin` takes `inviteLink` as a parameter, the wait-and-extract is an ad-hoc regex duplicated across the scenarios that do it, and `extractMagicLink` matches magic-link hrefs only. That is why the receiver is built rather than ported (§ *Pinned*).
