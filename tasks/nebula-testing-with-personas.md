## Context

One of Lumenize Nebula's main selling points is that every app built automatically gets a robust fine-grained access control model using our DAG orgTree model for Resources.

Right now, the preview in Nebula Studio is a single iframe. The user-dev is be expected to log in as founder, invite other users with their own dummy email addresses, accept those invites, and then log out as founder and in as each of those other users one at a time to test their fine-grained access control and see how the UI changes based upon those permissions. That does not align with Lumenize's de✨light✨ful DX core value.

Further, we want to guide each user to good software development practices and one of those practices includes utilizing a cast of named personas to think about the experience of their users. We already have some support in the platform standing guidance for encouraging this but we have more planned including testing. That guidance is `apps/nebula/platform/`: `AGENTS.md` names the cast file, and `apps/nebula/platform/skills/define-the-cast/SKILL.md` is the skill that elicits it. The files the model writes into the user-developer's Workspace repo are `docs/personas.md` and `docs/permissions.md`; the skill itself is ours and ships in the bundle. Whether a third artifact joins them is § *Open* A.

This task is the next increment on that fine-grained permissioning journey and we've chosen to tie the permissioning model to a cast of personas, not a list "roles", partially to highlight the difference between our ReBAC, not RBAC, model. That case is made in [auth.md](../docs/vision/auth.md) § *The layers a call passes* — the M7 data-plane DAG bullet, and the *Why relationships rather than roles?* paragraph beneath it, which cites AuthZed on role explosion.

## Objective and goals

**Objective -- create a de✨light✨ful experience for testing a Studio authored app as each persona.**

**Goals:**

1. **Provision each persona as a user.** Everytime the personas file, which includes the provisioning script, either provision from scratch, if the .dev Star was wiped, or adjust the existing provisioning to match the lastest of those two files. *(Whether the personas file carries the provisioning artifact or references a sibling is § *Open* A.)*
2. **Populate with (on a wipe), or adjust existing (no wipe), test data to minimally show off the difference in each persona's permissions.** *(What writes that data, and whether it is in scope, is § *Open* D.)*
3. **Accept each persona's invite.** Create dynamic email addresses for each persona. Send those emails and auto-accept those invites. *(Who composes the address and what grammar it uses is § *Open* C; where production reads the resulting mail is § *Open* B.)*
4. **Log each persona in to a separate tab in the preview area.** The preview area gets a list of tabs with the persona slug as the tab label.

## Verified on disk — so it need not be re-derived

- **`invite()` returns the minted `sub`** on `InviteeSummary`, which is the name-to-`sub` map's source. ⚠️ **And nothing else**: that type is `{ email, sub, outcome }`, its JSDoc says it *carries no token or URL*, and `InviteSummary.links` — the raw invite URLs — appears in test mode only, where the same JSDoc calls it the sole carrier of the URL past the entry. So the invite call cannot hand Studio a link to click (§ *Open* B), and cannot report acceptance either (§ *Open* I).
- **`impersonate(sub, activeScope)` is built and driven** by three `/live` scenarios — `impersonation-lifecycle.ts`, `impersonation-expiry.ts`, and `profile-takeover-refused.ts`, whose mint limb landed 2026-09-08. Disposing the parent tears every child down through one seam, `onClientTornDown`; a bare disconnect does not mark the parent torn down, so a blip or a reconnect leaves the personas intact.
- **`dagTree().setPermission` attaches the grants.** ⚠️ After ④ ([nebula-data-plane-owns-its-guards.md](nebula-data-plane-owns-its-guards.md)) the entrance is gone, not merely re-homed: that task's § *Design intent, constraints, and future state* states `@mesh() dagTree()` does not survive beside the one `resources()` door, and the call becomes `resources().dagTree.setPermission(...)` — **no parens on `dagTree`, it is a getter**. Type-check catches every stale site, so this needs no letter; a site written before ④ carries a `TEMP → target=resources() gate` comment, as `star.ts`'s host forwards already do.
- **A re-provision reuses the persona's `sub`, and an accepted persona stays accepted through a `.dev` wipe.** `Memberships` carries `UNIQUE (emailId, universeGalaxyStarId)`; `#mintIdentity` early-returns the existing row and its JSDoc says the mint never touches the `scopeAdmin` or `accepted` state it reports; and `Star.resetDevData` is a `.dev`-guarded `deleteAll()` on that Star's own storage, so the Registry is untouched. An unchanged persona therefore needs no second round trip — it is immediately impersonable after a wipe, on the same `sub`, and the `.nebula/` map stays valid. ⚠️ **One-time only**: ⑥'s worker-delete destroys the Registry, after which every persona re-mints pending.
- **Re-inviting an accepted persona still sends mail, just a link-less letter.** `invite-entry.ts`'s `buildInviteMessage` discriminates on acceptance: an accepted member gets `invite-existing`, a landing `redirectUrl` with no magic link. So a re-provision that calls `invite()` bounces a real message off the sender for nothing (§ *Open* J).
- **The Registry accepts the address grammar already.** `isValidEmail` is `atIdx > 0 && atIdx < email.length - 1` — the only email check on every Registry path a persona address crosses — so `~` and `.` pass unconditionally. ⚠️ `normalizeEmail` lowercases and trims every stored and compared address, and `SLUG_RE` already forces the `u` and `g` segments lowercase and dot-free, so a persona slug must round-trip lowercase. What is NOT verified is the catch-all and Resend against a tilde and a dotted local part (§ *Open* C).
- **The refresh cookie is one fixed name at `Path=/auth/{scope}`**, so two real logins at one scope overwrite each other. That is what made a real login per persona expensive, and it is why impersonation won — and it still binds goal 3, because acceptance IS a real login (§ *Open* E).
- **An unaccepted persona is refused by the mint, and the refusal names the wrong cause.** As built, `getIdentityScope` filters on acceptance, so an unaccepted subject reads as absent and lands in the mint's deliberately collapsed 403 — *does not administer this subject*, the same answer given for a `sub` that does not exist and for one the caller may not act for. **Studio cannot diagnose a persona from that reply**, which is a live input to goals 3 and 4 (§ *Open* I).
- **The shipped cast guidance mandates the opposite of goal 3, in two live files.** `apps/nebula/container/app/docs/personas.md` reads *"Every persona is synthetic, on a reserved dead domain (`@example.com`, `*.test`, `*.invalid`), never a real address"* and mints `sally@example.com`; `platform/skills/define-the-cast/SKILL.md` repeats it. Both ship — through `scaffold-seed.ts` and `platform-embed.ts`, each held by a drift test — so the model reads it every turn. The failure is silent end to end: `isValidEmail` accepts `sally@example.com`, the mail goes to a reserved domain, nothing accepts, and the impersonation returns the collapsed 403 above. That is § *Open* C's to fix, and `.claude/rules/studio-guidance.md` § *How the homes ship* carries the regenerate-and-commit step.
- **The only mailbox-reading path on disk is test-only.** `tooling/email-test` is `"private": true` and a **devDependency** of `apps/nebula`, so nothing in the production bundle can import it; its client pins one deployed host and one shared `testToken`, and its DO pushes to already-connected sockets rather than replaying stored mail, so a waiter must be armed before the send. `apps/nebula/src` has no inbound-mail handler at all. ⚠️ **There is no shared extractor to port, either** — `apps/nebula/test/lib/email-login.ts`'s `acceptInviteAndLogin` takes `inviteLink` as a parameter, the wait-and-extract is an ad-hoc regex duplicated across the scenarios that do it, and `extractMagicLink` matches magic-link hrefs only. § *Open* B is what this costs.

## Open, and this file's to settle

Ten decisions Pass 2 must make. Ordered by how much of the design moves if the answer changes; A first because several others only have answers once it does. Everything the old list carried as ANSWERED has moved into § *Pinned* or § *Verified on disk*, which is where a settled fact belongs.

**A. Plan or script? § *Context* names "the provisioning script" as one of the artifacts; § *Pinned* says the model emits ONE plan, typed and typia-validated, for a deterministic executor.** Those are different artifacts: a script is code that runs, a plan is data that is checked before anything runs, and only the second can be refused whole. The pinned form was chosen over granular tools and over a typed block Studio parses. Decide which the prose means, because goal 1's question — whether the personas file carries it or references a sibling — only has an answer once this does. ⚠️ Pass 2 owes a literal example of whichever it is; the hand-written reference for that is [archive/nebula-invite.md](archive/nebula-invite.md) § *The contract*.

**B. Where does production read the persona's accept link?** Goal 3's whole loop — send, click, accept — needs Studio to hold the link, and § *Verified on disk* says every door on disk is shut. Three candidates, each with a different bill: **(i) the shared email-test Worker**, which is a devDependency on one deployed host behind one shared token, so every user-developer's persona mail would pool in one place — the interim-scaffold smell `docs/vision/_review-lens.md` names; **(ii) a real inbound receiver**, which pulls [nebula-outside-world.md](nebula-outside-world.md)'s unbuilt ingress into pre-alpha; **(iii) hand the URL back from the invite**, which `InviteeSummary`'s JSDoc forbids outside test mode. Say which keeps [ADR-009](../docs/adr/009-real-auth-path.md) rung 1, and note that J is the same door under a different motivation.

**C. Who composes a persona's address, and what must the cast guidance stop saying?** Two halves of one decision, and the second is an edit nothing else owns now that ① is frozen. The format under consideration is `{u}.{g}~{personaSlug}@lumenize.io` — literally `acme.crm~mary@lumenize.io`, against the `test-<uuid>@lumenize.io` that `uniqueTestEmail` mints today with a **dash**. Three things ride on it. **Authorship:** that string is derived from ids the model does not hold and the skill forbids it to write, yet the seed makes authoring a literal address step 1 — so either the executor derives it and the guidance stops naming addresses, or the model authors it and needs the ids. The disk leans executor: [archive/nebula-profile-access-control.md](archive/nebula-profile-access-control.md) § *Future state* says *"② mints each persona an address unique to its Galaxy."* **Grammar:** the Registry accepts `~` and `.` already, so what is open is the catch-all and Resend, plus the lowercasing `normalizeEmail` forces on any name-derived slug. **Stability:** the format is Galaxy-scoped, so one address is one Profile ([ADR-013](../docs/adr/013-identity-profileid-resolution.md)) and cannot collide across apps — which also means the Profile, its display name and its picture survive the wipe that re-mints every `sub`. Probably wanted; say so, since it is the one piece of a persona a wipe does not reset. ⚠️ Whichever way this goes, the shipped seed and skill both need editing and the embeds regenerating, and a phase criterion owes the two drift tests.

**D. Test data — a second artifact, part of the plan, or out of scope?** Goal 2's question. The wipe takes the data with the tree, so a re-run starts from the plan and whatever rebuilds the data; nothing converges and nothing is half-migrated. Three sub-questions ride along: whose authority writes it, since a Resource created as the founder persona and one created as Studio land under different grants; what a second run does, which needs a key to be idempotent on; and whether the wipe is suggested, offered as the default of a two-button apply, or forced — a DX question, and goal 2's data is what makes it feel expensive.

**E. Where does the accept loop run — a browser cookie jar, or a server-side executor?** Acceptance is a real login (§ *Pinned*) into the single cookie slot § *Verified on disk* describes, so a cast accepting one after another at the same `{u}.{g}.dev` overwrites itself, and the failure mode is a silent identity swap on the next refresh rather than a 401. The two branches differ in what they can even do: `email-login.ts`'s `acceptMembership` passes an explicit `Cookie:` header and keeps no jar at all. This also bounds what question I can check, and depends on B.

**F. Which built path does the executor's `grant` verb mean?** Two reach "persona X holds tier T on node N": `dagTree().setPermission`, or `Star.invite` → `ResourceDataPlane.invite`, which writes the `pending` `_InviteStatus` rows the members panel query-subscribes and then flips to `sent`. A persona provisioned by `setPermission` has a grant and no `_InviteStatus` row, so the cast never exercises the app's own invite, pending and failed states — which is a chunk of the permission UI the objective exists to let someone see. § *Pinned*'s facade clause decides persona one only; this is personas two onward.

**G. Which personas get tabs, and is the user-developer one of them?** § *Pinned* says the OPEN set rides the URL ([ADR-017](../docs/adr/017-the-url-is-the-view-state.md)), so the tab strip and the open set are not the same list. And the stand-in founder is pinned as the first persona, which either makes the user-developer a persona or leaves them a separate seat.

**H. What does a tab render when its persona cannot reach the app's landing view?** This is the payoff in § *Context* — seeing the UI change with permissions — and the state most likely to look like a bug rather than a demonstration.

**I. How does provisioning know an accept succeeded — on run two, not just on the run that accepted?** The accept is a real POST with a real status, so the run that performs it can check there rather than inferring from a later impersonation. That answer does not survive a re-provision, a fresh session, or tomorrow: `#mintIdentity` early-returns `already-member` identically for an accepted persona and a stranded one, `InviteeMintResult`'s `accepted` flag is for the entry's sender alone and its JSDoc bars it from the caller-facing summary, and `getScopeSummary` is keyed on the caller's own `profileId`. So the durable signal has to be built or the constraint accepted — and the cost of accepting it is a user-developer told *does not administer this subject* about a persona they just watched get created.

**J. Does the executor call `invite()` on a re-provision, or skip it from the `.nebula/` map?** This replaces the retired no-send-mint gap, whose premise was false: it argued for minting without sending so a wipe would not re-bounce magic links, and a `.dev` wipe leaves an accepted persona accepted (§ *Verified on disk*), so there is nothing to re-accept. What a re-invite actually sends is a link-less `invite-existing` letter — cheap, but still real mail for no reason. ⚠️ The premise returns after ⑥'s worker-delete, so a one-time answer is not a standing capability.

## Criteria the plan already says to carry

- A wiped `.dev` Star is re-established from the persona file alone: provision from a seeded `personas.md`, wipe, run, and the tree and grants match the prose. ⚠️ Each unchanged persona keeps the **same** `sub`, because its membership survives a `.dev` wipe and is reused — assert that, not a fresh one. Mutation: drop create-if-missing, and the second run fails on "already exists".
- A plan naming an unknown node is refused before anything runs. Mutation: remove validation, and a grant lands on nothing.
