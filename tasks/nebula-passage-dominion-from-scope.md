## Objective

**Make the running code's `passage` and `dominion` be the ones [ADR-015](../docs/adr/015-passage-and-dominion.md) § *Decision* and `accepted` [`docs/vision/auth.md`](../docs/vision/auth.md) § *Coarse-grained access control* already specify, and make every site that needs either CALL them instead of re-deriving its own.** The model is not this file's to invent; this block is byte-identical in all three places, and must stay that way until this task file is archived:

```
isAtOrAbove(myScope, targetScope)  — my scope covers the target: the same scope, or an
                                     ancestor of it. The reserved platform scope is the ROOT
                                     of the tree, so it is at or above every scope.
isAtOrBelow(myScope, targetScope)  — my scope sits at or beneath the target: the same scope,
                                     or a descendant of it. Every scope is at or below the
                                     platform root. Exactly isAtOrAbove with the arguments
                                     flipped: isAtOrAbove(A, B) === isAtOrBelow(B, A).

dominion(authScope, scopeAdmin, targetScope) = scopeAdmin ∧ isAtOrAbove(authScope, targetScope)

passage(authScope, scopeAdmin, targetScope)  = isAtOrBelow(authScope, targetScope)
                                               ∨ dominion(authScope, scopeAdmin, targetScope)
```

The symbols are `hasDominionOver(access, targetScope)` and `hasPassageInto(access, targetScope)`.

**Those signatures take two arguments where the predicates take three**, because two of the three arrive together: `authScope` and `scopeAdmin` are both fields of the caller's `access` claim, so they are passed as that one claim. `targetScope` is passed separately.

Several goals, in the order they matter:

1. **Conformance.** Today the claim carries a wildcard *pattern* derived from the scope rather than the scope itself, and a non-admin reaches downward. Both are gaps `auth.md` names in its own `> **Today's code differs.**` blockquote, and closing them is this task file's work.
2. **Reuse, so the wrong thing is hard to write by mistake.** ADR-015 § *Predicate pair*'s **One implementation.** paragraph already requires exactly this, stating it over ADR-007: every site needing either verdict calls the shared predicate against the `targetScope` it acts on, instead of re-inlining the conjunction. Today nine sites delegate to `hasDominionOver` while eight more call the containment check directly, and `hasPassageInto` does not exist as a callable thing anywhere — `requirePassage` is the only place both arms appear together.
3. **Vocabulary — every identifier expressing this model spells it the way ADR-015 and `auth.md` do, and nothing expressing it is spelled any other way.** This has teeth in both directions. Today's names are normalized *onto* those terms: `matchAccess` and `buildAuthScopePattern` stop existing, and the claim becomes `access.authScope`. And no term is coined *beside* them, however reasonable a wrapper looks at the call site — a synonym is how a reader ends up holding a translation, which in this layer is how a security hole gets written.
4. **Detectability, so the rest survive later edits.** Afterwards a containment call outside `isAtOrAbove` / `isAtOrBelow` / `hasDominionOver` / `hasPassageInto` is non-conformant **by definition**, so the next one surfaces in a grep rather than in a review.

⚠️ **This file makes no claim on the current code's absence or presence of security risk, but it will make it much easier to assure that it is secure going forward.**

🔀 **`router.ts`'s Registry route GATE is not this file's** — [nebula-registry-route-guards.md](nebula-registry-route-guards.md) lands next and owns its shape and the argument for it. ⚠️ **Its containment EXPRESSION still converts here**, verdict-for-verdict, because Phase 1 deletes `matchAccess` and every call site must compile — the same verdict-preserving seam as the mint (§ *Constraints*).

## Design intent, constraints, and future state

### The target

§ *Objective* states the model. This section pins **which symbols carry it and how each is named** — nothing here restates a predicate.

⚠️ **Both structural predicates take `(myScope, targetScope)` in that order, always — never flipped.** § *Objective*'s block states the identity that makes this dangerous: a transposed call is not a type error and not a test failure, it silently inverts the security model. That identity is also why `isAtOrBelow` exists as its own symbol; without it the upward arm would be spelled `isAtOrAbove(targetScope, myScope)`, putting the same function on adjacent lines with flipped arguments. ⚠️ **Implement one as the other with the arguments swapped**, so the identity — and the platform-root branch with it — is structural rather than a property two functions must both remember.

⚠️ **`passage` is the UNION, not the upward arm alone.** An admin at `{u}` calling `{u}.{g}.{s}` has passage *because* they hold dominion there; writing passage as upward-only refuses the whole downward rule. It is also why `hasPassageInto` at the Registry gate would be an escalation (see [nebula-registry-route-guards.md](nebula-registry-route-guards.md) § *There is no authorization hole here*) — the same union misread in the opposite direction.

⚠️ **A caller with no principal never reaches either verdict — a structural fact, not a guard.** `verify.ts:44` refuses a token whose `access` carries no scope (`authScopePattern` today, `authScope` after Phase 1), so both verdicts run against a verified principal by construction. ⚠️ **Passage to the platform root is the model working, not a leak that wants closing** — every scope is at-or-below the root, so every authenticated caller has passage there, and § *Acceptance criteria*'s name-reservation criterion carries what that does and does not permit. ⚠️ **Whatever absent-`access` handling the verdicts carry is a stated contract, and it never moves onto `isAtOrAbove`** — that is a structural fact about two strings, unconditional by design, and its platform-root branch returns `true` without reading its second argument at all.

⚠️ **Stated STRUCTURALLY, because a per-site list is `calibration.md` §2's tell: every comment justifying an ordering, a guard or a skip from `matchAccess('*', x)` or from the `buildAuthScopePattern` tier grammar must be re-derived, not ported** — `nebula-do.ts`'s `requireDominionHere` licenses skipping the platform reject and the parse on exactly that ground, and its class JSDoc teaches the tier grammar as the model. ⚠️ **Open, and each is a `calibration.md` §4 re-derivation rather than a port:** `hasDominionOver`'s JSDoc argues its truthiness guard from `authScopePattern`, which Phase 1 deletes, and `requirePassage`'s tenant arm loses its `if (!aud) throw` when it stops reading `aud`. Decide whether either guard outlives its justification — `verify.ts:44` may already make both unreachable — instead of carrying them across on the strength of the old comments.

⚠️ **`dominion` and `passage` are RESERVED — [ADR-015](../docs/adr/015-passage-and-dominion.md) § *Terminology* is the definition home — and "reach" MUST NOT be used as a noun for either.** Three terms, one meaning each: `isAtOrBelow` the upward *structural* relation, `dominion` the downward verdict, `passage` the boundary verdict.

**The symbols THIS file pins, so no phase of it invents one.** Three tiers, and the tier decides the naming style: a **structural fact** gets a literal name, a **verdict** a reserved word, **data** its field name.

🔒 **The verdicts' second parameter is `targetScope` in source too — today it is `scope`.** `hasDominionOver(access: AccessEntry | undefined, scope: string)` (`parse-id.ts`) and every guard that forwards to it are renamed in the same edit that changes their bodies, so this costs a word per line already changing. ⚠️ **Not `callee`**, which the model docs use in prose and which is wrong here: two of the verdict's call classes are not calls at all — the mint asks dominion over the **subject's** scope (`worker-token.ts`), and the subscribe-time writers ask it over a **host** scope (`subscriptions.ts`, `query-subscriptions.ts`). `target` is also the incumbent word for this argument: the deleted `matchAccess(pattern, target)` already called it that.

⚠️ **Naming tiers: `.claude/rules/coding-style.md` § *Security-verdict identifiers*, which governs locals and guards as well as exports** — that is why the criteria below carry a grep-shaped one, since no behavioural criterion can see a correct predicate called by a guard named for the bit over a local named for the pattern.

`buildAuthScopePattern` is deleted and the claim becomes **`access.authScope`** — the member's scope verbatim. The rename drops `Pattern` and nothing else; § *Decisions* carries why not `scope`.

⚠️ **`isAtOrAbove` compares WHOLE dot-separated segments — contract, not implementation detail.** The obvious `b === a || b.startsWith(a)` type-checks, passes every behavioural criterion below, and silently makes `u.g.s1` cover `u.g.s10` and `acme` cover `acme-2`, both legal slugs. The boundary is closed explicitly in two independent places today (`parse-id.ts:148` `startsWith(prefix + '.')`, `nebula-auth-registry.ts:689`'s `LIKE ${prefix + '.%'}`); the replacement owes the same guarantee.

✅ **`isAdmin` → `scopeAdmin` landed 2026-08-07** (66 files, at rest and in flight). ⚠️ `packages/auth` and `packages/mesh` keep their own `isAdmin` — a *different* bit (auth's `Subjects` column, and a flat top-level claim mesh mints for auth's gate) — and the Data-plane's `admin` **grant on an orgTree node** keeps its name, being one of a symmetric triple (`CHECK(permission IN ('admin','write','read'))`). A repo-wide replace would break all three, the mesh one silently.

### What this buys, and what it costs

- **Two places, one string.** The `Memberships` row and the JWT hold the same value — nothing to reconcile, and ADR-015's clauses stop needing to be memorized (same predicate, opposite arguments). ⚠️ **The URL is not a third place** — it names the **`targetScope`**, which is the predicates' *other* argument; conflating the two is the mistake this layer exists to prevent.
- **Membership becomes the complete answer to where a person can work**, because nothing reaches beyond membership any more. Today a teammate with one high-tier non-admin membership shows up as one entry while the truth is scattered across N DagTrees with no index. ⚠️ **Do not wire a scope picker to `discover`** — [`docs/vision/auth.md`](../docs/vision/auth.md) § *`activeScope`* keys the person-wide list on `profileId` behind an authenticated caller, and flags today's email-keyed `discover` as an enumeration oracle it is replacing. `myScopeTree` is the picker's source (§ *Decisions*).
- **A residual disappears.** [nebula-collaborator-tiers.md](on-hold/nebula-collaborator-tiers.md) used to file the minimum-privilege collaborator reaching down into tenant Stars as a disclosure question to decide; with no downward **passage** without `scopeAdmin`, the question stops existing rather than getting answered.

**Cost, accepted: a person who works in N scopes needs N memberships and N sessions**, where a high-tier non-admin membership would have covered them with one. Grants are unaffected — DAG grants are per-node under both models — so this costs sessions, not permissions. Accepted because the surfaces are usually already separate (Studio on the Galaxy, preview on the `.dev` Star); each membership carries its own acceptance, a real per-scope consent moment that reads well to an enterprise buyer; and it is what makes `discover` honest. ⚠️ **The one friction is N invite emails**, and it cannot be waived because the address is verified elsewhere: `Memberships.acceptedAt` is set only by consuming a link delivered to the mailbox, and per-membership acceptance is ADR-012's manufacture defense. If it ever bites, the fix is a multi-invite-in-one-email flow — years away (Larry, 2026-08-05).

## Acceptance criteria

**Behaviour**

- **A non-admin reaches its own scope and nothing beneath it.** Passage at `{u}`; refused at `{u}.{g}` and `{u}.{g}.{s}`. *Reds against retaining downward passage for non-admins.*
- **An admin reaches downward, totally** — passage with dominion at `{u}`, `{u}.{g}` and `{u}.{g}.{s}`, including scopes created after the token was minted. *Reds against dropping the downward rule.*
- **Upward is nil for dominion.** An admin at `{u}.{g}` is refused **as admin** at `{u}`. ⚠️ **Stated over named methods, for the same reason its sibling criterion two rows below is** — a boundary refusal and a dominion refusal produce the same observable, so a transcription that collapsed upward passage into a denial would green a bare-denial assertion. The pair: **`Universe.getUniverseConfig` RETURNS** (bare `@mesh()`) while **`Universe.setUniverseConfig` refuses** (`@mesh(requireDominionHere)`). *Reds against a symmetric predicate — and against collapsing upward passage into a denial.*
- 🔒 **A malformed `activeScope` is refused at the mint, not minted into a token.** `POST /auth/{scope}/mint-narrower-token` with `activeScope` of **four** segments (`{u}.{g}.{s}.x`) answers 4xx and issues nothing; `parse-id.ts`'s own message names the bound — *"must have 1–3 dot-separated segments"*. *Reds against the plain transcription, which drops the only `parseId` this value ever receives and lets the widened star-tier compare admit it.* ⚠️ **Assert the STATUS is 400, not merely 4xx** — a bare `parseId` throw inside the handler answers `500 internal_error` through `router.ts`'s blanket catch, which is a refusal and would satisfy a 4xx-shaped criterion while proving the parse was sited wrong. ⚠️ Assert the **absence of a minted token**, not only the status — a 403 from the subject bound and a 400 from the parse are both refusals, and only the second is what this criterion is about.
- 🔒 **The scope is still the bound.** An admin at `{u1}` is refused everywhere in `{u2}`. *Reds against a predicate reading `scopeAdmin` without the scope — the "bare bit is dominion" bug, and the one this change makes easiest to write.*
- **The tenant direction survives, and confers no dominion.** Stated over **named methods**, because "denied" is also what a boundary refusal produces — so a criterion whose only observable is a denial cannot red against the collapse it exists to catch. A Star member whose `authScope` is that Star reaches its parent Galaxy and **`Galaxy.getLatestOntologyVersion` RETURNS** ([galaxy.ts:176](../apps/nebula/src/galaxy.ts), bare `@mesh()`), while **`Galaxy.setGalaxyConfig` refuses** ([galaxy.ts:130](../apps/nebula/src/galaxy.ts), `@mesh(requireDominionHere)`). *Reds against collapsing both directions into one rule — and against "fixing" upward passage into a denial.* 🚨 **Do NOT assert a blanket denial here, and do not let a reviewer talk you into one.** ADR-015 § *Terminology*'s **Lacking dominion is not a denial** bullet, which states that a caller with passage but no dominion may still be granted a great deal by the methods it reaches, as the callee's own guards decide. A peer-level invite is exactly that shape and **must be granted**, so a criterion demanding refusal would red against correct behaviour. Several reviewers have reached for the denial reading; it is wrong every time.
- **`aud` survives on the token and on the wire.** A call out to a client is still refused on an `aud` mismatch. *Reds against over-applying "passage no longer reads `aud`" into removing the claim — which would cross-deliver one tenant's updates to another.*
- **Platform means everywhere.** A `nebula-platform` admin holds dominion over every scope — asserted **at the predicate and on the Registry route path** (`hasDominionOver(platformAccess, anyScope)` is true; a platform admin passes `verifyInstanceJwt` for any instance). ⚠️ **Say nothing here about a mesh call to that name** — `nebula-do.ts`'s reject fires for everyone, superuser included, and runs before the dominion clause, so the two criteria would read as contradicting. The mesh outcome belongs entirely to the criterion below. *Reds against a hierarchy predicate with no case for a non-hierarchical name.*
- **A mesh call to a node NAMED `nebula-platform` is still refused**, for that same superuser. *Reds against removing the platform-name reject once its `'*'`-collapse justification is re-derived away.* ⚠️ **Its reason is NAME RESERVATION, not masquerade** — nothing intentional is deployed at that name yet. 🔀 **It is TEMPORARY and reversible**, and whatever is eventually deployed at that name (§ *Non-goals*) is what retires it. ⚠️ **The rule for whoever builds that: the name goes from REJECTED to BOUND — never to open.** Under the root model `nebula-platform` is the one instance name **every** authenticated caller has passage to, by construction; every other name needs the caller's scope at-or-below it or under their dominion. And `lmz.call` takes the binding and the instance name **separately**, so the callee's class is the caller's choice. Deleting this branch on its own would therefore let anyone instantiate an arbitrary DO class at the most-reachable name in the system and call its ungated `@mesh()` methods. Delete it in the same change that binds the name to a registered occupant, not before.
- 🔒 **Segment boundaries hold under colliding names.** `{u}.{g}.{s}1` is refused at `{u}.{g}.{s}10`; an admin at `{u}` is refused everywhere in `{u}-2`. *Reds against a prefix-match `isAtOrAbove` — the defect every other criterion is blind to, since no other scope names collide on a prefix.* 🚨 **Third limb, over the two SQL sites allow-listed OFF the predicate** — with `{u}` and `{u}-2` both present in `Scopes`, `myScopeTree` for a `{u}` admin returns no `{u}-2` scope, and `#computeDeletionPlan` for `{u}` lists no `{u}-2`. *Reds against a dot-dropped `LIKE ${authScope}%`, which greens every other criterion* — *Enumeration is unchanged for an admin* is self-disclaimed here, and no fixture registers colliding names. ⚠️ On the deletion plan the same slip widens a **destructive** operation, which is the price of allow-listing these two off the predicate.
- 🔒 **A superuser is unchanged everywhere.** Their token **verifies**; authorized at every scope; may refresh to any `activeScope`; `myScopeTree` returns every scope; passes the Profile owner/admin gate with **zero registry reads**. *Reds against any consumer of `access` that lost the platform branch when `'*'` stopped being the value.* ⚠️ The verification limb fails CLOSED and TOTAL, so a miss there is a superuser who cannot log in, not one who quietly loses admin. ⚠️ Its **registry-route** and **mint-`aud`** limbs belong to [nebula-registry-route-guards.md](nebula-registry-route-guards.md) — do not look for them here, and do not re-add them.
- **Enumeration is unchanged for an admin.** `myScopeTree` returns the same set before and after, for the same identity. *Reds against a bound that narrows the query.*
- 🌐 **Driven as `/live` scenarios, on the REAL login path — the default tier, not a supplement.** `live.md` § *`/live` is the DEFAULT tier* requires the scenario first and requires any in-lane test to say why it needed no running system. Four named limbs, each real-login (`provisionAndLogin`, ADR-009 rung 1) and real-socket:
  1. **Downward dominion.** A universe admin acts in a Star beneath — `superadmin-dominion.ts` re-derived (below), plus a covering-admin case at a real tier rather than at `'*'`.
  2. **Upward passage confers no dominion.** A star-scoped member reaches its Galaxy and `Galaxy.getLatestOntologyVersion` **returns**, while `Galaxy.setGalaxyConfig` **refuses** — the named-method pair, because a boundary refusal and a dominion refusal look identical from outside.
  3. **The superuser end to end.** A bootstrap-email login at `nebula-platform` verifies, refreshes, enumerates and passes the Profile gate. ⚠️ **This is the limb with no in-lane backstop that this task does not also rewrite** — see the Phase-1 note.
  4. **The refresh grammar.** A four-segment `activeScope` answers **400** and mints nothing, driven against the real endpoint rather than a constructed request.
  ⚠️ **Fidelity, not capability** — pool-workers can assert the predicate; only a real login proves the claim the *server actually minted* is the one the predicate expects.
  🚨 **`superadmin-dominion.ts` is RE-DERIVED, not ported, and the reason is the whole argument for this tier.** It drives `connectDriver`'s **mint** path (rung 3), and its own JSDoc records the consequence: *"You cannot produce a denial by narrowing through this harness"* — because the mint sets `instanceName: opts.mint?.issuerInstanceName ?? scope`, narrowing the scope narrows the pattern in lockstep. **That is a harness whose behaviour diverges from production, hiding the exact denial this task is about.** Under the new claim the lockstep reasoning dissolves entirely — `authScope` *is* the scope — so the scenario must be rebuilt on `provisionAndLogin` and its JSDoc rewritten, never mechanically converted.
