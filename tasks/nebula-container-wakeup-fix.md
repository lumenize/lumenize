**Status**: **Phase 0 spike DONE (2026-07-01) — QUALIFIED GO. Mesh sequencing gate CLEARED 2026-07-04** (continuation-only shipped; identity-stamp-removal rejected). **`/review-task` framing + conformance both PASSED (2026-07-04)** — see § Review. **`/build-task` Phases 1–2 BUILT + verifier-panel PASSED (2026-07-04)** — see § Build; remaining = a live `wrangler dev`+Docker session (ui-smoke fold + cooldown read-back) + opportunistic Phase 3. The **safety-net fix** for the (rare) DevContainer stuck-`running` stall: detect the stuck signature and force DO reconstruction with `ctx.abort()` on **both** entry paths — the preview-GET path (user-visible) **and** `ensureUp` (command path, belt-and-suspenders) — with the recover endpoint **only ever aborting a server-side-corroborated stuck container**. Phase 0 **confirmed the abort lever on deployed CF** (reconstruct → re-read `running` from reality → clean boot) but found the container **self-heals in every off-prod scenario** (local `docker kill`/`stop`, deployed new-image, deployed idle-sleep) — so the stuck flag is a **rare race, not the common wakeup path** (see Phase 0 RESULTS). Lands entirely **below the mesh layer** (`fetch()` + `containerFetch` + `ensureUp` + `ctx.abort()`) — touches only `apps/nebula/src/dev-container.ts` (+ its test), never `dev-studio.ts` — independent of the now-shipped mesh continuation-only work (which owns `dev-studio.ts`'s call sites). Implements diagnosis option **#1**. Mesh-orthogonality rationale is owned by the diagnosis — see [nebula-container-wakeup-recovery.md](archive/nebula-container-wakeup-recovery.md) Q1/Q5 + § Coordination; do not restate it here.

## The fix in one line
The stuck state is a stale `this.container.running=true` the base can't restart past (`startContainerIfNotRunning`: `if (this.container.running) return 0`), and `destroy()` doesn't clear it in the deploy-staled cloud case. **Detect the stale-flag signature and force DO reconstruction with `ctx.abort()`** — the forced, immediate equivalent of the idle-eviction that is today the *only* known clear (recovery drops from ~minutes to seconds). `ctx.abort()` is the same lever the container base itself uses on "Network connection lost" (`@cloudflare/containers` `dist/lib/container.js` ~L1416).

## Decisions

| # | Decision | Choice | Rationale |
|---|---|---|---|
| **D1** | Recovery lever | **`ctx.abort()`** (forced DO reconstruction) | `destroy()` does NOT clear the deploy-staled flag (diagnosis Q2: same dead id persisted across many attempts); only idle-evict does; `abort` = forced idle-evict = immediate. Base uses it for the analogous stuck-connection case. **Phase 0 CONFIRMED the mechanic deployed** (abort → reconstruct → re-read `running` from reality → clean boot, no wedge); the stuck-*clear* is inferred from this + "idle-evict is the confirmed prod clear," since the stuck precondition wouldn't reproduce off-prod to test directly. |
| **D2** | Where recovery lives | **Both entry paths** — the preview-GET path (`DevContainer.fetch`, primary/user-visible) **and** `ensureUp` (command path) | The preview-GET path is the user-visible "500s forever" surface (browser-driven, not a mesh call, always present in the Studio) and is the primary home for recovery. **`ensureUp` gets the same `#forceReset()` recovery too (belt-and-suspenders, Phase 2)** — so a stuck container self-heals when DevStudio *pushes code* too, not only when the user loads the preview. This was previously blocked (an abort mid-`ensureUp` would strand DevStudio's awaited `callRaw`) — but the mesh continuation-only work shipped: `DevStudio` now calls `ensureUp` via one-way `lmz.call`, so an abort strands nothing. Both paths gate on the stuck signature before calling the shared `#forceReset()` (whose cooldown they also share). |
| **D3** | Stuck detection | New **`isStuckFlagResponse(status, body)`** = `status===500 && /not running\|suddenly disconnected\|proxying request to container/i` — a **genuine strict subset** of `isContainerColdResponse`'s 500 phrases | The abort-worthy signature only: the **proxy-path** phrases where a stale `running=true` manifests (base `container.js` L972 `"Container suddenly disconnected, try again"`, L975 `"Error proxying request to container: …"` — the prod-observed `"…not running…"` rides inside the latter). Does NOT replace `isContainerColdResponse` (which also matches `502`/`429`/`503`/provisioning); distinct jobs (D4). **500-only** (M1: the base never emits `502` on the container path — a `502` is a CF edge fault `ctx.abort()` can't fix; it stays cold→page, not stuck→abort). **Excludes `Failed to start container`** (M3: a genuine crash-on-boot / bad-image / bad-entrypoint 500 — autoRecover on it = abort→recrash→abort loop; keep it in `isContainerColdResponse` for the page only) and **`Network connection lost`** (m1: never a response *body* — it's the internal error the base wraps *into* the `suddenly disconnected` body). ⚠️ **Phase 0 could NOT capture the verbatim prod stuck body** (self-healed every time) → this is the conservative base-library-emitted subset, NOT a captured signature; narrow only if a real stuck body is ever captured. `502`/`429`/`503`/provisioning excluded — Phase 0 captured the `503` body (`"There is no Container instance available…max concurrent instance count…"`); aborting it would thrash a legit boot. |
| **D4** | Abort orchestration + predicate precedence | **`isContainerColdResponse` gates the waking PAGE (unchanged); `isStuckFlagResponse` gates AUTO-RECOVER; the recover-GET re-corroborates server-side before aborting** | `ctx.abort()` kills its own invocation, so it can't return a `Response` — hence a two-step: `fetch()` serves `wakingPreviewPage({ autoRecover })` on any cold response (`isContainerColdResponse`, the existing gate at `dev-container.ts:336`, untouched), with `autoRecover = isStuckFlagResponse(status, body)`. When `autoRecover`, the page's JS hits the `/_nebula/recover` sentinel then reloads once; a cold-but-not-stuck response (provisioning/capacity) serves the SAME page with manual reload only (no abort). Auto-reload is safe now — recovery is abort-driven, not idle-evict-driven — but **bounded** (≤2 attempts via `sessionStorage`) with the manual button as final fallback. **The recover-GET does NOT trust the client's autoRecover claim: server-side it re-probes (bounded `containerFetch`) and calls `#forceReset()` only if `isStuckFlagResponse` holds (or the probe hangs past its timeout = frozen-stuck)** — so recovery fires only against a genuinely-stuck container regardless of who hits the endpoint (the D6 cross-tenant bound). The command path (`ensureUp`) self-gates the same way on `isStuckFlagError`. |
| **D5** | `#forceReset()` shape | **Cooldown check (`shouldAbortNow`) → best-effort `destroy()` (non-hanging) → persist abort timestamp → `this.ctx.abort()`** | `#forceReset()` is the **shared post-authorization primitive** (both paths call it; it does **no** origin check and **no** stuck-corroboration — those are the caller's job, D4/D6). It first consults the per-instance cooldown (`shouldAbortNow`, a pure predicate over the durable last-abort timestamp) and no-ops if within the window; else `destroy()` clears the *cold-but-not-deploy-staled* case, the timestamp is persisted to `ctx.storage.kv` **before** the abort (so it survives reconstruct), then `ctx.abort()` is the load-bearing clear for the deploy-staled case. `destroy()` must not block the abort (short timeout or fire-and-forget + catch). |
| **D6** | Recover-endpoint auth + abuse bounds (three distinct concerns, three distinct bounds — do not conflate) | **Ungated endpoint; (1) `Sec-Fetch-Site` closes cross-*site* CSRF; (2) server-side stuck-corroboration closes cross-*tenant* healthy-abort; (3) a per-instance cooldown bounds abort *frequency*** | The surface is ungated by design (ADR-007: `fetch()` is public-by-design, sensitive ops go over mesh); auth/rate friction is anti-wedge (`_review-lens.md` (b)). `/_nebula/recover` is a plain **GET** firing a state-changing `ctx.abort()`, so: **(1) Cross-site CSRF-via-GET** (`evil.com` `<img src=…>`) → closed by the `Sec-Fetch-Site: same-origin` check, enforced **in `fetch()` on the recover path** (browser-set + unforgeable; rejects cross-site + header-less callers). ⚠️ The check lives in `fetch()`, **not** in `#forceReset()` — `#forceReset()` is the shared post-authorization primitive (also reached by the `requireAdmin` command path) and performs no origin check, so it must never be exposed on a path that hasn't already gated. **(2) Same-origin cross-tenant** (untrusted agent-authored preview code on any tenant `fetch`es `/dev-container/{victim}/_nebula/recover`, carrying `same-origin`) → `Sec-Fetch-Site` is origin-scoped and **cannot** isolate tenants. Closed instead by **server-side corroboration (D4): the recover-GET aborts only if a bounded fresh probe confirms `isStuckFlagResponse`.** So an untrusted neighbor can trigger an abort *only against a genuinely-stuck container* — which the abort *recovers* (net-positive, data-safe); it **cannot** kick a healthy, actively-serving neighbor. Residual: forcing the recovery of an already-stuck neighbor — negligible + data-safe (abort touches **no data**; DevContainer holds no durable truth beyond the `appVersion` kv, which survives; disk reverts + re-pushed, Flow 1c). Anchor: **ADR-007** (public-by-design `fetch()`); **not** ADR-008 (scoped within-a-Star, silent on cross-tenant). **(3) Abort frequency** (a reload loop, or repeated failed probes) → bounded by the **per-instance cooldown** (`shouldAbortNow` over a durable timestamp, D5). ⚠️ The cooldown is a **per-instance frequency** bound (anti-thrash / self-abuse), **NOT** a cross-tenant blast-radius bound — it's keyed per victim instance, so it does not limit an attacker fanning across N victims; **corroboration (2), not the cooldown, is what closes cross-tenant.** A true per-caller bound is an unbuilt future option, unneeded while (2) holds. |
| **D7** | Efficacy verification | **Mechanic confirmed by Phase 0; stuck-clear inferred; wired-mechanism verify (Phase 3) is opportunistic** | The stuck trigger has **no local analog** AND did **not reproduce on a deployed throwaway harness** either (`docker kill`/`stop`, deployed new-image, deployed idle-sleep all self-heal; `docker pause` freezes with the instance still *present* so abort can't clear it). Phase 0 therefore confirmed the abort *mechanic* (reconstruct → re-read reality → boot) but could not exercise a stuck-*clear* end-to-end. Local tests cover detection + wiring + no-regression; Phase 3 (deploy-verify the wired mechanism against a real stuck) can only run if a genuine stuck recurs in prod — treat as **opportunistic**, not a hard gate. |

**RESULTS (2026-07-01 — throwaway harness `experiments/container-node-phase0` deployed to CF, then fully torn down: worker + container app deleted, spike code reverted):**
- ✅ **Abort lever CONFIRMED on real deployed CF** (Test A): `ctx.abort()` → RPC errors with `"Application called abort() to reset Durable Object"` (expected) → DO reconstructs → re-reads `this.container.running` **from reality** (`false`) → next `containerFetch` boots a fresh instance + serves; **no wedge**. Exactly the reconstruct → re-read → clean-boot mechanic the fix depends on, observed live.
- ⚠️ **Deploy-stale did NOT reproduce.** A genuine new-image deploy (image tag `b92a2722` → `7042f4f6`, verified changed) recycled **cleanly** — every probe immediately after showed `running:true, status:healthy`, `:9000` `{ok:true}`, `/cmd` served in ~4 ms. - ✅ **`503` provisioning body captured** → confirms D3's exclusion: `"There is no Container instance available at this time.\nThis is likely because you have reached your max concurrent instance count …"`. Never abort on this.
- ❌ **`500` stuck body NOT captured** — the stuck state never occurred, so the verbatim stuck signature stays unknown → D3's regex is **broadened** (superset), not frozen (see D3).

**VERDICT: QUALIFIED GO.** The load-bearing lever (abort → reconstruct → re-read reality → clean boot) is proven on real CF; the stuck-*clear* is inferred (abort = forced idle-evict, the confirmed prod clear — every observable link now holds), not directly reproduced. **Reframe:** this is a **safety net for a rare stuck race**, not the common wakeup path (the common case self-heals). Build Phases 1–2; Phase 3 is opportunistic (D7).

**GATE:** Phases 1–2 may proceed — abort lever confirmed. Carry the QUALIFIED-GO caveats: D3's regex is a superset (stuck body uncaptured), and Phase 3's end-to-end stuck-clear verification is opportunistic (needs a real prod stuck).

### Phase 2 — Wire recovery into `DevContainer.fetch()` (user-facing) + `ensureUp` (command path)
**Goal**: a stuck preview self-heals via abort, in seconds, bounded, and only against a *corroborated* stuck container; the command path (`ensureUp`) recovers the same way; every decision is a capable-of-failing pure predicate (the `fetch()`/`ensureUp` bodies can't construct under pool-workers).

**Success Criteria**:
- [ ] **Recover-sentinel matching** — extract an exported pure `isRecoverRequest(request)`, matched as the **first** statement in `fetch()` (before `#setPreviewBaseEnv` and the WS branch — on the recover path the DO is about to be torn down; neither the `envVars` mutation nor WS handling is wanted, #9). ⚠️ Premise: the direct-serve route passes **no** `prefix` and `routeDORequest` forwards the **full** original URL, so `fetch()` receives `url.pathname === '/dev-container/{u}.{g}.dev/_nebula/recover'` — segments are **NOT** stripped; match the trailing `/_nebula/recover`. Capable-of-failing test: matches `/dev-container/acme.app.dev/_nebula/recover`; does **NOT** match a legit asset containing the substring (`/dev-container/acme.app.dev/src/_nebula/recover.vue`).
- [ ] **Recover-GET handler order (all before `super.fetch()`):** `isRecoverRequest` → `isSameOriginRecover` (403 if not) → **server-side stuck-corroboration** → `#forceReset()`. Corroboration = a **bounded** `containerFetch` probe (`AbortSignal.timeout(~5s)`): `#forceReset()` fires only if `isStuckFlagResponse(probe.status, probeBody)` **or the probe times out** (frozen-stuck); a healthy `200` or a `503`/provisioning probe → **no abort**, return a benign response. ### Cooldown durability (criterion #4) — RESOLVED via a deploy test + FIX APPLIED (2026-07-04)
A throwaway deployed DO (`lmz-abort-kv-test` → CF → torn down) proved the shipped `#forceReset` had a **real bug**: `kv.put(ABORT_TS_KEY, now); ctx.abort()` with **no yield** between them **LOSES the write in cloud** (a sync write commits only on an I/O-gate flush; abort discards the uncommitted write). Two surprises: **`await ctx.storage.put` is NOT a fix** (also lost — the async API was never the issue; sync/async share the keyspace) and a **bare microtask yield is not enough**. **Fix applied:** one macrotask yield (`await new Promise(r => setTimeout(r, 0))`) between the `kv.put` and the `ctx.abort()` → the output gate flushes → the value **survived** in cloud. Stays **within** the sync-storage rule. So criterion #4's storage-durability crux is now **closed + verified in cloud** — NOT locally verifiable (miniflare's local abort reconstructs with wiped storage regardless — [[miniflare-local-abort-wipes-storage]]), so the ui-smoke test correctly omits it.
