# Nebula — DevContainer wakeup-after-hibernation FIX

**Status**: **Phase 0 spike DONE (2026-07-01) — QUALIFIED GO; re-reviewing (Stage 2).** The **safety-net fix** for the (rare) DevContainer stuck-`running` stall: detect the stuck signature on the preview-GET path and force DO reconstruction with `ctx.abort()`. Phase 0 **confirmed the abort lever on deployed CF** (reconstruct → re-read `running` from reality → clean boot) but found the container **self-heals in every off-prod scenario** (local `docker kill`/`stop`, deployed new-image, deployed idle-sleep) — so the stuck flag is a **rare race, not the common wakeup path** (see Phase 0 RESULTS). Lands entirely **below the mesh layer** (`fetch()` + `containerFetch` + `ctx.abort()`) — touches only `apps/nebula/src/dev-container.ts` (+ its test), never `dev-studio.ts` — independent of, and sequential with, the mesh continuation-only work. Implements diagnosis option **#1**. Mesh-orthogonality rationale is owned by the diagnosis — see [nebula-container-wakeup-recovery.md](archive/nebula-container-wakeup-recovery.md) Q1/Q5 + § Coordination; do not restate it here.

> **Read the diagnosis first** for the mechanism + evidence — this file is the **implementation plan** only: [nebula-container-wakeup-recovery.md](archive/nebula-container-wakeup-recovery.md) (§ The mechanism, § Local reproduction log, Q1–Q5).

## The fix in one line
The stuck state is a stale `this.container.running=true` the base can't restart past (`startContainerIfNotRunning`: `if (this.container.running) return 0`), and `destroy()` doesn't clear it in the deploy-staled cloud case. **Detect the stale-flag signature on the preview-GET path and force DO reconstruction with `ctx.abort()`** — the forced, immediate equivalent of the idle-eviction that is today the *only* known clear (recovery drops from ~minutes to seconds). `ctx.abort()` is the same lever the container base itself uses on "Network connection lost" (`@cloudflare/containers` `dist/lib/container.js` ~L1416).

## Decisions

| # | Decision | Choice | Rationale |
|---|---|---|---|
| **D1** | Recovery lever | **`ctx.abort()`** (forced DO reconstruction) | `destroy()` does NOT clear the deploy-staled flag (diagnosis Q2: same dead id persisted across many attempts); only idle-evict does; `abort` = forced idle-evict = immediate. Base uses it for the analogous stuck-connection case. **Phase 0 CONFIRMED the mechanic deployed** (abort → reconstruct → re-read `running` from reality → clean boot, no wedge); the stuck-*clear* is inferred from this + "idle-evict is the confirmed prod clear," since the stuck precondition wouldn't reproduce off-prod to test directly. |
| **D2** | Where recovery lives | **The preview-GET path** (`DevContainer.fetch`), browser-driven | It's the user-visible "500s forever" surface, it isn't a mesh call, and it's always present in the Studio when in a dev star. **Abort cannot live in `ensureUp`**: `DevStudio` invokes it via awaited `callRaw` from `dev-studio.ts` (hands-off), and aborting mid-invocation strands that await — so the preview-GET path is the *only* home for abort in this cut. Command path inherits recovery once the DO resets (no `ensureUp` change here). |
| **D3** | Stuck detection | New **`isStuckFlagResponse(status, body)`** = `status===500 && /not running\|suddenly disconnected\|proxying request to container/i` — a **genuine strict subset** of `isContainerColdResponse`'s 500 phrases | The abort-worthy signature only: the **proxy-path** phrases where a stale `running=true` manifests (base `container.js` L972 `"Container suddenly disconnected, try again"`, L975 `"Error proxying request to container: …"` — the prod-observed `"…not running…"` rides inside the latter). Does NOT replace `isContainerColdResponse` (which also matches `502`/`429`/`503`/provisioning); distinct jobs (D4). **500-only** (M1: the base never emits `502` on the container path — a `502` is a CF edge fault `ctx.abort()` can't fix; it stays cold→page, not stuck→abort). **Excludes `Failed to start container`** (M3: a genuine crash-on-boot / bad-image / bad-entrypoint 500 — autoRecover on it = abort→recrash→abort loop; keep it in `isContainerColdResponse` for the page only) and **`Network connection lost`** (m1: never a response *body* — it's the internal error the base wraps *into* the `suddenly disconnected` body). ⚠️ **Phase 0 could NOT capture the verbatim prod stuck body** (self-healed every time) → this is the conservative base-library-emitted subset, NOT a captured signature; narrow only if a real stuck body is ever captured. `502`/`429`/`503`/provisioning excluded — Phase 0 captured the `503` body (`"There is no Container instance available…max concurrent instance count…"`); aborting it would thrash a legit boot. |
| **D4** | Abort orchestration + predicate precedence | **`isContainerColdResponse` gates the waking PAGE (unchanged); `isStuckFlagResponse` gates AUTO-RECOVER within that page** | `ctx.abort()` kills its own invocation, so it can't return a `Response` — hence a two-step: `fetch()` serves `wakingPreviewPage({ autoRecover })` on any cold response (`isContainerColdResponse`, the existing gate at `dev-container.ts:336`, untouched), with `autoRecover = isStuckFlagResponse(status, body)`. When `autoRecover`, the page's JS hits the `/_nebula/recover` sentinel (→ `#forceReset()` → `ctx.abort()`) then reloads once; a cold-but-not-stuck response (provisioning/capacity) serves the SAME page with manual reload only (no abort). Auto-reload is safe now — recovery is abort-driven, not idle-evict-driven — but **bounded** (≤2 attempts via `sessionStorage`) with the manual button as final fallback. This is the reconciliation: one page gate, one abort-decision input, no overlap. |
| **D5** | `#forceReset()` shape | Best-effort `destroy()` (non-hanging) **then** `this.ctx.abort()` | `destroy()` is cheap and clears the *cold-but-not-deploy-staled* case; `abort()` is the load-bearing clear for the deploy-staled case. `destroy()` must not block the abort (short timeout or fire-and-forget + catch). |
| **D6** | Recover-endpoint auth | **Ungated**; `Sec-Fetch-Site: same-origin` closes cross-*site* drive-by only; a **per-instance abort cooldown (now Phase 2)** is the real rate bound | Auth/rate-limit friction is anti-wedge (`_review-lens.md` (b)); the surface is ungated by design (ADR-007: `fetch()` is public, sensitive ops go over mesh). **Honest boundary — two vectors, only one closed by the header:** `/_nebula/recover` is a plain **GET** firing a state-changing `ctx.abort()`. (1) **Cross-site CSRF-via-GET** (`evil.com` `<img src=…>`) → **closed** by the shipped `Sec-Fetch-Site: same-origin` check at `#forceReset()`'s entry (browser-set + unforgeable; rejects cross-site + header-less callers, passes the same-origin waking page; zero friction). (2) **Same-origin cross-tenant** → **NOT closed**: all tenant previews share ONE origin under path prefixes (`/dev-container/{u}.{g}.dev/…`) and previews render **untrusted agent-authored code**, so a script on *any* preview can `fetch('/dev-container/{victim}/_nebula/recover')`, carry `same-origin`, and force-abort the victim's DevContainer. `Sec-Fetch-Site` is origin-scoped (path-excluded) — it CANNOT isolate tenants; D6 does **not** claim it does. **Accepted, bounded residual:** abort is a *lifecycle* action touching **no data** (ADR-008: enforcement at the point of action; DevContainer holds no durable truth beyond the `appVersion` kv, which survives abort; disk reverts + re-pushed, Flow 1c) — worst case a recoverable forced cold-boot DoS. The loop-abuse bound is the **per-instance abort cooldown, promoted to a Phase 2 deliverable** (a DO-local guard, not an auth gate). |
| **D7** | Efficacy verification | **Mechanic confirmed by Phase 0; stuck-clear inferred; wired-mechanism verify (Phase 3) is opportunistic** | The stuck trigger has **no local analog** AND did **not reproduce on a deployed throwaway harness** either (`docker kill`/`stop`, deployed new-image, deployed idle-sleep all self-heal; `docker pause` freezes with the instance still *present* so abort can't clear it). Phase 0 therefore confirmed the abort *mechanic* (reconstruct → re-read reality → boot) but could not exercise a stuck-*clear* end-to-end. Local tests cover detection + wiring + no-regression; Phase 3 (deploy-verify the wired mechanism against a real stuck) can only run if a genuine stuck recurs in prod — treat as **opportunistic**, not a hard gate. |

**RESULTS (2026-07-01 — throwaway harness `experiments/container-node-phase0` deployed to CF, then fully torn down: worker + container app deleted, spike code reverted):**
- ✅ **Abort lever CONFIRMED on real deployed CF** (Test A): `ctx.abort()` → RPC errors with `"Application called abort() to reset Durable Object"` (expected) → DO reconstructs → re-reads `this.container.running` **from reality** (`false`) → next `containerFetch` boots a fresh instance + serves; **no wedge**. Exactly the reconstruct → re-read → clean-boot mechanic the fix depends on, observed live.
- ⚠️ **Deploy-stale did NOT reproduce.** A genuine new-image deploy (image tag `b92a2722` → `7042f4f6`, verified changed) recycled **cleanly** — every probe immediately after showed `running:true, status:healthy`, `:9000` `{ok:true}`, `/cmd` served in ~4 ms. So the container **self-heals in every off-prod scenario** (local `docker kill`/`stop`, deployed new-image, deployed idle-sleep). The prod 2026-06-28 stuck was a **rarer race** than "any deploy" — likely: the DO hibernating at deploy time + the base monitor missing the instance-stop + the traffic/reconnect storm keeping the DO resident so it never idle-evicts.
- ✅ **`503` provisioning body captured** → confirms D3's exclusion: `"There is no Container instance available at this time.\nThis is likely because you have reached your max concurrent instance count …"`. Never abort on this.
- ❌ **`500` stuck body NOT captured** — the stuck state never occurred, so the verbatim stuck signature stays unknown → D3's regex is **broadened** (superset), not frozen (see D3).

**VERDICT: QUALIFIED GO.** The load-bearing lever (abort → reconstruct → re-read reality → clean boot) is proven on real CF; the stuck-*clear* is inferred (abort = forced idle-evict, the confirmed prod clear — every observable link now holds), not directly reproduced. **Reframe:** this is a **safety net for a rare stuck race**, not the common wakeup path (the common case self-heals). Build Phases 1–2; Phase 3 is opportunistic (D7).

**GATE (updated):** Phases 1–2 may proceed — abort lever confirmed. Carry the QUALIFIED-GO caveats: broaden D3's regex (stuck body uncaptured), and treat Phase 3's end-to-end stuck-clear verification as opportunistic (needs a real prod stuck).

### Phase 2 — Wire recovery into `DevContainer.fetch()` (the user-facing fix)
**Goal**: a stuck preview self-heals via abort, in seconds, bounded — and every decision on this path is a capable-of-failing pure predicate (the `fetch()` body itself can't construct under pool-workers, so logic that lives only inside it is untested).

**Success Criteria**:
- [ ] **Recover-sentinel matching** — extract an exported pure `isRecoverRequest(request)`. ⚠️ Premise correction: the direct-serve route passes **no** `prefix` and `routeDORequest` forwards the **full** original URL, so `fetch()` receives `url.pathname === '/dev-container/{u}.{g}.dev/_nebula/recover'` — segments are **NOT** stripped. Match the trailing `/_nebula/recover` on the full path. Capable-of-failing test: matches `/dev-container/acme.app.dev/_nebula/recover`; does **NOT** match a legit asset containing the substring (`/dev-container/acme.app.dev/src/_nebula/recover.vue`).
- [ ] `fetch()` intercepts a recover request using **request-derived data only** — NOT `this.lmz.instanceName` (identity is stamped *inside* `super.fetch()` via `initIdentityFromHeaders`, which is also not exported for a direct pre-`super.fetch()` call — M5). Order, all **before** `super.fetch()` (so it never proxies to the container): `isRecoverRequest(request)` → the `Sec-Fetch-Site` guard (below) → `#forceReset()`. `routeDORequest` already routed to the correctly-addressed DevContainer by URL, so `ctx.abort()` only tears down *this* instance. Do **NOT** add a "400 on malformed/absent routing header" branch — the router always overwrites that header from the URL, so it's unreachable here (m2). The recover request is expected to error out (abort kills it); the client `.catch()`es it.
- [ ] **Cross-site CSRF guard (D6, shipped)**: `#forceReset()` runs only when `request.headers.get('Sec-Fetch-Site') === 'same-origin'`; otherwise return a 403 (no abort). Extract as a pure `isSameOriginRecover(request)` with a capable-of-failing test: `same-origin` → allowed; `cross-site` / absent → rejected. ⚠️ This blocks cross-*site* drive-by ONLY — it does NOT stop a same-origin cross-tenant caller (D6, vector 2); the **per-instance abort cooldown** below is that bound.
- [ ] **Serve/auto-recover decision** — extract an exported pure `decidePreviewResponse(status, body, isDoc)` returning `{ servePage, autoRecover }`: page iff `isDoc && !ok && isContainerColdResponse` (existing gate, untouched); `autoRecover = isStuckFlagResponse(status, body)`. `fetch()` calls it, then serves `wakingPreviewPage({ autoRecover })`. Capable-of-failing tests via `it.each`: `500` stuck body → `{servePage:true, autoRecover:true}`; **`502`/`503`/`429` → `{servePage:true, autoRecover:false}`** (cold→page, never abort — the M1/D3 anti-thrash cases, each a distinct assertion, not folded into a string match); **`500 "Failed to start container"` → `{servePage:true, autoRecover:false}`** (M3 crash-loop guard); genuine-app-`500` → `{servePage:false}` (never masked/aborted); non-doc asset → `{servePage:false}`.
- [ ] **Bounded reload counter** — extract an exported pure `nextRecoverAttempt(prevCount) → { reload, nextCount }` (reload iff `prevCount < 2`), embedded in the page's JS AND unit-tested with `it.each([[0,true],[1,true],[2,false],[3,false]])`. The `<2` bound is the reload-storm guard; a string `toMatch(/sessionStorage/)` would pass at any bound, so the proof lives in this pure fn.
- [ ] `wakingPreviewPage(autoRecover)`: when `autoRecover`, JS reads/writes the `sessionStorage` counter through `nextRecoverAttempt`; on `reload` → `fetch('<recover-url>').catch(()=>{})` then `setTimeout(()=>location.reload(), ~1500)`; else (bound hit, or `!autoRecover`) show the manual Reload button only. No unbounded `http-equiv=refresh`.
- [ ] **Per-instance abort cooldown (D6's real bound, promoted from Deferred — closes the same-origin cross-tenant abuse the `Sec-Fetch-Site` guard can't):** `#forceReset()` no-ops (returns without aborting) if it already aborted within the last ~N seconds. The last-abort timestamp lives in `ctx.storage.kv` (it MUST survive the abort→reconstruct, so persist it *before* calling `ctx.abort()`; `ctx.storage.kv` is durable, `Date.now()` advances across invocations — fine for a coarse cooldown). Not an auth gate. Capable-of-failing test: drive `#forceReset()` twice in quick succession → only the first aborts (the second is cooled-down); after the window, it aborts again.
- [ ] Tests updated: `wakingPreviewPage()` asserts (a) `autoRecover` wires the recover URL, (b) `!autoRecover` is manual-only, (c) still no unbounded meta-refresh — plus the extracted pure fns above carry the load-bearing proofs. Update the existing "no auto-reload" test's *intent* to "bounded, abort-coupled self-heal."

- ~~Per-instance abort cooldown~~ — **promoted to Phase 2** (M2: it's D6's real bound against the same-origin cross-tenant abort vector the `Sec-Fetch-Site` guard can't close; no longer deferred).
