# Profile access control — the same door as everything else, and the Resources plane behind it

**Status:** DRAFT 2026-09-08, Pass 1 (design intent) awaiting Larry's read. Gates ② personas, whose path is `impersonate()` over an accepted membership; gated by nothing; lands before ⑥ the wipe, which is what keeps the Profile's storage change migration-free. Decided 2026-09-07/08 (Larry): acceptance is enforced at the mint and by the Registry's reads, the Profile keys off `sub` like every other guard, and the Profile composes the Resources plane behind an allowlist. Personas are real `@lumenize.io` accounts that accept like anyone; no `synthetic` column lands anywhere.

## Context

Today, the only place in the system where an `act` chain is taken into account for a permission decision is when deciding who can edit the public fields and access the private fields of a Profile. Everywhere else, we only consider the principal `sub` and `act` chains only serve as a record of the impersonator or agent acting on their behalf. Months ago, when we added Profiles, we were forced to temporarily add an `!act` clause to the gate for Profile because it was possible for a bad actor to gain permissions they should not have using steps like these:

1. A bad actor uses self-signup for a Universe
2. They create a Galaxy
3. They invite a target user's email to be a collaborator in the Galaxy
4. Even before the target user accepts the invitation, the bad actor can now access private fields and modify all fields of the target user's Profile

However, on 2026-08-04 we required that all invites be accepted before they are considered "active" — for login, and for the Profile's own scoped-admin branch. The invitee is told not to accept unless they know the inviter and the purpose of the invitation. One site still treats an unaccepted membership as live: the narrower-token mint behind `impersonate()`, which reads the membership but never asks whether it was taken up, so the bad actor above can still mint a token that carries the target's `profileId`. Making that mint refuse a subject whose membership is not accepted closes the last door. Then an `act`-bearing token can only ever exist over a membership the person took up, and the gating for Profile can match the rest of the system and only key off of the `sub` claim.

The second half is where the Profile keeps its data. It is the one resource host in Nebula that is not on the Resources plane: a key-value table of fields, last-writer-wins, no history, no record of who wrote, and a forty-line copy of the plane's subscribe idea. Once impersonators can edit a profile, who wrote it matters, and the plane already records that on every snapshot. Composing the plane onto the Profile, behind the same access check, gives it the record, the history and the standard subscribe surface without copying any of them, and doing it before the wipe costs no migration.

**Objective — Profile access control matches the rest of the system, keying only off `sub`, and the Profile's data lives on the Resources plane behind that one check.**

**Five goals, in the order they matter:**

1. **Agents and other impersonators acting on someone's behalf have the exact same access as that someone acting on their own.** Today a token with an `act` chain is refused as the owner of the person's profile outright.
2. **The bad actor's path stays closed, at the mint.** Today the narrower-token mint issues a token over a membership nobody accepted. After: it refuses, and no token carrying a person's `profileId` can exist unless that person took the membership up.
3. **No Registry read can hand an inert membership to an authorization decision by accident.** Today one read that feeds a decision returns pending rows. After: a membership read returns active rows unless the caller asks for pending ones by name.
4. **Every profile write records the acting principal and keeps its history, from the plane rather than a copy.** Today nothing records who wrote a profile and nothing can, because the Profile is not on the plane.
5. **The Profile's copies go.** Its own subscribers table and fan-out loop, and the two profile-specific client calls, are replaced by the plane's subscribe and the client's standard resources surface.

## Relationships

- **② personas** ([nebula-pre-alpha.md](nebula-pre-alpha.md) § *② Personas*) waits on this: each persona is a real `@lumenize.io` account, invited and accepted through the inbound mail that `nebula-testing-with-personas.md` (Larry's, to write) ports to production as its early phase, and then impersonated. Goal 1 is what lets the persona own its profile.
- **⑥ the wipe** ([nebula-pre-alpha.md](nebula-pre-alpha.md) § *⑥ The wipe*) must come after: the Profile's storage changes from a fields table to plane snapshots, free while every Profile DO is about to be recreated and a migration afterwards.
- **Amends** [ADR-012](../docs/adr/012-global-profile-visibility.md), whose owner-branch tripwire names `!claims.act`, and [ADR-013](../docs/adr/013-identity-profileid-resolution.md), which gains the one sentence that a membership is inert until accepted. Both are Proposed; nothing is ratified before pre-alpha launches, and amending a Proposed ADR is an ordinary edit. `security.md`'s rule (1) loses its only exception; `workflow.md`'s ADR-012 one-liner follows.
- **Releases a deferral.** The Profile gating fix had been parked behind the invite and self-signup acceptance rejigger with a home/discovery page; it lands here, and the rejigger keeps the split of the pending-aware Registry reads that the login and discovery flows own.

## Context and current state

**Built already, and what becomes of each part:**

- **`#requireOwnerOrAdmin` in `packages/nebula-auth/src/profile.ts`** gates the public write and the private read and write through four branches: the owner, the token's `profileId` being this profile with no `act`; a bare `scopeAdmin` test that rejects a non-admin with no read; the platform root; and the scoped admin, which makes the guard's one registry read, `lookupProfileScopes`, and asks `hasDominionOver` of each scope the person accepted. **Adapted:** the owner branch loses `!claims.act` and nothing else changes; the whole guard becomes the allowlist check in front of the plane.
- **The narrower-token mint in `worker-token.ts`** issues `sub`, `authScope` and `scopeAdmin` as the subject's, the caller in `act`, the subject's `profileId` on the token, and refuses a subject the caller does not administer. Its membership read is `getIdentityScope`, which has no acceptance filter. **Adapted:** it refuses a subject whose membership is not accepted, with a refusal a test can tell from the dominion one.
- **The Registry's membership readers** — seventeen touch `Memberships`. Two feed authorization: `getScopesForProfile` already filters on acceptance; `getIdentityScope` does not. Seven read the flag to run the login, consent, resume and summary flows, and the rest are address-level operations that must see pending rows. **Adapted:** the authorization-facing read becomes active-only; the flows that need pending rows say so. **Carried over:** the rest, unchanged in behaviour.
- **The Profile DO** — `Profile extends ComposedMeshDO(DurableObject, 'Profile')` in `nebula-auth`, a `ProfileFields` key-value table, a `Subscribers` table, and a `#fanout()` that calls each subscriber with `lmz.call`, deliberately not `svc.broadcast`. **Adapted:** it moves to `apps/nebula`, where the plane and the other resource hosts live, keeps its `PROFILE` binding, composes a `ResourceDataPlane`, and keeps four `@mesh` methods. **Left behind:** the two tables and the fan-out.
- **`ResourceDataPlane`** in `apps/nebula` is built from a context getter, an ontology provider and a seven-callback bridge; it never calls `lmz` or `svc` itself, and every outbound rides the bridge the host implements. Galaxy's bridge delivers with `this.lmz.call` and fans out with its `broadcast`. **Carried over unchanged**, with one seam added: the plane's per-op DAG check on writes already yields to a server-composed verdict (the reply's `pinnedAtPost`); reads gain the same, under one general name.
- **The client's profile calls in `nebula-client.ts`** — a read and a subscribe on the fixed `PROFILE` binding with the `profileId` as instance. **Adapted:** they route to the plane's methods on that host; the client's standard resources surface is what a profile-aware UI reads through.
- **Tests that pin today's refusal.** `profile-do.test.ts`'s "a NARROWER token is NOT the owner" inverts; its owner-zero-reads, scoped-admin-one-read and manufactured-membership tests carry over against the plane; `impersonate.test.ts` and its siblings create subjects with `createSubject`, which invites and never accepts, so every one impersonates an unaccepted membership today — the helper accepts, and the fixtures become the honest ones; `identity-mint-point.test.ts`'s manufacture test carries over; the live `profile-takeover-refused` scenario already drives invite, refusal and acceptance end to end and gains the mint limb; `impersonation-lifecycle` and `impersonation-expiry` use real logins and carry over unchanged.

## Design intent, constraints, and future state

**Acceptance is enforced where a token is born, so no guard needs to ask about `act`.** A membership is a row the Registry creates at invite or self-signup, inert until the person consumes a link delivered to their mailbox and confirms behind the consent modal, and that accept endpoint is credentialed by the cookie the consume placed, so nothing else can accept it. Today the login and the Profile's scoped-admin branch honour that; the narrower-token mint does not, and it is the one door the bad actor's steps in § *Context* still open. After this task the mint refuses a subject whose membership is not accepted. Then an `act`-bearing token exists only over a membership the person took up, an admin impersonating them arrives at exactly the profiles that admin already reaches by dominion, and the Profile's owner branch keys off `sub` and `profileId` like every other guard. `security.md`'s rule (1) — authorization reads the subject's claims, never the `act` chain — has no exception left.

**The Registry says it structurally: a membership read is active unless asked otherwise.** The reads that feed authorization decisions return accepted memberships and nothing else; the flows that exist to accept, resume, list or delete memberships ask for pending rows explicitly, by a name or a parameter that says `pending`. A new authorization-facing reader written next year cannot see an inert row without asking for it. [ADR-013](../docs/adr/013-identity-profileid-resolution.md) records the commitment in one sentence, so the default is deliberate rather than incidental.

**The Profile composes the Resources plane and is its only door.** Moving the Profile into `apps/nebula` lets it compose `ResourceDataPlane` exactly as Galaxy does: an ontology of two types, `Profile` holding the public fields and `ProfilePrivate` holding `privateNotes`, so the public read is an allow-list by type rather than by subtracting keys; a bridge implemented with the Profile's own `lmz.call`, delivery to the client gateway and a per-target loop for fan-out, which is the flat loop `NebulaDO.broadcast` pins anyway; and four `@mesh` methods — `read` and `subscribe`, public by ADR-012; `transaction` and the private read, behind the owner-or-admin check. Nothing on the plane is reachable except through those four, so a method added to the plane later is unreachable here by construction. The plane's own DAG has no grants and is never consulted: its write path already yields to a server-composed verdict, and the read path gains the same, under one name that says the host decided. What the Profile gets for it is the plane's record of the acting principal on every snapshot, ADR-016's one shared projection, its history, its validation and its eTags, none of them copied.

**Every load-bearing assumption, stated so review can falsify it:**

- The plane makes no mesh call of its own; every outbound rides the host's bridge. (`resource-data-plane.ts`'s bridge JSDoc and the absence of `lmz`/`svc` calls in the file.)
- The accept endpoint is credentialed by the membership's own path-scoped refresh cookie, placed by consuming the magic link. (`worker-token.ts`'s accept handler.)
- `getIdentityScope` is the mint's membership read and has no acceptance filter. (`worker-token.ts` calls it at the mint; the Registry's query carries no `acceptedAt` clause.)
- The wipe recreates every Profile DO's storage, so a change of storage shape before it is not a migration. (⑥'s definition in the master plan; to be confirmed there.)
- A profile write is not an ADR-016 event in itself — it destroys nothing and changes no authority — so the plane's per-snapshot record is the traceability this task promises, and no further record is owed.

**Constraints.** [ADR-012](../docs/adr/012-global-profile-visibility.md) binds the open read and the two capability levels; this task amends its owner-branch tripwire and satisfies its allow-list rule by type. [ADR-013](../docs/adr/013-identity-profileid-resolution.md) keeps `profileId` stamped and never keyed, and gains the acceptance sentence. [ADR-015](../docs/adr/015-passage-and-dominion.md)'s `hasDominionOver` stays the only scope verdict. [ADR-007](../docs/adr/007-shared-node-security-core.md): the plane is a capability by composition, which is exactly why the Profile can hold one. `mesh.md`'s dependency direction is why the Profile moves up rather than the plane moving down. `security.md` rule (1) loses its exception and rule (2) gains the acceptance clause. `testing.md` wants the manufactured membership as the fixture, and `live.md` makes the scenario the default tier.

**Future state.** ② provisions personas as real accounts through the ported inbound mail, accepts them, and impersonates them; each persona then owns its profile through goal 1. ⚠️ Design consideration: ADR-012's deferred structural answer, private fields keyed by scope, is neither taken nor foreclosed — `ProfilePrivate` is one resource today and could become one per scope. ⚠️ Design consideration: the host-decided verdict on reads is a general seam; any future host whose authorization is not per-sub DAG grants can use it, and a review should ask each such host to say why.

## Decisions

| Decision | Rejected alternative — why |
|---|---|
| Acceptance is enforced at the mint, and the Profile guard keys off `sub`. | **An acceptance arm on the owner branch** (the 2026-09-07 design): the same fact checked at a branch instead of at the token's birth, keeping one `act`-presence exception alive. Superseded 2026-09-08 once Larry's framing made the mint the site. |
| Impersonation stays the persona path. | **Per-persona cookies** — a real login per persona with the refresh cookie named per persona. Touches every refresh site; the first refresh has no sub to name. **Synthetic sessions** — a mint variant with no `act`. A second mint form in rule (2). Both rejected 2026-09-07. |
| Personas are real `@lumenize.io` accounts that accept like anyone. | **A `synthetic` column licensing a membership created already accepted** — a second door beside the mailbox one, and its other consumer, the digest, never needed it: every persona action carries `act` naming the owner. Rejected 2026-09-08. |
| Registry membership reads are active by default; pending-aware reads say so by name. | **A sentence in an ADR alone** — a commitment nobody's code enforces, which is how the mint's read went unfiltered. The sentence still lands, in ADR-013, as the record of the default. |
| The Profile composes the plane behind four `@mesh` methods. | **Subclassing `NebulaDO`** — its `onBeforeCall` refuses lateral passage a global object needs, so it would be a no-op, and every plane method would then be a door to gate one by one, including the ones added later. |
| The Profile moves up into `apps/nebula`. | **Moving the plane down into a package** — larger, and the Profile is platform business logic by the layer map, not registry infrastructure. |
| The plane's DAG stays empty; the host's verdict is passed on reads and writes. | **Granting everyone at the root** — makes the plane's checks true by construction rather than skipped by decision, and a later reader of the DAG would believe the grant. |
| No hand-written acting-principal stamp on profile writes. | **A last-writer field in the fields table** (the 2026-09-07 draft) — an interim the plane deletes weeks later, paid for twice. |
