# Broadcast is core to every mesh node, and it delivers directly

**Status:** Pass 2, ready to build. The design intent was **hand-reviewed** (Larry, 2026-09-26; that review is where the tier removal, the Profile's scope and the ADR-007 answer came from). Stage 2 conformance ran the same day, and its decisions were folded in on 2026-09-27; they added a Gateway fix, a chain option and the client's `broadcast`.

**A deliberate detour** from [nebula-data-plane-owns-its-guards.md](nebula-data-plane-owns-its-guards.md), which cannot collapse its host bridge (its D22) until this lands. It runs on a **condensed process** (Larry, 2026-09-26): a hand review of Pass 1 instead of a Stage 1 panel, one Stage 2 conformance pass, and no `/build-task` verifier panel — so each phase below carries criteria that can fail on their own.

**Objective — every mesh node can fan one continuation out to many addresses, and every delivery comes from the node that originated it.** Today fanning out requires extending `LumenizeDO`, and above a hundred targets the delivery comes from somewhere else, which breaks two things that read the sender. And part of the call chain a receiver reads is written by the client, so the address a subscriber row stores, and a tab's check on who is calling it, can both be forged.

The sections below give what is true today, the changes that follow, and what the removal costs.

## Context and current state

**`svc` belongs to `LumenizeDO`; `lmz` belongs to every composer.** `get svc()` is declared on `LumenizeDO` alone, so a node composed the other way has no `svc` at all — not an empty one. `ComposedMeshDO(DurableObject, 'Profile')` in `packages/nebula-auth/src/profile.ts` is that node, in production today, and it therefore cannot reach `broadcast` by any path.

**What `broadcast` needs from its host is two things, and a bare composer has both.** `broadcast(doInstance)` reads exactly `doInstance.ctn` and `doInstance.lmz.call`, and `broadcast.ts` imports only from `./ocan/index.js`. Nothing in it touches storage, alarms, `onStart` or `fetch`. Its home on `svc` comes from one registration line in `lumenize-do.ts`, whose own comment scopes the consequence — *"always available on this.svc.broadcast for LumenizeDO subclasses"*. Once the tier branch goes, it reads only `lmz.call`.

**`sql` and `alarms`, its neighbours in that registry, are genuinely different**, which is why this task moves one service and leaves the registry standing. `Profile`'s own comment states the distinction from the outside: it has *"no `onStart`/`alarms`/`svc.broadcast` (a raw composer has no `onStart`…)"*. An alarm needs the `alarm()` handler `LumenizeDO` owns; a broadcast needs a continuation and a way to send it.

### The function has two branches, and the second one is broken

`broadcast` picks its branch on target count alone — a flat loop while `targets.length <= directThreshold` (default 100), and above that it hands the whole list to a recursive tier Worker. The two differ in **who sends the leaf call**, which is what `metadata.caller` is stamped from. On the flat loop that is the origin node; on the tier path it is the tier Worker. Three defects follow, none of them fixed:

1. **The dead-subscriber reaper deletes nothing.** `__forwardBroadcastResult` fires to the origin's `__handleResponse`, where `executeEnvelope` overwrites `callContext.callee` with the *receiving* node's own identity — so the reaper reads the broadcasting DO's own name and its `DELETE` matches no row. Nothing throws and nothing logs; the row just leaks.
2. **A caller-gated receiver refuses a legitimate push.** `NebulaClientGateway.onBeforeCallToClient` opens a cross-scope profile push only for `caller.bindingName === 'PROFILE'` and otherwise throws *Active-scope mismatch*. Past the threshold the caller is the tier Worker, so the fence correctly refuses — triggered by nothing but popularity.
3. **The client-origin branch is misrouted**, because `svc.broadcast` starts no fresh chain: `callChain[0]` is whoever originated the write, so a delivery failure is forwarded to that client rather than to the broadcasting DO. That same branch is also where a filled chain still reaches a client's push door, defended only incidentally — its op 0 happens to name a DO method.

**The tier is dormant, and doubly so.** `apps/nebula` binds no `LUMENIZE_BROADCAST_TIER`, and `lmz.call` validates its target synchronously, so without a pin the 101st subscriber would not degrade — it would throw and fail the transaction that triggered it. `NebulaDO.broadcast` pins `directThreshold: Infinity` to stop that. Nothing else reaches the tier: the only exercise anywhere is two `packages/mesh` unit tests that force it with `directThreshold: 0`, plus one browser bench built to measure it.

**And every `LumenizeWorker` offers it to whoever can call one.** `__broadcastTier` and `__forwardBroadcastResult` are `@mesh()` members that every `LumenizeWorker` subclass inherits. `NebulaAuthFacade` is one: it keeps the no-op default `onBeforeCall`, and clients call it directly. So today any client can have the facade re-send a chain it chose to targets it chose, fanned out with a `branch` it chose.

**Who calls broadcast today:** exactly one production site, `apps/nebula/src/nebula-do.ts` — the `NebulaDO.broadcast` wrapper, which Star and Galaxy call at nine sites — plus two calls in `packages/mesh/test/test-worker-and-dos.ts` and five conceptual blocks in `website/docs/mesh/broadcast.mdx`. Everything else a grep finds is JSDoc describing the mechanism.

**The Profile hand-rolls what the flat loop already does.** Its `#fanout()` is the same three lines per target — `lmz.call(binding, clientId, remote, onResult, { onErrorOnly: true })` — and its `onProfileBroadcastResult` reads `callContext.callee?.instanceName` exactly as `Star.onBroadcastResult` does. It exists because `svc.broadcast` was unreachable *and* unsafe, and this task removes both reasons.

**And part of the chain every receiver reads comes from the client.** The Gateway rebuilds a client's chain as `[verifiedOrigin, ...clientCallChain.slice(1)]`, so element 0 is stamped from verified sources and everything after it is copied from the client's own frame. Three readers trust the last element, `callChain.at(-1)`:

- **The Profile's `subscribe`** stores `subscriberBinding` from it, and later calls that binding.
- **Star and Galaxy** do the same at eight subscribe sites.
- **`LumenizeClient.onBeforeCall`** takes it as the immediate caller, and accepts any push whose last hop is a DO or a Worker.

What a forged hop buys depends on the reader:

- **An unroutable binding** — absent from `env`, or a Worker binding given an instance name — makes `lmz.call` throw synchronously on every later push, and no reaper clears the row, because the failure is not a `ClientDisconnectedError`. On the Profile, `#fanout()` has no per-target catch, so every subscriber ordered after the row stops receiving updates. On Star and Galaxy the throw lands in the fan-out that runs after a commit, so every later write to that resource lands and still fails the writer's call, skipping the query reruns and the `onCommitted` hook after it. A DO binding routes instead, to a DO named after the client.
- **A forged last hop naming a DO** gets a push past a tab's own guard, so a member can deliver fake updates into a co-member's tab, whose name rides every push that tab writes.

**A Profile push also carries the writer's claims into other scopes.** Every update inherits the writer's chain, and `#forwardToClient` sends `originAuth` down on purpose, since a client's `onBeforeCall` authorizes from it. So each subscriber's tab receives the writer's `sub`, `aud`, `access`, `profileId`, `act` when an admin is impersonating, and the writer's tab name in `callChain`. The Gateway's `aud` fence keeps a writer's claims in the writer's own scope, and Nebula's Gateway skips that fence for any push whose caller is `PROFILE`.

**The subdomain build has decided how that ends.** [nebula-scope-moves-to-subdomain.md](nebula-scope-moves-to-subdomain.md) § *A push speaks for the node, not the writer* makes a fan-out start a fresh chain by default, in `@lumenize/mesh`, and deletes the fence with its Profile exemption in the same phase, since a claim-less push arriving first would be refused at every Star and Galaxy subscriber.

## Design intent

**The changes.** The phases give the order they land in.

1. **`lmz.broadcast(targets, remote, opts?)`, registered beside `call` on every node's `lmz`** — the DO factory, which `LumenizeDO`, `LumenizeContainer` and the Profile all reach through `ComposedMeshDO`; the Worker factory; and the client's `LmzApiClient` (Larry, 2026-09-27). `broadcast.ts` keeps its module and its exported types; what moves is the registration line and which object the function hangs off. `svc.broadcast` goes with no alias, and so does its `LumenizeServices` member, or `this.svc.broadcast(...)` would still compile and fail at run time. One production caller makes the sweep trivial, and an alias would be a second spelling of one capability. Its options are `onResult`, plus `newChain` and `state` passed through to each target's `lmz.call`.
2. **The tier branch is deleted**, and with it `__broadcastTier` and `__forwardBroadcastResult` (whose only callers are the tier itself), `BROADCAST_TIER_BINDING`, the `directThreshold` and `branch` options, their two defaults, and the service bindings and bench wiring that exist only for it. Every fan-out is then a direct loop from the origin node at any N, so the sender a receiver sees is always the node that decided to push. **This deletes a class rather than guarding it** (`calibration.md` §2): a default flip or a fence-safe sibling primitive would both be guards on a mechanism that can simply not exist. It also takes the facade's relay away, since the two members go from every `LumenizeWorker`.
3. **`NebulaDO.broadcast` goes** (Larry, 2026-09-26). With no branch left to pin it holds no policy, and the chain default the subdomain build sets belongs in the package, so its nine call sites call `this.lmz.broadcast` directly. ④ records the bridge collapse this enables as its D22.
4. **The Gateway stops copying client hops** (Larry, 2026-09-26). `#handleClientCall` builds the chain from the verified origin alone, so every server node sees a Gateway-stamped `callChain.at(-1)` on a client's call. That closes all three readers above at once: the Profile's stored binding, Star's and Galaxy's, and a tab's own caller check. A client can no longer extend its own chain, and nothing in source or tests relies on it doing so.
5. **The Profile adopts `lmz.broadcast` and deletes its loop.** `#fanout()` becomes one `lmz.broadcast` call over targets built from its subscriber rows; `onProfileBroadcastResult` stays unchanged as the `onResult` continuation, and its explicit `onErrorOnly` becomes implicit, since the loop applies that whenever `onResult` is given. It passes `newChain: true` (Larry, 2026-09-27), so its pushes stop carrying the writer's claims — safe now, because the Profile exemption never reads a claim and `NebulaClient` reads no `originAuth`. ⚠️ **This is not tidying — it is the only proof the task works.** The Profile is the repo's one bare composer, so without it nothing shows a non-`LumenizeDO` host can broadcast, and the criterion would have to be synthetic.
6. **The Profile derives that binding from `callChain[0]` instead** (added to scope 2026-09-26, Larry — we are editing the file anyway, and `prefer-doing-small-local-work-now` prefers the fix to a backlog row). `callChain[0].bindingName` is the Gateway's own binding, stamped at the WebSocket upgrade from the `X-Lumenize-DO-Binding-Name` header `routeDORequest` sets, which the Gateway's comment calls out as replacing *"whatever the client sent"*. ⚠️ **After change 4 the two expressions read the same element on every client call**, so this is the second layer rather than the fix: it keeps the Profile right if a chain ever reaches it through a relaying node, and it makes the binding read the element `clientId` already reads.

**ADR-007's core gains `broadcast`** (Larry, 2026-09-26). The ADR defines the core as *"exactly comms + guards"* and lists receiving calls, `callContext` propagation, `lmz.ctn()`, `onBeforeCall` and `@mesh()`; broadcast belongs there because it is one continuation sent to many addresses and needs nothing else. Every node type gets it, the client included, so the amendment needs no divergence clause. ⚠️ **This AMENDS an Accepted ADR rather than changing its status**, which is a different act from ratifying one. The body is rewritten in place with git as the record, as `docs/adr/README.md` § *Forward-facing discipline* asks, so it gains no `**Amended**:` line. Its one-liner in `.claude/rules/workflow.md` gains the member, because that line is what an always-loaded session reads instead of the ADR, and both spell `ctn()` as the method on a node it is, not `lmz.ctn`.

**`svc` keeps `sql` and `alarms`** (Larry, 2026-09-26). This task is not the first step of retiring it.

**No per-target catch is added to the loop, and that is deliberate.** Once every binding comes from a verified source — change 4 makes that true on every host, not just the Profile — an unroutable one can only be a genuine misconfiguration, and failing loudly on the first is better than delivering to some targets and swallowing the reason. A catch here would be the second guard on a mechanism whose root cause this task removes (`calibration.md` §2).

**Every node's `lmz` gets it, the client's included.** `LumenizeWorker` and `LumenizeClient` both have `ctn` and `lmz.call`, so nothing distinguishes them here, and `workflow.md`'s cost test prefers the general form when it costs the same. The one argument for DO-only was that `broadcast` would sit confusingly beside `__broadcastTier` on the same class — and that method is being deleted. A client's broadcast grants nothing N calls would not: each delivery is its own call over its own socket, stamped at its Gateway.

**Fan-outs keep the writer's chain until the subdomain build flips it.** This task lands first. It adds `newChain` with today's default and opts in only the Profile, whose exemption reads no claim; a Star or Galaxy push without claims would be refused until the fence goes. The subdomain file carries the flip's acceptance criteria, in its § *A push speaks for the node, not the writer*.

## What the removal costs, stated plainly

- **Tail latency at high N becomes the only option.** With 1,000 subscribers deployed, the flat loop's median subscriber waited about 1.7 s and its last about 5.4 s, where the tier's median was roughly 2.2× better (corrected at build: the 1.7 s is the median, not the last subscriber — the post's own table). We keep working-but-slower and delete broken-but-faster; the measurement that would justify rebuilding stays in the 2026-06-06 blog post.
- **That blog post documents a capability that stops existing.** It is still a draft, so the row that publishes it (`tasks/backlog.md` § *Website, Blog, etc.*) gains one requirement: a postscript saying the tier was removed and the measurements stand. The body is not edited ([[blog-posts-frozen]]), and a reader following it finds no `directThreshold`. This is the real cost of removal, named here rather than discovered later.
- **Rebuilding is not free, but nothing is lost.** The design is in the blog, the three defects are in `tasks/backlog.md`'s flat-loop row, and the code is in git. What is deferred is work nobody has done. The row also gains what the facade's relay teaches: a rebuilt tier's entry is not a member every `LumenizeWorker` inherits, refuses a chain a client started, and never takes `branch` from its caller.

## What changes in the backlog

- **The fence-safe-primitive row CLOSES.** It asks for *"a reusable direct-delivery broadcast any `lmz-api` node (raw or `LumenizeDO`) can compose — no tier hop … `onErrorOnly` drop-on-failed-delivery built in"*, and `lmz.broadcast` satisfies every clause once the tier is gone. Its one named consumer, the Profile, is adopted here, so the row has no remaining work.
- **The flat-loop row INVERTS.** It currently reads *"the model is the recursive tier; this is the dead interim"* and lists what lifting the pin requires. It becomes: build the tier when a real workload needs it, and its three defect bullets become the specification for doing it right. The pin it describes will not exist. It absorbs the Option A fix and test matrix from `on-hold/broadcast-origin-transparency.md`, and that file is deleted, since the branch it fixes is gone.
- **The publish row for the 2026-06-06 post** gains its postscript requirement.
- **A new release-flag row** in § *Lumenize Mesh* records the three breaking changes in § *Relationships*.

## Non-goals

- **Rebuilding the tier**, now triggered by a real workload past ~100 subscribers on one resource or query, or a lag complaint.
- **Retiring `svc`, or moving `sql` or `alarms`** — neither has a consumer asking.
- **The data-plane's bridge collapse**, which is the sibling's work (its D22) and the reason this detour exists.
- **Flipping the chain default, and deleting the `aud` fence** — [nebula-scope-moves-to-subdomain.md](nebula-scope-moves-to-subdomain.md)'s, landing after this.
- **Moving Star's and Galaxy's binding reads to `callChain[0]`.** Change 4 makes their `at(-1)` Gateway-stamped; where that derivation lives is ④'s door.
- **The Profile composing the Resources plane.** `ResourceDataPlane` lives in `apps/nebula/src` and `packages/nebula-auth` cannot import from the app, so that host has a packaging blocker this task does not touch. Phase 5 records it in [on-hold/nebula-profile-storage.md](on-hold/nebula-profile-storage.md) as a precondition, because nothing records it today.

Not executable at write time, and named so nobody assumes otherwise: every behavioural criterion, every mutation, and the `/live` runs.

1. **The Gateway stamps the whole chain a client's call carries.** First, because it stands alone, it is the security fix, and later phases' proofs assume it.
   - **The change:** `#handleClientCall` builds `callChain: [verifiedOrigin]`, and the client's own `callContext.callChain` is no longer read. The comment allowing client hops goes with it; `originAuth`, `originRequest` and `state` are untouched.
   - **Success criteria:** the Phase 1 row reaches 0; `npm run test:code` and `npm run type-check` are green; the sweep matches the baseline.
   - **The proof is driven, not constructed** (`live.md`: a Gateway rebuilding a chain is not a pure function). A new container-free `/live` scenario runs one real login on several tabs, as `reaper-victim-is-the-address` does. The hostile tab is a real `NebulaClient` whose injected `WebSocket` rewrites its outgoing CALL frames to append a hop — the one thing an attacker controls — and that rewriting lives in the scenario file, never in a shared helper. Every limb runs, and the verdict comes at the end:
     - **Profile:** subscribe with an appended hop naming a binding absent from `env`. The next update still reaches the hostile tab, and an honest tab whose subscriber row sorts after it.
     - **Star:** subscribe with the same hop. A later commit from another tab still resolves ok, and the honest subscriber still receives the push.
     - **Tab guard:** push into a co-member's tab with an appended last hop naming a DO. That tab's handler never runs, and the refusal names a direct client-to-client call.
     - **Positive control:** with the rewrite switched off, each delivery above happens, so every path the limbs assert on is reachable.
   - **Mutation:** restore `...clientCallChain.slice(1)` and every limb reds. The tab-guard limb matches the refusal MESSAGE, because a Gateway refusal and a peer refusal are indistinguishable as booleans.
   - **A mechanism test in `packages/mesh`**, which CI runs: a client frame carrying extra hops reaches its callee with a one-element chain. Its header says it is the mechanism and the scenario is the proof, and the same mutation reds it.

2. **The tier branch is gone, and every fan-out is a direct loop from the origin at any N.** Before the move, because it shrinks the function Phase 3 moves.
