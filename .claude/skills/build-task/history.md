# Build Task — what real builds taught

The tuning record for `/build-task`: one data point per build whose verifier panel or retro said something about the skill. Newest first, appended to and never rewritten. `SKILL.md` does not load this file; read it when changing the skill, to see why an instruction is there and what a cut would give up. A section number inside an entry is the skill's at the time the entry was written.

**Data point — personas are real members (8 phases, 2026-11-14/15), and the panel passed none of the first seven.** Its findings in Studio's tab runner and the Galaxy's entry were one kind, a record outliving what it describes, the kind the 2026-10-05/06 entry below named, and the prompt's hunt for state with a lifetime found them again. The builder's mutation checks removed code in five of the eight phases. What the builder skipped was everything outside the files it touched: two phases each broke a `/live` scenario the build had not written, found only at the last phase's sweep, and one was committed with surface inventories red, found by the next phase's full suite run. ⇒ A phase now ends with its packages' whole suites and a sweep, and `testing.md` asks for a test that changes the other party after a record of it is made. The skill was cut down the same week (2026-11-16): its instructions became an ordered phase-end list, this history moved out of it, and the panel now reads the task file from disk.

**Data point — resource webhooks on Events (8 phases, 2026-11-03), and the worst bug was an ordering no test arranged.** Phase 7's client keeps its copies through queues that run at once, one per uri-specification, and its 443 tests passed. Its verifier, told to read code only, copied the commit to the scratchpad with `git archive`, wrote a script that resolved a wider catch-up while a narrower uri-specification was subscribing, and ran it with node. The narrower then dropped the copy the wider had just brought. It ran no suite and edited nothing in the tree, and the same method showed that one of the phase's tests still passed when the queue's runs overlapped. ⇒ The verifier prompt now asks for one such hand-built ordering in code that runs work concurrently.

**Data point — mesh calls to and from clients (10 phases, 2026-10-05/06), and the panels found the DESIGN's hole, not the build's.** Two phases' panels returned four majors between them, and every one was a record with a lifetime failing at its boundary: a client's loss recorded on a grace period that then ended, a dead socket still listed past it, a close arriving after it, and the Gateway's other 4401 starting none. The first sat inside a decision the task file had pinned through three review passes. Its rejected alternative argued the Gateway's own record "would be lost if it were evicted", while an evicted Gateway already gives the safe answer: a false premise under a conclusion nobody questioned (`calibration.md` §7). ⇒ The verifier prompt now hunts state with a lifetime by name. The same build ran unattended through several compactions, and the eleven items it left for the human had to be rebuilt from the transcript afterwards; the per-phase § *Build notes* exist because of it.

**Data point — the guidance file tree (7 phases, two panels, 2026-09-05/06), and the second pass located a class the first cannot: THE OTHER VENUE.** The first panel found three majors the builder's own discipline had missed in the ordinary way — a live limb that could not fail on its own (its `docker ps` check passed with the teardown deleted, because the real classifier rarely started a box for a question), markers without the stamped discriminator `testing.md` requires, and a gate that ran after the short-circuit it was meant to precede. Every one was fixed within the hour. The second panel, on the fixed tree, found three more majors and none was in the diff: a rule's `paths:` glob still loading on the constant's retired home and not on the platform file that replaced it; task-file handles in six test headers, spelled `Phase N`, which the letter-series grep the rule documented could not see; and a limb that read the dev stack's captured stdio, a capability only a local boot has, so it would have failed its own positive control on every deployed run — against a registry rule that every scenario runs unchanged in both venues. ⇒ **Two tuning lessons.** (1) A limb that reads an ENVIRONMENT capability — stdio, Docker, a mailbox — must be read against the other venue in the registry before it ships; the panel is the only reader that checks a scenario against a venue it did not run in, so its prompt now names that hunt. (2) An instrument's pattern is part of the claim it backs: "the handle grep is clean" was true of the grep and false of the tree, and a widened pattern was the whole fix. The falsified-text grep from the 08-20 entry caught nothing here because the falsified text was a glob, not a sentence — read the frontmatter of every rule the build repoints.

**Data point — two panels in one day (profile-gate + actingToken, 3 phases each, 2026-08-20), and together they locate the panel's residual value precisely: TEXT OUTSIDE THE DIFF.** Both builds ran the full in-skill discipline — every operand mutation-isolated (10 in-lane cycles + a live per-limb red between them), every instrument executed against a known hit — and every finding that survived was prose the diff never touched. The profile-gate panel found a **half-repointed JSDoc block** (line 7 of a header still citing a dead path while line 11 of the same block had been fixed — a diff-scoped sweep sees only the edited line). The actingToken panel found **ADR-016 itself still declaring "Resources is not conformant yet" and quoting the deleted coalesce compare verbatim** — the highest-traffic wrong copy available, since ADRs load in full at every `/review-task`, and the exact verbatim-quotation rot `workflow.md` § *Referring to things across files* names. ⇒ The falsified-text grep now in § 2 (pending-status language in any ADR/rule the work completes) is this data point's rule; the panels also priced the repair: every finding, majors included, was fixed pre-commit within the hour, so catching this class late is cheap — *shipping* it is what compounds.

**Data point — registry route-guards (3 phases, 2026-08-18), confirming the 2026-08-16/17 entry and adding one shape.** The builder mutation-checked every recognized test per limb (≈15 mutation cycles, two of them against live `/live` runs) and the panel still found four real things: a **missing criterion limb** — the criterion's trailing *"⚠️ Also assert…"* clause (a platform subject un-impersonable at the endpoint) was never written, because a multi-limb criterion stated as one sentence lets the tail drop silently while the headline limb passes; a **sweep limb incapable of failing** (a `not.toBe(turnstile_required)` on bodyless GET rows, where the mutated path can only ever produce a different error — `testing.md`'s vacuous-negative class, found by reading); and two **stale-symbol citations** in prose that the diff-scoped phase-end sweep structurally cannot see (a deleted function cited in a JSDoc security argument, and a README sentence contradicting two sibling lines edited in the same file). ⇒ When transcribing criteria into phase work, split each *"Also assert"* tail into its own checklist line — the tail is where this build's only conformance failure lived.

**Data point — passage/dominion spine (4 phases, 2026-08-16/17 retro), and it argues the panel is worth MORE than the 2026-06-15 entry suggests.** Implementation was again near-transcription: the task file's per-site conversion tables held, and the single deliberate verdict change had been pinned in advance. The panel's value was **not** rubber-stamping and **not** correctness of the shipped behaviour — every phase's code was right. It was **coverage**: four verifiers found **three assertions that could not fail**, all authored in the same build by a builder who had mutation-checked everything he recognised as a test — a documented conformance grep that returned empty on any tree, the mint's one verdict case with no other backstop, and both verdicts having no direct unit test at all. It also found **three false supporting premises under correct conclusions** (`calibration.md` §7), the sharpest being a security rationale that was checkable and wrong.

⇒ **Two tuning lessons.** (1) The bar that pays is *"what did this phase add that cannot fail?"*, not *"is the code right?"* — hence the explicit hunt now in the verifier prompt. (2) The classes that escape a builder's own mutation discipline are the ones with **no ritual attached**: an instrument is not obviously a test, and a multi-limb `/live` scenario reddens as a whole while any single limb rots. Both now have rules (`testing.md`, `live.md`) *and* a prompt clause, deliberately — the rules are path-scoped and a verifier may not load them.

**Data point — §5.3.7 Nebula-frontend (v1–v5, the largest single-batch build, 2026-06-15 retro).** The build validated the skill's core premise: after deep review, implementation was near-transcription — **~0.46 mid-build design decisions per phase, zero behavior churn, one structural reversal** (a separate-package → subpath repackaging caught during scaffolding). The verifier fan-out earned its keep beyond rubber-stamping at least once: a P9 verify panel surfaced an unguarded HTTP-403 operand that became a permanent rule (`testing.md` "mutation-check each operand of a compound condition"). Friction was NOT in task-writing — it was empirical test-infra discovery in the thin-spec **v4** phase (WS-disconnect tooling took 3 tries). See the exploratory-phase handling below.
