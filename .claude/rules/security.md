# Security Invariants

Lumenize-specific, not generic OWASP. Security is on by default — you have to jump through hoops to disable it, and those hoops must never be reachable in production. These are the *conformance* checks; deeper design review (sandbox-escape analysis, permission-model completeness) is a reviewer-panel concern — see `tasks/on-hold/task-review-panel.md`.

- **Secrets never committed** — see [critical.md](critical.md). No tokens/keys in source, `wrangler.jsonc`, or any committed file.
- **Never log secrets — at ANY level.** `@lumenize/debug` gates all output on the `DEBUG` var, so prod is normally silent — but we run broad `DEBUG` in pre-alpha for tracing, so *no log statement may emit a secret* regardless of level. Never log: magic-link tokens/URLs, raw/minted JWTs or access tokens, refresh tokens, cookies/`Authorization` headers, signing keys, or `TURNSTILE_SECRET_KEY`. Log **identifiers** (`sub`, `email`, `instanceName`, `method`) and **`url.pathname`** — **never `request.url`** (a full URL can carry a query-string secret, e.g. `/auth/{scope}/magic-link?token=…`). Emails/subs are identifiers, not secrets, and may be logged. (Audited clean 2026-06-26: the only `request.url` logs were two WS-reject lines in `entrypoint.ts`, tightened to pathname.)
- **Test-mode flags only in vitest `miniflare.bindings`**, never in `wrangler.jsonc` `vars` (see [packaging.md](packaging.md)). A test-mode flag that bypasses auth or admin checks must be unreachable in a deployed Worker. Never weaken `requireAdmin` / admin-bypass paths outside test bindings.
  - ⚠️ **The two auth packages are NOT equally forgiving of a leak, and `nebula-auth` is the unforgiving one.** `@lumenize/auth` needs **two** factors — the `LUMENIZE_AUTH_TEST_MODE` binding **and** a per-request `?_test=true` — so a leaked binding there only affects requests that deliberately opted in. **`nebula-auth` gates on the BINDING ALONE** and structurally cannot do otherwise: the decision is made inside the registry DO, reached by RPC with no request URL to sniff. ⇒ **a leaked `NEBULA_AUTH_TEST_MODE` on a deployed Worker hands magic links to ORDINARY traffic.** There is no second factor to save you, so the binding's absence from every deployable surface *is* the control: **`scripts/audit-test-mode.sh` is what holds that line** — it must stay passing, and the flag must appear in zero `wrangler.jsonc` / `.dev.vars` / CI config / npm scripts. Don't "helpfully" add a `?_test=true` check to `nebula-auth` to match the sibling either; a URL isn't available at the decision point, so it would be decorative. Closing the asymmetry for real means threading an explicit flag through the RPC — still open, tracked in `tasks/backlog.md`. ⚠️ It is **no longer coupled to a de-fork**: `nebula-auth` dropped `@lumenize/auth` from its manifest on 2026-07-31, so the two packages are already independent and this fix can land on its own schedule.
- **JWT verification on every protected path** — verify the token *and* enforce scope (`aud`/`activeScope`) before acting. Auth uses a two-scope model: `authScope` (cookie path) + `activeScope` (JWT `aud`). Don't trust an unverified claim.
- **Delegation (`act` chains) — two invariants.** (1) *Read-side*: authz decisions read the **authority principal** — the top-level `sub` + its `access` claim — and **never** the `act` chain; `act` (`act.sub`, `act.profileId`, nested) is traceability/display only. Enforcement sites: `dag-tree.ts` `requirePermission`, `nebula-do.ts` `enforceScopeReach`.
  - **The reader list, so completeness is checkable rather than asserted** (instrument: `grep -rn '\.act\b' packages/nebula-auth/src apps/nebula/src`). ⚠️ **Stated STRUCTURALLY, not by count** — every reader falls in exactly one of three buckets, so a new one inherits a classification instead of falsifying a tally:
    - **CONTENTS readers — traceability only, never authz.** `apps/nebula/src/resources.ts` (`#buildChangedBy` + the `projectActClaim` it delegates to) → `Snapshots.changedBy`, and `packages/nebula-auth/src/nebula-auth-registry.ts` `executeScopeDeletion` → the ADR-016 acting-principal record. ⚠️ **Every ADR-016 site joins this bucket by construction** — recording the acting principal *means* reading `act` — so re-run the instrument when one lands, and **keep the buckets a superset of what it returns**: a hit that fits no bucket is the signal to re-derive, not to widen a bucket to swallow it.
    - **MINT-SIDE or CLIENT PRE-FLIGHT presence gates — outside the read-side rule, and therefore NOT exceptions to it.** `worker-token.ts`'s root-identity gate (mint-side: it decides what to *issue*, not what an existing token may *do*), and `apps/nebula/src/impersonation.ts` `assertCanImpersonate` — a client-side pre-flight **mirror** of that same gate, which exists to turn a structurally impossible call into an accurate message rather than a 403 that reads as a problem with the subject. The server gate remains the enforcement; removing the client one changes no authorization outcome.
    - **READ-SIDE, where `act`-presence changes an authz outcome — EXACTLY ONE, and it is licensed.** `profile.ts` `#requireOwnerOrAdmin` branch (1), below.
    - ⚠️ The instrument also returns **comments and CONSTRUCTION sites**, which are in none of the buckets because they read nothing: `access-claims.ts` explains why `profileId` is spread conditionally at the point the `act` claim is *built*, and several files carry `!claims.act` in prose. Judge a hit by whether it *reads* `act` to decide or record something — a mention is not a reader.
  - ⚠️ **Rule (1) holds with exactly ONE named, licensed exception:** `profile.ts` branch (1)'s `&& !claims.act`, per [ADR-012](../../docs/adr/012-global-profile-visibility.md). It is the one place where the *presence* of `act` changes an authz outcome. What licenses it is **global**: a profile sits outside the scope tree and scope authority over one can be *manufactured*, so the owner branch must additionally require the token carries no `act` chain. It tests presence only — never *who* the actor is; reading the chain's identity (`act.sub === sub`, `act.profileId === profileId`) stays forbidden, and that presence/identity distinction is why rule (1) still holds.
  - **(2) *Mint-side*:** a narrower-token mint (`nebula-auth` `/mint-narrower-token`) rests on **four** invariants, all of them load-bearing — (a) `activeScope` is within the **caller's** verified reach; (b) `activeScope` is *also* within `buildAuthScopePattern(the subject's scope)`, so the token mirrors that person rather than merely something inside the caller's authority; (c) the minted `admin` is `caller.admin && subject.isAdmin` — an **intersection**, never either side's copy, and never the issuing instance's pattern; (d) the **identity bound** — the subject must be a *different* `sub`, and the caller must hold `hasAdminOverScope` over the **subject's scope** (ADR-015 §2, "upward is nil"). (a)+(d) together make escalation-safety a *consequence*: (d) has already placed the subject's whole scope inside the caller's authority, so the mirror (b)+(c) produces can only be narrower. ⚠️ (c) is why "never copy the subject's `isAdmin`" is stated as an intersection and not as a prohibition — a bare copy can exceed the caller; the conjunction cannot. (The absence of this rule was a real escalation; see `tasks/archive/rfc-act-chains.md`.)
- **Refresh tokens — no per-refresh rotation, no slide (decisions 2026-06-29 / 2026-07-11).** Rotation was dropped: a refresh does not re-issue or revoke the refresh token. The **slide** was also dropped (`tasks/archive/nebula-auth-surrogate-sub.md`): the refresh token gets a **fixed 30-day TTL at login** and refresh is a **Workers-KV read** (`worker-token.ts` `handleRefreshToken`) with **zero writes** on the hit path. ⚠️ **It is not yet registry-free**, despite how this sentence used to read: a KV **miss** falls back to `getRefreshRecord`, which reads the singleton's `RefreshTokenIndex` and re-puts KV. That fallback is load-bearing today only because login is a bodiless 302 carrying no access token, so the first refresh lands inside KV's propagation window. Do not reason about the refresh path as though the registry is never on it — that error has already been made once, in a task file, in a clause the author had contradicted three rows earlier; a 30-day re-login (a fresh magic link) is the accepted UX cost. Rationale for no-rotation: the cookie is `HttpOnly; Secure; SameSite=Strict`, Path-scoped (`/auth/{authScope}`), host-only — not JS-readable, not cross-site — so the theft surface rotation defends is already closed; and the implementation never had reuse-detection/family-revoke, so rotation only added fragility (overlapping refreshes racing a single-use token → spurious logout) with no detection benefit. **Don't re-introduce per-refresh rotation OR the slide.** If breach *detection* is wanted later, do it properly: rotation **with a grace window** **plus family-revoke on post-grace reuse** — never the no-grace form.
  - **⚠️ Revocation is now KV-eventually-consistent (a genuine, accepted softening vs the prior strongly-consistent DO revocation).** The refresh record lives in Workers KV; **logout still revokes** it (the registry deletes the KV record + its `RefreshTokenIndex` entry, KV-delete-first so an interruption never strands a live-but-unindexed token), but because KV is eventually consistent a revoked/demoted token can keep working for **up to the KV-propagation window (~edge `cacheTtl`, up to ~60s) PLUS the full access-TTL (`ACCESS_TOKEN_TTL=900s`), and repeatably within that window** — NOT "one more request." The mitigation is the short access-TTL (a demoted user's already-minted 15-min access token is the real exposure bound; the next refresh reflects the change once KV propagates). WebAuthN/MFA (pre-beta) restores defence-in-depth. **Keep intact:** JWT verification + scope enforcement on every protected path; logout revokes the KV record; the fixed 30-day refresh TTL.
- **A DERIVED session must never revoke on the ORIGINATING session's credential path.** When one session mints a second (impersonation today; the consent-gated support session next), the derived one holds **no refresh cookie of its own** — so its "log out" is teardown only, and any code path that would `POST /auth/{authScope}/logout` on its behalf spends the **originator's** 30-day refresh token. ⚠️ **Pinning the derived session's `authScope` to its own `activeScope` LOOKS like the guard and is not.** It diverges from the parent's cookie path only while the two scopes *differ* — RFC-6265 will not send an `/auth/{universe}` cookie to `/auth/{universe}.app.tenant/logout` (the first uncovered character is `.`, not `/`) — but an admin who logged in **at** the scope they act into gets an exact path match, and that is the ordinary support shape, not an edge case. So the explicit branch is the control; the pin is a coincidence. ⚠️ **The harm is invisible to the obvious assertions** — the originator's socket stays open (the Gateway verifies a stateless JWT) and it keeps minting off an unexpired access token — so a test must probe the **cookie** (`POST /auth/{authScope}/refresh-token` → 200 intact / 401 revoked), and must do it in the **same-scope** shape or it cannot fail. Live: `NebulaClient.logout()`'s `#mintedFrom` branch; covered by `impersonate-lifetime.test.ts` and `harness/scenarios/impersonation-lifecycle.ts`.
- **Permission checks before resource mutation** — resource operations must pass a DAG permission check. When refactoring a permission path, enumerate every throw case so a broadened catch doesn't silently turn a malformed-request error into a permission failure (see the typed-errors note in [durable-objects.md](durable-objects.md)).
- **Parameterized SQL only** — use `this.svc.sql` template binding or `ctx.storage.sql` parameters; never string-concatenate user input into SQL (see [durable-objects.md](durable-objects.md) § Storage).
- **Trust-boundary crossings** — when a design crosses a trust boundary (client → Gateway → DO, or DWL sandbox → host), name it and confirm the receiving side re-validates rather than trusting the sender.
