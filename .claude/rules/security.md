# Nebula Security Invariants

**Scoped to Nebula — the Registry (`nebula-auth`) and the platform (`apps/nebula`) — and it is the conformance half of one model.** [`docs/vision/auth.md`](../../docs/vision/auth.md) is that model: it describes the target in present tense and is `status: accepted`, so where the two disagree, **this file is what is wrong** unless it is deliberately describing today's code. Read it for *why* a rule exists; read this for what is checkable. `/review-task`'s security lens loads both.

Security is on by default — you have to jump through hoops to disable it, and those hoops MUST NOT be reachable in production. These are the *conformance* checks; deeper design review (sandbox-escape analysis, permission-model completeness) is a reviewer-panel concern — see the `/review-task` skill.

⚠️ **Nothing here binds the MIT packages.** `@lumenize/auth` and `@lumenize/crypto` have their own auth model and at least one **opposite** policy — the base package still rotates refresh tokens, which § *Refresh tokens* below forbids for Nebula. ⚠️ Whether that is a deliberate difference or a gap to close is **open**, tracked in [`tasks/backlog.md`](../../tasks/backlog.md) § Nebula Auth; what is settled is that this file is not the thing that decides it. Their local invariants live in JSDoc at the site; `@lumenize/auth`'s two-factor test-mode gate is on `LumenizeAuth`'s `#isTestMode`. Universal guardrails — secrets, SQL, storage — are in [critical.md](critical.md) and [durable-objects.md](durable-objects.md), which load regardless of package.

- **Test-mode flags MUST live in vitest `miniflare.bindings`**, and MUST NOT appear in `wrangler.jsonc` `vars` (see [packaging.md](packaging.md)). A test-mode flag that bypasses auth or admin checks MUST be unreachable in a deployed Worker. `requireDominionHere` / admin-bypass paths MUST NOT be weakened outside test bindings.
  - ⚠️ **The two auth packages are NOT equally forgiving of a leak, and `nebula-auth` is the unforgiving one.** `@lumenize/auth` needs **two** factors — the `LUMENIZE_AUTH_TEST_MODE` binding **and** a per-request `?_test=true` — so a leaked binding there only affects requests that deliberately opted in. **`nebula-auth` gates on the BINDING ALONE** and structurally cannot do otherwise: the decision is made inside the registry DO, reached by RPC with no request URL to sniff. ⇒ **a leaked `NEBULA_AUTH_TEST_MODE` on a deployed Worker hands magic links to ORDINARY traffic.** There is no second factor to save you, so the binding's absence from every deployable surface *is* the control: **`scripts/audit-test-mode.sh` is what holds that line** — it MUST stay passing, and the flag MUST appear in zero `wrangler.jsonc` / `.dev.vars` / CI config / npm scripts. You MUST NOT "helpfully" add a `?_test=true` check to `nebula-auth` to match the sibling either; a URL isn't available at the decision point, so it would be decorative. Closing the asymmetry for real means threading an explicit flag through the RPC — still open, tracked in `tasks/backlog.md`, which carries the current sequencing.
- **Every protected path MUST verify the JWT** — verify the token *and* enforce scope (`aud`/`activeScope`) before acting. Auth uses a two-scope model: `authScope` (cookie path) + `activeScope` (JWT `aud`). An unverified claim MUST NOT be trusted.
- **Delegation (`act` chains) — two invariants.** (1) *Read-side*: authz decisions MUST read the **subject** — the top-level `sub` + its `access` claim — and MUST NOT read the `act` chain; `act` (`act.sub`, `act.profileId`, nested) is traceability/display only. ⚠️ **The enforcement sites are stated as a PROPERTY, never as a list** (a tally here was falsified twice without failing anything): rule (1) is enforced at **every site that decides an authz outcome from the subject's claims** (instrument: `grep -rn 'hasDominionOver(\|hasPassageInto(' apps/nebula/src packages/nebula-auth/src` for the scope-verdict sites, plus the two non-scope deciders `requirePermission` (DAG grant) and `profile.ts`'s `#requireOwnerOrAdmin` (ownership)). A new guard **inherits** the obligation by deciding from `access`; it cannot extend or fall off a list.
  - **The reader list, so completeness is checkable rather than asserted** (instrument: `grep -rn '\.act\b' packages/nebula-auth/src apps/nebula/src`). ⚠️ **Stated STRUCTURALLY, not by count** — every reader falls in exactly one of three buckets, so a new one inherits a classification instead of falsifying a tally:
    - **CONTENTS readers — traceability only, never authz.** `apps/nebula/src/resources.ts` (`#buildActingToken` delegating to the shared `projectActingToken`, plus the record-walking helpers `identityKey`/`toWireActingToken` — they read RECORDS (the stored one, and the one freshly projected from the current call's claims) to decide coalescing/display, never authorization) → `Snapshots.actingToken`, and `packages/nebula-auth/src/nebula-auth-registry.ts` `executeScopeDeletion` → the ADR-016 acting-principal record. ⚠️ **Every ADR-016 site joins this bucket by construction** — recording the acting principal *means* reading `act` — so you MUST re-run the instrument when one lands, and **the buckets MUST stay a superset of what it returns**: a hit that fits no bucket is the signal to re-derive, not to widen a bucket to swallow it.
    - **MINT-SIDE or CLIENT PRE-FLIGHT presence gates — outside the read-side rule, and therefore NOT exceptions to it.** `worker-token.ts`'s root-identity gate (mint-side: it decides what to *issue*, not what an existing token may *do*), and `apps/nebula/src/impersonation.ts` `assertCanImpersonate` — a client-side pre-flight **mirror** of that same gate, which exists to turn a structurally impossible call into an accurate message rather than a 403 that reads as a problem with the subject. The server gate remains the enforcement; removing the client one changes no authorization outcome.
    - **READ-SIDE, where `act`-presence changes an authz outcome — legitimate only under the test below.** Judge each hit against it; the sites are not listed here, because a list rots and the instrument already finds them.
    - ⚠️ The instrument also returns **comments and CONSTRUCTION sites**, which are in none of the buckets because they read nothing: `access-claims.ts` explains why `profileId` is spread conditionally at the point the `act` claim is *built*, and several files carry `!claims.act` in prose. Judge a hit by whether it *reads* `act` to decide or record something — a mention is not a reader.
  - ⚠️ **Rule (1) admits `act`-presence checks under exactly ONE test, and an exception MUST satisfy it:** *an `act`-presence check may change an authz outcome only where impersonation would otherwise grant the actor something they could not already do themselves.* Everywhere else it buys nothing — an admin already holds total downward dominion (ADR-015 clause 1), so impersonating someone beneath them transfers power they already have, and blocking it is ceremony. The worked case is `profile.ts` `#requireOwnerOrAdmin` branch (1)'s `&& !claims.act` ([ADR-012](../../docs/adr/012-global-profile-visibility.md)): the owner check is `claims.profileId === profileId`, impersonation deliberately puts the SUBJECT's `profileId` on the token, and ownership of a global object sits outside the actor's scope tree — so this is the one place the block grants nothing away and withholds something real.
    - ⚠️ **The test is default-DENY: a new `act`-presence check is wrong until someone argues it past this.** The sites are deliberately NOT enumerated — a list rots, and the instrument above rediscovers them from the code, which cannot.
    - ⚠️ **Presence only, never identity.** The chain's identity (`act.sub === sub`, `act.profileId === profileId`) MUST NOT be read. That distinction is why rule (1) still holds even where a presence check is licensed.
    - ⚠️ **"What licenses it is *global*" was the old wording and it is WRONG — do not restore it.** Globalness is the justification for the *acceptance predicate* on the neighbouring **admin** branch (it is what stops manufactured dominion); it was borrowed onto the owner branch after the fact and would mis-license a future case. Corrected 2026-08-05.
  - **(2) *Mint-side*:** a narrower-token mint (`nebula-auth` `/mint-narrower-token`) MUST authorize on **one predicate and an identity check** — the caller MUST hold `hasDominionOver` over the **subject's scope** (ADR-015, "upward is nil"), and the subject MUST be a *different* `sub`. The minted token then carries the **subject's** `sub`, `authScope` and `scopeAdmin`, with the caller in `act`. ⚠️ **`activeScope` MUST NOT be an authorization input here.** The requested `aud` MAY be validated — reject one outside the subject's scope, so an unverifiable token fails fast — but a security decision on it is a decision on a value `authScope` already confines. ⚠️ **Narrowed 2026-08-11 from four invariants to this, and the deleted ones MUST NOT be restored as "hardening".** They bounded `activeScope` against the caller and against the subject; both are now *consequences*, because the minted `authScope` **is** the subject's scope and `verify.ts` already requires `aud` within `authScope` — so `aud ⊆ subject ⊆ caller` is a theorem, not a check. Likewise the minted bit was once the intersection `caller.scopeAdmin && subject.scopeAdmin`; the caller's bit is always set once dominion over the subject holds, making the left operand dead code inside a security predicate — invisible to mutation testing. The escalation all of them were written against (a narrower caller impersonating a broader subject — `tasks/archive/rfc-act-chains.md`) is unreachable under the one predicate that remains. ⚠️ **The live substitution risk is the ARGUMENT, not the predicate**: any scope reachable at the call site other than the subject's, passed where `hasDominionOver(access, subject.authScope)` belongs. That is what a named `canMintFor` wrapper exists to foreclose, and it holds however the route is addressed — **the route MAY be scope-less**. Two shapes, and the second is the quieter: where the route carries an instance, `hasDominionOver(access, instanceName)` is the wrong argument and refuses the wrong callers; where it does not, the nearest wrong argument is the **caller's own** `access.authScope`, which makes the predicate reflexively true and therefore silent — a check that can never refuse, which mutation testing cannot red.
- **Refresh tokens — no per-refresh rotation, no slide (decisions 2026-06-29 / 2026-07-11).** Rotation was dropped: a refresh does not re-issue or revoke the refresh token. The **slide** was also dropped (`tasks/archive/nebula-auth-surrogate-sub.md`): the refresh token gets a **fixed 30-day TTL at login** and refresh is a **Workers-KV read** (`worker-token.ts` `handleRefreshToken`) with **zero writes** on the hit path. ⚠️ **It is not yet registry-free**, despite how this sentence used to read: a KV **miss** falls back to `getRefreshRecord`, which reads the singleton's `RefreshTokenIndex` and re-puts KV. That fallback is load-bearing today only because login is a bodiless 302 carrying no access token, so the first refresh lands inside KV's propagation window. You MUST NOT reason about the refresh path as though the registry is never on it — that error has already been made once, in a task file, in a clause the author had contradicted three rows earlier; a 30-day re-login (a fresh magic link) is the accepted UX cost. Rationale for no-rotation: the cookie is `HttpOnly; Secure; SameSite=Strict`, Path-scoped (`/auth/{authScope}`), host-only — not JS-readable, not cross-site — so the theft surface rotation defends is already closed; and the implementation never had reuse-detection/family-revoke, so rotation only added fragility (overlapping refreshes racing a single-use token → spurious logout) with no detection benefit. **Per-refresh rotation and the slide MUST NOT be re-introduced.** If breach *detection* is wanted later, do it properly: rotation **with a grace window** **plus family-revoke on post-grace reuse** — the no-grace form MUST NOT be used.
  - **⚠️ Revocation is now KV-eventually-consistent (a genuine, accepted softening vs the prior strongly-consistent DO revocation).** The refresh record lives in Workers KV; **logout still revokes** it (the registry deletes the KV record + its `RefreshTokenIndex` entry, KV-delete-first so an interruption never strands a live-but-unindexed token), but because KV is eventually consistent a revoked/demoted token can keep working for **up to the KV-propagation window (~edge `cacheTtl`, up to ~60s) PLUS the full access-TTL (`ACCESS_TOKEN_TTL=900s`), and repeatably within that window** — NOT "one more request." The mitigation is the short access-TTL (a demoted user's already-minted 15-min access token is the real exposure bound; the next refresh reflects the change once KV propagates). WebAuthN/MFA (pre-beta) restores defence-in-depth. **These MUST stay intact:** JWT verification + scope enforcement on every protected path; logout revokes the KV record; the fixed 30-day refresh TTL.
- **A DERIVED session MUST NOT revoke on the ORIGINATING session's credential path.** When one session mints a second (impersonation today; the consent-gated support session next), the derived one holds **no refresh cookie of its own** — so its "log out" is teardown only, and any code path that would `POST /auth/{authScope}/logout` on its behalf spends the **originator's** 30-day refresh token. ⚠️ **Pinning the derived session's `authScope` to its own `activeScope` LOOKS like the guard and is not.** It diverges from the parent's cookie path only while the two scopes *differ* — RFC-6265 will not send an `/auth/{universe}` cookie to `/auth/{universe}.app.tenant/logout` (the first uncovered character is `.`, not `/`) — but an admin who logged in **at** the scope they act into gets an exact path match, and that is the ordinary support shape, not an edge case. So the explicit branch is the control; the pin is a coincidence. ⚠️ **The harm is invisible to the obvious assertions** — the originator's socket stays open (the Gateway verifies a stateless JWT) and it keeps minting off an unexpired access token — so a test MUST probe the **cookie** (`POST /auth/{authScope}/refresh-token` → 200 intact / 401 revoked), and MUST do it in the **same-scope** shape or it cannot fail. Live: `NebulaClient.logout()`'s `#mintedFrom` branch; covered by `impersonate-lifetime.test.ts` and `harness/scenarios/impersonation-lifecycle.ts`.
- **Permission checks before resource mutation** — resource operations MUST pass a DAG permission check. When refactoring a permission path, you MUST enumerate every throw case so a broadened catch doesn't silently turn a malformed-request error into a permission failure (see the typed-errors note in [durable-objects.md](durable-objects.md)).
- **Trust-boundary crossings** — when a design crosses a trust boundary (client → Gateway → DO, or DWL sandbox → host), you MUST name it and confirm the receiving side re-validates rather than trusting the sender.
