# Nebula Security Invariants

**Scoped to Nebula — the Registry (`nebula-auth`) and the platform (`apps/nebula`) — and it is the conformance half of one model.** [`docs/vision/auth.md`](../../docs/vision/auth.md) is that model: it describes the target in present tense and is `status: accepted`, so where the two disagree, **this file is what is wrong** unless it is deliberately describing today's code. Read it for *why* a rule exists; read this for what is checkable. `/review-task`'s security lens loads both.

Security is on by default — you have to jump through hoops to disable it, and those hoops MUST NOT be reachable in production. These are the *conformance* checks; deeper design review (sandbox-escape analysis, permission-model completeness) is a reviewer-panel concern — see the `/review-task` skill.

⚠️ **Nothing here binds the MIT packages.** `@lumenize/auth` and `@lumenize/crypto` have their own auth model and at least one **opposite** policy — the base package still rotates refresh tokens, which § *Refresh tokens* below forbids for Nebula. ⚠️ Whether that is a deliberate difference or a gap to close is **open**, tracked in [`tasks/backlog.md`](../../tasks/backlog.md) § Nebula Auth; what is settled is that this file is not the thing that decides it. Their local invariants live in JSDoc at the site; `@lumenize/auth`'s two-factor test-mode gate is on `LumenizeAuth`'s `#isTestMode`. Universal guardrails — secrets, SQL, storage — are in [critical.md](critical.md) and [durable-objects.md](durable-objects.md), which load regardless of package.

- **Test-mode flags MUST live in vitest `miniflare.bindings`**, and MUST NOT appear in `wrangler.jsonc` `vars` (see [packaging.md](packaging.md)). A test-mode flag that bypasses auth or admin checks MUST be unreachable in a deployed Worker. No binding, flag or env var MAY make `requireDominionHere`, `requireChatWrite` or the DAG's `requirePermission` pass for a caller the design refuses.
  - **A guard's floor changing by design decision is a different thing, and this file records it.** The Galaxy's source entries — `readSource`, `writeSource`, `buildNow`, `applyOntology` — moved from `requireDominionHere` to `requireChatWrite` on 2026-09-05. That guard is DAG `write` at the chat node, the check a Message create passes at the door, so a collaborator's direct call and their triggered turn agree. It reads the grant through `OrgTree.requirePermission` and inherits that check's obligations: the host-confined dominion bypass, and the `PermissionDeniedError` message a boundary refusal is told apart by. Configuration (`setGalaxyConfig`) stays behind dominion, and so does the Apply's wipe bit, decided in the body at dominion over the `.dev` Star.
  - **The two auth packages are NOT equally forgiving of a leak, and `nebula-auth` is the unforgiving one.** `@lumenize/auth` needs **two** factors — the `LUMENIZE_AUTH_TEST_MODE` binding **and** a per-request `?_test=true` (`LumenizeAuth`'s `#isTestMode`) — so a leaked binding there only affects requests that deliberately opted in. **`nebula-auth` gates on the BINDING ALONE.** ⇒ **a leaked `NEBULA_AUTH_TEST_MODE` on a deployed Worker hands magic links to ORDINARY traffic.** There is no second factor to save you, so the binding's absence from every deployable surface *is* the control: **`scripts/audit-test-mode.sh` is what holds that line** — it MUST stay passing, and the flag MUST appear in zero `wrangler.jsonc` / `.dev.vars` / CI config / npm scripts.
    - ⚠️ **"nebula-auth structurally CANNOT take a second factor" was the old wording and it is FALSE — do not restore it.** It claimed no request URL reaches the decision point. The link-returning site is `#deliverMagicLink`, reached three ways: from `claimUniverse` and `claimStar`, whose routes are `forwardRaw`, so the DO receives the original request and its `fetch()` already threads a URL-derived value — `origin` — into those very methods; and from the Worker's `email-magic-link` handler by RPC, where the Worker holds the URL and could pass a flag. Neither is a structural barrier. *(The facade's invite-send skip is a different shape: a mesh call with no request URL anywhere, so a per-request factor is meaningless there rather than merely absent.)*
    - **A second factor is therefore a DECISION, not an impossibility — and the standing answer is "not now".** It defends against a leaked binding reaching *ordinary* traffic; it defends against nobody who knows to append the flag, which is the same bounded value the sibling buys. It would also be a second guard on a mechanism the audit script already enforces (`calibration.md` §2). ⇒ A `?_test=true` check MUST NOT be added to `nebula-auth` as hardening; re-opening it is a decision, tracked in `tasks/backlog.md` § *Immediate work backlog*.
- **Every protected path MUST verify the JWT** — verify the token *and* enforce scope before acting. Auth uses a two-scope model: `authScope`, the membership whose `__Host-refresh-token.{scope}` cookie minted the token, and `aud`, the scope its host spells. An unverified claim MUST NOT be trusted.
  - **Passage and dominion MUST read `aud`, with the admin bit from the membership — the host rule** ([ADR-015](../../docs/adr/015-passage-and-dominion.md), [ADR-022](../../docs/adr/022-every-session-lives-on-the-platform-host.md)). A universe admin's token from `tenant1.crm.acme.lumenize.dev` holds dominion over `acme.crm.tenant1` alone and passage up to `acme.crm` and `acme`, never sideways to `acme.crm.tenant2`; the same membership from `acme.lumenize.dev` holds dominion over all of them. So a page's code acts within its host's subtree, whoever's membership the token rests on, and no token holds dominion over the platform root, which is no host's scope.
  - **A call chain a node started carries no JWT, and its `activeScope` is the starting node's name** ([ADR-015](../../docs/adr/015-passage-and-dominion.md)). A node named by a scope acts as a plain member of it, with no `scopeAdmin`, and a chain started by a node named by an id, such as a Profile, has no `activeScope` and gets no passage into a scoped node. A synthetic `aud` MUST NOT be written into `originAuth` for such a chain. ⏳ Today `requirePassage` refuses every such chain.
  - **A plain membership's token MUST have `aud` equal to its `authScope`**, enforced at verification and at the mint (`buildNebulaJwtPayload`). Without it, reading `aud` would widen a plain member of `acme.crm` holding a token for a tenant's host into passage over the tenant.
- **Cookie or token, never both.** Each route MUST authenticate one way, and no route MAY answer two credentials: a credential under `/auth/` is an emailed link, a refresh cookie or a signup ticket, and an access token authenticates a mesh call. The case it rejects is `scope-summary`, which answered Home by cookie and Studio by token until Home moved to `POST /auth/home-summary`. The trade: a cookie costs a Workers KV read per request where a token verifies statelessly, and buys a revocation that does not wait out an access token.
- **Delegation (`act` chains) — two invariants.** (1) *Read-side*: authz decisions MUST read the **subject** — the top-level `sub`, its `access` claim and the token's `aud` — and MUST NOT read the `act` chain; `act` (`act.sub`, `act.profileId`, nested) is traceability/display only. ⚠️ **The enforcement sites are stated as a PROPERTY, never as a list** (a tally here was falsified twice without failing anything): rule (1) is enforced at **every site that decides an authz outcome from the subject's claims** (instrument: `grep -rn 'hasDominionOver(\|hasPassageInto(' apps/nebula/src packages/nebula-auth/src` for the scope-verdict sites, plus the two non-scope deciders `requirePermission` (DAG grant) and `profile.ts`'s `#requireOwnerOrAdmin` (ownership)). A new guard **inherits** the obligation by deciding from the subject's claims; it cannot extend or fall off a list.
  - **The reader list, so completeness is checkable rather than asserted** (instrument: `grep -rn '\.act\b' packages/nebula-auth/src apps/nebula/src`). ⚠️ **Stated STRUCTURALLY, not by count** — every reader falls in exactly one of three buckets, so a new one inherits a classification instead of falsifying a tally:
    - **CONTENTS readers — traceability only, never authz.** `apps/nebula/src/snapshots.ts` (`#buildActingToken` delegating to the shared `projectActingToken`, plus the record-walking helpers `identityKey`/`toWireActingToken` — they read RECORDS (the stored one, and the one freshly projected from the current call's claims) to decide coalescing/display, never authorization) → `Snapshots.actingToken`, and `packages/nebula-auth/src/nebula-auth-registry.ts` `executeScopeDeletion` → the ADR-016 acting-principal record. ⚠️ **Every ADR-016 site joins this bucket by construction** — recording the acting principal *means* reading `act` — so you MUST re-run the instrument when one lands, and **the buckets MUST stay a superset of what it returns**: a hit that fits no bucket is the signal to re-derive, not to widen a bucket to swallow it.
    - **MINT-SIDE or CLIENT PRE-FLIGHT presence gates — outside the read-side rule, and therefore NOT exceptions to it.** `mintImpersonationToken`'s root-identity gate in `worker-token.ts`, behind `NebulaAuthFacade.impersonate` (mint-side: it decides what to *issue*, not what an existing token may *do*), and `apps/nebula/src/impersonation.ts` `assertCanImpersonate` — a client-side pre-flight **mirror** of that same gate, which exists to turn a structurally impossible call into an accurate message rather than a refusal that reads as a problem with the subject. The server gate remains the enforcement; removing the client one changes no authorization outcome.
    - **READ-SIDE, where `act`-presence changes an authz outcome — legitimate only under the test below.** Judge each hit against it; the sites are not listed here, because a list rots and the instrument already finds them.
    - ⚠️ The instrument also returns **comments and CONSTRUCTION sites**, which are in none of the buckets because they read nothing: `worker-token.ts` states the mint's authorize line as prose above the code, twice. Judge a hit by whether it *reads* `act` to decide or record something — a mention is not a reader.
  - ⚠️ **Rule (1) admits `act`-presence checks under exactly ONE test, and an exception MUST satisfy it:** *an `act`-presence check may change an authz outcome only where impersonation would otherwise grant the actor something they could not already do themselves.* Everywhere else it buys nothing — an admin already holds total downward dominion (ADR-015 clause 1), so impersonating someone beneath them transfers power they already have, and blocking it is ceremony. No live site uses it. It was written for the retired `scope-summary`, which answered a token with **every tenancy the subject holds** — scopes the admin driving it may not reach — so refusing an `act`-bearing caller withheld something real; Home's summary now reads cookies, which no token presents. ⚠️ **The Profile's owner branch is NOT an example and was one until 2026-09-08** — it carried `&& !claims.act` against a mint that would issue a token over a membership nobody had accepted; the mint now refuses that subject, so the clause withheld nothing and cost a person their own profile under impersonation ([ADR-012](../../docs/adr/012-global-profile-visibility.md) § *Alternatives considered*). Do not reinstate it.
    - ⚠️ **The test is default-DENY: a new `act`-presence check is wrong until someone argues it past this.** The sites are deliberately NOT enumerated — a list rots, and the instrument above rediscovers them from the code, which cannot.
    - ⚠️ **Presence only, never identity.** The chain's identity (`act.sub === sub`, `act.profileId === profileId`) MUST NOT be read. That distinction is why rule (1) still holds even where a presence check is licensed.
  - **(2) *Mint-side*:** the impersonation mint (`mintImpersonationToken`, behind `NebulaAuthFacade.impersonate`) MUST authorize on **one predicate, an identity check, and the subject's ACCEPTANCE** — the caller MUST hold `hasDominionOver` over the **subject's scope** (ADR-015, "upward is nil"), the subject MUST be a *different* `sub`, and the subject's membership MUST have been accepted. The minted token then carries the **subject's** `sub`, `authScope` and `scopeAdmin`, with the caller in `act` and the caller's own `aud` — no caller names the child's scope. The predicate reads the caller's dominion from its own host, `aud`, like every verdict (the host rule), and the child's `aud` MUST be validated against the subject's scope, refusing a host outside it so an unverifiable token fails fast. Together they hold the child's `aud` to exactly the subject's scope: an admin impersonates from the subject's own page.
    - ⚠️ **Narrowed 2026-08-11 from four invariants to this, and the deleted ones MUST NOT be restored as "hardening".** They bounded `activeScope` against the caller and against the subject; both are now *consequences*, because the minted `authScope` **is** the subject's scope, the predicate reads the caller's host, and the validation holds `aud` within the subject — so `aud = subject ⊆ caller's host` is a theorem, not a check. Likewise the minted bit was once the intersection `caller.scopeAdmin && subject.scopeAdmin`; the caller's bit is always set once dominion over the subject holds, making the left operand dead code inside a security predicate — invisible to mutation testing. The escalation all of them were written against (a narrower caller impersonating a broader subject — `tasks/archive/rfc-act-chains.md`) is unreachable under the one predicate that remains.
    - ⚠️ **The ACCEPTANCE conjunct is NOT one of the four bounds narrowed away above, and MUST NOT be deleted as though it were.** Those four were theorems of `aud ⊆ authScope`, so the containment already implied them; acceptance is a fact about the subject's membership that no containment implies. It is enforced through the read rather than a branch — the registry's `getIdentityScope` answers only for an accepted membership, so an unaccepted subject arrives as `null` and the existing collapsed refusal covers them. ⚠️ **A second acceptance read MUST NOT be added at the mint**, and a caller that needs pending rows MUST ask `getIdentityScopeIncludingPending` by name rather than widen the plain one. Pinned by the acceptance test in `packages/nebula-auth/test/impersonation-mint.test.ts`, which discriminates on its FIXTURE (a caller holding dominion over the scope the membership sits in) because the refusal is deliberately collapsed.
    - ⚠️ **The live substitution risk is the ARGUMENT, not the predicate**: any scope reachable at the call site other than the subject's, passed where `hasDominionOver(callerClaims, subject.universeGalaxyStarId)` belongs. That is what a named `canMintFor` wrapper exists to foreclose. The nearest wrong argument is the **caller's own** `aud`, the host it called from: it makes the predicate reflexively true for any admin, and therefore silent — a check that can never refuse, which mutation testing cannot red.
- **Refresh tokens — no per-refresh rotation, no slide (decisions 2026-06-29 / 2026-07-11).** Rotation was dropped: a refresh does not re-issue or revoke the refresh token. The **slide** was also dropped (`tasks/archive/nebula-auth-surrogate-sub.md`): the refresh token gets a **fixed 30-day TTL at login** and refresh is a **Workers-KV read** (`worker-token.ts` `handleRefreshToken`, on the platform host) with **zero writes** on the hit path. ⚠️ **It is not registry-free**: a KV **miss** falls back once to the singleton's `RefreshTokenIndex` (`getRefreshRecord`); a hit there mints and heals KV, and a miss on both expires the cookie. The fallback is load-bearing because KV is eventually consistent across colos: the consume's Worker writes the record where the person is, and KV reads back its own writes there, but a refresh served from another colo can miss a record written moments earlier. You MUST NOT reason about the refresh path as though the registry is never on it — that error has already been made once, in a task file, in a clause the author had contradicted three rows earlier; a 30-day re-login (a fresh magic link) is the accepted UX cost.
  - Rationale for no-rotation: each membership's cookie is `__Host-refresh-token.{scope}`, `HttpOnly; Secure; SameSite=Lax; Path=/`, on the platform host alone ([ADR-022](../../docs/adr/022-every-session-lives-on-the-platform-host.md)). `HttpOnly` hides it from script, `__Host-` keeps it on one host where no sibling can plant or overwrite it, and `Lax` keeps it off a cross-site `fetch` or `POST`, since it rides only a top-level navigation from another site — so the theft surface rotation defends is already closed; and the implementation never had reuse-detection/family-revoke, so rotation only added fragility (overlapping refreshes racing a single-use token → spurious logout) with no detection benefit. **Per-refresh rotation and the slide MUST NOT be re-introduced.** If breach *detection* is wanted later, do it properly: rotation **with a grace window** **plus family-revoke on post-grace reuse** — the no-grace form MUST NOT be used.
  - Every page on the site refreshes off the same few cookies, a page on any `lumenize.dev` host by a credentialed `fetch` to the platform host, so rotation's race between overlapping refreshes is worse here than it was under one cookie per path.
  - **⚠️ Revocation is now KV-eventually-consistent (a genuine, accepted softening vs the prior strongly-consistent DO revocation).** The refresh record lives in Workers KV; **logout still revokes** it (the registry deletes the KV record + its `RefreshTokenIndex` entry, KV-delete-first so an interruption never strands a live-but-unindexed token; and every writer of a KV record re-reads the index after its put and deletes the put if the row went or changed meanwhile, so a revoke racing a login strands none either — only a writer dying between its put and that check can), but because KV is eventually consistent a revoked/demoted token can keep working for **up to the KV-propagation window (~edge `cacheTtl`, up to ~60s) PLUS the full access-TTL (`ACCESS_TOKEN_TTL=900s`), and repeatably within that window** — NOT "one more request." The mitigation is the short access-TTL (a demoted user's already-minted 15-min access token is the real exposure bound; the next refresh reflects the change once KV propagates). WebAuthN/MFA (pre-beta) restores defence-in-depth. **These MUST stay intact:** JWT verification + scope enforcement on every protected path; logout revokes the KV record; the fixed 30-day refresh TTL.
- **A DERIVED session MUST NOT log out through the ORIGINATING session.** When one session mints a second (impersonation today; the consent-gated support session next), the derived one holds **no refresh cookie of its own** — so its "log out" MUST be teardown only. Every refresh cookie sits at `Path=/` on the platform host, so a logout from the derived client would end **every** session the browser holds, the originator's included: `logout()` sends a top-level page to the platform host's logout page, which ends every cookie it receives. The control is `NebulaClient.logout()`'s `#mintedFrom` branch, which disposes the child and navigates nowhere.
  - ⚠️ **The harm is invisible to the obvious assertions** — the originator's socket stays open (the Gateway verifies a stateless JWT) and it keeps minting off an unexpired access token — so a test MUST observe the **navigation** the child must not make, and SHOULD probe the originator's cookie on the platform host's refresh (200 intact / 401 revoked) as a regression guard. Covered by `impersonate-lifetime.test.ts` and `harness/scenarios/impersonation-lifecycle.ts`.
- **A turn's authority is pinned at the post that triggered it (decided 2026-09-06).** The door check on the Message create is the one permission decision for the whole turn: its source writes run in-DO, and its reply commits with the door's verdict pinned (`TransactionOpts.pinnedAtPost`, server-composed only — the same trust fence as `actor`), so a token expiring or a grant lapsing mid-turn neither stops the turn nor refuses its reply. The generation deadline is a hung-call backstop and MUST NOT be read as an authorization bound. Covered by `source-chat-floor.test.ts` F5.
- **Permission checks before resource mutation** — resource operations MUST pass a DAG permission check. When refactoring a permission path, you MUST enumerate every throw case so a broadened catch doesn't silently turn a malformed-request error into a permission failure (see the typed-errors note in [durable-objects.md](durable-objects.md)).
- **Trust-boundary crossings** — when a design crosses a trust boundary (client → Gateway → DO, or DWL sandbox → host), you MUST name it and confirm the receiving side re-validates rather than trusting the sender. The sanctioned exception is [ADR-023](../../docs/adr/023-the-mesh-boundary-is-crossed-at-a-bridge.md)'s `@rawRpc()` bridge: its entry re-validates only that the binding and instance name it is handed name this object, because only our own Worker holds the binding, and the decision it carries out was made where claims were checked.
