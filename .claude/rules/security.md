# Security Invariants

Lumenize-specific, not generic OWASP. Security is on by default — you have to jump through hoops to disable it, and those hoops must never be reachable in production. These are the *conformance* checks; deeper design review (sandbox-escape analysis, permission-model completeness) is a reviewer-panel concern — see `tasks/on-hold/task-review-panel.md`.

- **Secrets never committed** — see [critical.md](critical.md). No tokens/keys in source, `wrangler.jsonc`, or any committed file.
- **Never log secrets — at ANY level.** `@lumenize/debug` gates all output on the `DEBUG` var, so prod is normally silent — but we run broad `DEBUG` in pre-alpha for tracing, so *no log statement may emit a secret* regardless of level. Never log: magic-link tokens/URLs, raw/minted JWTs or access tokens, refresh tokens, cookies/`Authorization` headers, signing keys, or `TURNSTILE_SECRET_KEY`. Log **identifiers** (`sub`, `email`, `instanceName`, `method`) and **`url.pathname`** — **never `request.url`** (a full URL can carry a query-string secret, e.g. `/auth/{scope}/magic-link?token=…`). Emails/subs are identifiers, not secrets, and may be logged. (Audited clean 2026-06-26: the only `request.url` logs were two WS-reject lines in `entrypoint.ts`, tightened to pathname.)
- **Test-mode flags only in vitest `miniflare.bindings`**, never in `wrangler.jsonc` `vars` (see [packaging.md](packaging.md)). A test-mode flag that bypasses auth or admin checks must be unreachable in a deployed Worker. Never weaken `requireAdmin` / admin-bypass paths outside test bindings.
  - ⚠️ **The two auth packages are NOT equally forgiving of a leak, and `nebula-auth` is the unforgiving one.** `@lumenize/auth` needs **two** factors — the `LUMENIZE_AUTH_TEST_MODE` binding **and** a per-request `?_test=true` — so a leaked binding there only affects requests that deliberately opted in. **`nebula-auth` gates on the BINDING ALONE** and structurally cannot do otherwise: the decision is made inside the registry DO, reached by RPC with no request URL to sniff. ⇒ **a leaked `NEBULA_AUTH_TEST_MODE` on a deployed Worker hands magic links to ORDINARY traffic.** There is no second factor to save you, so the binding's absence from every deployable surface *is* the control: **`scripts/audit-test-mode.sh` is what holds that line** — it must stay passing, and the flag must appear in zero `wrangler.jsonc` / `.dev.vars` / CI config / npm scripts. Don't "helpfully" add a `?_test=true` check to `nebula-auth` to match the sibling either; a URL isn't available at the decision point, so it would be decorative. Closing the asymmetry for real means threading an explicit flag through the RPC, tracked in `tasks/backlog.md` alongside the token-core de-fork.
- **JWT verification on every protected path** — verify the token *and* enforce scope (`aud`/`activeScope`) before acting. Auth uses a two-scope model: `authScope` (cookie path) + `activeScope` (JWT `aud`). Don't trust an unverified claim.
- **Delegation (`act` chains) — two invariants.** (1) *Read-side*: authz decisions read the **authority principal** — the top-level `sub` + its `access` claim — and **never** the `act` chain; `act` (`act.sub`, nested) is traceability/display only, whose sole reader is `apps/nebula/src/resources.ts` `#buildChangedBy`. Enforcement sites: `dag-tree.ts` `requirePermission`, `nebula-do.ts` `enforceScopeReach`. (2) *Mint-side*: a delegated / act-for token mint (`nebula-auth` `/delegated-token`) must never grant scope or `admin` exceeding the **caller's** own verified reach — bind the minted `access.authScopePattern` to the caller-covered requested scope, set `admin` only if the caller holds admin covering it, and **never** copy the acted-for target's `isAdmin` or the issuing instance's pattern. (The absence of rule (2) was a real escalation; see `tasks/archive/rfc-act-chains.md`.)
- **Refresh tokens — no per-refresh rotation, no slide (decisions 2026-06-29 / 2026-07-11).** Rotation was dropped: a refresh does not re-issue or revoke the refresh token. The **slide** was also dropped (`tasks/archive/nebula-auth-surrogate-sub.md`): the refresh token gets a **fixed 30-day TTL at login** and refresh is a **pure Workers-KV read** (the singleton registry is never on the refresh path — `worker-token.ts` `handleRefreshToken`) with **zero writes**; a 30-day re-login (a fresh magic link) is the accepted UX cost. Rationale for no-rotation: the cookie is `HttpOnly; Secure; SameSite=Strict`, Path-scoped (`/auth/{authScope}`), host-only — not JS-readable, not cross-site — so the theft surface rotation defends is already closed; and the implementation never had reuse-detection/family-revoke, so rotation only added fragility (overlapping refreshes racing a single-use token → spurious logout) with no detection benefit. **Don't re-introduce per-refresh rotation OR the slide.** If breach *detection* is wanted later, do it properly: rotation **with a grace window** **plus family-revoke on post-grace reuse** — never the no-grace form.
  - **⚠️ Revocation is now KV-eventually-consistent (a genuine, accepted softening vs the prior strongly-consistent DO revocation).** The refresh record lives in Workers KV; **logout still revokes** it (the registry deletes the KV record + its `RefreshTokenIndex` entry, KV-delete-first so an interruption never strands a live-but-unindexed token), but because KV is eventually consistent a revoked/demoted token can keep working for **up to the KV-propagation window (~edge `cacheTtl`, up to ~60s) PLUS the full access-TTL (`ACCESS_TOKEN_TTL=900s`), and repeatably within that window** — NOT "one more request." The mitigation is the short access-TTL (a demoted user's already-minted 15-min access token is the real exposure bound; the next refresh reflects the change once KV propagates). WebAuthN/MFA (pre-beta) restores defence-in-depth. **Keep intact:** JWT verification + scope enforcement on every protected path; logout revokes the KV record; the fixed 30-day refresh TTL.
- **Permission checks before resource mutation** — resource operations must pass a DAG permission check. When refactoring a permission path, enumerate every throw case so a broadened catch doesn't silently turn a malformed-request error into a permission failure (see the typed-errors note in [durable-objects.md](durable-objects.md)).
- **Parameterized SQL only** — use `this.svc.sql` template binding or `ctx.storage.sql` parameters; never string-concatenate user input into SQL (see [durable-objects.md](durable-objects.md) § Storage).
- **Trust-boundary crossings** — when a design crosses a trust boundary (client → Gateway → DO, or DWL sandbox → host), name it and confirm the receiving side re-validates rather than trusting the sender.
