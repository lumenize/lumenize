# Nebula Security Invariants

**Scoped to the Registry in Mesh's auth layer (`packages/mesh/src/auth`), the platform (`apps/nebula`), and the Mesh code between them.** That code is the passage step in `ScopedMeshDO` and the core that dispatches it (`lmz-api.ts`, `node-kinds.ts`), `UnscopedMeshDO`'s refusal of a scope's name, every check a Client's frame meets before it leaves its host (`client-gateway.ts`, reading the routes an app declares in `routes.ts`), the session `MeshClient` holds, and the page-origin helpers a client's factory reads the platform host from (`page-origin.ts`). **This file is the conformance half of one model.** [`docs/vision/auth.md`](../../docs/vision/auth.md) is that model: it describes the target in present tense and is `status: accepted`, so where the two disagree, **this file is what is wrong** unless it is deliberately describing today's code. Read it for *why* a rule exists; read this for what is checkable. `/review-task`'s security lens loads both.

Security is on by default — you have to jump through hoops to disable it, and those hoops MUST NOT be reachable in production. These are the *conformance* checks; deeper design review (sandbox-escape analysis, permission-model completeness) is a reviewer-panel concern — see the `/review-task` skill.

⚠️ **Nothing here binds `@lumenize/auth` or `@lumenize/crypto`.** They have their own auth model and at least one **opposite** policy — the base package still rotates refresh tokens, which § *Refresh tokens* below forbids for Nebula. ⚠️ Whether that is a deliberate difference or a gap to close is **open**, tracked in [`tasks/backlog.md`](../../tasks/backlog.md) § Nebula Auth; what is settled is that this file is not the thing that decides it. Their local invariants live in JSDoc at the site; `@lumenize/auth`'s two-factor test-mode gate is on `LumenizeAuth`'s `#isTestMode`. Universal guardrails — secrets, SQL, storage — are in [critical.md](critical.md) and [durable-objects.md](durable-objects.md), which load regardless of package.

- **Test-mode flags MUST live in vitest `miniflare.bindings`**, and MUST NOT appear in `wrangler.jsonc` `vars` (see [packaging.md](packaging.md)). A test-mode flag that bypasses auth or admin checks MUST be unreachable in a deployed Worker. No binding, flag or env var MAY make `requireDominionHere`, `requireChatWrite` or the DAG's `requirePermission` pass for a caller the design refuses.
  - **A guard's floor changing by design decision is a different thing, and this file records it.** The Galaxy's source entries — `readSource`, `writeSource`, `buildNow` — moved from `requireDominionHere` to `requireChatWrite` on 2026-09-05. That guard is DAG `write` at the chat node, the check a Message create passes at the door, so a collaborator's direct call and their triggered turn agree. It reads the grant through `OrgTree.requirePermission` and inherits that check's obligations: the host-confined dominion bypass, and the `PermissionDeniedError` message a boundary refusal is told apart by. Configuration (`setGalaxyConfig`) stays behind dominion, and so does the one wipe: the plane's `resetDevData`, behind the `resources` door, checks dominion over its host itself and refuses off `.dev`. A build that lands moves only what `.dev` serves, its copy of the built app and the ontology row its Star runs, and records the build as `.dev`'s newest `ServedBuild`.
  - **`@lumenize/auth` and Mesh's auth layer are NOT equally forgiving of a leak, and Mesh's is the unforgiving one.** `@lumenize/auth` needs **two** factors — the `LUMENIZE_AUTH_TEST_MODE` binding **and** a per-request `?_test=true` (`LumenizeAuth`'s `#isTestMode`) — so a leaked binding there only affects requests that deliberately opted in. **Mesh's auth layer gates on the BINDING ALONE.** ⇒ **a leaked `AUTH_TEST_MODE` on a deployed Worker hands magic links to ORDINARY traffic.** There is no second factor to save you, so the binding's absence from every deployable surface *is* the control: **`scripts/audit-test-mode.sh` is what holds that line** — it MUST stay passing, and the flag MUST appear in zero `wrangler.jsonc` / `.dev.vars` / CI config / npm scripts.
    - **A second factor is a DECISION, not an impossibility, and the standing answer is "not now".** The link-returning site is `#deliverMagicLink`: the claim routes reach it through a DO `fetch()` that already threads a URL-derived `origin` in, and the Worker's `email-magic-link` handler reaches it by RPC holding the URL, so either could carry a flag. *(The facade's invite-send skip has no request URL at all, so a per-request factor is meaningless there.)* A second factor defends only against a leaked binding reaching *ordinary* traffic, which the audit script already prevents (`calibration.md` §2). ⇒ A `?_test=true` check MUST NOT be added to Mesh's auth layer as hardening; re-opening it is a decision, tracked in `tasks/backlog.md` § *Immediate work backlog*.
- **Every protected path MUST verify the JWT** — verify the token *and* enforce scope before acting. Auth uses a two-scope model: `authScope`, the membership whose `__Host-refresh-token.{scope}` cookie minted the token, and `aud`, the scope its host spells. An unverified claim MUST NOT be trusted.
  - **Passage and dominion MUST read `aud`, with the admin bit from the membership — the host rule** ([ADR-015](../../docs/adr/015-passage-and-dominion.md), [ADR-022](../../docs/adr/022-every-session-lives-on-the-platform-host.md)). A universe admin's token from `tenant1.crm.acme.lumenize.dev` holds dominion over `acme.crm.tenant1` alone and passage up to `acme.crm` and `acme`, never sideways to `acme.crm.tenant2`; the same membership from `acme.lumenize.dev` holds dominion over all of them. So a page's code acts within its host's subtree, whoever's membership the token rests on, and no token holds dominion over the platform root, which is no host's scope.
  - **A call chain a node started carries no JWT, and its `activeScope` is the starting node's name** ([ADR-015](../../docs/adr/015-passage-and-dominion.md)). A scoped node acts as a plain member of the scope that names it, with no `scopeAdmin`, and a chain started by an unscoped node, named by an id as a Profile is, has no `activeScope` and gets no passage into a scoped node.
  - **Mesh builds the only exceptions, and no other code MAY write `originAuth`** (ADR-025).
    - **`lmz.actFor(record, principal, fn)`** starts a chain under the claims a stored record holds, with the node's local principal prepended as the outermost `act`. The record is what the server stamped on a snapshot from the verified claims of the write that made it, so its `access` and `aud` are as of that write. `lmz.actFor` takes a plain record, so a node's own code MUST reach it only through `Resources.actUnderClaimsOf`, which names a snapshot by its resource id and `validFrom`, reads the record itself, and refuses a snapshot that has moved on. `grep -rnE '\.actFor\(' apps/nebula/src packages/resources/src packages/mesh/src` is the proof: it prints the plane's one call. Authorization is unchanged, since rule (1) below reads the subject and never `act`.
    - **`lmz.asLocalPrincipal(principal, fn)`** runs a block under claims Mesh builds: the principal's name as `sub`, the node's own name as `aud` and `authScope`, and never `scopeAdmin`. A call made inside starts a fresh chain with no claims, so they never leave the node. A name shaped like a UUID is refused, so built claims can never be a person's.
    - `lmz.actFor` refuses a record whose `sub` is not shaped like a person's id, which a local principal's own record never is. `packages/mesh/test/claims-forms.test.ts` holds the refusal.
  - **A plain membership's token MUST have `aud` equal to its `authScope`**, enforced at verification and at the mint (`buildAuthClaims`). Without it, reading `aud` would widen a plain member of `acme.crm` holding a token for a tenant's host into passage over the tenant.
- **Cookie or token, never both.** Each route MUST authenticate one way, and no route MAY answer two credentials: a credential under `/auth/` is an emailed link, a refresh cookie or a signup ticket, and an access token authenticates a mesh call. The case it rejects is `scope-summary`, which answered Home by cookie and Studio by token until Home moved to `POST /auth/home-summary`. The trade: a cookie costs a Workers KV read per request where a token verifies statelessly, and buys a revocation that does not wait out an access token.
- **Delegation (`act` chains) — two invariants.** (1) *Read-side*: authz decisions MUST read the **subject** — the top-level `sub`, its `access` claim and the token's `aud` — and MUST NOT read the `act` chain; `act` (`act.sub`, `act.profileId`, nested) is traceability/display only. [ADR-016](../../docs/adr/016-record-the-acting-principal.md) § *`act` is recorded, and never decides what a call may do* holds the commitment, and what rests on it: a persona's tab tests the app as a real member only while this holds. ⚠️ **The enforcement sites are stated as a PROPERTY, never as a list** (a tally here was falsified twice without failing anything): rule (1) is enforced at **every site that decides an authz outcome from the subject's claims** (instrument: `grep -rn 'hasDominionOver(\|hasPassageInto(' apps/nebula/src packages/resources/src packages/mesh/src` for the scope-verdict sites, plus the two non-scope deciders `requirePermission` (DAG grant) and `profile.ts`'s `#requireOwnerOrAdmin` (ownership)). A new guard **inherits** the obligation by deciding from the subject's claims; it cannot extend or fall off a list.
  - **The reader list lives in `scripts/audit-act-readers.mjs`, and nowhere else** (`npm run audit:act-readers`, run by CI). Its `ALLOWED` list names every reader of `act` by file and function, with its kind and what it does with `act`. The audit fails on a read the list does not name, and on an entry that no longer reads. Every reader is one of three kinds, so a new one inherits a classification:
    - **`record` builds or walks a record of who acted, for attribution or display, and never for authz.** `toRecordedClaims` in `access-claims.ts`, the one projection every record goes through, is one. ⚠️ **Every ADR-016 site is of this kind by construction**, since recording the acting principal *means* reading `act`, so a new site MUST be added to `ALLOWED` when it lands.
    - **`mint` and `client` sit outside the read-side rule, and are therefore NOT exceptions to it.** The mint's own gate, in `mintImpersonationToken`, decides what to *issue*, not what an existing token may *do*. A `client` reader mirrors that gate or chooses how the client tears itself down, and decides no access: `assertCanImpersonate` turns a structurally impossible call into an accurate message, and the server's gate remains the enforcement.
    - **A read where `act` would change an authz outcome fits no kind, and there MUST be none.** It is a defect, as the bullet below says, and MUST NOT be added to `ALLOWED`.
    - The audit counts reads only. A comment, and an object literal's `act:` key, read nothing.
  - **Rule (1) has no exception: a check MUST NOT read `act`, its presence included, to decide what a call may do** ([ADR-016](../../docs/adr/016-record-the-acting-principal.md)). Who may act as whom is decided at the mint, which requires dominion over the subject's whole scope, so such a check withholds nothing: an admin already holds total downward dominion (ADR-015 clause 1). A presence check was allowed until 2026-11-15, and each of its uses is gone:
    - **The retired `scope-summary`** answered a token with **every tenancy the subject holds**, scopes the admin driving it may not reach. Home's summary now reads cookies, which no token presents.
    - **The Profile's owner branch** carried `&& !claims.act` until 2026-09-08, against a mint that would issue a token over a membership nobody had accepted. The mint now refuses that subject ([ADR-012](../../docs/adr/012-global-profile-visibility.md) § *Alternatives considered*).
    - **`Galaxy.runInTab`** refused a post written while impersonating, for a day.
    - **A call that answers for a PERSON across scopes MUST read the session's cookies, never a token.** It is the one kind of call where impersonation would hand an actor more than their own dominion reaches, and a cookie is what an impersonation token cannot present. Do not reinstate a check on `act` in its place.
  - **(2) *Mint-side*:** the impersonation mint (`mintImpersonationToken`, behind `AuthFacade.impersonate`) MUST authorize on **one predicate, an identity check, and the subject's ACCEPTANCE** — the caller MUST hold `hasDominionOver` over the **subject's scope** (ADR-015, "upward is nil"), the subject MUST be a *different* `sub`, and the subject's membership MUST have been accepted. The minted token then carries the **subject's** `sub`, `authScope` and `scopeAdmin`, with the caller in `act` and the caller's own `aud` — no caller names the child's scope. The predicate reads the caller's dominion from its own host, `aud`, like every verdict (the host rule), and the child's `aud` MUST be validated against the subject's scope, refusing a host outside it so an unverifiable token fails fast. Together they hold the child's `aud` to exactly the subject's scope: an admin impersonates from the subject's own page.
    - **The refresh on a persona's host is the mint's second caller, and adds no rule of its own.** `gerry--dev.crm.acme.lumenize.dev` spells an address, and the refresh finds the accepted member under it at that Star. It then hands the mint the claims `buildAuthClaims` would have minted for the opener on that host, so the predicate, the identity check and the acceptance above decide, as they do for `AuthFacade.impersonate` ([ADR-022](../../docs/adr/022-every-session-lives-on-the-platform-host.md) § *A persona's host*). The refresh MUST NOT decide who may open a persona's session itself: a mutation showed such a rule changed no outcome with the mint behind it. A held session is read under the mint's own predicate, `canMintFor`, asked of the opener's KV record.
    - **A persona's host holds a session of its own, which only its first refresh opens through the mint.** That refresh records the session with `recordSessions`, naming the opener as its `actor`, and sets `__Host-refresh-token.{u}.{g}.{persona}--{star}`, a day long. A later refresh MUST mint from the session only while the opener it names sends their own cookie, and that record holds dominion over the Star (`holdsPersonaSession`). So a KV hit reads nothing from the Registry ([ADR-018](../../docs/adr/018-singleton-is-the-scarce-resource.md)).
    - **A record that names an `actor` MUST mint with it as `act`, on every path.** The session's value under any cookie name then cannot mint a token naming the persona alone, and an admin persona's session opens no other persona's. The Registry composes every derived record in `#recordOf`, so no writer can drop the actor. `persona-host-refresh.test.ts` holds each.
    - **The Worker's mail handler is a third acceptance writer, beside the link's page and Home's Accept.** `acceptPersonaInvite` MUST accept only an unspent invite whose address is the message's own recipient and spells forward, through `personaAddress`, from the Star the Registry names for that invite. It MUST NOT read a Star, a persona or a link from the message's body or its address alone, and it records no session. That is what keeps ADR-012's rule that an invite confers nothing until accepted: the only memberships it takes up are in the Star an address itself names. `persona-mail.test.ts` holds each refusal.
    - **An invite MUST NOT send a persona's address anywhere but the Star it spells.** `AuthFacade.invite` answers such an invitee with an error of its own and passes the rest on, so no membership is made. Into an app, the invite would leave a pending admin membership of the workspace, and an invite never lowers a bit, so the workspace's own plain invite would make the persona an admin nobody chose. The check spells `personaAddress` forward from the target scope and compares. `invite-facade.test.ts` holds it.
    - ⚠️ **Narrowed 2026-08-11 from four invariants to this, and the deleted ones MUST NOT be restored as "hardening".** They bounded `activeScope` against the caller and against the subject; both are now *consequences*, because the minted `authScope` **is** the subject's scope, the predicate reads the caller's host, and the validation holds `aud` within the subject — so `aud = subject ⊆ caller's host` is a theorem, not a check. Likewise the minted bit was once the intersection `caller.scopeAdmin && subject.scopeAdmin`; the caller's bit is always set once dominion over the subject holds, making the left operand dead code inside a security predicate — invisible to mutation testing. The escalation all of them were written against (a narrower caller impersonating a broader subject — `tasks/archive/rfc-act-chains.md`) is unreachable under the one predicate that remains.
    - ⚠️ **The ACCEPTANCE conjunct is NOT one of the four bounds narrowed away above, and MUST NOT be deleted as though it were.** Those four were theorems of `aud ⊆ authScope`, so the containment already implied them; acceptance is a fact about the subject's membership that no containment implies. It is enforced through the read rather than a branch — the registry's `getIdentityScope` answers only for an accepted membership, so an unaccepted subject arrives as `null` and the existing collapsed refusal covers them. ⚠️ **A second acceptance read MUST NOT be added at the mint**, and a caller that needs pending rows MUST ask `getIdentityScopeIncludingPending` by name rather than widen the plain one. Pinned by the acceptance test in `packages/mesh/test/auth/impersonation-mint.test.ts`, which discriminates on its FIXTURE (a caller holding dominion over the scope the membership sits in) because the refusal is deliberately collapsed.
    - ⚠️ **The live substitution risk is the ARGUMENT, not the predicate**: any scope reachable at the call site other than the subject's, passed where `hasDominionOver(callerClaims, subject.universeGalaxyStarId)` belongs. That is what a named `canMintFor` wrapper exists to foreclose. The nearest wrong argument is the **caller's own** `aud`, the host it called from: it makes the predicate reflexively true for any admin, and therefore silent — a check that can never refuse, which mutation testing cannot red.
- **Refresh tokens — no per-refresh rotation, no slide (decisions 2026-06-29 / 2026-07-11).** Rotation was dropped: a refresh does not re-issue or revoke the refresh token. The **slide** was also dropped (`tasks/archive/nebula-auth-surrogate-sub.md`): the refresh token gets a **fixed 30-day TTL at login** and refresh is a **Workers-KV read** (`worker-token.ts` `handleRefreshToken`, on the platform host) with **zero writes** on the hit path. A 30-day re-login (a fresh magic link) is the accepted UX cost.
  - ⚠️ **It is not registry-free**: a KV **miss** falls back once to the singleton's `RefreshTokenIndex` (`getRefreshRecord`); a hit there mints and heals KV, and a miss on both expires the cookie. A KV record still **pending** asks the index too, because a colo that read it before the accept can serve that copy for KV's window, and refusing on it tells someone who just accepted that they have not: staleness may permit, never refuse. The fallback is load-bearing because KV is eventually consistent across colos: the consume's Worker writes the record where the person is, and KV reads back its own writes there, but a refresh served from another colo can miss a record written moments earlier. You MUST NOT reason about the refresh path as though the registry is never on it.
  - Rationale for no-rotation: each membership's cookie is `__Host-refresh-token.{scope}`, `HttpOnly; Secure; SameSite=Lax; Path=/`, on the platform host alone ([ADR-022](../../docs/adr/022-every-session-lives-on-the-platform-host.md)). `HttpOnly` hides it from script, `__Host-` keeps it on one host where no sibling can plant or overwrite it, and `Lax` keeps it off a cross-site `fetch` or `POST`, since it rides only a top-level navigation from another site — so the theft surface rotation defends is already closed; and the implementation never had reuse-detection/family-revoke, so rotation only added fragility (overlapping refreshes racing a single-use token → spurious logout) with no detection benefit. **Per-refresh rotation and the slide MUST NOT be re-introduced.** If breach *detection* is wanted later, do it properly: rotation **with a grace window** **plus family-revoke on post-grace reuse** — the no-grace form MUST NOT be used.
  - Every page on the site refreshes off the same few cookies, a page on any `lumenize.dev` host by a credentialed `fetch` to the platform host, so rotation's race between overlapping refreshes is worse here than it was under one cookie per path.
  - **⚠️ Revocation is now KV-eventually-consistent (a genuine, accepted softening vs the prior strongly-consistent DO revocation).** The refresh record lives in Workers KV; **logout still revokes** it (the registry deletes the KV record + its `RefreshTokenIndex` entry, KV-delete-first so an interruption never strands a live-but-unindexed token; and every writer of a KV record re-reads the index after its put and deletes the put if the row went or changed meanwhile, so a revoke racing a login strands none either — only a writer dying between its put and that check can), but because KV is eventually consistent a revoked/demoted token can keep working for **up to the KV-propagation window (~edge `cacheTtl`, up to ~60s) PLUS the full access-TTL (`ACCESS_TOKEN_TTL=900s`), and repeatably within that window** — NOT "one more request." The mitigation is the short access-TTL (a demoted user's already-minted 15-min access token is the real exposure bound; the next refresh reflects the change once KV propagates). WebAuthN/MFA (pre-beta) restores defence-in-depth. **These MUST stay intact:** JWT verification + scope enforcement on every protected path; logout revokes the KV record; the fixed 30-day refresh TTL.
  - **Work the agent does for a person runs on the claims recorded when they posted.** A turn's tools run under the record on the post it took up, so the poster's passage and dominion are as they stood at posting, until an agent message answers the post. No token's lifetime bounds that, and no eviction does. So a call the agent makes for a person, an invite included, can land after they were demoted. They held the permission when they posted, the call is recorded as theirs with the agent as actor, and a membership it creates can be removed. A grant in an orgTree is not part of this: it is read when each call arrives (below).
- **A DERIVED session MUST NOT log out through the ORIGINATING session.** When one session mints a second (impersonation today; the consent-gated support session next), the derived one's "log out" MUST be teardown only. An impersonated child holds **no refresh cookie of its own**, and a persona's tab holds one beside its opener's. Every refresh cookie sits at `Path=/` on the platform host, so a logout from either would end **every** session the browser holds, the originator's included: `logout()` sends a top-level page to the platform host's logout page, which ends every cookie it receives. The control is `MeshClient.logout()`, in two places: its `#mintedFrom` branch, which disposes an impersonated child, and its return for a page whose own token carries `act`, which a persona's tab holds, minted by the refresh on its host. Neither navigates anywhere. That second check reads only whether `act` is present, to choose what the page's own logout does, and decides no access.
  - ⚠️ **The harm is invisible to the obvious assertions** — the originator's socket stays open (its socket's upgrade verified a stateless JWT) and it keeps minting off an unexpired access token — so a test MUST observe the **navigation** the child must not make, and SHOULD probe the originator's cookie on the platform host's refresh (200 intact / 401 revoked) as a regression guard. Covered by `impersonate-lifetime.test.ts` and `harness/scenarios/impersonation-lifecycle.ts`.
- **A turn's source writes and builds meet the chat floor as each runs, and every Resources write is checked when it lands (decided 2026-11-12, reversing 2026-09-06's rule that they ran on the post's verdict).** Two doors exist, both DAG `write` at `CHAT_NODE_ID`: the Message create's check, which admits a post, and `requireChatWrite`, which admits a direct `readSource`, `writeSource`, `buildNow` or `readCast`. A turn's tools reach those entries in-process, where a decorator's guard does not run, so each source tool calls `requireChatWrite` itself, under the claims recorded on the post its turn took up. A poster whose grant was removed after posting is refused at the next tool call, and the model reads the refusal as that call's error. The generation deadline is a hung-call backstop and MUST NOT be read as an authorization bound. Covered by `source-chat-floor.test.ts` F5.
  - **The agent's reply and a landing's `ServedBuild` are the agent's own writes.** They are checked live against its own protected grant on the chat node ([ADR-025](../../docs/adr/025-fine-grained-access-is-the-orgtree.md)); `served-build.test.ts`'s grant case covers it. A Resources write a tool makes for a person, an invite's pending row for one, is checked live under that person's recorded claims.
  - **`TransactionOpts.pinnedAtDoor` and the `actor` write option are gone and MUST NOT return.** A write records the claims its call carries and passes the tree's check under them.
- **Code a turn hands to a tab runs as that tab's member, and each place it passes is a boundary.** The agent's `run_in_tab` runs code the model wrote with a page's own session, in a dev Star, whose data a wipe can drop. Nothing asks the person to confirm it (`docs/vision/_ai-security.md` § *Reversibility, not agency, is the risk variable*).
  - **The page.** `answerRunRequests` MUST be started only on a page the serving layer marked as a dev Star's, in a frame, and MUST obey only a message from `window.parent` at the galaxy's Studio origin. A tenant Star's page MUST NOT have it. `run-request.test.ts` holds each refusal.
  - **The Galaxy.** `Galaxy.runInTab` MUST carry no `@mesh()`, and MUST call only a Studio tab this Galaxy hosts whose chat subscription was made under the `sub` of the claims its turn acts under. It MUST NOT read `act`: a post written while impersonating runs in the impersonated person's own Studio, as their own post does, since the mint already requires dominion over their whole scope. A refusal stood here from 2026-11-14 to 2026-11-15 and withheld nothing. A tab that held its socket and stayed silent MUST NOT be passed over for another, since the code may still run there. `onTabAnswer`, the call's result handler, MUST carry no `@mesh()` either, MUST write only the outcome of the call its continuation names, on the round it names, and MUST choose the tab after one that ran nothing by the same rule, under the claims of the post the turn took up. `run-in-tab.test.ts`, `tab-call.test.ts` and `galaxy-resource-surface.test.ts` hold each.
  - **The record.** What the code writes names the tab's member, and a persona's tab names its opener in `act`. The agent is named on the turn's message, which records the call and its result. Server code MUST NOT write in the dev Star for a persona: the design that did was reverted on 2026-11-13.
- **Permission checks before resource mutation** — resource operations MUST pass a DAG permission check. When refactoring a permission path, you MUST enumerate every throw case so a broadened catch doesn't silently turn a malformed-request error into a permission failure (see the typed-errors note in [durable-objects.md](durable-objects.md)).
- **Trust-boundary crossings** — when a design crosses a trust boundary (client → host node → DO, or DWL sandbox → host), you MUST name it and confirm the receiving side re-validates rather than trusting the sender. The sanctioned exception is [ADR-023](../../docs/adr/023-the-mesh-boundary-is-crossed-at-a-bridge.md)'s `@rawRpc()` bridge: its entry re-validates only that the binding and instance name it is handed name this object, because only our own Worker holds the binding, and the decision it carries out was made where claims were checked.
