# Working in This Repo

## Task files
Work is tracked in `tasks/`:
- `tasks/backlog.md` — small tasks and ideas
- `tasks/[project-name].md` — active multi-phase projects
- `tasks/on-hold/` — designed but paused, expected to resume
- `tasks/icebox/` — parked indefinitely, no planned return (colder than on-hold)
- `tasks/archive/` — completed projects + point-in-time decision/research records (`decision-*.md`). **Frozen on entry — never update an archived file** (no link fixups, no terminology syncs, no code-drift corrections); sole exception: a dated superseded banner at the top. See `tasks/README.md`.

Use `/task-management` to choose docs-first vs task-file-first when starting a project, then `/write-task` to draft the file (design intent first, hand-reviewed, then phases). When the plan changes mid-stream from what you learn in earlier steps, propose updates to the task file, and summarize what changed after each step. **Not every change needs a task file** — process/organizing tweaks (editing rules, moving content) can be done directly. See `tasks/README.md` for templates.

### Referring to things across files — name them, don't number them
**Cite the durable COMMITMENT, not whichever file currently implements it.** Task files move, get renumbered, get absorbed, get archived; an ADR or a rule does not. A task file that justifies itself by pointing at a sibling task file inherits that file's churn — and reads as circular when the sibling is itself mid-restructure. Bit 2026-07-28: `/mint-narrower-token` justified a guard by citing `identity-mint §4`, when the commitment was ADR-012 all along and §4 was only its current home.

**Across a file boundary, refer to a section by NAME.** Numbers are fine *inside* a file, and are load-bearing where they encode order (phases, gates — `/build-task` transcribes phase order). But a bare `§4` in another file carries no meaning, is unfindable without opening that file, and **rots**: `identity-mint` renumbered the moment its former §3 moved out, and in one file `§4` meant two different sections depending on which filename preceded it. Give sections meaningful names and cite those; add the number only as a convenience alongside.

⚠️ **A numbered handle others are expected to cite must be APPEND-ONLY** — assigned once and never reused or renumbered when a sibling is inserted or removed (`D7`, `ADR-016`, `calibration.md` §3(d)). That is what makes it safe to cite; a section number, which shifts under insertion, is not.

⚠️ **A task-file handle must never ship in SOURCE.** `S4`, `D12`, `Phase 3` are a task file's native currency and are fine *inside* it — but code outlives the file that specified it, and that file archives. A comment citing `D12` is unresolvable the moment it does, which is the cross-file rule above with a worse blast radius: nobody re-reads a five-year-old code comment against a frozen task file. **In source, cite an ADR, a rule file, or nothing** — most handles reduce to one of those, and the rest are a clause of prose (`nebula-auth`'s `schemas.ts` already writes them that way: *"Existence is INDEPENDENT of membership — a wildcard-managed child scope has a row here and zero `Identities`"*, no handle). ⇒ **Convert at transcription, as a phase criterion** — not as a cleanup step, which is the shape that gets skipped — and check it: `grep -nE '\b[SD](1[0-9]|[1-9])\b'` over the changed files, then eyeball (`S3` also spells a storage product). Where a long rationale genuinely has no ADR home, cite the archived path by name; archived files are frozen, so that pointer is stable.

⚠️ **Never restate another file's COUNTS or DATES — and prefer a pointer to a summary.** Distinct from the rule above, and it rots for a different reason: not that the handle moves, but that **the source keeps growing while the copy does not**. An inventory (*"S1–S7 inherited, D1–D13 decided"*) and a status date (*"decisions RESOLVED 2026-07-26"*) are false the moment the source gains a row, and nothing makes them fail loudly — they read authoritative while wrong. Bit 2026-08-02: the pre-alpha master plan's entry point for the identity work carried a stale inventory, a stale date, **and a headline naming the design that file had explicitly rejected**, which had already propagated to a backlog row. ⇒ A cross-file reference states the **target shape in one line** and **points by section name**; anything a reader needs beyond that, they get by following the link. **A summary has no derivation, so nothing updates it** — if you find yourself restating a sibling's reasoning, you are creating the next stale copy. (Corollary: a pointer needs no owner, which is why "add it to a sweep list" is the weaker fix — a sweep list is itself a summary.)

## Design-first: diagrams before prose when the design is tangled
When a multi-node/mesh design gets tangled — or when task files have drifted into mutual contradiction — **lead with sequence diagrams (a participant/cast model + per-flow diagrams), not prose.** Prose hides contradictions; a diagram's participants + ordering + gating force precision and make the drift visible (this is what the Phase-3.5 review kept surfacing, and what `tasks/nebula-dev-flows.md` was built to fix — Larry: "my mind works better with sequence diagrams than prose"). Nail the cast + naming + flows *with the user* first, **then** rewrite the prose/task files to conform. Proactively offer this when you sense the design space is tangled. Mermaid traps: no `;` in `Note` text (statement separator → parse error); no `#` in ANY diagram text — participant label, message, or note (`#` starts an HTML-entity escape like `#35;`, so `participant D as #dispatchEnvelope` renders a **blank actor box**; bitten 2026-07-02 drawing methods-as-actors with `#`-private names — write `dispatchEnvelope (private)`; do NOT "escape" via `#35;`, which trips the `;` check); a long `Note over` anchored on the **leftmost** actor(s) overflows off-canvas and clips — span more actors (`Note over A,C`); solid `->>` = call/request, dashed `-->>` = response/return/push. **After every Mermaid write/edit, run the mechanical render-safety check before considering it done** — knowing the traps is NOT enough on its own (this guidance was already in place when the `;`-in-`Note` bug got *reintroduced right after being fixed*; you can't visually render from here, so verify with the grep, then have the human eyeball the actual render). Extract the fenced `mermaid` blocks and grep for the killer glyphs `;` `#` — it should print nothing:

```sh
awk '/[`][`][`]mermaid/{m=1;next} /[`][`][`]/{m=0} m' <file> | grep -E '[;#]' || echo "clean"
```

(Applies equally to Mermaid in `website/**` docs — see `documentation.md`.)

**Stray invisible characters (U+00A0 non-breaking space, U+0000 NUL):** two vectors, same class of bug — a byte you can't see in the rendered diff. (1) Some WYSIWYG markdown editors (e.g. Typora) silently insert **NBSP** on edit; they break exact-match string edits (the `Edit` tool can't match an "identical" line) and can break rendering. (2) An **agent `Edit`/`Write` can inject a NUL** into a string literal that reads as a space in the diff — it compiles and runs (NUL is a valid string char), so it passes type-check *and* tests; the `/build-task` verifier panel caught one as the separator inside a `` `${a} ${b}` `` dedup key.

⚠️ **`grep` CANNOT detect the NUL — it reports nothing for a file it considers binary, which is exactly what a NUL makes it.** The old check here (`grep -nP '[\xc2\xa0\x00]' <file>`) therefore *passes silently on a corrupt file*; bitten 2026-07-21, where the only symptom was an unrelated `grep` mysteriously returning empty on a file `Read` showed fine. Use a **byte count**, which cannot be fooled:

```sh
tr -cd '\000' < <file> | wc -c          # NUL count — must be 0
grep -c $'\xc2\xa0' <file>              # NBSP count — must be 0 (grep IS fine for NBSP)
file <file>                             # a source file reporting "data" instead of "text" = NUL
```

Strip with `perl -i -pe 's/\xc2\xa0/ /g; s/\x00/ /g' <file>`.

⚠️ **Never put the invisible character *literally* into the check command.** Write it as an explicit escape (`b'\x00'`, `$'\xc2\xa0'`), never by pasting the character itself — a pasted NBSP silently degrades to a plain space in transit, so the check then matches every file with any space and reports the whole tree dirty (also bitten 2026-07-21, in the very command written to catch the first bug). For a whole-tree sweep, count bytes in a script rather than grepping:

```sh
python3 -c "import pathlib,subprocess as s
for f in [l.split(maxsplit=1)[1] for l in s.run(['git','status','--short'],capture_output=True,text=True).stdout.splitlines()]:
    p=pathlib.Path(f)
    if p.is_file():
        b=p.read_bytes()
        if b.count(b'\x00') or b.count(b'\xc2\xa0'): print('DIRTY', f)"
```

## Evaluating alternatives: weigh the unlearning tax, not just build cost
When you compare options and **recommend** one (interim-vs-target, build order, scope cut, design choice), make the **unlearning tax** an explicit criterion alongside build cost — and usually the deciding one. The bottleneck is **reviewer time**, not lines of code. A known-temporary artifact ("interim") that lands in a surface re-read every session — code, docs, task files, agent memory — gets re-anchored on as "the model" and must be **unlearned, repeatedly, at the reviewer's expense.** (Empirically the single largest drain on pre-alpha review time has been unlearning the `acme.app.dev` interim — see the `interim-unlearning-tax` memory.)

Score each candidate on this, and say so when you recommend:
- **Interim cost ≈ (how many re-read surfaces reflect it) × (its lifetime) × (sessions over that life)** — paid in the bottleneck reviewer's correction time, *not* in build size. An option that is cheaper to *build* but seeds a durable, widely-reflected interim is usually the **more expensive** choice. Recommend accordingly, and name this tax in the trade-off.
- **Prefer building the target over a lean interim _when the target is pinnable now_.** A half-pinned "final" becomes its own interim and costs the same tax → the move is **pin → purge → build**, not rush-to-final. Don't over-pin either: pin only what the current step needs to stop describing the model wrongly; leave genuinely-later mechanics as clearly-fenced "not yet built" pointers (not interims).
- ⚠️ **A TEST IS A CONSUMER — and an interim built to make tests runnable ossifies as hard as production code.** This is the clause most often got wrong, in the *conservative* direction. When judging "is there a present consumer," a test we need today counts: if a test would exercise the real mechanism, that is a consumer, and building the real thing beats building a stand-in for it. **Every test written against a stand-in must also be unlearned**, so a mock/fixture/shortcut is not the cheap option — it is the same ossification with the cost hidden in the test suite.
  - **Prefer `it.skip` over an ossifying stand-in.** Skipping defers *one* test; a mock creates an artifact that N future tests anchor to. (See `testing.md` § Deferring ≠ deleting.)
  - **Case study — the login shortcuts.** Test-mode mints were used instead of the real login loop to save a round trip on a mechanism *we had already built*. The cost: (1) **fidelity** — the shortcut diverged from the real path, so real bugs got through; (2) **ossification** — every fixture anchored to it, and un-anchoring took a whole phase; (3) **delay** — it deferred building what the feature actually needed to be *usable*, not merely low-fidelity testable. Weigh all three, not just the round trip.
  - **The asymmetry that decides it:** a slightly-wrong thing you built early is usually *cheaper to fix* than an interim is to overcome, because the interim has consumers and the wrong design mostly has a shape. Favor **the goal** (a product someone pays for) over **the milestone** — a milestone is a checkpoint, not the thing being built.
- **YAGNI gates capability, never generality.** *Whether* to build a capability now is a scope question — push back when there is no present consumer *of any kind, tests included* (see above). *How* to shape a capability already in scope is **not**: prefer the generic form that solves today's problem without foreclosing tomorrow, and treat point solutions / tier-or-case special-casing as the anti-pattern. **Cost test:** when the general form costs the **same or less** than the narrow one (removing a restriction, widening a parameter, moving a flag from the batch to the entry), the narrow one is strictly worse — it is a lean interim someone must later unlearn. Reserve the objection for a general mechanism costing *materially more* than the immediate need (a new subsystem, carrier, or protocol). Bit 2026-07-19: a proposal to restrict an invite's `isAdmin` flag to one scope tier would have **added** a tier check to a mechanism whose reach invariant was already uniform across every tier — more code, less capability, and an interim to unlearn.
- **When an interim is genuinely unavoidable, minimize its tax:** single-source it (one constant, not scattered), label it `TEMP → target=X` at every site, and record it (memory / task file) as a **dead interim, model is X** — never as the model. Task files state the **target in present tense**; the interim is a fenced, dated exception.
- **Self-check before trusting current code:** reading any default / scope / identity / config value, ask "**target or interim?**" — don't assume the current code is the model. **This extends to BEHAVIORS/ENDPOINTS, not just values:** during a rewrite to a pinned new model, a code path that *exists in the old code with passing tests* is NOT thereby validated for the new model — conform it to the pinned model or cut it, and never carry a test that **enshrines the old shape** (a green test asserting deprecated behavior is a false-confidence trap the reviewer must then catch). Bit 2026-07-13: a rewrite preserved the old open, identity-minting `claimStar` (mirroring `claimUniverse`) though the task pinned "Star = parent-Galaxy admin, wildcard-managed" — reintroducing a stranger-claims-a-child escalation, with new tests that codified it as intended (caught by the `/build-task` verifier panel, not the suite).

## Architecture commitments (ADRs)
`docs/adr/` holds the few repo-shaping commitments — decisions that span packages and survive mechanism swaps (`docs/adr/README.md` has the bar; adding an ADR means adding its one-liner here). `/review-task` reads the full files; these one-liners are the always-loaded constraints:
- **ADR-001** — TypeScript types ARE the schema language; never introduce a second schema language (Zod, JSON Schema, …). The mechanism is typia now; the principle is the commitment.
- **ADR-002** — every surface (wire, storage, validation, diff/patch, history) round-trips the full structured-clone value space, incl. cycles, aliases with identity, Errors, Web API types. A JSON-only surface is never acceptable.
- **ADR-003** — mesh flows are one-way messages carrying continuations; **no node holds a Promise (reply channel) open across a hop for more than an instant** (resiliency: tabs sleep, WS reconnect, DOs hibernate/evict — a held Promise strands). Request/response *semantics* are fine, simulated via a continuation for the result (delivered, not returned). Awaiting is OK only very-briefly under-the-covers (early-ack transport, all call forms) and, in user-land, **only on the Client** (`callAsync` — its heap survives freeze+reconnect and delivery re-resolves to the current socket). No RpcTarget/Cap'n Web sessions.
- **ADR-004** — resources are Snodgrass-style snapshot sequences; history is the substrate. No destructive writes; "current" queries honor the `END_OF_TIME` sentinel.
- **ADR-005** — optimistic concurrency: forward-only eTags prove currency AND provide idempotency (`newETag` replay detection); no locks, no dedupe ledger; non-monotonic checks (permissions, not-found) stay inside the transaction.
- **ADR-006** — resources reference each other by id (FK), never by embedding; a field typed as another ontology type is a relationship rewritten to `string`/`string[]` in the write shape. Related resources are separate ops in one atomic transaction (client supplies every id). Nesting is composition *within* one resource's value only. Embedding an object in a reference field is a loud error. FK referential integrity is deferred (intra-Star, same-transaction scope).
- **ADR-007 (Accepted)** — every Lumenize node type shares one **narrow comms + guards core** — `lmz.call` (receive), `lmz.ctn` (outgoing), `callContext`, `onBeforeCall`, `@mesh()` — by **composition**, never reimplemented. Storage (`lmz.sql`)/alarms/`onStart`/`fetch` are **per-node-type capabilities, NOT the invariant** (a node takes only what it needs — a Worker takes neither alarms nor `onStart`; a **driven container is a capability**, raw `ctx.container` on a `LumenizeDO`, not a node type). New types compose it regardless of base class. Mechanism = `executeEnvelope`/`EnvelopeExecutorNode`, now realized by **2 of 3** server types (`LumenizeDO`/`LumenizeWorker`); the `LumenizeClient` hand-rolls a parallel path — classified as justified browser/Node compat (no ALS), not consolidated. Accepted 2026-06-17 (Q5 spike GOed). `LumenizeContainer` has since been **retired** — we don't `extends Container`; container-driving is raw `ctx.container` on a `LumenizeDO` (`containers.md`).
- **ADR-008 (Accepted; amended 2026-07-08)** — within a Star, the full org/permission tree (nodes, edges, grants, **grantee identity — read/write/admin**) is visible to every member, and the principle **extends to presence** (who is *actively subscribed*, Star-reachability-gated — not per-resource read); **visibility ≠ capability** — enforcement is at the point of action, never secrecy of the tree (which was never a control). Org structure is **not confidential by design** within a Star, so it's not a leak to mitigate. **No per-subtree hiding** — need invisibility? use a separate Star. The denied-node set is **always disclosed** (drives request-access; a query caller already named those nodes). Hard dependency: enforcement at the point of action — this relaxes no access-control requirement. Reopen **only** on a new attack class rooted in tree visibility. Accepted 2026-06-30.
- **ADR-009 (Accepted)** — the **real email-based login is the default** auth path (harness / e2e / `/live` / multi-user) and the path design reasoning **grounds on**; never conclude system behavior from a synthetic path. Ladder, most-preferred first: (1) real login (frictionless via `*@lumenize.io` catch-all → email-test Worker); (2) test-mode server-issuance (`LUMENIZE_AUTH_TEST_MODE`/`createTestRefreshFunction`) for isolated units — real issuance, no email, no client mint; (3) client-side mint (`create-nebula-test-token`) = last resort, justify per-site; (4) negative-control *wrong-shape* mints stay legit. Rationale: shortcuts diverge from real code → mis-grounding + reviewer-time tax; the real magic-link loop costs **~1.4s standalone / ~0.9s marginal** in a running suite, with **no meaningful CF-vs-Resend difference and no cold-start penalty** (re-measured 2026-07-21, instrumented — the earlier "~8s on Resend" was uninstrumented AND attributed to an instrument that sent via Cloudflare; do not re-cite it). So **speed is never a reason to reach for a lower rung**; rung 2 survives on flake/external-dependency grounds only, and is flagged open in the ADR. The mock-email prior is a miscalibrated training reflex ([[real-auth-path-over-shortcuts]]). Accepted 2026-07-06; cost line amended 2026-07-21.
- **ADR-010 (Accepted)** — **keys are random opaque values, statistically unique WITHOUT coordination** (generatable anywhere — client or any server — no round-trip, offline-safe, idempotent). Never key off a **natural/mutable attribute** (email/slug/name — they change) or an **auto-incrementing/rowid counter** (only the sequence-owner can mint the next → round-trip, no offline). The axis is **coordination, not client-vs-server** — identity keys are legitimately registry-minted. Type per `coding-style.md` § IDs: UUID (unordered) / ULID (creation-ordered) — both random-tailed, not counters. Companion **replication rule**: immutable keys copy freely; a **mutable** attribute has one authoritative source — other copies are caches needing an explicit convergence mechanism (read-through / push-on-change / short-TTL token), so denormalization is deliberate not free (e.g. the planned `isAdmin` push), never an un-reconcilable copy (a long-lived token, or a second store with no propagation plan). Motivated by two prod-wipe failures — email-as-cross-DO-FK + ROWID-vs-client-gen ([nebula-auth-surrogate-sub.md](../../tasks/archive/nebula-auth-surrogate-sub.md)). Accepted 2026-07-08.
- **ADR-011 (Accepted)** — persisted/wire **timestamps are ISO 8601 UTC ("Zulu") strings** (`…T…Z`, ms precision, fixed-width), SQLite `TEXT`, string-compared (lexical = chronological); end-of-time sentinel `9999-01-01T00:00:00.000Z` (ADR-004). **Never epoch `number`.** Carve-out: protocol-mandated formats keep their spec (JWT `exp`/`iat` = NumericDate epoch seconds; HTTP = RFC-1123). Mechanism in `coding-style.md` § Timestamps. Motivated by the auth-`number`-vs-Snapshots-`string` split. Accepted 2026-07-11.
- **ADR-012 (Accepted)** — **global cross-scope profile visibility via an unguessable handle**: a person's PUBLIC profile fields (`name`/`nickname`/`picture`) are readable/subscribable by **any authenticated caller holding the `profileId`**, across scope/Star/Universe — no reach gate, no registry read on the read path; holding the (random opaque, ADR-010) `profileId` IS the capability (open-resolution ≠ enumeration). **Generalizes ADR-008** beyond intra-Star, so it's its own commitment. Boundary: only public fields are open — `privateNotes` stays behind `requireOwnerOrAdmin`, and the pushed `value` carries public fields only. Fallback if un-ratified: a scope-intersection reach gate. **Exactly TWO capability levels, no per-field roles:** (1) read the public fields — any authenticated holder of the `profileId`; (2) read/write the private fields **and** write the public ones — owner, super-admin, and an admin covering a scope where this profile holds an **ACCEPTED** membership. **Private-by-default is DERIVED** — the public set is an allow-list, every other field is private by construction, and the pushed snapshot is built from that allow-list (never by subtracting known-private keys), so a new field cannot leak by omission. ⚠️ **Acceptance is load-bearing authz living in a QUERY, not a gate** (`getScopesForProfile`'s predicate): without it anyone could claim a Universe, invite an address they guessed, and become "an admin of a scope that stranger's profile touches" — acceptance closes it because only consuming a link delivered to the mailbox sets it. Re-point it, never drop it. Two residuals are **accepted, not answered**: the branch points *sideways* (global object, scope-local grant) and reaches every scope the person belongs to — scope-keying the private fields is the deferred structural answer. Blast radius is display fields + `privateNotes`, never Star/Galaxy/Universe contents. ⚠️ **The load-bearing reason is that scope authority over a profile can be MANUFACTURED** — Universe self-signup is open by design and an invite mints the membership immediately (`emailVerified=0`, no acceptance), and `profileId` hangs off the email row, so **anyone** can claim a Universe, invite any address, and become "an admin of a scope that profile touches". Any *admin-of-a-touching-scope ⇒ rights* rule therefore grants those rights to everyone. Same manufacture defeats impersonation-eligibility, so **a narrower token is not the owner**: the owner branch is `claims.profileId === profileId && !claims.act` — the one deliberate exception to `security.md`'s read-side rule, licensed because a global object is the only thing an attacker can drag into a scope they invented.
- **ADR-013 (Accepted)** — **`sub` is the only KEY; `profileId` resolves off it and rides as a denormalized display copy**: `profileId` is a plain column on the `Identities` row (not a join table — `sub`→`profileId` is single-valued); resource records (grants/snapshots) **key on `sub` only**, `profileId` **never the authoritative/FK value** — so future `sub`-unification is **additive** (re-point = one-row `UPDATE`, no re-key). ⚠️ **"Never copied" = never as the KEY, NOT absent:** the immutable, **public** `profileId` **IS stamped alongside `sub`** wherever a consumer would otherwise resolve it live — JWT/KV **and the roster/attribution (`changedBy`) path** (ADR-010 immutable-copy, self-heals on re-point) — so the display path reads it off the record: **no `sub`→`profileId` hop, no singleton-Registry load** (live resolution shrinks to the cold case). But **never denormalize an *unsafely*-staling value**: authz scope-sets resolve live (a stored one → security bug). Owner authz short-circuits off the unforgeable JWT `profileId` claim. Accepted 2026-07-15; **amended 2026-07-18** — `profileId` MAY *also* be stamped on a snapshot's **attribution metadata** as a **permanently-immutable, write-time-pinned** historical record (the value **never changes** → no staleness, no re-key; display-only, never a key/FK/authz input) — the immutable carve-out to "never copied onto snapshots" (mutable/keying copies stay rejected).
- **ADR-014 (Proposed)** — a container node **orchestrates from its own companion DO, never across a hop from a sibling**. Reaching a container across a mesh hop multiplies **independently-hibernating state machines** (sibling DO × companion DO × container lifecycle) whose cold-start wake-ordering is the wedge that forced `ctx.abort()` recovery. The companion DO **IS the hub** — it calls *out* (AI/DOs/world) and *down* (`containerFetch`), one hop each side; the container is a **general platform, not a single-purpose binary**. Generalizes to: don't distribute a **liveness-coupled** workflow across independently-hibernating nodes (colocate → one lifecycle, not the product of several) — hops stay fine where liveness is *not* coupled (Star data plane, Gateway). Distinct from ADR-007 (which is comms/guards *uniformity* across node types; this is *placement* for the container node). Mechanism in `containers.md`. **Proposed 2026-07-17 — pending Larry's read.**
- **ADR-017 (Proposed)** — **a URL one person shares takes the recipient to the same page AND the same view state.** View state that changes *what you are looking at* (active scope, selected record, open tab, filters, sort, paging) rides the URL; state that reflects *what you are doing* (scroll, hover, focus, unsaved drafts) does not — test: *would the sender be surprised the recipient didn't see it?* ⚠️ **The URL names WHAT, never permission to look** — no credentials, tokens, or personal data; authorization is re-evaluated on arrival (ADR-008 applied to addressing). ⚠️ **The boundary is NARROWER than the reflex wants** — a `profileId` in a URL is **fine** (it grants public display fields to an already-authenticated caller, the `github.com/{user}` tier; `privateNotes`/email stay behind `requireOwnerOrAdmin`). Do not invent a non-capability alias to avoid it — that is calibration §1 friction against a deliberately-open surface. Test: *does it reveal anything NOT already public?*, not *does it reveal anything?* Scope includes the **codegen scaffold**, so generated apps inherit it. Mechanism (path vs query, encoding) is unspecified and swappable; a shipped view-state param name is public and stable. Written because the default reflex is component-local state and the breakage is **invisible to the author** — only the recipient sees it. Motivated by Studio's `activeScope` diverging from `/app/{scope}`, which breaks the admin-debug support flow. **Proposed 2026-07-29 — principle is Larry's (long-standing); boundary/scope clauses pending his read.**
- **ADR-018 (Proposed)** — **a global singleton DO is the system's scarce resource; state and requests default to OFF it.** A single DO is a hard, non-sharding ceiling — **10 GB**, and roughly **410 rps** all-writes / a little **under 1000 rps** reading one indexed row / a little **over 1000** with no DB reads (measured; evidence, not the commitment) — and passing it means re-architecting the authority model, arriving as an outage, not a warning. Landing anything there needs a reason no other placement satisfies, and the **only** qualifying reasons are **global uniqueness** and **strong consistency at the moment of decision**. Placement preference: (1) derive it, (2) put it where it scales (edge KV / per-entity DO / the Worker) and design for eventual consistency explicitly, (3) the singleton. Two standing obligations for whatever qualifies: **never on a per-request path that scales with user activity** — and a hot path moved off stays off, since a miss-fallback is the same path renamed and will be called "rare" by whoever adds it; and **bounded lifetime, stated** (sweep, TTL, or a row count bounded by something that cannot itself grow without limit — "stale rows are harmless" answers correctness, not the 10 GB ceiling). ⚠️ Constrains **design, never correctness** — if uniqueness or strong consistency is genuinely required, the singleton IS the answer. Written because the pressure is incremental and always locally reasonable: three proposals in two weeks (a per-action audit table, an enumeration index, a convenience read), each cheap alone, none aware of the numbers. **Proposed 2026-08-03 — pending Larry's read.**
- **ADR-016 (Proposed)** — every action that **destroys or removes state, or changes a principal's authority**, records the **FULL verified claims** of the acting token (authority `sub` + the complete `act` chain + `profileId` + the `access` entry), write-time-pinned and immutable. Written because authz keys off `sub` and **never** `act` (`security.md` rule (1)) — which is exactly *why* the record must carry `act`: under impersonation a `sub`-only record **names the person acted upon as the person who acted**, which is worse than no record because it will be believed. **Reversibility is not an exemption** (an un-reversed reversible action is indistinguishable from an irreversible one). An actor may be **token-attested or server-composed** (the platform prepending itself when an agent writes on a person's behalf) — the boundary is **never client-supplied**, and the commitment is that the record names every party, not that every party came from a JWT; keep a composed actor id self-describing (`agent:nebula`). The stored `access` is *asserted* authority — immutable history, **never read back as an authz input** (a stored scope-set is ADR-013's security bug). ⚠️ **ONE SHARED PROJECTION produces every record — no site assembles its own**; a caller passes verified claims and receives the record, never picking fields (a hand-assembled record is how sites silently diverge, and divergence here is unrecoverable history). `executeScopeDeletion` is that migration's FIRST CALLER, not its template — it still hand-assembles inline. **Contents are the commitment; the mechanism is not** — a mechanism is swappable, but an actor not captured at write time is gone. ⚠️ **The current mechanism is the activity log** (a `@lumenize/debug` line at the point of action, as `executeScopeDeletion` does), so this ADR imposes **no storage obligation on any component's schema** — discharge it by logging; never stand up an audit table to satisfy it. ⚠️ **No carve-out — the rule is uniform.** Where a record *also* serves as a same-actor dedup key, **derive the key from identity only** (`sub` + the complete `act` chain); never stringify the stored record, and never narrow the record to fit the key. `resources.ts:212` is the live instance: widening `changedBy` while keeping its stringify compare would break coalescing (a 1-hour window spans several 15-minute tokens → differing `jti`/`iat`), whereas a derived key is **identical** to today's behavior, since `{ sub, act }` is already all `changedBy` holds. Keep `profileId` (derived from `sub`) and `access` (asserted authority) OUT of the key. Resources is **not conformant yet** — a breaking storage change gated on the pre-alpha wipe (`nebula-pre-alpha.md` schema-surgery batch, item 6). Motivated by four mutually inconsistent caller shapes in one registry file (`setIdentityAdmin` records nothing at all). **Proposed 2026-07-28 — pending Larry's read.**
- **ADR-015 (Proposed)** — **scope authority flows strictly DOWNWARD, and only downward.** (1) *Downward is total and non-vetoable*: a principal whose `authScopePattern` covers a node has full authority over it and everything beneath; descendants — including a scope's own members — can never veto or attenuate an admin above them, and restraint for destructive actions is a **UI warning carrying decision-grade info**, never a refusal in the authorization layer. (2) *Upward is nil*: the bare `admin` bit is NEVER authority by itself — authority is always (`admin` ∧ pattern-covers-this-node). (3) *Admission ≠ authority*: being admitted upward is legitimate (a child reaching its parent for tenant-facing reads) and grants no authority there; which reads are tenant-facing is a per-method guard decision, never a narrowing of admission. Mechanism: `hasAdminOverScope`, delegated to by every guard (ADR-007). Written because the invariant was assumed everywhere and stated nowhere — **two opposite violations shipped** (the `access.admin` upward leak; `#computeDeletionPlan`'s downward veto) and a third was proposed while fixing the second. **Proposed 2026-07-21 — pending Larry's read.**

## Dependencies
- **Ask before installing any npm package.** Favor copy-paste-with-attribution over a dependency for <1000 SLOC (add an entry to `ATTRIBUTIONS.md` *and* a comment above the copied code).

### `package-lock.json` — commit it, never review it
**Commit the lockfile, always.** It is what makes `npm ci` reproducible, and it is already tracked. The friction is not *whether* to commit — it is that adding one workspace or one dep can re-resolve a few hundred lines of unrelated tree (measured 2026-08-03: adding one experiment workspace + 2 deps produced **1054 insertions / 939 deletions**, including packages nobody asked for). That churn is normal npm behaviour, not a symptom.

Standard practice, and what this repo does:
- **Treat it as generated output.** `.gitattributes` marks it `linguist-generated=true -diff`, so GitHub collapses it in PRs and `git diff` stays readable locally. **Review the `package.json` change; never read the lock diff.**
- **`npm ci` everywhere that isn't deliberately changing deps** — it installs *from* the lockfile and never writes it, so CI can't drift the tree.
- **Commit the lock in the same commit as the `package.json` that caused it.** A lockfile landing separately is unbisectable, and a `package.json` landing without it breaks the next `npm ci`.
- **Never hand-edit.** Sole exception, and it is a real one: **removing a workspace package** — surgically edit via JSON parse → stringify rather than a from-scratch regen ([[delete-workspace-package-lockfile]]).
- ⚠️ **Don't reach for root `overrides` to tame it** — see § *Toolchain bumps*: a *changed* override is silently ignored by every npm command, so maintaining one is worse than the problem.

⇒ When an agent's install churns the lock, the answer is **commit it with the change**, not to hand-prune it or leave it dirty for the human.

### Startup cost is the criterion — and it's WORK-AT-IMPORT, not size
**A DO is not a separate deployment** — its class is exported from the Worker bundle, so every DO instance pays for the *whole* Worker's import graph, including code it never touches. Cost is **per-Worker-project**: a dep added anywhere in `apps/nebula`'s graph taxes every DO in it, and moving the heavy import behind a subpath **does not help** while its importers still share the Worker. So "is this dep worth it?" is never a question about one package.

⚠️ **Size is a screening proxy, not the cause.** V8 pre-parses lazily and defers full compilation until a function is *called*, so a bundle that merely **defines** a lot is nearly free. What costs is code that **runs at module scope** — and it is almost always the dependency's, not ours: eager init tables (tsc's keyword/scanner/diagnostic catalogues), `new Map`/regex/`Object.freeze` of "constants", class field initializers and decorators, shim installation, wrangler's `keepNames` `__name()` wrapper per function definition, and the GC to collect it all.

Measured 2026-07-31 on the `do-cold-start-bundle-ab` arms: `ts-runtime-parser-validator` (9.2 MB) spends a 295 ms local startup window on **66 ms garbage collection**, ~104 ms of top-level init inside `deps.bundle.mjs` (tsc + typia), and ~15 ms in 18,298 `__name()` wrappers. That is why 2.7 MB → 9.2 MB costs **16×** startup for **3.4×** the bytes: the two bundles do different *amounts of work*, not proportional amounts. ⇒ **Never gate on byte count** — it would fire on `isomorphic-git` (684 KiB, 25 ms, harmless) and stay silent on a small package that builds a big table at import.

**Measure it — two commands, no deploy** (use `--workerBundle`; the direct `check startup` path misdetects a Worker as Pages and exits 1 on 4.113):
```sh
npx wrangler deploy --dry-run --outfile /tmp/w.bundle    # prints Total Upload
npx wrangler check startup --workerBundle /tmp/w.bundle  # → .cpuprofile
```
Read the `.cpuprofile` in `speedscope.app` (Left Heavy) or Chrome DevTools. **Self-time plateaus along the top edge are the cost**; tall narrow towers are deep call chains that cost nothing. A profile with single-digit samples means there is nothing to optimize. Local CPU ≠ Cloudflare's, so trust it for *relative* comparison, never as a predicted production number — for that, `wrangler deploy` reports a server-side `Worker Startup Time`. The summary line (bundle KiB, active/idle/GC split) needs wrangler ≥ 4.116, which is a toolchain-**triple** bump — see § Toolchain bumps, never `wrangler` alone.

⚠️ **Startup cost ≠ wake latency.** End-to-end DO `create` and `wake` also depend on eviction depth, which is **not predictable from any of this**: an identical 9.2 MB bundle measured 120 ms and 1,256 ms on repeat runs. Method and full tier data in `experiments/do-cold-start-bundle-ab/RESULTS.md` (2026-07-23, n=10).

## Sequential implementation — no parallel worktrees
One long-running branch, implemented sequentially. Never parallelize code-writing across worktrees, parallel PRs, or concurrent write-agents — in this solo workflow, merge/conflict cost exceeds any speedup. Parallel agents are for reading and verifying (review panels, verifiers), never for writing code concurrently. Worktree isolation is fine only for self-contained experiments whose code never merges back (next section); if a worktree's code would need to come back, don't use a worktree.

Empirical confirmation (§5.3.7 Nebula-frontend, the largest single-batch build): one file (`nebula-client.ts`) was threaded through 9 of ~24 phase commits, the phases formed a strict chain (engine → client → store → subscribe → e2e → deletions, where the deletion phase depends on *all* prior phases by construction), and at least one cross-phase dependency was invisible at plan time (a later phase fixed an earlier phase's code). Parallel writers would have N-way-merged the hot file for zero wall-clock gain — each phase was minutes of transcription. The only genuinely independent phases were two leaf-utility ports, exactly the cases where parallelism saves nothing. Not even a narrow exception is worth it.

## Experiments
`experiments/*` are point-in-time spikes, not maintained artifacts. Results live in the experiment's `RESULTS.md` / `FINDINGS.md` / blog post, not in keeping the code runnable. An experiment commonly breaks soon after it runs because we change the source it depended on — **that's fine; don't fix it.**
- ⚠️ **NEVER experiment outside `experiments/` — build a throwaway Worker there instead.** This includes *test* files and *test* workers under `packages/**` / `apps/**`: they look low-risk because "it's only a test," but they are shared, committed surface. Spin up a new `experiments/<name>/` with its own `package.json`, `wrangler.jsonc`, and Worker and **deploy that**, however much scaffolding it seems to duplicate. The experiment's own `package.json` also lets it declare heavy deps (`isomorphic-git`, a package barrel) that a real package must not take on — so this *removes* friction rather than adding it.
  - ⚠️ **The specific trap: adding a DO class to an ALREADY-DEPLOYED worker creates permanent registry debt.** Cloudflare keeps every DO class the worker ever deployed. Once you delete the experiment's class from source, the deployed worker holds a class the `exports` map no longer lists, and **the next deploy of that worker fails reconciliation** until someone adds a `"state": "deleted"` tombstone or dashboard-deletes it. The cleanup is therefore *not* symmetric with the setup — you cannot simply revert. Bit us 2026-07-22 on `nebula-browser-test` + `lumenize-mesh-browser-e2e` during the DO cold-start work.
  - Corollary: a deployed experiment worker also **drifts from source** the moment you revert (the deployed bundle keeps whatever you last pushed), so a shared test worker ends up in a state no one can reproduce from `git`.
  - **Name every deployed experiment Worker `experiment-<something>`.** They accumulate in the Cloudflare account and are indistinguishable from real projects at a glance — a `do-cs-nebula` arm reads alarmingly like the product. The prefix makes the throwaways obvious in the dashboard and safe to bulk-delete.
  - **Delete a throwaway experiment Worker from the DASHBOARD, not with `wrangler delete`.** A dashboard project-delete **also removes that Worker's DO namespaces**, so deleting the project is all you need — no ordering dance. `wrangler delete` leaves the namespaces orphaned ([[wrangler-delete-leaves-do-data]]), and there is no `wrangler durable-objects` command to clean them up afterward. Delete a namespace *individually* only when you're **keeping** the Worker and just retiring one class from it. (Confirmed on a 9-worker cleanup, 2026-07-23.)
- **Tracked by default.** `experiments/` is *not* git-ignored — just commit new experiment files like any other code (no `git add -f`). Only experiment-local generated output stays ignored (`node_modules`/`dist`/`.wrangler`/`coverage`/`__screenshots__`/`.dev.vars` via global rules, plus targeted `experiments/...` rules in `.gitignore` for any bulk-generated artifacts, as `experiments/tsgo-benchmarks/schemas/` does). (It used to be ignored — a footgun, since a `workspaces` entry pointing at a clone-absent dir breaks `npm install` on a fresh clone.)
- **New experiment**: create `experiments/<name>/` (own `package.json`, `wrangler.jsonc`, etc.), add `"experiments/<name>"` as an **individual** entry (not a glob) to the root `package.json` `workspaces` list, then `npm install` at the repo root. Individual entries are load-bearing — `experiments/*` would break `npm install` the moment one experiment references a renamed/deleted package.
- **Broken old / stale experiment**: remove its entry from `workspaces`, and once its results are captured elsewhere (task file / `RESULTS.md` / blog post) `git rm -r experiments/<name>` rather than letting it rot. Do **not** make it run again. The `workspaces` list holds only currently-active experiments; git tracks active + not-yet-pruned ones, so prune periodically.
- **Adopting a spike's result**: when a spike proves something works via specific build tooling, productionize that tooling into the real package *before* the integration phase — don't leave it in the experiment. (The tsc-bundling spike worked; the missing productionization broke every vitest-pool-workers test when Ontology was wired into Galaxy/Star. The live pattern: `packages/ts-runtime-parser-validator/scripts/bundle-tsc.mjs`, whose header is the canonical doc.)

## No build during development
Source runs directly — **never add or run a build step in the dev loop.** vitest transpiles Workers TypeScript on the fly; Node tooling is JS + JSDoc (no compile). A build happens **only at publish**. Reaching for a build during development is a recurring failure mode: it spawns doom loops chasing build caches, `dist/`-vs-`src/` confusion, and stale output. If something isn't working, the fix is never "build it."

## Toolchain bumps — `@cloudflare/vitest-pool-workers` is the knob, never `wrangler` alone
**`@cloudflare/vitest-pool-workers` depends on `wrangler` EXACTLY, 1:1, and drags `miniflare` with it** (0.18.5→4.111.0, 0.18.6→4.112.0, 0.18.7→4.113.0, 0.18.8→4.114.0). Every workspace here that declares `wrangler` also declares pool-workers — never one alone — so the repo is uniform **because pool-workers hard-pinned it** and npm deduped our `^` ranges onto that exact version. The declared `wrangler` range is therefore *documentation of a floor*, **not** the mechanism.

⇒ **Bumping `wrangler` on its own splits the tree**: our caret resolves to the newer version while pool-workers' nested dep stays pinned to the old one — two copies, the exact hazard the version-uniformity work exists to prevent (and the root-hoist footgun in `durable-objects.md` § DO class registration is what it feels like). Bump the pair together, and treat it as a **toolchain-triple** change: miniflare is the workerd runtime under every pool-workers test, so behavior can shift — budget a full-suite run and treat an unexplained new failure as signal, not flake.

⚠️ **Don't reach for root `package.json` `overrides` to force uniformity.** It *does* pin one version everywhere, but a **changed** override is silently ignored by `npm install`, `npm update`, `npm dedupe`, `--force`, and `--package-lock-only` alike — only deleting `package-lock.json` re-resolves it, so every bump becomes a full lockfile regeneration. Set-once is fine; maintaining it is worse than the problem. (Both behaviors verified in a scratch monorepo, 2026-07-27.)

**Enumerate over the `workspaces` list, not a `packages/*` glob** — `doc-test/*/*` is a workspaces entry and is easy to miss (`npm ls @cloudflare/vitest-pool-workers --all`). An experiment that declares `wrangler` *without* pool-workers has nothing pinning it forward, which is how stale experiments hoist an ancient wrangler to the repo root.

### The Node major and the CF triple are INDEPENDENT axes — bump them separately
**Baseline: Node 24 LTS ("Krypton").** Six surfaces carry it and must move in one sweep, or the lanes silently disagree: root `engines` · `.nvmrc` · `@types/node` (root + `tooling/check-examples` + `tooling/doc-testing`) · every `node-version:` in `.github/workflows/` · `apps/nebula/container/Dockerfile` (`node:24-slim`) · `experiments/computer-vfs-build/Dockerfile` (nodesource `node_24.x`).

⚠️ **A Node bump does NOT imply a toolchain-triple bump, and conflating them destroys your ability to read a failure.** wrangler/miniflare declare `node >=22.0.0`, so a Node major inside that floor costs the triple nothing — measured 2026-08-03: the entire suite went green on Node 24 with pool-workers/wrangler/miniflare **completely unchanged**, before a single dependency moved. Bumping both at once would have put a runtime major (miniflare 4→5) on the same commit as the Node major, so any red would be unattributable — the exact opposite of the "treat an unexplained failure as signal" rule above. **Establish the new Node on the pinned triple first, then bump the triple on its own budget.**

⚠️ **`@types/node` tracks the RUNTIME major, never "latest".** Types ahead of the runtime typecheck code against APIs that don't exist at runtime — a green `type-check` that ships a `TypeError`. The root pin had drifted to `^25` while the runtime was 22; Node 24 + `@types/node@^24` closes it.

⚠️ **npm 11 (bundled with Node 24) WARNS about lifecycle scripts but still RUNS them.** `npm warn allow-scripts … not yet covered by allowScripts` fires for `workerd`/`esbuild` on every install and reads exactly like a block — it is not. Verified 2026-08-03 with a sentinel postinstall that wrote a marker file: the marker appeared. Do **not** "fix" this by adding an `allowScripts` allowlist or re-running installs; treat the warning as noise **until npm actually enforces it**, at which point `npm ci` in CI is what breaks (per §4, re-derive then — don't pre-build the guard now). Note the binaries would survive enforcement anyway: workerd/esbuild ship theirs via **optional platform deps**, and the postinstall is only the fallback.

## Releases
All packages publish together with synchronized versions (Lerna); publish scripts repoint `package.json` from `src/` to `dist/`, then revert (the only time a build runs). Favor breaking changes over technical debt — they bump major semver and need the next release flagged. Use `/release-workflow`.

## Semantic code search
For conceptual searches ("where do we validate JWTs", "what handles rate limiting"), use Probe: `npx -y @probelabs/probe search "<query>" [path]` — AST-aware, fully local, returns whole functions/classes. `Grep` stays the default for literal strings and symbols.

## Symbol renames — grep the BARE identifier to verify
Probe/Grep *find*; they don't *rename*. A rename done with a text replace (`sed`/`perl`) can't tell the symbol from a same-spelled string, comment, or unrelated identifier — so **after any `Old`→`New` rename, grep the bare identifier (`grep -rn '\bOld\b'`), not just the form you replaced.** A `'Old'`→`'New'` quoted-literal replace silently misses **member/type-position access** (`x.Old`, `rels.Old.field`, `interface X extends Old`) and doc comments; those survive, compile, and only surface as a runtime/test failure (empirically bit the `Turn`→`Message` rename *twice* — `rels.Turn.session`, `.Turn?.session`). The bare-identifier grep should return only the refs you *intend* to keep (deliberately-different concepts — e.g. `TurnRecord`, `trackTurn`), which you then eyeball. For a **pure symbol** rename, an LSP/`ts-morph` rename is scope+type-correct and strictly better than `sed` — but it still can't touch **string literals coupled to a name by convention** (`typeName: 'Old'`) or comments, so the grep-verify is irreducible regardless of the replace tool.
