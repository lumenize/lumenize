# Working in This Repo

## Task files
Work is tracked in `tasks/`:
- `tasks/backlog.md` — small tasks and ideas
- `tasks/[project-name].md` — active multi-phase projects
- `tasks/on-hold/` — designed but paused, expected to resume
- `tasks/icebox/` — parked indefinitely, no planned return (colder than on-hold)
- `tasks/archive/` — completed projects + point-in-time decision/research records (`decision-*.md`). **Frozen on entry — an archived file MUST NOT be updated** (no link fixups, no terminology syncs, no code-drift corrections); sole exception: a dated superseded banner at the top. See `tasks/README.md`.

Use `/task-management` to choose docs-first vs task-file-first when starting a project, then `/write-task` to draft the file (design intent first, hand-reviewed, then phases). When the plan changes mid-stream from what you learn in earlier steps, you MUST propose updates to the task file, and MUST summarize what changed after each step. **Not every change needs a task file** — process/organizing tweaks (editing rules, moving content) can be done directly. See `tasks/README.md` for templates.

### Referring to things across files — name them, don't number them
**You MUST cite the durable COMMITMENT, not whichever file currently implements it.** Task files move, get renumbered, get absorbed, get archived; an ADR or a rule does not. A task file that justifies itself by pointing at a sibling task file inherits that file's churn — and reads as circular when the sibling is itself mid-restructure. Bit 2026-07-28: `/mint-narrower-token` justified a guard by citing `identity-mint §4`, when the commitment was ADR-012 all along and §4 was only its current home.

**Across a file boundary, a section MUST be referred to by NAME.** Numbers are fine *inside* a file, and are load-bearing where they encode order (phases, gates — `/build-task` transcribes phase order). But a bare `§4` in another file carries no meaning, is unfindable without opening that file, and **rots**: `identity-mint` renumbered the moment its former §3 moved out, and in one file `§4` meant two different sections depending on which filename preceded it. Give sections meaningful names and cite those; add the number only as a convenience alongside.

**A section reference MUST be written `§ *Name*`** — italic, never bold, and whether or not the section is in the same file. Bold is a claim on a skimmer's attention, and a pointer *away* from the prose has the weakest claim there is; the `§` then says "section" so the italics need not be inferred from context, and it makes every cross-reference in the repo greppable with one character. Already the de facto convention (~160 uses when this was written); it is stated here because `docs/vision/auth.md` drifted to bold and nothing caught it. An anchor link is the tempting alternative and is worse: rendered, a link pulls *more* attention than bold, and the generated anchor for a heading with backticks or punctuation is not predictable from the text.

⚠️ **A numbered handle others are expected to cite MUST be APPEND-ONLY** — assigned once and never reused or renumbered when a sibling is inserted or removed (`D7`, `ADR-016`, `calibration.md` §3(d)). That is what makes it safe to cite; a section number, which shifts under insertion, is not.

⚠️ **A task-file handle MUST NOT ship in SOURCE.** `S4`, `D12`, `Phase 3` are a task file's native currency and are fine *inside* it — but code outlives the file that specified it, and that file archives. A comment citing `D12` is unresolvable the moment it does, which is the cross-file rule above with a worse blast radius: nobody re-reads a five-year-old code comment against a frozen task file. **In source, you MUST cite an ADR, a rule file, or nothing** — most handles reduce to one of those, and the rest are a clause of prose (`nebula-auth`'s `schemas.ts` already writes them that way — see `SCOPES_SCHEMA`'s JSDoc, which states the existence-is-independent-of-membership invariant as a clause of prose and cites no handle at all). ⇒ **Conversion MUST happen at transcription, as a phase criterion** — never as a cleanup step, which is the shape that gets skipped — and you MUST check it: `grep -nE '\b[SD](1[0-9]|[1-9])\b'` over the changed files, then eyeball (`S3` also spells a storage product). Where a long rationale genuinely has no ADR home, cite the archived path by name; archived files are frozen, so that pointer is stable.

⚠️ **Another file's COUNTS or DATES MUST NOT be restated — and a pointer SHOULD be preferred to a summary.** Distinct from the rule above, and it rots for a different reason: not that the handle moves, but that **the source keeps growing while the copy does not**. An inventory (*"S1–S7 inherited, D1–D13 decided"*) and a status date (*"decisions RESOLVED 2026-07-26"*) are false the moment the source gains a row, and nothing makes them fail loudly — they read authoritative while wrong. Bit 2026-08-02: the pre-alpha master plan's entry point for the identity work carried a stale inventory, a stale date, **and a headline naming the design that file had explicitly rejected**, which had already propagated to a backlog row. ⇒ A cross-file reference MUST state the **target shape in one line** and **point by section name**; anything a reader needs beyond that, they get by following the link. **A summary has no derivation, so nothing updates it** — if you find yourself restating a sibling's reasoning, you are creating the next stale copy. (Corollary: a pointer needs no owner, which is why "add it to a sweep list" is the weaker fix — a sweep list is itself a summary.)

⚠️ **A VERBATIM QUOTATION of another file is the same defect wearing a more convincing costume, and it MUST NOT be used as evidence.** A quote earns its persuasive force from being *real* — "here is the actual line that does this well" — so when the source is reworded the quote silently becomes an invented example, and a reader who greps for it finds nothing. Nothing updates it and nothing fails when it drifts, exactly as with a restated count. **Cite the SYMBOL and characterise it in a clause** (`see X's JSDoc, which states the invariant as prose`) — that survives any rewording, because the wording was never the load-bearing part. Bit 2026-08-04: this very section quoted `schemas.ts` as its model of handle-free prose, and the same session's schema work rewrote that line — leaving an always-loaded rule quoting a sentence that no longer existed, in both its qualifier and its table name. ⚠️ The phase criterion that should have caught it (*"no standing-guidance statement is falsified"*) did not, because "statement" reads as *a claim* and this was *a quotation* — so when you sweep standing guidance, grep for quoted fragments of files you touched, not only for claims about them.

## Design-first: diagrams before prose when the design is tangled
When a multi-node/mesh design gets tangled — or when task files have drifted into mutual contradiction — **you SHOULD lead with sequence diagrams (a participant/cast model + per-flow diagrams), not prose.** Prose hides contradictions; a diagram's participants + ordering + gating force precision and make the drift visible (this is what the Phase-3.5 review kept surfacing, and what `tasks/nebula-dev-flows.md` was built to fix — Larry: "my mind works better with sequence diagrams than prose"). Nail the cast + naming + flows *with the user* first, **then** rewrite the prose/task files to conform. Proactively offer this when you sense the design space is tangled. Mermaid traps: no `;` in `Note` text (statement separator → parse error); no `#` in ANY diagram text — participant label, message, or note (`#` starts an HTML-entity escape like `#35;`, so `participant D as #dispatchEnvelope` renders a **blank actor box**; bitten 2026-07-02 drawing methods-as-actors with `#`-private names — write `dispatchEnvelope (private)`; do NOT "escape" via `#35;`, which trips the `;` check); a long `Note over` anchored on the **leftmost** actor(s) overflows off-canvas and clips — span more actors (`Note over A,C`); solid `->>` = call/request, dashed `-->>` = response/return/push. **After every Mermaid write/edit, you MUST run the mechanical render-safety check before considering it done** — knowing the traps is NOT enough on its own (this guidance was already in place when the `;`-in-`Note` bug got *reintroduced right after being fixed*; you can't visually render from here, so verify with the grep, then have the human eyeball the actual render). Extract the fenced `mermaid` blocks and grep for the killer glyphs `;` `#` — it should print nothing:

```sh
awk '/[`][`][`]mermaid/{m=1;next} /[`][`][`]/{m=0} m' <file> | grep -E '[;#]' || echo "clean"
```

(Applies equally to Mermaid in `website/**` docs — see `documentation.md`.)

**Stray invisible characters (U+00A0 non-breaking space, U+0000 NUL):** two vectors, same class of bug — a byte you can't see in the rendered diff. (1) Some WYSIWYG markdown editors (e.g. Typora) silently insert **NBSP** on edit; they break exact-match string edits (the `Edit` tool can't match an "identical" line) and can break rendering. (2) An **agent `Edit`/`Write` can inject a NUL** into a string literal that reads as a space in the diff — it compiles and runs (NUL is a valid string char), so it passes type-check *and* tests; the `/build-task` verifier panel caught one as the separator inside a `` `${a} ${b}` `` dedup key.

⚠️ **`grep` CANNOT detect the NUL — it reports nothing for a file it considers binary, which is exactly what a NUL makes it.** The old check here (`grep -nP '[\xc2\xa0\x00]' <file>`) therefore *passes silently on a corrupt file*; bitten 2026-07-21, where the only symptom was an unrelated `grep` mysteriously returning empty on a file `Read` showed fine. You MUST use a **byte count**, which cannot be fooled:

```sh
tr -cd '\000' < <file> | wc -c          # NUL count — must be 0
grep -c $'\xc2\xa0' <file>              # NBSP count — must be 0 (grep IS fine for NBSP)
file <file>                             # a source file reporting "data" instead of "text" = NUL
```

Strip with `perl -i -pe 's/\xc2\xa0/ /g; s/\x00/ /g' <file>`.

⚠️ **The invisible character MUST NOT be put *literally* into the check command.** It MUST be written as an explicit escape (`b'\x00'`, `$'\xc2\xa0'`), never by pasting the character itself — a pasted NBSP silently degrades to a plain space in transit, so the check then matches every file with any space and reports the whole tree dirty (also bitten 2026-07-21, in the very command written to catch the first bug). For a whole-tree sweep, count bytes in a script rather than grepping:

```sh
python3 -c "import pathlib,subprocess as s
for f in [l.split(maxsplit=1)[1] for l in s.run(['git','status','--short'],capture_output=True,text=True).stdout.splitlines()]:
    p=pathlib.Path(f)
    if p.is_file():
        b=p.read_bytes()
        if b.count(b'\x00') or b.count(b'\xc2\xa0'): print('DIRTY', f)"
```

## Evaluating alternatives: weigh the unlearning tax, not just build cost
When you compare options and **recommend** one (interim-vs-target, build order, scope cut, design choice), the **unlearning tax** MUST be an explicit criterion alongside build cost — and usually the deciding one. The bottleneck is **reviewer time**, not lines of code. A known-temporary artifact ("interim") that lands in a surface re-read every session — code, docs, task files, agent memory — gets re-anchored on as "the model" and must be **unlearned, repeatedly, at the reviewer's expense.** (Empirically the single largest drain on pre-alpha review time has been unlearning the `acme.app.dev` interim — see the `interim-unlearning-tax` memory.)

You MUST score each candidate on this, and MUST say so when you recommend:
- **Interim cost ≈ (how many re-read surfaces reflect it) × (its lifetime) × (sessions over that life)** — paid in the bottleneck reviewer's correction time, *not* in build size. An option that is cheaper to *build* but seeds a durable, widely-reflected interim is usually the **more expensive** choice. Recommend accordingly, and name this tax in the trade-off.
- **Building the target SHOULD be preferred over a lean interim _when the target is pinnable now_.** A half-pinned "final" becomes its own interim and costs the same tax → the move is **pin → purge → build**, not rush-to-final. You MUST NOT over-pin either: pin only what the current step needs to stop describing the model wrongly; leave genuinely-later mechanics as clearly-fenced "not yet built" pointers (not interims).
- ⚠️ **A TEST IS A CONSUMER — and an interim built to make tests runnable ossifies as hard as production code.** This is the clause most often got wrong, in the *conservative* direction. When judging "is there a present consumer," a test we need today counts: if a test would exercise the real mechanism, that is a consumer, and building the real thing beats building a stand-in for it. **Every test written against a stand-in must also be unlearned**, so a mock/fixture/shortcut is not the cheap option — it is the same ossification with the cost hidden in the test suite.
  - **`it.skip` SHOULD be preferred over an ossifying stand-in.** Skipping defers *one* test; a mock creates an artifact that N future tests anchor to. (See `testing.md` § Deferring ≠ deleting.)
  - **Case study — the login shortcuts.** Test-mode mints were used instead of the real login loop to save a round trip on a mechanism *we had already built*. The cost: (1) **fidelity** — the shortcut diverged from the real path, so real bugs got through; (2) **ossification** — every fixture anchored to it, and un-anchoring took a whole phase; (3) **delay** — it deferred building what the feature actually needed to be *usable*, not merely low-fidelity testable. Weigh all three, not just the round trip.
  - **The asymmetry that decides it:** a slightly-wrong thing you built early is usually *cheaper to fix* than an interim is to overcome, because the interim has consumers and the wrong design mostly has a shape. Favor **the goal** (a product someone pays for) over **the milestone** — a milestone is a checkpoint, not the thing being built.
- **YAGNI gates capability, never generality.** *Whether* to build a capability now is a scope question — push back when there is no present consumer *of any kind, tests included* (see above). *How* to shape a capability already in scope is **not**: the generic form that solves today's problem without foreclosing tomorrow SHOULD be preferred, and point solutions / tier-or-case special-casing MUST be treated as the anti-pattern. **Cost test:** when the general form costs the **same or less** than the narrow one (removing a restriction, widening a parameter, moving a flag from the batch to the entry), the narrow one is strictly worse — it is a lean interim someone must later unlearn. Reserve the objection for a general mechanism costing *materially more* than the immediate need (a new subsystem, carrier, or protocol). Bit 2026-07-19: a proposal to restrict an invite's `scopeAdmin` flag to one scope tier would have **added** a tier check to a mechanism whose reach invariant was already uniform across every tier — more code, less capability, and an interim to unlearn.
- **When an interim is genuinely unavoidable, its tax MUST be minimized:** single-source it (one constant, not scattered), label it `TEMP → target=X` at every site, and record it (memory / task file) as a **dead interim, model is X** — never as the model. Task files MUST state the **target in present tense**; the interim is a fenced, dated exception.
- **Self-check before trusting current code:** reading any default / scope / identity / config value, you MUST ask "**target or interim?**" and MUST NOT assume the current code is the model. **This extends to BEHAVIORS/ENDPOINTS, not just values:** during a rewrite to a pinned new model, a code path that *exists in the old code with passing tests* is NOT thereby validated for the new model — it MUST be conformed to the pinned model or cut, and a test that **enshrines the old shape** MUST NOT be carried (a green test asserting deprecated behavior is a false-confidence trap the reviewer must then catch). Bit 2026-07-13: a rewrite preserved the old open, identity-minting `claimStar` (mirroring `claimUniverse`) though the task pinned "Star = parent-Galaxy admin, wildcard-managed" — reintroducing a stranger-claims-a-child escalation, with new tests that codified it as intended (caught by the `/build-task` verifier panel, not the suite).

## Architecture commitments (ADRs)
`docs/adr/` holds the few repo-shaping commitments — decisions that span packages and survive mechanism swaps (`docs/adr/README.md` has the bar; adding an ADR means adding its one-liner here). `/review-task` reads the full files; these one-liners are the always-loaded constraints. ⚠️ **A line here is a POINTER, not a summary — one sentence naming the commitment, plus any tripwire that would bite before you thought to open the ADR. Argument, evidence, measurements, and worked examples belong in the ADR.** (Budget stated in `docs/adr/README.md` § *The index line*; it exists because this section grew to 3,273 words of restated reasoning before anyone noticed.)
- **ADR-001** — TypeScript types ARE the schema language; never introduce a second one (Zod, JSON Schema, …). The mechanism (typia) is swappable; the principle is the commitment.
- **ADR-002** — every surface (wire, storage, validation, diff/patch, history) round-trips the full structured-clone value space, incl. cycles, aliases with identity, Errors, Web API types. A JSON-only surface is never acceptable.
- **ADR-003** — mesh flows are one-way messages carrying continuations; **no node holds a reply Promise open across a hop** (tabs sleep, WS reconnects, DOs hibernate — a held Promise strands). Request/response *semantics* are fine, via a continuation. User-land awaiting is **Client-only** (`callAsync`). No RpcTarget/Cap'n Web sessions.
- **ADR-004** — resources are Snodgrass-style snapshot sequences; history is the substrate. No destructive writes; "current" queries honor the `END_OF_TIME` sentinel.
- **ADR-005** — optimistic concurrency: forward-only eTags prove currency AND provide idempotency (`newETag` replay detection); no locks, no dedupe ledger. Non-monotonic checks (permissions, not-found) stay inside the transaction.
- **ADR-006** — resources reference each other by id (FK), never by embedding; a field typed as another ontology type is rewritten to `string`/`string[]` in the write shape. Related resources are separate ops in one atomic transaction (client supplies every id). Embedding where an id belongs is a **loud error**.
- **ADR-007 (Accepted)** — every node type shares one **narrow comms + guards core** (`lmz.call`, `lmz.ctn`, `callContext`, `onBeforeCall`, `@mesh()`) by **composition**, never reimplemented. Storage/alarms/`onStart`/`fetch` are per-type **capabilities, NOT the invariant** — and a driven container is a capability too (raw `ctx.container` on a `LumenizeDO`), never a node type or base class.
- **ADR-008 (Accepted)** — within a Star, the full org/permission tree — nodes, edges, grants, **grantee identity**, and **presence** — is visible to every member. **Visibility ≠ capability**: enforcement is at the point of action, never secrecy of the tree. **No per-subtree hiding** (need invisibility? separate Star); the denied-node set is **always disclosed**. Cross-scope profile reads are ADR-012's, not this one's.
- **ADR-009 (Accepted)** — **real email login is the DEFAULT auth path**, and what design reasoning grounds on; never conclude system behavior from a synthetic path. Ladder, most-preferred first: (1) real login, (2) test-mode server issuance, (3) client-side mint = last resort, justify per-site, (4) negative-control wrong-shape mints. ⚠️ **Speed is never a reason to drop a rung** — the real loop is ~1s, measured; the ADR says which older number not to re-cite.
- **ADR-010 (Accepted)** — **keys are random opaque values, statistically unique WITHOUT coordination** (mintable anywhere, offline-safe, idempotent). Never key off a natural/mutable attribute (email/slug/name) or an auto-increment/rowid counter; the axis is **coordination, not client-vs-server**. Companion **replication rule**: a *mutable* attribute has one authoritative source and every other copy is a cache owing an explicit convergence mechanism.
- **ADR-011 (Accepted)** — persisted/wire **timestamps are ISO 8601 UTC strings** (`…T…Z`, ms precision, fixed-width), SQLite `TEXT`, string-compared. **Never epoch `number`.** End-of-time sentinel `9999-01-01T00:00:00.000Z`. Carve-out: protocol-mandated formats keep their spec (JWT, HTTP).
- **ADR-012 (Accepted)** — a person's PUBLIC profile fields are readable/subscribable by **any authenticated caller holding the `profileId`**, across every scope boundary — no reach gate, no registry read on the read path; holding the handle IS the capability. Generalizes ADR-008 globally. **Exactly two capability levels, no per-field roles**; private-by-default is **derived** from an allow-list, never by subtracting known-private keys. ⚠️ **Two tripwires, both load-bearing against a scope authority that can be MANUFACTURED** — the scoped-admin branch requires an **ACCEPTED** membership (and *not* `emailVerified`), and the owner branch requires **`!claims.act`**. Read the ADR before touching either.
- **ADR-013 (Accepted)** — **`sub` is the only KEY; `profileId` hangs off the ADDRESS and is never keyed on** — a column on the `Emails` row, never a join table, which is what makes "one human, one profile" structural rather than emergent. Resource records key on `sub` only, so a future `sub`-unification stays additive. ⚠️ **"Never copied" = never as the KEY, not absent**: exactly two licensed denormalizations (self-healing JWT/KV; write-time-pinned immutable attribution) and no others. **Authz scope-sets resolve live — a stored one is a security bug.**
- **ADR-014 (Proposed)** — a container node **orchestrates from its own companion DO, never across a hop from a sibling**; the companion DO IS the hub. Generalizes to: don't distribute a **liveness-coupled** workflow across independently-hibernating nodes. Hops stay fine where liveness is *not* coupled. Distinct from ADR-007 — that is uniformity, this is *placement*.
- **ADR-015 (Proposed)** — **dominion flows strictly DOWNWARD, and only downward**; downward is total and non-vetoable, so restraint for destructive actions is a **UI warning, never an authorization refusal**. ⚠️ `dominion` and `passage` are RESERVED terms defined in ADR-015 § *Terminology*, which states both as predicates — read them there rather than reconstructing them, because the two obvious paraphrases are both wrong: **dominion is not the bare `scopeAdmin` bit** (it is that bit ∧ `isAtOrAbove`, so the scope is always the bound — and the reserved platform scope is the ROOT of the tree, so `isAtOrAbove` covers a superuser without a special arm), and **passage is not the upward arm** (it is the union, so it runs downward too, priced at dominion). They replaced `authority` and `admission` on 2026-08-09 because the general words meant four things and the ambiguity shipped real bugs; **`reach` is not to become their umbrella noun** — it stays a verb. Do not reintroduce any of the three.
- **ADR-016 (Proposed)** — every action that **destroys or removes state, changes a principal's authority, or establishes a session** records the **FULL verified claims** of the acting token (`sub` + the complete `act` chain + `profileId` + `access`), write-time-pinned and immutable — because authz keys off `sub`, so a `sub`-only record names the person acted *upon* as the actor. **Reversibility is not an exemption.** ⚠️ **ONE shared projection produces every record**, and conformance is stated structurally, never as a caller list. The stored `access` is asserted history — **never read back as an authz input**. ⚠️ Ratification **deferred past pre-alpha**, jointly with ADR-019 — do not ratify at `/build-task`.
- **ADR-017 (Proposed)** — **a URL one person shares takes the recipient to the same page AND the same view state.** What you are *looking at* (scope, selection, tab, filters, sort, paging) rides the URL; what you are *doing* (scroll, hover, focus, drafts) does not. ⚠️ The URL names WHAT, **never permission to look** — no credentials or personal data; authz is re-evaluated on arrival. ⚠️ The boundary is **narrower than the reflex wants**: a `profileId` in a URL is fine. Test: *does it reveal anything NOT already public?* Scope includes the codegen scaffold, so generated apps inherit it.
- **ADR-018 (Proposed)** — **a global singleton DO is the system's scarce resource; state and requests default to OFF it.** One DO is a hard, non-sharding ceiling (10 GB; low-thousands rps at best — the ADR carries the measurements) and passing it arrives as an outage, not a warning. The **only** qualifying reasons are **global uniqueness** and **strong consistency at the moment of decision**. Prefer: derive it → put it where it scales → the singleton. Whatever qualifies owes two things: never a per-request path that scales with user activity, and a **stated bounded lifetime**.
- **ADR-019 (Proposed)** — **ADR-016's read-side MIRROR: any artifact derived from resource reads records the ids of what it read ("observations"), immutably at write time, and EVERY subsequent reader is authorized against them, LIVE.** Our security claim is per-*asker*, but an answer is persisted and re-read, so the artifact outlives the authorization that produced it. ⚠️ **Store the REFERENCES, never the VERDICT** — the whole boundary against ADR-016. **Capture is the commitment; the policy on top is not.** ⚠️ Ratification deferred past pre-alpha, jointly with ADR-016.

## Dependencies
- **You MUST ask before installing any npm package.** Copy-paste-with-attribution SHOULD be favored over a dependency for <1000 SLOC (add an entry to `ATTRIBUTIONS.md` *and* a comment above the copied code).
- Licenses MUST be permissive (MIT, Apache-2.0, BSD-3-Clause, ISC). **Fastest startup** SHOULD be preferred over fastest steady-state, as SHOULD strongest Cloudflare Workers compatibility. Nothing MAY be installed globally.

### `package-lock.json` — commit it, never review it
**The lockfile MUST be committed, always.** It is what makes `npm ci` reproducible, and it is already tracked. The friction is not *whether* to commit — it is that adding one workspace or one dep can re-resolve a few hundred lines of unrelated tree (measured 2026-08-03: adding one experiment workspace + 2 deps produced **1054 insertions / 939 deletions**, including packages nobody asked for). That churn is normal npm behaviour, not a symptom.

Standard practice, and what this repo does:
- **Treat it as generated output.** `.gitattributes` marks it `linguist-generated=true -diff`, so GitHub collapses it in PRs and `git diff` stays readable locally. **You MUST review the `package.json` change, and MUST NOT read the lock diff.**
- **`npm ci` MUST be used everywhere that isn't deliberately changing deps** — it installs *from* the lockfile and never writes it, so CI can't drift the tree.
- **The lock MUST be committed in the same commit as the `package.json` that caused it.** A lockfile landing separately is unbisectable, and a `package.json` landing without it breaks the next `npm ci`.
- **It MUST NOT be hand-edited.** Sole exception, and it is a real one: **removing a workspace package** — surgically edit via JSON parse → stringify rather than a from-scratch regen ([[delete-workspace-package-lockfile]]).
- ⚠️ **Root `overrides` MUST NOT be reached for to tame it** — see § *Toolchain bumps*: a *changed* override is silently ignored by every npm command, so maintaining one is worse than the problem.

⇒ When an agent's install churns the lock, the answer is **commit it with the change**, not to hand-prune it or leave it dirty for the human.

### Startup cost is the criterion — and it's WORK-AT-IMPORT, not size
**A DO is not a separate deployment** — its class is exported from the Worker bundle, so every DO instance pays for the *whole* Worker's import graph, including code it never touches. Cost is **per-Worker-project**: a dep added anywhere in `apps/nebula`'s graph taxes every DO in it, and moving the heavy import behind a subpath **does not help** while its importers still share the Worker. So "is this dep worth it?" is never a question about one package.

⚠️ **Size is a screening proxy, not the cause.** V8 pre-parses lazily and defers full compilation until a function is *called*, so a bundle that merely **defines** a lot is nearly free. What costs is code that **runs at module scope** — and it is almost always the dependency's, not ours: eager init tables (tsc's keyword/scanner/diagnostic catalogues), `new Map`/regex/`Object.freeze` of "constants", class field initializers and decorators, shim installation, wrangler's `keepNames` `__name()` wrapper per function definition, and the GC to collect it all.

Measured 2026-07-31 on the `do-cold-start-bundle-ab` arms: `ts-runtime-parser-validator` (9.2 MB) spends a 295 ms local startup window on **66 ms garbage collection**, ~104 ms of top-level init inside `deps.bundle.mjs` (tsc + typia), and ~15 ms in 18,298 `__name()` wrappers. That is why 2.7 MB → 9.2 MB costs **16×** startup for **3.4×** the bytes: the two bundles do different *amounts of work*, not proportional amounts. ⇒ **You MUST NOT gate on byte count** — it would fire on `isomorphic-git` (684 KiB, 25 ms, harmless) and stay silent on a small package that builds a big table at import.

**Measure it — two commands, no deploy** (use `--workerBundle`; the direct `check startup` path misdetects a Worker as Pages and exits 1 on 4.113):
```sh
npx wrangler deploy --dry-run --outfile /tmp/w.bundle    # prints Total Upload
npx wrangler check startup --workerBundle /tmp/w.bundle  # → .cpuprofile
```
Read the `.cpuprofile` in `speedscope.app` (Left Heavy) or Chrome DevTools. **Self-time plateaus along the top edge are the cost**; tall narrow towers are deep call chains that cost nothing. A profile with single-digit samples means there is nothing to optimize. Local CPU ≠ Cloudflare's, so it MAY be trusted for *relative* comparison and MUST NOT be cited as a predicted production number — for that, `wrangler deploy` reports a server-side `Worker Startup Time`. The summary line (bundle KiB, active/idle/GC split) needs wrangler ≥ 4.116, which is a toolchain-**triple** bump — see § Toolchain bumps, never `wrangler` alone.

⚠️ **Startup cost ≠ wake latency.** End-to-end DO `create` and `wake` also depend on eviction depth, which is **not predictable from any of this**: an identical 9.2 MB bundle measured 120 ms and 1,256 ms on repeat runs. Method and full tier data in `experiments/do-cold-start-bundle-ab/RESULTS.md` (2026-07-23, n=10).

## Sequential implementation — no parallel worktrees
One long-running branch, implemented sequentially. Code-writing MUST NOT be parallelized across worktrees, parallel PRs, or concurrent write-agents — in this solo workflow, merge/conflict cost exceeds any speedup. Parallel agents are for reading and verifying (review panels, verifiers), and MUST NOT write code concurrently. Worktree isolation MAY be used only for self-contained experiments whose code never merges back (next section); if a worktree's code would need to come back, a worktree MUST NOT be used.

Empirical confirmation (§5.3.7 Nebula-frontend, the largest single-batch build): one file (`nebula-client.ts`) was threaded through 9 of ~24 phase commits, the phases formed a strict chain (engine → client → store → subscribe → e2e → deletions, where the deletion phase depends on *all* prior phases by construction), and at least one cross-phase dependency was invisible at plan time (a later phase fixed an earlier phase's code). Parallel writers would have N-way-merged the hot file for zero wall-clock gain — each phase was minutes of transcription. The only genuinely independent phases were two leaf-utility ports, exactly the cases where parallelism saves nothing. Not even a narrow exception is worth it.

## Experiments
`experiments/*` are point-in-time spikes, not maintained artifacts. Results live in the experiment's `RESULTS.md` / `FINDINGS.md` / blog post, not in keeping the code runnable. An experiment commonly breaks soon after it runs because we change the source it depended on — **that's fine, and it MUST NOT be fixed.**
- ⚠️ **You MUST NOT experiment outside `experiments/` — build a throwaway Worker there instead.** This includes *test* files and *test* workers under `packages/**` / `apps/**`: they look low-risk because "it's only a test," but they are shared, committed surface. Spin up a new `experiments/<name>/` with its own `package.json`, `wrangler.jsonc`, and Worker and **deploy that**, however much scaffolding it seems to duplicate. The experiment's own `package.json` also lets it declare heavy deps (`isomorphic-git`, a package barrel) that a real package must not take on — so this *removes* friction rather than adding it.
  - ⚠️ **The specific trap: adding a DO class to an ALREADY-DEPLOYED worker creates permanent registry debt.** Cloudflare keeps every DO class the worker ever deployed. Once you delete the experiment's class from source, the deployed worker holds a class the `exports` map no longer lists, and **the next deploy of that worker fails reconciliation** until someone adds a `"state": "deleted"` tombstone or dashboard-deletes it. The cleanup is therefore *not* symmetric with the setup — you cannot simply revert. Bit us 2026-07-22 on `nebula-browser-test` + `lumenize-mesh-browser-e2e` during the DO cold-start work.
  - Corollary: a deployed experiment worker also **drifts from source** the moment you revert (the deployed bundle keeps whatever you last pushed), so a shared test worker ends up in a state no one can reproduce from `git`.
  - **Every deployed experiment Worker MUST be named `experiment-<something>`.** They accumulate in the Cloudflare account and are indistinguishable from real projects at a glance — a `do-cs-nebula` arm reads alarmingly like the product. The prefix makes the throwaways obvious in the dashboard and safe to bulk-delete.
  - **A throwaway experiment Worker MUST be deleted from the DASHBOARD, never with `wrangler delete`.** A dashboard project-delete **also removes that Worker's DO namespaces**, so deleting the project is all you need — no ordering dance. `wrangler delete` leaves the namespaces orphaned ([[wrangler-delete-leaves-do-data]]), and there is no `wrangler durable-objects` command to clean them up afterward. Delete a namespace *individually* only when you're **keeping** the Worker and just retiring one class from it. (Confirmed on a 9-worker cleanup, 2026-07-23.)
- **Tracked by default.** `experiments/` is *not* git-ignored — just commit new experiment files like any other code (no `git add -f`). Only experiment-local generated output stays ignored (`node_modules`/`dist`/`.wrangler`/`coverage`/`__screenshots__`/`.dev.vars` via global rules, plus targeted `experiments/...` rules in `.gitignore` for any bulk-generated artifacts, as `experiments/tsgo-benchmarks/schemas/` does). (It used to be ignored — a footgun, since a `workspaces` entry pointing at a clone-absent dir breaks `npm install` on a fresh clone.)
- **New experiment**: create `experiments/<name>/` (own `package.json`, `wrangler.jsonc`, etc.), add `"experiments/<name>"` as an **individual** entry — a glob MUST NOT be used — to the root `package.json` `workspaces` list, then `npm install` at the repo root. Individual entries are load-bearing — `experiments/*` would break `npm install` the moment one experiment references a renamed/deleted package.
- **Broken old / stale experiment**: remove its entry from `workspaces`, and once its results are captured elsewhere (task file / `RESULTS.md` / blog post) `git rm -r experiments/<name>` rather than letting it rot. It MUST NOT be made to run again. The `workspaces` list holds only currently-active experiments; git tracks active + not-yet-pruned ones, so prune periodically.
- **Adopting a spike's result**: when a spike proves something works via specific build tooling, that tooling MUST be productionized into the real package *before* the integration phase, and MUST NOT be left in the experiment. (The tsc-bundling spike worked; the missing productionization broke every vitest-pool-workers test when Ontology was wired into Galaxy/Star. The live pattern: `packages/ts-runtime-parser-validator/scripts/bundle-tsc.mjs`, whose header is the canonical doc.)

## No build during development
Source runs directly — **a build step MUST NOT be added to or run in the dev loop.** vitest transpiles Workers TypeScript on the fly; Node tooling is JS + JSDoc (no compile). A build happens **only at publish**. Reaching for a build during development is a recurring failure mode: it spawns doom loops chasing build caches, `dist/`-vs-`src/` confusion, and stale output. If something isn't working, the fix is never "build it."

## Toolchain bumps — `@cloudflare/vitest-pool-workers` is the knob, never `wrangler` alone
**`@cloudflare/vitest-pool-workers` depends on `wrangler` EXACTLY, 1:1, and drags `miniflare` with it** (0.18.5→4.111.0, 0.18.6→4.112.0, 0.18.7→4.113.0, 0.18.8→4.114.0). Every workspace here that declares `wrangler` also declares pool-workers — never one alone — so the repo is uniform **because pool-workers hard-pinned it** and npm deduped our `^` ranges onto that exact version. The declared `wrangler` range is therefore *documentation of a floor*, **not** the mechanism.

⇒ **Bumping `wrangler` on its own splits the tree**: our caret resolves to the newer version while pool-workers' nested dep stays pinned to the old one — two copies, the exact hazard the version-uniformity work exists to prevent (and the root-hoist footgun in `durable-objects.md` § DO class registration is what it feels like). The pair MUST be bumped together, and treated as a **toolchain-triple** change: miniflare is the workerd runtime under every pool-workers test, so behavior can shift — you MUST budget a full-suite run and MUST treat an unexplained new failure as signal, not flake.

⚠️ **Root `package.json` `overrides` MUST NOT be reached for to force uniformity.** It *does* pin one version everywhere, but a **changed** override is silently ignored by `npm install`, `npm update`, `npm dedupe`, `--force`, and `--package-lock-only` alike — only deleting `package-lock.json` re-resolves it, so every bump becomes a full lockfile regeneration. Set-once is fine; maintaining it is worse than the problem. (Both behaviors verified in a scratch monorepo, 2026-07-27.)

**You MUST enumerate over the `workspaces` list, never a `packages/*` glob** — `doc-test/*/*` is a workspaces entry and is easy to miss (`npm ls @cloudflare/vitest-pool-workers --all`). An experiment that declares `wrangler` *without* pool-workers has nothing pinning it forward, which is how stale experiments hoist an ancient wrangler to the repo root.

### The Node major and the CF triple are INDEPENDENT axes — bump them separately
**Baseline: Node 24 LTS ("Krypton").** Six surfaces carry it and MUST move in one sweep, or the lanes silently disagree: root `engines` · `.nvmrc` · `@types/node` (root + `tooling/check-examples` + `tooling/doc-testing`) · every `node-version:` in `.github/workflows/` · `apps/nebula/container/Dockerfile` (`node:24-slim`) · `experiments/computer-vfs-build/Dockerfile` (nodesource `node_24.x`).

⚠️ **A Node bump does NOT imply a toolchain-triple bump, and conflating them destroys your ability to read a failure.** wrangler/miniflare declare `node >=22.0.0`, so a Node major inside that floor costs the triple nothing — measured 2026-08-03: the entire suite went green on Node 24 with pool-workers/wrangler/miniflare **completely unchanged**, before a single dependency moved. Bumping both at once would have put a runtime major (miniflare 4→5) on the same commit as the Node major, so any red would be unattributable — the exact opposite of the "treat an unexplained failure as signal" rule above. **The new Node MUST be established on the pinned triple first, and the triple bumped afterward on its own budget.**

⚠️ **`@types/node` MUST track the RUNTIME major, never "latest".** Types ahead of the runtime typecheck code against APIs that don't exist at runtime — a green `type-check` that ships a `TypeError`. The root pin had drifted to `^25` while the runtime was 22; Node 24 + `@types/node@^24` closes it.

⚠️ **npm 11 (bundled with Node 24) WARNS about lifecycle scripts but still RUNS them.** `npm warn allow-scripts … not yet covered by allowScripts` fires for `workerd`/`esbuild` on every install and reads exactly like a block — it is not. Verified 2026-08-03 with a sentinel postinstall that wrote a marker file: the marker appeared. You MUST NOT "fix" this by adding an `allowScripts` allowlist or re-running installs; the warning MUST be treated as noise **until npm actually enforces it**, at which point `npm ci` in CI is what breaks (per §4, re-derive then — don't pre-build the guard now). Note the binaries would survive enforcement anyway: workerd/esbuild ship theirs via **optional platform deps**, and the postinstall is only the fallback.

## Releases
All packages publish together with synchronized versions (Lerna); publish scripts repoint `package.json` from `src/` to `dist/`, then revert (the only time a build runs). Breaking changes SHOULD be favored over technical debt — they bump major semver and MUST have the next release flagged. Use `/release-workflow`.

## Semantic code search
For conceptual searches ("where do we validate JWTs", "what handles rate limiting"), Probe SHOULD be used: `npx -y @probelabs/probe search "<query>" [path]` — AST-aware, fully local, returns whole functions/classes. `Grep` stays the default for literal strings and symbols.

## Symbol renames — grep the BARE identifier to verify
Probe/Grep *find*; they don't *rename*. A rename done with a text replace (`sed`/`perl`) can't tell the symbol from a same-spelled string, comment, or unrelated identifier — so **after any `Old`→`New` rename, you MUST grep the bare identifier (`grep -rn '\bOld\b'`), not just the form you replaced.** A `'Old'`→`'New'` quoted-literal replace silently misses **member/type-position access** (`x.Old`, `rels.Old.field`, `interface X extends Old`) and doc comments; those survive, compile, and only surface as a runtime/test failure (empirically bit the `Turn`→`Message` rename *twice* — `rels.Turn.session`, `.Turn?.session`). The bare-identifier grep should return only the refs you *intend* to keep (deliberately-different concepts — e.g. `TurnRecord`, `trackTurn`), which you then eyeball. For a **pure symbol** rename, an LSP/`ts-morph` rename is scope+type-correct and strictly better than `sed` — but it still can't touch **string literals coupled to a name by convention** (`typeName: 'Old'`) or comments, so the grep-verify is irreducible regardless of the replace tool.
