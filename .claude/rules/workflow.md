# Working in This Repo

## Task files
Work is tracked in `tasks/`:
- `tasks/backlog.md` — small tasks and ideas
- `tasks/[project-name].md` — active multi-phase projects
- `tasks/on-hold/` — designed but paused, expected to resume
- `tasks/icebox/` — parked indefinitely, no planned return (colder than on-hold)
- `tasks/archive/` — completed projects + point-in-time decision/research records (`decision-*.md`). **Frozen on entry — an archived file MUST NOT be updated** (no link fixups, no terminology syncs, no code-drift corrections); sole exception: a dated superseded banner at the top. See `tasks/README.md`.

Use `/task-management` to choose docs-first vs task-file-first when starting a project, then `/write-task` to draft the file (design intent first, hand-reviewed, then phases). When the plan changes mid-stream from what you learn in earlier steps, you MUST propose updates to the task file, and MUST summarize what changed after each step. **Not every change needs a task file** — process/organizing tweaks (editing rules, moving content) can be done directly. See `tasks/README.md` for templates.

### Referring to things across files — name them, don't number them
**You MUST cite the durable COMMITMENT, not whichever file currently implements it.** Task files move, get renumbered, get absorbed, get archived; an ADR or a rule does not. A task file that justifies itself by pointing at a sibling task file inherits that file's churn — and reads as circular when the sibling is itself mid-restructure. Bit 2026-07-28: `/mint-narrower-token` justified a guard by citing `identity-mint §4`, when the commitment was ADR-012 all along and §4 was only its current home.

**Across a file boundary, a section MUST be referred to by NAME.** Numbers are fine *inside* a file, and are load-bearing where they encode order (phases, gates — `/build-task` transcribes phase order). But a bare `§4` in another file carries no meaning, is unfindable without opening that file, and **rots**: `identity-mint` renumbered the moment its former §3 moved out, and in one file `§4` meant two different sections depending on which filename preceded it. Give sections meaningful names and cite those; add the number only as a convenience alongside.

**A section reference MUST be written `§ *Name*`** — italic, never bold, and whether or not the section is in the same file. Bold is a claim on a skimmer's attention, and a pointer *away* from the prose has the weakest claim there is; the `§` makes every cross-reference in the repo greppable with one character. An anchor link is the tempting alternative and is worse: rendered, it pulls *more* attention than bold, and the generated anchor for a heading with backticks or punctuation is not predictable from the text.

⚠️ **A numbered handle others are expected to cite MUST be APPEND-ONLY** — assigned once and never reused or renumbered when a sibling is inserted or removed (`D7`, `ADR-016`, `calibration.md` §3(d)). That is what makes it safe to cite; a section number, which shifts under insertion, is not.

⚠️ **A task-file handle MUST NOT ship in SOURCE.** `S4`, `D12`, `Phase 3` are a task file's native currency and are fine *inside* it — but code outlives the file that specified it, and that file archives, so a comment citing `D12` becomes unresolvable with nobody left re-reading it against a frozen task file. **In source, you MUST cite an ADR, a rule file, or nothing** — most handles reduce to one of those, and the rest are a clause of prose. ⇒ **Conversion MUST happen at transcription, as a phase criterion** — never as a cleanup step, which is the shape that gets skipped — and you MUST check it: `grep -nE '\b[SD](1[0-9]|[1-9])\b|\bPhase[ -][0-9]+\b|\bChild [0-9]+\b'` over the changed files, then eyeball (`S3` also spells a storage product). `Phase N` is in the pattern because it is the handle a test header reaches for and the one the letter series cannot see. Where a long rationale genuinely has no ADR home, cite the archived path by name; archived files are frozen, so that pointer is stable.

⚠️ **Another file's COUNTS, DATES, INVENTORIES, or WORDING MUST NOT be restated — for those, a pointer MUST be preferred to a summary.** **This is scoped to things that ROT, and MUST NOT be read as a general preference for indirection.** Restating a sibling's *reasoning* in a sentence or two, so a reader need not open it, is wanted here — `.claude/rules/prose-voice.md` § *Duplication — the reader decides it* owns that, and the two rules meet exactly at this line. What rots is different: **the source keeps growing while the copy does not**, so an inventory (*"S1–S7 inherited, D1–D13 decided"*) or a status date is false the moment the source gains a row — and reads authoritative while wrong. ⇒ A cross-file reference MUST state the **target shape in one line** and **point by section name**; anything more, a reader gets by following the link. **A restated COUNT has no derivation, so nothing updates it.** Restating its *argument* is not that; an argument does not gain a row.

⚠️ **A VERBATIM QUOTATION is the same defect in a more convincing costume, and MUST NOT be used as evidence.** A quote earns its force from being *real*, so when the source is reworded it silently becomes an invented example and a reader who greps for it finds nothing. **Cite the SYMBOL and characterise it in a clause** (`see X's JSDoc, which states the invariant as prose`) — that survives any rewording. When you sweep standing guidance, grep for quoted fragments of files you touched, not only for claims about them: "statement" reads as *a claim*, so a criterion about falsified statements will not catch a stale quotation.

## Design-first: diagrams before prose when the design is tangled
**When a multi-node design gets tangled, or task files drift into contradicting each other, you SHOULD lead with sequence diagrams, not prose:** a participant/cast model, then one diagram per flow. Prose hides contradictions; a diagram's participants, ordering and gating force precision and make the drift visible (Larry: "my mind works better with sequence diagrams than prose"). Nail the cast, naming and flows *with the user* first, **then** rewrite the prose or task files to conform, and offer this unprompted when you sense the design is tangled.

**After every Mermaid write or edit, you MUST run the render-safety check before considering it done.** You cannot render from here, so the grep is the check, and the human eyeballs the real render after it. It extracts the fenced `mermaid` blocks and prints nothing but `clean` when they are safe:

```sh
awk '/[`][`][`]mermaid/{m=1;next} /[`][`][`]/{m=0} m' <file> | grep -E '[;#]' || echo "clean"
```

Knowing the traps is not enough on its own: the `;`-in-`Note` bug came back right after being fixed, with this guidance already in place. The traps, which apply equally to Mermaid in `website/**` (`documentation.md`):

- **No `;` in `Note` text.** It is a statement separator, so the diagram fails to parse.
- **No `#` in any diagram text** — participant label, message or note. `#` starts an HTML-entity escape, so `participant D as #dispatchEnvelope` renders a blank actor box (bitten 2026-07-02). Write `dispatchEnvelope (private)`; do not "escape" it as `#35;`, which trips the `;` check.
- **A long `Note over` anchored on the leftmost actors overflows the canvas and clips.** Span more actors (`Note over A,C`).
- **Solid `->>` is a call or request; dashed `-->>` is a response, return or push.**

## Bytes you cannot see, and search strings you did not see whole
**Two kinds of edit pass type-check, tests and review while being wrong in a way the diff cannot show: an invisible byte, and a replacement built from a truncated line.**

- **A stray NBSP (U+00A0) or NUL (U+0000).** WYSIWYG editors such as Typora insert NBSP on edit, which breaks exact-match `Edit`s and can break rendering. An agent `Edit` or `Write` can inject a NUL into a string literal that reads as a space in the diff; it compiles and runs, and the `/build-task` verifier panel caught one as the separator inside a `` `${a} ${b}` `` dedup key.
- **You MUST check with a byte count, because `grep` CANNOT see a NUL.** It reports nothing for a file it considers binary, which is what a NUL makes it, so the old `grep -nP '[\xc2\xa0\x00]'` passed silently on a corrupt file (2026-07-21).

  ```sh
  tr -cd '\000' < <file> | wc -c          # NUL count — must be 0
  grep -c $'\xc2\xa0' <file>              # NBSP count — must be 0 (grep IS fine for NBSP)
  file <file>                             # a source file reporting "data" instead of "text" = NUL
  ```

  Strip with `perl -i -pe 's/\xc2\xa0/ /g; s/\x00/ /g' <file>`.
- **The character MUST NOT be put *literally* into the check command; it MUST be written as an escape** (`b'\x00'`, `$'\xc2\xa0'`). A pasted NBSP degrades to a plain space in transit, and the check then reports every file dirty (2026-07-21, in the very command written to catch the first bug). For a whole-tree sweep, count bytes in a script:

  ```sh
  python3 -c "import pathlib,subprocess as s
  for f in [l.split(maxsplit=1)[1] for l in s.run(['git','status','--short'],capture_output=True,text=True).stdout.splitlines()]:
      p=pathlib.Path(f)
      if p.is_file():
          b=p.read_bytes()
          if b.count(b'\x00') or b.count(b'\xc2\xa0'): print('DIRTY', f)"
  ```
- **You MUST read the full line before building a replacement from it.** A `grep … | cut -c1-N`, a `sed -n 'Np'` on a long line, or a tool result the harness elided gives you a prefix, and replacing a prefix deletes the middle of whatever followed. On 2026-08-17 one such edit silently dropped the target from a markdown link (`](../nebula-foo.md)` → `](nebula-foo.md)`). After a scripted doc edit, verify the property it could have broken — resolve links, re-run the example checker, re-parse the block — rather than eyeballing the diff.

## Evaluating alternatives: weigh the unlearning tax, not just build cost
When you compare options and **recommend** one (interim-vs-target, build order, scope cut, design choice), the **unlearning tax** MUST be an explicit criterion alongside build cost — and usually the deciding one. The bottleneck is **reviewer time**, not lines of code. A known-temporary artifact ("interim") that lands in a surface re-read every session — code, docs, task files, agent memory — gets re-anchored on as "the model" and must be **unlearned, repeatedly, at the reviewer's expense.** (Empirically the single largest drain on pre-alpha review time has been unlearning the `acme.app.dev` interim — see the `interim-unlearning-tax` memory.)

You MUST score each candidate on this, and MUST say so when you recommend:
- **Interim cost ≈ (how many re-read surfaces reflect it) × (its lifetime) × (sessions over that life)** — paid in the bottleneck reviewer's correction time, *not* in build size. An option that is cheaper to *build* but seeds a durable, widely-reflected interim is usually the **more expensive** choice. Recommend accordingly, and name this tax in the trade-off.
- **Building the target SHOULD be preferred over a lean interim _when the target is pinnable now_.** A half-pinned "final" becomes its own interim and costs the same tax → the move is **pin → purge → build**, not rush-to-final. You MUST NOT over-pin either: pin only what the current step needs to stop describing the model wrongly; leave genuinely-later mechanics as clearly-fenced "not yet built" pointers (not interims).
- ⚠️ **A TEST IS A CONSUMER when deciding HOW to build something already in scope — never when deciding WHETHER to build it at all.** An interim built to make tests runnable ossifies as hard as production code. This is the clause most often got wrong, in the *conservative* direction. When judging "is there a present consumer," a test we need today counts: if a test would exercise the real mechanism, that is a consumer, and building the real thing beats building a stand-in for it. The mechanism must have its own reason to exist first — a capability whose only purpose is to make a test possible is a YAGNI question, not a specification (`calibration.md` §3(d)). **Every test written against a stand-in must also be unlearned**, so a mock is not the cheap option — it is the same ossification with the cost hidden in the test suite, and it costs fidelity besides: the login-shortcut mints diverged from the real path, so real bugs got through.
  - **`it.skip` SHOULD be preferred over an ossifying stand-in.** Skipping defers *one* test; a mock creates an artifact that N future tests anchor to. (See `testing.md` § *Deferring ≠ deleting*.)
  - **The asymmetry that decides it:** a slightly-wrong thing you built early is usually *cheaper to fix* than an interim is to overcome, because the interim has consumers and the wrong design mostly has a shape. Favor **the goal** (a product someone pays for) over **the milestone** — a milestone is a checkpoint, not the thing being built.
- **A PERMANENT divergence from an established in-repo pattern is priced like the unlearning tax's sibling — and when the conforming form costs the same at runtime, the divergent form MUST be treated as the more expensive option.** The unlearning tax prices *known-temporary* artifacts; a divergence is permanent, so its cost is per-reader-per-encounter, forever: every reader who knows the established pattern cold must stop and ask *why is this different here?* — and a reviewer can only hold so many differences. Divergences also **accrete false justifications**, because each reader who asks either invents an answer or preserves a wrong one — one such invented comment was nearly canonized into a task file by a review panel. **The tell:** the honest answer to "why is this different?" is history, not a requirement. Conform it, or write the requirement down where the divergence lives.
- **YAGNI gates capability, never generality.** *Whether* to build a capability now is a scope question — push back when there is no present consumer *of any kind, tests included* (see above). *How* to shape a capability already in scope is **not**: the generic form that solves today's problem without foreclosing tomorrow SHOULD be preferred, and point solutions / tier-or-case special-casing MUST be treated as the anti-pattern. **Cost test:** when the general form costs the **same or less** than the narrow one (removing a restriction, widening a parameter, moving a flag from the batch to the entry), the narrow one is strictly worse — it is a lean interim someone must later unlearn. Reserve the objection for a general mechanism costing *materially more* than the immediate need (a new subsystem, carrier, or protocol). The narrow form routinely costs *more* code for *less* capability — a tier check added to a mechanism already uniform across every tier.
- **When an interim is genuinely unavoidable, its tax MUST be minimized:** single-source it (one constant, not scattered), label it `TEMP → target=X` at every site, and record it (memory / task file) as a **dead interim, model is X** — never as the model. Task files MUST state the **target in present tense**; the interim is a fenced, dated exception.
- **Self-check before trusting current code:** reading any default / scope / identity / config value, you MUST ask "**target or interim?**" and MUST NOT assume the current code is the model. **This extends to BEHAVIORS/ENDPOINTS, not just values:** during a rewrite to a pinned new model, a code path that *exists in the old code with passing tests* is NOT thereby validated for the new model — it MUST be conformed to the pinned model or cut, and a test that **enshrines the old shape** MUST NOT be carried. A green test asserting deprecated behavior is a false-confidence trap the reviewer must then catch — carrying one past a pinned rewrite reintroduced a real privilege escalation here, with new tests codifying it as intended.

## Architecture commitments (ADRs)
`docs/adr/` holds the few repo-shaping commitments — decisions that span packages and survive mechanism swaps (`docs/adr/README.md` has the bar; adding an ADR means adding its one-liner here). `/review-task` reads the full files; these one-liners are the always-loaded constraints. ⚠️ **A line here is a POINTER, not a summary — one sentence naming the commitment, plus any tripwire that would bite before you thought to open the ADR. Argument, evidence, measurements, and worked examples belong in the ADR.** (Budget stated in `docs/adr/README.md` § *The index line*; it exists because this section grew to 3,273 words of restated reasoning before anyone noticed.)
- **ADR-001** — TypeScript types ARE the schema language; never introduce a second one (Zod, JSON Schema, …). The mechanism (typia) is swappable; the principle is the commitment.
- **ADR-002** — every surface (wire, storage, validation, diff/patch, history) round-trips the full structured-clone value space, incl. cycles, aliases with identity, Errors, Web API types. A JSON-only surface is never acceptable.
- **ADR-003** — mesh flows are one-way messages carrying continuations; **no node holds a reply Promise open across a hop** (tabs sleep, WS reconnects, DOs hibernate — a held Promise strands). Request/response *semantics* are fine, via a continuation. User-land awaiting is **Client-only** (`callAsync`). No RpcTarget/Cap'n Web sessions.
- **ADR-004** — resources are Snodgrass-style snapshot sequences; history is the substrate. No destructive writes; "current" queries honor the `END_OF_TIME` sentinel.
- **ADR-005** — optimistic concurrency: forward-only eTags prove currency AND provide idempotency (`newETag` replay detection); no locks, no dedupe ledger. Non-monotonic checks (permissions, not-found) stay inside the transaction.
- **ADR-006** — resources reference each other by id (FK), never by embedding; a field typed as another ontology type is rewritten to `string`/`string[]` in the write shape. Related resources are separate ops in one atomic transaction (client supplies every id). Embedding where an id belongs is a **loud error**.
- **ADR-007 (Accepted)** — every node type shares one **narrow comms + guards core** (`lmz.call`, `lmz.broadcast`, `ctn()`, `callContext`, `onBeforeCall`, `@mesh()`) by **composition**, never reimplemented. Storage/alarms/`onStart`/`fetch` are per-type **capabilities, NOT the invariant** — and a driven container is a capability too (raw `ctx.container` on a `ScopedMeshDO`), never a node type or base class.
- **ADR-008 (Accepted)** — within a Star, the full org/permission tree — nodes, edges, grants, **grantee identity**, and **presence** — is visible to every member. **Visibility ≠ capability**: enforcement is at the point of action, never secrecy of the tree. **No per-subtree hiding** (need invisibility? separate Star); the denied-node set is **always disclosed**. Cross-scope profile reads are ADR-012's, not this one's.
- **ADR-009 (Accepted)** — **real email login is the DEFAULT auth path**, and what design reasoning grounds on; never conclude system behavior from a synthetic path. Ladder, most-preferred first: (1) real login, (2) test-mode server issuance, (3) client-side mint = last resort, justify per-site, (4) negative-control wrong-shape mints. ⚠️ **Speed is never a reason to drop a rung** — the real loop is ~1s, measured; the ADR says which older number not to re-cite.
- **ADR-010 (Accepted)** — **keys are random opaque values, statistically unique WITHOUT coordination** (mintable anywhere, offline-safe, idempotent). Never key off a natural/mutable attribute (email/slug/name) or an auto-increment/rowid counter; the axis is **coordination, not client-vs-server**. Companion **replication rule**: a *mutable* attribute has one authoritative source and every other copy is a cache owing an explicit convergence mechanism. ⚠️ A persona's `sub` and `profileId` are spelled from its host instead (ADR-022).
- **ADR-011 (Accepted)** — persisted/wire **timestamps are ISO 8601 UTC strings** (`…T…Z`, ms precision, fixed-width), SQLite `TEXT`, string-compared. **Never epoch `number`.** End-of-time sentinel `9999-01-01T00:00:00.000Z`. Carve-out: protocol-mandated formats keep their spec (JWT, HTTP).
- **ADR-012 (Accepted)** — a person's PUBLIC profile fields are readable/subscribable by **any authenticated caller holding the `profileId`**, across every scope boundary — no passage check, no registry read on the read path; holding the handle IS the capability. Generalizes ADR-008 globally. **Exactly two capability levels, no per-field roles**; private-by-default is **derived** from an allow-list, never by subtracting known-private keys. ⚠️ **One tripwire, load-bearing against a scope authority that can be MANUFACTURED: every read of a membership that confers authority requires an ACCEPTED one** (and *not* `emailVerified`) — the registry's `getScopesForProfile` for the scoped-admin branch, and its `getIdentityScope` for the narrower mint, which is what keeps an impersonation token honest at the owner branch. Read the ADR before touching either.
- **ADR-013 (Accepted)** — **`sub` is the only KEY; `profileId` hangs off the ADDRESS and is never keyed on** — a column on the `Emails` row, never a join table, which is what makes "one human, one profile" structural rather than emergent. Resource records key on `sub` only, so a future `sub`-unification stays additive. ⚠️ **"Never copied" = never as the KEY, not absent**: exactly two licensed denormalizations (self-healing JWT/KV; write-time-pinned immutable attribution) and no others. **Authz scope-sets resolve live — a stored one is a security bug.**
- **ADR-014 (Proposed)** — a container node **orchestrates from its own companion DO, never across a hop from a sibling**; the companion DO IS the hub. Generalizes to: don't distribute a **liveness-coupled** workflow across independently-hibernating nodes. Hops stay fine where liveness is *not* coupled. Distinct from ADR-007 — that is uniformity, this is *placement*.
- **ADR-015 (Proposed)** — **dominion flows strictly DOWNWARD, and only downward**; downward is total and non-vetoable, so restraint for destructive actions is a **UI warning, never an authorization refusal**. ⚠️ `dominion` and `passage` are RESERVED terms — read the predicates in § *Terminology* rather than reconstructing them, because both obvious paraphrases are wrong (dominion is not the bare `scopeAdmin` bit; passage is not the upward arm). They replaced `authority` and `admission`; **`reach` is not to become one either, in noun or verb form** (2026-09-20); reintroduce none of the four.
- **ADR-016 (Proposed)** — every action that **destroys or removes state, changes a principal's authority, or establishes a session** records the **FULL verified claims** of the acting token (`sub` + the complete `act` chain + `profileId` + `access` + `aud`), write-time-pinned and immutable — a `sub`-only record names the person acted *upon* as the actor. **Reversibility is not an exemption**; **ONE shared projection** produces every record, conformance stated structurally and never as a caller list; the stored `access` and `aud` are asserted history, **never an authz input**. ⚠️ Ratification **deferred past pre-alpha** — do not ratify at `/build-task`.
- **ADR-017 (Proposed)** — **a shared URL takes the recipient to the same page AND view state.** What you are *looking at* (scope, selection, tab, filters, sort, paging) rides the URL; what you are *doing* (scroll, focus, drafts) does not. ⚠️ An overlay someone would link to has the URL as its ONLY opener; a confirmation or menu never touches it. ⚠️ The URL names WHAT, **never permission to look** — no credentials or personal data; authz re-checked on arrival; a `profileId` is fine: the test is *does it reveal anything NOT already public?* Generated apps inherit it.
- **ADR-018 (Proposed)** — **a global singleton DO is the system's scarce resource; state and requests default to OFF it.** One DO is a hard, non-sharding ceiling (10 GB; about 1000 rps at best, ~410 if every request writes — the ADR carries the measurements) and passing it arrives as an outage, not a warning. The **only** qualifying reasons are **global uniqueness** and **strong consistency at the moment of decision**. Prefer: derive it → put it where it scales → the singleton. Whatever qualifies owes two things: never a per-request path that scales with user activity, and a **stated bounded lifetime**.
- **ADR-019 (Withdrawn 2026-08-26)** — was: derived artifacts record what they read, every later reader re-checked live. Withdrawn for the consent-loop model — Nebula reads AS the asking human, a refusal becomes a brokered ask to a permission holder, and a shared answer is that holder's disclosure decision. Under the model every read rides the asking human's token and a posted answer is a disclosure decision — nothing is left to capture.
- **ADR-020 (Proposed)** — **the look goes through the theme: color from semantic classes, ONE theme per surface declared ONCE, markup carries none of it.** Nebula's own UI is one surface; a generated app never wears Nebula's. ⚠️ A class the installed daisyUI no longer defines emits nothing and fails no tier — `npm run audit:classes` is the proof.
- **ADR-021 (Proposed)** — **everything user-facing lives on `lumenize.dev`, one host label per scope tier, and the host IS the scope** (`manny--dev.crm.acme.lumenize.dev`). ⚠️ The certificate set never grows with tenants or personas, so never give a Star or persona a label of its own; environments are reserved Star slugs; no Public Suffix List entry is planned (ADR-022 needs `lumenize.dev` to stay one site).
- **ADR-022 (Proposed)** — **every session lives on `platform.lumenize.dev`: a page on any `lumenize.dev` host gets its access token by a credentialed `fetch` there.** ⚠️ `aud` is the scope its host spells, from `Origin`, and passage and dominion read it, taking only the admin bit from the membership; `authScope` is the broadest-dominion membership there, never narrowed to the host; every cookie is `__Host-`-named, none on a scope host; the client names neither scope; a persona host's token has no `act`, by design.
- **ADR-023 (Proposed)** — **code crosses the mesh boundary only at one of two bridges**: **a facade** the infrastructure package owns (the Registry facade, so far), through which mesh code reaches raw infrastructure, and **`@rawRpc`**, through which our own code reaches a mesh node, for an operation no client may call. ⚠️ Never an operation only our own code may invoke on a node's `fetch`, never a general channel free of claims.

## Teeing up decisions for Larry
**When more than one thing needs Larry's decision, each MUST be teed up on its own, one per turn**, never as a list to answer at once. Each item carries four parts:

- **Context**, with the source quoted rather than pointed at, so Larry need not open a file to follow it.
- **Analysis**: what is true, checked against the code, and what each answer would cost.
- **Alternatives**, each with its trade-off.
- **A recommendation.**

**Order them by dependency first, then by risk, and re-order after each answer**, since an answer can settle or reshape what follows. The first item MAY open with a short numbered list of what is coming. The same procedure serves a build's hand-off (`/build-task`) and a review's gate (`/review-task`). Larry, 2026-10-06: *"I use that all of the time now."*

## Sequential implementation — no parallel worktrees
One long-running branch, implemented sequentially. Code-writing MUST NOT be parallelized across worktrees, parallel PRs, or concurrent write-agents — in this solo workflow, merge/conflict cost exceeds any speedup. Parallel agents are for reading and verifying (review panels, verifiers), and MUST NOT write code concurrently. Worktree isolation MAY be used only for self-contained experiments whose code never merges back (next section); if a worktree's code would need to come back, a worktree MUST NOT be used.

Empirical confirmation, from the largest single-batch build: one hot file was threaded through 9 of ~24 phase commits, the phases formed a strict chain, and at least one cross-phase dependency was invisible at plan time (a later phase fixed an earlier phase's code). Parallel writers would have N-way-merged that file for zero wall-clock gain — each phase was minutes of transcription. The only genuinely independent phases were two leaf-utility ports, exactly the cases where parallelism saves nothing. Not even a narrow exception is worth it.

## Experiments
`experiments/*` are point-in-time spikes, not maintained artifacts. Results live in the experiment's `RESULTS.md` / `FINDINGS.md` / blog post, not in keeping the code runnable. An experiment commonly breaks soon after it runs because we change the source it depended on — **that's fine, and it MUST NOT be fixed.**
- ⚠️ **You MUST NOT experiment outside `experiments/` — build a throwaway Worker there instead.** This includes *test* files and *test* workers under `packages/**` / `apps/**`: they look low-risk because "it's only a test," but they are shared, committed surface. Spin up a new `experiments/<name>/` with its own `package.json`, `wrangler.jsonc`, and Worker and **deploy that**, however much scaffolding it seems to duplicate. The experiment's own `package.json` also lets it declare heavy deps (`isomorphic-git`, a package barrel) that a real package must not take on — so this *removes* friction rather than adding it.
  - ⚠️ **The specific trap: adding a DO class to an ALREADY-DEPLOYED worker creates permanent registry debt.** Cloudflare keeps every DO class the worker ever deployed. Once you delete the experiment's class from source, the deployed worker holds a class the `exports` map no longer lists, and **the next deploy of that worker fails reconciliation** until someone adds a `"state": "deleted"` tombstone or dashboard-deletes it. The cleanup is therefore *not* symmetric with the setup — you cannot simply revert.
  - Corollary: a deployed experiment worker also **drifts from source** the moment you revert (the deployed bundle keeps whatever you last pushed), so a shared test worker ends up in a state no one can reproduce from `git`.
  - **Every deployed experiment Worker MUST be named `experiment-<something>`.** They accumulate in the Cloudflare account and are indistinguishable from real projects at a glance — a `do-cs-nebula` arm reads alarmingly like the product. The prefix makes the throwaways obvious in the dashboard and safe to bulk-delete.
  - **A throwaway experiment Worker MUST be deleted from the DASHBOARD, never with `wrangler delete`.** A dashboard project-delete **also removes that Worker's DO namespaces**, so deleting the project is all you need — no ordering dance. `wrangler delete` leaves the namespaces orphaned ([[wrangler-delete-leaves-do-data]]), and there is no `wrangler durable-objects` command to clean them up afterward. Delete a namespace *individually* only when you're **keeping** the Worker and just retiring one class from it. (Confirmed on a 9-worker cleanup, 2026-07-23.)
- **Tracked by default.** `experiments/` is *not* git-ignored — just commit new experiment files like any other code (no `git add -f`). Only experiment-local generated output stays ignored (`node_modules`/`dist`/`.wrangler`/`coverage`/`__screenshots__`/`.dev.vars` via global rules, plus targeted `experiments/...` rules in `.gitignore` for any bulk-generated artifacts, as `experiments/tsgo-benchmarks/schemas/` does). (It used to be ignored — a footgun, since a `workspaces` entry pointing at a clone-absent dir breaks `npm install` on a fresh clone.)
- **New experiment**: create `experiments/<name>/` (own `package.json`, `wrangler.jsonc`, etc.), add `"experiments/<name>"` as an **individual** entry — a glob MUST NOT be used — to the root `package.json` `workspaces` list, then `npm install` at the repo root. Individual entries are load-bearing — `experiments/*` would break `npm install` the moment one experiment references a renamed/deleted package.
- **Broken old / stale experiment**: remove its entry from `workspaces`, and once its results are captured elsewhere (task file / `RESULTS.md` / blog post) `git rm -r experiments/<name>` rather than letting it rot. It MUST NOT be made to run again. The `workspaces` list holds only currently-active experiments; git tracks active + not-yet-pruned ones, so prune periodically.
- **Adopting a spike's result**: when a spike proves something works via specific build tooling, that tooling MUST be productionized into the real package *before* the integration phase, and MUST NOT be left in the experiment. (The tsc-bundling spike worked; the missing productionization broke every vitest-plugin test when Ontology was wired into Galaxy/Star. The live pattern: `packages/ts-runtime-parser-validator/scripts/bundle-tsc.mjs`, whose header is the canonical doc.)

## No build during development
Source runs directly — **a build step MUST NOT be added to or run in the dev loop.** vitest transpiles Workers TypeScript on the fly; Node tooling is JS + JSDoc (no compile). A build happens **only at publish**. Reaching for a build during development is a recurring failure mode: it spawns doom loops chasing build caches, `dist/`-vs-`src/` confusion, and stale output. If something isn't working, the fix is never "build it."

## Toolchain bumps — `@cloudflare/vitest-plugin` is the knob, never `wrangler` alone
**`@cloudflare/vitest-plugin` pins `wrangler` exactly and drags `miniflare` with it, so the pair MUST be bumped together, never `wrangler` alone.** Bumping `wrangler` by itself leaves two copies of the runtime in the tree. Treat it as a **toolchain-triple** change: miniflare is the workerd runtime under every vitest-plugin test, so you MUST budget a full-suite run, MUST compare each workspace's `Test Files` count before and after rather than the exit code, and MUST treat an unexplained new failure as signal, not flake. **The Node major is a separate axis: the new Node MUST be established on the pinned triple first, and the triple bumped afterward in its own commit.** `packaging.md` § *Toolchain bumps* has the rest: the exact pins, why the exit code lies, why root `overrides` are refused, enumerating workspaces, and the six places the Node major lives.

## Releases
All packages publish together with synchronized versions (Lerna); publish scripts repoint `package.json` from `src/` to `dist/`, then revert (the only time a build runs). Breaking changes SHOULD be favored over technical debt — they bump major semver and MUST have the next release flagged. Use `/release-workflow`.

## Semantic code search
For conceptual searches ("where do we validate JWTs", "what handles rate limiting"), Probe SHOULD be used: `npx -y @probelabs/probe search "<query>" [path]` — AST-aware, fully local, returns whole functions/classes. `Grep` stays the default for literal strings and symbols.

## Symbol renames — grep the BARE identifier to verify
Probe/Grep *find*; they don't *rename*. A rename done with a text replace (`sed`/`perl`) can't tell the symbol from a same-spelled string, comment, or unrelated identifier — so **after any `Old`→`New` rename, you MUST grep the bare identifier (`grep -rn '\bOld\b'`), not just the form you replaced.** A `'Old'`→`'New'` quoted-literal replace silently misses **member/type-position access** (`x.Old`, `rels.Old.field`, `interface X extends Old`) and doc comments; those survive, compile, and only surface as a runtime/test failure (empirically bit the `Turn`→`Message` rename *twice* — `rels.Turn.session`, `.Turn?.session`). The bare-identifier grep should return only the refs you *intend* to keep (deliberately-different concepts — e.g. `messageId` locals beside a `Message` type), which you then eyeball. For a **pure symbol** rename, an LSP/`ts-morph` rename is scope+type-correct and strictly better than `sed` — but it still can't touch **string literals coupled to a name by convention** (`typeName: 'Old'`) or comments, so the grep-verify is irreducible regardless of the replace tool.
