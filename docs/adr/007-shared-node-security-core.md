# ADR-007: Lumenize Node Types Share One Mesh Comms + Guards Core (Composed, Not Reimplemented)

**Date**: 2026-06-17
**Status**: Accepted
**Deciders**: Larry
**Evidence**: `packages/mesh/src/lmz-api.ts` (the shared executor + composition seam), `lumenize-do.ts` / `lumenize-worker.ts` (the two server node types composing it), `lumenize-client.ts` (the client's separate path — the one documented divergence), `lumenize-client-gateway.ts` (JWT verified at the Gateway), `apps/nebula/src/nebula-do.ts` (the scope guard), `packages/mesh/src/ocan/execute.ts` (entry-op-only allowlist). Day-to-day mechanics: `.claude/rules/mesh.md`.

## Context

Lumenize is a mesh of **nodes** that talk over `lmz.call()`. Every node must expose the *same* comms-and-guards behavior — receive a call with its propagated identity and provenance, make outgoing continuations that carry that context forward, and run the authorization guards. That behavior is **security-relevant**: it is where identity propagates and where every access check happens. Divergence between node types here is not a style problem — it is an audit surface, and a place for holes to hide.

But the node types are **heterogeneous by necessity**: each extends a different third-party base — a Durable Object, a Worker entrypoint — chosen for what that node is *for*. Single inheritance is already spent on that base, so they cannot always also share a Lumenize base class. The shared behavior therefore cannot be *inherited*; and hand-reimplementing it in each node type guarantees drift — sooner or later a new node-shaped surface forgets a check.

> **Today's code differs, in one place — the container.** `packages/mesh/src/lumenize-container.ts` defines `LumenizeContainer extends ComposedMeshDO(Container, 'LumenizeContainer')`, whose own JSDoc calls it "the 4th Lumenize node type", and `DevContainer → NebulaContainer → LumenizeContainer` is live in `apps/nebula`. So a container-driving node today **is** a separate node type and base class, which the **Deliberately narrow** bullet below says it is not. It composes the same core through the same mixin, so no guard and no seam differs — what differs is that the capability was given a base class of its own. [`tasks/nebula-galaxy-collapse-and-chat.md`](../../tasks/nebula-galaxy-collapse-and-chat.md) closes it: its target `Galaxy` is a plain `NebulaDO` driving the build container through raw `ctx.container`.

## Decision

**Every Lumenize node type provides the comms + guards core — receiving calls, propagating `callContext` (identity / provenance / state), making continuations (`lmz.ctn()`), and the guards (`onBeforeCall`, `@mesh()`) — by composing one shared implementation, never reimplementing it. A new node type composes this core no matter which base class it must extend.**

- **Composed, not inherited.** The core lives behind a composition seam that every node type invokes, so a node extending a third-party base gets the identical receive-and-guard path without a shared base class. *(Mechanism today, all in `lmz-api.ts`: the shared `executeEnvelope` executor and the `EnvelopeExecutorNode` interface every node type satisfies. How a type reaches it depends on its base — `LumenizeDO` and `LumenizeContainer` mix in `ComposedMeshDO(Base, name)`, while `LumenizeWorker` calls the executor from its own entry methods, since `WorkerEntrypoint` needs no mixin. Two routes, one executor; the commitment survives a refactor of either — cf. ADR-001.)*
- **Deliberately narrow.** The core is exactly comms + guards. Storage, alarms, lifecycle initialization, a node's own request/`fetch` handling, **and a driven container** (raw `ctx.container`) are **per-node-type capabilities**, not part of the core — a node takes only what it needs. Widening the core to include them would force every node to carry machinery it doesn't have, and collide with its base's own lifecycle. *(A container-driving node is exactly this: a `LumenizeDO` that opens `ctx.container` as a capability — **not** a separate node type or base class. We do not `extends Container`; see `containers.md`.)*
- **One gated path, selected by address not content.** The core exposes two distinct *addressed* entries — one for incoming requests, one for delivering a call's result back. **The authorization guard (`onBeforeCall` — the origin→node containment check) runs on both**; they differ only in whether the app-method allowlist also applies: a request must target an allowlisted (`@mesh()`) method, while a result-delivery runs the caller's own continuation with the allowlist off. **Allowlist-off is not guard-off.** Which mode applies is a function of **which entry is addressed, never of attacker-influenced message content.**
- **The guard covers the mesh path only.** A node's own `fetch()`/WebSocket surface is **outside** the shared guard — it must be secured by that node's own design (public-by-design, or its own explicit check), **never *assumed* gated.** Such a surface forgoes the mesh's identity propagation and authorization, so it is a **last resort**: add one only when the mesh genuinely can't carry the traffic, and only with dedicated security review. **The one node-owned HTTP surface today** is a **container-driving DO's own `fetch()`** — e.g. serving its built `dist/` for a dev preview; its privileged operations still travel over the mesh, and the served output carries no tenant secrets. **No node type accepts its own application WebSocket** — client WebSockets terminate at the Gateway, which is not one of these node types.
- **Object-capability access, not only per-method gating.** Because the allowlist is checked at a chain's *entry op only*, a gate method (e.g. `onlyAdmins()`, guarded by an admin check) can **return a capability instance whose methods are the privileged surface**; those methods need no allowlist entry of their own and are reachable only by first passing the gate, in one round trip — so holding the returned instance *is* the authorization (object-capability security). This is sanctioned alongside the common per-method `@mesh(guard)` shape, and spelled out because it is the less familiar of the two: LLMs and humans both reach for per-method gating by default and would otherwise never discover it. (The framework's own `svc` chains are the built-in instance of the same entry-only checking; worked example in `mesh.md`.)
- **JWT verified once, at the Gateway trust boundary; nodes enforce authorization.** The Gateway verifies the token; each node enforces *scope/permission* in its guard (`onBeforeCall` + `@mesh(requireDominionHere)`), never re-verifying the JWT.
- **`callContext` propagation is core, not a per-type detail.** Each node makes the propagated identity/provenance/state available during a call and carries it across outgoing continuations — including the node's own persistent identity, which the framework stamps on **every** first-contact entry, not just the mesh path. *(How the context is bound differs on the client — the one documented divergence, below; identity-stamping mechanics live in `mesh.md`.)*
- **Divergence must be documented and defensible.** The lone current divergence is the client's separate path (browser/Node compat). It is a documented parallel path — to keep documented or consolidate — not a license to reimplement the core freely. Unjustified divergence is a defect.

## Alternatives considered

| Approach | Why rejected |
|---|---|
| Each node type reimplements the receive + guard logic | Drift and security holes by construction; every new surface eventually forgets a check. |
| Share the core via a common base class (inheritance only) | Breaks the instant a node must extend a third-party base; single inheritance forbids a second Lumenize base. A composition seam works across bases instead. |
| A **broad** "mesh + security" core (storage + alarms + init too) | Forces every node to carry lifecycle capabilities it doesn't need, and manufactures collisions with each base's own lifecycle hooks that the narrow scope avoids entirely. |
| A **single** receive entry with a request/response `kind` flag | Lets a sender label a fresh request as a "response" and run its chain allowlist-off. Two *addressed* entries make the gate mode a function of the address, not attacker-influenced content. |

## Consequences

### Positive
- **Uniform secure-by-default comms** — one gated path, one place to audit.
- A new node type composes the **narrow core**, then adds only the per-type capabilities it needs (a `LumenizeWorker` takes neither storage nor alarms nor `onStart`; a container-driving `LumenizeDO` adds only raw `ctx.container` — no separate base or node type).
- Keeping the core narrow **sidesteps the base-class lifecycle collisions** a broad core would have forced us to reconcile.

### Negative / open
- **The client shares the dispatch engine but hand-rolls the receive shell** — a documented divergence justified by browser/Node compat, not a parallel stack. It runs the *same* continuation-dispatch engine as the server node types (including the `@mesh()` allowlist check), the same structured-clone wire, the same `lmz.call`/`ctn`/`callContext` surface, and its own `onBeforeCall` guard at the same point. What it can't reuse is the `executeEnvelope` receive shell: that binds context via `AsyncLocalStorage` — which the server nodes' workerd runtime has (as do Node and Bun) but browsers don't — so a client, which must also run in a browser, captures context synchronously across all its runtimes, and it settles results as an in-heap Promise over a WebSocket — safe because the client's heap survives freeze/reconnect (ADR-003) — rather than firing back to an addressable door it doesn't have. So **every** node type composes the shared engine, and every **server** node type composes the `executeEnvelope` shell as well — only the client hand-rolls it, and its parallel shell is essentially irreducible (no ALS, no addressable fire-back door).
