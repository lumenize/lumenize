# ADR-007: Lumenize Node Types Share One Mesh Comms + Guards Core (Composed, Not Reimplemented)

**Date**: 2026-06-17
**Status**: Accepted
**Deciders**: Larry
**Evidence**: `packages/mesh/src/lmz-api.ts` (the shared executor + composition seam), `lumenize-do.ts` / `lumenize-worker.ts` (the two server node types composing it), `lumenize-client.ts` (the client's separate path — the one documented divergence), `client-gateway.ts` (a Client's server-side half, composed by the node that hosts the Client), `apps/nebula/src/entrypoint.ts` (the JWT verified at the edge, before the upgrade), `apps/nebula/src/nebula-do.ts` (the scope guard), `packages/mesh/src/ocan/execute.ts` (the entry-op-only check). Day-to-day mechanics: `.claude/rules/mesh.md`.

## Context

Lumenize is a mesh of **nodes** that talk over `lmz.call()`. Every node must expose the *same* comms-and-guards behavior — receive a call with its propagated identity and provenance, make outgoing continuations that carry that context forward, and run the authorization guards. That behavior is **security-relevant**: it is where identity propagates and where every access check happens. Divergence between node types here is not a style problem — it is an audit surface, and a place for holes to hide.

But the node types are **heterogeneous by necessity**: each extends a different third-party base — a Durable Object, a Worker entrypoint — chosen for what that node is *for*. Single inheritance is already spent on that base, so they cannot always also share a Lumenize base class. The shared behavior therefore cannot be *inherited*; and hand-reimplementing it in each node type guarantees drift — sooner or later a new node-shaped surface forgets a check.

## Decision

**Every Lumenize node type provides the comms + guards core — receiving calls, propagating `callContext` (identity / provenance), making continuations (`ctn()`) and sending them (`lmz.call`, `lmz.broadcast`), and the guards (`onBeforeCall` and `@mesh()`, with the passage step a scoped node runs ahead of `onBeforeCall`) — by composing one shared implementation, never reimplementing it. A new node type composes this core no matter which base class it must extend.**

> **Today's code differs.** A scoped node's passage runs inside its `onBeforeCall()`, in `apps/nebula`'s `NebulaDO`, so the core calls one guard hook where this describes a passage step ahead of it.

- **Composed, not inherited.** The core lives behind a composition seam that every node type invokes, so a node extending a third-party base gets the identical receive-and-guard path without a shared base class. *(Mechanism today, all in `lmz-api.ts`: the shared `executeEnvelope` executor and the `EnvelopeExecutorNode` interface every node type satisfies. How a type reaches it depends on its base — `LumenizeDO` mixes in `ComposedMeshDO(Base, name)`, while `LumenizeWorker` calls the executor from its own entry methods, since `WorkerEntrypoint` needs no mixin. Two routes, one executor; the commitment survives a refactor of either — cf. ADR-001.)*
- **Deliberately narrow.** The core is exactly comms + guards. `broadcast` is comms: one continuation sent to many addresses, needing nothing but `lmz.call`. Storage, alarms, lifecycle initialization, a node's own request/`fetch` handling, **and a driven container** (raw `ctx.container`) are **per-node-type capabilities**, not part of the core — a node takes only what it needs. Widening the core to include them would force every node to carry machinery it doesn't have, and collide with its base's own lifecycle. *(A container-driving node is exactly this: a `LumenizeDO` that opens `ctx.container` as a capability — **not** a separate node type or base class. We do not `extends Container`; see `containers.md`.)*
- **One gated path, selected by address not content.** The core exposes two distinct *addressed* entries — one for incoming requests, one for delivering a call's result back. **The authorization guards run on both: a scoped node's passage step, the origin→node containment check, then the node's own `onBeforeCall`**; they differ only in whether the member-level check also applies: a request must target a mesh-callable (`@mesh()`) member, while a result-delivery runs the caller's own continuation with that check off. **Member-level-check-off is not guard-off.** Which mode applies is a function of **which entry is addressed, never of attacker-influenced message content.**
  - **Hosting a Client adds no mode.** A node that hosts Clients also receives messages addressed to them: `STAR/acme.crm.tenant1/alice.9f2c41aa` arrives at the Star `acme.crm.tenant1`. It hands each to that Client's server-side half, which sends it down the socket and runs nothing on the node, so nothing runs on the node except under the mode its entry selects.
- **The guard covers the mesh path only.** A node's own `fetch()`/WebSocket surface is **outside** the shared guard — it must be secured by that node's own design (public-by-design, or its own explicit check), **never *assumed* gated.** Such a surface forgoes the mesh's identity propagation and authorization, so it is a **last resort**: add one only when the mesh genuinely can't carry the traffic, and only with dedicated security review.
  - **What may reach a node's own `fetch()`:** page traffic, under a prefix the Worker's forward writes — a container-driving DO serving its built `dist/` is the case today — and the node's own container, at the paths its library fixes. A node hosting Clients also hears a Client's WebSocket upgrade under `/gateway`, which the Worker forwards after verifying its token.
  - **An operation only our own code may invoke never does.** It travels by raw RPC to a method decorated `@rawRpc()`, through the bridge [ADR-023](023-the-mesh-boundary-is-crossed-at-a-bridge.md) describes, since `@mesh()` would open it to every caller its guard admits.
  - **A node accepts a Client's WebSocket only through the composed server-side half.** A Client's call becomes a mesh call that the half builds from the socket's verified claims, and it reaches the node through its request entry. A Client's answer to a node's call only fills the continuation that node wrote, which runs at the node's fire-back entry on the node's own chain, so the Client supplies a value and nothing else. No frame reaches the node any other way.
- **Object-capability access, not only per-method gating.** The member-level check runs at a chain's *entry op only*, so a gate — `@mesh(requireAdmin) get admin()`, or a method where the gate takes arguments — can **return a capability instance whose methods are the privileged surface**. Those methods are never an entry op, so the member-level check never sees them, and they are reachable only by first passing the gate, in one round trip: holding the returned instance *is* the authorization.
  - **Past the entry, the WALK RULES still apply.** `constructor`, `__proto__`, the four Annex-B accessors and anything resolving on `Function.prototype` are refused on every leg, at every flag setting — those are the doors JavaScript puts on every object, and no amount of careful authoring removes them. Everything else past the entry is the author's business.
  - **Spelled out because it is the less familiar of the two.** LLMs and humans both reach for per-method gating by default and would otherwise never discover this; it is sanctioned alongside that shape, not instead of it. (Worked example in `mesh.md`.)
- **JWT verified once, at the edge Worker before the upgrade; nodes enforce authorization.** The Worker verifies the token, and the Client's server-side half keeps its claims on the socket; each node enforces *scope/permission* in its guards (passage, `onBeforeCall` and `@mesh(requireDominionHere)`), never re-verifying the JWT.
- **`callContext` propagation is core, not a per-type detail.** Each node makes the propagated identity/provenance available during a call and carries it across outgoing continuations — including the node's own persistent identity, which the framework stamps on **every** first-contact entry, not just the mesh path. A message addressed to a Client a node hosts stamps nothing, since its address names the Client. *(How the context is bound differs on the client — the one documented divergence, below; identity-stamping mechanics live in `mesh.md`.)*
- **Divergence must be documented and defensible.** The lone current divergence is the client's separate path (browser/Node compat). It is a documented parallel path — to keep documented or consolidate — not a license to reimplement the core freely. Unjustified divergence is a defect.

## Alternatives considered

| Approach | Why rejected |
|---|---|
| Each node type reimplements the receive + guard logic | Drift and security holes by construction; every new surface eventually forgets a check. |
| Share the core via a common base class (inheritance only) | Breaks the instant a node must extend a third-party base; single inheritance forbids a second Lumenize base. A composition seam works across bases instead. |
| A **broad** "mesh + security" core (storage + alarms + init too) | Forces every node to carry lifecycle capabilities it doesn't need, and manufactures collisions with each base's own lifecycle hooks that the narrow scope avoids entirely. |
| A **single** receive entry with a request/response `kind` flag | Lets a sender label a fresh request as a "response" and run its chain with the member-level check off. Two *addressed* entries make the gate mode a function of the address, not attacker-influenced content. |

## Consequences

### Positive
- **Uniform secure-by-default comms** — one gated path, one place to audit.
- A new node type composes the **narrow core**, then adds only the per-type capabilities it needs (a `LumenizeWorker` takes neither storage nor alarms nor `onStart`; a container-driving `LumenizeDO` adds only raw `ctx.container` — no separate base or node type).
- Keeping the core narrow **sidesteps the base-class lifecycle collisions** a broad core would have forced us to reconcile.

### Negative / open
- **The client shares the dispatch engine but hand-rolls the receive shell** — a documented divergence justified by browser/Node compat, not a parallel stack.
  - **What it shares.** It runs the *same* continuation-dispatch engine as the server node types, including the `@mesh()` member-level check, the same structured-clone wire, the same `lmz.call`/`lmz.broadcast`/`ctn`/`callContext` surface, and its own `onBeforeCall` guard at the same point.
  - **What it can't reuse is the `executeEnvelope` receive shell.** That shell binds context via `AsyncLocalStorage`, which workerd, Node and Bun have and browsers don't, so a client, which must also run in a browser, captures context synchronously. Its results arrive the way a node's do: the server-side half on its host node writes a filled continuation down the socket as a frame only that half sends, and the client runs it at that door.
  - **So every node type composes the shared engine**, and every **server** node type composes the `executeEnvelope` shell as well. Only the client hand-rolls it, and its parallel shell is essentially irreducible: no ALS.
